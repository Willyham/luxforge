# Luxforge user guide

The Develop workspace opens JPEG and the camera recording modes listed in the bundled RAW catalog, with exact transforms, crop/straighten, persistent history and the JSON API. On a RAW photo the same Basic section sets the white balance on the sensor data, in kelvin. [Exporting](#exporting) writes the photograph on screen to a new JPEG. Locate and MCP are planned; a Rust CLI for the live editor session is specified and awaits implementation authorization ([feature status](features.md)).

JPEG Basic exposure, tone, white balance and colour controls are built, with the neutral picker, and so are the histogram and clipping inspector that share their [design](design/basic-and-histogram.md), and the Presence, Colour mixer and Vignette sections of their own [design](design/presence-mixer-vignette.md). [Presets](design/presets.md) save and apply those settings, and import Lightroom Classic presets.

[Detail](design/detail.md) provides manual capture sharpening and luminance/colour noise reduction. Its photographic quality qualification remains open; the [numerical study](design/detail-study.md) records the outstanding gates. Output sharpening for a destination size or medium is separate future export work.

RAW profiles cover 316 observed recording modes on 259 camera/phone identities, including older DSLRs, compacts, high-resolution bodies and sampled Pixel/Galaxy DNGs. The [sample manifest](../fixtures/sample-corpus.json) lists the retained qualified files. A listed camera does not imply every compression, resolution, burst or drone camera-module mode is supported. Sony A7 V Compressed HQ opens with a separate 1 GiB decoder working-space allowance; total process memory can exceed that. Nikon High Efficiency and High Efficiency★ NEF remain refused: record Lossless compressed RAW. DNG development applies supported embedded corrections in their recorded order; unknown required corrections fail explicitly. Selected iPhones and other phones without licensed samples remain unqualified, including their HEIC/ProRAW paths. A failed Open keeps the previous photo. The bundled [camera catalog](../crates/luxforge-raw/data/cameras.json) defines admission; a matching filename extension alone does not enable a camera.

An optional [extended test corpus](design/sample-corpus.md) collects samples for
a broader camera and recent flagship phone selection. That selection is a test
and acquisition target; the bundled camera catalog above still defines which
RAW files the editor opens. Phone HEIC and Apple ProRAW support remain unqualified.

## Start the editor

macOS is the primary platform. Linux has automated build and functional checks; native desktop qualification remains open. Windows support will come later, and Windows CI is disabled. See [platform status](engineering/platforms.md).

After [developer setup](engineering/development.md), start an optimized build with a catalog and an optional original:

```sh
cargo xtask develop --catalog /path/to/catalog.sqlite --open /path/to/photo.jpg
```

For repeated development builds across worktrees, the developer guide covers the
[shared compiler caching](engineering/development.md#build-caches-and-worktrees) used by agents.
The [CI workflow](engineering/development.md#ci) checks formatting and repository validity
before heavy verification, and reuses compiled dependencies across runs and corpus shards.
Developer repository checks and audits now start without compiling photo tooling;
photo and evidence commands build the tools they need through the same `cargo xtask` interface.

Omit `--catalog` to use the catalog chosen in [Settings › General](#settings-and-experiments), or the one in the platform configuration directory when none is chosen. `--data-root DIRECTORY` isolates config, data and log paths. `cargo xtask develop --debug` is a lightly optimized build with debug assertions, for debugging, and is unsuitable for timing.

Developer mode registers the test modules, the pixel proof (`luxforge.pixel`) and the controls proof (`luxforge.controls`), with their API methods, and shows them under Developer. It is a [flag](#settings-and-experiments), on by default in debug builds and off in optimized ones; turn it on in Settings › Experiments for the next launch, or pass `--developer` to force it on for one launch. Without it they are absent from both discovery and the workspace: `module.list` and `schema.list` name no test module or method, and a stored layer of one is reported unavailable rather than rendered. `--disable-module luxforge.crop` (or another built-in id) registers that module as unavailable, which keeps its stored layers readable and reports them instead of rendering without them.

`--no-gpu-render` starts the editor without its GPU stage, as on a computer whose graphics device cannot run it: every picture is drawn by the reference renderer on the CPU, which is slower, the status bar says `Reference renderer`, and `session.state` names it (see the GPU preview below). The window itself is still drawn by the graphics device. A computer whose only graphics adapter is a software one, a rasterizer on the CPU such as Mesa's lavapipe on Linux or WARP on Windows, starts the same way, with the reference renderer: drawing through the GPU stage on such an adapter was measured too slow to drag smoothly, so it is not used by default. `--software-adapter` uses it for that launch anyway; the status bar then says `Software GPU preview` or `Software GPU render`, and `session.state`'s renderer has `software: true`. `cargo xtask develop --gpu-adapters` prints the graphics adapters the editor's renderer can choose among, one JSON line each with its backend, name and device type (`Cpu` for a software rasterizer, such as Mesa's lavapipe), and exits without opening a window; `cargo xtask doctor` lists them once a release editor is built.

For agent-driven API or rendered checks on macOS, add `--background` to keep the editor from taking desktop focus. Use a separate test catalog or `--evidence-dir NEW_DIR`; background evidence runs capture the editor and exit automatically. `--hidden-window` additionally creates the window invisible: it still renders and captures through a real surface, but never appears on the desktop. Smoke and diagnostic harnesses use background, hidden launches by default on macOS. Launch normally for keyboard, mouse and native-dialog interaction.

Open references an existing supported original without copying or modifying it: it develops the file into the catalog at once, as [Developing picks](#developing-picks) describes, then prepares and shows it. JPEG input supports the existing sRGB/greyscale subset; RAW input is developed from sensor data. A JPEG whose image data is corrupt or cut short is refused with an error rather than opened with grey where the data ran out; a harmless irregularity, such as stray bytes between the file's header segments or an unknown JFIF version, does not stop it opening. Cmd+O on macOS and Ctrl+O elsewhere opens the picker, and a file dropped on the window in Develop opens the same way. EXIF orientation is applied once before any edit. The catalog stores stable identities, the source fingerprint, ordered operations and history. It is not a backup of the original photo.

The status bar at the bottom of the window starts with a sentence saying what last happened, such as "Applied Clarity +18 · entry 7", "Opened DSC_0412.NEF" or the reason an edit was refused. Anything that cannot start says why there — a draft still open, a historical state on screen ("Return to the current state before editing") or a request still running ("Waiting for the last request") — and nothing is sent. Choose the copy button beside it to copy the sentence to the clipboard; it stays visible after copying. The rest of the status bar shows how many agents are connected to the live API (the dot is green when any are), what drew the picture on screen and how long it took (`GPU render · N ms` for the picture the GPU draws at rest, `GPU preview · N ms` while a drag is drawn on the GPU — see the GPU preview below — `Exact render · N ms` for a picture the reference renderer drew on the CPU, `Approximate render · N ms` for a RAW white balance previewed on the image already developed, or `Rendering…` while a newer one is on its way), then, only while a drag is drawn on the slower CPU path for a reason that lasts, a short muted phrase saying why, such as `GPU memory full`, or, at all times while the reference renderer draws every picture, `Reference renderer` (hover it for a sentence; see the GPU preview below), and the zoom with its percentage and what it means on this display ("Fit · 18% · 2×"). The render time is the renderer's own time for that picture. At Fit, the picture is drawn at the display's size, and at zooms below 100% at the size it is shown. At 100% and larger zooms, the GPU draws the visible area at full detail, at rest and while a drag moves (below); where it cannot, the reference renderer draws the whole photograph at full detail, which takes longer, especially when a cold whole-stage estimate is needed. During a deferred GPU upload, the coherent preceding picture can remain visible and is marked updating until the new pixels draw. The whole-image histogram and counts stay dimmed until the picture you let go on has been counted. Where the reference renderer draws the picture and finishing it is expected to take more than a second, as heavy Detail on a large photograph can, a thin bar along the bottom of the photograph fills as the work completes and the status bar reads `Rendering… 42%`; the bar goes when the finished picture replaces the one on screen.

## The workspace

The window has five regions: a title bar with the workspace switch (Select and Develop, see [Select](#select)), the file name, its size and format, Open, the zoom control (Fit, 100% and the current percentage, which you can click to type another, or rest the pointer on for the zoom stops), Compare, Clipping, Undo, Redo, two panel toggles and Settings; the state panel on the left (versions, history and Performance); the photograph in the middle with a floating mode strip under it; the tools panel on the right; and a status bar. Cmd+Option+[ and Cmd+Option+] hide and show the side panels, and the canvas takes whatever remains. Panel visibility, the canvas mode, the thirds and Information overlays and the clipping overlays are session state, reported by `session.state` and settable through `workspace.set` like zoom. The panels, thirds and clipping overlays are also remembered: the next launch opens with them as you left them. So is the window's size and position, which a window closed in fullscreen leaves as it was; a remembered frame that no longer fits on its display, as after unplugging a monitor, opens centred on the main display, shrunk to fit.

Cmd+K opens the command palette. Its first entries open the tools panel: type a section's name, such as Detail, or a control's, such as Clarity, and Enter opens that section, with any group or tab holding the control, collapses every other section, scrolls the panel to it and briefly tints the control's row; the panel is shown if it was hidden. A whole-label match, such as Undo, still comes first. Below those, type to filter every module action, reset and canvas mode plus Fit, 100%, Undo, Redo, Return to current, Restore, Pointer, Thirds, Information, the panel toggles, Show or Hide performance and Settings · Experiments, then Enter or click runs the entry through the same path the control uses. Right-click any generated control and choose Copy as JSON request to put the exact `edit.<action>` request for its current values, with the current expected revision, on the clipboard; the crop draft's Apply offers its `edit.crop` request the same way.

The GPU draws the photograph wherever it can, and the reference renderer on the CPU draws the rest; there is no setting to choose. A drag — a slider, a mask's shape moved or a brush stroke — is drawn on the GPU once the editor holds the picture as it stands before the stack's adjustments, which it prepares after each edit and keeps between gestures, so a drag is usually drawn on the GPU from its first tick: the status bar then reads `GPU preview · N ms`, N being the time the editor spent preparing that frame. At Fit and at zooms below 100% that is the whole picture at the size it is shown, so panning while you drag keeps drawing on the GPU, and the first drag at a new zoom keeps the picture you had on screen for its first tick while the editor prepares the picture at that size; at 100% and larger zooms it is the visible area at full detail, with the mask overlay's coverage of that area drawn over it when it is shown, and panning past that area plans the new area at once, even while the drag holds still. RAW geometry previews preserve extended linear values through resampling before encoding the display frame. A brush stroke, or a mask's shape being moved, redraws only the part of the picture its latest change reaches, so painting or moving a mask that holds Clarity, Texture or Detail keeps pace with the pointer, with several masks too. A photograph may carry up to 16 masked Presence and Detail layers. At Fit, painting over ten or more masked Presence layers is still drawn on the GPU but no longer keeps up with every display frame. At 100% and larger zooms each masked Presence or Detail layer widens the area the GPU preview holds, so a stack of many of them can need more than it holds: a drag over such a stack is drawn on the GPU at the detail Fit shows, scaled to the view, softer than the picture you get when you let go, and the status bar says `Softer while dragging`; only if even that does not fit is it drawn by the reference renderer, more slowly, with `GPU memory full`. A tick the GPU cannot draw yet because what it draws from is still being prepared — its first tick, a program still compiling, the photograph still uploading — keeps the picture you had on screen, which the GPU's frame replaces once it is ready, and if that has not happened within half a second the reference renderer draws that tick's whole picture. A drag the GPU cannot draw — a layer it has no program for, or more than its memory holds even at the softer detail — is drawn by the reference renderer, one whole picture of your newest value at a time, which takes longer the larger the photograph and the heavier the adjustments. N is the interface's own time; the GPU's is not measured. With a clipping overlay shown, a drag drawn on the GPU marks its own clipped pixels: an approximate overlay, per pixel of the preview, while the histogram, dimmed, shows the counts of the picture the drag last drew, or the last full count when that picture carries the overlay's marks. The picture at rest is the GPU's too: after a release, a history selection, a preset, Compare or an open, the GPU draws the stack as it now stands, at Fit and below 100% first from the photograph reduced to the view's size — the same picture the drag drew, so a release changes nothing on screen — and then processed at full resolution and reduced to the view, which replaces it through a 150 ms dissolve in linear light; at 100% and larger zooms it draws the visible area at full detail. The status bar reads `GPU render · N ms`. Nothing is rendered on the CPU for such a picture: the histogram and its counts are the GPU's count of the stack at full resolution, which arrive a moment after the picture and replace the dimmed plot. The GPU's programs are prepared in the background as a photograph opens and after each edit, those of the picture on screen first, then those of a drag of each of its adjustments, then those of every other adjustment's first drag, so no later drag waits for them. Opening a photograph whose picture's programs are already prepared — any photograph after the first in a session, unless its adjustments need programs no earlier picture used — draws the GPU's picture from the start, once the photograph is on the GPU, with no CPU render. Until the picture's own are ready, for a moment usually and a second or two the first time after an update, the photograph is drawn by the reference renderer on the CPU and the status bar says `Preparing GPU render`; the GPU's picture then replaces it. After an edit, a preparation shorter than half a second leaves the picture you had on screen, marked rendering, until the GPU's picture replaces it. The preparation is listed in Performance as Preparing GPU renderer when it lasts. A pause during a drag the GPU draws renders nothing more. When a CPU frame replaces a GPU frame — a drag tick the GPU could not draw, drawn by the reference renderer, or a committed stack the GPU cannot draw at rest — it does so through the same dissolve, and the status bar names the CPU frame from its start. Any new input cancels a dissolve, a cancelled drag goes back to the picture before it with no dissolve, and nothing is redrawn once it ends. When a drag is not drawn on the GPU at full detail for a reason that lasts, the status bar says why in a short muted phrase right after the render slot, with a one-sentence tooltip; nothing is drawn on the photograph. `Softer while dragging` says the layers at this zoom need more than the GPU preview holds at full detail, so the drag is drawn on the GPU at the detail Fit shows and is sharp again when you let go; `GPU memory full` says even that needs more than the GPU preview holds (fewer masked Presence or Detail layers, or Fit, draw on the GPU); `GPU preview unavailable` says this graphics device cannot run the GPU preview for these adjustments; `Not on the GPU:` and a layer's name names a layer the GPU preview cannot draw yet; and `Preparing GPU preview` says its programs are still compiling, shown only once that has lasted half a second. The phrase appears from the first tick of such a drag and goes with the next GPU frame or when the drag settles. A reason that passes within a tick or two, such as waiting for the picture the drag starts from, says nothing. When the GPU cannot draw at all — this graphics device cannot run the GPU stage, the device was lost, or the editor was started with `--no-gpu-render` — every picture is drawn by the reference renderer on the CPU and the status bar says `Reference renderer`, at rest as well as during a drag. A drag then shows a quick picture at the size the view shows the photograph, or at the size Fit shows it at 100% and larger zooms, where it is enlarged to fill the view and softer; the status bar's render time says `Approximate render`, its message adds `Moving preview · Detail approximate` over Detail, and the histogram keeps its last count, dimmed. When you let go the reference renderer draws the photograph sharp, with its histogram. Every client's `session.state` names the same renderer as `renderer`: `{"record": "gpu", "reason": null}` while the editor draws on its GPU, and `{"record": "reference", "reason": ...}` while it cannot, the reason being `surface-pending` before it has drawn a photograph, `no-adapter` or `device-lost`; no method sets it.

On macOS, pinch with two fingers on the trackpad while the pointer is over the canvas to zoom in or out. Zoom follows the point under the pointer, starting from the displayed size at Fit and staying between 10% and 1600%; the image stays centred on an axis where it fits, and pan stops at its edges. Two-finger scrolling pans at a percentage zoom. Press F for Fit or 1 for 100%. Pinch changes only your view and creates no history entry. Native trackpad pinch on Windows and Linux remains outstanding.

### Performance

The last block of the state panel, pinned under History, is **Performance**, open on first use and then restored to your last choice; click its heading to close or open it. It shows the editor's own memory, CPU and GPU use, each with its value and a sparkline of the last minute, and the long-running work in progress: preparing an original, developing a RAW, rendering a preview, measuring a histogram or preparing the GPU renderer, once it has run for half a second, with how long it has been running. When nothing long is running it shows the last long piece of work for ten seconds after it finished, then No background work.

The catalog's own work — indexing a folder or card, reading previews, developing picks, checking and finding originals, applying a preset or exporting many photographs — has a row of its own there with **Cancel**: what it works on ("Indexing ~/Pictures"), a bar filled only as far as the work knows it has got, its own count ("312 of 612 headers read", or "48,210 of about 200,000 files" while a folder is still being listed; "working" when it can say nothing yet) and, once its pace has been steady for a couple of seconds, how long is left ("about 1 min 40 s"). The estimate goes away again when the work slows sharply or stops, so a stuck job never looks nearly done. Cancel stops the job (`job.cancel`) and its row then says it was cancelled. While any such job runs, the status bar carries the one that has run longest, with its bar and the number of jobs ("24% · 2 jobs"); click it to open this section. A job that took more than a second leaves a sentence in the status bar when it ends ("Indexed 12,408 files in ~/Pictures", "Cancelled indexing ~/Pictures"). The desktop hears of this work when it changes, a few times a second at most, and reads nothing while nothing runs.

- **Memory** is the process's memory footprint, the figure Activity Monitor's Memory column shows; on Apple silicon it includes the GPU's allocations. Hover it for the peak since launch, the resident memory and the GPU allocations.
- **CPU** is a percentage of one core, as Activity Monitor counts it, so a busy 14-core machine can read over 100%.
- **GPU** is the share of time the GPU spent on the editor's work. It is measured on macOS only; elsewhere the row shows a dash and its tooltip says why.

The section reads the same `resources.read` and `activity.list` methods any client can call, once a second, and only while it is open, the state panel (in Select, the sources panel) is shown and visibility permits presentation; closed, it costs nothing. Your open or closed choice is remembered across launches. Running jobs that support cancellation show Cancel; while its request is pending the button is disabled. A source or analysis cancel releases your window's interest, while an export or capability cancel stops that job. A refusal or a job that already ended is reported in the status bar. Show performance and Hide performance in the command palette do the same as the heading.

On macOS, minimizing Luxforge or hiding its window/app pauses Performance sampling and elapsed-time refreshes. Background work continues, including exports and catalog follow-up, and a minimized or hidden window still draws: an edit made through the API while it is hidden gets its GPU picture and histogram, so `analysis.request` answers at once. Restoring keeps your disclosure choice and starts a fresh sample history; CPU and GPU need two new samples. A visible window keeps sampling when unfocused or covered. Native visibility pausing is not yet supported on Windows/Linux.

The [measured rendering costs](specs/performance.md#isolated-rendering-kernels) distinguish rendering an already-prepared image from developing a RAW sensor image and from presenting a preview. Faster rendering can shorten the wait for an exact photograph and histogram; changing RAW white balance still needs redevelopment. A photograph passed at launch starts preparing while the desktop initializes. [Startup and RAW measurements](specs/performance.md#startup-and-raw-throughput) distinguish preparation from the time until the photograph is displayed.

### Select

Luxforge works in two steps, each a workspace. In **Select** you browse the photographs on a camera card or anywhere on disk, organized for you into events and moments, and pick the few worth developing; **Develop** brings the picks into the catalog and edits them. The catalog holds only what you develop: the files you browse stay where they are and are never written to, moved or copied ([catalog design](design/catalog.md)). Every gesture in Select is a request an agent can send too ([Browsing files and the catalog](#browsing-files-and-the-catalog) and the sections after it).

The switch at the title bar's leading edge chooses the workspace, **Select** or **Develop**, in either one; `G` in Develop also shows Select. In Select, `G` returns from the loupe to the grid. `D` always shows the existing Develop screen, matching its tab, and keeps the photograph already open there. Letters act when no text field takes the key. Switching commits, discards or pauses nothing, and each workspace keeps what it had; an open crop draft, slider drag or mask gesture is applied or cancelled first, and the status bar says so ("Apply or Cancel the crop draft before switching to Select"). Which workspace is shown is this window's own: the session does not report it.

Select's window has a title bar (the workspace switch, what you are looking at with its dates, count and cameras, **Add a folder…**, Undo and Redo of library changes, **Develop N** and the panel toggles), the sources panel on the left with Performance pinned under it, the filter bar and the grid (or the loupe) in the middle with a floating strip for Grid, Loupe, the sort and the size slider, the Info panel on the right, and the status bar, which says what last happened and counts the view, its picks and the selection.

#### Browsing cards, folders and events

The sources panel lists what you can browse:

- A search field that finds events by place, date and camera.
- **Cards**: the connected camera cards, each with how many files it held when last read. Press one to read it and show it. A card you connect while Select is open is also offered at the top of the view ("NIKON Z 8 card connected", with how many photographs it holds and how many events they make once Luxforge has read it, and "Nothing is copied or changed"): **Browse** shows it, **Not now** puts the notice away.
- **Events** by month, each named by its place or folder with its dates beside it ("Konstanz · 12–13 Sep"), with its picks over its total and a hollow dot when its files are offline. Luxforge makes events itself from the photographs' capture times and positions: a trip stays one event across its nights, and a move of more than 25 km, or a break of more than 3 hours that the positions do not show was spent in one place, starts a new one. Place names come from a table of towns and cities bundled with Luxforge; nothing is looked up online.
- **On disk**: the volumes, the startup disk first, each with a green dot while it is connected and a hollow one while it is not (a card is under Cards instead). The startup disk is included regardless of its filesystem type. Open a volume, and then any folder, with its arrow to see the folders inside it, and press a folder to read it with its subfolders and show it. Then your **indexed folders** ([below](#indexed-folders)), and **Browse a folder…** at the end, which chooses a folder the volumes do not reach.
- **Catalog**: All photographs, Recently developed, your catalog folders by year and your collections ([below](#the-catalog-in-select)), Missing originals and Removed, with how many photographs each holds, Missing originals' count in red.

Reading a card or folder lists its photographs and reads each file's header — when and where it was taken, the camera and lens, the exposure — and never its image; the status bar says so while it reads. Coming back is quick: only new and changed files are read again. A first look that takes a while shows its progress in place of the grid: the card's or folder's name, how many files it has found or headers it has read, how long is left once that is steady, **Continue in background**, which lets you browse on while it reads, and **Cancel**; it goes away by itself when the view can be drawn. While a card or folder is being read the title names it; choose another source meanwhile and the reading carries on in the status bar without replacing what you chose.

#### Indexed folders

Indexed folders are the folders whose photographs Luxforge organizes into events by itself, such as `~/Pictures` or the folder you copy cards into. **Add a folder…** in the title bar, Cmd+O in Select or the `+` beside On disk asks for a folder, and dropping a folder on the window while Select is shown adds it too. Luxforge reads it with its subfolders, saying so in the status bar and under Performance, and keeps it up to date from then on as files are added, changed or removed. Each indexed folder is listed under On disk with how many photographs its last reading found, and beside its name "listing…" while it is first read, "offline" (dimmed, with a hollow dot) while its drive is not connected, "stale" while a reading Luxforge started by itself did not finish, or why it is not followed as it changes. Press one to see its photographs. Right-click one for **Remove from indexed folders…**, which asks first: its photographs leave Events and what Luxforge read from them is forgotten, while the files, your picks and your developed photographs stay. Adding and removing are library changes like a pick: the status bar says what happened ("Added Card dumps to indexed folders · Undo ⌘Z") and Cmd+Z undoes it. A folder inside or around one already indexed, or a file, is refused, and the status bar says why.

When another client changes the library while Select is shown — an agent picks a file, say — the view is read again without a reload, the scroll kept where it was (with the active item still in view if it was), and the status bar says so ("Konstanz changed elsewhere and was read again"); what the index learns by itself, such as previews arriving or files changing on disk, is shown without a word.

#### The grid and picks

Over a card, a folder or an event the filter bar holds **All**, **Picked** with its count and **Moments without a pick**, which leaves only what is still to decide, then the **Camera** and **Kind** chips and the **Group** chip: Day › Camera › Moment (the default), Day, or None. The grid is grouped by the camera's local day, then by camera when a day has more than one, then by **moment**: frames of one camera a second or two apart are a burst, and such frames whose exposure steps — by the exposure metadata or, when that cannot say, by the previews' brightness — are a bracket. A moment is a framed row whose header names its kind, its span or exposure steps and how many of its frames are picked ("Burst · 6 frames in 1.4 s · 1 picked", "Bracket · 3 exposures · −2 · 0 · +2 EV · from metadata"), and each day heading counts its picks too. A cell shows the camera's own preview, soft from its tiny thumbnail until the preview is read.

Click selects a cell, Cmd-click adds or removes it and Shift-click extends the selection to it. The arrow keys move the active item, with Shift extending the selection; Cmd+A selects everything in view and Cmd+D nothing; `S` collapses the active burst to one cell, showing its pick or its first frame, or expands it; Tab hides and shows both side panels, and Cmd+Option+[ and ] one each. Letters act only when no text field has focus. The Info panel shows the active file's Pick band ("Pick", or "Picked for Develop" and what that means), its moment (burst or bracket, why, its frames) and its metadata, or how many are selected.

`P`, or the Pick band, picks the selected files, or clears them when every one is shown picked: the accent check appears on each, and the status bar says what happened ("Picked DSC_0412.NEF · Undo ⌘Z"). A bracket's header offers **Pick all 3**, which picks its frames together. There are no stars, flags or ratings: a frame is picked or not. A pick is kept in the catalog until you develop or clear it, so a long session survives a restart. Cmd+Z undoes your last pick or clear in Select, and Shift+Cmd+Z redoes it, as do Undo and Redo in the title bar; they undo only what this window did, never an agent's picks, and "Nothing to undo" means there is nothing of yours left. When an item changed since, the undo is refused and the status bar names it ("Could not undo: DSC_0412.NEF changed since"). In Develop, Cmd+Z stays the photograph's history. A pick an agent makes appears as the accent check on its cell and in the counts.

Every change of source, filter, sort or grouping asks the catalog owner for the whole view with `browse.view`, every selection is `browse.select`, a pick is `pick.set` of your selection and an undo `library.undo`: the same requests an agent sends, each pick and undo recorded in the journal of library changes ([Picks and library changes](#picks-and-library-changes)).

#### The loupe

`Space` or `E` (or the strip's Loupe) shows the active frame fitted to the screen; with nothing active it opens on the view's first frame, and `Esc` goes back to the grid on the frame the loupe left. The bar over it names the moment ("Moment 4 of 37 · burst", or the file's name for a single frame), the frame's place and its time after the moment's first frame ("Frame 3 of 6 · +0.52 s"), its exposure, and what the picture is and its size: "Camera preview · 2560 × 1707" for a file's largest embedded preview (at most 2560 px), "Preview" for a developed photograph's rendered 2048 px tier, with "approximate" when the render approximates and "reading full size…" while a smaller preview stands in for the one being read. Under it are the moment's frames, numbered, with the pick check on a picked one; click one to show it, or a chevron for the moment either side. Each is its grid preview: a file's camera preview, or a developed photograph's rendered preview, its camera preview standing in until the photograph is first rendered.

- `←` `→` step through the view's frames, across moments; they repeat while held.
- `↑` `↓` go to the first frame of the previous or next moment; a single frame counts as a moment of its own, so every frame is reached.
- `1`–`9` jump to that frame of a burst or bracket.
- `Z` turns the 100% focus check on or off: a box on the photograph follows the pointer (the middle while the pointer is elsewhere), and an inset at its lower right shows the rectangle under it at 100%, one of the photograph's pixels to one of the screen's. It is the camera's own full-size preview, labelled "100% · Focus check under the pointer", or, where the camera's preview is smaller than the sensor, a neutral Luxforge development of that frame, labelled "100% · Luxforge development"; a first development can take a second or more.
- `C` shows up to four frames of the moment side by side at one zoom, the active one outlined; `←` `→` move through them. A single frame has nothing to compare, and the status bar says so.
- `P` picks or clears the frame, as in the grid; picking a frame of a burst moves on to the next moment's first frame, since one frame of a burst is usually the one.
- `Tab` hides the side panels, as in the grid.

The loupe reads the frames ahead in the direction you are moving, and the next moment's first frame, while you look, so the next frame is usually on screen in the frame after the key; the status bar says "next frames ready" once they are. Its decoded frames are held within 256 MiB. Every step is the `browse.select` an agent would send, and `Z` is `preview.region`.

#### Developing picks in Select

**Develop N** at the right of the title bar (Cmd+Return), over a view of files with picks, asks where the picks go before anything changes, in a small confirmation under the button:

- **Into the catalog folder**: the picks' event's catalog folder. For an event developed for the first time it is a new folder named after it ("Konstanz · Sep 2026"), its name selected, so Return accepts it and typing names it. Picks from an event you developed before go into the folder that Develop made. **Or add to an existing folder** lists every catalog folder; choose one instead, or type a name to go back to a new folder. Picks from several events each have a row of their own, with how many picks each holds.
- **Picks on a card**: the confirmation says so. When the card's files were copied into an indexed folder, the copies are used once their bytes are checked to be the same, and **Use the copies in indexed folders** turns that off; the rest are developed from the card, which the catalog then points at. Picks whose drive is not connected stay picked.
- Escape (or Cancel, or Develop N again) closes it, and nothing changes. **Develop** (Return) develops them: Develop N shows its progress while it reads them, and Develop then opens on the first photograph, with every photograph it developed in the filmstrip. The status bar says how many it developed and names the first it could not. A Develop you cancel (from its row under Performance) or that fails keeps what it had already brought in.

Pick a frame with `P`, then use **Develop N** (Cmd+Return) to open the confirmation. In a catalog view — All photographs, Recently developed, a catalog folder or a collection — a double-click opens the photograph in Develop, with the view's photographs as its development set. `D` only switches to the existing Develop screen.

#### The development set

Develop opened on developed picks, or from a catalog view, shows a **filmstrip** under the photograph, between the side panels: the photographs you opened it with, each by its preview, the one you are editing outlined, and its place in the set at the right ("3 of 18"). `←` and `→` move to the previous or next photograph (held, they keep moving), as do the chevrons, and a click on a cell goes to that photograph. Its preview appears at once — the status bar says "Showing DSC_0412.JPG · cached preview while the original prepares" and "Cached preview" where it gives the render's time, "approximate" when the preview is — while the original is read; the controls come back once it is, and the exact render replaces the preview. Luxforge decodes the previews of the photographs either side of the one you are on while you edit, so the next one is usually on screen in the frame after the key; it never prepares their originals ahead. Moving waits while a slider, crop or mask gesture is open: apply or cancel it first, as the status bar says. Cmd+Option+F hides and shows the filmstrip. A file opened with Open has no set and no filmstrip.

#### The catalog in Select

The catalog holds the photographs you developed, each in exactly one **catalog folder** — the catalog's own organization, made from the photograph's event when you developed it, and never a folder on disk — and in any number of collections.

Under **Catalog**, the folders your developed photographs live in are listed by year, newest first: a folder under the year of the earliest photograph in it or its subfolders, with how many photographs they hold (a folder of undated photographs under Undated, an empty one under Empty). Open a year, or a folder that holds folders, with its arrow. Your collections follow, a group opening to what it holds. Press a folder or a collection to see its photographs, newest first; a smart collection shows what its saved search finds, in the order it was saved with, and the title bar names what you are looking at.

Right-click a folder for **Rename…** (type the name and press Return; Escape leaves it as it was), **New folder inside…**, **Move to…** (into another folder, or to the top level), **Merge into…** (its photographs and folders go into the other folder, and it is gone) and **Delete folder**, which only an empty folder offers. The `+` in the Catalog heading makes a folder, a collection or a collection group; right-click a collection to rename or delete it (a group only once it is empty). A name already used beside it is refused, and the status bar says so. Nothing on disk changes when folders and collections do.

Over the catalog the filter bar holds a search field (Cmd+F; it finds file names, places, cameras and lenses), **Metadata**, **Kind**, **Edited** (edited or not edited, cleared with its ✕) and, in the accent with its ✕, each metadata condition you have set; at its right, how many photographs are shown of how many the folder or collection holds ("9 of 55"). **Metadata** opens four columns — **Date** by year and month, **Place**, **Camera** and **Lens** — each value with how many photographs it would show given your other conditions; press one to narrow the view to it, and press it again, or All, to clear it. The strip's sort offers capture time (newest first), date developed, file name and last edited. **Save as smart collection…** saves exactly what is shown — where it is from, every condition and the sort — under the name you type.

Select one photograph and the Info panel shows its preview, **Organize** (its catalog folder and its collections), its metadata and whether it has been edited. Select several and it shows the first five previews and how many are selected; the folders they are in and the collections they belong to, each saying how many of them it holds when not all do ("2 of 5"); when they were taken, where, with which cameras, their kinds and whether their originals are where they were; and how many are edited. **Move to…** moves them into another folder, **+ Add to…** adds them to a collection, and pressing a collection's chip removes them from it or adds the rest. Each of these is one change that Cmd+Z undoes, like a pick, and the status bar says what it did ("Added 5 to Print order · Undo ⌘Z"). A cell whose preview was made through an approximate proxy says "approximate" under it, as the loupe does.

#### Presets and exports of many photographs

The Info panel's **Develop** band applies a preset to the selected photographs, or exports them. **Apply preset…** lists your library's presets, as Develop's Presets section keeps them; choose one and each photograph gets its own history entry, `Preset: Warm`, exactly as applying it in Develop would. **Export 5…** asks for a folder and writes each photograph's current edit into it as the title bar's Export does, as `<name>-edited.jpg` or the next free name, never replacing a file. While it works the band says how far it has got ("Applying Warm · 3 of 5"); it is also in the status bar and the Performance section, where Cancel stops it after the photograph in hand. When it ends the status bar says what it did ("Applied Warm to 5 photographs · 1 left out"), and **Report**, beside it and in the band, lists every photograph left out and why — a draft open on it in Develop, already like that, an original that is not there — and those that took only some of the preset's settings, such as a RAW development on a JPEG. Nothing is skipped silently. These are not library changes: Cmd+Z in Select does not undo them, and each photograph's own history does. One batch runs at a time.

#### Removing from the catalog

**Remove from catalog…**, at the foot of the Info panel, or Delete over a catalog view, asks first how many photographs you are removing, then moves them to **Removed**: they leave every other view and count, and keep their edits, history, folder and collections. Their files stay on disk. Cmd+Z puts them back. In Removed the button is **Put back**, which returns the selected photographs as they were, and the filter bar offers **Empty Removed…**, which, after asking, deletes every photograph in Removed from the catalog with its edits and history; the files stay on disk, and nothing undoes it.

#### Sending a photograph back

Changed your mind about a photograph you developed but never edited? **Send back**, in the Info panel above Remove from catalog… or when you right-click it in the grid, takes it out of the catalog and picks its file again, so it is back among your picks in its event, ready to develop later or to clear. It works for several selected photographs at once, and the status bar says what happened ("Sent back DSC_0412.JPG · its file is picked again"). A photograph you have edited is never sent back: the button is greyed with the reason when the Info panel knows it is edited, and otherwise the status bar says why it was refused (it is in a collection, or has a named version, or its original is not where the catalog looks); such a photograph leaves the catalog only through Remove from catalog…. A photograph sent back is brought back by developing its file again: Cmd+Z does not undo a send-back, and says so. Nothing on disk changes.

Right-clicking a photograph in a catalog view selects it, unless it is already selected, and opens a menu with **Send back** and **Remove from catalog…** (Put back over Removed).

#### Missing originals

When you have moved, renamed or reorganized originals, or unplugged the drive they are on, choose **Missing originals** under Catalog. It lists every photograph whose original was last found missing, offline or replaced, grouped by the folder on disk each was developed from, with how many, the catalog folders they are in now and why ("Photos SSD is not connected: connect it, or find the files elsewhere", "the folder is gone from Macintosh HD"). A drive that is merely unplugged needs nothing but the drive.

1. **Find in a folder…** on a group asks for the folder to search, such as the drive or folder you moved the files to. Luxforge looks there, with its subfolders, for each photograph's file by name and size, then reads each candidate to check it is the same photograph. Each row fills in as it is checked: **Found, same bytes** and where; **Different bytes at the same name**, another picture that is left alone; **2 files with the same bytes**, with **Choose…** to pick the copy to use; **Not found**; or **Another photograph uses this file**. One search runs at a time, and **Stop search** in the bar at the foot stops it and changes nothing.
2. The filters over the list show only what was **Found**, what **Needs you** (different bytes, copies to choose between, files another photograph uses) or what was **Not found**. Selecting a row shows, on the right, where the original was, where it was found, what the check found, its catalog folder and its edits.
3. **Relink N** points every found photograph, and every copy you chose, at its file, in one step that Cmd+Z in Select undoes. Nothing changes until you press it: searching, choosing and stopping change nothing. A relinked photograph keeps its catalog folder, collections, edits and history; only where the catalog looks for its file changes.
4. For a photograph the search could not find, **Locate…** on its row (or **Locate a different file…** on the right) lets you pick its file anywhere, under any name; Luxforge reads it and relinks the photograph only if its bytes are the original's.

In Develop, a photograph whose original is not where the catalog looks shows **Original not found** on the canvas, saying why, with **Locate original…**: pick the file, and once its bytes are checked the photograph is pointed at it and opened again. A file of other bytes changes nothing, and the status bar says why.

#### Long-running work

Reading a card or folder, reading previews, developing picks, checking and searching for originals, and applying a preset to or exporting many photographs run in the background. Each is a row with **Cancel** in the Performance section under the sources panel, and the one that has run longest is in the status bar with its bar; click it to open the section ([Performance](#performance)). Only a first look at a card or folder, which has nothing to show yet, shows its progress in the view, and you can send it to the background.

#### Not in Select yet

Previews in Missing originals' rows, dragging photographs onto a folder (Move to… does it), moving a collection into another group and changing a smart collection's search (`collection.move` and `collection.update-smart` over the API), Locate original… when an export is refused, and narrowing the Metadata browser to photographs with no date, place, lens or known camera, which it lists with their counts but cannot select.

## Edit and inspect

The tools panel is generated from registered modules. Each module is a band you click to open or close, with its hint while closed and its reset while open; groups inside it are separated by a rule that ends in their Original or Custom caption and their reset. A section whose controls form a single group, such as Presence or Vignette, shows them directly under its band with no group rule. Only Basic starts open, so every section's band fits on screen under it. Declared resets are offered, and an unavailable section shows its reason on its band. Every control reflects the displayed history entry, including edits made by another API client. Historical previews keep the controls visible and disabled.

Numbers use a slider, a field, or a stepper. A slider's rail may have a narrower soft range than typing allows; an over-range mark keeps values outside the rail visible. Click a value to type and press Enter to commit; leaving the field commits nothing, and invalid text remains editable with its range message. Drag values use the declared step and display precision. Double-click a label or slider rail to reset it: to its default, unless its control declares a reset of its own, as Temperature and Tint do on a RAW photo (they return to As shot). Arrows step, Shift steps ×10 and Option uses the fine step (with extra decimals when needed to show it); Iced sliders receive arrows only while the pointer is over the rail. Scrolling the panel never changes a value.

Toggles commit on click or Space. Choices use segments, chips or a menu and commit on selection. Colours use RGB fields or a swatch that opens an HSV plane, hue rail, RGB fields and hex entry. Curves show the module's sampled curve, its points and, when more than one channel is declared, a channel switch; the plot is square and fills the panel's width. Click a point to select it and drag it to move it; a drag starts only once the pointer has moved a few pixels, so a click never moves a point. Click anywhere else on the plot to add a point: on or next to the drawn curve it lands exactly on the curve, elsewhere at the pointer. Double-click a point, or press Delete, to remove it; a double-click on empty plot adds one point and leaves it. The new point is selected after an add, and nothing is after a remove. The first and last points move but are not removed from the editor ("The end points move but are not removed"), and a curve's point limits are reported in the status bar, for example "Curve holds at most 8 points" or "Curve needs at least 2 points". The hint under the plot says so when points can be added and removed. The **Points** row under the plot shows how many points the curve has and holds (`4 of 16`); open it for the numeric list, where each Enter commits one coordinate. The list starts closed and stays as you left it while the window is open; opening it changes nothing, and closing it discards any coordinate you typed but did not enter. Changing channels changes only the view. A curve's samples are asked for only while it is on screen: in an expanded section, an open group and, in a tabbed section, the selected tab. A module's canvas picker button enters its picking mode and stays lit while selected; clicking it again returns to the pointer.

Slider, stepper, colour picker and curve gestures whose field is a whole request (a patch action's field or an action's only parameter) open one draft, preview each new value as soon as the previous one has answered, and commit once on release. Escape cancels the gesture. Fields commit on Enter; toggles, choices and action buttons commit once. Tab follows the generated control order. Right-click any generated control to inspect its action/parameter and copy the JSON request with the current revision.

The Controls proof in developer mode demonstrates this vocabulary without changing photo pixels. Its edits still create normal history entries; `edit.set-controls` changes one field and `edit.reset-controls` restores the defaults. Text and 2D pad controls are deferred.

Colour grading is [planned for the Colour mixer](design/colour-grading.md), alongside its existing eight-range HSL controls. Tonal/Global wheels, Blending and Balance are not available yet.

### Settings and experiments

The gear at the end of the title bar or Cmd+, (Ctrl+, elsewhere) opens Settings over the workspace at its **General** tab; the palette's Settings · General, Settings · Appearance and Settings · Experiments open it at any tab. General holds your preferences, each saved as you change it, outside any catalog:

- **Auto collapse history**, on by default, keeps one history entry for a run of edits of the same control ([History](#history)).
- **Starting look for new RAW photos**, Standard by default, is the [look](#look) a RAW photo starts from when you bring it in: Standard, Luxforge's own, or Neutral, the bare development. It is part of the photo's Original, so the catalog's previews, a batch export and Before all show it. It affects photos brought in from then on, never one already in the catalog.
- **Correct lens distortion on new RAW photos**, on by default, applies a new RAW photo's detected lens profile as its first history entry ([Lens correction](#lens-correction-and-perspective)). Turned off, the Lens section offers the profile with Apply instead. It affects photos first opened from then on, never one you have already edited or that already has its lens entry.
- **Mask overlay colour**, Green or White, is the tint a mask overlay is drawn in; the Masks panel's colour choice is the same setting.
- **Canvas background** is the colour around the photograph: Theme (the default), the theme's own neutral surround; Dark; Black; or Grey, an 18% grey for judging tone the way a print is judged. Dark, Black and Grey stay the same in every theme.
- **Interface size**, 100%, 110%, 125% or 150%, scales the whole interface at once. The window keeps its size, and at 100% zoom the photograph is still one pixel per display pixel.
- **Catalog** shows the catalog this launch uses. **Choose Folder…** picks the folder whose `catalog.sqlite` Luxforge opens at the next launch, creating it there if the folder holds none, and **Use Default** goes back to the configuration directory's. Your current catalog stays where it is: nothing is moved or copied, so a catalog you want to take with you is moved by hand while Luxforge is closed, with its `catalog.sqlite-wal` file if there is one. Until you relaunch the row says "Relaunch to use …"; a launch with `--catalog` says so. If the chosen folder is missing at launch, as with an unplugged drive, Luxforge opens the default catalog, says "Catalog folder not found" in the status bar and on the row, and opens the chosen one again at the next launch that finds it.

Any client reads and changes every preference with `preferences.read` and `preferences.set`: `auto_collapse_history`, `auto_lens_profile`, `raw_look` (`standard`, `neutral`), `mask_overlay_colour` (`green`, `white`), `canvas_background` (`theme`, `dark`, `black`, `grey`), `theme` (a theme id, or `null` for Luxforge Dark), `interface_size` (`100`, `110`, `125`, `150`) and `catalog` (an absolute catalog path), and the remembered `workspace`, `brush`, `window` and `export_folder`, with `null` resetting any of them to its default. A bad value is refused by name and nothing is written. Another client's change to a General preference reaches an open Settings sheet, and the theme, canvas background, interface size and mask overlay colour change at once. The **Experiments** tab lists the feature flags that gate unfinished features and experiments: each has a switch, a set of choices or a number field (type a value and press Enter). A change is saved as you make it; Reset returns a flag you changed to its default, which follows later builds. Experiments never change how a photo renders or exports. A flag that applies on the next launch says so, and says "Relaunch to apply" once its next value differs from this launch's; one forced from the command line names the switch, such as "On for this launch: --developer". A saved value that this build does not recognise, or that no longer fits its flag, is kept and reported rather than discarded. Escape, Done or a click outside closes Settings.

The **Appearance** tab chooses the interface's colours. **Luxforge Dark**, the default, comes first, then six themes built in from [Omarchy](https://github.com/omacom/omarchy) (Tokyo Night, Catppuccin, Catppuccin Latte, Gruvbox, Nord and Everforest), then the themes you imported. Each row shows the theme's surround, background, surface, text and accent, whether it is dark or light, and where it came from; click a row to use it at once, everywhere, including the Settings sheet itself. A theme only changes the interface, never a photo, its render, its histogram or an export, and the canvas around the photograph stays a neutral grey in every theme. The clipping, mask overlay and histogram colours stay the same in every theme. **Import theme file…** adds a Luxforge theme (`.lftheme`). **Import Omarchy theme…** takes an Omarchy theme folder, or a folder of them such as Omarchy's own `themes` directory, and reads only its `colors.toml`, `alacritty.toml` and `light.mode`; a theme whose name is already taken is listed and left as it was, and one that cannot be read says why. To keep every imported theme readable, Luxforge may darken or lighten its text or accent just enough; such a theme shows **Adjusted**, and its row's menu (**⋯**, or a right-click) copies the import report that says what moved. The same menu exports a theme as a `.lftheme` file and deletes an imported one; choose another theme before deleting the one in use. The palette's **Theme: name** entries switch theme too. If the theme you chose cannot be found, Luxforge shows Luxforge Dark, says why in the status bar, and keeps your choice. Agents and scripts list, read, import, export and delete themes with `theme.list`, `theme.read`, `theme.inspect`, `theme.import`, `theme.export` and `theme.delete`, and choose one with `preferences.set {theme}`.

Flags are yours, outside any catalog, in the application configuration directory beside the Performance preference. Any client reads and changes them with `flags.list` and `flags.set {flag, value}` (`null` resets), and an open Settings sheet follows another client's change. Developer mode is the one product flag today; developer mode also lists two proof flags, Proof choice and Proof number, which change nothing.

### Presets

Presets follows Crop in the tools panel, collapsed until you open it. A preset is a named set of Basic, Tone curve, Detail, Presence, Colour mixer and Vignette settings, and a RAW photo's white balance. Click one to apply it: the settings it holds replace the photo's values for those settings, every setting it does not hold keeps its value, and the change is one history entry, "Preset: Soft film", which Undo reverses as a whole. Applying a preset that changes nothing adds no entry. A preset may hold settings for another kind of photo: a RAW white balance does not apply to a JPEG, and Basic's relative Temperature and Tint do not apply to a RAW photo, whose white balance is its development's. Those are skipped, the rest is applied, and the status bar says how many were left out, for example "1 setting does not apply to a RAW photo"; a preset with nothing that applies adds no entry and says so. Presets never hold transforms or crop, which belong to one photograph.

Choose + to save the displayed entry's settings as a preset. Give it a name and a group (User presets unless you type another), and tick the groups of settings it should hold. Every group starts ticked except White balance, because white balance usually belongs to one photo; tick it to include it. On a RAW photo, White balance saves the development's white balance: As shot is saved as As shot, so the preset applies each photo's own camera white balance, and a custom or picked one as its Temperature and Tint in kelvin. A preset saves every value of the groups you tick, including those at their defaults, so applying it resets them. Names are unique within a group, ignoring case.

With a photo open, choose Import to add a preset file: a Lightroom Classic develop preset (`.xmp`), a legacy Lightroom template (`.lrtemplate`) or a Luxforge preset (`.lfpreset`), up to 1 MiB. The status bar reports how many of the file's settings were carried over and how many were not; Copy copies the message. Lightroom settings are carried over as values on the Luxforge controls with the same name, range and direction, such as Exposure, Contrast, Clarity, the colour mixer and the post-crop vignette. Lightroom's point tone curve carries over to the Tone curve as the same points, rescaled from Lightroom's 0–255 to 0–1; Lightroom applies that curve to each colour channel and Luxforge to luminance, so the tonal shape carries over and the colours are Luxforge's own. The numbers transfer, but Luxforge's processing is its own, so an imported preset looks similar, not identical. A preset whose settings could not all be carried over shows **Partial**; its tooltip gives the counts, and right-click › Copy import report gives every setting with the reason. Luxforge does not carry over:

- tools it does not have: per-channel (red, green and blue) and parametric tone curves, colour grading, sharpening, noise reduction, grain, lens corrections, profiles, masks and crop;
- a point tone curve with more than 16 points, or whose output ever falls as its input rises (Luxforge's Tone curve only rises or stays level), or that the preset switches off;
- Lightroom's Auto and named white balances, and a Kelvin and tint pair outside 2000–12000 K or ±100 once converted;
- values outside Luxforge's ranges, which are never clamped;
- presets from Lightroom's 2003 and 2010 processes.

Lightroom's RAW Temperature and Tint are converted together to Luxforge's kelvin and tint through the white they name, and apply only to RAW photos; this carries the value, not Adobe's rendering of it. Its relative Temperature and Tint for JPEGs carry over to Basic's. Settings at their neutral value, such as grain at 0, lose nothing and are listed separately. Lightroom profiles and files with nothing Luxforge can apply are refused. The imported file is kept in the catalog, so nothing in it is lost.

Right-click a preset to delete it or to export it as a `.lfpreset` file that another Luxforge catalog can import. Cmd+K lists "Apply preset: <name>" for every preset. Presets live in the catalog beside history, so a new catalog starts with none.

### Look

On a RAW photo the **Look** section sits above Basic. A look turns the RAW development, which is deliberately neutral and flat, into a finished picture, as a camera does for its own JPEG: it brightens the midtones, adds contrast and colour, and rolls bright highlights off smoothly to white instead of clipping them. **Standard**, Luxforge's own look, is where every new RAW photo starts unless Settings › General says otherwise; its brightness, contrast and colour were chosen to sit on the median of about a hundred cameras' own JPEGs. **Neutral** is the bare development. **Amount**, 0 to 200, scales the look: 0 is the development, 100 the look, and above 100 strengthens it; it drafts while you drag. Double-click Amount or use the section's reset to return to Standard at 100. A JPEG has no Look section: its look is already in its pixels.

The look acts after Basic and before the Tone curve. So Exposure, Highlights and Whites work on the photograph's full range and push bright areas into the look's soft roll-off rather than a hard clip, and the Tone curve shapes the finished picture. Standard counts as unedited, so its band shows no dot until you choose Neutral or change Amount. Photos already in your catalog before looks existed keep the bare development until you choose Standard. Looks are not part of presets.

### Basic

Basic follows Presets in the tools panel, and on a RAW photo the Look section, in three groups.

**White balance** is Temperature and Tint, each −100 to +100 in whole steps. Positive temperature warms the photograph and negative cools it; positive tint is magenta and negative is green. They correct the rendering the JPEG already has — they are not the camera's Kelvin value, which a JPEG does not carry and nothing here recovers. **As shot** returns both to zero, the file's own rendering. The group header reads **Original** while both are zero and **Custom** once either is not, and every group reads its own state the same way. On a RAW photo the same controls, in the same places, set the development's white balance in kelvin instead ([RAW development](#raw-development)); inside a mask they are always this relative correction.

**Tone** is Exposure, Contrast, Highlights, Shadows, Whites and Blacks. Exposure runs from −5.00 to +5.00 EV in hundredths and multiplies the photograph's linear-light channels by `2^EV`; on a RAW photo it is the same control, applied to the developed image. The other five run −100 to +100 in whole steps and compose one global luminance curve: Whites and Blacks move the endpoints, Highlights and Shadows reshape the bright and dark ranges, and Contrast separates the midtones about a fixed pivot. Being a global curve, lifting deep shadows loses some local contrast; an edge-aware stage is a later proposal, not a missing setting.

**Colour** is Vibrance and Saturation, each −100 to +100 in whole steps. Saturation scales colour intensity uniformly and −100 is exact neutral grayscale; Vibrance raises near-neutral colour more than colour that is already strong, with less gain in a skin-like hue band — a colour heuristic, not face or skin detection.

Whatever order you touch them in, they are evaluated in a fixed one: white balance, then exposure, then Tone, then Vibrance, then Saturation. All of it is one layer in the recipe, placed before the quarter-turns and the crop the first time a value leaves zero, and updated in place ever after.

Dragging Exposure previews live. The drag opens a draft, the canvas keeps up with it while you move, and the status bar says which control you are drafting; nothing is written until you let go. Release commits the whole gesture as one history entry, labelled with the value you landed on — "Exposure +1.00 EV" — which is the value the slider was showing, not a longer number behind it. A drag that ends where it started commits nothing at all. Press Escape to discard a drag and put the slider and the photograph back to where they were. Holding an arrow key over the slider's rail steps it and commits once when you let the key go; the arrow keys reach the slider only while the pointer is over that rail. Clicking the value and typing a number commits that one value when you press Enter, with no draft at all.

If another client commits while you are dragging, the Changed elsewhere card appears over the canvas and your drag is kept, not thrown away. Discard drops it; Reapply rebases it on the new state, keeping the value you had chosen and putting your preview back over it. Until you choose, the drag will not commit.

Each group header has its own reset, which returns that group's fields to zero as one entry — "Reset White balance", "Reset Tone", "Reset Colour" — and leaves the other groups exactly as they were. The section header's reset returns the whole module, "Reset Basic". Double-clicking one control's label, or the slider itself, resets that one field. All of them keep the Basic layer with its identity and a neutral payload, so a reset is an edit you can undo, not a deletion, and a reset of something already neutral does nothing at all. Only one draft is open at a time — a slider drag, a mask gesture or a crop draft: starting another while one is open is refused, and so is a button, toggle, choice or typed value that would commit around it, a Masks panel command, or Undo, Redo or Restore, from the title bar, a shortcut, the palette or the history panel; the title bar shows Undo and Redo, and the history panel Restore, disabled while it is open. Nothing is sent, and the status bar says what the open one needs. An existing brush between strokes can be put down by another allowed gesture. New mask creation owns the controls from arming until its first successful stroke or cancellation, and an Add or Edit gradient until Apply or Cancel; scrolling a zoomed view and moving focus stay available.

#### Activity and resources

Two read-only methods report what the editor is doing and what it costs. Neither needs an asset, takes parameters, changes anything or emits an event.

`activity.list` answers the host's activity board: `active`, the work running now, oldest first, and `recent`, up to 16 pieces of work that ran for at least 250 ms, newest first, so a drag's many short previews never push a RAW development out. Each entry has an `id`, a stable `kind`, a `label` for people and `elapsed_ms` (running) or `outcome` (`completed`, `cancelled` or `failed`), `duration_ms` and `ended_ms_ago` (recent), plus `detail` (a file name), `asset_id`, `phase` and `job_id` when known. The kinds today are `source.prepare` (Preparing original), `source.develop` (Developing RAW), `preview.render` (Rendering preview, in phase `proxy` and then `exact`) `analysis.histogram` (Measuring histogram), `gpu.warm` (Preparing GPU renderer, the desktop compiling its GPU programs in the background) and `export` (Exporting JPEG, with the destination's file name as `detail`, in phase `rendering`, then `encoding` and `writing`), with a module's capability jobs beside them. An entry's `job_id` is the job `job.read` answers, and the two agree about its status. `sequence` changes exactly when the contents change, so a poller can skip an unchanged answer, and `untracked` counts work that began while 64 entries were already active.

```json
{"id":"work","method":"activity.list","params":{}}
```

```json
{"id":"work","sequence":9,"result":{"sequence":812,"active":[{"id":41,"kind":"source.develop","label":"Developing RAW","detail":"DSC_0412.NEF","asset_id":"asset-…","job_id":"job-…","elapsed_ms":1204}],"recent":[],"untracked":0}}
```

`resources.read` returns the counters the operating system keeps for the editor process. They are cumulative, so a rate needs two reads: CPU percent of one core is `100 × Δcpu.time_ns / Δmonotonic_ns`, as Activity Monitor counts it, and GPU percent is the same over `gpu.time_ns`. `monotonic_ns` is only meaningful as a difference. `memory` is `{kind, bytes, peak_bytes, resident_bytes}`, where `kind` is `footprint` on macOS (Activity Monitor's Memory column, which on unified memory includes GPU allocations), `resident` on Linux and `private` on Windows. `gpu` is `{time_ns, allocated_bytes, unified_memory}` on macOS; GPU allocations are reported only by the desktop, because reading them would create a GPU device in a headless process. `budgets` gives the colour-scratch and spatial working-memory targets with their bytes in use and high-water marks. A counter the platform cannot give is left out and named, with its reason, under its object's `unavailable`:

```json
{"id":"cost","method":"resources.read","params":{}}
```

```json
{"id":"cost","sequence":9,"result":{"monotonic_ns":167,"cpu":{"time_ns":6377125,"logical_cpus":14},"memory":{"kind":"footprint","bytes":2392448,"peak_bytes":2392448,"resident_bytes":9191424},"gpu":{"unavailable":{"time_ns":"no GPU client in this process","allocated_bytes":"no GPU presenter in this process"}},"budgets":{"colour_scratch":{"target_bytes":67108864,"in_use_bytes":0,"peak_bytes":0},"spatial":{"target_bytes":268435456,"in_use_bytes":0,"peak_bytes":0}}}}
```

GPU time and allocations are reported on macOS only; on Linux and Windows they are unavailable with that reason.

### The neutral picker

Click Neutral picker in the White balance group, or press `W`, and click something in the photograph that should be neutral grey; the pointer is a crosshair while the picker is selected. Luxforge reads a 5 × 5 patch of pixels around where you clicked, works out the Temperature and Tint that make that patch neutral, and applies them as one edit. It reads the patch as the image is *before* Basic's own white balance, so clicking the same spot twice answers the same way however strong a correction is already set. A pick that applies puts the picker away, so press `W` again to try another spot; a refused pick leaves it selected. Clicking Neutral picker again, `V`, Escape or another mode also leaves it, and leaving commits nothing. On a RAW photo the same button and `W` pick from the sensor instead ([RAW development](#raw-development)). With a mask open in the Masks panel, the picker sets that mask's own Temperature and Tint, reading the patch as the mask's adjustments receive it, and leaving it, by a pick or otherwise, returns to the Masks panel.

Some patches cannot answer, and the status bar says which:

| Reason | What it means |
| --- | --- |
| `clipped:` | A sampled pixel is at 0 or 255, so the patch has no usable colour left |
| `near-black:` | The patch is too dark for its colour to be trusted |
| `out-of-range:` | The correction this patch needs is outside what Temperature and Tint can express; it is reported rather than quietly clamped |
| `outside the stage:` | The point is not inside the image |

A refusal commits nothing and changes nothing on screen. The picker is refused, with the reason, while a slider drag, a mask gesture or a crop draft is open: finish or discard that first.

Pixel proof lives in the Developer section in developer mode. It accepts integer x/y coordinates and RGB values from 0 to 255. Coordinates are content coordinates: the photograph after EXIF orientation, with a top-left origin, x right and y down, regardless of any crop or rotation applied afterwards. Clicking the photo at Fit or any zoom fills X and Y with the content pixel shown under the pointer without committing anything, so a click in the corner of a cropped view names the pixel of the photograph that is drawn there. Changing the crop later never moves an edit; it only changes what is visible. Apply pixel creates one layer and one attributed history action when the resulting pixel changes. Invalid, out-of-bounds and same-value requests add nothing.

Exact transforms are Rotate left, Rotate right, Mirror horizontal and Flip vertical, the four icon buttons at the top of **Crop, transform, straighten**; hover one for its name. Quarter-turns swap dimensions. Repeated transforms fold into one orientation layer, so four Rotate right actions leave one neutral layer and four history actions to undo through. That layer always sits ahead of the crop: a transform made after you crop turns or reflects the crop with the photograph, as one history entry, so the picture is the cropped one turned, and cropping again shows the turned photograph. Through a straightened crop the frame lands on the turned photograph's own pixel grid, so it can move by up to half a pixel. Pixel edits always sit before the transforms and crop, so they move with the image.

Fit shows the whole image, centred with a margin of canvas around it, rendered at the size your display can show. At 100%, one source pixel maps to one physical framebuffer pixel; at larger zooms, each source pixel spans more than one. While an edit or pan moves at 100% or above, the visible region is shown at full detail where the GPU draws it, and otherwise the reference renderer draws the whole photograph at full detail, which takes longer. The full-image histogram and clipping counts always describe the whole photograph, counted at full resolution, never the visible area. Type a percentage from 10 to 1600 in the field beside it and press Enter, or choose 100%; neither Fit nor 100% is selected while a typed percentage is in force. Rest the pointer on the percentage, or on the field while you type, and the zoom stops drop under it: 50%, 100%, 150%, 200%, 300%, 400%, 600%, 800% and 1200%, evenly spaced on a notched rail. Click a stop or its label to zoom there, or drag along the rail and release on the stop you want; the zoom changes once, on release, however many stops you pass. The thumb shows where the zoom on screen sits, between two notches when it is between two stops (Fit often is), and none when it is below 50% or above 1200%. The stops stay while the pointer is over them or the percentage, so you can try several, and close a moment after it leaves both. While they show, the arrow keys step them: Up or Right zooms in a stop, Down or Left zooms out, and while you are typing in the field only Up and Down step, leaving Left and Right to the text. Cmd+= (Cmd++ works too) and Cmd+- zoom in and out a stop at a time from anywhere, from the zoom on screen; the stops drop for a moment so you see the thumb move, and stay if you bring the pointer to them. The percentage segment's chevron marks that the stops are there. They are a shortcut to the same `view.set` zoom the field sends. Both scroll axes pan content larger than the viewport.

Hold `\` to see the Original for as long as the key is down. It keeps the crop, straighten angle and orientation of the photograph on screen, so only the adjustments differ; hold Shift+`\` (`|` on a US layout) to see the whole, uncropped Original. Releasing either key, or switching away from the window, returns to your previous selection.

Tap `\` (release within 200 ms) or click Compare in the title bar to open the Before/After slider. Holding the key for 200 ms shows Before until release. Before is on the left and After is on the right. Drag the divider, or click anywhere on the photograph, to compare different portions; drag to either edge to show one side across the whole image. Tap `\` again or press Escape to leave. While the slider is open, holding `\` temporarily shows Before across the whole photograph; release restores the slider. After is the current or historical entry you were viewing when you entered, and leaving restores that selection. Both sides keep the same crop and orientation. At Fit and below 100% both sides are the GPU's pictures at rest, and leaving shows the photograph's own at once. Opening the slider over a picture the GPU drew with no CPU frame of it first renders the photograph once on the CPU, while the status bar reads `Rendering the photograph to compare…`; that frame is the After side at 100% and above. Zoom and pan continue to work; an After side retained as a display preview stays at that detail when magnified. Clipping and mask overlays and the pixel readout are hidden during slider comparison; the histogram follows Before. Comparison creates no history entry and is refused during a crop draft, an adjustment drag, a mask gesture or an edit request in flight; the status bar explains why.

A strip of icons floats under the photograph with the pointer, Mask, one entry per registered module that declares a canvas mode (Crop), and the Thirds and Information overlays; hover one for its name and letter. At Fit the photograph leaves room for the strip, so it never covers the picture. Thirds draws two guides each way over the fitted photograph; at a percentage zoom, and while a crop draft is open, the overlay is left to the crop rectangle's own guides.

Cards appear over the top of the canvas when something needs saying: a draft or a slider drag that was changed elsewhere, a preview that is stale because a stored layer's module is unavailable, an original that cannot be found, or a rendering limit. They name the cause and offer only the actions the core allows; none of them blocks the rest of the screen.

### Image information

Press `I`, click Information in the floating mode strip, or use Show/Hide information in the command palette to toggle the readout over the photograph. It shows the selected image's full resolution, or the live crop size while cropping, and the original size when different. The size follows history previews and stays the same when you zoom.

The readout includes the camera, lens, aperture, shutter speed, ISO and focal length from the original's EXIF, plus the capture date when available. Missing fields say Unavailable. Capture information is read once when the photograph opens; edits and lens-profile choices never change it. The toggle starts off, applies to this session and changes no photograph or history. `workspace.set {"information": true}` exposes the same preference; `source.inspect {"asset_id": "…"}` reports the prepared original's fields under `capture` and `recipe.describe` reports the selected entry's output size; `render.transform` reports the output size of an open draft.

### Histogram and clipping

The histogram sits at the top of the tools panel. It describes the **rendered output** of the photograph you are looking at: the whole composition after the crop and every edit, in 8-bit sRGB. It is not a camera or RAW histogram, so an endpoint count here is a warning that the finished picture has flat black or blown white, not a statement about what the sensor recorded or about detail that could be recovered. Panning, zooming and your display's scale never change it; selecting a history entry or a different photograph does, and so does dragging a slider — while a gesture is open the plot and the counts describe the picture on the canvas as it moves — counted from that picture itself, at the size it is drawn, where the GPU draws the drag — and the plot is dimmed until you let go and the full-resolution picture of the value you landed on has been counted; a drag drawn on the CPU keeps the last full count, dimmed. The overlay follows the drag from the picture on screen.

The three channels are drawn as filled, overlapping shapes on one shared vertical scale, so red twice as tall as green really does mean twice as many pixels. A grey area is the three channels overlapping, not a separate brightness curve. The histogram is just the plot, with the two triangles in its bottom corners, always the same height, so nothing in the tools panel moves while you drag, move the pointer or wait for a render. While a new version of the picture is still rendering or being counted the previous plot stays on screen, dimmed. The counts are the GPU's where it draws the picture and the exact CPU renderer's where it cannot; the GPU's clipping counts are held within 0.1% of the output pixels of the exact counts, and each channel's histogram and the luminance's within a quarter of a code of the exact one, so a share of the pixels can sit one code from where the exact renderer counts them. If the picture cannot be rendered at all, or nothing has been analysed yet, the plot says so in its middle — "No analysis yet", or "Unavailable:" with the reason — instead of showing an empty plot.

The two small triangles in the plot's bottom corners are the clipping overlays, shadows on the left and highlights on the right. A triangle takes its colour when that endpoint has any pixels; click it to draw that overlay on the photograph. Blue marks a pixel with any channel at 0, red a pixel with any channel at 255, and magenta a pixel that is both at once — the rule each triangle states when you hover it. Under the rule, the tooltip writes the counts out: the shadow triangle's says how many pixels have red, green or blue at code 0, how many have any channel there and how many have all three; the highlight triangle's says the same at code 255 and how many pixels are at both endpoints at once. Without an analysed picture the counts show a dash rather than zeros that would read as "nothing is clipped". `J`, and the Clipping button in the title bar, turn both overlays on and off together. The overlay is drawn over the photograph and changes nothing else: not the pixels, not the saved recipe, not the histogram's own counts, and not a future export. A single clipped pixel still lights its own mark when the photograph is shown fitted, so an isolated blown highlight is not lost in the reduction.

Move the pointer over the photograph and the three output codes under it appear in the status bar, with the pixel's coordinates: `R 128 · G 64 · B 255 · 120, 80`. It reads the same evaluated picture the plot describes, clears when the pointer leaves, and asks for one pixel at a time however fast you move. It has a fixed place in the status bar, so nothing else there moves as it appears and clears.

### Tone curve

The Tone curve follows Basic in the tools panel, collapsed until you open it. It reshapes the photograph's tones with one curve drawn over the histogram: the horizontal axis is a tone of the picture, from black on the left to white on the right, on the histogram's own scale, and the vertical axis is the tone it becomes. A new curve is the diagonal from black to white, which changes nothing. Raise a point to brighten the tones around it and lower it to darken them; an S, its lower points pulled down and its upper points pushed up, adds contrast. Points are added, selected, dragged, removed and typed as on [every curve](#edit-and-inspect); with a point selected, the arrow keys nudge it by 0.01, Shift by 0.1 and Option by 0.001. The curve holds 2 to 16 points.

The curve passes through every point and only rises or stays level between them, never overshooting, so two tones never swap places: a dragged point stays between its neighbours' heights, and a typed value that would make the curve fall is refused. Tones beyond the first or last point take that point's output, so raising the first point lifts the black, a faded matte look, and lowering the last dims the white.

The curve changes brightness, not colour. It sets each pixel's luminance and scales red, green and blue together, so hue and relative saturation are preserved and greys stay grey, except that a lifted black mixes its floor grey into the shadows: the deepest shadows fade toward that grey, rather than turning their noise into coloured speckle. An S-curve therefore adds contrast without the extra saturation a Lightroom curve applied to each colour channel gives.

A point drag previews live and commits once on release, as Basic's sliders do; adding or removing a point, and each coordinate typed in the **Points** list, is one entry, because each Enter commits one coordinate, checked against the other points as they stand. So to move a point past where its neighbour now is, type the neighbour first. Entries are labelled by the point count, "Tone curve 4 points", and the band's reset is "Reset Tone curve". It is one layer in the recipe, always evaluated after Basic and before the colour mixer whichever you touched first. Inside a mask the same section edits that mask's own curve ([masks](#masks)), and presets carry the curve ([presets](#presets)).

### Detail

Detail starts collapsed with the hint **Judge fine detail at 100%**. All three strengths start at zero on JPEG and RAW, and opening a photo adds no Detail layer. The Sharpening group offers **Amount** (0–150), **Radius** (0.5–3 px), **Detail** (0–100) and **Masking** (0–100). Amount restores apparent edge definition at the developed image's pixel scale; Radius controls the blur used to find edges, Detail retains finer structure, and Masking reduces sharpening away from stronger edges. This is capture sharpening; inspect at 100% before increasing it.

The Noise reduction group offers **Luminance**, **Luminance detail**, **Colour** and **Colour detail**, all 0–100. Luminance suppresses lightness noise; Colour suppresses chroma noise. Higher detail values protect more structure. Reduction runs before sharpening, and both run before Basic and Presence. RAW receives these operations after development and sensor white balance; JPEG already includes its camera's processing. Ancillary values stay editable and stored with the corresponding strength at zero. Such a layer renders unchanged pixels; a reset keeps the layer's identity and restores every default.

At Fit, a Detail drag is drawn on the GPU; where the GPU cannot draw it, the reference renderer draws each whole picture at full resolution, one at a time. On release the picture at rest is the fully processed image reduced to the view, drawn by the GPU, and the status bar says **GPU render**. Its histogram describes the full image, counted by the GPU over the fully processed image, and shows as updating until that count arrives. At 100% and 200%, the GPU draws the visible area at full detail, in motion and at rest.

Detail can be bound to an existing mask. A masked layer follows the global Detail layer and adds its own denoise/sharpen operation; it does not replace the global settings. Native presets capture all eight fields, including stored ancillary values at zero strength. Lightroom sharpening and noise-reduction values remain unsupported because their controls are not equivalent to these algorithms.

The API uses `edit.set-detail {asset_id, sharpening?, radius?, sharpen-detail?, sharpen-masking?, luminance?, luminance-detail?, colour?, colour-detail?, mask?}`. A patch retains omitted values; `edit.reset-detail {asset_id, mask?}` restores defaults. The generated controls use the same actions and draft lifecycle.

### Presence

Presence is the section under the Tone curve, collapsed until you open it, with three sliders that each run −100 to +100 in whole steps. They act on a neighbourhood of every pixel rather than on the pixel alone, which is what separates them from Basic's Contrast.

**Texture** raises or lowers medium-scale detail: fabric weave, foliage, skin texture. Positive values strengthen it and negative values soften it while broad shading stays where it was. **Clarity** does the same for broad local contrast, the difference between a region and its surroundings, so a flat scene gains depth and a harsh one calms down; it works on brightness only, so colours keep their hue and saturation, and its gain is compressed near black and white so it cannot create a new clipped highlight or crushed shadow. **Dehaze** estimates the atmospheric veil in the photograph, the brightest low-contrast light the haze adds, and removes a fraction of it at positive values or adds a uniform veil at negative ones. It changes colour as well as brightness, because haze is a coloured veil, and it can only remove what the estimate finds: a veil that varies quickly across the frame is partly left in place.

Whatever order you touch them in, they run in a fixed one: Dehaze, then Texture, then Clarity, after Basic and the Colour mixer and before the quarter-turns and the crop, as one layer updated in place. Each slider drafts and previews live as Basic's do and commits once on release with a label such as "Clarity +40"; the section's reset returns the three to zero as one entry, "Reset Presence". A neighbourhood operation costs more than a pointwise one, and the three together cost more than their sum, because every tile of the photograph is computed with a wide margin around it; the GPU draws the drag at the display's size at Fit, so it follows the drag, and the picture at rest at full resolution; where the GPU cannot draw a drag, the reference renderer draws each whole picture at full resolution, one at a time. The histogram and whole-image clipping counts come from the full-resolution picture and stay marked updating until the release has been counted. Point readout and committed edits use exact evaluation. Fine noise is texture as far as these controls can tell, so both amplify noise in shadows; inspect at 100%.

### Colour mixer

The Colour mixer is the section after Presence, collapsed until you open it. It adjusts eight colour ranges separately: red, orange, yellow, green, aqua, blue, purple and magenta, in that order around the wheel, each with a **Hue**, **Saturation** and **Luminance** slider from −100 to +100 in whole steps. The three properties are three tabs over the same eight ranges, Hue selected first; a dot on a tab marks a property you have changed, so edits on a hidden tab stay visible, and the reset at the right of the tabs resets the visible property. Choosing a tab only changes what you see: it adds nothing to history.

For Saturation and Luminance a pixel belongs to at most two neighbouring ranges, in proportion to where its hue sits between their centres, so a change to Red fades smoothly into Orange and Magenta and never draws a hard edge through a gradient. Hue turns a range's colours toward the next range (positive) or the previous one (negative): at ±100 the range's own colour travels 85% of the way to its neighbour's, so Blue −100 turns blues teal and Yellow +100 turns yellows green. The hues around it bend smoothly to make room, out to the ranges beyond its neighbours, and never cross; two neighbouring ranges pushed toward each other share one slider's travel. Greys and near-greys are never turned, lightened, darkened or coloured, which keeps shadow noise clean. Saturation runs from fully grey at −100 to twice the colour's chroma at +100, and with all eight Saturation sliders at −100 the whole photo is exactly black and white. Luminance darkens or lightens the range's colours without pushing them past black or white. The rail under each slider shows what it does: the hue rail runs from the previous range's colour through this one to the next, the saturation rail from grey to the colour, the luminance rail from its dark to its light version.

It is one layer in the recipe, always evaluated after Basic whichever you touched first, and each slider drafts, previews and commits as Basic's do, labelled with the range and property: "Red hue +20", "Reset Hue", "Reset Colour mixer". Lightroom's per-colour view, targeted adjustment drag and black-and-white mix are not built.

### RAW development

The NEF, RAF or DNG remains the original throughout editing. Exposure, white balance and composition are saved as recipe settings. History and versions retain those settings; reopening rebuilds the needed high-precision image from the original directly at the saved white balance. Display previews are disposable.

A RAW photo shows the same Basic section as a JPEG, with the same controls in the same places; there is no separate RAW section. Exposure is Basic's, applied to the developed image, and drafts exactly as on a JPEG. White balance is the development's: Temperature spans 2000–12000 K and Tint −100 to +100 Luxforge units, with positive values making the result more magenta. These set the sensor gains before the image is developed, which a JPEG's relative correction cannot do. Inside a mask, Temperature and Tint are Basic's relative correction on top of the developed image, as on a JPEG.

A monochrome RAW original stays grayscale. Basic's White balance group reads **Monochrome original** and disables Temperature, Tint, As shot, reset and the Neutral picker. `W` does not enter the source picker, and colour-changing source white-balance and picker API requests return `validation` without adding history. An As shot reset is already neutral and changes nothing, allowing Reset Basic to reset exposure/tone. Tone, exposure and geometry remain available.

Dragging Temperature or Tint previews the change approximately: an exact new white balance needs the sensor data redeveloped, so while you drag, the GPU preview draws the change on the image Luxforge has already developed, at Fit and at every zoom, at full detail at 100% and above. The histogram follows the frame on screen, marked updating, while you drag. When you let go, the sensor data is redeveloped for the value you landed on — about half a second on the Z6, longer on larger files — and the exact photograph and its histogram replace the preview, which stays on screen until then. The approximation itself is within about a code of the redeveloped result almost everywhere on the Z6 and X100VI; fine high-contrast edges, specular highlights and strongly saturated colours can differ by more, most for a large change on the Air 2S. Each drag records one history entry when you let go, such as "Temperature 5500 K".

As shot uses the captured camera-channel gains. While As shot is in force the two sliders show the temperature and tint that reproduce the camera's own gains — 4861 K and −50 on the supplied Z6 file, for example — so they read what is in force. A tint that falls between whole units shows one decimal. After a Neutral picker pick they show the pick's own equivalent the same way. If no temperature in 2000–12000 K and tint within ±100 reproduces the gains in force, they show 6504 K and 0 instead. Changing one of the two keeps the other at what it shows, as Lightroom does: dragging Temperature from As shot keeps the camera's tint, and dragging Tint keeps its temperature. Changing either control stores resolved sensor gains. These units do not promise numeric equivalence with another editor. The As shot button, the White balance group's reset and a double-click on Temperature's or Tint's label or rail all return to As shot, recorded as "Reset White balance"; a double-click on Exposure returns it to 0 EV. A double-click on the rail first moves the value to where you pressed, which is an entry of its own, and the reset follows once that entry is saved; for Temperature and Tint that takes as long as the redevelopment. Basic's reset also returns the development to As shot. Basic's header shows the edited dot when any of its settings, the development's white balance included, differs from the Original's; the White balance group reads Original at As shot and Custom otherwise.

Click Neutral picker in the White balance group, or press `W`, then click a neutral surface. On a RAW photo it is the sensor picker: it maps the point back to the original sensor and averages a bounded patch before white balance, and the pick is recorded as "White balance". A dark, clipped or unusable patch reports an error and commits nothing. Every successful change remains undoable. A white-balance change redevelops the retained mosaic; exposure and geometry reuse the prepared float image. The previous rendition stays visible during preparation.

The development itself is neutral: it uses camera calibration without film simulations, Picture Controls or automatic brightness, and the [look](#look) on top of it gives a new photo its finished starting point. Air 2S applies its required embedded optical corrections and uses fixed daylight calibration for custom Temperature/Tint; optional Lens correction applies only to the distortion role that remains uncorrected; dual-illuminant color-profile interpolation is not implemented. Sensor headroom remains available to exposure changes even when the current display is clipped. On the Bayer cameras (Z6 and Air 2S) the demosaic clips each colour at the sensor's white level once white balance is applied, so a highlight brighter than that cannot be recovered by lowering exposure; X100VI files keep values beyond it. Camera crop metadata and EXIF orientation determine the initial frame.

### Keyboard

Letters act only when no text field has focus. `G` shows the [Select](#select) workspace. `F` fits, `1` is 100%, `I` toggles image information, `O` toggles mask coverage in Mask mode and thirds elsewhere, `J` toggles both clipping overlays, `V` returns to the pointer, `M` enters Mask mode, and each module's declared letter (`R` for crop and straighten, `W` for the Neutral picker, which picks from the sensor on a RAW photo) enters its canvas mode, exactly as the mode strip and the pickers in the tools panel do. Escape cancels an armed or active mask tool, or leaves a canvas mode that has no draft of its own. Tap `\` to toggle the Before/After slider; hold it for 200 ms to show Before until release. Shift+`\` holds the uncropped Original. Escape exits comparison. Cmd+Option+[ and Cmd+Option+] show and hide the two side panels. With a [development set](#the-development-set), `←` and `→` move through it and Cmd+Option+F collapses and expands its filmstrip. Cmd+O / Ctrl+O opens a file, Cmd+E / Ctrl+E exports it and Shift+Cmd+E / Shift+Ctrl+E exports it keeping metadata, Cmd+Z / Ctrl+Z and Shift+Cmd+Z / Shift+Ctrl+Z undo and redo, Cmd+= / Ctrl+= (or Cmd++) and Cmd+- / Ctrl+- zoom in and out a stop at a time, and Tab and Shift+Tab move between fields. ### Lens correction and Perspective

Lens correction and Perspective are collapsed sections below Crop, transform, straighten. Lens correction never shows a list of lenses on its own; it shows one of these:

- **The applied profile**, as a card: a camera with a built-in lens is named by its camera ("DJI Air 2S (FC3411) · built-in lens", with the profile "FC3411 & compatibles" and the focal length beneath), an interchangeable lens by the lens, with the camera and focal length beneath. **Change** opens a search under it; **Close** hides it again.
- **The detected lens with Apply**, when nothing is applied. On a camera JPEG the card says the camera may already have corrected distortion and that applying assumes it did not; Apply applies it on that assumption.
- **A warning that no profile matches the lens**, with a search to find it by name and **Report missing lens**.
- **A warning that the camera is not in the lens database** (the X100VI, for example) with **Report missing lens** and no search, since no profile could fit it.

When you first open a RAW or DNG whose distortion the camera did not correct, before anything has been done to it, Luxforge applies its detected profile at once, as the history entry after Original, labelled like any selection ("Lens profile FC3411 & compatibles"). Undo removes it and Original stays uncorrected; Reset turns it off for good, and opening or developing the photo again never re-applies it. A JPEG is never corrected until you press Apply.

The search lists only profiles that fit your camera, sensor, frame and focal length; an empty search lists nothing. If a search finds none, the section says so and offers **Report missing lens**. That button opens a prefilled GitHub issue in your browser, naming the camera, lens, focal length, crop factor, source kind, in-camera correction, the lens database release and the Luxforge version, and nothing personal: no file name, path, serial number or location. Nothing is sent until you submit the issue yourself. If an answer is temporarily unavailable, Retry repeats the query with the same search and inputs. Supply a focal length when the section asks for one. A source already corrected for distortion says so and offers no profile. The supported Air 2S DNG's required warp corrects lateral CA, so its distortion profile still applies. The caption under the section lists what the camera corrected. Reset turns the profile off and keeps its layer identity.

For a client, `query.lens-profiles` answers the same states in its `status` (`state`, `current`, `suggestion` with the `parameters` its Apply sends, `notice`, `report` and `detected`), and the `job.read` of a photograph's first preparation (`source.prepare`) lists any `first_open` entry it committed after its Original.

Perspective offers Horizontal and Vertical from −100 to +100. Positive values compress the right or bottom side. Each drag is one undoable edit. Both modules keep the canvas size and cover it without exposed corners; **Cover** reports the automatic scale. Very strong minification is refused because the bilinear sampler would alias. These modules change the picture inside an existing crop while keeping its frame. A rotation or reflection carries Perspective with the image. Before/After includes the whole geometry; Original retains required source corrections and omits optional profile and perspective edits.

Profiles are a distortion-only subset of Lensfun v0.3.4: no vignetting, chromatic aberration, automatic keystone or defringe correction. Profiles and Perspective are photo-specific and excluded from presets; Lightroom Perspective fields report a different perspective model. X100VI has no exact camera match in this database. DJI drones are named by product ("DJI Air 2S", "DJI Mini 3 Pro") from a short list of well-known camera codes; the name is for display and reports only. [Photographic qualification](design/lens-and-perspective.md#verification-and-qualification) is separate from RAW decode support and remains incomplete where suitable photographs are missing.

### Crop, transform, straighten

The crop editor appears in the tool panel as soon as a registered module declares a crop frame; the ratios, the angle range and the action it commits all come from that module's descriptor.

Crop, transform, straighten is the first module in the tools panel. Its four transform buttons rotate 90° left or right, mirror horizontally, or flip vertically, each committing immediately as one undoable action. Apply or Cancel an open crop draft before using them. The header’s Reset crop resets the crop rectangle and straighten angle; it keeps the orientation. Its **Ratio** group holds the custom ratio's W and H, Lock ratio and Swap; its **Angle** group holds the angle rail, its −0.5° and +0.5° buttons, the numeric angle and the ruler-shaped **Straighten** button. Idle, the ratio shortcuts also appear in the section. During crop mode they move to the floating control bar above the photograph, where the selected ratio stays highlighted. The controls read the committed crop: Original when its rectangle keeps the input stage's ratio, a `W:H` preset in either orientation, and Free when it matches none or there is no crop. The recipe stores the rectangle, not the preset name.

Choose Crop in the strip under the photograph, or press `R`, to open a draft that changes nothing yet. Entering crop mode collapses every other module and opens Crop. Apply, Cancel or a failed start restores the previous module disclosure states, including Crop's own state. Changing a ratio or angle control in the section does the same and applies that change: choose 16:9 and the photograph enters crop mode with a 16:9 frame; drag the rail and it opens at that angle. The draft is live at once: the section, Apply and Cancel act on it while its picture is still being prepared ("Preparing the crop's input stage…"), and the frame appears on the photograph as soon as that picture arrives. Cancel, or Escape, while it is still being prepared cancels it straight away. Choosing the chip that is already chosen opens the draft without refitting the frame, and typing the angle the crop already has just closes the box. Nothing is committed until Apply. The open draft is this window's one draft, so an agent using the same session sees it in `session.state` with the angle and rectangle it would commit, updated at the end of each change. The section's controls are disabled while a historical state is shown or a request is in flight, and a crop draft cannot start while a slider drag or a mask gesture is open.

While a draft is open the surface shows the crop layer's own input stage, which is the stack rendered up to but not including that layer: every rotation, reflection and edit you have made, however you ordered them against the crop. Only the post-crop Vignette, which is centred on the cropped picture, is not drawn while you adjust it. At Fit the stage is drawn from a display-size preview, so a draft opens at once even on a large photograph; zoom to 100% or more and the stage is rendered at full resolution for that view, and back at Fit the display-size preview returns without another render. If something rotates the photograph while a draft is open, Reapply turns the drafted frame with it. Everything outside the crop rectangle is dimmed, and the rectangle carries a thirds overlay, a border and eight handles.

- Drag a corner handle to move two edges, or a side handle to move one with the opposite edge fixed. Drag inside the rectangle to move the composition; it slides along a boundary instead of stopping. The rectangle never leaves the photograph, so a crop never has an empty corner, and it never shrinks below one pixel on either axis.
- Hold Option (Alt on Windows and Linux) while dragging any handle to apply one scale factor about the fixed centre, keeping the current width to height even with no ratio locked. The centre does not move.
- Choose a ratio preset to keep the centre and fit the largest rectangle of that ratio inside the current one. Custom takes the two extents typed beside it. Lock ratio pins whatever the rectangle currently is, Unlock ratio releases it, and Swap inverts a locked ratio. Press `X` while cropping to do the same, for example changing a custom 4:5 ratio to 5:4. The shortcut leaves text fields alone.
- Drag the angle's rail between the −0.5° and +0.5° buttons, which moves in 0.05° steps, or use the buttons, or the arrow keys while the angle has focus (0.5°, 5° with Shift, 0.05° with Option), or click the angle's box, type an angle from −45 to 45 degrees and press Enter; text that is not an angle in that range stays in the box with the reason. Double-click the rail to put the angle back to 0°. Every angle is measured against the last handle, move or ratio change, so sweeping the angle away and back returns exactly the rectangle you had. Larger rotations use the 90° left and right buttons at the top of this section.
- Click the ruler-shaped Straighten button and drag a line along something that should be level; releasing rotates by the angle that makes that line horizontal or vertical, whichever is nearer, and automatically returns to the crop handles. Click the selected button again to put the tool down without drawing.
- Hold Space and drag to pan at a percentage zoom. Fit, 100% and a typed percentage all work while drafting, and 100% still shows one input pixel per physical pixel.

While drafting, the panel adds under those controls the input stage, the rectangle in whole box pixels, the resulting output size and the exact values the draft would commit, then Cancel and Apply.

Apply, or press Enter, commits one action and one new history entry, adjusting the existing crop layer in place and keeping its identity or appending one when there is none. Cancel, or press Escape, discards the draft and changes nothing. Enter and Escape act only when no field has just consumed the key. Reset crop is the module's own control: it commits the neutral crop through history and ends the draft. No pointer movement commits anything, and the rotation shown while drafting is a display filter — the committed render is what counts.

If an edit commits but its picture cannot be rendered, the edit stays in history and the canvas says so: the picture from before the edit is taken off the surface, and "Preview unavailable" with the reason, a notice such as "Rendering limit", and an unavailable histogram take its place until a state renders again. A draft whose input stage cannot be rendered does not open; the status bar gives the reason and the canvas returns to the pointer mode. Nor does one whose input stage is superseded while it is being prepared — by another client's commit, your own undo or edit, or a zoom that needs a new frame: the canvas returns to the pointer mode and you start the crop again. A superseded reapply keeps its draft, still marked as changed elsewhere.

Selecting a historical state pauses the draft rather than discarding it: the historical preview is shown and Return to current resumes drafting. Undo, Redo and Restore are refused while the draft is open, with the reason in the status bar. If another client changes the photograph while a draft is open, the draft is kept and marked "Changed elsewhere". Apply is refused until you choose Discard, which drops the draft, or Reapply, which re-reads the current stack, rebases the draft onto it keeping the angle and the composition as far as it fits, and lets you apply normally.

### Masks

New gradients start empty, live overlays show the actual candidate coverage, and `O` shows or hides
coverage in Mask mode. Creating a mask keeps unrelated controls disabled until it is made or
cancelled. Selecting another mask or component puts an idle brush down. The
[masking interaction contract](design/masking-interactions.md) describes the exact behaviour.

A mask is a selection plus the adjustments that apply through it. Choose Mask in the mode strip, press `M` or pick Mode · Mask from the command palette; the tools panel then shows the Masks panel in place of the module sections, and the canvas draws what the open mask selects.

The panel reads top to bottom. The **Masks** band says how many masks there are and that Escape leaves Mask mode; its chevron folds the panel away down to the adjustments. Under it is the **overlay** row, then one row per mask: a small picture of what the mask covers, its name, a dot when it is changing the photograph, its amount, an eye and a menu. Under the list are **New mask** and a count of masks against the limit of sixteen. The open mask follows under its own name, with its **Amount** and **Invert mask**, its components, the **Add component** row, the **Brush** settings while a brush is in hand or selected, and then the adjustments that apply through it, each band marked with the mask's name.

**New mask** opens a menu of every component kind this build offers, each with its icon — Linear gradient (`L`), Radial gradient (`R`) and Brush (`B`), then Luminance range and Colour range — and while the menu is open its letter starts that kind. Each acts the way its own shape demands: a gradient has handles to drag, so choosing it starts a gesture; a brush is painted, so choosing it puts the brush in your hand; a range selection has numbers rather than a shape, so choosing it creates the selection those numbers start at in one history entry. Either way, **the mask you just made is the one that opens**, so the adjustments under the component list are already bound to it and the next slider you move belongs to it. There is no Sky, Subject, People, Objects or Background: every selection offered is brightness, colour, a shape or painted coverage, with no model behind it. A linear gradient is drawn across the photograph from the side you do not want to the side you do, exactly as Lightroom's gradient works: the press sets the end at no coverage and the pointer the end at full coverage. The three lines the design draws are that first end, the midpoint and the far end, each with a handle; drag an end to move it, or the midpoint to move the whole axis without changing its length or direction. As in Lightroom, **letting go commits**: the drag that draws the gradient is one history entry, written when you release, with no Apply step, and Escape while the button is still down discards it and changes nothing. The numbers follow the drag in the panel while it is down, and a committed component's `x0`, `y0`, `x1` and `y1` are ordinary fields under its row, each with the same Copy as JSON request its context menu offers anywhere else.

A **radial** is drawn the same way in one stroke: the press sets the centre and the drag sets both radii. Its handles are four radius grips on the ellipse's own axes, a centre that moves the whole ellipse, a rotation grip just beyond the sideways radius, and a feather grip on the ellipse's diagonal, where the dashed inner ring shows where the falloff begins. **Inside the ellipse is selected**, which is the other way round from Lightroom; the component's own Invert gives Lightroom's reading exactly. Radii are in units of the picture's height on both axes, so a circle stays a circle whatever the shape of the frame, and `x`, `y`, `radius_x`, `radius_y`, `angle` and `feather` are fields beside the handles and under the row. Dragging any handle is one history entry when you let go, and the numbers follow the drag exactly.

While a gradient is open, the bar over the top of the canvas names the mask in the accent (New mask while the gesture will create one), then the component beside its kind's icon with the mode it has or will be added with, then the gesture's numbers — a linear's two ends as `x0, y0 → x1, y1`, a radial's radii, angle and feather as `0.180 × 0.240 · −12° · feather 60` — read out compactly. The fields in the panel show the same precision — positions to two decimals, radii to three, the angle and feather whole — which is a display choice only: a typed or fine-nudged value is sent and stored exactly, and the field shows the extra digits while the value has them. A component the gesture is adding is named by its kind until its commit gives it its number. The bar ends with Done, and the status bar says how the gesture becomes history: `Mask mode · Face · Radial 1 · each drag is one entry`. The handles are white, the centre or midpoint that moves the whole shape is the one in the accent, and the rotation grip is square. Choosing Linear or Radial first arms an empty tool: click and drag on the photograph to place it; no initial shape is inserted, a click alone places nothing, and Done or Escape before a drag puts the tool down. The actual overlay appears while drawing, including the feather. `O` or the overlay row can hide it during the gesture. Until the new mask is drawn or the tool put down, unrelated controls are disabled.

The **brush** is painted rather than dragged. Choose Brush from New mask to paint a new mask, from Add component to put a further brush on the open mask in the mode the Add row has chosen, or Paint more from a brush component's menu to add strokes to it. The brush's Size, Feather and Flow are remembered from one launch to the next. While a brush is in hand, or a brush component is selected, the **Brush** settings appear under the Add row — **Size**, **Feather** and **Flow** as sliders, each also typed and reset by double-clicking its name, then **Erase** and **Limit to colour**, with **Colour refine** as a slider under it while the limit is on — `armed · Esc puts it down` beside the heading while the brush is in hand; otherwise they are out of the way. The cursor is two circles: the outer one where coverage ends, the dashed inner one where the falloff begins. `[` and `]` change the size, `Shift+[` and `Shift+]` the feather, and holding Option erases for as long as the stroke lasts — letting go halfway along a path does not turn an erase back into an add. The evaluated overlay follows the stroke with its actual feather, flow, erase and composition; the cursor circles show size and feather. A stroke may begin outside the picture and paint in over its edge, and painting behaves the same at Fit, at 100% and under a straightened crop: what you paint is recorded in the photograph's own coordinates, so the zoom you were at and the crop you were under are no part of the edit. After the first stroke creates the mask, adjustments are available between strokes. Selecting a different mask or component puts the old brush down; choose Paint more or Add before painting that new target. Creating a mask, an active stroke and a gradient draft keep their target until completion or Cancel. Done or Escape puts the brush down.

**Each stroke is one history entry.** The first reads "Add brush", every later one "Update Brush 1", and undo walks back one stroke at a time. The brush stays in your hand between strokes, so you keep painting without starting a new gesture; Escape puts it down, and a second Escape leaves Mask mode. While it is in hand the bar over the canvas names the mask and the brush component with its mode, reads the size and feather the next stroke will take — or `painting` while a stroke is down — and ends with **Done** rather than Apply, because every stroke has already been written: Done puts the brush down, as Escape does. Strokes combine inside their component rather than being flattened, so each of them stays an object: select the component and its strokes are listed in the order they compose, each reading the settings it was drawn with — `add · 0.060 · f50`, `erase · 0.040 · f30 · colour-held`, with `flow 80` when it was drawn below full flow — and each with its own Delete. **That Delete is not an undo.** It removes one stroke and appends an entry of its own, so a stroke you made ten edits ago can go while everything after it stays exactly where it is. A component's last stroke has no Delete, because a component with no stroke selects nothing: delete the component instead. Painting over the same spot again and again has a limit: a stroke that would pile more than 64 path segments of one brush over a single spot is refused when you paint it, with the reason, and nothing of it is kept. That keeps every pixel of a brush quick to draw, and because the limit is paid when you paint, a mask you have painted is never refused later when you adjust through it.

A stroke can retain at most 16,384 distinct positions before simplification. If it exceeds that limit, or strays outside the stored range, it stops growing and reports the refusal; releasing it drops that stroke, commits nothing and keeps the brush in hand, so the next press starts another. Existing strokes stay intact.

One brush control is worth naming because you may go looking for it and will not find it: there is no **Density**. In Lightroom, Density and Flow interact through a build-up model *along a single stroke*: coverage accumulates from overlapping stamps, so what you get depends on how densely the stroke was stamped, and therefore on the size of the picture it was stamped on. Luxforge's stroke is a path rather than a row of stamps: one pass of the brush reaches its Flow and no more, however fast your hand moved, however finely the pointer was sampled and whatever the picture's resolution. A second pass over the same place is a second stroke and does build up. A control called Density on top of that would have to mean something other than Lightroom's, so it is left out and named here rather than shipped under a familiar label with unfamiliar behaviour.

**Limit to colour** holds a stroke to the colour it started on. Turn it on, put the brush down on a
blue sky, and the stroke paints the sky and leaves the red roof beside it; **Colour refine**, the slider that
appears under the toggle while it is on and whose value the toggle reads beside its name, says how
tight the hold is, on the same 0-to-100 axis a colour range's Refine uses and with the same meaning,
where a higher number is a narrower hold and 50 holds an ordinary surface across a stop of shading.
**It is not Lightroom's Auto Mask:** it compares each pixel with the colour under the brush where the
stroke began and knows nothing about edges or connectivity, so it will also paint that same colour
anywhere else the stroke passes over — if a strip of the same sky shows through on the far side of the
roof and your stroke reaches it, it is painted too, and the remedy is to subtract a brush over what it
caught. The colour is sampled once, where the stroke starts, and stored with the stroke: later edits
never move it, and nothing is re-read when the picture is drawn. It is read from the GPU's picture,
so the first moment of a limited stroke draws once that one read lands, while the window stays responsive; a stroke painted through the JSON
API without the desktop reads it from the reference, which may differ by a code. Because the stroke then reads pixels,
it inherits what the range selections say below — what it holds follows the adjustment's own input, so
a layer ahead of the mask changes it, and its overlay is read on that input rather than on the finished
picture.
Limit to colour needs an adjustment to read the input of, so the toggle is unavailable until the open
mask is bound to a layer, and it says so.

A mask's geometry is stored in the photograph's own content coordinates, so it travels through every quarter-turn, reflection and crop with the picture: cropping after masking never moves the mask. A stroke is stored on a grid fine enough that a position is one pixel of the largest picture the editor admits, simplified to within a twenty-fifth of its own brush radius so a large brush keeps only the positions its size can show, and each stroke is kept once under the fingerprint of its own contents, so painting for an afternoon costs kilobytes rather than megabytes.

Selecting a mask opens it. Its **components** are always listed, in the order they compose, each row carrying a grip, its kind's icon, its name, its own `+ − ∩` control for Add, Subtract and Intersect (Subtract reads red and Intersect blue), its own invert glyph and a menu with Rename, Paint more for a brush, Move up, Move down and Delete. Each of those is one command, and the menu's Copy as JSON request lists the exact request each of them sends. Selecting a linear or radial row also puts its handles on the photograph, and they stay there, as Lightroom's do: a gradient you have just drawn is selected with its handles showing, and opening a mask selects its first gradient, so its handles are ready to drag. A mask with no gradient opens with nothing selected. Drag the accent handle — a linear's midpoint, a radial's centre — to move the whole shape, or any other handle to reshape it; each drag is one history entry when you let go, with no Apply. A click on a handle that moves nothing writes nothing, and a press on the photograph away from the handles leaves the shape alone. The handles hold nothing open, so the adjustments, the list and history stay usable between drags; Escape while the button is down abandons that drag. Selecting a row shows its numbers under it in two columns — a radial's six, a gradient's four, without units except the angle's degree sign — typed like any field, with the field's own Copy as JSON request on a right click. Drag a row by its grip to move it: the row in hand dims, an accent line marks where it will land, and a move the host would refuse says why in the status bar and changes nothing. With a component selected, `X` inverts it, `⌫` deletes it — or the whole mask when it is the mask's only component, as its menu's Delete mask does — Up and Down move the selection and Option-Up and Option-Down move the component; with none selected the same keys act on the mask list. A control belongs to the row it sits on: changing the third component's mode never touches the first, and none of it changes what is selected or what the handles are editing. Pointing at a row shows that component's own contribution in the overlay and leaving the row brings the composed mask back, which is how you see what a Subtract is doing on top of a gradient. **Add component** offers the same kinds from the same menu, with the mode — the `+ − ∩` control after `as` — chosen before the gesture starts rather than guessed from a modifier afterwards. A mask's first component is always an Add, because nothing precedes it to subtract from; the panel says so on that row rather than offering a mode it would refuse, it refuses a move that would leave a component that is not an Add at the front, and while Add component is set to Subtract or Intersect, New mask is refused with that reason rather than quietly making an Add. A recipe that holds sixteen masks, or a mask that holds thirty-two components, disables the button and says why when you point at it. A mask never exists empty either, so its only component's menu offers Delete mask instead. A menu item that is greyed out says why in its tooltip, in the words the command would refuse with.

Under the component list are the **adjustments**: the ordinary Basic, Detail, Presence and Colour mixer sections, bound to this mask, each band carrying the mask's name in the accent so a slider there never looks global. They are the same controls with the same ranges, the same drafting behaviour and the same Copy as JSON request, which now carries the mask, and they edit that mask's own layer rather than the global one — so a photograph can carry a global exposure and a different exposure through each mask. Detail and Presence act on a neighbourhood of every pixel, and the settled picture and an export run each such masked layer over the whole photograph in turn, so a recipe holds at most 16 masked Detail and Presence layers between them: a change that would add a seventeenth is refused with the reason, and nothing is written. Leaving Mask mode binds them back to the global layer. A module with nothing a mask can carry, such as Crop, is not offered inside a mask.

The whole mask has an **Amount** (0 to 100, multiplying the composed coverage) and an **Invert mask**. Each row carries a small picture of what the mask covers, a dot when the mask is doing something, an eye that shows or hides its overlay, and a menu with Rename, Duplicate, Invert, Move up, Move down, Delete and Copy as JSON request. Rename edits the name in place: Return keeps it and Escape leaves it as it was; a component renames the same way from its own menu. Drag a mask by its picture to reorder the list. Duplicating a mask copies its components **and** the layers bound to it, because a mask without its adjustments is not a useful copy, and deleting one deletes those layers and names them in the history entry.

The **overlay** row shows what the mask selects: off, a tint over the photograph, the mask alone on black, or the photograph seen through the mask on black, as four icons whose names are in their tooltips, then the tint's two colours. The colour you choose is remembered, and Settings › General sets it too. `O` shows or hides the tint in Mask mode. The tint is green or white and never red — the clipping indicators already own red, blue and the magenta between them on this canvas, and an overlay you cannot tell apart from a clipping indicator is worse than none. The overlay updates independently from the photograph, using the actual draft coverage and feather. Starting a tool makes it visible automatically; pressing `O` or choosing Off hides it even while you continue drawing. The overlay is a view setting: it changes no recipe, and hiding a mask's overlay with the eye does not stop that mask applying to the picture. Outside Mask mode, `O` toggles thirds. The two black presentations remain choices in the overlay row.

Masked layers stay in the recipe list on the left, in the durable processing order, each naming the mask it applies through and the first of them carrying that mask's heading. They are not moved under it: the list's job is to show the order edits are applied in, and a mask's layers belong to different stages.

**Luminance range** and **Colour range** select by what a pixel *is* rather than by where it is, and
they combine with gradients and brushes in the same component list. A luminance range has a **Low**
and a **High** edge with a shoulder below and above each, all on the histogram's own horizontal axis
from 0 to 100, so one unit is 2.55 output codes and the number on the slider is the number you read
off the histogram. They are drawn as one band over a black-to-white rail: drag either thumb to move an
edge, or the small grip beyond it to widen its shoulder, which shows as a fade. When two grips sit on
top of each other the first move decides which one you took; a press on the bare rail moves the nearer
thumb, and a double-click on a grip resets it. The four numbers stay under the band, because a typed
value is exact. A shoulder of 0 is a hard edge; anything else is at least 1, because a narrower
shoulder is a hard edge asked for indirectly. A colour range holds up to five sampled colours, each
added and removed on its own, and one **Refine** slider from 0 to 100: a higher refine is always a
tighter selection, from a whole family of related colours at 0 to a single flat patch at 100, and the
default of 50 is the setting measured to hold an ordinary surface together across a stop of shading.
An unsampled colour range selects nothing, which is what a new one is.

Neither kind is drawn on the photograph, because neither has a shape: choosing it from New mask or
Add component creates it straight away as a starting selection — the whole tonal range with soft
shoulders for a band, no swatches for a colour range — and you narrow it through the numbers under
its row. A colour range's swatches are **picked off the photograph**: select the component and press
**Pick**, which counts the swatches it holds (`Pick 3 of 5`), then click the picture, and each click
adds one swatch, up to five. The swatches sit under the row in the colours they hold, with an empty
slot for each one left; press a swatch for its Remove, so one picked by accident goes without
clearing the rest, and picking a colour the component already holds changes
nothing rather than spending a swatch on it. The same two commands do it from a script:
`mask.add-colour-range-sample` takes a linear sRGB triple and `mask.delete-colour-range-sample` an
index.

The pick needs something to read: a selection by value is evaluated on the pixel the adjustment it
modulates *receives*, so the mask has to be bound to a layer before a colour can be picked into it.
Until it is, the button says so. The colour never comes from the frame you are looking at — that
frame holds the adjustment's output, and picking from it would sample a colour the selection is never
evaluated against — so the host reads the pixel itself and the click carries a position, not a
colour.

Four things about a range selection are worth knowing before you rely on one, because they are how it
works rather than faults to be fixed. **The panel says all but the third on the component's own
row**, above the numbers they apply to, so you read them before you type a number rather than after
you have made an edit you did not mean; what it cannot say in a line is the arithmetic behind them,
which is here:

- **It reads the input of the adjustment it modulates, not the finished picture.** A layer ahead of
  it changes what it selects: a `+0.75 EV` lift before a band drawn for a sky takes that sky from
  fully selected to not selected at all. Reordering layers therefore moves a range selection, which
  the gradients and brushes never do.
- **It reads the adjustment's input at a position on the current view.** The mask-coverage overlay samples the first bound layer's input through the uncut full-stage
  recipe, then maps its grid into the visible region. It uses full-stage coordinates rather than the
  displayed pixels and remains separate from pixel-derived clipping. It never reads the finished frame, whose pixels are the
  adjustment's *output* and would draw a selection the picture never had. The grid is capped at 4096
  cells per side, so one cell can cover several source pixels; it is a coverage sample over the
  visible rectangle, not an average of every pixel in that cell. Its density follows the physical
  display pixels in the visible rectangle; the whole-stage mask tint uses a separate coverage grid,
  while histogram and clipping counts come from full-frame analysis. The displayed image at Fit is
  downscaled, and at 100% and above the GPU draws the visible region at full scale, the coverage
  grid of that region laid over it; where the reference renderer draws the whole photograph, the
  whole-stage grid is. The coverage grid uses the mask's full-stage coordinates independently of
  that displayed pixel scale. Two masks have no grid at all and say why: one no layer
  is bound to yet, because there is no adjustment whose input to read, and one whose adjustment sits
  behind Presence or another neighbourhood effect, because reading that input costs a tile of the
  picture per overlay cell. Read either in the picture at 100%.
- **A narrow band speckles on noise.** A range selection is a per-pixel test, so it inherits the
  picture's grain: on a shadow around output code 40 with two codes of noise, a hard edge flips 47%
  of neighbouring pixels by more than half, a shoulder of 1 flips 31%, and a shoulder of 5 — about 13
  output codes, comfortably wider than the noise — flips none. Feather generously in the shadows.
- **These are deterministic selections, not subject recognition.** A luminance band cannot separate a
  photographed blue sky from a mid-grey card: they sit 1.4 output codes apart, and no band takes one
  without the other. A colour range cannot separate one person's skin from another's — dark skin is
  0.0108 from light skin in the metric, a third of what one face's own shading spans — and it cannot
  separate a face from an oak floor, which at the default refine stays about 30% selected. Every
  neutral is one colour to it: white, mid grey and black are within 0.0015 of each other, so a
  sampled grey selects the whole tonal range at any refine, which is what the luminance range is for.
  The remedy in each case is the component list: intersect a band with a colour range, or subtract a
  brush over what you do not want.

Leaving Mask mode with a gesture open is refused with the reason rather than discarding what you drew, as the crop draft is; so is holding Compare. Undo, Redo and Restore are refused while a gesture is open, as they are during a crop or slider draft. If another client changes the photograph while a gesture is open the gesture is kept and marked "Changed elsewhere", with Discard and Reapply, exactly as a crop or slider draft is. An armed brush with no active stroke has nothing to reapply and follows the new state; a held stroke keeps its conflict and recovery controls. After Reapply, the held stroke keeps its position on the original content and new pointer input waits for the refreshed geometry coordinates. An unplaced new tool remains armed until it is made or cancelled.

A mask made of several components is ordinary, not a special case: draw a radial, take a region back out of it with a Subtract, confine what is left with an Intersect, and adjust through the result exactly as through a single gradient. Order matters, and the list is the order: an Add moved above a Subtract is no longer cut by it, and moving a row is an ordinary history entry like any other edit.

The linear gradient, the radial gradient, the brush and the two range selections are every kind this
build offers, and Limit to colour is the part of Lightroom's Auto Mask that can be evaluated exactly:
a colour similarity, not edge detection. **A genuinely edge-aware refinement is not built.** Nothing
here finds a boundary, follows one, or snaps a selection to it; that needs a neighbourhood operation
over what is today a test of one pixel at a time, and it will get its own design rather than being
approximated under a familiar name. No selection here is made by a model either: there is no Select
Subject, Sky, People, Objects or Background, and none of them is drawn as a control that does nothing.

### Vignette

Vignette is the last section of the tools panel, collapsed until you open it, and it is applied after the crop: its centre is the centre of the cropped picture, and a later crop moves it, exactly as a post-crop vignette should. **Amount** runs −100 to +100; negative darkens toward black at the edges, and −100 reaches black at the corners, while positive lightens toward white without ever exceeding it. **Midpoint** (0 to 100) sets how far from the centre the falloff begins, **Feather** (0 to 100) how wide the transition is, from a hard edge at 0 to a gradient that spans the whole picture at 100, and **Roundness** (−100 to +100) the shape, from a rounded rectangle through the ellipse that matches the picture's proportions to a circle. The corners are always the far edge of the mask, whatever the shape.

Amount 0 is the identity whatever the other three hold, so a layer with the amount at zero changes nothing. Each slider drafts and commits as Basic's do, labelled "Vignette amount −35" or "Vignette feather 80"; the reset returns all four to their defaults as one entry, "Reset Vignette". Only this one style is built: the highlight-priority, colour-priority and paint-overlay variants are not.

### Module settings and consent

A module that needs settings, a download or a network service shows a small block at the top of its section: each resource it can download, with its size, its state and Download, Cancel or Remove; its own settings, drawn like any other control; how many permissions you have given it, with Revoke all; and one line saying what went wrong, if anything did. If another program changes the settings while you are typing, the block reads them again and says so on that line. Provider profiles and their keys are set through the API (`module.profile.create`, `module.settings.set` and `module.settings.set-secret`); a key is kept in the macOS Keychain, never in the catalog or a settings file, and is only ever reported as present or not.

Nothing downloads, loads or leaves your machine until you ask. When a module first needs to download a resource or send part of a photo somewhere, a notice over the photo says exactly what, where to, how much, where it is stored and whether it may cost money, with Allow and Don't allow. Allowing a send covers this photo only. The block counts what you allowed and declined, and Revoke all withdraws every permission the module holds at once, cancelling any work that depended on them without touching your edits; `module.permission.list` and `module.permission.revoke` list and withdraw a single one. Today the only module with this block is the developer capability proof, shown with `--developer --proof-endpoint URL`.

## Exporting

The Export button beside Open in the title bar opens a small menu with **Export JPEG…** and **Export JPEG, keep metadata…**; Escape or a click elsewhere closes it. Cmd+E runs the first and Shift+Cmd+E the second, and Cmd+K lists both, with a third, **Export reference render…**, offered only there, which writes the reference renderer's export instead of the GPU's. Either exports the entry on screen: the current state, or the history entry you are previewing. While the Before/After slider is open, export writes the fixed After entry, even with the divider moved to show only Before. A draft is never exported; the export is the saved entry behind it.

A save dialog opens in the folder you last exported to through it, while that folder exists, or else in the original's folder, with `<name>-edited.jpg` suggested, or `<name>-edited-2.jpg` and so on when that name is taken; any other name or folder can be chosen there. The file is a quality-90 JPEG in sRGB with its colour profile embedded, at the photograph's own size after orientation and crop: nothing is resized. On macOS the file records 72 pixels per inch for each physical pixel per point of the display the window is on, 144 on a Retina display, so Preview's Actual Size shows it pixel for pixel, as the editor's 100% does; a density changes no pixel. The GPU draws the export, in full-resolution tiles that are encoded as they arrive, as it draws the picture on screen: it is within the display limit of the reference renderer's export, the slower CPU render every GPU output is measured against, the same file each time on this Mac, and possibly different in the last digit on another machine. When the GPU cannot draw it — the editor was started with `--no-gpu-render`, the graphics device cannot, the photograph has not been drawn yet, the stack needs more GPU memory than the export may use, or the device is lost part-way, which starts the export again — the reference renderer writes the file, more slowly, and says nothing different in the status bar; the job's `renderer` says which wrote it and why. While it is written the status bar reads "Exporting <name>…", then "Exported <name> · width × height · size", or why it failed, and the Performance section lists the running export with its phase.

Without Keep metadata the file carries no EXIF, IPTC or XMP. Keep metadata copies the original's description, artist and copyright, camera and lens, capture settings and times, and GPS position, and writes the new file's own orientation, colour space and size; maker notes, serial numbers, thumbnails, IPTC and XMP are never copied.

Luxforge never replaces a file, and never touches the original. Exporting to a name that already exists is refused, even after the save dialog asked whether to replace it, and the status bar reads "Not exported: <name> already exists; Luxforge never replaces a file".

## History

History lists Original and every committed action newest first, with its sequence, a label and who made it: `you` for your own edits and `agent · <name>` for another client's. Its heading shows the photograph's revision. The label comes from the action's declared summary ("Crop 16:9", "Rotate right") or its title, and is stored with the entry. The filled accent marker is current and an accent outline is the previewed entry; selecting the current row keeps you on the live state, and selecting another row previews that immutable snapshot without changing current state or revision, the status bar says which entry is shown, and Return to current and Restore appear under the list. Restore appends a new action containing the selected recipe. Editing is disabled during a historical preview.

`recipe.describe` lists the displayed entry's layers in processing order with the module title and the module's own summary of each layer, from `recipe.describe`; a layer whose module is unavailable shows the reason instead. Each row also carries the parameter `values` that layer represents, when its module reports them, so a client can show the settings of the entry on screen, and `neutral`, the module's answer to whether the stored layer changes nothing: a Basic layer returned to 0, a vignette at amount 0, a whole-image crop, the identity orientation or a RAW development at As shot and 0 EV. A section's edited dot shows only for a layer that is not neutral. Each row also carries `input_stage`, the `{width, height}` that layer receives from the layers before it (the photograph's own size for the first layer), which is the stage its settings address, such as the stage a crop's rectangle is a fraction of. It is `null` after a layer whose module is missing or cannot read its settings, since nothing after that layer has a known size. Beside it, `input_orientation` is the `{mirror, turns}` the rotations and reflections before the layer gave that stage. The answer ends with `output_stage` and `output_orientation`, the same two for the whole stack, which is what a layer added at the end, such as a first crop, would receive.

Versions are chips naming saved states. Choose + to reveal the name field and Save; each chip carries its entry number, selecting one previews it, and Restore brings it back as a new action. Right-click a chip to delete the name; the entry stays in history. History rows marked branch were undone and replaced by later edits; they remain available for preview, restore and versions.

With **Auto collapse history** on, the default (Settings › General), successive edits of the same control keep one entry. Contrast +15, then −30, +30 and +10 leave one row, Contrast +10, and Undo goes straight back to the state before the first of them. Setting a control back to where the run started leaves no row at all, and the status bar says "Back to entry N · collapsed …". Only the same control on the same target, set one edit after another by the same actor (you, or one agent), collapses: another control in between, an undo, a mask, a rotation or an entry you named as a version starts a new row. Collapsed entries are hidden, not deleted: `history.list {collapsed: true}` lists them, marked `collapsed`, and `history.inspect`, preview and Restore still reach them by id.

Undo and Redo navigate saved states without appending rows. Cmd+Z / Ctrl+Z and Shift+Cmd+Z / Shift+Ctrl+Z invoke the same service as the buttons. A new edit clears shortcut redo while every older entry remains available for preview or Restore. Layers, history, navigation state and stable IDs survive reopening the catalog.

Missing or changed sources keep their catalog data and report why rendering is unavailable. Only the [current catalog format](design/versions-and-lineage.md#storage-catalog-format-13) (which stores the recipe's masks and its content-addressed stroke store, the preset library and derived-artifact references, as well as typed source interpretation, entry labels, each entry's history row in columns of its own, each request's whole answer, each asset's source kind in a column of its own and the entries auto-collapse hid, and the tables of the [catalog of developed picks](design/catalog.md): catalog folders, capture metadata, volumes, picks, collections and the journal of library changes) and operation formats are supported during pre-release development. A catalog made before format 13 is refused; start a new one. Unsupported formats fail explicitly; Luxforge never silently resets or drops them. If a catalog format is rejected, start with a new path using `--catalog /path/to/new-catalog.sqlite` and develop the originals again.

## JSON automation

The headless owner, `luxforge-json`, reads one JSON request per line and writes one response per line. Diagnostics stay off stdout. `cargo xtask build --release` builds it with the editor; `cargo build --release -p luxforge-cli` builds it alone:

```sh
target/release/luxforge-json --catalog /path/to/catalog.sqlite
```

It serves the same modules as the desktop through the same registry, and draws nothing, so its `session.state` reports `renderer` as `{"record": "reference", "reason": null}`: everything it answers is the reference renderer's. `--developer` adds the test modules, the pixel and controls proofs, as the desktop's developer mode does; unlike the desktop, `luxforge-json` reads no flag at launch and is never in developer mode without `--developer`, so what `schema.list` lists never depends on your settings or on how the binary was built. `--proof-endpoint URL` needs developer mode in both, and each refuses it otherwise with the same message.

Keep the process and its input open while requests are in progress. For example, send:

```json
{"id":"schema","method":"schema.list","params":{}}
{"id":"develop","method":"pick.develop","params":{"targets":{"kind":"paths","paths":["/path/to/photo.jpg"]},"into":[],"confirm_removable":true,"mutation":{"request_id":"open-1","actor":"my-client"}}}
```

A photograph comes into the catalog only by being developed ([Developing picks](#developing-picks)), so opening a file is three steps. `pick.develop` of the file's path, into the folder the plan proposes (`into: []`) and with `confirm_removable` (you chose the file, so a file on a card is developed where it is), answers a job: read `job.read` with its `job_id` once it is `ready` (the job records an event naming its `job_id` as it ends, so `events.wait` says when, or poll `job.read`), and take the photograph from its `result`'s `developed[0].asset_id` — a new photograph, or the one that already has the file's bytes — or read why from `failed`. Then `source.prepare {asset_id}` reads and decodes the original and answers another job; once it is `ready` its `result` is the photograph's state, and `job.adopt {job_id}` makes it the client's current photograph. A preparation the client asked for since supersedes an older one: adopting the older is `conflict`. A job whose work fails unexpectedly, a panic included, reads `failed` with an `internal` error, the activity list records it failed, and the next job runs. `job.cancel` removes that client's interest in a preparation; another client's use of the same source continues. Ending the connection cancels its pending work.

Every job the editor runs — preparing a source, an analysis, a module's job, an export or reading a file's previews — is read with `job.read {job_id}` and cancelled with `job.cancel {job_id}`. `job.read` answers `{job_id, kind, status, progress, asset_id?, module_id?, resource_id?, identity?, result?, error?, request_id?}`: `kind` says what the job does (`prepare`, `develop`, `artifacts`, `collect`, `analysis`, `install`, `remove`, `task` or `export`, or one of the catalog's: `index-refresh`, `preview-extract`, `preview-render`, `preview-region`, `develop-picks`, `source-check`, `source-find`, `source-locate`, `batch-preset` or `batch-export`), `status` is `queued`, `running`, `ready`, `failed`, `cancelled` or `superseded`, and only a `ready` job carries `result`, apart from a running `source-find` job, which carries its report so far. A source preparation, an analysis or the job a `preview.read` answers (`preview-extract`, `preview-render`) belongs to the clients that asked for it: only they can read it, and `job.cancel` or disconnecting releases only the caller's interest, so the work stops only when nobody else wants it, and the caller can still read how it ended. Another client's `job.cancel` of such a preview job is refused with `conflict` ("another client is waiting for this preview", its `job_id` in `data`) while a client waits for it, and once none does it stops it for everyone and answers the job. A module's job, an export or another catalog job (a view's background preview reading, an edit's background re-render or a `preview.region` among them) belongs to no client: any client can read it, `job.cancel` stops it for everyone, and disconnecting leaves it running. `job.cancel` answers the job as `job.read` then does; sending it again changes nothing, so it takes no `mutation` envelope. The last 64 finished source jobs and the last 32 of every other kind stay readable. A catalog job — `pick.develop`, `source.check`, `source.locate`, `source.find`, `batch.apply-preset`, `batch.export`, or an `index.refresh` listing — records one event as it ends, however it ends, under your request and naming its `job_id`, as the events it records on the way do: an event naming your job is the moment to read `job.read`, with no need to poll it.

To follow a job without polling, send `job.wait {job_id}` for its current record and change token, then `job.wait {job_id, after: change}` with that token. The answer is `{change, job}`, where `job` has the same shape and access rules as `job.read`. An unchanged live job waits until progress, a partial result or its outcome changes; a finished job answers immediately. Omit `timeout_ms` to wait without a timer, or give 0–30000 milliseconds for an immediate observation or bounded wait. Keep the returned token for the next request. At most 32 waits are held per owner and 16 per client; exhaustion returns `resource-limit`. Closing the connection drops its held wait. A connection serves one request at a time, so use another connection for other commands while waiting.

A source-dependent request after reopen can return `preparation-required` with `error.job_id`. Wait for that job and retry against the current asset revision. `source.prepare` also allows explicit preparation. Loading, hashing, decoding and RAW development run on a bounded worker so other catalog requests can continue.

`source.inspect {asset_id}` reads one photograph's whole interpretation and `asset.state {asset_id}` its current state; `catalog.info` counts the catalog's photographs, and `folder.list` lists its folders with theirs.

A client's history selection is kept per photo. `preview.select {asset_id, entry_id}` previews that entry of that photo only, and the session reports it in `session.preview.selections`, keyed by asset id, as `{entry_id, geometry_from}`; a photo not listed there is at its current entry. While a photo has a selection your edits, undo, redo and drafts of that photo are refused, and `render.sample`, `render.locate`, `render.transform`, `preset.capture` and a query without an `entry_id` answer against that photo's selection; another photo is unaffected, so you can preview one photo's history while you edit another. Select a photo's current entry to return that photo alone; `preview.return-current` returns every photo. At most 16 photos can have a selection at once.

`preview.compare {asset_id, enabled: true, position?: 0..1}` enters the slider, fixing the displayed After entry and framing the Original with the same geometry. `preview.compare {asset_id, position}` moves the divider without advancing the preview generation or rendering; `enabled: false` exits and restores the prior selection. `session.state` reports the fixed entry, previous selection and divider position in `preview.comparison`. The command has no mutation envelope and changes no history.

A request has `id`, `method` and `params`. A success carries the matching `id`, an event `sequence` and `result`; a failure carries a structured `error` with a `code`, a `message` and, for some codes, structured `data`. Act on the code and the data, never on the message's wording: an unavailable effect names it in `data.effect_id`, a full source queue says `data.retry: "after-source-job"` (ask again once a source job ends), a module that does not apply to the photo names `data.source` and `data.module_id`, and a superseded field names `data.source`, `data.field` and `data.by`, the field to use instead. Start with `schema.list` for the authoritative method list. Edit actions are generated from the registered tool modules: `module.list` returns every module with its effects, actions, parameter descriptors (kind, range, unit, default), semantic controls, hint, reset action, canvas title and shortcut and developer flag, and each action `<id>` is callable as `edit.<id>` with its parameters as top-level fields beside `asset_id` and `mutation`. `recipe.describe` lists an entry's layers with each module's summary; `workspace.set` and `session.state` carry the per-client panels, canvas mode, thirds overlay, clipping overlays and GPU preview preference beside the view; every history entry carries its rendered `label`. `history.list` pages history **rows** newest first — `id`, `sequence`, `action_id`, `label`, `actor`, `timestamp_ms`, `undo_parent` and `restore_target`, without the stack, leaving out entries auto-collapse hid unless `collapsed: true` asks for them — and `history.inspect` returns one whole entry with its stack and stored parameters. An edit that collapsed an entry names it in its answer's `collapsed_entry_id`; one that set a control back to where its run began answers `applied` with no `created_entry_id`, and its `current_entry_id` is the entry before the run. Today that is `edit.set-basic` (`temperature`, `tint`, `exposure`, `contrast`, `highlights`, `shadows`, `whites`, `blacks`, `vibrance`, `saturation`), `edit.reset-basic`, `edit.set-look` (`look`, `amount`), `edit.reset-look`, `edit.set-curve` (`luminance`), `edit.reset-curve`, `edit.set-presence` (`texture`, `clarity`, `dehaze`), `edit.reset-presence`, `edit.set-mixer` (a hue, saturation and luminance field per colour band, such as `red-hue`), `edit.reset-mixer`, `edit.transform` (`transform`), Lens selection/reset, Perspective set/reset, the crop module's three actions, `edit.set-vignette` (`amount`, `midpoint`, `roundness`, `feather`), `edit.reset-vignette`, `edit.apply-preset` and the RAW module's development actions; a `--developer` run adds the proofs' actions, such as `edit.set-pixel` (`x`, `y`, `rgb`). Each effect in `module.list` may list `sources`, the source kinds (`jpeg`, `raw`, as `asset.state` reports a photo's `source.kind`) a layer of it may exist on; an effect without `sources` exists on every kind. A module applies to a photo when any of its effects lists that photo's kind, or when it declares no effect. Pass `asset_id` to `module.list` to receive only the modules that apply to that photo, which is the same list you get by filtering the whole one with that rule; an action of a module that does not apply is refused, for example `validation: RAW does not apply to a JPEG photo`; `source.inspect` reports source interpretation and readiness. A module may also declare read-only **queries**, which are generated the same way as `query.<id>`; they take `asset_id`, an optional `entry_id` defaulting to the session's selection, and their own parameters, and they write nothing. The controls proof adds `query.sample-controls-curve` with the active channel's points when `--developer` is enabled; its curve interpolation belongs to that module. The Basic neutral picker uses `query.neutral-sample` (`x`, `y`), the Look section reads its curve from `query.sample-look`, and the Tone curve draws its plot from `query.sample-curve` (`luminance`). Parameters are checked against the descriptors before the module sees them, so every client gets the same structured validation error. A number parameter may declare a `step` and a display `precision` for the control that drives it; they are hints, and a request is never rounded to them. An action listed with `patch: true` takes whichever of its fields you name: the fields you send are validated, nothing declared is filled in, the module merges them over what it already stores, the entry records the fields as sent, and a patch that changes nothing writes no entry. `version.create`, `version.list`, `version.delete` and `history.lineage` cover named states and the undo-parent chain. The `preset.*` methods cover the preset library, and `edit.apply-preset` applies one (below). `render.sample` reads one rendered pixel, `render.locate` maps a rendered pixel back to the content pixel it shows, and `render.transform` answers the whole geometry tail as an identity-stamped mapping (below). The `mask.*` methods cover masks, and every action of a maskable module takes an optional `mask` (below). `activity.list` and `resources.read` report the editor's running work and its own resource use ([below](#activity-and-resources)). Mutations require `asset_id` and a `mutation` object:

```json
{"id":"rotate","method":"edit.transform","params":{"asset_id":"asset-…","mutation":{"expected_revision":0,"request_id":"rotate-1","actor":"my-client"},"transform":"rotate-right"}}
```

Every method that changes anything carries a `mutation` envelope, and `schema.list` names which one in the method's `mutation` field. A change to something with a revision — an asset's edits, masks and history, a draft's commit, or a module's settings — carries `{expected_revision, request_id, actor}`, and a stale revision is a `conflict`. Every other change — the preset library, versions, `artifact.collect`, `export.jpeg`, picks, Develops, sending back and library undo and redo, and module permissions, resources and jobs — carries `{request_id, actor}` and no revision. Either way, sending the same request again with the same `request_id` returns the first answer marked `deduplicated: true` and changes nothing twice, so a client that lost an answer can simply retry; the same `request_id` with a different request is a `conflict`. Every method refuses a parameter it does not declare, including one that takes none. Every method's entry in `schema.list` names its `required` and `optional` fields and lists its typed `parameters` in the shape `module.list` gives an action's, the host's own methods included: `asset_id` is `{"kind": "identity", "of": "asset"}` (likewise `entry`, `draft`, `job` and `preset`), `history.list`'s `limit` is an integer within 1..=100 with its default of 50, a path or a preset file's contents is `text` with a byte limit, and a structured field such as `view.set`'s `zoom` is `json`, whose notes give its shape. A value outside its declared kind is refused before the method runs, in the words a module parameter's check uses, for example `parameter limit must be an integer within 1..=100`.

RAW actions use the same mutation envelope:

| Method | Parameters |
| --- | --- |
| `edit.set-raw` | a field patch of `temperature` (2000–12000 K), `tint` (−100..+100) and `white-balance` (`as-shot` or `custom`) |
| `edit.pick-raw-neutral` | `x`, `y` in upright original-content coordinates |

`edit.set-raw` changes only the fields it is sent: a `temperature` keeps the tint in force, and a `tint` the temperature in force. `{"white-balance": "as-shot"}` returns the development to the camera's own white balance, the Original's; `as-shot` beside a temperature or tint, and `custom` alone, are refused. `render.locate` maps an edited-image point to the content coordinates needed by the picker. Explicit `edit.set-raw-red-gain` and `edit.set-raw-blue-gain` actions remain available to programs; each preserves the other effective camera gain and accepts 0.01–32×. The RAW development's effect declares `sources: ["raw"]`, so RAW actions are refused on a JPEG photo and the desktop offers no RAW control, palette entry or sensor pick for one. On a RAW photo's global target, `edit.set-basic`'s `temperature` and `tint` are refused, naming `set-raw`, because the development's white balance is their one path there; inside a mask they are accepted. `schema.list` lists this as the parameters' `superseded`. `recipe.describe` reports the RAW layer's `values` as `white-balance`, `temperature` and `tint`: a custom temperature and tint as stored, and otherwise the temperature and tint whose gains are the gains in force — the camera's as-shot gains under As shot, or the gains a neutral pick or an explicit gain set — with 6504 and 0 when none in range reproduces them. In `module.list`, Basic's White balance controls carry `variants` for `raw`: the control the RAW module provides in that place on a RAW photo's global target, such as Temperature over `set-raw` with `"reset": {"action": "set-raw", "preset": {"white-balance": "as-shot"}}`, the request a client sends to reset it.

`edit.crop-fit` (`aspect`, optional `aspect-width`/`aspect-height` with `aspect: "custom"`, `angle`, optional `center-x`/`center-y`) fits the largest rectangle of a ratio about a center without computing the box geometry by hand:

```json
{"id":"crop-169","method":"edit.crop-fit","params":{"asset_id":"asset-…","mutation":{"expected_revision":3,"request_id":"crop-1","actor":"my-client"},"aspect":"16:9"}}
```

`edit.crop` (`angle`, `x`, `y`, `width`, `height`) sets the straightening angle and rectangle exactly as persisted, normalized to the rotated box:

```json
{"id":"crop-exact","method":"edit.crop","params":{"asset_id":"asset-…","mutation":{"expected_revision":4,"request_id":"crop-2","actor":"my-client"},"angle":0,"x":0.1,"y":0.1,"width":0.8,"height":0.6}}
```

Both actions reject a rectangle that would need an empty corner with a structured `validation` error naming the offending corner, its mapped input coordinates and how far outside the input stage it lands. Every crop request updates the stack's one crop layer in place, keeping its layer ID, or appends one when the stack has none; a request equal to the saved payload is a no-op. The rectangle is normalized to the crop's input stage, which already includes every transform, so it addresses the photograph as it is displayed: after `edit.transform` the crop layer's payload is re-expressed in the turned stage, and `recipe.describe` reports those values. `edit.crop-reset` takes no parameters, returns an existing crop layer to the neutral payload (`angle 0, x 0, y 0, width 1, height 1`) and is a no-op without one.

`edit.set-basic` is a field patch over the Basic adjustments. `temperature` and `tint` are −100 to +100 in steps of 1, shown as whole numbers: positive temperature warms the image and negative cools it, positive tint is magenta and negative is green. They are a relative correction of the image's existing rendering — a JPEG as decoded, or inside a mask a RAW as developed at its own white balance — not the camera's Kelvin value, which is not recoverable from a JPEG. On a RAW photo's global target they are refused in favour of `edit.set-raw`. `exposure` is −5.00 to +5.00 EV in steps of 0.01, shown to two decimals, multiplying the image's linear-light channels by `2^EV`: on a JPEG it corrects the rendered image, so it cannot recover detail a clipped plateau no longer holds, and on a RAW photo it multiplies the developed linear planes, which keep their headroom until the image is rendered. The five Tone fields `contrast`, `highlights`, `shadows`, `whites` and `blacks` (each −100 to +100, step 1, no decimals) compose one frozen global luminance curve — Whites/Blacks, then Highlights/Shadows, then Contrast — documented in [Basic Tone](design/basic-tone.md). `vibrance` and `saturation` are each −100 to +100 in steps of 1, shown to zero decimals, scaling Oklab chroma about the achromatic axis: `saturation` uniformly, and `−100` is exact neutral grayscale, not merely a strong desaturation; `vibrance` with more gain for near-neutral colour than for colour already close to the sRGB gamut edge, and reduced gain in a skin-like hue band as a colour heuristic, not detection. The internal order is fixed regardless of edit order: white balance, then exposure, then Tone, then vibrance, then saturation.

```json
{"id":"expose","method":"edit.set-basic","params":{"asset_id":"asset-…","mutation":{"expected_revision":5,"request_id":"expose-1","actor":"my-client"},"exposure":0.5}}
{"id":"warm","method":"edit.set-basic","params":{"asset_id":"asset-…","mutation":{"expected_revision":6,"request_id":"warm-1","actor":"my-client"},"temperature":20,"tint":-5}}
{"id":"tone","method":"edit.set-basic","params":{"asset_id":"asset-…","mutation":{"expected_revision":7,"request_id":"tone-1","actor":"my-client"},"contrast":20,"shadows":15}}
```

The first non-neutral value adds the stack's one Basic layer before the quarter-turns, reflections and crop, and every later value updates that same layer in place; a value equal to the stored one is a no-op. A field you do not name keeps its stored value. `edit.reset-basic` takes no parameters, returns that layer to neutral and keeps its layer ID, and is a no-op without one or when it is already neutral. `recipe.describe` reports the layer's `values`, so a client can seed its controls from the entry it displays.

`edit.set-look` sets a RAW photo's look: `look` is `standard`, which writes the current Standard look's curve, colour gain and highlight knee into the layer, or `neutral`, the bare development; `amount` (0 to 200) changes the amount of the look in force and is refused on a Neutral look. Either field may be sent alone. The stored layer holds the resolved curve, so a later change to Standard never changes a photo you edited. `edit.reset-look` returns to Standard at 100. `look: camera` (Match camera) is not available yet and is refused. `query.sample-look {asset_id}` returns the look in force, its `chroma` gain, its `amount` and `points`, 257 samples of its tone curve over the encoded tones it covers; it reads no pixel. On a JPEG every look action is refused, as for any module that does not apply.

`edit.set-curve` sets the Tone curve's one field, `luminance`: 2 to 16 `[x, y]` points, each coordinate 0 to 1, `x` strictly increasing and `y` never decreasing, where `x` is the encoded tone the histogram is drawn in and `y` the tone it becomes. The points are stored exactly as sent; a list the curve cannot hold is refused by name, for example `parameter luminance has an invalid curve point 2`. `edit.reset-curve` returns the layer to the diagonal `[[0, 0], [1, 1]]`, keeping its layer ID. `query.sample-curve {asset_id, luminance}` returns `points`, 257 samples `[i / 256, C(i / 256)]` of the curve through the points you submit, the curve the pixels receive; it reads no pixel and changes nothing.

```json
{"id":"curve","method":"edit.set-curve","params":{"asset_id":"asset-…","mutation":{"expected_revision":8,"request_id":"curve-1","actor":"my-client"},"luminance":[[0,0],[0.25,0.2],[0.75,0.8],[1,1]]}}
```

### Presets

`preset.list` returns the library, sorted by group, then name, each record with its `id`, `name`, `group`, `settings`, `origin`, the counts of its import `report` (`null` for a preset made in Luxforge) and any `unavailable` actions. `preset.read {preset_id}` adds the full report and the imported file's text. A settings set maps field-patch actions to the fields each one sets, for example `{"set-basic": {"exposure": 0.35, "contrast": 12}, "set-vignette": {"amount": -18}}`. Apply one with `edit.apply-preset`, which takes the set, a `name` for the history label and optionally the library `preset-id` as provenance:

```json
{"id":"preset","method":"edit.apply-preset","params":{"asset_id":"asset-…","mutation":{"expected_revision":8,"request_id":"preset-1","actor":"my-client"},"name":"Soft film","preset-id":"preset-…","settings":{"set-basic":{"exposure":0.35,"contrast":12},"set-vignette":{"amount":-18}}}}
```

The host runs each named action exactly as that action would run alone without a `mask`, in alphabetical order of the action names, and commits the result once as one entry, "Preset: Soft film". A preset therefore edits the global layer of a masked photo, creating one if there is none, and never a masked layer. An unknown or non-patch action, an action of an unavailable module that applies to the photo, or a field its action refuses, refuses the whole preset and writes nothing.

| Method | Parameters | Does |
| --- | --- | --- |
| `preset.capture` | `asset_id`, `fields`, optional `entry_id` | Reads a settings set from an entry's stack (default: the displayed one). `fields` maps each action to an array of parameter names or `true` for all of them. Each action reads its global layer, never a masked one; without one, a field takes its default |
| `preset.create` | `name`, `settings`, `mutation`, optional `group` | Saves a preset; the group defaults to `User presets` |
| `preset.update` | `preset_id`, `mutation`, optional `name`, `group`, `settings` | Renames, regroups or replaces the settings |
| `preset.delete` | `preset_id`, `mutation` | Removes it; a no-op when absent |
| `preset.export` | `preset_id` | Returns `file_name` and `content`, a `.lfpreset` document |
| `preset.inspect` | `content`, optional `file_name` | Returns the preset and report an import would produce, storing nothing |
| `preset.import` | `content`, `mutation`, optional `file_name`, `name`, `group` | Imports a Lightroom `.xmp` or `.lrtemplate` preset or a `.lfpreset` document from its text; `name` and `group` override the file's |

A (group, name) pair is unique ignoring case, and a duplicate is a `conflict`. The library holds at most 1,000 presets. Create, update, delete and import take the `{request_id, actor}` envelope, and the preset records its `actor`. They emit events like every mutation, so another client's desktop refreshes its Presets section.

### The neutral picker

`query.neutral-sample {asset_id, entry_id?, x, y}` is the neutral picker, and it is a **query**: a read-only question about a stored stack that writes no history entry, emits no event and changes nothing. `x` and `y` are pixels of the content stage — the image after EXIF orientation, the stage the Basic layer receives — so map a pixel of the rendered image to them with `render.locate` first, exactly as the canvas mode does. `entry_id` defaults to the session's selection, so a client previewing a historical entry may pick in it.

It averages up to a 5 × 5 patch centred on that pixel in linear light, clipped at the stage's edges rather than clamped, evaluated **before** the Basic layer, and answers the temperature and tint that make the average neutral:

```json
{"id":"pick","method":"render.locate","params":{"asset_id":"asset-…","x":812,"y":544}}
{"id":"neutral","method":"query.neutral-sample","params":{"asset_id":"asset-…","x":1024,"y":768}}
```

```json
{"id":"neutral","sequence":6,"result":{"temperature":20,"tint":-5,"patch":{"x":1022,"y":766,"width":5,"height":5,"pixels":[[164,151,140]," … "],"mean_linear":[0.3706,0.3128,0.2664]}}}
```

Apply the answer with an ordinary `edit.set-basic` carrying its `temperature` and `tint`; that is the one entry the pick costs, and cancelling before you send it commits nothing. Because the patch is read before the Basic layer, picking the same spot twice answers the same way however strong a correction is already set.

The picker never guesses. A patch with a pixel at code 0 or 255, a patch too dark to carry reliable colour, a non-finite value, a correction the −100..100 axes cannot represent and a point outside the stage are each refused with a `validation` error whose message begins with its reason — `clipped:`, `near-black:`, `non-finite:`, `out-of-range:` or `outside the stage:` — and nothing is committed or clamped. In the workspace the picker is a canvas mode named Neutral picker, entered from the Neutral picker button in the White balance group, with `W` or from the command palette — the button is a declared `picker` control of the Basic module, and pressing it is one `workspace.set` — and it runs this same query with the same coordinates and the same solver.

A gesture that changes a setting over and over — a slider drag, a held arrow key — is a **draft**, so it costs one history entry instead of one per step. `draft.begin {asset_id, action}` opens this client's one draft and answers `{draft_id, action, asset_id, base_revision, draft_revision, fields, conflicted}`; `draft.set {draft_id, fields}` validates and merges the named fields against the action's parameter descriptors and counts up `draft_revision`; `draft.read {draft_id}` reads it back; `draft.cancel {draft_id}` ends it and commits nothing; `draft.commit {draft_id, mutation}` runs the action with the accumulated fields and ends the draft, returning the ordinary mutation result, so a gesture that returned to its start is a `no-op` with no entry. Only the commit changes the catalog; everything else is session state, reported by `session.state` and gone when the client disconnects. A draft is refused while this client already holds one, while a historical entry is previewed, for an unknown action, and for one its commit would refuse for this kind of photo, such as `set-raw` on a JPEG; `draft.set` likewise refuses a field its commit would, such as `set-basic`'s `temperature` on a RAW photo's global target, with the commit's own message and without changing the draft. Nothing is committed until the commit, and `render.sample {asset_id, x, y, draft_id}` evaluates the draft's settings so a readout during a gesture matches what committing would produce.

```json
{"id":"begin","method":"draft.begin","params":{"asset_id":"asset-…","action":"crop"}}
{"id":"drag","method":"draft.set","params":{"draft_id":"draft-…","fields":{"angle":2.5}}}
{"id":"release","method":"draft.commit","params":{"draft_id":"draft-…","mutation":{"expected_revision":5,"request_id":"straighten-1","actor":"my-client"}}}
```

`mutation.expected_revision` must be the draft's `base_revision`. If any client commits while the draft is open, the draft is kept and marked `conflicted: true`; committing it is then refused with a `conflict`. `draft.cancel` discards the gesture, or `draft.reapply {draft_id}` rebases it on the current revision and keeps only the fields this client set, so an unrelated field another client changed is retained by the commit that follows.

### Masks

Masks are the host's own objects, and their commands are published as one **host descriptor**, `luxforge.masks`, in the shape a module's descriptor takes: `module.list` and `schema.list` list it under `host`, beside `modules`, with the commands as its `actions`, `mask.list` and `mask.sample-input` as its `queries` and the Masks panel's widgets as its `controls`, and `schema.list` lists each command as a method of its own name. A command is resolved, checked, deduplicated, planned, drafted and committed through the same action path a module's action is. `mask.list {asset_id, entry_id?}` is read-only and answers every mask with its `amount`, `invert`, its `components` — each with its `id`, `index`, `name`, `mode`, `invert`, `kind`, `payload`, whether this build can evaluate the kind (`available`) and its `strokes` — and the `layers` bound to it. `strokes` lists the strokes a brush payload references, in the order they compose, each as `{id, settings}` where `settings` is `{erase, size, feather, flow, colour}` read from the stroke store (`size` the stored radius in picture heights, `feather` and `flow` whole percentages, `colour` the held `{seed, refine}` or `null`), or `null` when the store does not hold that stroke; it is empty for every other kind. `recipe.describe` reports the same relation from the other side, naming each layer's `mask`, so a client reading the processing order can tell a masked layer from a global one without a second question.

The geometry commands are **generated per component kind**, because one command carrying a kind and every kind's fields could not be declared honestly: `mask.create-linear {x0, y0, x1, y1}` creates a mask whose first component is that gradient, `mask.add-linear {mask, mode, …}` adds a further component, and `mask.set-linear {mask, component, …}` patches one component's geometry. `linear`, `radial`, `luminance-range`, `colour-range` and `brush` are the kinds this build registers, and the first four generate that trio of commands each; a **brush** declares no geometry, because its shape is a drawn path rather than a set of numbers, so it has no `mask.create-brush`, `mask.add-brush` or `mask.set-brush` and reaches a mask through `mask.add-stroke` instead. A colour range's swatches are not a declared parameter either, so they are edited one at a time through `mask.add-colour-range-sample` and `mask.delete-colour-range-sample`. The kind-independent commands keep one name each: `mask.delete`, `mask.rename {name}`, `mask.duplicate`, `mask.set-amount {amount}`, `mask.set-invert {invert}`, `mask.reorder {index}`, `mask.set-component-mode {mode}`, `mask.set-component-invert {invert}`, `mask.rename-component {name}`, `mask.delete-component`, `mask.reorder-component {index}` and `mask.delete-stroke {mask, component, stroke}`.

`mask.sample-input {mask, x, y}` is the family's second read-only method: it answers `r`, `g` and `b`
— the linear-sRGB pixel the adjustment that mask modulates *receives* at one content position of the
stage that adjustment's layer sees — plus the position and that stage's size. It is where a canvas
pick gets the colour a colour range's swatch is, and it exists because a client must not read that
colour off the frame: the frame holds the adjustment's output, which is a different colour wherever
the adjustment does anything. The values are 32-bit floats, read from the GPU with the desktop open,
and the answer names the `renderer` that read them as `render.sample`'s does. A mask no layer is bound
to has no adjustment to be the input of and is refused by name. `mask.add-stroke` takes `limit_to_colour` and `colour_refine` beside its path and its
brush; it carries **no colour**, because the host reads the pixel at the stroke's first position
itself, and a stroke limited on a mask no layer carries is refused by name for the same reason.

The `mask`, `component` and `stroke` a command addresses are declared parameters of the **identity** kind (`{"kind": "identity", "of": "mask"}`), listed first among its parameters, and a rename's `name` is one of the string kind; every other field — an endpoint, an amount, a mode, an inversion — is a declared parameter too, and all of them go through the same generic check a module action's do. A malformed identity is refused with, for example, `parameter mask must be a mask identity`, and a required identity stays required on a patch: `mask.set-linear` always names its mask and component. Every one of these is an ordinary mutation with a revision check, request deduplication, one history entry and one immutable snapshot. A retry with the same `request_id` answers with the whole first answer, the `mask` and `component` a create minted included, because the answer is stored with the request. Each drafts through `draft.*` exactly as a module action does — `draft.begin` names the mask and component the gesture edits, and must name every identity its command requires — so a whole gradient drag costs one entry.

An effect declares `maskable`, and the host then puts one optional top-level `mask` field on every action of that effect's module, checked as a mask identity and listed as the method's `target` in `schema.list`. `luxforge.basic`, `luxforge.detail`, `luxforge.mixer` and `luxforge.presence` declare it; sending `mask` to any other action is a `validation` error rather than being ignored. `edit.set-basic {asset_id, exposure}` edits the global Basic layer; `edit.set-basic {asset_id, mask, exposure}` edits the Basic layer bound to that mask, committing it on the first non-neutral field and updating it in place afterwards. At most one layer of an effect exists per target, where the global layer and each mask are distinct targets.

```json
{"id":"draw","method":"mask.create-linear","params":{"asset_id":"asset-…","mutation":{"expected_revision":0,"request_id":"sky-1","actor":"my-client"},"x0":0.5,"y0":0.3,"x1":0.5,"y1":0.7}}
{"id":"draw","sequence":4,"result":{"outcome":"applied","revision":1,"current_entry_id":"entry-…","created_entry_id":"entry-…","deduplicated":false,"label":"Add linear","mask":"mask-…","component":"component-…"}}
{"id":"lift","method":"edit.set-basic","params":{"asset_id":"asset-…","mutation":{"expected_revision":1,"request_id":"sky-2","actor":"my-client"},"mask":"mask-…","exposure":0.8}}
```

Positions are normalized fractions of the **content stage** — the picture after EXIF orientation and before the geometry tail — in the range −1 to 2, so a gradient dragged from off the canvas is an ordinary edit. Distances are in mask-space units, where one unit is the content stage's height. Storing geometry there is what makes a mask travel with the picture through every quarter-turn, reflection and crop, and what keeps a masked recipe resolution independent.

A mask attaches only to a layer before the geometry tail, so a `finish`- or `geometry`-stage layer carrying one is refused. A component of a kind this build cannot evaluate, or a stroke the store has lost, is retained byte for byte and reported; any render, sample or overlay that has to draw that mask refuses it by name, and so does appending an edit to the stack or restoring it, exactly as for a layer whose effect has no provider. A mask is never rendered as if it were not there.

`workspace.set` also accepts `mask_overlay` (`off`, `tint`, `mask-on-black`, `image-on-black`) and `mask_overlay_colour` (`green`, `white`), reported by `session.state`. Both are per-client view state: they change no pixels of the saved recipe and no history, and hiding a mask's overlay does not stop that mask applying.

`render.sample {asset_id, x, y, draft_id?}` answers one pixel of the rendered image, of the session's selected entry or of this client's open draft, as `{entry_id, snapshot_id, source_fingerprint, width, height, x, y, rgba, draft?, source_detail_ready, renderer}`; a pixel outside the rendered image is a `validation` error naming the stage. The answer names the entry and snapshot it was evaluated against, and its response `sequence` is the event sequence when the editor planned it, so a client that sees a later event knows a newer stack may exist. Every pixel is read off the editor's catalog thread, so other clients are answered meanwhile. With the desktop open it is read from the GPU: one tile of the stack around the pixel, the byte the picture shows there at 100%, and `renderer` is `{"record": "gpu", "reason": null}`. Where the GPU cannot draw the stack — a pixel proof's layer, a launch with `--no-gpu-render` — and always from `luxforge-json`, the reference renderer reads it, `renderer` naming the reference and why (`pixel-stage`, `refused`; no reason from `luxforge-json`, which has no GPU); through a Detail or Presence layer the reference renders that layer's whole picture for the read, which takes about as long as rendering the photograph through it. When nine reads are already waiting it answers `resource-limit`, and a retry after an answer succeeds. The GPU and the reference may differ by a code at a pixel, within the display limit the release gate holds them to.

`render.transform {asset_id, entry_id?, draft_id?}` answers the whole geometry tail, so a client editing in content coordinates can map pointer positions without a request per move. It returns `{entry_id, snapshot_id, source_fingerprint, draft?, content: {width, height}, output: {width, height}, mapping, mapping_sha256}`. An affine tail's `mapping` is `{kind: "affine", forward: [6], inverse: [6]}`; a nonlinear tail carries `kind: "warp"`, bounded steps, cover scales and its local minification bound. The core's `GeometryMap` evaluates either form with `to_output`, `to_content` and `local_scale_at`; clients use its hash to correlate a displayed frame, pointer map and coverage cache. Coordinates are continuous pixel edges: pixel index `n` has its centre at `n + 0.5`, and a stage spans `0..width` by `0..height`. A coordinate outside the output stage was cropped away. Mapping failures are explicit. A draft whose base revision changed returns `conflict` until it is reapplied. An unavailable stack returns its own reason. `render.locate` maps one rendered pixel back for a pick.

Read-only **analysis** answers "what does this image actually contain": an exact RGB histogram and the output clipping counters of one evaluated stack, with no GUI and without changing what the editor is showing. `analysis.request {asset_id, target}` returns the job as `job.read` does, right away, where `target` is `{"kind":"current"}`, `{"kind":"entry","entry_id":"entry-…"}` for a frozen historical entry, or `{"kind":"draft","draft_id":"draft-…"}` for this client's own open draft at the revision it holds now. Read it with `job.read {job_id}`, which carries its `identity` and, once it is `ready`, the report as its `result`, and cancel it with `job.cancel {job_id}`; a job this client did not request is a `validation` error. None of these changes anything or emits an event.

```json
{"id":"hist","method":"analysis.request","params":{"asset_id":"asset-…","target":{"kind":"current"}}}
{"id":"read","method":"job.read","params":{"job_id":"job-…"}}
```

Only a `ready` analysis carries a report, so no status can be mistaken for a valid but empty histogram. A report holds three 256-entry arrays `r`, `g`, `b` of raw counts — each summing to the output pixel count — plus the endpoint counters `r0 g0 b0 r255 g255 b255 any_shadow any_highlight all_shadow all_highlight both`, the output `width`/`height` and the `domain`. These describe the **rendered sRGB output** after crop and edits; endpoint counts are output clipping warnings, not evidence about the original capture. The `identity` beside them names the asset, source fingerprint, entry, snapshot, the SHA-256 `recipe_hash` of the effective recipe, the `{draft_id, draft_revision}` when a draft was analysed, the output dimensions and the domain, so a result is never attached to the wrong image. One worker runs one job at a time with one replaceable pending job: a third request supersedes the pending one, which reads `superseded` and may simply be requested again. Identical requests from different clients share one job, and a cancel or a disconnect releases only that client's interest. `workspace.set` also accepts `clip_shadows` and `clip_highlights` booleans, reported by `session.state`; they are per-client view state and change no pixels, no saved recipe and no histogram, and they are the same two flags the histogram's triangles, the title bar's Clipping button and `J` set. Asking for the stack the desktop is displaying costs no render at all: the desktop's own preview worker reduces each frame it draws and hands the report to the owner, so a request for that identity is answered from it. `render.sample` (of the displayed draft, when one is on screen) evaluates one pixel of the compiled recipe and rasterizes nothing, so any client can read the same codes at any coordinate; the desktop itself reads nothing under the pointer.

### Export

`export.jpeg` writes one saved entry's render to a new JPEG: baseline, quality 90, 8-bit sRGB with an embedded sRGB profile, at the recipe's output size (after orientation, transforms and crop; nothing is resized). It never touches the original, the catalog's history or any existing file. `export.plan {asset_id, entry_id?}` answers `{asset_id, entry_id, snapshot_id, width, height, suggested}` without rendering anything: the output size of the current entry, or of the saved entry `entry_id` names, and `suggested`, an absolute path `<original name>-edited.jpg` beside the original, counting up to `-edited-2.jpg` and so on when that name is taken, or `null` when no free name is found among the first 64. A stack the editor cannot evaluate, such as one whose provider is unavailable, is refused with that reason.

```json
{"id":"plan","method":"export.plan","params":{"asset_id":"asset-…"}}
{"id":"export","method":"export.jpeg","params":{"asset_id":"asset-…","destination":"/Users/me/Pictures/DSC_0042-edited.jpg","keep_metadata":false,"mutation":{"request_id":"export-1","actor":"my-client"}}}
{"id":"progress","method":"job.read","params":{"job_id":"job-…"}}
```

`export.jpeg {asset_id, entry_id?, destination, keep_metadata?, pixels_per_inch?, reference?, mutation}` takes the `{request_id, actor}` envelope. The destination is an absolute path ending `.jpg` or `.jpeg` whose folder exists; anything already at that path, a file, a folder or a link, is refused with `conflict`, so nothing is ever replaced, the original included. The entry is frozen when the request is accepted: a later edit by any client does not change what is written, and a draft is never exported. `pixels_per_inch`, from 1 to 65535, is the density the file's JFIF header records, which sizes it in viewers such as Preview and in print; without it the header records none. The editor's GPU renders the export in full-resolution tiles that the encoder takes as they arrive, within the display limit of the reference renderer's export, identical run to run on one machine and driver and possibly different in the last digit across machines. `reference: true` asks for the reference renderer's export instead, rendered on the CPU. The reference also renders it when the client's owner has no GPU, as `luxforge-json`'s does, and when the GPU cannot draw the stack, at once or part-way, in which case the export starts again from nothing on the reference: one file is never both renderers' pixels. The answer is `{job_id, status, asset_id, entry_id, snapshot_id, destination, width, height, keep_metadata, pixels_per_inch, reference, deduplicated}`; the same request again returns that first answer and writes no second file. A source that is not prepared answers `preparation-required` with the job to wait for, as analysis does, and a missing or changed original answers `source-unavailable`. Metadata is off by default and the file then carries no EXIF, IPTC or XMP at all. With `keep_metadata: true` it carries one EXIF segment with the original's supported descriptive, camera, capture and GPS fields, Orientation 1, the colour space, the pixel size and the software; no thumbnail, maker note or serial number is copied ([the field list](design/export.md#keep-metadata)).

Read the export with `job.read {job_id}`: its `kind` is `export`, its `status` is `queued`, `running`, `ready`, `failed` or `cancelled`, and `progress.message` names the phase: `rendering`, `encoding` (with `progress.fraction`) or `writing`. A ready export's `result` is `{path, bytes, width, height, metadata, renderer}`, where `metadata` lists the EXIF fields written from the original and `renderer` names the renderer that rendered the file: `{"record": "gpu", "reason": null}`, or `{"record": "reference", "reason": ...}` with why — `requested` for `reference: true`, `surface-pending` before the desktop has named its graphics adapter (as its window opens on a computer with one, once it has drawn a photograph on one with several), `no-adapter`, `refused` (`--no-gpu-render`), `device-lost`, `adapter-mismatch`, `tiles-budget`, or the GPU's own code for a stack it cannot draw, such as `pixel-stage` for a layer no GPU program replaces — and `{"record": "reference", "reason": null}` from `luxforge-json`, whose only renderer is the reference. `schema.list`'s `renderer` block lists the reasons. `job.cancel {job_id}` stops an export for every client: a waiting one never starts, and a running one stops within a few rows and removes its temporary file, answering as `job.read` does. Exports run one at a time, beside previews and analysis; four more may wait, and a sixth is refused with `resource-limit`. Any client may read or cancel any export, the last 32 finished ones stay readable, disconnecting does not cancel an export, and a finished one records an `export.jpeg` event under its request.

### Browsing files and the catalog

The catalog's browsing methods work over the index of the files Luxforge has read and over the photographs you developed ([catalog design](design/catalog.md)). The desktop's Select workspace browses through them ([Select](#select)). The index is filled by `index.refresh` over the folders you add (`index.add-folder`) and the cards and folders you browse; `cargo xtask generate-catalog` writes generated ones for testing. The sections after this one cover the volumes and the index, previews and the 100% focus check, picks and the journal of library changes, developing picks, catalog folders and collections, batches, removing, and originals that moved.

`event.list {month?, query?}` lists the events over the files of the indexed folders and mounted cards, newest first with the Undated events last: `{events: [{id, name, label, place?, first_day?, last_day?, months, cameras, count, picked, offline, roots, volumes, undated}], months: [{month, events, files, picked}]}`, where `label` is the name without its dates. `month` (`YYYY-MM`) keeps the events listed under that month; `query` keeps those whose name, place, cameras or dates contain it ignoring case, or whose days span a `YYYY-MM-DD` it names. `months` counts every month the matching events are listed under, with the files taken that month and their picks.

`browse.view` evaluates a query into your one view, which the editor holds for your connection, and answers its summary without a row:

```json
{"id":"view","method":"browse.view","params":{"source":{"kind":"event","event_id":"event-…"},"filter":{"without_pick":true,"cameras":["NIKON CORPORATION|NIKON Z 8|3001234"]}}}
{"id":"rows","method":"browse.rows","params":{"from":0,"count":200,"revision":1}}
{"id":"select","method":"browse.select","params":{"mode":"add","range":{"start":10,"len":6},"active":12,"revision":1}}
```

- **Source.** Files: `{kind: event, event_id}`, `{kind: folder, path, subfolders?}` (an absolute path; `subfolders` defaults to false) or `{kind: card, volume_id}`. Photographs: `{kind: all-photographs}`, `{kind: recently-developed, days?}` (30 by default), `{kind: catalog-folder, folder_id, subfolders?}` (true by default), `{kind: collection, collection_id}` (a smart collection evaluates its stored query, and finds nothing from a catalog folder or collection it names that has since been merged away or deleted), `{kind: missing-originals}` and `{kind: removed}`; only Removed shows removed photographs.
- **Filter.** Every condition is optional and they combine with AND, the values of one list with OR: `text` (file names, places, cameras and lenses, ignoring case), `picked` and `without_pick` (files), `cameras` (body keys `make|model|serial`; `""` is no camera recorded), `lenses`, `kinds` (`jpeg`, `raw`), `edited` (photographs with history beyond their Original), `dates` (`{from, to}`, camera-local days, inclusive) and `places`. `without_pick` keeps the moments none of whose frames is picked and the unpicked singles; moments are decided over the whole source, grouped Day › Camera › Moment with the query's thresholds, before the other conditions.
- **Sort and grouping.** `sort` is `{key: capture-time | file-name | date-developed | last-edited, descending?}`, capture time earliest first by default; the last two sort photographs only. `grouping` (`day-camera-moment`, `day`, `none`) applies under the capture-time sort only. Equal keys fall to capture time (undated last), then the file name ignoring case, then the path or the photograph. `thresholds` overrides any of the moment and event rules.
- **Summary.** `{revision, query, count, picked, in_catalog, unavailable, groups: {days, cameras, moments}, library_sequence, index_revision}`: `query` with every default filled in, and `groups` the layout a grouped grid draws from, positions `start` to `start + len`. A source of more than 1,000,000 items is refused with `resource-limit`.

`browse.rows {from, count, revision?}` answers positions `from` to `from + count` (at most 1000, fewer at the view's end): each row's `position`, `file_id` or `asset_id`, `path`, `file_name`, `kind`, `dimensions`, `orientation`, `capture` (the camera's own time text), `place`, `camera`, `lens`, `exposure`, `moment: {index, frame}` into the summary's moments, `picked`, `developed_as` (the photograph a file already is), `edited`, `availability` (`available`, `offline`, `missing`, `changed`) and `preview` (`ready`, `thumbnail`, `pending`, `unavailable`). `browse.facets {source, filter?, facets}` counts the values of `date`, `place`, `camera`, `lens`, `kind` and `pick` (files only), most frequent first; each count is exactly the size of the view the same source and filter give with that facet's own condition set to that value, and a value without `value` counts the items that record none.

`browse.select {mode?, items?, range?, all?, active?, revision?}` changes your selection and answers your session: the union of `items` (`[{file_id}]` or `[{asset_id}]`), `range` (`{start, len}`) and `all` is what `mode` (`replace`, the default, `add`, `remove` or `toggle`) applies; without any of them only `active` moves, and `{"all": false}` selects none. It writes nothing. `session.state` reports the view as `browse: {query, revision, count, stale, selection: {count, ranges, active}}`, the selection as disjoint ascending position ranges. Evaluating the view again carries the selection over to the same items at their new positions.

A request naming another `revision` is refused with `conflict`. A view is stamped with the catalog's latest library change and the index's revision; once either moves on it is `stale`. A stale view still answers rows for its items, but a window whose file has gone is a `conflict`: evaluate it again. A request that targets the selection of a stale view evaluates it again first and goes ahead when the selection still names the same items, and is refused with `conflict` when it does not; `pick.plan` and `pick.develop` with no targets take the view's picks as they are now.

### Volumes, folders and the index

Luxforge reads the folders you browse into its **index**, beside the catalog, and never writes to them: it lists the supported files (JPEG and the RAW formats Luxforge develops, by extension) and reads each one's header, never its image. It skips hidden files and folders, macOS packages such as a Photos library, other applications' caches such as Lightroom's `.lrdata` and Capture One's `CaptureOne` folders, system folders, and its own index and artifact directories; it follows no symbolic link and does not cross into another volume.

- `volume.list` answers the mounted volumes, the startup disk first, each `{volume: {id, mount_point, label, removable, platform_id?, last_seen_ms}, offline, card, startup}`, then the volumes the catalog knows that are not connected, with `offline: true`. A volume's `id` stays the same each time it is connected when the platform gives it a UUID (every local volume on macOS, cards included).
- `card.list` answers the connected camera cards, the volumes with a `DCIM` folder: `{volume, dcim, files?, cameras}`, where `files` is what the card's last listing found and `cameras` the bodies its headers name.
- `disk.folders {path}` answers the subfolders of an absolute folder, `{path, folders: [{name, path}], truncated}`, in name order without what indexing skips; start from a volume's `mount_point`. It answers at most 2,000 folders and says `truncated` past them.
- `index.refresh {source}` lists a source again: `{"kind": "folder", "path": ...}` for any folder, `{"kind": "card", "volume_id": ...}` for a card's `DCIM` folder, `{"kind": "indexed-folder", "path": ...}` or `{"kind": "all-indexed"}`. It answers `{job_id, status, deduplicated}` at once; a source already being listed answers that job. Follow it with `job.read`: its `kind` is `index-refresh`, `progress.message` counts the files found ("1,204 files found", or "1,204 of about 12,408 files" when an earlier listing found 12,408) while the folder is still being listed, with no `progress.fraction` because its extent is not known yet, and then the headers read, with `progress.fraction`, and a ready job's `result` is `{roots, files, added, changed, moved, removed, unreadable, headers_read, unreadable_folders, offline?, missing?}`. Listing a folder again reads only new and changed files; a file renamed or moved on its volume keeps its index row and `file_id`. `job.cancel` stops a listing and keeps what it wrote. A folder or card that is not connected answers `source-unavailable` (an `all-indexed` listing names it under `offline` instead); past 500,000 files a listing fails with `resource-limit`. Each batch the index writes records one event naming its `index_revision`, and the job records one more as it ends, however it ends, naming its request, the job (`job_id`, which each batch's event names too) and the revision it left: an event naming your request is the moment to read `job.read`, with no need to poll it.

```json
{"id":"list","method":"index.refresh","params":{"source":{"kind":"folder","path":"/Volumes/NIKON Z 8/DCIM"}}}
```

**Indexed folders** are the folders Luxforge organizes into events, such as `~/Pictures`. `index.add-folder {path, mutation}` adds one with its subfolders and starts listing it, answering `{change, folder, job_id?, deduplicated}`; `index.remove-folder {path, mutation}` removes one, answering like `pick.set`, and forgets its index rows. Both are library changes: journaled with your `actor`, retried safely, and reverted by `library.undo` and `library.redo`, which list the folder again or forget it. Adding a folder already indexed changes nothing; a folder inside or around an indexed one is refused with `conflict` (`error.data.folder` names it), and a file, a package, another application's cache or Luxforge's own directory with `validation`. `index.folders` answers each indexed folder with `offline` (it is not there and its volume is not connected; its index rows stay), `files` and `listed_ms` from its last listing, `watching`, with `unwatched` saying why not when it is `false`, and `stale: true` while a listing Luxforge ran on its own was cancelled or failed and the folder has not been listed since.

**The index keeps up by itself.** Once an indexed folder is listed, Luxforge watches it: a photograph added, changed, renamed or deleted in it reaches the index within about a second, with no `index.refresh`, and only the files that changed are read. On macOS what changed while Luxforge was closed is caught up as the catalog opens, from where its notifications stopped; on Linux and Windows, which keep no such history, each indexed folder is listed again as the catalog opens. A card mounted while Luxforge runs is listed by itself, and so is a card already mounted when a catalog with indexed folders opens; a drive taken out makes its folders offline at once. What the index applies on its own is recorded as events under the method `index-watch`, with no request id. When it lists a folder again on its own — changes it could not follow one by one, a folder that moved, a folder listed again as the catalog opens — that listing is an `index-refresh` job like a card's, on the activity board with its `job_id`: read it with `job.read` and stop it with `job.cancel`, which keeps what it committed. A folder whose listing was stopped or failed is `stale` in `index.folders`; Luxforge lists it again before applying its next change, and as the catalog next opens. A folder on a network volume is not watched, since its changes are not reported: refresh it to list it again.

### Previews of browsed files

`preview.read {item, tier, priority?}` answers a file's cached preview, or the job that makes it. A file is named by its row in the index beside the catalog, `{"kind": "file", "file_id": 12}`, which [`index.refresh`](#volumes-folders-and-the-index) fills; `browse.rows` and `pick.list` name a file's row. `tier` is `grid` or `loupe`, and `priority` is `look-ahead`, `visible` (the default) or `background`: the loupe's look-ahead is read first, then visible cells, the most recently asked first, then the rest, oldest first.

```json
{"id":"cell","method":"preview.read","params":{"item":{"kind":"file","file_id":12},"tier":"grid"}}
```

The answer is `{"state": "ready", "preview": {item, tier, path, width, height, origin, approximate, bytes, key, renderer?}}`, or `{"state": "queued", "job_id": "job-…", "fallback": {…}}` with the best preview already cached meanwhile. `path` is a JPEG under `<catalog stem>.index/previews/`, upright, which a client draws as it is; `origin` says what its pixels are — `exif-thumbnail` (the file's tiny thumbnail), `embedded` (the camera's preview, or a JPEG original itself), `developed` (a neutral Luxforge development, for a RAW that carries no usable preview) — `approximate` is `false` for every file's preview, and `key` names exactly what it was made from, so a preview is never shown for anything else. A grid tier is at most 512 px on its long edge and arrives in two stages: the file's thumbnail first, which a read answers as the `fallback` of the same job, then its embedded preview. A loupe tier is the largest embedded preview at most 2560 px, never enlarged, so a drone's 960 px preview stays 960 px; while it is read, the grid tier is the fallback.

A RAW that carries no usable preview, such as a Canon EOS R5 Mark II's or R8's, whose previews are H.265 only, is developed as the editor shows an unedited RAW, one RAW at a time, taking about a second: for a `visible` or `look-ahead` request only, since development is done for what is on screen. A `background` request of such a file answers `not-ready` at once; ask again with `visible`. A camera or mode outside Luxforge's RAW catalog cannot be developed and is `unsupported-input` naming why.

A file changed since it was indexed, gone or on an unplugged drive is `source-unavailable`, and its cached previews are still answered. A file that cannot give the tier keeps its own error — a corrupt file (a JPEG that does not decode, a RAW that cannot be opened) is `invalid-input`, a colour or ICC profile it cannot read `unsupported-color` or `unsupported-profile`, one past a limit `resource-limit` — and is answered at once and not read again until it changes. `tier: large`, and a file the index does not hold, are `validation`. At most 20,000 previews wait to be read, and a request past that is refused with `resource-limit`.

The job's `kind` is `preview-extract`; every request for the same file and tier shares it, with the same `job_id`, the clients that asked read it, and its `result` is the preview. `job.cancel` releases only your interest: another client waiting on the same preview keeps waiting, and you can still read how it ended; a client that never asked for it is refused `conflict` while one waits. Once every client that asked has cancelled or disconnected, the job ends `cancelled` and the preview is dropped before it starts, or stopped before it writes anything, unless a view still wants it. The desktop is woken when a preview its own request waits on is written — each stage of a grid tier it was answered `queued` for — and reads `preview.read` again; a view's background reading wakes nothing and shows its progress on the activity board. A script polls `job.read`.

### Previews of developed photographs

`preview.read` also answers a developed photograph's preview: `{"kind": "photo", "asset_id": "asset-…"}` names its current entry, and an `entry_id` of its own names another. `tier` is `grid` (512 px on the long edge) or `large` (2048 px, for Develop's instant switch); `loupe` is a file's and `validation` here, as are an unknown photograph and an entry that is not its own.

```json
{"id":"thumb","method":"preview.read","params":{"item":{"kind":"photo","asset_id":"asset-…"},"tier":"grid"}}
```

A tier is `ready` when it is the entry rendered by this version of Luxforge: `origin` is `rendered`, and `key` is `photo:<asset>:<entry>:<tier>:r<generation>`, so an edit, an undo, a redo or a restore — by any client — makes a new key, and the next read renders it. Otherwise the answer is `queued` with a `preview-render` job, one for each tier, shared by every request for it, whose `result` is the rendered preview. Both tiers asked for before the render starts come from one render. While it renders, the `fallback` is the best preview cached, labelled by its own `key` and `origin`: the tier of an earlier entry after an edit, or, until the photograph's first render, its **camera preview** (`origin` `embedded`, `key` ending `:embedded`) — a RAW's embedded preview, or a JPEG original itself, fitted to the tier — which the read asks for on the preview workers and which arrives within a moment. Once the new tier is written, the tiers of other entries are removed. A photograph whose cached grid tier an edit made stale, by any client, has it rendered again in the background, so views stay current.

A rendered tier is the entry's full-resolution render reduced to the tier's size, so it says `approximate: false`, as a camera preview does: it is never an approximation of the edit, whatever its spatial adjustments or masks. On the desktop the GPU draws it, as it draws an export, held to the reference renderer's tier within the display limit; a host without a GPU, `luxforge-json`, or a GPU that cannot draw the stack has the reference renderer draw it. Its `renderer` says which, as an export's result does: `{"record": "gpu", "reason": null}`, or `{"record": "reference", "reason": ...}` with why the GPU did not draw it (`surface-pending` until the desktop has named its graphics adapter, which it does as its window opens on a computer with one graphics adapter and once a photograph is drawn on one with several, `refused` under `--no-gpu-render`, `no-adapter`, `device-lost`, `tiles-budget` or the stack's own reason), and no reason under `luxforge-json`. A file's preview and a camera preview carry no `renderer`.

Renders run one at a time on a worker of their own, the look-ahead first, then visible requests, the most recent first, then the rest; at most 2,000 wait, and one past that is `resource-limit`. The one running is a "Rendering previews" row on the activity board. A tier's job is shared like a file's: `job.cancel` releases only your interest, and once every client that asked for the tier has left it the job ends `cancelled` and the render is removed before it starts, or stopped, once no tier of it is wanted. An edit's background re-render of a grid tier has a job of its own, which wants the tier whatever the clients that asked for it do; any client can read it, and its `job.cancel` stops the re-render for everyone, as the Performance section's Cancel does. A render reads the original itself and checks it is the file that was developed: one that is missing, offline or changed is `source-unavailable`, and an edit whose module is missing or disabled is `incompatible`, naming its layers. Large tiers share the loupe tiers' 4 GiB, least recently used out first; grid tiers are kept. Deleting `<catalog stem>.index` while Luxforge is closed costs only the time to render again.

### The 100% focus check

`preview.region {item, rect, frame?}` answers one rectangle of a frame at 100%: of a file (`{"kind": "file", "file_id": 12}`) or of a developed photograph's original (`{"kind": "photo", "asset_id": "asset-…"}`, with an optional `entry_id` of its own; the region is the original's whatever the entry). `rect` is `{x, y, width, height}` in the image's upright full-resolution pixels. A client that knows the rectangle in another upright frame, such as the loupe's preview, names it in `frame: {width, height}`, and the rectangle's centre is mapped into the image's frame with its size kept, since a 100% region is never resampled.

```json
{"id":"focus","method":"preview.region","params":{"item":{"kind":"file","file_id":12},"rect":{"x":1200,"y":800,"width":400,"height":300},"frame":{"width":2560,"height":1707}}}
```

It starts a job and answers `{job_id, status, deduplicated}`; read it with `job.read`. Its `kind` is `preview-region` and its `result` is `{item, rect, frame, path, width, height, origin}`: `rect` is the rectangle returned, clamped to the image, in the full-resolution `frame` it was cut from; `path` is a quality-95 JPEG of those pixels under `<catalog stem>.index/previews/regions/`, valid until your next region; `origin` is `embedded` when the pixels come from the camera's full-size preview (a JPEG original is its own), decoded for that rectangle alone, or `developed` when the camera's preview is smaller than the image and the frame was developed neutrally, which takes a second or more the first time and is kept for the next region of the same frame. Your next region cancels the previous one, waiting or running, and `job.cancel` stops one; while one runs it is a "Checking focus" row on the activity board. Regions run one at a time on a worker of their own, so they never hold up previews; at most 9 wait, and one past that is `resource-limit`. A rectangle of no pixels, a `frame` of no pixels, one starting outside its frame and a file the index does not hold are `validation`, a rectangle past 32 MiB of pixels `resource-limit`, a file changed or gone (or an original no longer the file the catalog recorded) `source-unavailable`, a corrupt file `invalid-input`, an unreadable one `read-error`, and a camera outside the RAW catalog `unsupported-input`.

### Picks and library changes

The Select workspace sends `pick.set`, `library.undo` and `library.redo` for its picks and undo ([The grid and picks](#the-grid-and-picks)). A **pick** marks a file to develop. `pick.set {targets, picked, mutation}` picks (`picked: true`) or clears the files `targets` names: `{"kind": "paths", "paths": [...]}` (absolute paths), `{"kind": "files", "file_ids": [...]}` (rows of the index) or `{"kind": "selection"}` (the files selected in your view), at most 50,000; more is `resource-limit`. A pick keeps the file's path, signature (length, modification time and file identity) and volume with who picked it, the request and the time, in the catalog, so it survives a restart. Picking a file already picked keeps its pick as it was. A file the index lists is picked from the index's record of it; any other must exist, and a file whose volume is not connected can be cleared but not picked. `pick.list {source?, after?, limit?}` pages the picks in path order, every pick or those of a `{kind: folder, path, subfolders?}` or `{kind: card, volume_id}` source, each with its index row as `file_id` when the index lists it; continue with `after` set to the page's `next_after`.

```json
{"id":"pick","method":"pick.set","params":{"targets":{"kind":"paths","paths":["/Volumes/NIKON Z 8/DCIM/100NZ8_1/DSC_0412.NEF"]},"picked":true,"mutation":{"request_id":"pick-1","actor":"my-client"}}}
```

Every pick or clear is one **library change**, answered as `{outcome, change?, items, deduplicated}`: `applied` with the change's number and how many items it changed, or `no-op` when nothing needed changing, which records nothing. The journal keeps each change's actor, request, method, label ("Picked DSC_0412.NEF", "Picked 18 files") and each item's value before and after: `library.journal {after?, limit?}` pages the changes oldest first without their items, each with `undoes`, `redoes` or `undone_by` where it has them, and `library.inspect {sequence}` returns one with its items. A change records one event naming its `library_sequence`, however many items it covered. `library.undo {mutation}` reverts the latest change your `actor` made that is not yet undone, by recording its inverse, and `library.redo {mutation}` reverts your latest undo, until your next new change; either is a `no-op` when there is nothing to revert. One is refused with `conflict` when an item it would revert changed since, by another change still in effect or otherwise, and `error.data.items` names those items (the first 100, with `data.count`); nothing changes. Undo is per actor, so an agent never undoes the desktop's picks, and it survives a restart. `catalog.info` reports the catalog's path, identity and formats, the counts behind the Catalog sources (`photographs`, `recently_developed`, `removed`, `unavailable`) and of folders, collections, picks, indexed folders and library changes, the index database's size and the files it lists, and the preview cache's size and files.

### Developing picks

**Developing** brings files into the catalog as photographs, each into a catalog folder; the file stays where it is and is only read. The Select workspace's **Develop N** sends these same requests ([Developing picks in Select](#developing-picks-in-select)). `pick.plan {targets?}` answers what developing the files `targets` names would do, picked or not (without `targets`, the picks in your view, which is `conflict` when a change since it was evaluated left it stale: evaluate it again): the files by **event**, organized over every file the index lists in their folders (a file it does not list is an undated frame of its folder), and for each event its name, its count, the folder it would go into and the picks on removable volumes, with how many have a copy. The folder is an existing one when an earlier Develop made it from the same event (`folder_name` names it), or else a new top-level folder named after the event: its place with the month and year of its first day ("Konstanz · Sep 2026"), else the event's name, with " 2" added when that name is taken. `offline` counts the files whose drive is not connected.

```json
{"id":"plan","method":"pick.plan","params":{"targets":{"kind":"paths","paths":["/Users/me/Pictures/Konstanz/DSC_0412.NEF"]}}}
{"id":"develop","method":"pick.develop","params":{"targets":{"kind":"paths","paths":["/Users/me/Pictures/Konstanz/DSC_0412.NEF"]},"into":[],"mutation":{"request_id":"develop-1","actor":"my-client"}}}
```

`pick.develop {into, targets?, use_copies?, confirm_removable?, mutation}` develops them. `into` lists `{event_id?, folder}` entries, where `folder` is `{"kind": "existing", "folder_id": "folder-…"}` or `{"kind": "new", "name": "…", "parent_id"?: "folder-…"}`: an entry with an `event_id` sends that event there, one without covers every other event, and an event no entry covers goes where the plan proposed, so `"into": []` accepts the plan. A new folder's name follows a folder's rules, and events given the same new folder share it. It answers `{job_id, status, deduplicated}` at once; the `develop-picks` job reads each file once (its SHA-256, its header and, for a RAW, the camera's interpretation, without developing it), off the thread that serves requests, with its progress ("3 of 18") on the activity board. Its result, read with `job.read`, is `{developed: [{path, used?, asset_id, outcome}], failed: [{path, code, message}], changes}`:

- `created`: a new photograph with its Original entry, its capture metadata and place, the folder on disk it came from, and, for a frame of a burst or bracket, the moment.
- `linked`: the file's bytes are already a photograph's, so nothing is added twice.
- `relinked`: a photograph whose original was missing now points at this file, because its name, size and bytes match (or it is the same file, moved on its drive); its folder, collections and edits stay as they were.

A photograph in Removed whose file is linked or relinked is put back, in the Develop's own change, so `library.undo` returns it to Removed.

A file that is another photograph's original with different bytes, or that cannot be read or opened, is listed in `failed` with its error and stays picked; so is a file on a drive that is not connected (`source-unavailable`). Picks on a card or other removable drive are refused (`conflict`, naming the drive in `error.data`) unless you say what to do with them: `"use_copies": true` develops each from a copy of the same name and size in an indexed folder once its bytes are confirmed identical (listed as `used`), and `"confirm_removable": true` develops from the card itself what has no such copy.

The job commits as it goes: the first file at once, then batches of up to 100 files or 5 seconds, each batch from one event and each one library change ("Developed DSC_0412.NEF", "Developed 17") with its own event, clearing the picks it brought in; the job records one more event as it ends. `job.cancel` stops it between files: what it committed stays, whole, and nothing else is written. Sending the same request again answers the first job, after a restart too. `library.undo` of a Develop sends all its photographs back and picks their files again, every batch in one step, and is refused, naming it, when a photograph has been edited since. `asset.send-back {targets, mutation}` does the same for photographs you name, as one library change: each must hold nothing but its Original (no edit, an edit auto-collapse hid from history included, no named version, no collection) and have its original where the catalog looks for it, or the request is refused with `conflict` saying why and nothing changes. A photograph sent back is developed again with `pick.develop`.

Opening a file — Open or `luxforge --open FILE` in the desktop, or a JSON client ([JSON automation](#json-automation)) — is a Develop of that one file at once, into the folder the plan proposes and confirming removable media, since you chose the file; then its photograph is prepared and shown. A file the index does not list is an undated frame of its folder, so it goes into the folder the newest photograph developed from its folder on disk is in, or else a new folder named after its folder on disk ("Konstanz"). Opening a file that is already a photograph, or whose bytes one already has, opens that photograph.

### Catalog folders and collections

Every developed photograph is in exactly one **catalog folder**, the catalog's own organization: nothing on disk changes when a folder or collection does. Every change below takes the `{request_id, actor}` envelope, is one library change answered as `{outcome, change?, items, deduplicated}` (a `no-op` when nothing needed changing), and is undone and redone with `library.undo` and `library.redo`. A name is trimmed and holds 1 to 128 characters without control characters (`validation` otherwise); it must be unique among its siblings ignoring case, the top level counting as one parent, and a clash is `conflict` naming what is already there. An unknown folder, collection or photograph is `validation`.

`folder.list` answers every folder, parents before children and siblings by name, as `{folders: [{id, name, parent_id?, created_ms, event?, count, year?}]}`: `count` is the photographs directly in it, removed ones excepted, and `year` the capture year of its earliest dated photograph. `folder.create {name, parent_id?, mutation}` makes an empty folder and answers `{change, folder, deduplicated}`. `folder.rename {folder_id, name, mutation}` renames one; `folder.move {folder_id, parent_id?, mutation}` nests it in another folder, or moves it to the top level without `parent_id`, and refuses a move into itself or a folder inside it. `folder.merge {folder_id, into_id, mutation}` moves every photograph of `folder_id`, removed ones too, into `into_id`, then its subfolders, gives `into_id` its event span when it has none (so later picks from that event still propose it), then deletes `folder_id`, all as one change that one undo reverts; it refuses a merge into itself or a folder inside it, a subfolder whose name `into_id` already holds (`conflict`), and more than 50,000 items (`resource-limit`). `folder.delete {folder_id, mutation}` deletes only an empty folder: one holding any photograph, even a removed one, or any folder is `conflict`, saying what it holds. `asset.move {targets, folder_id, mutation}` moves photographs into a folder, leaving out those already there; `targets` names photographs as `{"kind": "assets", "asset_ids": [...]}`, by their originals' `paths`, by index rows (`files`) or as the `selection`, at most 50,000.

A **collection** holds any photographs you add, across folders; a **smart collection** keeps a browse query over photographs; a **group** holds collections, smart collections and groups. `collection.list` answers them all, parents first, as `{collections: [{id, name, parent_id?, kind, query?, created_ms, count?}]}`, with a plain collection's members, removed photographs excepted, as `count`. `collection.create {name, kind, parent_id?, mutation}` makes a `collection` or a `group`, and `collection.create-smart {name, query, parent_id?, mutation}` a smart collection; both answer `{change, collection, deduplicated}`, and `parent_id` must be a group. A smart collection's query is kept as given, with its defaults filled in, and must be one `browse.view` accepts over photographs: a source over files (an event, a folder on disk or a card) is refused, as is a `{"kind": "collection"}` source naming a smart collection, a group or an unknown collection, and a `{"kind": "catalog-folder"}` source naming an unknown folder. `collection.update-smart {collection_id, query, mutation}` replaces a smart collection's query under the same rules. `collection.rename {collection_id, name, mutation}` renames any of them; `collection.move {collection_id, parent_id?, mutation}` moves one into a group or to the top level, never a group into itself or a group inside it. `collection.delete {collection_id, mutation}` deletes a plain collection with its memberships (so its undo restores every member with when it joined), a smart collection, or a group only when it is empty (`conflict` otherwise). `collection.add` and `collection.remove {collection_id, targets, mutation}` change a plain collection's members; a member added again keeps when it first joined, and a smart collection or a group is refused.

```json
{"id":"folder","method":"folder.create","params":{"name":"Konstanz · Sep 2026","mutation":{"request_id":"folder-1","actor":"my-client"}}}
{"id":"move","method":"asset.move","params":{"targets":{"kind":"assets","asset_ids":["asset-…"]},"folder_id":"folder-…","mutation":{"request_id":"move-1","actor":"my-client"}}}
{"id":"add","method":"collection.add","params":{"collection_id":"collection-…","targets":{"kind":"assets","asset_ids":["asset-…"]},"mutation":{"request_id":"add-1","actor":"my-client"}}}
```

The journal labels each change as you would say it: "Created folder Konstanz · Sep 2026", "Moved 5 photographs to Konstanz · Sep 2026", "Merged Konstanz · Sep 2026 into Travel", "Added 5 to Portfolio › Landscapes", naming a collection by its path through its groups.

### Batch preset and export

A batch applies one preset to many developed photographs, or exports them into one folder, exactly as applying or exporting each one alone would, one photograph at a time, with one report; the Select workspace's Develop band sends these ([Presets and exports of many photographs](#presets-and-exports-of-many-photographs)). `targets` names photographs as `asset.move` takes them, at most 50,000. Each answers `{job_id, status, deduplicated}` at once: read the job with `job.read {job_id}` and stop it with `job.cancel`.

`batch.apply-preset {targets, preset_id, mutation}` reads the library preset once and applies it to each photograph as `edit.apply-preset` does with that preset's settings, name and id: each gets its own history entry, "Preset: Warm", by your `actor`, which undoes like any other edit, and each records an event naming the photograph and its new revision. The entry's request is `<request_id>/<asset_id>`, so a retry of the batch applies nothing twice, after a restart too. A ready job's `result` is `{done, skipped, settings_skipped?}`: `done` lists the photographs that got an entry, and `settings_skipped` lists, for each of them, the preset's settings that do not apply to it, such as a RAW white balance on a JPEG, with the reason `edit.apply-preset` gives. An unknown preset is refused with `validation`.

`batch.export {targets, destination, mutation, keep_metadata?}` writes each photograph's current entry into `destination`, an existing folder, as `export.jpeg` writes it: the same quality-90 sRGB JPEG, with or without the original's supported metadata, named from its original's name by the export's rule, `DSC_0042-edited.jpg`, or `DSC_0042-edited-2.jpg` and so on when that name is taken (two originals of one name get two names), and never replacing a file. A photograph whose original is not prepared is prepared first, one at a time, which reads and decodes it as opening it would; the photograph open in Develop is then prepared again when you return to it. Each written file records an event, as a single export does. A ready job's `result` is `{done, written, skipped}`, with `written` the files in the order written, each `{asset_id, path, renderer}`: `renderer` names what rendered that file as a single export's result does, `{"record": "gpu", "reason": null}` or `{"record": "reference", "reason": ...}` with why the GPU did not, so one batch may hold files of both. A relative path or a file as `destination` is refused with `validation`, and a folder that is not there with `read-error`. A retry is answered with the first job; after a restart the export keeps no record of what it wrote, as a single export keeps none, so the same request exports again under the next free names.

`skipped` lists every photograph left out, `{asset_id, code, reason}`, and nothing is written for it:

- `removed`: it is in Removed;
- `draft-open`, for a preset: you hold an unapplied draft on it;
- `history-selected`, for a preset: you are previewing its history;
- `unchanged`, for a preset: it already has the preset's settings;
- `not-applicable`, for a preset: none of the preset's settings apply to it;
- otherwise the code and message the single call refuses it with, such as `source-unavailable` naming why its original is missing or offline (for an export: a preset reads no pixels), or `conflict` when every name the export's rule tries is taken.

While a batch runs, `job.read` reports `progress.message` "3 of 18" with `progress.fraction`, and its `result` is the report so far; the activity board shows the same. `job.cancel` stops it between photographs, or within the photograph being exported, whose temporary file is removed; every photograph finished stays finished, and a cancel while an original is being prepared takes effect when that preparation ends. A cancelled job reports `cancelled` rather than its report. At most four library jobs wait behind a running one; another is refused with `resource-limit`.

```json
{"id":"preset","method":"batch.apply-preset","params":{"targets":{"kind":"assets","asset_ids":["asset-…","asset-…"]},"preset_id":"preset-…","mutation":{"request_id":"batch-1","actor":"my-client"}}}
{"id":"export","method":"batch.export","params":{"targets":{"kind":"selection"},"destination":"/Users/me/Pictures/Konstanz","keep_metadata":false,"mutation":{"request_id":"export-1","actor":"my-client"}}}
{"id":"progress","method":"job.read","params":{"job_id":"job-…"}}
```

### Removing photographs

Removing a photograph from the catalog moves it to **Removed**; its file stays where it is and is never touched. The Select workspace's Remove from catalog…, Put back and Empty Removed… send these requests ([Removing from the catalog](#removing-from-the-catalog)). `asset.remove {targets, mutation}` removes the photographs `targets` names, as `asset.move` takes them, as one library change ("Removed DSC_0412.NEF", "Removed 5 photographs") answered as `{outcome, change?, items, deduplicated}`. A removed photograph keeps its edits, history, named versions, catalog folder and collections, but no view shows it except the `removed` source of `browse.view`, and no count includes it except `catalog.info`'s `removed`: All photographs, Recently developed, its folder, its collections, Missing originals, `folder.list`, `collection.list` and `source.missing` leave it out, a view of its folder on disk no longer shows its file as in the catalog, and a batch preset or export skips it. Removing one already removed keeps when it was removed. `asset.restore {targets, mutation}` puts photographs back ("Put back DSC_0412.NEF") exactly where they were; `library.undo` and `library.redo` undo and redo either, like any other library change.

`catalog.empty-removed {mutation}` permanently deletes every removed photograph's catalog record: its history, named versions, collection memberships and everything else the catalog keeps of it, with the brush strokes and derived artifacts no other photograph uses. Their files on disk are not touched. It cannot be undone, so only a client with permission authority may send it: the desktop, or `luxforge-json --permission-authority`, which you pass yourself; any other client is refused with `forbidden`. It answers `{outcome, deleted, remaining, deduplicated}`: one call deletes at most 50,000 photographs, the earliest removed first, and `remaining` says how many are still in Removed for another call; with nothing removed it is a `no-op`. It records one event and leaves every view stale, to be evaluated again, but is not a library change, and the journal keeps what it recorded: `library.undo` of a removal whose photographs have been deleted is refused with `conflict`.

```json
{"id":"remove","method":"asset.remove","params":{"targets":{"kind":"assets","asset_ids":["asset-…"]},"mutation":{"request_id":"remove-1","actor":"my-client"}}}
{"id":"put-back","method":"asset.restore","params":{"targets":{"kind":"assets","asset_ids":["asset-…"]},"mutation":{"request_id":"restore-1","actor":"my-client"}}}
{"id":"empty","method":"catalog.empty-removed","params":{"mutation":{"request_id":"empty-1","actor":"my-client"}}}
```

### Originals: availability and Locate

Luxforge never moves, copies or deletes an original, so when you move, rename or unplug one the catalog keeps the photograph, its edits and its history, and only needs to be told where the file is now: in the desktop, with **Locate original…** in Develop or Missing originals in Select ([Missing originals](#missing-originals)), which send the requests below. Opening a photograph (`source.prepare`), any render of it and `export.jpeg` answer `source-unavailable` when its original is not where the catalog looks, and say why: "the volume Photos SSD is not connected", "the original DSC_0412.NEF is missing from /Volumes/Photos SSD/2026-09-12", or, when another file has taken its place, that the original's fingerprint changed. `error.data` carries `{availability, locator, volume?}`: `offline`, `missing` or `changed`, the path the catalog looked at, and the volume as the catalog knows it (its label and mount point) when the file was not at its path.

`source.check {targets}` looks at where photographs' originals are, as a `source-check` job: `targets` names photographs by id (`{"kind": "assets", "asset_ids": [...]}`), by the path of their original or its index row, or the photographs selected in your view, at most 50,000. Read it with `job.read {job_id}` and stop it with `job.cancel`; its `result` is `{rows: [{asset_id, availability, checked_ms}]}`, each `available`, `offline` (its drive is not connected; one look covers every photograph on it), `missing` or `changed`, and what it found is recorded with the time it looked. A photograph whose file you moved or renamed within the same drive, in a folder Luxforge has indexed, is found again by the file's identity, checked against its fingerprint and pointed at its new path by the check itself, as one library change by the actor `system`; nothing else is changed without being asked. A check that changed anything records one event.

`source.locate {asset_id, path, mutation}` points one photograph at the file you choose, which may have another name, be in another folder or on another drive. Before reading it, a relative path, a folder, a file of another length and a file another photograph already uses are refused, the last with `conflict` naming that photograph in `error.data.asset_id`: two photographs are never merged. The answer is `{job_id, status, deduplicated}`; the job reads the whole file, one megabyte at a time, and checks its fingerprint against the one recorded when the photograph was developed, so a different photograph with the same name and size is refused (`source-unavailable`), as is a file that changes while it is read or before it is used (`conflict`). A ready job's `result` is `{outcome, change?, items, deduplicated}`: the photograph's new path is one library change, labelled "Located <file name>", which `library.undo` reverts, and nothing else about it changes, its edits and history included. Cancelling it, unplugging the drive meanwhile or any failure leaves the photograph as it was. At most four library jobs wait behind a running one; another is refused with `resource-limit`.

```json
{"id":"check","method":"source.check","params":{"targets":{"kind":"assets","asset_ids":["asset-…"]}}}
{"id":"locate","method":"source.locate","params":{"asset_id":"asset-…","path":"/Volumes/Archive/2026/DSC_0412.NEF","mutation":{"request_id":"locate-1","actor":"my-client"}}}
{"id":"read","method":"job.read","params":{"job_id":"job-…"}}
```

### Resolving missing originals

When you move a whole folder of originals, reorganize a drive or unplug it, the photographs developed from it are resolved together, grouped by the folder on disk each was developed from; the desktop's [Missing originals](#missing-originals) view sends these requests. `source.missing` lists every photograph, removed ones excepted, whose original was last found offline, missing or changed, as `{groups: [{source_folder, volume_id, count, catalog_folders: [{id, name}], reason}], count}`, in folder order. `reason` says why: `{kind: volume-offline, label}` when the group's drive is not connected (connecting it and checking again is all it needs), `folder-gone` when the drive is there and the folder is not, `changed` when every file in it was replaced by another, and `files-gone` otherwise. The list is what `source.check` and refusals recorded, so check first: a photograph nothing has looked at since its original went is not listed yet, and a group recorded offline whose drive is connected again reads `files-gone` until you check it.

`source.find {search_root, source_folder}` searches one folder you choose, with its subfolders, for every missing photograph developed from `source_folder`; name photographs with `targets` instead (as `source.check` takes them) to look for those. Name exactly one of the two. The folder is walked once, following no symbolic link, staying on its drive and skipping hidden folders, packages such as a Photos library and other applications' caches; more than 500,000 files or 100,000 folders is `resource-limit`, so choose a smaller folder. A file with a photograph's file name (ignoring case on macOS and Windows) and length is read in full and checked against the fingerprint recorded when the photograph was developed. The answer is `{job_id, status, deduplicated}`, and the job changes nothing; its `result` is `{rows: [{asset_id, file_name, result, ...}]}`, one row per photograph:

- `found` with `path`: one file with the original's bytes;
- `several-identical` with `paths`: several copies with its bytes, for you to choose between;
- `different-bytes` with `path`: a file of that name whose bytes differ, left as it is;
- `claimed` with `path` and `by`: a file with its bytes that another photograph already uses, which is never taken;
- `not-found`.

While the search runs, `job.read` shows its report so far, `checking` for photographs not yet looked at, and its progress counts the files looked at, then the photographs checked. `job.cancel` stops it between files. A folder or file it cannot read fails it with `read-error`, and a drive disconnected during the search fails it with `source-unavailable`; either way nothing changes.

`source.relink {pairs, mutation}` points each photograph of `pairs: [{asset_id, path}]` at its file, in one library change, labelled "Relinked 18 originals", that `library.undo` reverts. Each photograph's source folder becomes the file's folder; its edits, history and catalog folder stay. Only what a finished search verified is relinked: a file no search found for that photograph, one changed or gone since, one another photograph uses and a copy you did not choose are refused. Any such pair refuses the whole request, and nothing changes. `error.data.pairs` names each one with its `reason` (`not-verified`, `changed`, `gone`, `claimed` or `same-file`): the code is `source-unavailable` when a file is gone and `conflict` otherwise. Search again after a file changes. A pair whose photograph already uses its file needs nothing, and more than 50,000 pairs is `resource-limit`.

```json
{"id":"missing","method":"source.missing","params":{}}
{"id":"find","method":"source.find","params":{"search_root":"/Volumes/Archive/2026","source_folder":"/Volumes/Photos SSD/2026-09-12"}}
{"id":"relink","method":"source.relink","params":{"pairs":[{"asset_id":"asset-…","path":"/Volumes/Archive/2026/Konstanz/DSC_0412.NEF"}],"mutation":{"request_id":"relink-1","actor":"my-client"}}}
```

### Module settings, consent and resources

Modules can declare settings, provider profiles, secrets, resources to download and worker tasks; the [module capabilities](design/module-capabilities.md) design has the whole contract. They live outside every catalog: settings and grants in `<config>/modules/` (`~/Library/Application Support/Luxforge/modules` on macOS), installed resources in `<data>/modules/resources/`, secrets in the macOS Keychain. `luxforge-json --data-root DIRECTORY` isolates both directories like the desktop's flag, and `--secret-store memory` keeps secrets for the process only, for scripts and tests. Nothing is read, created, downloaded or loaded merely because a module is listed or a catalog is opened. Only the capability proof module declares any of this today, and only with `--developer --proof-endpoint URL`, in the desktop and headless alike.

`module.settings.read {module_id}` returns each field's value, default and validity, each secret field only as `secret_present`, and each provider profile with its status. `module.settings.set {module_id, profile_id?, values, mutation}` commits non-secret fields together (`null` resets one); `module.settings.set-secret {module_id, profile_id?, setting, value, mutation}` stores a secret and never echoes it; `module.settings.clear-secret`, `module.settings.reset`, `module.profile.create {module_id, adapter, label, mutation}` and `module.profile.remove` complete the set. The `mutation` envelope is the edit one, with `expected_revision` the module's settings revision. A locked or unavailable secure store answers `not-ready`; nothing falls back to plain text.

```json
{"id":"key","method":"module.settings.set-secret","params":{"module_id":"luxforge.capabilities","profile_id":"profile-…","setting":"api-key","value":"…","mutation":{"expected_revision":3,"request_id":"key-1","actor":"my-client"}}}
```

Downloading a resource and sending photo data need consent. A request that needs it fails with `consent-required`, and `error.data.consent` carries the module, the capability, the exact `scope` and a `disclosure` of what would be sent, where to, how many bytes, where a download is stored, its license, the adapter's retention note and whether it may cost money; `denied` is true when that scope was declined before. Only a client with permission authority may answer it with `module.permission.grant {module_id, capability, scope, mutation}`: the desktop, after you press Allow, or `luxforge-json --permission-authority`, which you pass yourself as an explicit setup step. A live-session client cannot grant, so an agent connected to the running editor can never give itself access. Consent to send photo data covers one photo: the next photo asks again. At most 1,024 permission records are kept; once they are all live permissions, the oldest photo-data permission makes room for the next one, and its photo asks again. A download permission is never dropped this way. `module.permission.deny {module_id, capability, scope, mutation}`, `module.permission.revoke {grant_id, mutation}` and `module.permission.list` are open to any client; revoking a grant cancels the jobs that depend on it and never changes a recipe, a history entry or an accepted result. Changing a profile's endpoint revokes the grants of the old one.

There is no `module.activate` or `module.deactivate`: loading a module's state ahead of its tasks is deferred until a module needs a local runtime, so a task reads the resources it uses when it runs. `module.resource.install {module_id, resource_id, mutation, source?}` downloads a resource from its pinned URL, once the `download-artifact` permission is granted, and installs it only after its length and SHA-256 match (`source` is `{"kind":"download"}` or left out); `module.resource.list` and `module.resource.remove {module_id, resource_id, mutation}` report and delete installed resources; `module.status` summarises settings, resources, how many grants and denials are recorded, and jobs. A task is generated like an action, as `task.<id>` with `asset_id` and `profile_id` when it declares them, and a `mutation` envelope. Each of these answers promptly with a job, or with `not-ready` and `error.data.requirements` naming every profile that is not ready and every resource that is not installed. Read a job with `job.read {job_id}` until its `status` is `ready`, `failed` or `cancelled`, and stop one with `job.cancel {job_id}`. Each of these requests, a task included, carries the `{request_id, actor}` envelope, so sending the same request again returns the first job rather than starting another. A task that publishes a derived artifact returns its identity in `result.artifacts`; commit it with the action the task names, such as `edit.apply-proof-tint {artifact}`.

Quit Luxforge, and stop any `luxforge-json` serving the catalog, before you copy or move it. While a catalog is open, and after Luxforge stops unexpectedly, recent changes are in a `-wal` file beside it (`catalog.sqlite-wal` for `catalog.sqlite`), which the next open folds into the catalog; a clean close does that and removes the file. If the `-wal` file is there, copy or move it with the catalog, or the copy can lack recent edits.

Derived artifacts live beside the catalog in `CATALOG.artifacts/`; move that directory with the catalog. `artifact.status` reports it, `artifact.inspect {artifact_id}` one artifact, and `artifact.collect {mutation}` removes artifacts no entry references. A missing or corrupt artifact makes rendering fail with `source-unavailable` naming it, while history keeps working.

While the desktop owns a catalog it creates `CATALOG.live-session.json` beside it, recording a `127.0.0.1` address and a token. That session accepts the same newline-delimited requests with the token as the request's top-level `token`. The file is owner-readable on Unix and removed on orderly shutdown. Up to eight clients are accepted; requests are limited to 1 MiB and retained events to 256. `events.since {after}` answers `{events, current_sequence, gap}`. Each event names its `sequence`, the `method` and `request_id` of the change and, when the change has one, the `asset_id` it changed and the `revision` it left that asset at, or the `library_sequence` of the library change it recorded: each batch of a Develop names its library change, a version names its asset but no revision, since naming an entry moves none, and a preset, module or artifact change names no asset. Keep `current_sequence` as your cursor. `gap` is true when the log no longer holds every event after your cursor, or when your cursor is past the newest sequence, as one kept from an earlier run of the editor is; then read what you show again, with `asset.state` for a photograph. To be woken by a change instead of polling, send `events.wait {after, timeout_ms?, asset_id?}`: it answers the same `{events, current_sequence, gap}` as soon as the log holds an event after `after`, one naming `asset_id` when you give it (or `gap` is true), and otherwise answers with no events when `timeout_ms` passes. `timeout_ms` is 0 to 30000 and defaults to 10000; a larger value is refused rather than shortened, and 0 answers at once like `events.since`. Read the answer's `current_sequence` as your next cursor and wait again. The editor holds the wait without blocking anything or polling. A client holds at most one wait: a second `events.wait` from it answers the earlier one at once with no events and takes its place, and closing the connection drops a held wait. A connection serves one request at a time, so while a wait is held on it the client sends nothing else there: use a second connection for other requests, or wait with a short `timeout_ms`. The editor itself reads back only changes to the photograph it has open, and skips an event whose revision it already shows.

A catalog has one owner. Starting the headless command against a catalog open in the GUI fails instead of creating competing state. A request the owner fails to serve unexpectedly is answered `internal`, and the owner goes on serving every client. Request IDs deduplicate retries; reusing one with different input fails.

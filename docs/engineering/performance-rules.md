# Performance rules for core and desktop changes

Required for every change to `luxforge-core`, the desktop adapter or the JSON API. Budgets and measurement method live in [the performance plan](../specs/performance.md).

## Why these rules exist

The first M1 implementation was correct and fully tested, and every test ran on a 480×320 fixture. At 24 MP the same code re-read and hashed the original twice, decoded it again, cloned the frame, rewrote the whole frame once per transform layer, rendered a full frame to check one pixel and re-fetched the history page after every command. One pixel click cost about 330 ms and stalled every API client, and none of it was visible in the test suite. Correctness tests do not reveal per-operation cost, and small fixtures hide it completely.

## Rules

1. **Decode the original once and reuse it by signature.** Every request path obtains pixels through the signature-verified prepared-source cache. Byte length, modification time, file identity and change marker validate a hit without hashing. On a miss the source worker reads, hashes and decodes one bounded file handle; the owner adopts only a matching completion. A cold known RAW develops directly at the validated requested entry’s gains; a new import uses as-shot gains. A committed RAW WB change redevelops the retained mosaic on that worker; a drafted one is previewed approximately on the development in memory and redevelops nothing. Never call `open_source` from an owner request path or hash the file on a cache hit.
2. **Share immutable pixels; never clone a frame you do not modify.** `SourceImage` and `Raster` hold `Arc<Vec<u8>>` frames allocated zeroed (`vec![0; n]`, so fresh pages are faulted in by the pass that writes them rather than filled first), the upload handle borrows the same allocation and a JPEG identity recipe returns the source buffer itself. RAW retains an `Arc<Vec<u16>>` mosaic and a planar float `Arc<Vec<f32>>`; crop/orientation views share the float allocation, and display pixels are a terminal rendition. A new full-frame `Vec` needs a reason written in the code.
3. **Compile a recipe before rasterizing, and rasterize in one pass.** Exact geometry composes into one integer mapping; pixel replacements map through the suffix geometry after that pass. A new effect joins `compile` as an operation with declared input and output stages. An interpolating or color operation that cannot fuse states its own stage boundary and is measured before merge.
4. **Point queries never rasterize.** Anything that answers "what is this pixel" or "what are these dimensions" uses `Render::sample` or the compiled geometry and costs O(layers), including no-op detection, API sampling and future eyedropper or histogram-at-point features. **The one declared exception** is a sample through a spatial segment, whose value depends on a bounded neighbourhood and cannot be answered in O(layers). The reference renderer answers it until samples come from GPU tiles ([GPU-first](../design/gpu-first.md), stage 4): it evaluates the one stage-aligned tile that contains the pixel (512 px, or 1024 px when the operation's summed halo passes 128 px, the side the render uses), plus the operation's summed halo, through the same tile function the reference render uses and one working set from the spatial budget, so the sampled byte is the reference frame's byte by construction; a frame the GPU draws is held to that frame within the declared tolerance, not to its bytes. It allocates no frame. Its cost is O((tile + halo)² × layers), plus one bounded reduction of the stage when a unit's global estimate is not cached. Through several spatial segments the halo reads the earlier segments' tiles from one cache per query, so each tile is evaluated once per query and never once per pixel. No-op detection and validation never take it, because a module plans by payload comparison.
5. **The catalog owner thread does catalog work only.** It serves every client in turn, so a render there stalls the desktop and every agent. It never reads image payloads, decodes, demosaics, rasterizes, resizes, encodes or hashes pixels. Source cache misses return a preparation job; short signature and catalog checks remain on the owner. Frame work goes to the preview worker (one persistent thread, one active job plus one replaceable pending job, results tagged with a generation) or to another worker on the same latest-job primitive, `luxforge_core::latest`. Every pixel read through a spatial prefix, including a module query or a mutation's planning sampler, is planned on the owner in `O(layers)` and evaluated by the point worker: one thread, idle-blocked, taking samples, queries and parked mutation reads in order from a queue bounded by the live-client limit plus the desktop, because every waiting call has a caller waiting on it and none may be superseded. A mutation returns its pixels to the owner for entry, revision, draft and verified source checks before replay, at most four rounds. Draft memoization is bounded to 32 answers; disconnect cancels active point work and drops queued and parked reads. Pointwise samples and metadata-only queries stay owner work.
6. **Every buffer and queue has a limit and a `ResourceLimit` error.** Current limits are listed in [architecture](../design/architecture.md#limits). The current viewport implementation admits, per photo surface, one current and one retiring full-photo allocation, each up to 512 MiB, plus two region sets up to 32 MiB each including retirement, within one 1 GiB full and 64 MiB region aggregate shared by every surface. The owner provisionally accepted this 1088 MiB temporary-overlap engineering ceiling on 2026-09-27; it keeps the old photograph drawable during a size change but is not a total editor or GPU product budget. The mip levels of a photograph drawn under half its size, a third more than its base, are part of the slot that holds them and count against both caps; a photograph that cannot have them within one texture and one allocation is drawn from its display reduction instead. The GPU stage's boundary, a geometry tail's intermediate, its output, its program buffers and a spatial step's planes and a chain's link intermediates, one slot per surface, a picture at rest's tile slot, accumulator and output, each surface's two histogram reductions (3,096 bytes of counts and the kernel's table of up to 32,776 bytes, and each readback's 3,096-byte staging copy), and the photograph's source held once for every surface are charged to their own 2 GiB GPU-preview budget, shared by every surface and outside the photo ceiling; an allocation that would pass it is refused and the frame is drawn from the CPU's, but for a picture at rest's tile the budget holds once what the tiles before it released has retired, which waits for that retirement. One boundary is bounded separately, at 256 MiB, and a boundary past that bound is never derived ([decisions](../decisions.md#gpu-previews)). The desktop's GPU tile worker draws export tiles on a device of its own, charged before anything is created to its own budget, `GPU_TILE_BUDGET` (1 GiB, a proposal), apart from the GPU-preview budget: an export draws at the longest tile side whose every tile fits it less a 256 MiB reserve for reads, and one none of whose sides fits is the reference's (`tiles-budget`); its stream holds at most two bands waiting for the encoder (`EXPORT_BANDS_IN_FLIGHT`), and the worker draws nothing more until the encoder takes one. A crop-stage GPU texture is separate from these photo slots: its source raster is core-limited to 512 MiB, but tile aprons and the stage texture are not charged to the photo ceiling. Overlays are also excluded. Uploads use 8 MiB chunks that borrow the raster, so application staging adds no full-frame copy; native backend staging remains unmeasured and outside this application-owned ceiling. Crop GPU textures, overlays and backend staging need native measurement and bounds before any total-memory guarantee. A new allocation that scales with image size or history length names the limit that bounds it. A shared working-memory budget is a target, not a limit: it keeps work small or sets how much runs at once, and when it is taken the work runs with less, or past it, rather than failing. The spatial and colour scratch budgets work this way; see [decisions](../decisions.md#rendering-memory).
7. **Desktop commands take the narrowest completion path.** A mutation calls the command, refreshes `asset.state`, reads what the changed panels show (the session and the displayed entry's recipe rows and masks), requests one preview job and merges the resulting entry into the loaded page and lineage; undo, redo and restore also read the lineage. The history page, the versions and the Original's identity are read when an asset opens or changed elsewhere, never after the desktop's own commit, and a history page is rows read from columns, never decoded stacks. Whether an answer is still wanted is decided from what it carries when it arrives — its session's preview generation and its asset revision — never by asking the owner again. A history selection requests only the preview job. A view change reuses matching full-image or region texels when they cover the viewport; otherwise it submits one bounded region request through the shared gate.
8. **Idle means asleep.** Blocking receives and blocking `accept` are correct; loops that wake to check a flag are not. Preview and overlay workers wake the desktop while work is outstanding; a whole-frame exact phase also wakes it with its progress, only after 250 ms and at most every 50 ms, and no timer reads that progress. The GPU-retirement worker blocks on receive when idle; while textures are retiring it calls nonblocking device poll at 2 ms intervals so completion callbacks progress without another input or draw. A held `events.wait` adds no thread or timer: the catalog owner sleeps on its channel's receive timeout, set to the soonest deadline, and on a plain receive when none is held. The retirement channel subscription remains open while a photograph is shown; the catalog owner wakes the desktop when another client's change reaches the event log (`OwnerHandle::watch_events`), and only then does event sync read `events.since`, while an asset is open. The shared 25 ms quiet timer is armed only while a view at 100% or above is unsettled and, after 120 ms without newer accepted input, settles it — a pan at rest planned at rest, a paused draft the reference draws refined to its exact visible region alone; no pause renders a whole frame — and it is disarmed after settlement. A histogram readback, the picture at rest's tiles' counts or a gesture tick's, adds no thread, timer or wait: it completes on the retirement worker's existing poll and wakes the desktop through the surface's waker. The Performance section's one-second sampler runs only while that section is expanded with the state panel shown. A running export's and capability job's 100 ms readers exist only while that job is queued or running: each is a subscription stream that reads the job through the owner itself, off the update loop, and yields a message only when the record changed or the job ended, so an unchanged read wakes nothing and costs no view rebuild or redraw. The photo surface's settle dissolve asks for the next frame from its own redraw only while it runs, at most 150 ms, and runs no update; the redraw that finds it ended asks for nothing. A picture at rest in tiles asks for the next frame only while tiles remain and through its own 150 ms dissolve, and the source's upload only while rows remain; a tile waiting for a compile or a retirement asks for none, the compile's or the retirement's end waking the desktop. With nothing happening, the desktop's update loop does not run.
9. **Parallelize from each pass's own measured threshold with the shared Rayon pool.** A rendering pass runs on the pool at and past a pixel count chosen for its kind and measured, serial against pooled with one unit at 0.025 to 2 MP, never one constant for every pass: a segment's geometry from 0.5 MP; its colour runs from 0.1 MP with one or two units and from 25,000 pixels with three or more or a mask, counted over the rows they reach; a resample from 0.1 MP of output; a spatial operation's tiles from 0.25 MP of stage; a proxy's box downscale from 0.5 MP of source read. The thresholds are named in `luxforge-raw`'s limits module (`parallel_pixels`), each with the measurement it rests on, and every rendering pass asks the one gate that reads them (`render::parallel`). A new pass kind gets its own measured row; a changed kernel is measured again before its threshold moves. RAW development, a spatial operation's global-estimate reduction, the analysis reducer and the overlays keep the one-megapixel `PARALLEL_PIXELS`. No private thread pools or a thread per row.
10. **History storage grows with stack size; do not add copies.** Each entry already stores its complete stack. History entries hold no derived pixels: do not add per-entry buffers or materialize every snapshot to show the first page. Disposable caches of rendered pixels live outside history, under rule 14.
11. **The GPU renders at the view's size; the reference renderer supplies what the GPU does not render yet, by name.** The GPU is the renderer of record ([GPU-first](../design/gpu-first.md)): a gesture's frames are drawn on the GPU at Fit and below 100% from the source reduced to the view's size and at 100% and above over the visible region at full scale, and the committed stack at rest is drawn on the GPU too, at Fit and below 100% process-first, the stack at full resolution in tiles reduced to the view's size, and at 100% and above over the visible region. Every boundary is derived on the GPU from the photograph's source it holds. Every output the GPU renders is held to the reference renderer's whole frame at the view's size within the declared tolerance, which `cargo xtask gpu-qualification` measures: by the [recorded default](../design/gpu-first.md#proposals-with-recorded-defaults) the picture at rest is gated against the reference, and a drag's frame, which at Fit and below 100% processes a reduced source for speed, is reported against the picture at rest it settles to and against the reference, not gated while the owner's question is open ([performance](../specs/performance.md#gpu-qualification-against-the-reference)). Nothing approximate is drawn at rest. A committed stack the GPU draws is presented by the GPU with no CPU render, and its histogram and whole-image clipping counts are the GPU's reduction over the stack's tiles at full resolution, held to the reference's counts by the gate; during motion the counts are the displayed frame's, labelled updating. Until each later stage of that plan lands, the reference renderer supplies the rest: a stack the GPU cannot present at rest (its exact whole frame and its report, reduced to the view where the view draws it smaller: before the surface has checked its stage, an open's first picture, a plan the GPU cannot draw, a comparison, no usable adapter), any drag the GPU cannot draw, which names its reason (the recipe against a cached display-bounded source proxy at Fit and below 100%, and at 100% and above the visible region at half linear resolution, its exact region after the shared 120 ms quiet policy, its whole frame only as the release's), and samples. Export is the GPU's, in full-resolution tiles the desktop's GPU tile worker draws on its own device and the encoder takes as they arrive, held to the reference export within the display limit; the reference renders it when asked (`reference: true`), on a host with no GPU and when the GPU cannot draw the stack, at once or part-way, starting again from nothing ([export](../design/export.md#behavior)). Every reference pass checks its cancellation token per row or chunk. A layer is region-eligible only when its coordinates and effects can be evaluated exactly through the cut; unsupported stacks report their fallback.
12. **Every runtime hop costs a display frame, and the update loop waits for nothing slow.** During a drag a redraw is always in flight and the main thread waits on its present, so a task result, a worker's wake or an allocation answer arrives one frame later. The gesture's session-only draft requests — `draft.begin`, `draft.set` with its preview job, `draft.reapply` and `draft.cancel` — are therefore synchronous owner calls on the desktop thread, so a press sends its first `draft.set` in its own update; only `draft.commit`, which writes the catalog, is an owner task. An owner task runs on the runtime's blocking pool, never on the update loop: iced 0.14 polls every new task once, synchronously, on the update loop, so a task whose future never awaits does its work right there, and that is how a hover readout's `render.sample` through a spatial stack held the window for minutes and a RAW white-balance release held it for its whole redevelopment until 2026-10-04. The pool's price is one hop per answer, about 8 ms on a slider release's committed frame, listed under known remaining costs. The photograph is drawn through a surface that owns its texture and writes it in the frame that draws it. Put a new hop on the input path only with a measurement.
13. **Measure on photo-sized inputs before claiming anything, once the change is complete.** Run the release diagnostic on 24 MP and 60 MP JPEGs and record p50/p95, host, profile and cache state. The 480×320 fixture proves exactness, not cost. Take the before/after once the feature is complete: a figure taken mid-implementation measures code that is about to change, on a host other sessions are building and testing on. Only work whose subject is performance measures as it goes, with one targeted command at its default sample count, and still takes its claimed distribution at the end. Timing gates do not belong in CI; exactness and bound tests do.

```sh
cargo xtask generate-fixtures --output fixtures/generated
cargo run --release --locked --package xtask -- editor-performance --source fixtures/generated/24mp.jpg --output artifacts/new-perf-24 --samples 30
```

14. **Reuse unchanged work through bounded, disposable caches.** Editing responsiveness comes first, and recomputing what has not changed is a cost like any other. When a measured interaction repeats work whose inputs are unchanged, a cache is an expected fix, weighed by the memory it holds against the time it saves ([decisions](../decisions.md#rendering-memory)). The existing ones are the prepared source, the second RAW development, the owner's hydrated entries, the frames an open crop draft holds and each overlay worker's mask input grid, the photograph's source held on the GPU, and the Fit proxy, the estimate store and the store of reduced planes (a spatial operation's first unit's reduced grid, [efficiency](../design/efficiency.md#the-reduced-grid-cache)), which the [GPU-first plan](../design/gpu-first.md#stages-and-what-each-deletes) retires stage by stage. A cache:
    - is keyed by everything its value depends on — source and development identity, the recipe prefix or entry it evaluated, geometry, window, scale and quality — so a hit returns the bytes a recomputation would, and a test proves it for each part of the key;
    - has a byte budget or entry count named in [limits](../design/architecture.md#limits), like any allocation under rule 6, and evicts before it builds a replacement that would take it past that;
    - counts RAW planes it holds through the source worker's memory gate, as the second development does, and otherwise holds its own bytes, never an evaluation or a source, so nothing cached stops the next development from starting;
    - is disposable: it never stands in for an original or an artifact, is never stored in history, and losing it costs only time;
    - is filled by frame work on a worker, never on the owner or UI thread;
    - is adopted with its hit rate, rebuild cost and retained bytes measured on photo-sized inputs under rule 13, and removed when it does not pay for itself, as the desktop's per-region derivation keys were.

    A budget that adds to the RAW working set or another memory target the owner has set needs the owner's acceptance or delegation, as the second development's 600 MiB did. Candidate caches are recorded in [instant previews](../design/instant-preview.md#proposals-and-later-work).

## Review checklist

Answer each item in the commit or plan for any change under `crates/`, once, for the finished change:

- Which request paths read, hash or decode the original, and do all of them go through the cached verified source?
- Which new full-frame allocations exist, which limit bounds each one, and which are shared rather than cloned?
- Does any point query, validation or no-op check render a frame?
- What now runs on the owner thread, and is any of it frame work?
- Which desktop messages trigger `asset.state`, `history.list`, a preview job or an upload, and is each one necessary?
- Which timers, polls or subscriptions were added, and what gates them?
- Which work does an interaction repeat with unchanged inputs, and for each cache added or changed, what is its key, which limit bounds it, and what hit rate, rebuild cost and retained bytes were measured?
- What did `editor-performance` report on 24 MP before and after, and where is that recorded with its scope?
- Which exact-buffer tests hold the reference renderer to a stepwise reference for new effects; which reference-buffer comparisons hold what the GPU renders to the reference within the declared tolerance (`cargo xtask gpu-qualification`, the release gate, for every output kind and view the change touches); and which tests prove buffer sharing where sharing is claimed?

### Image information review

The information overlay reads only the document's capture projection, selected recipe output stage and live crop geometry. `source.inspect` projects validated EXIF from the signature-verified prepared source; the desktop adds one inspection on open after preparation and keeps its small result per photo. The existing metadata reader bounds ASCII fields to 1024 bytes and each source's retained metadata to one EXIF segment. No new full-frame allocation, pixel query, render, source decode or cache is added. The owner projects small metadata fields only. Toggling makes one `workspace.set` call and a session adoption, with no `asset.state`, history refresh, preview job or upload; no timers or subscriptions are added. Each visible view derives bounded text from the same inputs; no performance improvement is claimed. Native smoke checks raster version, texture writes and preview generation across a toggle, and metadata tests exercise exact values through independent EXIF fixtures. The general 24 MP editor-performance workload does not measure this overlay's text-layout cost.

### Viewport change review

The original is still opened through the signature-verified source cache. RAW region views share the
retained planes; byte regions use a bounded source copy, and the resample stage materializes only the
requested rectangle. The current implementation allows each photo surface one current and one
retiring full-photo allocation, each at most 512 MiB, and two region sets at most 32 MiB each
including retirement, with every surface's allocations within one 1 GiB full and 64 MiB region
aggregate. This full-slot count increase is proposed for owner acceptance. Full and
region slots reserve bounded size buckets, so a rotated Fit proxy and half-to-exact region change
usually rewrite active texels without reallocating. A deferred upload keeps one coherent previous
picture visible and marks it updating; overlays tied to other content are suppressed. The crop stage
has separate GPU tiles outside these photo slots, sized to its frame: display-size at Fit, full
size only at a percentage zoom that needs the exact stage. An 8 MiB upload chunk borrows the raster; it
makes no full-frame application staging copy. Backend staging is not measured.

Rendering, estimate reduction and coverage run on workers. The desktop owner admits a single desired
view through the shared gate; preview has one active and one replaceable pending job. Abandoned
interactive work stops; superseded interactive work continues to make progress under sustained input,
while newer refinement and exact analysis supersede old work. One retirement worker blocks while
idle and polls without waiting while a resource is retiring; a flushed queue submission fences
pending writes before a completion callback releases its charge. The surface wakes the app when a
draw enters or leaves its temporary stale or blank state. The shared 25 ms timer implements the
120 ms quiet policy and is disarmed after settlement; release settles immediately after its last
input drains.

Point sampling remains the exact `Render::sample` query; viewport display never rasterizes a frame for
sampling, validation or no-op detection. A view-only change updates desired-view state and requests
one bounded preview; it does not add `asset.state` or `history.list` calls. The owner handles recipe,
history and request identity, while the desktop worker and surface own region scheduling, drawing and
texture retirement. The existing full-frame analysis path alone supplies exact whole-image histogram
and clipping counts.

Native photo-sized evidence and its limits are recorded in [performance](../specs/performance.md#native-viewport-region-qualification).
The final build's first 60 MP Dehaze region arrived after 863.91 ms with a cold exact whole-stage
estimate on a host starting at load 9.51. Fit exposure input-to-adoption was 8.34 / 8.95 ms
p50 / p95 at 24 MP and 8.57 / 8.80 ms at 60 MP (30 inputs each, both starting below load 8.0);
the 200% masked moving-pan burst's staleness was 25.66 / 34.47 ms
(153 samples) on a host above the 8.0 load threshold. A native crop-window artifact recorded a
451 × 418 intermediate, while the committed 1000 × 800 fixture proves bounded materialization;
byte/RAW windows match full-frame slices. Permanent native viewport scenarios and Metal surface
readbacks verify current draw and retirement behavior. The final default-open Performance-section
idle result was 1.421% of one core over one 30.26-second window. Backend staging remains unmeasured,
and no numeric photo-error bound or general speedup is claimed.

The focused renderer and scheduling references are `a_half_detail_region_is_the_same_scaled_recipe_at_the_same_pixels`,
`rotated_resample_entry_keeps_only_the_viewport_on_both_domains`,
`a_raw_window_composes_every_source_orientation_without_copying_planes`,
`settled_viewport_delivers_exact_region_then_whole_report`, and
`settled_viewport_carries_region_then_whole_stage_mask_coverage`.

## Anti-patterns already removed

| Seen in this repository | Replacement |
| --- | --- |
| Read, hash and decode the original on every preview, sample and edit | Signature-validated decoded-source cache |
| Clone the source into the render buffer, then allocate a new frame per transform layer | Composed geometry, one parallel pass, shared identity buffer |
| Render a full frame to compare one pixel for no-op detection | `Render::sample` |
| Materialize a RAW spatial operation's whole float frame to answer one point sample through it | The one tile that contains the pixel, through the render's own tile function |
| Evaluate an earlier spatial layer's whole tile for every pixel a later layer's tile reads, or materialize its frame, to answer one point sample | One tile cache per query, shared by both paths, that evaluates each tile once |
| Re-fetch state and the history page after every command, and re-render on zoom | Narrow command, preview and session tasks with entry merge |
| Decode every entry's whole stack to list a history page; read versions, lineage and a one-row page for the Original after every commit; check a preview job's currency with two owner round trips before and after it | History rows read from columns; a refresh scoped to what the command changed, the Original read once per open; currency decided from the answer's session generation and asset revision |
| Accept loop sleeping 10 ms in a non-blocking spin | Blocking `accept` woken by one loopback connection on shutdown |
| Desktop tasks sleeping 50 ms between source job reads while a source job prepares or the source queue is full, through four call helpers and a capability copy of them | One owner task and one call helper; `OwnerHandle::wait_source` blocks until the owner says a job ended |
| Per-region derivation keys over `Tracked` stamps, a compared session, per-section digests that formatted and serialized each section's inputs, and a debug re-derivation to catch a missing key, added with no measurement | Every region derived after every message, measured at 0.05 to 0.14 ms p50 per message (0.003 to 0.05 ms keyed); the p95 follows the shared host's load, 0.08 to 0.68 ms against the keyed build's 0.02 to 0.37 ms, and input to presented frame is unchanged ([performance](../specs/performance.md#the-workspace-derivation-per-message)). The palette lists its entries only while it is open |
| A 100 ms timer message and a read task per tick for every running export or capability job, so each tick cost two messages, two view rebuilds and two redraw requests whether or not the job had changed (a fast path in `update` skipped the derive but not iced's rebuild) | A subscription stream that makes the reads itself and yields only a first, changed or final record (`app/job_reads.rs`) |
| A 500 ms timer that woke the desktop to read `events.since` whenever an asset was open, whether or not anything had changed | The owner wakes the desktop when another client's change reaches the log; its own changes wake nothing, since their answers read them back |
| Debug build as the default development launch | Release-profile `develop`; explicit `--debug` for debugging only |
| Tiny fixture as the only timing evidence | `editor-performance` on generated 24 MP and 60 MP inputs |
| Zero-fill a RAW development's planes, mosaic and warp scratch with `Vec::resize` on one thread before a pooled pass writes every value | `zeroed_vec` (`alloc_zeroed`), so the writers fault fresh pages in |
| Allocate a fresh zeroed input and one output per unit for every spatial tile | One slot a worker, two ping-pong plane buffers grown once to the plan's largest tile and never cleared ([performance](../specs/performance.md#cpu-and-memory-efficiency-measured-on-the-m4)) |
| Wait for a whole batch of spatial tiles before starting the next | A rolling window: each worker starts its next tile as soon as its last is written, under the same reservation |
| Hold a normalized float copy of the RAW mosaic through the demosaic | The demosaics read each site from the u16 mosaic through a checked-in librtprocess patch, 4 bytes a site less at the peak |
| Hash every original in software on aarch64 | `sha2`'s `asm` feature on aarch64, the hardware SHA-256 instructions |
| Desktop tasks carrying a session copy out and writing it back after the round trip | Owner-held sessions per client with a revision; the desktop adopts only newer responses |
| Decode an entry's JSON, look up, hash and parse each of its strokes, and re-parse the RAW interpretation on every state read, three times per slider tick; deep-copy every stroke with each recipe clone | The owner's bounded cache of hydrated entries and asset heads, updated by every write; `revision()` for a draft's conflict check; a shared stroke table; the RAW interpretation typed once per row read |

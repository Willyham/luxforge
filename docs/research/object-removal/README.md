## Segment once, fill locally, share the encoder

Luxforge should build object removal as two stages on one shared, local inference service: a SAM-class segmenter whose image encoder runs once when the tool is picked and whose small prompt decoder answers every hover, click and brush stroke, then a background fill whose shipped baseline is Big-LaMa (Apache-2.0 code and weights) inside a crop, detail-transfer and grain-resynthesis pipeline built for 24–60 MP frames. Real-time hover is achievable: SAM-style decoders measured **5.6–9.1 ms** on an M4 under Core ML after a **25–56 ms** mobile-encoder pass ([onnxsim PR #1904](https://github.com/onnxsim/onnxsim/pull/1904)), and the front-runners (EfficientViT-SAM, SAM 2.1, EdgeTAM) are Apache-2.0 in code and weights. A painted stroke becomes a box, a few sampled points and stroke-filtered proposals, which yields Lightroom's "one object → remove, several → pick" behaviour directly, but SAM masks never include shadows or reflections, so the selection needs an explicit, editable effect region, as Lightroom's Detect objects provides. Generative, effect-aware removal is the unsolved part: the best removers (the ObjectClear family, everything on FLUX.1-dev) are non-commercial, the fast SDXL-based ones carry OpenRAIL++-M use restrictions, and the one Apache base with the capacity, FLUX.2 klein 4B, has no removal training and needs an estimated 15–30 s per 1024-px candidate. Native code should accelerate rather than segment, because Apple Vision's instance masks cover only noticeable foreground objects, its brush-seeded segmenter is Swift-only on macOS 27, no Apple API removes objects, and Windows' extractor and remover run only on Copilot+ NPUs. OpenStill confirms the flow but not the method: it pairs Apple Vision with a Python, CPU-only LaMa fixed at 512 px and bakes the result into a new base image, which Luxforge's first pillar forbids. The same runtime, embedding cache, picker and stored alpha artifacts then carry semantic auto-masking (BiRefNet for Subject, a DINOv2 EoMT pass for Sky and Landscape, RF-DETR-Seg for People), and nothing should be pinned until twelve M4 measurements and nine owner decisions, chiefly the weights-licence policy, are settled.

## OpenStill sketches the flow; Adobe and darktable set the bar

OpenStill is the requested reference, and its code answers the question quickly. It is an MIT-licensed Swift editor for macOS 13+, created on 25 September 2026, with one star when read. **134 of its 183 commits were authored by `claude`** ([GitHub API](https://github.com/haon-v2/OpenStill), [contributors](https://github.com/haon-v2/OpenStill/graphs/contributors)). All object selection is Apple Vision. A click downsizes the image to at most 1600 px and runs `VNGenerateForegroundInstanceMaskRequest` over the whole frame. It reads the instance label under the cursor, then asks Vision for a full-resolution soft mask of that one instance ([VisionEditor.swift](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/Sources/OpenStillCore/VisionEditor.swift#L14-L31), [MaskEditingController.swift](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/Sources/OpenStill/MaskEditingController.swift#L159-L183)). The README states plainly that this "is not arbitrary text-prompt/background-object selection" ([README](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/README.md#L387-L393)).

Removal is a separate two-step "Erase AI" tool: the user builds a mask, then presses Remove ([README](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/README.md#L453)). The app spawns a worker in a Python virtual environment. The worker runs the OpenCV LaMa export (92.6 MB, pinned by revision and SHA-256) through onnxruntime 1.23.2 with **only the CPU execution provider** ([models.json](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/Resources/AI/models.json), [engine.py](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/Resources/AI/engine.py#L9-L41)). It pads the mask's bounding box by max(48 px, 0.4 × its longer side) and Lanczos-resizes that crop to **exactly 512×512**. After LaMa runs, it scales the result back and composites `rgb*(1-mask) + restored*mask`. Unmasked pixels stay exact, and HDR residuals outside [0,1] survive ([float_bridge.py](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/Resources/AI/float_bridge.py#L126-L140)). The app then **replaces the photo's `baseAsset` with the result and starts a fresh `PhotoEdits()`**, so every edit made before the removal stops being a live parameter ([EditingController.swift](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/Sources/OpenStill/EditingController.swift#L417-L423)). There is no hover segmentation; the canvas's only mouse-move handler moves the brush outline. There is also no automatic detection, no shadow handling and no variations. Its QA notes contain one timing, a smoke test of about 3.1 s on a 256×192 image ([PhotoCanvas.swift](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/Sources/OpenStill/PhotoCanvas.swift#L50-L53), [QA.md](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/QA.md)).

Luxforge should keep four of OpenStill's ideas. The first is **a precomputed instance label map that makes hit-testing constant-time**; OpenStill computes one but never uses it for hover. The others are **a crop margin proportional to the mask**, **bit-exact compositing outside the mask with HDR residuals preserved**, and **a SHA-pinned model manifest** whose notices keep each weight's own licence. It should reject four others. Baking the render breaks "edits are data". A Python sidecar breaks the rule that all tooling is Rust ([decisions](../../decisions.md)). CPU-only inference at a fixed 512 px enlarges big regions into softness. Foreground-only selection misses the poles, signs, litter and distant people that removal exists to target. The project is two days old, so it is a design sketch, not proven practice.

Adobe sets the UX bar that both requested modes copy. In Lightroom Classic the user brushes roughly. With Detect objects on, Lightroom "will also identify the shadow and reflections (if any) around the object and include it in the selection". The user refines with Add and Subtract, and Remove generates **three Firefly variations**, with Generate for three more. The generative path needs an internet connection ([Adobe HelpX](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/remove-tool.html)). Distraction Removal › People scans for people and marks each with a pin on a red overlay; deleting a pin keeps that person ([Adobe HelpX](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/distraction-removal-people.html)). Photoshop's Object Selection tool analyses the image as soon as it is chosen, then highlights objects on hover ([Adobe HelpX](https://helpx.adobe.com/photoshop/desktop/make-selections/get-started-selections/select-objects-with-object-selection-tool.html), [Photoshop Essentials](https://www.photoshopessentials.com/basics/using-the-object-selection-tool-and-object-finder-in-photoshop-2022/)). DxO PhotoLab 9 does the same with a red hover overlay ([Life after Photoshop](https://lifeafterphotoshop.com/dxo-photolab-9-ai-masking-tools-explained-with-examples/)).

Local generative removal is expensive even for Adobe. Photoshop's on-device generative Remove requires, for example, an RTX 30-series GPU with 14 GB or more of VRAM on Windows ([Adobe HelpX](https://helpx.adobe.com/photoshop/desktop/repair-retouch/remove-objects-fill-space/remove-tool-minimum-and-recommended-hardware-requirements.html)). The cloud path has limits too. Adobe staff confirmed Generative Remove patches are **capped at 2048 px**, and users report fills that do not match the photo's grain ([Lightroom Queen](https://www.lightroomqueen.com/community/threads/resolution-with-generative-remove.50557/), [Adobe community](https://community.adobe.com/t5/lightroom-classic-discussions/more-noise-after-using-generative-ai-remove-on-a-raw-file-with-denoise-14-4/td-p/15422951)). A 60 MP frame is exactly where Luxforge can beat the reference.

darktable 5.6 is the portable template. It runs SAM 2.1 or SegNext through ONNX Runtime with CoreML, DirectML, CUDA, ROCm, OpenVINO or CPU providers, and ships AI off by default. Models download on demand from a GPL-3.0 model repository that admits only weights "under a license compatible with GPL-3.0". The first click on an image costs **1–10 s** for the encoder, after which clicks are interactive. It has no inpainting model yet ([darktable blog](https://www.darktable.org/2026/06/meet-darktable-5.6-ai-tools/), [darktable-ai](https://github.com/darktable-org/darktable-ai)). The owner's brush mode is therefore Lightroom's Detect objects plus its People pins, and the hover mode is Photoshop's Object Finder. darktable proves the plumbing in a GPL editor, and no open-source editor yet ships removal that handles shadows.

## A cached encoder and a sub-10 ms decoder make hover real

Segment Anything splits a heavy image encoder, run once per image, from a prompt decoder of about 3.9 M parameters. SAM ViT-H's encoder takes 452 ms on a GPU; its decoder takes 4 ms ([MobileSAM](https://github.com/ChaoningZhang/MobileSAM)). Meta's own demo precomputes the embedding and runs a quantised ONNX decoder in the browser, updating the mask "in real time" as the cursor moves ([SAM demo](https://github.com/facebookresearch/segment-anything/blob/main/demo/README.md)).

The only direct M4 evidence is a parity spot check on an M4 Mac mini under Core ML, with one image and one prompt:

| Model | Encoder | Decoder |
|---|---|---|
| EfficientViT-SAM-L0 (at 512²) | 25.5 ms | 6.2 ms |
| EdgeSAM | 30.3 ms | 9.1 ms |
| MobileSAM | 56.3 ms | 5.6 ms |

— [onnxsim PR #1904](https://github.com/onnxsim/onnxsim/pull/1904)

Every decoder sits well inside a 16–33 ms hover budget. SAM 2.1's decoder does more work, and there is no Apple measurement of it. It consumes 256² and 128² feature maps and emits three 1024² masks ([darktable-ai SAM 2.1 card](https://github.com/darktable-org/darktable-ai/tree/main/models/mask-object-sam21-small)). Drawing hover overlays from its 256² low-resolution masks, and upsampling only on click, should keep it inside the budget (estimate). The requested hover mode is feasible. What limits it is how long the encoder pass takes after the tool is activated.

**EfficientViT-SAM is the front-runner.** It is the fastest licence-clean model measured on an M4 and has the best box-prompt quality in the unified benchmark. Box quality matters most here, because the brush flow is driven by boxes.

**SAM 2.1-small is the conservative challenger.** darktable ships it, Apple publishes FP16 Core ML exports of it ([Apple Core ML SAM 2.1](https://huggingface.co/apple/coreml-sam2.1-small)), and it reports better single-click image quality. Its Hiera encoder, however, does not fit the Neural Engine. One developer measured about 310 ms on a Mac GPU, plus a roughly 16 s first-load penalty when Core ML is left on `ALL` and tries and fails the ANE compile ([WobblePic](https://wobblepic.com/blog/apple-neural-engine-vs-gpu-cpu/)).

**EdgeTAM is the ANE-friendly alternative.** EdgeSAM would be ideal on speed, but it is non-commercial.

SAM 3 matches SAM 2.1-L on clicks (66.1, 81.3 and 85.1 mIoU at 1, 3 and 5 clicks, against 66.4, 80.3 and 84.3) at roughly ten times the size, under a custom, gated licence ([SAM 3 paper](https://arxiv.org/html/2511.16719)). It earns a place only if text prompts such as "remove all people" are wanted later.

### Convert the brush into a box, a few points and filtered proposals

No SAM-family model accepts a scribble, and the naive conversions fail. Treating every scribbled pixel as a click gave SAM ViT-h only Dice 0.56 in the ScribblePrompt benchmark, against 0.70 for a box fitted to the scribble ([ScribblePrompt](https://arxiv.org/abs/2312.07381)). Feeding the stroke as a `mask_input` prompt mostly returns the input again, users report ([segment-anything #169](https://github.com/facebookresearch/segment-anything/issues/169)). Boxes beat points by a wide margin: on COCO, SAM-H scores 53.6 mIoU from a centre point, 67.5 from three points and 77.4 from a ground-truth box ([survey](https://arxiv.org/abs/2410.04960)).

The robust conversion follows from that evidence (an inference). Rasterise the stroke at encoder resolution and send its padded bounding box as a **box prompt** with multimask output. Add three to five **positive points** chosen by farthest-point sampling along the stroke's medial path, plus every cached **proposal** whose mask intersects the stroke. Score each candidate on four measures: predicted IoU, stability, **stroke coverage** (the share of the stroke it explains) and **object coverage** (the share of the object the stroke touched). Then deduplicate with mask-IoU NMS around 0.7, following SAM 2's defaults ([sam2 mask decoder](https://github.com/facebookresearch/sam2/blob/main/sam2/modeling/sam/mask_decoder.py), [sam2 AMG](https://github.com/facebookresearch/sam2/blob/main/sam2/automatic_mask_generator.py)).

The owner's UX is then a decision rule over those scores. When one stable candidate explains most of the stroke (start at 0.6–0.8 coverage), it is removed, with its selection visible and cancellable while the fill job runs. When several disjoint candidates each have meaningful object coverage, they are pinned like Lightroom's People pins and a click chooses. When only "part" masks come back, the largest stable parent wins, because for removal the whole object is nearly always the intent. These thresholds are starting points to tune on a Luxforge fixture set, not published values.

SegNext (MIT) is the one permissive model that takes scribbles natively. Its decoder is heavy, about 103 MB. Its backbone was pretrained with MAE, whose repository is CC BY-NC 4.0, so it needs Luxforge's own licence review ([SegNext paper](https://arxiv.org/abs/2404.00741), [darktable-ai SegNext card](https://github.com/darktable-org/darktable-ai/tree/main/models/mask-object-segnext-b2hq), [MAE](https://github.com/facebookresearch/mae)).

### Precompute proposals so "several objects" and hover become lookups

Production hover follows one of two patterns. Meta's demo runs the decoder on every pointer move. Photoshop's Object Finder, like OpenStill's Vision map, precomputes every object and hit-tests a label map. A hybrid of the two is best. On activation, the encoder and a cheap proposal pass run on the module lane, cancellably. Hover hit-tests the proposals first and decodes live only where no proposal exists. A click refines at full quality. For a single hover point, show the candidate with the highest predicted IoU, biased toward the whole object. SAM 2's own guidance is to request multiple masks for ambiguous single clicks ([sam2 predictor](https://github.com/facebookresearch/sam2/blob/main/sam2/sam2_image_predictor.py)).

The proposal source decides the cost. A 32×32 segment-everything grid means 1,024 decoder calls, roughly 6–9 s unbatched at the measured M4 decoder speed (arithmetic). MobileSAMv2 showed that box prompts from a detector reach the same mask recall in **97 ms, against 1,616 ms** for the grid on a GPU ([MobileSAMv2](https://arxiv.org/abs/2312.09579)). Its bundled detector, however, is Ultralytics code under AGPL-3.0. The licence-clean replacement is **RF-DETR-Seg Nano or Small**: Apache-2.0, with 40.3–43.1 COCO mask AP at 3.4–4.4 ms on a T4 ([RF-DETR](https://github.com/roboflow/rf-detr)). It proposes people, vehicles, signs and other common distractors. Its person instances also directly power a Lightroom-style "remove these people" pin list.

### Recover resolution and the object's shadow before anything is filled

At a 1024² input, a 60 MP frame is downscaled about 9.3×. One cell of SAM's 256² low-resolution mask then covers **about 37 source pixels**, working from [SAM](https://ar5iv.labs.arxiv.org/html/2304.02643)'s 64² embedding and 256² mask. Three remedies recover detail. **Crop re-encoding** re-encodes a padded crop around a small object before the final decode, the same idea as SAM's own crop layers. **Viewport encoding** encodes the visible viewport when the user is zoomed in and cancels on pan (inference). **Guided upsampling** upsamples the logits with a guided or joint-bilateral filter against full-resolution luminance, as darktable does ([DeepWiki on darktable](https://deepwiki.com/darktable-org/darktable/6.2-neural-restore-and-ai-object-masking)). After that, dilate the mask by a radius proportional to the resolution. Inpaint Anything's 15 px was set for images of 1–2 MP ([Inpaint-Anything](https://github.com/geekyutao/Inpaint-Anything)). Removal masks are dilated anyway, so completeness matters more than edges of matting quality.

Completeness includes the object's shadow and reflection. Generic inpainters do not remove effects they are not given ([ObjectClear](https://arxiv.org/html/2505.22636)), and SAM masks never include them. The explicit detectors that could add them are unusable here. SSIS is non-commercial, FastInstShadow's licence is unconfirmed, and neither covers reflections ([SSIS](https://github.com/stevewongv/SSIS), [FastInstShadow](https://arxiv.org/html/2503.07517)).

Luxforge should therefore make the **effect region a first-class, editable component of the removal selection**, which is the Lightroom behaviour. For the baseline it starts from a heuristic contact-band suggestion, refined by the user's Add and Subtract brushes. PredErase's band, for example, grows upward from the object's floor contact with σ = max(6, 0.5·h) and δx = max(8, 0.35·w) ([PredErase](https://arxiv.org/html/2609.00956)). Later, an effect-aware model's predicted region can be offered for the user to accept. The learned route is clearly better when it is available. On OBER-Test, ObjectClear given only the object mask scored **33.04 dB PSNR**; RORem, given the ground-truth object-plus-effect mask, scored 27.23 dB ([ObjectClear](https://arxiv.org/html/2505.22636)). The explicit region is a crutch for the baseline, and the slot where the learned model's answer will go.

## LaMa is the honest baseline; no licence-clean generative remover exists

### Ship Big-LaMa inside a pipeline built for 60 MP

**Big-LaMa** is the permissive baseline. It has 51 M parameters of fast Fourier convolutions and was trained on 256-px crops of Places images. It stays coherent at 1536² and is strong on periodic structure such as fences and windows. It "struggles when a strong perspective distortion gets involved" ([LaMa paper](https://arxiv.org/pdf/2109.07161)). Its code is Apache-2.0 ([repo](https://github.com/advimman/lama)). Its weights are labelled Apache-2.0, but only on a Hugging Face mirror ([big-lama](https://huggingface.co/smartywu/big-lama)).

**MI-GAN** is the lightweight fallback. It has MIT code, separately MIT-licensed weights and 5.95 M parameters. It ran in 1.2 s at 1024² and 3.9 s at 2048² on an iPad Pro M2 ([MI-GAN](https://github.com/Picsart-AI-Research/MI-GAN), [RETHINED](https://arxiv.org/html/2503.14757), Table 2 and Figure 3).

Both models are deterministic, give one answer, and leave shadows alone unless the shadows are masked. Both need full precision. LaMa's Fourier blocks collapse to garbage in FP16, so its MLX port runs in bf16 ([mlx-lama-swift](https://github.com/xocialize/mlx-lama-swift)). Core ML LaMa runs well on the macOS GPU but fails in FP16 on the Neural Engine ([CoreMLaMa](https://github.com/mallman/CoreMLaMa)). **The fill runs on the GPU or CPU in fp32 or bf16, never on the ANE.**

At 24–60 MP, the pipeline around the model decides quality more than the model does. The proposed pipeline is an inference still to be validated:

| Stage | What it does | Precedent |
|---|---|---|
| Crop | Crop the object plus its effect region, with context proportional to the mask; OpenStill's max(48 px, 0.4×) is a reasonable start | IOPaint's fixed 128-px default margin was set for small images ([IOPaint schema](https://raw.githubusercontent.com/Sanster/IOPaint/main/iopaint/schema.py)) |
| Encode | Convert the scene-linear crop to display-referred sRGB with a recorded, invertible transform, using a log curve for crops with heavy highlights | Log encoding aligns HDR data with the priors of models trained on standard-range images ([arXiv 2604.11788](https://arxiv.org/abs/2604.11788)) |
| Rebuild detail | Run the model at its native size, keep its output only for low and middle frequencies, and rebuild high frequencies from the surrounding context | HiFill's contextual residual aggregation inpaints up to 8K from a 512-px network ([HiFill](https://arxiv.org/abs/2005.09704)) |
| Re-synthesise grain | Estimate noise from flat regions in a ring around the hole and synthesise matching grain | AV1's autoregressive grain model ([Norkin & Birkbeck](https://norkin.org/pdf/DCC_2018_AV1_film_grain.pdf)) |
| Match tone | Match low-frequency colour and tone across the ring | IOPaint's `sd_match_histograms` option ([IOPaint schema](https://raw.githubusercontent.com/Sanster/IOPaint/main/iopaint/schema.py)) |
| Blend | Blend with a Laplacian pyramid across the feathered edge | [Burt & Adelson](https://dl.acm.org/doi/10.1145/245.247) |

The corrections design already requires pixels outside the committed mask to match the input exactly, and freezes the accepted patch as an immutable artifact ([corrections design](../../design/corrections.md)). The detail and grain stages target the softness and grain complaints users raise against Adobe's 2048-px patches.

| Qwen-Image-Edit-2511 | 20B instruction editor with no mask input | The earlier 2509 model's 4-step variant took 2 min 28 s on an M1 Max ([lilting.ch](https://lilting.ch/en/articles/comfyui-qwen-mps-bf16-slowdown)) | Good in anecdotal tests | Apache / Apache ([HF](https://huggingface.co/Qwen/Qwen-Image-Edit-2511)) | Too heavy |

The qualification order follows from the table. **Ship LaMa first**, as the quality floor and the test bed for the crop, encoding, detail, grain and blend stages. Next, if the owner accepts OpenRAIL++-M, **qualify OSOR-SDXL and RORem-4S on the M4**. They replace the corrections design's PowerPaint and SDXL-inpainting candidates, which paired-data removers supersede. In parallel, **test FLUX.2 klein 4B zero-shot**, with the contact band and a fixed "empty scene" prompt embedding computed once, which removes the text encoder from runtime (inference). If klein shows promise, **train a removal LoRA for it** on OSOR's Apache-licensed CORNE pairs plus owner-shot pairs. CORNE's 287,012 pairs were mined from instruction triplets of unstated origin ([OSOR repo](https://github.com/Zhouqm-Git/osor)). This is the only licence-clean route to local removal that handles shadows. ObjectClear, TurboClear and the removers built on FLUX.1-dev (OmniEraser, OmniPaint, GeoRemover) stay evaluation ceilings, never downloads. Generative variations come from seeds, and Lightroom offers three per click. Diffusers warns that reproducibility "is not *guaranteed* even with an identical seed" across hardware ([diffusers](https://huggingface.co/docs/diffusers/using-diffusers/reusing_seeds)). That is why the corrections design's frozen patch, not regeneration, must stay the source of truth.

## Accelerate natively, keep models and masks portable

The capabilities contract rejects `local-runtime` by name today ([module capabilities](../../design/module-capabilities.md)). The masking proposal leaves the choice between tract and ONNX Runtime to the owner, to be made after measurement ([masking workspace](../../design/masking-workspace.md)). The evidence sharpens that choice without settling it.

**ONNX Runtime through `ort`** is the broadest and most proven option. darktable runs it with these provider orders ([darktable AI.md](https://github.com/darktable-org/darktable/blob/master/dev-doc/AI.md)):

| Platform | Provider order |
|---|---|
| macOS | CoreML → CPU |
| Windows | DirectML → CPU |
| Linux | CUDA → MIGraphX → ROCm → CPU |

pyke's static archive for Apple silicon with CoreML is 8.9 MB compressed ([dist.tsv](https://github.com/pykeio/ort/blob/main/ort-sys/build/download/dist.tsv)). Its risks are concrete. The binding is still a release candidate (rc.13, 2026-07-28), and its maintainer warned users to expect "little to no macOS support" ([ort rc.11](https://github.com/pykeio/ort/releases/tag/v2.0.0-rc.11)). The CoreML execution provider has **no DFT kernel**, so LaMa's FFT nodes fall back to the CPU and split the graph ([ORT CoreML operators](https://github.com/microsoft/onnxruntime/blob/gh-pages/docs/execution-providers/CoreML-ExecutionProvider.md)). An open bug returns wrong FP16 outputs on macOS 15 with MLProgram and static shapes, while the same settings pass on macOS 26 ([onnxruntime #32569](https://github.com/microsoft/onnxruntime/issues/32569)). By default ort downloads a prebuilt binary from a single maintainer's CDN, checked by SHA-256 and attestation ([ort binaries](https://github.com/pykeio/ort/blob/main/docs/content/misc/prebuilt-binaries.mdx)). Building ONNX Runtime from source instead takes over an hour and needs CMake, Python and C++20. That conflicts with the one-toolchain rule, under which LibRaw is built from pinned source ([RAW backend selection](../raw-backend-selection.md)).

**tract** keeps every project rule. It is pure Rust under MIT or Apache, with Metal and CUDA runtimes, per-node CPU fallback, and ONNX DFT and STFT with GPU FFT kernels. Those paths are only weeks old: the irfft correctness fix landed on 2026-09-21 and Metal implicit-GEMM convolution on 2026-09-08. There is no published SAM or LaMa result on tract, and it has no ANE path ([tract changelog](https://github.com/sonos/tract/blob/main/CHANGELOG.md)).

The other options fall short. **candle** has no FFT op and an open SAM-on-Metal bug ([candle #3307](https://github.com/huggingface/candle/issues/3307)). **burn** compiles each model architecture into Rust at build time, so a new architecture needs an app release ([burn-onnx](https://github.com/tracel-ai/burn-onnx)). **Direct Core ML through `objc2-core-ml`** is the only way to place work deliberately on the ANE and to use IOSurface zero-copy ([objc2-core-ml](https://crates.io/crates/objc2-core-ml), [Apple MLMultiArray](https://developer.apple.com/documentation/coreml/mlmultiarray/init(pixelbuffer:shape:))), but it costs a second model format and an offline coremltools conversion.

The recommendation is a single narrow inference port in the core and a measured choice between the two runtimes behind it. ort makes the A/B cheap, because `ort::set_api(ort_tract::api())` puts tract behind the same API ([ort rc.10](https://github.com/pykeio/ort/releases/tag/v2.0.0-rc.10)). The proposed decision rule: **adopt tract if the hover decoder holds about 10 ms p95 and the encoder about 300 ms with exact outputs; otherwise adopt ort with CoreML**, statically linked, with its archive hash and attestation checked in `xtask`.

The ANE matters less than its reputation suggests. LaMa cannot run in FP16, and SAM 2.1's Hiera encoder does not compile for the ANE. On the M4, a Metal-only path ran mobile encoders at 1.1–2.6× Core ML's time: 34.5 against 30.3 ms for EdgeSAM, and 53.2 against 25.5 ms for EfficientViT-L0 ([onnxsim PR #1904](https://github.com/onnxsim/onnxsim/pull/1904)). Both are well inside an activation budget. The same source measured eager ONNX-on-Metal at 327 ms for EdgeSAM's encoder, so the quality of the implementation dominates. That is exactly why tract's new Metal path has to be measured, not assumed.

Keeping outputs inside Luxforge's wgpu device is blocked for now, because tract-wgpu and burn target wgpu 30 and Luxforge is on 27. A CPU round trip is fine: a 4 MiB mask crosses unified memory in tens of microseconds (arithmetic), so hover latency comes from inference and a synchronous hand-off to the overlay. Record the runtime, execution provider and precision with every mask, because they change results. EdgeSAM at default ANE precision matched its FP32 mask at only 0.86 IoU ([onnxsim PR #1904](https://github.com/onnxsim/onnxsim/pull/1904)).

| Layer | macOS | Windows | Linux | Portable fallback |
|---|---|---|---|---|
| Accelerator | Core ML GPU, and the ANE only for convolutional encoders that pass an FP16 parity check, via the ORT CoreML provider or objc2 | DirectML from the OS copy; Windows ML on 24H2+ for NPU providers ([Windows ML](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/overview)) | User-installed CUDA or ROCm, never bundled ([CUDA EULA](https://docs.nvidia.com/cuda/eula/index.html)) | CPU through tract or ORT |
| Object segmentation | Portable SAM-class model; optional Vision instance map as a hover hint on macOS 14+; the macOS 27 iterative request as a measured challenger | Portable model; `ImageObjectExtractor` deferred (Copilot+ only) | Portable model | Same model everywhere |
| Removal fill | Luxforge's own model (Apple has no removal API) | Own model; `ImageObjectRemover` deferred (Copilot+ only) | Own model | Same model everywhere |

The OS segmentation APIs fit worse than they first appear. **`VNGenerateForegroundInstanceMaskRequest`** is callable from Rust through `objc2-vision` on macOS 14+ ([objc2-vision](https://docs.rs/crate/objc2-vision/latest/source/Cargo.toml.orig)), but it returns only "noticeable" foreground objects, class-agnostic as it is ([Apple docs](https://developer.apple.com/documentation/vision/vngenerateforegroundinstancemaskrequest), [WWDC23](https://developer.apple.com/videos/play/wwdc2023/10176/)). **`GenerateIterativeSegmentationRequest`** is an exact match for the brush UX: it takes point, box or scribble seeds with up to 13 include and exclude points ([Apple docs](https://developer.apple.com/documentation/vision/generateiterativesegmentationrequest)). It needs macOS 27, released on 14 September 2026 ([MacRumors](https://www.macrumors.com/2026/09/10/macos-27-golden-gate-release-date/)), and is Swift-only with an asset download. Using it therefore means a Swift shim with a C ABI, which is a second toolchain. **Apple offers no removal API**; Photos Clean Up is not exposed, as OpenStill's author also concluded ([OpenStill README](https://github.com/haon-v2/OpenStill/blob/99f96974912fd0700f2fa957023ff4636301f7c8/README.md#L459)). Windows' **`ImageObjectExtractor` and `ImageObjectRemover`** run only on Copilot+ NPUs, in MSIX-packaged apps with the `systemAIModels` capability ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/ai/apis/imaging), [Object Erase](https://learn.microsoft.com/en-us/windows/ai/apis/image-object-erase)). **Linux has nothing native.**

The usual objection to Vision, that its model changes with OS updates, carries little weight in Luxforge. Rendering uses frozen artifacts, so drift affects only recomputation, never an accepted edit. The objections that stand are foreground-only coverage, availability tied to Swift or the macOS version, and parity across platforms.

## One analysis cache serves removal and every AI mask

Luxforge has already designed a model-selection mask kind: a pinned resource, a `task.select-<class>` job on the module lane, and an 8-bit alpha artifact capped at 4096 px. Each selection records its source fingerprint and model version, and offers Recompute or Keep when either changes ([masking workspace](../../design/masking-workspace.md)). Object removal should be that design's first consumer, not a parallel system.

Four pieces are shared. The first is **an inference port with model resources**, installed under the `download-artifact` grant with SHA-256, licence and provenance. The second is **a bounded per-image analysis cache**, keyed by source fingerprint, content-stage fingerprint and model ID and version. It holds derived, recomputable data: the SAM embedding (about 16 MiB in FP32 or 8 MiB in FP16 for SAM 2.1, estimated from darktable's tensor shapes), proposals, semantic probabilities and depth. It is kept apart from the immutable artifacts that recipes reference. The third is **one picker**: hover, click to add, Alt-click to subtract, box and brush all emit the same prompt data for "New mask › Object" and "Remove object". The fourth is **one guided upsampler**, written in pure Rust, deterministic and exact-testable, that serves every model mask. The removal selection, the object plus its accepted effect region, is published as the same kind of alpha artifact. The corrections repair-layer operation references it beside the frozen patch ([corrections design](../../design/corrections.md)).

One piece must not be shared: **hover cannot go through the job table.** The module lane runs one job with at most four queued, and the desktop reads a tracked job every 100 ms ([module capabilities](../../design/module-capabilities.md)). That suits encoders and fills, not 60 Hz hover. Hover needs a dedicated worker that keeps only the latest request and holds the loaded decoder and the cached embedding. Its output is view state and never an edit. Its programmatic equivalent, a point or box query that returns candidate masks, keeps UI and API parity; that query is a proposal, not an existing command.

SAM 2.1 and EfficientViT-SAM have no semantic head, so they serve Objects only. Each other mask class needs its own specialist:

The payoffs run both ways (inference). The person detector feeds both a People mask and a "remove people" pin list. A semantic region seeds SAM prompts, for example to pick one tree out of Vegetation. A Subject mask keeps the main subject out of removal proposals, and depth restricts fill context to surfaces at the same distance. Because removal and Objects masks rest on the same SAM foundation, building it first serves both features. That reverses the masking proposal's Subject-and-Sky-first order, so the order is the owner's call.

## Conclusion

The research inverts the expected difficulty. Finding the object is solved under Apache terms, within the M4's latency budget. Replacing it convincingly, shadow and reflection included, is limited by licences rather than engineering: every model that does it well today carries non-commercial or use-restricted terms. Two assets therefore matter more than any model choice. The first is the effect region as a user-editable part of the selection. It lets even a LaMa baseline remove shadows, and later it is where a learned model's predicted effect mask is shown and accepted. The second is the owner's own tripod-shot RAW pairs. They are the evaluation set now, and later the only rights-cleared seed for a licence-clean removal fine-tune.

Two common assumptions also weaken under the evidence. The Neural Engine matters less than it seems. The fill cannot run in FP16, SAM 2.1's encoder does not compile for the ANE, and a GPU path kept mobile encoders within 1.1–2.6× of Core ML's time, all under 150 ms. That makes a pure-Rust runtime a more serious contender than its reputation suggests, and measurement, not ANE access, should decide. Drift in OS models matters less than it seems too, because Luxforge renders from frozen artifacts. Native segmenters are held back by foreground-only coverage, by availability that depends on Swift, OS version or NPU, and by parity across platforms, not by reproducibility.

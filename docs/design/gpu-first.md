This is separate from hosted CI and native Windows/Linux GPU acceptance, which remain open.

## Why

Two renderers with an equivalence contract, a CPU renderer of record and a GPU approximation qualified per program with a fallback whenever it cannot promise its limit, need machinery around the CPU path to make it fast enough to interact with: proxies, prefix caches, windowed and region renders, settle phases and timers, estimate and grid stores, spatial budgets and point-tile caches. Each has a key, an invalidation rule, a fallback and a test family, and the contracts between them are proofs over the workarounds. The cost of an ordinary edit is then almost entirely that CPU path and the machinery around it, not the problem itself. Every module has a GPU program, every spatial unit included, so the GPU renders everything, and of that machinery only the Fit proxy, which a session without a GPU drags on, and the spatial budget, which paces the reference renderer's tiles, remain.

## Decision

- The GPU is the renderer of record for display at every zoom, for the histogram and clipping counts, for `render.sample` and the other pixel reads, and for export.
- Image correctness is a **declared tolerance against the CPU reference render**, measured on the qualification corpus, for every output kind. Bit identity is not required of the GPU. On one machine with one driver the GPU is deterministic; across machines an export or a histogram may differ in the last digit, and that is accepted.
- The CPU kernels stay as the **reference renderer**: whole frames, no proxies, windows, point tiles or caches. It is the oracle every tolerance is measured against and the renderer a machine without a usable GPU falls back to, with a notice.
- The convergence is staged; no stage lands without the previous stage's tolerance evidence.

## The contract

**Renderer of record.** One GPU path renders the full stack at the size the view needs: the displayed size at Fit and at percentages below 100%, the visible window plus halos at 100% and above, and full-resolution tiles with halos for the histogram, samples and export. The RAW development stays a CPU step done once per source and white balance; its planes are uploaded as the GPU's source, with the mip chain the Fit view samples.

**Reference.** `luxforge_core::render` is a whole-frame renderer: compile, one pass per segment, spatial operations over the whole stage in tiles for memory alone, no proxies, no windows, no point tiles, no caches beyond the prepared source. It renders slowly and plainly, and every test compares the GPU to it.

**Tolerance by output kind.** The picture is measured on the corpus by `cargo xtask gpu-qualification`, at rest and in motion, on the M4 Pro's Metal adapter ([performance](../specs/performance.md#gpu-qualification-against-the-reference)); the histogram limit is decided, and samples and export are measured within their recorded defaults below. **Where the numbers come from.** Each limit is measured against the reference on the corpus, per module and per stage, by `cargo xtask gpu-qualification` ([development](../engineering/development.md#image-correctness-exact-and-reference-buffers)), which `verify --tier rendered` runs after its scenarios as the release gate: a native run, not a preview qualification. It strictly gates the picture at rest against the reference and reports the picture in motion below 100% against the picture at rest and against the reference; `--gate-motion against-rest` or `--gate-motion against-reference` gates the picture in motion by either reading. A kind the GPU does not render yet is reported as such, neither a pass nor a failure; a cell that could not run, or a host without an adapter, makes the gate incomplete. A limit that cannot be met by a program is a defect of the program, never a reason to widen the limit without the owner.

**Headless and portability.** Native tolerance evidence comes from the M4 and, when available, Windows and Linux machines with a GPU. CI and VMs run the reference renderer's own tests and, on Linux, the functional journeys through a software Vulkan adapter; macOS has no software Metal, so a macOS VM proves the reference and the owner thread, not the GPU. The pillars' distinction between VM functional checks and native GPU evidence stands. Every client's `session.state` names the renderer that draws the desktop's picture, `renderer` `{record: "gpu" | "reference", reason}`, with the photo surface's own reason for the reference: `surface-pending` before it has checked its GPU stage, `no-adapter` for a device that cannot run it or a launch that refused it, `device-lost`; an owner that draws nothing, `luxforge-json`'s, reports the reference with no reason. The desktop reports it through a desktop-internal path and no method sets it. `--no-gpu-render` refuses the GPU stage for a launch, as on a machine whose adapter cannot run it, and every rendered run records the adapter that drew it ([CI](../engineering/development.md#ci)). A host whose only adapter is a software one (lavapipe on Linux, WARP on Windows) draws through the GPU stage on it only once the software adapter is adopted or with `--software-adapter`, the session's GPU record then saying `software: true`; until then its launch refuses the stage as `--no-gpu-render` does, naming `no-adapter` ([GPU previews](gpu-preview.md#fallback-and-portability)). Measured in a container on the M4, lavapipe misses the drag thresholds, a pointwise drag by 2.7 to 7.3 times, so it is not adopted ([performance](../specs/performance.md#software-adapters)).

**Outside the renderer.** The catalog owner thread, recipes, history, masks, the command registry and UI/API parity do not depend on it. Nor do the gesture's synchronous `draft.set`, which never waits on a pixel read, and the owner tasks on the blocking pool ([rule 12](../engineering/performance-rules.md#rules)), or RAW development. The 2 GiB GPU preview budget and the photo-texture ceiling stand, and the rendering plan completes their accounting.

## Constraints

- **Texture limits.** iced's wgpu limits cap a texture at 8192 px, and 60 MP of f32 RGBA is nearly a gigabyte per plane set. Full-resolution work uses anchored windows with halos: the visible window at 100% and above, and full-resolution tiles for the picture at rest, counts, samples, export and catalog tiers. Spatial stacks use staged sweeps where their stage textures fit and light sweeps where they do not.
- **Memory.** The GPU-preview budget is 2 GiB, the tile worker's separate budget 2 GiB, and the full-photo slots share a 1 GiB ceiling; the rendering plan's accounting of the resources outside them is a prerequisite of a total-memory claim, not of this plan.
- **Cold shader caches.** After an update a Presence drag's sequences can take seconds to compile, and the first picture would wait on them, so the program set is warmed in the background at launch and open, the picture on screen's programs first, then the open stack's drags, then the first drag of every module the stack does not hold, and until the picture's own are compiled the photograph is the reference renderer's frame, the status bar saying "Preparing GPU render"; each warm-up's duration is recorded in the Performance section and the events ([GPU previews](gpu-preview.md#warming-at-launch-and-open)).
- **Determinism.** Same machine, same driver: identical bytes frame to frame, which the rendered scenarios check. Across machines: last-digit differences accepted.
- **Iced's one hop per frame** stands; the surface primitive that writes its own texture is how the GPU frame reaches the screen.

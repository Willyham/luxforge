# Module manager

Status: **in progress.** The owner decided the scope on 2026-10-25 ([decisions](../decisions.md#module-manager)) and authorized the [task plan](../../tasks/programmability/modules.json). Phase 1 is delivered: the core layout (the descriptor's `toolset` and `locked`, placements derived in the core, `module_layout` in `preferences.json`, the layout methods and the `module.layout` event), the desktop's panel, strip, palette and keymap following it, and Settings › Modules. Its evidence is core and desktop tests and the background `module-layout` scenario, run on Linux under Xvfb with llvmpipe; it has not been run on the M4. Phase 2's external module contract is implemented in the core: the package reader and validator, the manifest and its field table, and the WIT world ([package and manifest](#package-and-manifest)). The engine, `luxforge-wasm`, is implemented and passes its tests on Linux: it loads a package's component, runs its units under the bounds below and hands the registry assembly its module ([engine](#engine)). The install store and the lifecycle API are implemented and pass their core and `luxforge-json` tests on Linux: packages are inspected, installed and uninstalled, folders loaded in developer mode, and the desktop and `luxforge-json` register the installed modules at launch ([lifecycle](#lifecycle)). The desktop's interface for them is implemented and passes its desktop tests and an ad hoc rendered run on Linux under Xvfb: Install module… with its review sheet, the external rows of Settings › Modules with Uninstall… and Relaunch, and the Community, Not installed and Didn't load bands ([external modules on the desktop](#external-modules-on-the-desktop)); its `external-module` journey has not been run. External GPU programs are implemented and pass their tests on Linux: an installed package's program is registered at the desktop's launch, probed at its first use, the window's view included, on the desktop's GPU tile worker, cached per package hash and adapter, and reported in each module's status ([GPU programs](#gpu-programs)). Authoring is implemented and passes its tests on Linux: the SDK with its identity harness, `module-package`, `module-check` and the Split toning example ([authoring](#authoring)). None of phase 2 has been run on the M4. The rest of phase 2 is in progress.

The module manager lets a person decide which modules their workspace offers and where, and later install modules that other people wrote. Phase 1 works on the built-in modules: turn one off or on, and reorder the tools panel's sections and the mode strip's tools. Phase 2 loads separately authored **adjustment** modules, each a sandboxed WebAssembly component with its own WGSL program, installed from a package file. A community library to browse and publish modules is the stated direction but is not planned: there is no index yet.

Boards: [module-manager/board.html](module-manager/board.html), with notes per board in [module-manager/screens.md](module-manager/screens.md). Where the boards and this page differ, this page is the contract.

## Decided

| Question | Decision |
| --- | --- |
| What phase 1 arranges | Any built-in module can be turned off or on unless it is locked. The tools panel's sections and the mode strip's module tools can be reordered. Corrections and mask-kind contributions follow their module's switch and keep their fixed order |
| How external modules run | A WebAssembly sandbox for the module's logic and its CPU reference, plus a WGSL program that the host validates and qualifies at first use |
| The first external kind | An adjustment section: a processing module with its own controls in the tools panel. Canvas tools, mask kinds and correction kinds come later and are not planned |
| How modules are published | No index yet. A module is installed from a package file the person chooses. In developer mode a module author can also load an unpacked folder |
| Price | Free. There are no paid modules, accounts or ratings |
| The SDK's licence | `luxforge-module-sdk` and the example module are MIT OR Apache-2.0, so a module built on the SDK chooses its own licence. The host crates stay GPL-3.0-or-later (decided 2026-10-28) |

## Terms

- **Toolset**: where a module's interface lives. `adjustments` is the tools panel's sections. `corrections` is the Corrections band's kinds. `masking` is the New mask and Add component kinds. `tools` is the mode strip's canvas takeovers. `processing` is a module with no interface of its own, such as the RAW development.
- **Placement**: one module's entry in one toolset. The core derives placements from what the descriptor already declares: a drawn section is an `adjustments` placement, a `crop-frame` or `brush-mask` takeover canvas is a `tools` placement, a `fill-` task or object pick is a `corrections` placement, and object selection is a `masking` placement. Crop has two placements: its section and the strip's R.
- **Home**: the toolset a module declares in its new `toolset` descriptor field. Settings › Modules lists the module and its switch there.
- **Off**: the person's choice, stored outside every catalog. An off module offers no section, strip entry, kind, palette entry, letter or chord in the workspace. It stays registered, so every photo that uses it renders, samples and exports exactly as before, and its API methods stay callable. Off is not **unavailable**: unavailable means the provider is missing, and rendering refuses ([missing effects](modules-and-api.md#missing-effects)).
- **Locked**: always on. A locked module can still be moved. Locked modules are Crop, transform, straighten (every photo's geometry), Basic (it carries the RAW development's white balance and exposure), the RAW development (processing only) and the host's Mask entry and mask kinds. A descriptor declares `locked` with its reason; the host owns Mask's lock.
- **Origin**: `built-in`, `community` (installed from a package file) or `folder` (loaded from a folder in developer mode).

## Phase 1: arranging the built-in modules

### Rules

- **Presentation only.** The layout changes what a client draws and offers, never what the host accepts or how anything renders. Processing order stays each effect's declared stage and order, and the registry keeps its order. That order also decides the Original's layers, first-open actions, the GPU warm list and which provider serves Corrections, so reordering the registry itself is not allowed ([registry](modules-and-api.md#registry)).
- **One layout per person.** It is stored in `preferences.json` as `module_layout`, outside every catalog, with no history entries. Only explicit choices are stored: a module never turned off has no entry, and a toolset never reordered follows registry order. An automated launch keeps it inside its evidence directory.
- **Nothing is discarded.** An id the layout names that this run does not register stays stored and is listed as unrecognized: an uninstalled module, a module this build no longer has, or a developer module outside developer mode. A newly registered module appears at its default place, after the registry neighbour that precedes it in the stored order, until the person moves it.
- **Edits are never hidden.** A photo with a non-neutral layer from an off module draws that module's band at its place, marked **Off · edit kept**. Expanded, the band lists the values read-only and offers **Enable *Title***. The band is in the neutral grey, not the unavailable red, because the picture is whole. A neutral layer brings no band back.
- **Everything else is unchanged.** Presets, copy and paste settings, Auto tone, first-open actions and agents act on an off module exactly as before. The status bar names what changed (`Turned off Vignette · rendering unchanged`).

### Descriptor and API

- `ModuleDescriptor` gains `toolset` (required: the module's home) and `locked` (optional: `{reason}`). Every built-in declares its toolset. Homes: Crop, transform, straighten, Presets, Look, Basic, Presence, Tone curve, Detail, Colour mixer, Lens correction, Perspective and Vignette are `adjustments`. Corrections is `tools`, with the Heal and Clone kinds following it. AI editing is `corrections`, with Masks › Object following it. The RAW development is `processing`. Developer modules keep their Developer group.
- `module.list` adds, for each module, `toolset`, `locked`, `origin`, `placements: [{toolset}]` and the person's `enabled`. The desktop reads placements from the core instead of deciding them itself, so Settings, the panel and agents agree. The rule moves from the desktop into the core unchanged.
- `module.layout.read` answers `{toolsets: [{toolset, order, default}], disabled, unrecognized}` for the orderable toolsets, `adjustments` and `tools`. The strip's pointer and Mask are host entries at its start and are not part of the order. A toolset's default is registry order, except that the strip's brush workspaces come before its crop frames, as the strip has always drawn them (Corrections, then Crop).
- `module.enable {module}` and `module.disable {module}`. A locked module refuses with `validation`, the API's code for a refused parameter, and its reason, and an unregistered id refuses by name. Enabling a module that is on by default removes its stored entry. At most 64 modules are stored off.
- `module.order.set {toolset, order}` takes the complete order, a permutation of that toolset's registered placements, and refuses anything else by name. A move up, down, to the top or to the bottom is computed by the client and sent as the whole order. Unrecognized ids stored in that toolset keep their stored positions. The default order stores no order.
- `module.layout.reset {toolset?}` restores one toolset's order. Without `toolset` it restores every order and turns every module on. Unrecognized ids are kept either way. It is an ordinary write, which the desktop can undo by writing back what it read.
- Every change answers the new layout, as `module.layout.read` does, and announces one `module.layout` event under its request; a no-op or a refusal announces none. The desktop's event sync, an open Settings sheet and agents follow it. A change counts as the `preferences-change` usage interaction, which names no module. `schema.list` is unchanged by the layout. `luxforge-json`, `luxforge-ctl` and `luxforge-mcp` reach the same methods.

### Desktop

- **Tools panel.** Sections draw in the person's `adjustments` order. A secondary click on a band opens Move up (⌥↑), Move down (⌥↓), Move to top, Move to bottom, Turn off *Title* (absent when locked), Customize panel… and Copy as JSON request. The panel takes no drags: a band press still expands or collapses it. A footer after the last section names the modules that are off (`2 modules off: Perspective, Vignette · Customize…`), and is absent when every module is on.
- **Mode strip.** The pointer and Mask first, then the module tools in the person's `tools` order. A **⋯** at the strip's end, also opened by a secondary click on the strip, lists every strip tool with its check and lock or letter, then Customize tools…. Off tools stay listed there, unchecked.
- **Letters.** A letter belongs to the first module in registry order that declares it, and host letters (V, M) come first. A later module gets no letter rather than a substitute: its tooltip says whose the letter is, and the palette still enters it. Today's built-ins do not collide, and registration already refuses duplicates between modules.
- **Palette.** *Customize panel…*, *Settings · Modules*, and *Turn off Title* or *Enable Title* for every module that is not locked. An off module's own actions, resets and mode are not listed.
- **Settings › Modules.** A tab after Appearance, in every build. Modules are grouped by home (Adjustments, Corrections, Tools, Masking, Processing only), each group in the person's order, and each row has a grip, its title, an optional qualifier (`RAW photos only`), its letter, and a switch or a lock. The detail pane shows the hint, the placements, where it renders among the stages with "Panel order doesn't change this", and the API methods it adds. A row moves by dragging its grip within its group, or with ⌥↑ and ⌥↓, and Space toggles it. Each change is written at once. An **Undo** toast reverts the last change, and ⌘Z does the same while the toast shows. **Reset order** works per group and **Reset all** restores everything. Neither needs confirming, since no photo changes. Another client's change reaches an open sheet through the event sync. The Corrections group lists only AI editing: the core declares no `corrections` placement for Heal and Clone, which are kinds of the Corrections module and follow its switch in the Tools group.
- **One layout on screen.** The workspace and an open Settings › Modules draw by the same layout. The event sync skips this desktop's own `module.layout` events, so whichever surface wrote adopts the write's answer for both: a change in the sheet moves the panel and the strip at once, and a band menu, strip or palette change moves an open sheet. Another client's change, or a gap in the events, reads the layout again for the workspace and for an open sheet. Customize panel… opens the sheet with its module selected, the footer's Customize… at the Adjustments group and Customize tools… at the Tools group.
- **Where it lives in code.** The layout is derived in `state/` from `module.list` and `module.layout.read`, beside `tools::derive` and the strip's derivation in `state/canvas.rs`, with no layout logic in widgets. The keymap and palette take the effective layout from the same derivation.

### Evidence

The rendered smoke scenario `module-layout` runs in the background with an isolated evidence directory, through the desktop's own gestures ([commands](../engineering/development.md#commands)): a band's menu moves Vignette to the top of the panel and turns it off, the photo with a Vignette layer is reopened and draws its Off · edit kept band, Customize panel… opens Settings › Modules at Vignette, the Tools group moves Crop ahead of Corrections, the strip's ⋯ menu lists them, and Reset all restores everything. Each gesture's frame records the owner's `module.layout.read` and `module.list`, which the layout the desktop draws must equal, and each photo's on-screen pixels hash the same in every frame that shows it with no sheet or menu over it. It passes on Linux under Xvfb with llvmpipe; it has not been run on the M4. Core tests cover storage, merge with unregistered ids, refusals, events and the unchanged `schema.list`. Desktop state tests cover the derived panel, strip, palette and keymap, and the Off · edit kept band.

## Phase 2: external adjustment modules

### Contract

An external module is a **field-patch module** whose field table comes from its manifest and whose colour unit runs in WebAssembly. The host already does everything a field-patch module needs from a field table: the descriptor, `edit.set-<name>` and `edit.reset-<name>`, parsing, planning, no-op detection, canonical payloads, history labels, the recipe row, neutrality, presets and copy groups ([field patches](modules-and-api.md#field-patches)). So the sandbox supplies only what is genuinely the module's: its compiled coefficients and its pixel arithmetic. This keeps the trust boundary small and gives community modules the same history, preset, copy-settings, API, MCP and generated-panel behaviour as built-ins with no desktop changes.

- **Package.** A `.lfmodule` file is a zip of `luxforge-module.toml`, `module.wasm` and an optional `program.wgsl`. Size and entry limits are checked, with no paths outside the package root. The manifest declares:
  - `id`: reverse-DNS, never `luxforge.*`, and valid as an identity.
  - `title`, `hint`, `version` (semver), `authors`, `license` (SPDX), `repository` URL and the `api` version it targets.
  - `toolset = "adjustments"`, the only value in phase 2.
  - One effect: `stage` is `color` or `finish`, with `order` and `format`. It is not maskable and exists on every source kind.
  - The fields, ranges, defaults, steps, units, hints and groups, in the existing parameter and control vocabulary ([UI components](ui-components.md)). The host refuses a table it could not draw, as `Spec::new` does for built-ins.
- **Component interface.** The WIT world `luxforge:module/adjustment@0.1.0`, in [`wit/adjustment.wit`](../../wit/adjustment.wit), exports one interface, `adjust`, with three functions:
  - `coefficients(values) -> result<list<u32>, string>`: the unit's words from the canonical field values.
  - `apply-row(words, y, x0, rgb: list<f32>) -> list<f32>`: the CPU reference, under the [`PointwiseColor`](../../crates/luxforge-core/src/modules/processing.rs) contract.
  - `label(values) -> option<string>`: an optional history summary.
  It has **no imports**: no WASI, clock, randomness, files or network. A module that imports anything does not load. The words are the unit's identity, so equal values give equal operations. The value types live in `adjust` rather than in the world, because a type declared in a world is encoded as a type import of the component.
- **Determinism and bounds.** The engine is Wasmtime 49.0.4, with relaxed SIMD and threads off and NaN canonicalization on, so the reference is reproducible across machines. Each instance has a fixed memory limit and each call an epoch deadline. A call that traps, overruns or returns the wrong length fails that render explicitly, naming the module, and never yields a partial frame. Instances are created lazily per worker on first use, so an installed module that no photo uses costs no instance. Compiled code is cached under the data root, keyed by the package hash and the engine's compatibility ([engine](#engine)).
- **GPU program.** `program.wgsl` declares one `Colour` entry, `fn lf_module(rgb, pos, words, block) -> vec3<f32>`, and only functions and constants whose names start with `lf_module`, under the surface's prelude ([GPU programs](../../crates/luxforge-core/src/render/gpu/program.rs)). The loader validates it with naga and gives its names a unique prefix. A program starts disabled. At first use, a bounded probe on a worker renders a fixed set of probe patches and field values through the reference and the GPU, and enables the program only within the colour class's tolerance. The result is cached per package hash and adapter. A module without a program, or whose program fails the probe, renders through the reference fallback with the program named ([GPU-first](gpu-first.md)). That is correct, but slower.
- **Where it lives.** `luxforge-wasm` owns Wasmtime and the component bindings, and hands the registry assembly a module per installed package ([engine](#engine)). The core names neither Wasmtime nor a GPU crate *(enforced for Wasmtime)*. Program text and words cross into the core as data, as built-in programs do.

### Package and manifest

The core reads and validates a package without any WebAssembly engine, in `crates/luxforge-core/src/modules/module_package/`, and publishes it as `luxforge_core::module_package`. `ModulePackage::read` takes the package's bytes and `ModulePackage::read_file` its path. Either answers the manifest, the component's bytes, the program's text when there is one and the package hash (`sha256:` and the hex SHA-256 of the file), or refuses. Reading writes nothing.

- **Archive.** The end of central directory record is read before the zip reader parses anything. A package is one archive starting at its first byte, not split or zip64, of at most 24 MiB, with at most three entries and a directory of at most 16 KiB. An entry must be one of the three files at the root: a regular file, unencrypted, stored or Deflate, named once. The manifest may hold 64 KiB, the component 16 MiB and the program 256 KiB, uncompressed. Each limit is checked against the declared size before an entry is decompressed, and again while it is read. `module.wasm` must begin with a component's preamble, and `program.wgsl` must be UTF-8. The engine and the GPU loader check the rest.
- **Refusals.** Each refusal is a `validation` error whose detail names the reason and whose `data.refusal` holds a stable code (`PackageRefusal`): `archive`, `too-large`, `entries`, `outside-root`, `unexpected-entry`, `missing-file`, `content`, `manifest`, `api`, `identity`, `reserved-identity`, `toolset`, `stage`, `maskable`, `sources`, `table` or `component`, the last when the engine would not load the component, which the store checks before it installs ([lifecycle](#lifecycle)).
- **Folders.** `ModulePackage::read_folder` reads an unpacked module, the same three files at a folder's root, each a regular file within its limit, for developer mode. Anything else in the folder is not read. Its hash is the SHA-256 of each file present in the package's order, as its name, a NUL, its length as eight little-endian bytes and its bytes, so a rebuilt component compiles again.
- **Manifest.** TOML, with unknown keys refused at every level and `api` read first, so a manifest for another interface version is refused as that. The top level holds:
  - `api = "0.1"`.
  - `id`: at least three identity segments, outside `luxforge.*` and `app.luxforge.*`.
  - `name` (optional): the actions' noun, `set-<name>` and `reset-<name>`. It is hyphenated lowercase words (`split-toning`), and defaults to the id's last segment.
  - `title`, `hint`, `version` (SemVer), `authors` (1 to 16), `license` (an SPDX expression's shape; the licence list is not checked) and `repository` (an `https` URL without credentials).
  - `toolset = "adjustments"`.
  - `[effect]`: `stage` (`color` or `finish`), `order` (default 0) and `format` (from 1). Its identity is `<id>.adjust`, it is `single`, and a `maskable = true` or any `sources` is refused.
  - `[[fields]]`, at most 64, the most a settings set captures: `name`, `kind` (`number`, `integer`, `boolean`, `enum` or `color`) and `label`. Each field may add `history`, `notes` and `default`, and the hints of its kind: `min` and `max` (required for a number or integer), `unit`, `step`, `precision`, `soft_min`, `soft_max`, `fine_step` and `zero` for a number or integer, and `options` for an enum. A field may also choose its control's `style`: `slider`, `field` or `stepper` for a number, `automatic`, `segmented`, `chips` or `menu` for a choice, and `fields` or `picker` for a colour. A number may carry a `rail`, as the descriptor spells one.
  - `[[groups]]`, 1 to 16: a `label`, its `fields` by name and up to four `[[groups.wheels]]` (`label`, `hue`, `saturation` and an optional `luminance`).
- **The table.** The manifest's table is built into a field-patch `Spec` (`Spec::named`) and checked as a built-in's is, then validated as registration validates a descriptor. So a module of a table is the module a hand-written field patch of the same table would be. Curves, subgroups, views, tabs, extra controls, variants, queries and canvas tools are not part of a manifest in `0.1`.
- **The seam.** `ModuleManifest::module(units)` makes the module, a `ToolModule` whose descriptor is the manifest's. `units` is an `AdjustmentUnits`, whose `compile` takes every field's canonical value in the manifest's order (`FieldEntry`, the WIT `field` record) and answers the layer's `ColorOperation`. The engine crate provides it. A neutral layer never reaches it.

### Engine

`crates/luxforge-wasm` runs a package's component; the core sees only the `AdjustmentUnits` it supplies and the units they compile.

- **Loading.** `WasmHost::external(package)` answers the registry's `ExternalModule` (`luxforge_core::module_package`): the manifest's module with the engine's units, or the same module **unavailable** with the loader's reason. A load compiles the component, or reads its compiled code from the cache, refuses a component that imports anything (`its component imports log, and an adjustment module imports nothing`), and checks that it exports `adjust` with the three functions' types. It creates no instance. `WasmHost::load(package)` answers the loaded module itself, or a `validation` error naming the module, for a harness that calls its functions directly.
- **Assembly.** `RegistryOptions::external` holds a launch's external modules, and `ModuleRegistry::assemble` registers them after every linked module, so the linked modules' order and everything it decides (the Original's layers, first-open actions, letters, which provider serves Corrections) is unchanged. `--disable-module` reaches an external as it does a linked module. One whose registration is refused, because its identity, an action, its effect or a letter is already provided by a linked module or an earlier external, is left out, the assembly continues, and `ModuleRegistry::refused_externals` lists it with the refusal. Its photos' layers then name an unknown effect and are kept. The desktop and `luxforge-json` read the store and load its modules through `luxforge_cli::installed_modules` ([lifecycle](#lifecycle)). `module.list` reports an external module's `origin` as `community` or `folder` (`ModuleRegistry::external_origin`).
- **Engine and bounds.** One engine serves the process. Each instance has its own store with one linear memory of at most 32 MiB, and every call, instantiation included, an epoch deadline of one second. The epoch advances every 10 ms on one ticker thread, started at the first call into any module, which waits without ticking while no call runs. Instances are created on first use, one per worker calling at once, and at most 64 are kept for reuse; an instance a call failed in is dropped.
- **Units.** A layer compiles to one unit holding the words `coefficients` answers for its values, at most 4096. Its identity is the package hash and the words. Its rows call `apply-row` with at most 16,384 pixels a call. Its GPU description is the package's registered program with the unit's words ([GPU programs](#gpu-programs)). A unit with no registered program has none, and a stack holding it renders through the reference renderer, the unit named (`no-program`; `ID (N words; its program.wgsl was refused at load)` when it was refused).
- **Failures.** A failure is an error naming the module and what failed, whose `data` holds `{"module", "failure"}`. `failure` is `trap` (`module ID trapped in apply-row: …`; growing past the memory limit fails the growth, and a guest that cannot continue traps), `deadline` (`overran its 1000 ms deadline in apply-row`), `length` (`answered N values for a row of M`, or too many words or too long a label), `invalid` (an answer that breaks the canonical ABI) or, for `coefficients`' own `err`, `refused`, a `validation` error with the component's text. Every other failure is a `render` error. The render, sample or export that meets one produces no frame. `apply_row` itself has no error channel, so the host's colour runs call `PointwiseColor::try_apply_row`, which an external unit overrides; its `apply_row` fills the run with non-finite values on a failure, which the host's finite check refuses.
- **Compiled-code cache.** Under `<data>/modules/compiled` (`Paths::module_code_cache`), one file per package hash and engine compatibility hash (`<package sha256>-<engine>.cwasm`): the SHA-256 of the serialized code, then the code. A read checks the digest before Wasmtime loads the code, so a torn or corrupted entry is compiled again, and a write goes to a temporary name and is renamed into place. Without a data root nothing is cached. Entries are not pruned yet.
- **Labels.** `label` is called only through `Adjustment::label`; history entries keep the host's own labels.

### GPU programs

- **Registration.** A load hands `program.wgsl` to the host's `ProgramLoader` (`WasmHost::with_programs`). The desktop's is the GPU backend's own check (`luxforge_gpu::external_program::register`), which `module-check` runs too. naga validates the program under the surface's prelude, called by a harness. It may declare only functions and constants named `lf_module…`, with an `lf_module` entry of the colour signature: no global, override, type, alias or entry point. The check then renames every name naga parsed as declared, by token, to the package's prefix `lf_ext_<first 16 hex digits of the package hash>`, and checks the renamed program again. A refused program leaves the module loaded, and its units have no GPU description. `luxforge-json` cannot link naga (the `headless-cli` rule), so it registers no programs. A desktop launch that refused the GPU stage registers none either.
- **Probe.** A registered program starts **pending**: the plan falls back with `disabled-program`, naming its entry. The desktop's GPU tile worker queues its probe when one of its reads or streams falls back on it: a sample, an export or a catalog preview tier. The probe carries that work's cancellation. The worker runs it on its own thread and device, on the window's adapter, after its calls and its streams' steps, one value set a step. It runs the program alone in a compute harness over the five 64 × 64 probe patches (`luxforge_gpu_types::probe`), for each of the manifest's probe value sets (`ModuleManifest::probe_values`: at most 7 + 2 × 64), and compares the result with the component's `apply-row`. The judgment is CIEDE2000 on 8-bit sRGB, within the colour class's limits (`COLOUR_LIMITS`). Within them, the program is **enabled** on that adapter and the next plan draws it. Outside them, or refused by the device, it is **disabled**, with the value set and patch at fault, and its stacks keep falling back by name. Cancelling the work, losing the device or replacing the worker's runner leaves it pending, to be probed at its next use.
- **The view's first use.** The window's own view asks for the probe too, so a person who installs a module and edits a photograph gets the GPU without sampling or exporting anything. When a committed stack's view plan falls back on a pending program, the message after it queues that program's probe on the tile worker (`GpuTiles::probe_for_view`), with the photograph's cancellation. Another photograph, or none, sets that cancellation, which lets the probe go and leaves the program pending. Before the window's adapter is named the ask waits for a later message. A program is asked for once per photograph, and again only if its probe was let go pending. When a probe of the program ends, the worker answers the view with the program's state as a message. If it is enabled, the stack on screen is planned again, unless a gesture is open, whose commit plans it, and the photo surface then draws it with the program. The ask, the answer and the second plan are each a lock or a message on the interface thread, with no wait and no timer.
- **Cache.** Results are kept under `<data>/modules/probes` (`Paths::module_probe_cache`), one JSON file per package hash and adapter: `{format, package, adapter, enabled, words | reason}`. The adapter is keyed by name, backend and driver. A file is written to a temporary name and renamed into place. A later launch on that adapter takes the result without probing, and a driver update probes again. Without a data root nothing is cached. Entries are not pruned yet.
- **State.** `ExternalModule::program_state()` answers `none`, `unchecked`, `refused {reason}`, `pending`, `probing`, `enabled {adapter}` or `disabled {adapter, reason}` (`ProgramState`, serialized as `{state, adapter?, reason?}`). `module.status` and `module.package.list` report it as each row's `program` ([lifecycle](#lifecycle)).

### Lifecycle

The store and the launch's reading live in `crates/luxforge-core/src/module_store/` (`luxforge_core::module_store`), the methods in `api/owner/module_install.rs`, and the launch's assembly in `luxforge_cli::installed_modules`.

- **Store.** Installed packages live under the data root, in `<data>/modules/packages/<id>/<version>-<first 12 hex digits of the hash>/`: `package.lfmodule`, the exact bytes that were validated, and a copy of its `luxforge-module.toml`, so a package that no longer reads still names its module. `<data>/modules/modules.json` records them: a format-marked document (`format: 1`) of at most 64 KiB outside every catalog, written atomically under its lock through the document store every small host file uses. It lists `packages` (`id`, `version`, `hash`, `format`, `program`, `title`, `installed_ms`) and, for developer mode, `folders` (`id`, `path`, `title`, `loaded_ms`), at most 64 modules together. A file of another format or shape, or one that breaks a rule (a duplicate or unsafe identity, a malformed hash or version, a relative folder path), is refused as `incompatible` by every write and kept byte for byte; a launch then loads no external module and says why. Each write holds a second lock across its document write and its package directories, so two processes never remove each other's files. An evidence run's data root is inside its evidence directory, so it keeps its own store. Without a data root there is no store, and every write is refused `not-ready`.
- **Next launch.** The registry is fixed for a launch, so installing, updating or uninstalling a package, or loading or removing a folder, takes effect on the next launch. A launch reads every installed package, and in developer mode every loaded folder, into memory before its registry is assembled, so a write after it never changes what it runs. Settings shows **Relaunch to apply** with a Relaunch button, as Experiments does for launch flags ([on the desktop](#external-modules-on-the-desktop)). Live loading is later and not required.
- **API.** Reading, hashing, validating, compiling, copying and removing a package all run on the index lane's query thread while the call waits parked, never on the catalog owner. None of the writes takes a mutation envelope, as the module layout's do not: installing the same package again changes nothing, and an uninstall retried after its answer was lost is refused by name.
  - `module.package.inspect {path}` reads and checks a package without installing it, for the review sheet: `{path, bytes, hash, manifest, program, descriptor, placements, methods, access: {network: none, files: none}, reviewed: false, installed, already_installed, format_change, status}`. `installed` is what the store holds for the id now (`{origin, title?, version?, hash?, format?, program?, path?}`) or `null`, and `status` its load state or `null`. A refused package is the reader's `validation` error with its `data.refusal` code. The engine's check refuses a component that would not load (`component`), and a module whose identity, action or effect a built-in module or another stored external provides is refused with `data.refusal: collision`, naming the provider. Nothing is written.
  - `module.install {path}` checks the package as inspect does, then copies the bytes it checked into the store: `{module, origin: community, outcome, installed, previous, format_change, status}`. `outcome` is `installed`, `replaced` (a package with the same id, which the next launch replaces and whose directory is removed, since there is no rollback store) or `unchanged` (exactly this package is installed already). When the new version's payload format differs from the installed one, `format_change` is `{installed, package, notice}`, the notice saying that existing edits will be unavailable until a version that reads them is installed. A module loaded from a folder, or a full store, is refused by name.
  - `module.uninstall {module}` removes the package at the next launch: `{module, removed, status}`. The running launch keeps what it read. An id the store does not hold, or a folder module, is refused by name.
  - `module.folder.load {path}` and `module.folder.remove {module}` are developer mode only: outside it they are absent from `schema.list` and dispatch answers them as unknown methods. The store keeps the folder's canonical path, and every developer launch reads the folder again; the folder is never written. An installed package of the same id is refused, and a package install of a folder module's id too. An ordinary launch neither loads nor lists a stored folder, and keeps it stored.
  - `module.package.list` answers every external module this launch read or the store holds now, `{modules, pending_relaunch, store: {state: ready | unreadable {reason} | unconfigured}, launch_problem}`, folder modules only in developer mode. Each row is `{module, origin, state, reason?, installed, running, program: {state, adapter?, reason?}}`: `installed` is what the next launch loads (`null` once uninstalled), `running` what this launch read (`null` for one stored since). Each side's `program` says whether its package ships a GPU program.
  - `module.status {module_id}` adds that row as `external` for an external module, and answers `{module_id, external}` alone for an id only the store knows, such as a package installed since launch. The load state is `loaded`, `pending-relaunch` (the store names something other than what this launch read, by hash for a package and by path for a folder, or nothing) or `failed` with `reason` (the engine's, the reader's or the registration's refusal).
  - A row's `program` is the GPU program's state ([GPU programs](#gpu-programs)). For a module this launch registered, it is the live state, which a probe changes while the launch runs: `none`, `refused`, `pending`, `probing`, `enabled` or `disabled` in the desktop, and `unchecked` in `luxforge-json`, which checks no program. For a row this launch did not register, such as a package stored since launch or one that failed to load, it is `unchecked` when the package ships a program and `none` when it does not. So `none` always means no program, and every other state means the package ships one. Only `enabled` is drawn on the GPU; every other state renders through the reference renderer.
  - Each write that changes the store announces one `module.installed` event under its request; a write that changes nothing, and a refusal, announce none.
  - Installing is a person's or agent's explicit API call, with no consent grant, because phase-2 modules hold no capabilities. The desktop's review sheet is the human confirmation. `luxforge-ctl` and `luxforge-mcp` reach every method through `schema.list`.
- **Failure is explicit and keeps data.**
  - A package that does not validate, or a component that does not instantiate, is registered **unavailable** with the loader's reason when its manifest is readable. A stored package whose bytes no longer match the hash it was installed with fails the same way. Otherwise its effect id is simply unknown.
  - Either way the photos that use it keep every layer, and rendering, sampling, appending and export refuse with the existing `unavailable effect` error ([missing effects](modules-and-api.md#missing-effects)).
  - Panels show **Didn't load** or **Not installed** in red. Installing a compatible version restores rendering without touching stored data.
  - A layer of a payload format the module does not declare is refused by its format marker, as a built-in's is.
- **Off** means the same as for a built-in: the module stays loaded, so its photos render and export.
- **Usage statistics** report an external module's commits as the `external` tool, without its id. Installing and uninstalling are exempt, since they name a module.

### External modules on the desktop

The desktop draws everything here from `module.package.list`, `module.package.inspect` and the writes' answers ([boards E and F](module-manager/screens.md)); it decides nothing about what installs. Each call runs off the update loop, one lifecycle write at a time, and its answer shows at once and is read back with the tab's next read.

- **Install module…** sits in Settings › Modules' header, and the stale-preview notice of a photo whose module is missing offers it too, opening the tab. It opens the system file picker filtered to `.lfmodule`; an evidence run never opens a picker, and its script hands in the path. It is disabled while a picker, a sheet or a write is open, and while the store takes no writes, which the tab says under its header (an unreadable `modules.json`, or a launch with no store).
- **The review sheet** is the one modal step. It opens on the picked file reading *Reading the package…* while `module.package.inspect` runs, then shows `Install Title Version?`, that the module comes from its author and that Luxforge hasn't reviewed it, and the facts: Adds (a section in Adjustments, last), Renders (stage and order, and that panel order doesn't change this), Program, Network and Files (None), Author, Licence, Source, Version and interface, the API methods it adds, the package hash and the file with its size, then *It is added when Luxforge relaunches.* **Install** sends `module.install {path}`; Return presses it, Escape and Cancel close the sheet. A package the owner refuses reads *This package can't be installed* with the owner's reason word for word and only Close. A package with an installed version reads `Replace Title From with Version?` with **Replace**; when its payload format changes, the owner's notice is shown in red and the button is a red **Replace anyway**, which Return never presses. Exactly this package installed already offers nothing to press, and an identity loaded from a folder says to remove it first. A refused install keeps the sheet open with the reason.
- **Rows.** An external module's row carries its origin badge, *Community* or *From folder* (grey), and its state badge, *Relaunch to apply* (accent) or *Didn't load* (red). A module installed since launch, which the registry does not list yet, joins Adjustments last with no switch or grip. A line under the header counts the pending changes (`1 change applies when Luxforge relaunches.`) beside **Relaunch**. The detail pane says the module is from its author and not reviewed, quotes a Didn't load reason word for word with **Copy error**, says what the next launch does, shows the version (and the one the next launch loads when it differs), the program's state as `module.package.list` reports it (CPU reference only, checked at first use, being checked, drawing on its adapter, or refused or disabled with the reason word for word) and a folder module's path, and offers Install module… for a module that didn't load, **Uninstall…** for an installed package, and in developer mode **Remove** for a folder module.
- **Uninstall…** confirms first: `Uninstall Title?`, saying the photos that use it keep their edits but can't be previewed or exported with them until it is installed again, that other catalogs aren't checked, and that it is removed when Luxforge relaunches. It names no count. Its red **Uninstall** sends `module.uninstall {module}`; Return never presses it.
- **Load from folder…** appears in the header in developer mode only and sends `module.folder.load {path}` for the picked folder with no review sheet, since the developer wrote the module; **Remove** sends `module.folder.remove {module}` without confirming, since the folder is never written.
- **Relaunch** waits until no write is in flight, then quits through the ordinary close path (the window's frame and the last preferences stored, the catalog closed and its thread joined) and starts the same program with the same arguments, less each `--open`, so the remembered catalog opens and Develop lands on the photo it had open. A macOS bundle started with no arguments is started again through `open`. Closing the sheet keeps the changes pending, and a later launch applies them. An evidence run records the command it would start and quits nothing.
- **Bands.** An installed module's section is generated from its descriptor like a built-in's, with no desktop change, and carries the *Community* or *From folder* badge after its title. A photo that keeps a global layer of an effect no registered module provides draws a red band after the registered sections: *Not installed*, titled with the module's identity, or *Didn't load* with the loader's reason under its title when this launch read the module and did not register it. A module registered unavailable draws its own band reading *Didn't load* with the reason. Neither expands. The stale-preview notice says the module is not installed or didn't load and that the photo keeps its edit, and offers Install module…; export refuses with the unavailable effect in the status bar, as for any missing provider.
- **Following other clients.** Another client's `module.installed` event, or a gap, reads the layout and an open Modules tab again, as `module.layout` does. The workspace reads `module.package.list` once with `module.list`, since what is registered is fixed for the launch.
- **Where it lives in code.** `state/external_modules.rs` derives the sheet, the confirmation, the badges and the detail; `app/external_modules.rs` sends the calls and runs Relaunch through `relaunch::after_close`; `view/module_settings.rs` draws them. `settings_summary()["modules"]["external"]` records the store, the pending line, each row's state, the sheet and the confirmation as drawn, the write in flight, the last answer and what Relaunch did. The `modules` evidence step takes `{"install": PATH}`, `"review_install"`, `{"uninstall": M}`, `"confirm_uninstall"`, `"dismiss"` and `"relaunch"`, and records `module.package.list` beside each frame. `--evidence-data` keeps an earlier evidence run's `host/data`, so the modules one run installed are what the next loads.

### Trust

Community modules are not reviewed by Luxforge, and the review sheet and Settings say so. Their safety rests on the sandbox: no imports, bounded memory and time, a validated WGSL program run under the host's bindings, and output that is only colour values. The review sheet shows the manifest's identity, licence, authors, repository, version, package hash, what it adds and where, and "Network: none · Files: none". Signing, a verified-author mark and reproducible builds wait for a library.

### Authoring

The workflow is in the [authoring guide](../engineering/module-authoring.md).

- **SDK.** `luxforge-module-sdk` is a small guest crate with no dependencies: the `adjust` interface's exports written against the canonical ABI by hand (`export_adjustment!`), typed access to field values (`Values`) and coefficient words (`Words`). A module crate is built for `wasm32-unknown-unknown`, so its component imports nothing. Its `host` feature is the authoring tooling for native builds: the module build with the pinned toolchain, the component step through `wit-component`, a runner on the module engine itself (`luxforge-wasm`'s `WasmHost`, with the host's configuration, memory limit and deadline), and the harness that runs a module's `coefficients`, `label` and `apply-row` natively and on that engine over fixed patches and asserts identical buffers (any two NaNs count as identical, since the engine canonicalizes them).
- **Packaging and checking.** `cargo xtask module-package DIR --output FILE` checks the manifest, builds the crate into `target/modules`, and writes the package with its entries in a fixed order at a fixed time, read back through the core's reader before it replaces `FILE`. `cargo xtask module-check FILE [--json NEW_FILE]` reads the package with the core's reader, loads the component on the module engine as the host does (refusing any import), instantiating it on its first call, runs the reference over the probe's value sets and patches, checks the program as the host registers it, and reports the GPU difference against the colour class's limits on the local adapter, running the program alone in the probe's harness. Each refusal names the step and the value set, patch or declaration at fault. It reports and does not qualify: the GPU result is not gated, and without an adapter it says so.
- **Example.** `examples/modules/split-toning` is a separate Cargo project, outside the workspace, that depends only on the SDK: highlight and shadow hue and saturation and a balance, on the colour stage at order 20, after the colour mixer, with its WGSL program. It is the proof: it is built, packaged and installed with no change to host source, it appears in the tools panel, and it is reachable through `module.list`, `schema.list`, `edit.set-split-toning`, presets, copy settings and MCP. It builds, packages and checks today; installing it waits for the rest of phase 2.

### Evidence and measurement

- **Journey.** A rendered journey, `external-module`, starts from an empty data root:
  - Inspect and install the example, relaunch, and edit through the desktop and the API.
  - Compare the GPU picture with the reference, export, and check the original's bytes are unchanged.
  - Turn the module off and check the export is unchanged.
  - Uninstall and relaunch: the band reads Not installed and export refuses, with the layer kept.
  - Reinstall and relaunch: the export matches the first.
- **Core tests.** These cover the manifest and package refusals, the import refusal, traps and deadlines, determinism, the program's validation and probe, and an unknown format. The package and manifest tests (`cargo test -p luxforge-core module_package`) hold a fixture package's descriptor to a hand-written field-patch module of the same table, and check each refusal by its code and words. The engine tests (`cargo test -p luxforge-wasm`) build their components in the test from WAT with `wit-component`: a valid one held byte for byte to a native Rust twin of its arithmetic, and ones that import, trap, overrun the deadline, answer the wrong length or outgrow their memory; they also hold two runs and cached and freshly compiled code to identical frames. The registry tests (`cargo test -p luxforge-core registry`) hold the linked order, the Original's layers and the first-open actions unchanged with externals registered. The program tests cover four levels. The GPU backend's (`cargo test -p luxforge-gpu external_program`) check the rename and each refusal, and run a program alone within the colour limits and a wrong one outside them. The engine's (`tests/host/program.rs`) cover a correct program probed once per package and adapter and cached, a deliberate error disabled by name, an invalid or misnamed program refused at load, and a stopped probe left pending. The core's (`module_package`) hold the probe's statistics to the reference's preview difference. The desktop's (`cargo test -p luxforge-app gpu_probe`) probe a program on the tile worker's thread at a read's first use, draw it within the pointwise class of the reference afterwards, and leave it pending when the asking work is cancelled. They also show that the view's first use queues one probe however many messages follow, and that once it is enabled the plan handed to the photo surface draws the stack with the program. The lifecycle tests hold a running module's row to its program's live state.
- **Measurement.** Once the feature works, this is measured on the M4: launch and idle RSS with no external module, with one installed and unused, and with five; first use, meaning instantiation, shader compilation and the probe; and the reference's per-frame cost at 24 and 60 MP against the native vignette's. The binary-size and build-time cost of Wasmtime is recorded too. Figures go in the [performance spec](../specs/performance.md).
  - **Workload.** `module-measure` (`xtask/src/module_measure/`) takes every figure in one report, `module-measure.json` with `module-measure.md` beside it, each row with its scope and the load at its step's start and end, and a header naming the machine, the checkout and the editor binary. It builds the example with `module-package` and packages its component and program under four more identities (`org.example.splittoning2` to `5`), leaving the example's source untouched. Every install goes through `module.install` into a data root inside the output, and the next launch's `module.package.list` must answer each module loaded.
  - **Steps.** `size` attributes the release editor's text symbols to the packages only `luxforge-wasm` brings into its dependency graph. `first-use` times, in its own process, the compile with no cache, the cached load, the call that instantiates, the program's registration, the probe harness's pipeline and the probe. `reference` alternates whole-frame reference renders of the 24 MP and 60 MP JPEGs with no layer, a vignette and Split toning. `launch` makes background launches over copies of data roots holding none, one and five modules, opening the 24 MP JPEG, for the time to the first `render_ready`, the RSS to it and a thirty-second idle window. `desktop-first-use` makes a launch over a photograph with a Split toning layer and an unprobed program, timing the view's probe and the GPU's picture after it on the editor's clock. `build` makes a clean, uncached release build of `luxforge-wasm` with Cargo's timings. `--only` takes a list of steps.
  - **On the M4**, on a quiet host on mains power, with a current release editor and the generated JPEGs: `tools/cargo-cached build --release --locked -p luxforge-app`, `tools/cargo-cached xtask generate-fixtures`, then `tools/cargo-cached run --release --locked -p xtask -- module-measure --output artifacts/NEW_DIR`. `--launches` (default 5) sets the launches per workload, and `--samples` (default 30) the rounds per size and the first-use repetitions. The first-use and reference steps need the release xtask, which the command checks.

## Performance rules checklist

- **Phase 1** adds no work to rendering or the owner thread's edit path. The layout is read once per launch and on its event, and the desktop derives it with the panel, bounded by the module count.
- **Phase 2's desktop** adds no work to rendering or the owner thread: every lifecycle call runs off the update loop through the owner's index lane, one at a time; the workspace reads `module.package.list` once per launch and the Modules tab on opening and after each write; the bands and badges are derived with the panel, bounded by the layers and module count.
- **Phase 2** adds one thread, the epoch ticker, started at the first call into an external module and waiting without ticking while no call runs. Calls run on the existing pools with bounded instances, memory and deadlines. Instances and program probes are created lazily, and nothing is loaded for an unused module beyond its compiled code. A probe adds no thread: it runs on the GPU tile worker, one value set a step behind its calls and stream steps, about 25 bytes a patch pixel of buffers, and once per package and adapter. The view's ask costs the interface thread a lock and at most one channel per program and photograph. It may start the tile worker's thread and open its device a little earlier than a read would. Its answer is one message, and the second plan of an enabled program's stack is one preview job. Untrusted input is checked for size and shape before it is parsed. Costs are measured once at the end, as above, and no performance claim is made before then.

## Recorded defaults

These are recorded defaults the owner can revise. The plan runs on them.

- The words Off and Enable; the locked set above; one switch per module at its home; no drag inside the tools panel; Masking shown as one locked summary row.
- An off module's methods stay callable, and `schema.list` ignores the layout.
- The layout is per person, not per catalog or per workspace profile.
- The Off · edit kept band is read-only, with Enable as its only action.
- External effects are restricted to the colour or finish stage, not maskable, on every source kind, with one effect per module.
- Install, update and uninstall take effect on the next launch, with no rollback store.
- Uninstall… names no photo count: no read answers which photos hold a module's layers off the catalog owner, so the consequence is stated for every such photo.
- Load from folder… has no review sheet and Remove no confirmation. The From folder badge is grey like Community, not dashed.
- Relaunch drops `--open` so the remembered catalog and photo open; an evidence run records the relaunch and does not quit.
- A Not installed band is titled with the module's identity, the effect's identity less `.adjust`, and is drawn after the registered sections.
- A failed program probe falls back to the reference rather than refusing the module.
- The names `.lfmodule`, `luxforge-module.toml`, `luxforge-wasm`, `luxforge-module-sdk` and the example's Split toning.
- The example's identity is `org.example.splittoning`, outside Luxforge's reserved namespace, and its numerics are its own: a tonal position from the square root of Rec. 709 luminance, a smooth split around a pivot the balance moves by up to 0.45 each way, and tints that move white halfway toward the hue's pure colour at full saturation, normalized to unit luminance.

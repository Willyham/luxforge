# Tool modules and the shared core

Status: implemented (M3, M4). The **Crop, transform, straighten**, presets, RAW, Basic, Tone curve, Detail, presence, mixer, lens, perspective and vignette tools are the built-in modules; the test modules, the pixel and controls proofs, are registered only in developer mode, and the capabilities proof only in developer mode with a proof endpoint; the host owns everything a module does not declare here. Settings, provider profiles, secrets, consent, resources, worker tasks and derived artifacts are the [module capabilities](module-capabilities.md) contract; this page lists only where they meet the descriptor, the trait and dispatch. The registry, descriptors and built-in modules live in `crates/luxforge-core/src/modules/`; the desktop models them in `crates/luxforge-app/src/state/` and renders them in `crates/luxforge-app/src/view/`, and the crop-frame editor's own draft and canvas live in `crates/luxforge-app/src/crop_draft.rs` and `view/crop_canvas.rs`.

An operation is semantic and programmable: set one pixel, rotate, set crop parameters, restore history, select a preview or change view state. Scripts never simulate pointer movement. Exposure, masks, clone strokes and lifecycle actions inherit this rule when they arrive.

## Ownership

| Owner | Responsibility |
| --- | --- |
| Host (`luxforge-core`) | Asset identity, shared invariants, atomic recipe and history commits, revisions, undo/redo/restore, request deduplication, the decoded-source cache, one-pass rendering of compiled processing, preview jobs, notifications, API discovery and dispatch; module settings, secrets, grants, the capability worker, installed resources and derived artifacts |
| Module (`luxforge-core::modules::*`) | Its descriptor (identity, effects, actions, parameters, controls), input parsing, state validation and no-op detection, payload validation and compilation of its payloads into host processing primitives |
| Desktop (`luxforge-app`) | Layout, styling, focus, text editing, gesture capture; renders controls, including the `crop-frame` canvas editor, from descriptors and calls the declared actions through the same API every client uses; holds no authoritative state |

Module code never writes catalog tables, never keeps an undo stack and never renders. Preview, undo and restore never ask a module to reverse pixels: a snapshot is evaluated from original pixels and its ordered payloads.

## Descriptor

Registered lookups return `Provider`: its public `descriptor()` reports registry availability, including a module disabled for this run. `descriptors()`, `module()`, `action()` and `effect()` agree. `Provider` retains `Deref` for raw implementation hooks; callers check the registered descriptor before using them. Explicitly dereferencing to `ToolModule` accesses the implementation's own descriptor, which does not carry registry overrides.

Every module returns one `ModuleDescriptor` from `descriptor()`. It is plain data, cheap to build and serializable, and it is the single source of API discovery, GUI controls and validation limits. A module builds it in Rust with the typed constructors — `EffectDescriptor::new(id, stage)`, `ActionDescriptor::new(id, title, notes)`, the `ParameterDescriptor` kinds and one struct per control kind (`Control::number(…)` returns a `NumberControl`, `Control::choice(…)` a `ChoiceControl`, and so on, each with only its own kind's setters, so a setter of another kind does not compile) — and registration validates it. There is no reader for descriptors arriving as JSON: `module.list` serializes them, and a client deserializes that listing. The code lives in `modules/descriptor/`: the shapes and the control variants' resolution in `types.rs`, the registration rules in `validate.rs`, the checks a request's values meet (the settings check among them) in `values.rs` and how a label names a value in `labels.rs`.

| Field | Meaning |
| --- | --- |
| `id`, `title` | Stable provider identity, e.g. `luxforge.pixel`; lowercase ASCII words separated by dots |
| `hint`, `collapsed`, `developer`, `layout` | Section hints for clients: the one-line description under the title, whether the section starts collapsed (a person's own expand or collapse still wins), whether the module is a developer tool hidden outside developer mode, and how a client arranges the module's top-level controls — `stacked` (the default) or `tabs`. `tabs` is validated at registration: the module must declare at least two top-level controls and every one of them must be a group. None of them changes the API |
| `effects[]` | `id` (durable effect identity stored in every layer, e.g. `luxforge.pixel.replace`), `format` (internal payload format marker), `stage` (`source`, `pixel`, `restoration`, `color`, `spatial`, `geometry` or `finish`) and `order` (a `u16`, default `0`, always reported), which together decide where the host puts a new layer of that effect; `artifacts` (default `false`): only a layer of an effect that declares it may list derived artifacts, and `single` (default `false`, listed only when true): a stack holds at most one layer of the effect per target. Every delivered photo effect declares no artifacts, and order `0` except the mixer's `10`, Lens's `2`, Perspective's `4` and the crop's `10`; Detail, Basic, Presence, the colour mixer, Lens, Perspective, the vignette, the crop and both proof modules declare `single`; `maskable` (default `false`, listed only when true): the host adds its optional `mask` target field to every action of the module, as [masking](masking.md) describes. Detail, Basic, the colour mixer and Presence declare it; and `sources` (default every kind, listed only when declared): the source kinds a layer of the effect may exist on, named by the `kind` tags `asset.state` reports for a photo's source (`jpeg`, `raw`), each at most once. The RAW development declares `["raw"]`; every other delivered effect exists on every kind. See [source kinds](#source-kinds) |
| `actions[]` | `id` (unique across all modules, e.g. `set-pixel`), `title`, `notes`, `patch`, `parameters[]`, and an optional `shortcut`: the chord a client binds to running the action with no parameters, as its control does, written `Command+U`, `Command+Shift+C` or `Command+Option+V` (the held modifiers in the order Command, Option, Shift, then one uppercase letter, digit or punctuation key; Command is ⌘ on macOS and Control elsewhere). A shortcut must hold Command, the action must require no parameter, and the chord must not be one the host keeps for its own commands (`HOST_CHORDS`: copy and paste settings, undo and redo, open, export and the like), or registration refuses the descriptor. Basic's `auto-tone` declares `Command+U`. The desktop binds it, shows it beside the action's palette entry, and an evidence `key` step presses it as written |
| `queries[]` | Optional read-only questions about a stored stack, declared and validated exactly like an action: `id` (unique across all modules' queries), `title`, `notes`, `parameters[]`. A query mutates nothing, writes no history entry and emits no event. The Basic module declares `neutral-sample {x, y}` |
| `parameters[]` | `name`, `kind`, `required`, `default`, `unit`, `step`, `precision`, `soft_min`, `soft_max`, `fine_step`, `zero`, `notes`. Kinds: `integer {min, max}`, `number {min, max}` (finite f64), `enum {options[]}`, `color` (three 8-bit sRGB channels), `boolean`, `artifact` (one `artifact-…` identity; the commit checks the catalog holds it), `curve {points_min, points_max, monotone, fixed_x?}` (ordered `[x, y]` fractions, at most 32 points), `string {max_length}` (text of at most `max_length` characters, `max_length` at most 256, no control characters; emptiness is the module's to refuse) `settings` (a [settings set](presets.md#settings-sets): 1 to 16 action identities, each with an object of at most 64 validly named fields, empty only for a declared analysis step such as `auto-tone`; the generic check validates only this shape), `settings-origin` (where a settings set came from, read whole by the generic check: `{kind: preset, name, preset_id?}` with a name of 1 to 128 characters, or `{kind: paste, source, source_asset?}` with a source file name of 1 to 255, neither blank nor holding a control character, and typed identities), and two kinds only a [module setting](module-capabilities.md#configuration-contract) declares, which registration refuses on an action, query or task: `endpoint {classes[]}` (a URL of at most 4096 bytes the capability transport accepts as one of `remote` or `loopback`, never with a default) and `secret {max_length}` (a credential of at most 4096 characters held only by the OS secret store; no plain value is valid and it never has a default); and three kinds only the host declares, which registration refuses on a module's action, query or task and on a setting: `identity {of}`, one host object's identity — `asset`, `entry`, `draft`, `job` or `preset` for a host method, `mask`, `component` or `stroke` for a mask command — checked by that identity type's own parser; `text {max_bytes}`, UTF-8 text of at most `max_bytes` bytes that may hold control characters such as line breaks, for a file's contents or a filesystem path; and `json`, any JSON value, for a host method's structured field whose notes give its shape and whose own type checks it. A required identity stays required on a patch, because it says which state the patch merges over, and no control edits one. Enum options are non-empty and distinct. Steps and display precision (at most 6 decimals) are hints for numeric and curve controls. Numeric soft bounds stay inside hard bounds; an omitted bound uses the hard bound. `fine_step` must be positive; `zero` stays inside the hard bounds. Hints never round or clamp a request: the host validates and stores the exact value sent |
| `controls[]` | Ordered semantic controls: `group {label, controls[], reset?, collapsed?, per_photo?}` (`per_photo`: the group's values usually belong to one photograph, as Basic's White balance's do, so `preset.groups` leaves it unchecked by default when a preset or Copy settings carries settings to other photographs; a hint the host does not enforce), `number {action, parameter, label, style?, rail?, reset?}` (integer or number; slider, field or stepper), `toggle {action, parameter, label}` (boolean), `choice {action, parameter, label, style?}` (enum), `query-choice {label, query, text, page, action, key, shared[]}` (own query with string text and integer page, own non-patch action with string key; equal-kind shared inputs), `color {action, parameter, label, style?}` (fields or picker), `curve {action, channels[{parameter, label}], label, sample_query, background?}` (curve parameters), `range {action, low, high, low_feather?, high_feather?, label, rail?}` (a band over two or four distinct number parameters of one action, whose `low` and `high` declare the same range; each thumb or grip drafts its own field as a slider does), `action {action, label, preset?, style?, icon?}`, `picker {label}`, `presets {action}` and `task {task, label}` (runs a declared task through the consent and progress flow and offers Apply with its artifact when the task declares `apply`); a number, action or picker control, and a group's reset, may also carry `variants` ([control variants](#control-variants)). A picker enters this module's own `point-pick` or `sample-apply` mode through `workspace.set`. A query-choice control searches and pages its own query, and submits an eligible row’s key once. A module declares at most one. The host validates at most 100 rows with string `key` and `title`, boolean `eligible`, optional string `subtitle` and string-array `reasons`; invalid answers are internal errors naming the module. Shared inputs go to both query and action; stale answers for an older asset, entry, text, page or input are dropped. A presets control is where the host renders its preset library; its action is this module's own, not a patch, and declares a required `settings` parameter of kind `settings`, a required `name` of kind `string`, optionally a non-required `preset-id` of kind `string`, and nothing else, and a module declares at most one. Omitted styles use the documented defaults. Rails, on a number or a range, are plain, hue, temperature, tint or a gradient of 2–8 RGB stops. A number control's `reset` is what resetting that one field runs — a double-click on its label or rail, or its field's own reset — as an `{action, preset}` of this module, the shape a group's and the module's resets use; it is listed only when declared, and without it the field resets to its parameter's declared default. The RAW variants of Basic's Temperature and Tint declare `{action: set-raw, preset: {white-balance: as-shot}}`, so resetting either returns the development to the camera's white balance. A curve's `sample_query` declares each channel as an optional parameter without a default; the host asks only for a curve on screen, sends only the active channel's points and uses the module's `{points: [[x, y], …]}` result for the plot (2–1024 finite, increasing-x fraction pairs). An action button on a patch action names at least one preset field, as Basic's As shot names `temperature` and `tint`. Icon names are lowercase hyphenated; an unknown valid name falls back to the label |
| `canvas` | Optional, and the mode's `title` and optional one-letter `shortcut` travel with it. `point-pick {action, x, y, commit}`: a pointer pick on the image maps through `render.locate` to the content pixel and fills the named integer parameters of that action; with `commit: true` those two coordinates are the whole request and the pick submits it at once as one command, which registration allows only for an action that declares no other parameter (RAW's `pick-raw-neutral`). A client decides whether a pick commits from this declaration alone, never from the action's name. `sample-apply {query, x, y, action}`: a pointer pick maps through `render.locate` to the content pixel, runs `query` with those coordinates and, when it answers, submits once to `action` every top-level number field of the result whose name is a parameter of `action`; a refused query commits nothing and its reason is shown. `crop-frame {action, angle, x, y, width, height, fit_action, aspect}`: the host's crop-frame editor edits a transient draft of the named number parameters of `action` and derives its ratio presets from the `aspect` enum of `fit_action`; only Apply calls the action. A `point-pick` or `sample-apply` module declares at most one `picker` control, and when it declares none another module's picker variant must reach its canvas, which registration checks once the registry is complete (the RAW module's sensor pick is reached by Basic's Neutral picker); a `crop-frame` module declares none |
| `availability` | `available` or `unavailable {reason}`; an unavailable provider keeps its descriptor and effect identities |
| `settings`, `capabilities`, `resources`, `tasks` | Optional capability declarations, all empty by default and omitted from JSON when empty: typed module settings and provider profiles with adapters, the `remote-image-request` and `download-artifact` capabilities, pinned resources, and worker tasks with their parameters, uses and optional `apply` action. Their shapes and every registration rule are in [module capabilities](module-capabilities.md#configuration-contract); declarations carry no values and never a secret |

API method names are generated: action `set-pixel` is `edit.set-pixel`, query `neutral-sample` is `query.neutral-sample`, and task `generate-proof-tint` is `task.generate-proof-tint`. Parameters are top-level request fields beside `asset_id` and, for an action, `mutation`. A query takes `asset_id`, an optional `entry_id` that defaults to the session's selection as `render.sample` does, the same optional `mask` target a maskable module's actions take, and its own declared parameters; it is non-mutating, so a client previewing a historical entry may run one. `schema.list` lists generated action, query and task methods with their parameter descriptors, each method's `sources` when its module does not apply to every kind, and each superseded parameter's `superseded: [{source, by}]` ([control variants](#control-variants)), and `module.list` returns every descriptor, queries, tasks and capability declarations included. Beside `modules`, both answer `host`: the descriptors the host publishes for its own objects in the same shape — today one, `luxforge.masks`, whose actions are the `mask.*` commands, whose queries are `mask.list` and `mask.sample-input` and whose controls are the Masks panel's widgets. A host action or query is called by its own identity (`mask.create-linear`), which already carries its family's namespace. A host descriptor is validated by the rules a module's is, through `ModuleDescriptor::validate_host` where the built-in modules are registered, with three allowances only the host has — method-name identities, parameter names that are its stored payload's `_`-joined field names, and identity parameters — and one extra rule: no host control declares a [variant](#control-variants), because a variant applies only on the global target and a host control always addresses one of the host's objects. There is no hand-maintained list of module or mask methods. A task method takes the `request` mutation envelope, `asset_id` and `profile_id` when the task declares them, and its own parameters; it checks requirements and grants on the owner and answers a job, and a retry answers the first job (see [lifecycle](module-capabilities.md#lifecycle-jobs-and-resources)). A control the desktop cannot render shows an explicit unsupported-control message with the descriptor's kind; it is never silently dropped.

A query-choice answer may include `status.summary` text for the list’s status line and `status.visible_shared`, an array of declared shared parameter names to display for this source. With no visibility hint, every declared shared input is shown. Hidden inputs retain their declared defaults; the host and module still validate every submitted input.

### Source kinds

A module applies to a photo when any of its effects lists the photo's source kind in `sources`, or when it declares no effect at all: a module that writes no layer, such as the presets module, has nothing a kind could refuse. One function answers it, `ModuleDescriptor::applies_to(kind)`, in `O(effects)` with no allocation, and nothing names a module to decide it:

- The host refuses an action or a query of a module that does not apply before the module plans or answers anything, worded from the descriptor's title and the kind: `validation: RAW does not apply to a JPEG photo`, with `data: {source: "jpeg", module_id: "luxforge.raw"}` naming the kind and the module. A draft is refused alike when it begins, and a composite step plans through the same path and is refused alike ([drafts](#drafts)).
- Admission refuses a stack holding a layer whose effect does not list the asset's kind: `incompatible: RAW does not apply to a JPEG photo`, with the same `data`. The RAW source's own invariants — exactly one development layer at index zero, with the original's calibration — are the host's RAW source's, not part of this rule.
- `module.list` without `asset_id` returns every module, each effect with its declared `sources`; with `asset_id` it returns the modules that apply to that asset's kind. So a client that filters the whole list with the same rule for a photo's kind holds exactly what naming the photo returns. The desktop lists once and filters for the displayed photo.
- The desktop's tools sections, command palette, mode strip, mode shortcuts and canvas pick gate show a module only when it applies to the displayed photo's kind. With no photo open they show the modules that apply to every kind.
- The photo's kind reaches a module's plan and queries as `StageContext::kind`, so no plan inspects the stack to learn which kind of photo it edits; the RAW module's plan reads it and then finds its own layer.

`cargo xtask check-repository` refuses product code outside the RAW module (`crates/luxforge-core/src/modules/raw*`) that names the module's identity literal or its effect constant, so no name check can return; tests and the `xtask` harness, which drives the module as an API client does, may name it.

### Control variants

One control can behave as each source kind requires. A `number`, `action` or `picker` control may carry `variants: [{source, module, control}]`, and a `group` may carry `variants: [{source, module, reset}]` for its reset: what another module provides in that place on a photo of the kind `source` names. A variant's `control` has the base control's kind and addresses `module`'s own actions or pick canvas; it carries no variants of its own. `variants` is serialized only when declared, so every other descriptor reads exactly as before. Basic's White balance group is the one delivered example: Temperature, Tint, the Neutral picker and As shot (on a JPEG `set-basic {temperature: 0, tint: 0}`, icon `target`) each name the RAW module's `set-raw.temperature`, `set-raw.tint`, sensor pick and `set-raw {white-balance: as-shot}`, and the group's reset names `set-raw {white-balance: as-shot}` ([source-kind controls](source-controls.md)).

- **Registration.** A descriptor checks its own variants: another module's valid identity, at most one variant per kind, a `control` of the base's kind on a number, action or picker, a `reset` on a group that has one. `ModuleRegistry::check_complete` checks the rest once every module is registered: the named module is registered and applies to the variant's kind, its replacement is valid as that module's own control or reset, and every module whose pick canvas none of its own controls reaches is reached by a picker variant. `ModuleRegistry::builtin` and every editor service run it, so an incomplete registry is refused before any catalog work.
- **One resolver.** `resolve_control(owner, control, kind, mask)` answers which control applies to a photo of `kind` edited through `mask`: the variant for that kind on the global target (`mask` is `None`), and the base control — `owner`'s — on a mask target, with no photo (`kind` is `None`) or with no variant for the kind. It returns `{module, control, variant}`. `resolve_group_reset(owner, group, kind, mask)` answers the same for a group's reset, `{module, reset, variant}`, or none when the group declares no reset. Both are plain functions over descriptors, so a client that holds only what `module.list` returned calls them directly, and `ModuleRegistry::resolve_control` and `resolve_group_reset` are the same rule for a caller that holds the registry. `module.list` returns the declarations unresolved; `asset.state` gives the kind. `O(variants)`.
- **Superseded fields.** Derived from the variants and never listed by name: when a number control of action `A` and parameter `P` has a variant for kind `K`, `P` of `A` is superseded on the global target of a `K` photo (`ModuleRegistry::superseded`). The host refuses such a field there, next to the applicability refusal, and so does `draft.set` for a draft on that target, worded from the declarations: `validation: on a RAW photo, Temperature is the source development's: set-raw temperature (K)` — the kind, the base control's label, the variant module's hint and the variant's field and unit — with `data: {source: "raw", field: "set-basic.temperature", by: "set-raw.temperature"}` naming the kind, the refused field and the field that supersedes it. On a mask target nothing is superseded. Admission refuses a stack whose global layer holds a superseded field away from its default (`incompatible`, the same words). A composite's step skips such a field rather than refusing it ([presets](presets.md#settings-sets)). `schema.list` marks each superseded parameter `superseded: [{source: "raw", by: "set-raw.temperature"}]`. `preset.groups` derives the same superseded fields over the published descriptors, so each settings group says what it captures on each kind and what applying it skips on another ([settings groups](presets.md#settings-groups)). `O(controls)` per request; nothing runs per frame.
- **Module reset.** A field-patch module's reset on the global target of a photo whose controls have variants there is one `Compose`: the patch of every field that is not superseded to its default, then each group reset's variant for that kind, recorded as one entry with the module reset's label. On a RAW photo, Reset Basic therefore also returns the development to As shot, and is a no-op when both already are.

## Module trait

Pointwise units supply an `OperationIdentity` with the unit kind and exact coefficient/stage bits. Colour and spatial operation equality uses those identities in unit order, with conservative compiled-mask allocation identity; `describe` remains diagnostics only. Variable identity sections include lengths, and comparison uses no digest.

The supported current cross-crate authoring interface is `ToolModule` plus the descriptor, action, context and processing types it uses. `EffectDescriptor::new`, `NewLayer::new` and `LayerUpdate::new` construct current effects/plans; artifact builders are available when an effect declares artifacts. Planning uses `StageContext::own_layer` and `insertion_index_for` for target ownership and placement, and its lazy stage, point-sample, input and sensor helpers for questions. A plan need not reconstruct mask ordering or sample a frame. The developer control proof is constructed through the opaque `controls_module()` factory. The built-in field-patch table (`FieldPatch`, `FieldPatchModule`, `Spec`, `Values`) is internal. `SpatialOperation` remains an opaque processing output constructed by built-in spatial units; there is no external spatial authoring or loading framework.

External author compile/tests prove this supported surface and registry-aware provider availability. The integrated [structural qualification](../specs/performance.md#code-structure-consolidation) preserves current command schemas, recipe/history semantics and unavailable-provider refusals.

```text
descriptor()                             -> &ModuleDescriptor
parse(action_id, input)                  -> ActionInput { action_id, parameters }
plan(&ActionInput, &StageContext)        -> ActionPlan::{NoOp, Commit(NewLayer), Update(LayerUpdate), Edits(edits), Compose(steps)}
validate_payload(effect_id, format, payload)
describe(effect_id, format, payload)                     -> LayerReport { summary, values, neutral }
label(&ActionDescriptor, &ActionInput)                   -> String
settings(effect_id, format, payload)                     -> Map<String, Value>
query(query_id, parameters, &StageContext)               -> Value
compile(effect_id, format, payload, CompileStage)        -> Processing
carry(effect_id, format, payload, Stage, Orientation)    -> Option<Value>
capabilities()                                           -> Option<&dyn CapabilityModule>
```

A module that declares worker tasks, managed resources or an effect with `artifacts: true` also implements `CapabilityModule` and returns itself from `capabilities()`; every other module keeps the default `None` and implements nothing more. Registration refuses a module whose declarations need the capability hooks and that provides none, naming the declaration.

```text
compile_bound(effect_id, format, payload, CompileStage, &[PreparedArtifact]) -> Processing
validate_resource(resource_id, &Path)
run_task(task_id, parameters, &ModuleContext)             -> Value
```

- `parse` normalizes a request the host has already checked. The host checks required parameters, integer and number ranges, colors, enum options, booleans and curve constraints generically before calling `parse`, and fills declared defaults, so every caller gets the same structured `validation` error and a module never checks a range or an option again: it decodes the checked fields (`decode_parameters`) and keeps only the rules across fields that no one declaration states, such as `crop-fit`'s custom ratio needing both sides or `set-raw`'s As shot refusing a temperature. The returned `action_id` is the durable history action identity (`set-pixel`, `rotate-left`, `mirror-horizontal`, ...) and `parameters` is the object stored on the history entry.
- `plan` sees a `StageContext`: the current ordered layers, `stage()`, the current output stage (`width`, `height`), `stage_before(i)`, the stage the layer at index `i` receives, `insertion_index_for(effect_id)`, where the host would place a committed layer of that effect for the plan's target by its declared stage and order, `kind`, the photo's source kind, `masks`, the recipe's masks in list order, `sample_before(i, x, y)`, one display pixel of the stage the first `i` layers produce, `input_before(i, x, y)`, the linear channels the receiving layer reads: the final colour run’s unclamped `f32` value for a colour layer, or the full recipe’s encoded spatial boundary for a spatial layer, `sensor_neutral(x, y)`, a RAW original's pre-white-balance sensor patch, and `own_layer(effect_id)`, the module's own layer for the plan's target. The context is lazy. Before the module is asked anything the host checks the stack's structure (`Recipe::validate`: the format marker, the layers and each layer's mask reference; no compile), and it answers every question only when asked: the output stage and a prefix stage by compiling that prefix, and the first question that reads a pixel or the sensor by looking up the verified source, and for a RAW stack its linear settings, strictly, once per plan (the questions that compile a prefix or read pixels are the `StageQuestions` trait the host implements). A plan that asks for no stage, such as a field patch, compiles nothing: a commit compiles the stack the plan produced when it is admitted, and a drafted preview when it is evaluated, and either refuses a stack that cannot compile. A plan that reads no pixel — a transform, a crop, a field patch, a RAW white balance — needs neither the original prepared nor a development at the stack's white balance, and one that samples is `preparation-required` exactly when it samples. So a module plans against the stage its layer will actually receive. It rejects out-of-stage coordinates and reports no-ops; it allocates no frame and mutates nothing. A plan names only what the module decides: `Commit` names an effect and a payload (`NewLayer {effect_id, payload, artifacts}`, the artifacts only for an effect that declares them), and `Update` names a layer and its new payload (`LayerUpdate {id, payload, artifacts}`). The host owns the rest of a layer's identity: a committed layer gets a new identity, the format its effect declares and the request's mask target, and an updated layer keeps its identity, effect, position and mask while the host writes its effect's declared format, so no module can drop, move or invent a mask. A commit of an effect no provider declares is refused with `incompatible: unavailable effect <id>` and `data.effect_id`. The host places a committed layer by the effect's declared stage and order:

  | Stage | Where a committed layer joins the stack |
  | --- | --- |
  | `source` | index zero |
  | `pixel` | before the first restoration, spatial, geometry or finish layer |
  | `restoration` | after pixel layers and before the first colour, spatial, geometry or finish layer |
  | `color` | before the first spatial, geometry or finish layer |
  | `spatial` | before the first geometry or finish layer, after every pixel, restoration and colour layer |
  | `geometry` | before the first finish layer |
  | `finish` | at the end, in the output coordinates the geometry tail produced |

  A leading source layer always keeps index zero. Within the region its stage chooses, the new layer goes after the last layer of the **same** stage whose `order` is at most its own and before the first whose order is greater; layers of other stages in that region keep their positions. No existing layer ever moves, so two effects of one stage land in their declared order whichever was committed first.

  `Update` replaces the payload and artifacts of the layer with that identity in place, which is how the crop module edits its existing crop and orientation layers and folds an action into the orientation layer ahead of the crop without changing history identities. The host rejects an `Update` whose identity is not in the stack. Recipe validation does not reject other orders, and a stack renders by its stored order whatever it is, with one exception: a stored stack in which a finish layer precedes a geometry layer has no stage the finish effect could address, so compiling it — and therefore rendering, sampling and planning against it — fails with `validation: finish layer precedes geometry` naming both layers. Nothing is rewritten or reordered and the stack stays readable through `recipe.describe` and history.

  `Edits(changes)` applies several `Commit` and `Update` changes, in order and each by its own rule, as this one action, and commits the final stack once; it is never empty. The crop module returns it for a transform over a crop: the orientation ahead of the crop is committed or updated, and the crop is updated so it frames the same content in the turned stage ([orientation layer](orientation-layer.md#carrying-the-crop)). The host compiles the final stack before persisting, as for any plan.

  `Compose(steps)` applies other actions, in order, as this one action; the presets module's `apply-settings` returns it ([composite actions](presets.md#composite-actions)), and so does a field-patch module's reset on a photo whose controls have variants. The host runs each step exactly as that action would run alone, against the stack the steps before it produced: the action must be a settings key, which `ModuleRegistry::settings_action` answers: a declared analysis step, or registered, a presettable field patch and provided by an available module (otherwise `validation: unknown action X`, `validation: X is not a field-patch action`, `validation: X is not presettable` or `incompatible: unavailable module M`; a step whose module does not apply to the photo is skipped before its availability is checked), its fields go through the generic check and the module's `parse`, and the module plans against the intermediate stack through the same plan path a single action takes. A step whose plan is itself a composite is refused with `validation: composite actions do not nest`, and more than 16 steps are refused. Any refused step refuses the whole action before anything is written. A final stack equal to the starting one is a no-op; otherwise it is committed once, as one entry storing the composite action's own identity, label and parameters. Planning costs O(steps × layers) and rasterizes nothing.
- `carry` re-expresses one stored geometry layer for its input stage turned or reflected by an exact orientation, so it selects the same content in the turned stage: it returns the layer's new payload, or `None` for a payload that stays as it is. The default is `None`, which declares the effect orientation-invariant; a geometry effect whose payload addresses its input stage's coordinates implements it, as the crop does with `CropPayload::carried`. The crop module asks it of every geometry layer after the orientation through the registry, writes what comes back as that layer's own `Update`, and refuses an unavailable geometry module, so it names no other module and a later geometry effect placed after the orientation cannot keep an unchanged payload over different content unnoticed. It reads a payload only, never renders, and is exact for an exact orientation: geometry that is not affine over the whole stage is beyond it ([architecture](architecture.md#geometry-beyond-an-exact-orientation)).
- `validate_payload` accepts or rejects a persisted payload structurally. `compile` turns it into a host processing primitive at its input stage. Its `CompileStage` carries `stage`, the actual sampled input dimensions; `full`, the corresponding full-resolution layer input dimensions; and `scale {x, y}`, their separate ratios. Exact frames, samples and export use equal stages and scale 1. A reduced stage — the GPU's at Fit and below 100%, the CPU proxy's in a session without a GPU — retains the full dimensions before any window cut, so a module can express fixed full-resolution radii correctly on odd or asymmetric sampled stages. Existing modules use `at.stage`; Detail scales its sensor-pixel radii through this context. The capability hook `compile_bound` is called instead for a layer whose host-owned `artifacts` list is not empty, with the verified bytes of each listed artifact in order; its default ignores them and calls `compile`.
- `monotonic_luminance` says whether a colour effect, with a stored payload, never lowers its output's luminance as its input's rises, reading the payload only. An analysis that solves through a later layer's compiled units, as Auto tone solves through the Look after Basic, searches an earlier value by bisection only when every such layer says so, and tries every value otherwise. The default, `false`, claims nothing; the Look answers `true` up to amount 100, where its blend with the identity stops extrapolating.
- The capability hooks `validate_resource` and `run_task` run only on the capability worker, never on the owner or UI thread, and receive only what the host checked through a `ModuleContext`: effective setting values, the secrets the module declares, installed resource paths, scoped file reads, host-built adapter sends, artifact publishing, progress and cancellation. Each has a default on `CapabilityModule`, so a capability module implements only the hooks its declarations use.
- A `single` effect is one a module owns exactly one layer of per target, because it could not say which of two holds its state; the global layer and each mask are distinct targets of a maskable effect. Compiling a stack that holds two layers of a `single` effect for one target fails with `validation: ambiguous <module title> layers` (`ambiguous Basic layers`, `ambiguous Crop, transform, straighten layers`); nothing is rewritten and the stack stays readable. A module finds its one layer through `StageContext::own_layer(effect_id)`, the host's one lookup (`ModuleRegistry::own_layer`): it returns the layer of that effect that belongs to the target the plan or query addresses — a masked layer of a maskable effect only for its own mask, every other layer for every target — with its index, and refuses two with the same words. Every field-patch module, the crop, both proofs and a preset's capture use it. The transform's orientation effect is not `single`: folding an orientation stored after the crop leaves that layer neutral in place beside the one ahead of the crop ([orientation layer](orientation-layer.md)).
- `describe` answers what a stored layer is, reading the payload only — no render, no sample, no source — as one `LayerReport`, which `recipe.describe` reports on the layer's row (`ModuleRegistry::layer_report`): its one-line `summary`; the parameter `values` it represents, so a client seeds its controls from the displayed entry; and whether it is `neutral`, changing nothing. A field patch is neutral by its own rule (every field at its default; the vignette at amount 0), the crop at the whole image unstraightened, the orientation at the identity and RAW at As shot, which is exactly the Original's development; a payload with no neutral form, such as a pixel replacement, is always an edit. A layer whose provider is missing or unavailable, or whose payload the provider cannot read, is listed with the reason as its summary, no values, and not neutral. A client's edited mark reads `neutral` rather than parsing a payload. The crop module reports `angle`, `x`, `y`, `width` and `height`. The RAW module reports `white-balance` (`as-shot` or `custom`), `temperature` and `tint`, the parameters of `set-raw`: a custom temperature and tint as stored, and otherwise the temperature and tint whose gains are the gains in force — the camera's as-shot gains under As shot, or a neutral pick's — solved from the payload's gains and camera matrix; `set-raw` keeps the field it is not sent at that same value (see [initial RAW](initial-raw.md#minimal-controls-and-shared-basic-integration)). Its explicit gains have no control and are not reported.
- `label` is the one history-label mechanism: the label the entry stores for a request, reading the request only. It receives the action that was requested, which is not always the durable identity the request carries (`transform` is requested, `rotate-left` stored), and defaults to that action's title. A module says more when it has something to say: a field patch names the one field it changed (`Exposure +0.50 EV`), the group a patch set or reset (`White balance`, `Reset Tone`), or a count of fields (`Basic (3 fields)`); a transform names the orientation it applies (`Rotate left`), a crop its angle or ratio (`Crop 7.5°`, `Crop 16:9`), the pixel proof its coordinates (`Pixel 12, 34`) and a preset its name (`Preset: Soft film`). `settings` is what a preset captures of a layer; it defaults to the values `describe` reports, and the RAW module narrows it to `{white-balance: as-shot}` under As shot and `{temperature, tint}` otherwise ([presets](presets.md#methods)).
- `query` answers one declared read-only question. The host resolves it from the same registry discovery lists, checks its parameters through the same generic check, and asks it through the same plan path an action is planned through, so a query sees exactly the stage a commit would address: no frame on the owner and no catalog write. A query that reads a pixel is deferred to the owner's tile service as `Planned::Query`, through a spatial prefix or not; `TileStage` reads every pixel of the query through one session, so a neutral picker's 25 points are one GPU tile, or one evaluation of the prefix on the reference. The answer carries the owner's sequence when it was planned. Queries that read no pixels remain on the owner. The default refuses with `validation: module <id> declares no queries`. `EditorService::run_query` is the read-only counterpart of `apply_action`, so a query and a commit can never disagree about which stage a coordinate names. A query of a maskable module takes the same optional `mask` target its actions take. On the global target it sees the stack as an action does; on a mask it reads the whole stack, so the stage before that mask's own layer holds the global layer and the earlier masks' layers exactly as they render: Basic's neutral picker on a mask reads the image with the global white balance applied.

There is one plan path. `EditorService::ask` asks a module one question about one stack for one target: it refuses an unavailable module (`incompatible: unavailable module <id>`), a module that does not apply to the asset's source kind ([source kinds](#source-kinds)) and a field superseded on this target ([control variants](#control-variants)) — one refusal, `check_askable`, which a draft also runs before it holds anything its commit would refuse — checks the stack against the asset's source kind, binds its artifacts, refuses a mask target the stack does not hold, and hands the module the stack of that target through the lazy `StageContext`. `EditorService::plan_action` plans an action through it and resolves the plan into the stack it produces, or a no-op; a commit, a draft's effective recipe and each composite step plan through them, and a query is answered through `ask`. No module is special: the RAW development updates its source layer through the same path, and no plan can move or add one, because compiling refuses a source-stage layer anywhere but index zero and a RAW stack must hold exactly one.

Every action — a module's and a host `mask.*` command alike — resolves through the registry's one action lookup, `ModuleRegistry::resolve_action`, as `ActionRef::Module(module, action)` or `ActionRef::Host(command)`, and runs through one path, `EditorService::run_action`: `Prepared::new` resolves it, takes a module action's host `mask` field out through the one target check a module query's `mask` also takes (`take_mask_target`) and checks its parameters with the one generic check (a module then parses them); the request identity is built once; `EditorService::plan_request` plans it — a module action through `plan_action` above, a mask command through `plan_mask_command`, which rewrites the mask table and reads a pixel only for a stroke limited to a colour — and `mutate` admits and commits it. A draft's effective recipe is prepared and planned through the same two functions with the request its commit will send, so a draft equals its commit by construction for both. Queries resolve the same way (`resolve_query`, `QueryRef::{Module, Host}`), and `run_query` answers the host's `mask.list` and `mask.sample-input` beside a module's.

### Analysis actions

An action button with `style: group-header` appears as a compact button before its enclosing
group's reset, including while that group is collapsed. Basic declares Auto in its Tone header.

An action may declare `analysis: {query, writes}`. The query belongs to its module; `writes` maps
its field-patch actions to the fields the analysis replaces. Registration checks those names and
refuses parameters, a patch declaration, duplicate fields or an undeclared query. Basic's
`auto-tone` is the first analysis action. It cannot be drafted. A direct analysis action or a
settings composite containing one refuses an open draft; the registry answers whether a request
contains one (`ModuleRegistry::contains_analysis`). A photograph with nothing to analyse is refused
with an `AnalysisRefusal`: `validation`, its `data.analysis_refusal` the reason alone, such as
`no-tonal-range`, which a composite reads to skip the step.

The owner defers the entire declared query to its tile worker, then replays the small answer during
planning only while the asset revision, source identity and draft state still match. The query
and action therefore share the same analysis without frame work on the owner. The action answers
the report it used beside its mutation result, as `analysis.<query>` (`ActionResult::analysis`),
added after the commit and never stored with the request, so a deduplicated retry carries none; a
settings composite whose analysis step applied answers it too.

Batch presets drive the same replay (`editor::pixels::Replay`) from their library worker rather
than parking on the owner: each pass runs on the owner through `Owner::pixel_pass`, the pass every
parked call takes, after the owner has checked that what the last read was read from is still
current; each read is submitted as `DeferredRead::tile_call` to the owner's tile service under the
job's cancellation and for no client, so a disconnect of the client that started the batch leaves
it; each photograph keeps a memo of its own and never reads or changes the caller's session memo;
the same four-read bound applies; and the job's commit gate keeps a cancelled batch from
committing late. The owner's own parked reads are cancelled when superseded, stale or
disconnected ([detail](detail.md)). Analysis settings are empty objects and execute after every
patch; overlapping written fields are refused at store. See [Auto tone](auto-tone.md) for its
sample, cache and report bounds.

### Field patches

An action may declare `patch: true`. The generic check then validates the fields the caller sent and fills no declared default, so the module receives exactly those fields and merges them over the state it already holds; omitted fields are preserved by that merge, unknown fields are still rejected, and every parameter is optional however it is declared (`schema.list` lists them all as optional). The history entry stores the patch as sent, not the merged payload, request deduplication covers the patch as sent, and a patch that changes nothing is a no-op with no entry. Defaults stay declared on patch parameters because clients seed and reset fields from them.

Basic, the Tone curve, Detail, the colour mixer, Presence, Perspective, the vignette and the developer controls proof are each one declarative field-patch module (`modules/field_patch.rs`). A module declares a spec — its identity, its one effect, its `set-<name>` patch and `reset-<name>` action, and a field table, grouped into its sections with their layout — and provides only `compile` over the payload's canonical values, optionally its own neutrality rule and optionally its queries. A spec is made only by `Spec::new(id, title, hint, effect_id, stage)`, which derives the noun (the id's last segment, `basic`), the actions `set-<noun>` titled `Set <title>` and `reset-<noun>` titled `Reset <title>` with shared notes a module may replace with its own, and an effect whose format is the shared effect format, with no artifacts, `single` and no source list, for every module; the module sets the effect's order and maskability. The effect's stage is `restoration`, `color`, `spatial` or `finish`; any other is refused. A field is a declared parameter of any kind the field patch holds — `number`, `integer`, `boolean`, `enum`, `color` or `curve` — with its default and hints, the control that draws it (a number control in a style, a toggle, a choice in a style, a colour control in a style, or, for a curve, a channel of a curve control its group lists beside its fields), its history name, and for a number control a rail and any [source-kind variants](source-controls.md); a spec whose field is outside that vocabulary, lacks a valid default, or declares a rail or variants on a control that cannot carry them, whose group lists a name that is not a declared field, or whose field is in no group or in more than one is refused when the module is built, so registering a built-in field-patch module is its own directory and one line in `builtin_modules()`. The shared module builds the descriptor from the spec and implements everything else once: a payload is a JSON object in which a missing key is that field's default, so a set merges the sent fields over the stored values or the defaults and stores the canonical payload, which holds only the fields that differ from their defaults, so the all-default payload is `{}`. Every comparison is by canonical value, not by JSON spelling: a number, and each coordinate of a curve, is the f64 it reads as, so `1` and `1.0` are the same state. A first set whose merge is neutral commits no layer, a later one updates the layer in place, and a merge equal to the stored values is a no-op; `describe` reports every field with defaults filled; a stored payload is refused by effect, format, shape and unknown field, and each value by the one generic parameter check. A history label names the one field a patch moved with its value: a number with its declared decimals and unit, signed when the field's range is (`Exposure +0.50 EV`, `Red hue +20`, `Vignette midpoint 60`), a boolean as `on` or `off`, an option title-cased (`Mode Two`), a colour as `r,g,b` and a curve by its point count (`Master 4 points`); `Reset <group>` for a patch holding exactly one group's fields at their defaults, the group's label for a patch holding exactly one group's fields otherwise (`White balance` for a neutral pick's temperature and tint), `<title> (N fields)` for any other patch and `Reset <title>` for the reset action. A recipe row reads `Neutral` for the all-default payload and otherwise lists the fields that differ from their defaults, labelled the same way. The neutrality rule defaults to every field at its default; the vignette's is `amount == 0`. A layer the rule calls neutral compiles, for every field-patch module in one place, to no units in its stage's shape — an empty colour operation for a colour or finish effect, an empty spatial operation for a restoration or spatial one — which the host drops, keeping the identity byte path and the shared source buffer; the module's `compile` sees only a layer with a non-neutral configuration. Basic's one query is its neutral picker, and the Tone curve's is its sampled curve. A module's `compile` reads a number field with `Values::number`, a curve field's points with `Values::curve`, and whether every field holds its default with `Values::is_default`.

Configuration neutrality controls storage. A nondefault configuration may still compile to no pixel work: Detail retains Radius and other ancillary settings while their strengths are zero; the Tone curve retains extra diagonal points while compiling an identity curve. Such a layer reports its stored settings and shares the source allocation until activated. Conformance checks empty compiled work for exact byte and linear identity independently of the configuration's neutrality, and requires active settings to compile work and change pixels.

The Basic module (`luxforge.basic`) owns the one colour-stage effect `luxforge.basic.adjust`, format 1, and is edited through `set-basic`, a field patch over the implemented Basic parameters, and `reset-basic`, which returns that layer to neutral. A payload is a JSON object whose keys are the implemented parameter names; a missing key is neutral, so the canonical neutral payload is `{}` and `{"exposure": 0}` is the same state written differently. Its fields are White balance (`temperature`, `tint`), Tone (`exposure`, `contrast`, `highlights`, `shadows`, `whites`, `blacks`) and Colour (`vibrance`, `saturation`); their ranges, equations and fixed internal order are in [Basic adjustments](basic-and-histogram.md), [Basic white balance](basic-white-balance.md) and [Basic Tone](basic-tone.md). The first non-neutral set commits the layer at the colour insertion index, before the geometry tail, and every later set updates it there in place.

The Tone curve module (`luxforge.curve`, [design](tone-curve.md)) owns the one colour-stage effect `luxforge.curve.tone`, declared order 5 and `maskable`, and is edited through `set-curve`, a field patch over its one `curve` field `luminance` (2 to 16 points, monotone, default `[[0, 0], [1, 1]]`, step 0.01, precision 2), and `reset-curve`. Its one group is the curve control alone, one Luminance channel over a histogram background, so the section draws no group header, and its query `sample-curve` returns 257 samples of the curve through the submitted points, computed in `f64` from the construction production casts its coefficients from. A field patch is labelled by its point count (`Tone curve 3 points`). The layer is neutral exactly when `luminance` is canonically its default, so a curve with an extra point on the diagonal is a stored, labelled layer; a curve that is the exact identity map still compiles to no units, and every other curve to one `PointwiseColor` unit implementing the frozen [curve and reconstruction](tone-curve.md#processing-contract).

The colour mixer module (`luxforge.mixer`) owns the one colour-stage effect `luxforge.mixer.hsl`, format 1, declared order 10 so a committed mixer layer always follows the Basic layer, and is edited through `set-mixer`, a field patch over its twenty-four `<range>-<property>` parameters (hue, saturation and luminance for each of the eight colour ranges red, orange, yellow, green, aqua, blue, purple and magenta), and `reset-mixer`, which returns that layer to neutral. The payload follows the same field-patch shape as Basic's: a missing key is neutral, so `{}` is the canonical neutral payload. The module compiles its payload into one `PointwiseColor` unit implementing the frozen equations in [the mixer study](mixer-study.md); a neutral payload compiles to no units, keeping the identity byte path and the shared source buffer.

The Presence module (`luxforge.presence`) owns the one spatial-stage effect `luxforge.presence.adjust`, format 1, and is edited through `set-presence`, a field patch over `texture`, `clarity` and `dehaze` (each −100..100, step 1, neutral 0), and `reset-presence`, which returns that layer to neutral. The payload follows the same field-patch shape as Basic's: a missing key is neutral, so `{}` is the canonical neutral payload. Because it declares the `spatial` stage, the first non-neutral set commits the layer after every pixel and colour layer and before the geometry tail, and every later set updates it there in place. The module compiles its payload into one `Spatial` operation whose units run in the frozen order dehaze, texture, clarity, implementing the equations, radii and halos in [the presence study](presence-study.md); a unit whose amount is 0 is the exact identity, so it is left out of the operation entirely and its halo and its work go with it, and a neutral payload compiles to no units at all, keeping the identity byte path and the shared source buffer. Dehaze declares the one global estimate in this design, an atmospheric light of three `f64`; texture and clarity declare none. The summed halo is 274 px at a 24 MP stage and 448 px at 60 MP and above, inside the host's 512 px bound.

The Vignette module (`luxforge.vignette`) owns the one finish-stage effect `luxforge.vignette.postcrop`, format 1, and is edited through `set-vignette`, a field patch over `amount`, `midpoint`, `roundness` and `feather`, and `reset-vignette`, which returns that layer to its all-default payload. Unlike Basic, a missing key does not mean 0: it means that field's own default (amount 0, midpoint 50, roundness 0, feather 50), so the canonical all-default payload is still `{}` but `{"midpoint": 50}` is the same state written differently, not the same as an empty payload for every other field. The layer as a whole is neutral — compiles to no processing and keeps the identity byte path — exactly when `amount` is `0`, whatever `midpoint`, `roundness` and `feather` hold, because the frozen mask geometry never affects the output when the amount equation is itself the identity. Because it declares the `finish` stage, the first non-neutral set commits the layer at the end of the stack, after the geometry tail, and every later set or crop that runs after it updates its own position or recentres its mask on the new output stage, in place.

Processing primitives are the closed host set for v0: `ExactGeometry` (an integer mapping with declared output size, composable into one raster pass), `PointReplace` (one input-stage pixel, applied through the geometry that follows it), `Color` (pointwise colour over the whole stage), `Spatial` (a bounded neighbourhood of the whole stage), `Warp` (one Lens or Perspective step in a bounded chain) and `Resample` (an affine or nonlinear map from output pixel centers to input coordinates with a declared output size, sampled bilinearly in linear light with edge clamping, as defined in the [crop contract](../specs/single-image.md#sampling)). Adjacent geometry steps fuse into one resample. A resample and a spatial operation are both stage boundaries: the exact layers before one rasterize into one bounded intermediate frame, the boundary writes the next frame, and exact layers after it compose as before. A point replace whose pixel falls outside a later crop is simply not visible. There is no generalized graph.

A `Color` operation is an ordered list of at most eight `PointwiseColor` units. The module owns each unit's equation and declares whether its coefficients are finite; the host owns everything else. A unit's `apply_row(y, x0, rgb)` carries the position of the row it is given: `y` is the row and `x0` the column of the first pixel, in the coordinates of the stage its segment produces, and the slice is always one contiguous run of that row. A unit that does not depend on position ignores both; every delivered unit does except the vignette's. The rasterizing pass, `render.sample`, the byte point path and the RAW linear path address the same coordinates, so a sample equals the rendered byte for a position-dependent unit as well. Only a stage whose input is its output — a finish-stage layer after the geometry tail — sees the coordinates its own payload was written in; a colour layer before a transform is still evaluated in the transformed frame, which is why position-dependent effects declare the `finish` stage. The host decodes each channel into f32 linear sRGB (D65) through an 8-bit or 16-bit table computed in f64, hands rows to every unit of every operation of a run in order, and only at the end of that run clamps to `[0, 1]` and quantizes to the code whose exact linear threshold interval holds the value, which equals `floor(M · encode(v) + 0.5)` for the selected encoded maximum `M` (255 or 65535). Values outside `[0, 1]` and negative values are preserved between units and between consecutive operations, so an inverse pair returns its input bytes; alpha is never touched. A point replacement, a resample and the end of the recipe are the quantization boundaries: a replacement earlier in the operation list is processed by the colour operations after it and one later in the list is not, and a resample interpolates the quantized frame. Exact geometry commutes with a position-independent unit composes as before. Compilation refuses an operation with more than eight units or a unit whose coefficients are not finite, and a non-finite value after any unit fails the render or sample with `resource-limit`; a neutral payload compiles to no units, which is no processing at all, so the identity byte path and the shared source buffer are kept. The rasterizing pass streams each run over the frame in bounded row chunks and hands each unit one row of a chunk at a time, and `render.sample` applies the same phases to one pixel at its own coordinates, so a sample equals the rendered byte.

JPEG frame precision is a pure property of the compiled segments. Spatial output that feeds a later colour run or another spatial boundary uses RGB16 encoded sRGB; pass-through spatial chains propagate that demand, while a later point replacement or resample ends it at a narrow boundary. Source, point replacement, resampling and terminal display retain their RGBA8 behavior. Frames and point samples read the same width policy, and each RGB16 buffer is checked as six bytes per pixel against the 512 MiB evaluated-frame limit. RAW keeps its planar f32 spatial frames and terminal-only quantization.

A `Spatial` operation is an ordered list of at most four `SpatialUnit` units, for an effect whose value at a pixel depends on a bounded neighbourhood of that pixel. A unit declares `halo(stage)`, the input pixels it reads beyond what it writes; `scratch_bytes(region)`, the working buffer it wants; `estimate_key()` and `prepare(reduction)`, an optional global estimate and its identity; `apply(input, output, global, scratch)` over planar f32 linear-sRGB rectangles that carry their position in the stage; and `describe()`, which writes every coefficient exactly, in shortest round-trip form and never rounded to a display precision, because the host compares compiled operations by it. The module owns those answers and nothing else; a colour unit's `describe()` follows the same rule. The host calls `apply_cancellable` with the render token; its default checks before and after `apply`, while Detail checks between levels and bounded row chunks within the first tile as well.

The operation opens a new segment at the same dimensions as the stage it receives, so the segment before it finishes its frame, the operation reads that frame and writes the next one, and later exact layers compose as before. The host streams square output tiles anchored at the stage origin, with partial tiles at the right and bottom edges: 512 × 512, or 1024 × 1024 once the operation's summed halo at its stage passes 128 px, where a small tile would recompute more of the halo than the larger tile costs, reading each tile grown by the operation's summed halo and clamped to the stage. Inside a tile the units chain: unit `i` is given the rectangle unit `i − 1` filled, and fills that rectangle shrunk by its own halo on every side except a side that lies on the stage edge, where it writes up to the edge because there is nothing further to read. Reads are clamped to the stage, so a unit never sees a coordinate outside it. A unit's value must therefore depend only on its pixel's neighbourhood: the host chooses the tiling, so a filter is evaluated in a fixed order that does not depend on where evaluation started, and a rendered frame is the same at any tile size and across runs.

One tile's working set — the input region, the intermediate planes, the last unit's output, each at the largest it is over the operation's tiles, and the largest scratch any unit asked for — is charged to the render context's `SpatialBudget` with a 256 MiB target, separate from the 64 MiB float scratch budget, with an observable high-water mark. The target paces the work and never refuses it. The host refuses an operation when it compiles the recipe, before any pixel is read, only for what the operation declares: a summed halo over 512 px, more than four units or a non-finite one; nothing is reduced to fit and nothing is rewritten. A render's window of tiles reserves working sets before any of its tiles allocates, asking for as many as fit the whole target and the shared Rayon pool's workers, and runs as many tiles at once as fit beside what other evaluations hold, never fewer than one; after each tile it gives one back while the target is passed and takes one more while one fits. So a render that overlaps another — the histogram's analysis and the preview's exact phase rendering the same stack — slows to one tile at a time rather than failing, and speeds up again once the other releases; a tile larger than the whole target runs alone. The process can then pass the target by at most one working set per spatial evaluation in flight, and the high-water mark shows it. Tiles run on the pool from the spatial pass's threshold, each worker starting its next tile as soon as its last one is written, and the render's cancellation token is checked between tiles.

A global estimate is prepared once from a host-built 1/16-per-side box average of the operation's input stage — at most a quarter of a megapixel, partial blocks averaged over their actual pixels, the grid anchored at the stage origin — and is at most 4 KiB. Only a unit that declares an estimate key has one: `estimate_key()` names everything `prepare` reads besides the reduction — the unit and any coefficient its preparation depends on — and a unit that declares none (the default) is never prepared, is handed no global and never causes a reduction. The reference renderer reduces the operation's input stage at most once per frame, only when a unit declares a key, and prepares each key once from that reduction (`render::spatial::resolve_globals`); nothing is kept between renders, so each frame reduces its own stage. Dehaze's atmospheric light reads the reduction alone, and Texture and Clarity declare none. The key belongs to the unit rather than to its position, because a module compiles whichever units its payload needs — Presence leaves out a unit whose amount is zero, which moves the others up — and two units that declare the same key over one stage share one preparation. On the GPU a unit with an estimate also describes its light passes (`SpatialUnit::gpu_light`), the same reduction into 16-pixel block means of the whole stage and the same selection, which the plan's light link runs every frame from the source at full resolution, and its GPU description reads the light from the plane that link writes ([GPU previews](gpu-preview.md#spatial-programs)).

On the byte path each tile is decoded through the same table the colour run uses and quantized through the same exact thresholds into a new frame of the same size, with alpha copied; at most two frames exist and no full-frame float buffer ever does. The RAW linear path pulls the compiled prefix a row at a time and never materializes it, so a render materializes each spatial operation's output once as three f32 planes inside the 1.5 GiB RAW planar limit and pulls from that, with nothing quantized before the terminal boundary. Each frame is built from the one before it and replaces it, so at most two exist at once. A pixel read through a spatial segment is not a point query: on the desktop it is one GPU tile around the pixel, drawn by the catalog owner's tile service, and on the reference renderer, which answers what the GPU cannot draw and every read of `luxforge-json`, the whole frame of each spatial segment the read passes through, materialized once per call as a render materializes it, so a sample equals the rendered byte by construction ([architecture](architecture.md#point-queries-and-pixel-reads)). Each reference frame computes its required global estimates from reductions of its whole spatial stages; no estimate store is retained. A sample grid reads the reference's frames the same way. A non-finite value after any unit fails the render or the sample with `resource-limit`, and a neutral payload compiles to no units, which is no processing at all, so no boundary is opened and the identity byte path and the shared source buffer are kept.

## Host dispatch

Every method resolves through one method table (`crates/luxforge-core/src/api/methods.rs`), for the desktop, the JSON API and headless callers alike. A host method's entry names its parameters, its notes, who answers its retries and its handler: a service handler, which the editor service answers with the caller's session, or an owner handler, which the catalog owner answers from its own state — the one job table, the event log, the capability host and the activity board. A handler that only forwards to one operation is written inline in its entry, so the capability host's `module.*` operations are table rows. A mutating service handler reports beside its answer whether it changed anything and, for an asset, the revision it left: a no-op and a retry the catalog's request log answered changed nothing. The owner announces from that report and never reads an answer's `outcome`, `deduplicated` or `revision` back. `edit.*`, `query.*` and `task.*` methods are generated from the registry's modules, and the `mask.*` methods from the host descriptor, by the same lookup (`action_for_method`, `query_for_method`); a `task.*` method carries its task's identity to the capability host. The owner finds the method, checks its mutation envelope, answers a retry from its request table when the method declares that the owner answers its retries, otherwise calls the handler, and records the event each change announced; nothing is routed any other way. A panic while the owner serves one message is contained: the request it was serving is answered `internal`, a source job whose result it was committing fails `internal` and releases its waiters, a change committed before the panic keeps its event, and the owner serves the next message. Every durable write is one transaction and the entry cache moves only after a commit, so nothing is left half written. The source worker contains a panic in one task the same way: the job fails `internal`, `job.read`, `wait_source` and the activity board agree, and the worker runs the next task. A host method's parameters are declared once, as the `deny_unknown_fields` struct its handler parses (`host_params!` in `api/params.rs`), each field with a kind from the one parameter vocabulary module descriptors use (`ParameterKind`): identity kinds for the host's assets, entries, drafts, jobs, presets, masks and components, the `artifact` kind, integer and number ranges, enumerations, bounded strings, `text` for a file's contents or a path, `settings`, `secret` for the one secret `set-secret` carries, and one `json` kind for a structured field, such as a zoom, an analysis target or a draft's fields, whose notes give its shape and whose own type checks it. `schema.list` lists those `parameters` exactly as it lists a generated method's, beside the `required` and `optional` field names, and the parse checks every named field against its kind with the generic value check before the struct is read, so the schema and the parser cannot differ and a published range is an enforced one. Adding a typed field is one line of the struct. Every host method refuses a field it does not declare, including one that takes none.

Every mutating method carries a `mutation` envelope, and `schema.list` names it in the method's `mutation` field; a method mutates exactly when it carries one. `revision` is `{expected_revision, request_id, actor}`, for a change to something with a revision: an asset (actions, `mask.*` commands, history, `draft.commit`) or a module's settings. `request` is `{request_id, actor}`, for every other change: the preset library, versions, the library's changes (picks, Develops, folders and collections), `artifact.collect`, `export.jpeg`, module permissions and resources, and the `task.*` methods, which queue a job. Cancelling a job is not one of them: every cancel converges ([jobs](#jobs)). The rule is the same for both: a retry with the same `request_id` and the same input returns the first answer marked `deduplicated: true`, changes nothing again and emits no event, and the same `request_id` with other input is a `conflict`. The dispatcher checks every envelope once, before any handler runs (`Envelope::check` in `api/params.rs`): `request_id` and `actor` are 1..128 characters, and no handler, service or store checks its own; an absent or malformed envelope is refused by the method's own parse, which names the field. Each mutating method declares which of two answers its retries, and the owner reads nothing else to decide. The catalog records an asset change's request durably in the same write as the change, per asset, because a retry after a restart must be answered rather than refused as stale: it answers the retries of actions, `mask.*` commands and history. Every other mutation's retry — each `request` method's, a module settings write's and `draft.commit`'s, whose first answer ends the draft its retry names so the retry cannot reach the asset's log — is answered from the owner's request table, keyed by `(scope, request_id)` with the scope the method's family (its name without the last segment) and the input hashed, a `set-secret` value redacted first; it holds the most recent 256 successful answers, at most 8 MiB, for the owner's lifetime. Each of those methods is safe to run again after a restart: it is a no-op, joins the work already done, fails visibly on the uniqueness it would break, or, for a settings write, which sets values rather than changing them, conflicts on the revision it was made against; a draft does not outlive the owner, so a commit's retry after a restart is refused as naming no draft.

An action request goes through one path for the desktop, the JSON API and headless callers:

1. The dispatcher has checked the mutation envelope. Resolve the action through the registry's one action lookup — a module's, or a host `mask.*` command — else `validation: unknown action`; refuse an action whose module is registered as unavailable with `incompatible: unavailable module <id>`.
2. Generic parameter checks, then module `parse` (a host command's checked parameters are what it stores). A patch action's check validates only the fields that were sent, and demands only the identities it addresses.
3. Request deduplication: the stored input hash covers `{action: <durable action id>, mutation}` merged with the parsed parameters. A retry returns the original answer, stored whole with the request — for a `mask.*` command its label and the mask and component it minted — marked `deduplicated`, and emits no event, because the first attempt emitted it; the same request ID with different input is a `conflict`.
4. Revision check, then module `plan` against the current stack through the one plan path, which looks up the cached verified source only when the plan samples a pixel.
5. `NoOp` records the request without a row. `Commit` places the layer by its effect stage, and `Compose` resolves its steps into one final stack or a no-op; `Commit`, `Update` and a changing `Compose` admit the resulting recipe and persist the snapshot, entry, current pointer, revision, cleared redo and request result in one transaction. Admission is one function that every new snapshot passes, a `mask.*` command's and a Restore's included: the registry validates the recipe, which checks its whole mask table once — the limits, every stroke it references and every component kind — it is checked against the asset's source kind (every layer's effect lists that kind, and a RAW stack keeps its RAW source's invariants), every artifact it lists must be recorded with a present file and is bound, and it is compiled against the asset, trusting that table, which leaves no later layer addressing a stage that no longer exists. A drafted `mask.*` gesture's recipe has its mask table checked once the same way; compiling never checks the table again.

### Preparation

An evaluation that needs something the catalog owner has not prepared — the verified original, a RAW development at a white balance, or a derived artifact's bytes — is refused `preparation-required`, and the refusal names exactly what the stack it evaluated needs as a typed `PreparationNeeds {asset_id, entry_id, gains, artifacts}`: the asset whose original it reads, the saved entry it evaluated (or planned over, for a change or a draft), the sensor gains a RAW development must hold (`None` for a JPEG) and the artifacts that stack references that are not ready. The service names them where it knows the stack, in one function every evaluating method answers through (`EditorService::needing`), so a request that leaves the entry to the session — `render.sample` or a `query.*` on a historical selection, a draft — is prepared for the stack it actually evaluated, never the current one re-derived from the request's parameters. A strict evaluation names its own white balance; a drafted preview, the one evaluation that approximates a white balance, names the development its entry holds, so a drag never queues one development per drafted value.

The owner has one answer to every such refusal, from any method or a preview job: it queues exactly those needs as one source job and answers `{code: "preparation-required", job_id, message}`, the message saying why. The job reads the original when the cache does not hold it, developing a RAW one at the named gains in the same pass; otherwise it redevelops only when the planes do not hold those gains; and it reads and verifies the named artifacts that are still not ready after either. Needs with nothing left to prepare answer with a job that is already ready. `source.prepare {asset_id, entry_id?}` queues the needs of that entry, or of the current one, the same way. A client waits for the job and asks again. The owner's planning (`EditorService::preparation`), the job's work (`SourceWork::run`) and its completion (`EditorService::complete_preparation`) are the service's own, and nothing else reads an original or an artifact: a direct service client, a test or the harness, prepares the same needs blocking with `EditorService::prepare(&needs)` — the needs a refusal names, or `EditorService::entry_needs` — and imports with `EditorService::import`, which runs the same three steps on its own thread.

## Jobs

Every job the catalog owner runs is one record in one table (`crates/luxforge-core/src/jobs.rs`): source preparation (kinds `prepare`, `develop`, `artifacts` and `collect`), `analysis`, capability work (`install`, `remove` and `task`) and `export`. The records share one identity, one status vocabulary (`crate::JobStatus`), one progress model (the activity board's), one bounded retention and one read shape. `job.read {job_id}` answers a job of any kind as `{job_id, kind, status, progress: {fraction?, message?}, asset_id?, module_id?, resource_id?, identity?, result?, error?: {code, message, data?}, request_id?}`:

| Status | Meaning |
| --- | --- |
| `queued` | Accepted and not started: in the source worker's queue, the analysis worker's one replaceable pending slot or a lane's waiting list |
| `running` | Its worker holds it now |
| `ready` | Complete; `result` carries what it produced: the prepared asset's state, a collection's `{rows, objects, temporary}`, an analysis report, a capability job's value or an export's `{path, bytes, width, height, metadata, renderer}`, `renderer` naming which renderer drew it (`{record, reason}`: the GPU, or the reference with why, [export](export.md#api)) |
| `failed` | `error` carries the structured reason |
| `cancelled` | Stopped before it finished; `error` names why |
| `superseded` | Replaced before it ran: a pending analysis a newer request displaced |

Only `ready` carries `result`, apart from a running job that reports its answer as it goes: a `source-find` job's `result` is its report so far ([missing originals](catalog.md#missing-originals)). Each kind keeps its own admission, scheduling and cancel rule:

| Kind | Scheduled by | A second request | `job.cancel` | A client disconnecting |
| --- | --- | --- | --- | --- |
| Source | The source worker: eight queued, and queued developments, with preparations holding the sensor a Develop read, pin at most one sensor mosaic | Joins the queued or running job for the same file signature, gains and artifacts; a collection is never joined | Leaves the caller's interest; the work stops only when no client wants it | Leaves its interest, as a cancel does |
| Analysis | The analysis worker: one running and one replaceable pending job; a newer request supersedes the pending one | Joins the job for the same identity, a kept report included | As for source | As for source |
| Capability | The `transfer` and `module` lanes, first in first out: one running and four waiting each | An install or removal already queued or running is answered with that job | Stops the job for every client | Nothing: the job belongs to its module |
| Export | The `export` lane: one running and four waiting, never superseded | Always a new job | Stops the job for every client; a running export removes its temporary file | Nothing: the export runs on |

A source or analysis job is read and cancelled by the clients that requested it, including one that has cancelled, which keeps reading the outcome; any other client is refused `validation`. A capability or export job belongs to no client, and any client reads and cancels it. A job the last interested client leaves reads `cancelled` at once if it had not started, and otherwise `running` until its worker stops, within a chunk of its render or at its next step, and then `cancelled`, whatever the worker produced. `job.cancel {job_id}` answers the job as `job.read` does afterwards. Every cancel converges — a left job stays left, a cancelled one stays cancelled and a finished one is answered unchanged — so `job.cancel` carries no mutation envelope and a repeat needs no stored answer. A cancelled capability job that had not started is the job's own outcome and is announced under the request that started it.

The table keeps the last 64 finished source jobs, the last 32 of each other family and at most eight analysis reports, forgetting the oldest of a family first; a live job is never forgotten. `activity.list` lists running work with the `job_id` `job.read` answers, and the two agree about its status. A task on the source worker or a lane that panics fails `internal`, and the worker runs the next. `job.adopt {job_id}` makes the ready preparation of this client's latest import its current asset.

### Waiting for a job change

`job.wait {job_id, after?, timeout_ms?}` returns `{change, job}`, where `job` is the authoritative `job.read` record and `change` is that retained job's unsigned change token. Omit `after` for an immediate first observation. Passing the last answer's token holds an unchanged queued or running job until its lifecycle, progress or partial result changes. A different token, a terminal job or `timeout_ms: 0` answers immediately. An explicit timeout is 0–30,000 ms; at its deadline the current record is returned, with the same token if nothing changed. Omitting the timeout waits without a timer. Tokens apply to this job in this owner process and are not persisted cursors.

Registration and re-arming use the job's token, including changes that happened before a waiter registered. A token is read before its record: a concurrent worker report may cause one extra observation, but cannot lose a change. Workers publish progress and partial updates directly to their job control; lifecycle and terminal tokens advance after the owner has stored the corresponding record and final result. Notifications coalesce to one pending wake per watched job. Waiting emits no catalog mutation event, so progress cannot displace history events.

Ownership matches `job.read`: source, analysis and other shared jobs are observed only by their requesters; capability, export and globally readable catalog jobs may be observed by any client. Unknown, evicted or inaccessible jobs return `validation`. There are at most 32 held waits globally and 16 per client, with at most 32 watched jobs and the existing 64-message owner channel; exhaustion returns `resource-limit`, with no polling fallback. Finished-record retention remains unchanged. Dropping an asynchronous wait releases its monitoring interest without cancelling the job. Disconnecting a client releases all its waits and applies that job kind's existing cancellation rule; a loopback TCP peer closing its input is detected even while its unchanged wait is held.

The desktop awaits the same command with `OwnerHandle::call_async`, which uses one bounded reply slot and an executor waker per request, without blocking an executor thread or making a waiter thread. Export, capability and followed catalog jobs use independent subscriptions per job. A visibility transition reconciles each followed job once; while hidden, only presentation progress is coalesced, and partial/business results and terminal outcomes still reach their adoption paths. Restoring reads the current record once. Visible readers send first, changed and final records and end after a terminal record or error.

The loopback transport keeps its existing maximum of eight connection threads. Each runs one current-thread socket event loop, multiplexing the owner reply with socket reads; it starts no runtime worker or per-wait thread. Pipelined input is bounded to one MiB while an answer is held. A socket EOF drops the outstanding asynchronous response and disconnects the client. Stdin/stdout uses its existing sequential JSON-lines path.

```json
{"id":"first","method":"job.wait","params":{"job_id":"job-…"}}
{"id":"next","method":"job.wait","params":{"job_id":"job-…","after":123}}
```

Use the `change` from the first response in the second request; another request is needed only after an answer, until `job.status` is terminal. The exact request schema and response contract are discoverable through `schema.list`.

## Drafts

The core holds one draft per client session, in `ClientSession.draft`, reported by `session.state`. A draft is the settings of one gesture: it is bound to one asset and one action, never outlives the session, emits no event and appears in no history. Its methods are `draft.begin {asset_id, action}`, `draft.set {draft_id, fields}`, `draft.read {draft_id}`, `draft.cancel {draft_id}`, `draft.commit {draft_id, mutation}` and `draft.reapply {draft_id}`; only `draft.commit` touches the catalog.

`draft.begin` returns `{draft_id, action, asset_id, base_revision, draft_revision, fields, conflicted}` and is refused with `conflict` when the client already holds a draft and with `validation` while the session previews a historical entry, the action is unknown, its target is one its commit would refuse — checked by the commit's own checks (`EditorService::draft_target`): a module action's `mask` by the one target check a commit and a query take, and a `mask.*` gesture's identities as a patch's are, so an undeclared one, a component on a module action included, or a missing required one is refused in the commit's words; the draft holds its target as the action's declared identity parameters by name (`DraftTarget`), and a name the action declares as a value rather than an identity is refused by name — or its commit would be refused for what the photo is: an unavailable module, or one that does not apply to the asset's source kind, in the commit's words (`validation: RAW does not apply to a JPEG photo`). `draft.set` validates every named field against the action's parameter descriptors — unknown name, non-finite, out of range or wrong kind is a `validation` error and nothing changes — and refuses, in the commit's words, a field superseded on the draft's target, such as `set-basic`'s `temperature` on a RAW photo's global target (accepted through a mask), then merges the fields and increments `draft_revision`. `conflicted` is `base_revision != the asset's current revision`, recomputed whenever the draft is read, set, committed or reported, so a commit by any client, including this client's own undo, redo or restore, marks it without a notification path. `draft.commit` refuses a conflicted draft or a `mutation.expected_revision` that is not the draft's `base_revision` with `conflict` and keeps the draft; otherwise it runs the action with the accumulated fields through the ordinary `apply_action` path and ends the draft, so a gesture that returned to its start is a `no-op` with no entry. `draft.reapply` rebases the draft on the current revision, keeps and revalidates only the fields this client set and clears `conflicted`; whatever another client changed meanwhile stays in the layer the next commit merges over. `draft.cancel` ends the draft and commits nothing. Two clients' drafts never interact. The desktop's crop frame drafts `crop` through the same lifecycle: each change's end sets the payload's declared fields, Apply commits and Cancel cancels it, and Reapply rebases it once the frame has been carried onto the new input stage.

A draft's effective recipe is the current snapshot with its action's plan applied to its fields, computed on demand by `EditorService::draft_recipe` and never persisted; a `NoOp` plan means the current recipe. A draft plans through the functions its commit plans through — `Prepared::new` and `plan_request`, for a module action and a `mask.*` gesture alike — with the request the commit will send, its drafted fields with its target's fields over them, so a draft equals its commit by construction for every module and source kind, composites included: a drafted Basic edit, Exposure on a RAW photo included, previews exactly the bytes its commit renders. Planning it costs what a commit's planning costs and allocates no frame. A complete `draft.set` whose fields ask for a colour limit, or whose stack declares spatial processing, plans read-only before accepting its fields, so a colour-limited stroke obtains its seed before its preview; other drafts keep their field-only set path. A planning read parks the request, is read by the owner's tile service and returns to the owner for identity checks and replay, once for each pixel the plans read, at most four (`resource-limit` past them). The checked key carries the asset entry and revision, draft id and revision, prefix and boundary precision, source fingerprint and RAW development. A stale answer is discarded and the request replayed once, which returns `conflict` if it needs a pixel again. Requests are recorded only after a final answer. Each session retains at most 32 pixel answers, advances them with its own accepted draft ticks and clears them at begin, reapply, cancel, commit or a change of state. A disconnect drops its parked requests and cancels its active read. `OwnerHandle::preview_job` takes a `PreviewRequest` carrying the client, the entry, an optional `layer_count` and an optional draft: the owner resolves the draft from that client's own session, the job carries the recipe to render and `draft_revision` for correlation, and another client's draft is a `validation` error. `render.sample {asset_id, x, y, draft_id?}` samples the same effective recipe and stamps the answer with `{draft_id, draft_revision}`; every answer names the `renderer` that read it.

Every evaluation the service plans — a preview job, an analysis, a sample, a point, `render.locate`, an export's plan and its job — is one bound value, `Evaluation`, built by one service method (`EditorService::evaluation`) on the catalog owner: the entry it evaluates and its stack, that entry's own or a draft's effective recipe, admitted as a stack of the photo's source kind and with its artifacts bound; the providers and the render context; the draft revision; the stack's one compilation against the content stage, kept with its reason when the host cannot evaluate it; and, once the original is prepared, the source it reads. It decides the one rule a RAW white balance is evaluated under — strict, except a drafted preview, which approximates — and so what a `preparation-required` refusal of it names. The jobs and plans wrap it and derive none of it again: a preview's worker renders the compilation the owner made for the whole frame, and compiles only a truncated job's layer prefix and, in a session without a GPU, the CPU proxy's stage. A drafted preview job is compiled once on the owner, to evaluate its effective recipe, and never on its worker: planning the draft's action, as its commit is, compiles only what its module asks of the lazy `StageContext`, and a field patch asks nothing. The desktop changes only how a planned job is presented (`intent`, `proxy`). A caller that needs only the current entry's id reads `EditorService::current_entry_id`, which copies the asset's head and no entry.

Rendering and point sampling resolve every layer's effect through the registry: `compile` runs per layer at its input stage, exact geometry composes into one mapping per segment, point replacements map through the suffix geometry of their segment, and a resample separates segments. A preview job may truncate the stack to its first `n` layers; the desktop uses that to show a crop layer's input stage while drafting. `recipe.describe` reports each row's `input_stage`, the `{width, height}` its layer receives, from one fold of the stack over the asset's extents by the compile's own rule (`ModuleRegistry::stages`, which `ModuleRegistry::describe_recipe` reads): each layer compiled at the stage it receives and an exact mapping's or resample's checked output taken as the next stage, which is what `stage_before` answers for that index. It compiles no mask and reads no pixel. After a layer whose output cannot be known (no available provider, or a payload its provider cannot compile) every later row's `input_stage` is `null`, never a guess; that layer's own is still reported. The description also carries `output_stage`, what the whole stack produces and so what a layer appended to it would receive, `null` when any layer's output cannot be known. Each row's `input_orientation` is the `{mirror, turns}` the orientation layers before it composed, and `output_orientation` the stack's, `null` exactly when the matching stage is, or after an orientation payload that cannot be read. A client reads a layer's geometry from these, as the idle crop section reads the committed crop's ratio and a crop draft opens its frame and carries it through a turn, and folds no geometry itself. `render.locate {asset_id, entry_id?, x, y}` maps one rendered pixel back through the geometry tail to the content pixel it shows, returning `{content_x, content_y, width, height}`; the desktop's canvas pick uses the same mapping to fill point-pick parameters and to give a `sample-apply` pick the content coordinates its query is run with.

## Histogram analysis

The histogram is not a recipe effect and writes no history. It is a read-only **analysis job** over the rendered SDR sRGB output of one evaluated stack, run off the catalog owner thread and keyed to an identity that says exactly which image the counts describe.

`analysis.request {asset_id, target}` returns the job as `job.read` does, promptly, with the report as its `result` when one is already kept. `target` is one of `{"kind": "current"}`, `{"kind": "entry", "entry_id"}` (a frozen historical entry, which a later commit by any client never relabels) or `{"kind": "draft", "draft_id"}` — the calling session's own draft, evaluated at the `draft_revision` it holds now; another client's draft, or one that has ended, is a `validation` error. The job is read with `job.read {job_id}`, which carries its `identity`, and cancelled with `job.cancel {job_id}` ([jobs](#jobs)). A job this client never requested is a `validation` error on read and on cancel. None of these mutates anything or emits an event, and none requires a GUI or a change of selection.

`status` is the one job-status vocabulary every job kind shares ([jobs](#jobs)):

| Status | Meaning |
| --- | --- |
| `queued` | Accepted, waiting in the worker's one replaceable pending slot |
| `running` | The worker holds it now |
| `ready` | Complete; `result` carries the report |
| `failed` | The stack could not be evaluated; `error` carries the structured reason |
| `superseded` | A newer request took the single pending slot; the requester may simply ask again |
| `cancelled` | Every interested client withdrew before the work finished |

Only `ready` ever carries a report. Queued, running, failed, superseded and cancelled results have no counts at all, so no status can be read as a valid but empty histogram.

The identity is `{asset_id, source_fingerprint, entry_id, snapshot_id, recipe_hash, draft?, width, height, domain}`. `recipe_hash` is the SHA-256 of the effective recipe's canonical JSON, `draft` is `{draft_id, draft_revision}` when a draft was analysed, `width`/`height` are the **output** stage, and `domain` is always `srgb-8bit-output`. A `failed` job whose stack has no output stage at all — an unavailable provider, or a payload the registry refuses — reports `width` and `height` as `0` and carries its error; nothing is rewritten or discarded to make such a stack renderable.

Scheduling and bounds. One analysis worker runs one active job with one replaceable pending job, globally. Requesting a third job while one is active and one pending replaces the pending one, which reads `superseded`. Identical identities share one job: a second request joins its interest set and gets the same `job_id`, so the same work is never done twice. `job.cancel` drops only the calling client's interest; the job is cancelled only when no interested client is left, and a disconnect releases that client's interests the same way. A cancel drops a job that has not started, which reads `cancelled` at once, and stops one already under way within a chunk of its render or reduction, which reads `cancelled` when its outcome arrives, whatever that outcome was. A newer request never interrupts the running job, because another client may still want it. The job table keeps at most eight reports and the last 32 finished analysis jobs, evicting the oldest first, and a report is bounded to 16 KiB. No raster is retained per result.

Building a job on the owner costs a state read, the cached verified source and an `O(layers)` plan and compile to learn the output stage; the render and the reduction happen on the worker. The worker is one persistent thread on the same latest-job primitive as the preview (`luxforge_core::latest`): it starts the pending job itself when the running one ends and wakes the owner through the owner's own channel when an outcome is ready, so nothing polls and no timer is added.

Preview reuse. `PreviewJob.analyse` (via `PreviewRequest::analyse()`) makes the preview worker reduce the frame it just rendered and return the `Report` beside the raster, with the job's `AnalysisIdentity` for correlation. The desktop hands that report to `OwnerHandle::submit_analysis(identity, report)`, and an `analysis.request` for the same identity is then a cache hit: a displayed target is never rendered twice. A preview job's identity is its evaluation's, computed exactly as an analysis job's is; a truncated job (`layer_count`) renders a layer prefix its identity does not describe and cannot be analysed.

Overlays. `workspace.set` accepts `clip_shadows` and `clip_highlights` booleans and `session.state` reports them; they are per-client view state and change no raster, recipe, histogram population or export. The display overlay itself is derived from the same final raster by `analysis::overlay(rgba, width, height, cells_w, cells_h)`, which ORs the shared `clip_class` predicate over every source pixel of each display cell — one byte per cell, `0` none, `1` shadow, `2` highlight, `3` both — so an isolated clipped pixel survives a Fit reduction and a cell grid equal to the image is one to one. No full-resolution mask is allocated; the grid is bounded to 4096 cells a side.

## Registry

The registry a run serves is assembled in one place, `ModuleRegistry::assemble(&RegistryOptions { disabled, developer, proof_endpoint })`, which the desktop and `luxforge-json` both call. It registers the linked modules — presets, the pixel proof, RAW, Basic, the Tone curve, presence, mixer, transform, crop, the vignette and the controls proof, in that order — except that a module whose descriptor declares `developer` (a test module: the pixel and controls proofs) joins only a developer run, and the capability proof joins only a developer run that names a proof endpoint. A proof endpoint outside developer mode is refused (`--proof-endpoint requires developer mode (--developer)`), as is a `disabled` identity the run does not serve (`--disable-module names no registered module: <id>`), in the same words from both binaries; the `registry-assembly` repository rule keeps a second assembly out. `ModuleRegistry::builtin()` is the ordinary run's registry, the product modules only, and `ModuleRegistry::developer()` a developer run's without a proof endpoint, which the tests that reach a proof use. What the ordinary registry publishes — `module.list` with its `host` array and every method `schema.list` generates from the descriptors — is committed once as a snapshot ([built-in descriptor snapshot](../engineering/development.md#the-built-in-descriptor-snapshot)), so registering a built-in module changes that file and no hand-kept list. `register_unavailable(module, reason)` registers a module with its descriptor, effects, actions, queries and tasks exactly as `register` does and its availability `unavailable {reason}`, which the registry keeps on its own entry: every lookup hands out a `Provider`, the module with the descriptor the registry publishes for it, and the host reads that availability before any of the module's methods runs, so none runs for an unavailable module. The assembly's `disabled`, the binaries' `--disable-module ID`, uses it, and no client keeps a wrapper of its own. The presets module declares no effects, so it owns no layer; a module without effects registers like any other. The Tone curve's colour-stage effect declares order 5 and the mixer's order 10, so a committed curve layer always follows the Basic layer and a committed mixer layer follows both in the colour run whichever was touched first, and presence declares the spatial stage, so its layer follows all of them whichever was touched first. The crop's geometry effect declares order 10 too, so the orientation layer is always placed ahead of the crop and the crop's input stage includes every transform. `register` accepts any `ToolModule` and rejects: an invalid module, effect, action or query identity; a duplicate module, effect, action or query ID; a control naming an undeclared action or parameter; a module, group or number-control reset naming an action this module does not declare, or a preset field its action does not declare or cannot accept; a canvas interaction naming an undeclared action, query or coordinate parameter, or a coordinate parameter of the wrong kind; a preset or default outside the parameter's range; a parameter without a kind; a canvas shortcut letter another module already claims; an action `shortcut` without `Command`, on an action with a required parameter, on a query, declared twice, already claimed by another module's action, or one the host keeps for its own commands (`luxforge_core::HOST_CHORDS`: copy and paste settings, select all and none, find, undo and redo, open, the palette, export, Settings, zoom and the panel toggles, each with the modifier combinations the desktop answers; a desktop test presses every Command chord in every workspace and holds the keyboard table to that list); a `picker` without a pick canvas, more than one `picker` in a module, or a pick canvas without a `picker`; a `string` bound outside 1..=256; an effect that lists a source kind twice; a `presets` control whose action is undeclared, a patch or not shaped exactly as that control requires, or more than one `presets` control in a module. Queries and tasks have their own identity namespaces, because `query.<id>`, `task.<id>` and `edit.<id>` are different methods; a task identity is unique across the registry. Registration also runs every capability declaration rule. It builds hash lookups from descriptors only and touches no image, catalog, settings, keychain, network or model resource. A module that needs an expensive resource initializes it on first `compile` or `plan`; registration and first-use costs are measured separately.

The desktop and `luxforge-json` register `luxforge.capabilities`, the capability proof described in [module capabilities](module-capabilities.md#proof-module), only with `--developer --proof-endpoint URL`, and the pixel and controls proofs only in developer mode. The desktop is in developer mode automatically in debug builds and with an explicit `--developer` in optimized builds; `luxforge-json` only with `--developer`, whatever its build, so an agent's `schema.list` never depends on the build profile. `luxforge.controls` is a field-patch module like Basic, with a field of every non-numeric kind beside its numbers, and declares the complete delivered control vocabulary over `edit.set-controls`, its field patch, plus the non-patch module reset `edit.reset-controls`; its one group's reset is the patch of every field to its default. Its two-channel curve query returns 257 piecewise-linear samples. The stored colour-stage layer compiles to identity and shares unchanged source pixels. Outside developer mode every test module and its methods are absent, which the committed descriptor snapshot shows; a catalog containing a layer of one reports an unavailable provider explicitly.

## Developer workspace

The developer components gallery is the desktop's own view state, not core session state: which
page is shown is held by that desktop, and neither `workspace.set` nor `session.state` carries it
(a `component_gallery` field is refused as unknown). It requires no asset, changes no recipe and
submits no request or rendering job. Normal optimized desktops keep the diagnostic button and
board hidden; debug builds and `--developer` runs expose them.

## Missing effects

A layer whose derived artifact is missing, corrupt or in a directory that belongs to another catalog stays in every snapshot unchanged too; rendering, sampling and analysis of its stack fail with `source-unavailable` (or `incompatible` for a foreign directory) naming the artifact, and history keeps working ([derived artifacts](module-capabilities.md#derived-artifacts)).

Layers whose effect has no available provider stay in every snapshot and entry unchanged. `state`, `history.list`, `history.inspect`, undo and redo keep working. Rendering, sampling, appending an edit and restoring such a stack fail with `incompatible: unavailable effect <id> (layers …)`, whose `data` is `{effect_id, layers}`; every producer of the refusal builds it through `Error::unavailable_effect`, and a module's own payload check refuses a foreign effect the same way with `data.effect_id`. A client names the missing provider from `data.effect_id`, never from the message: the desktop's stale-preview notice does. A cached preview may only be shown with an explicit stale or unavailable label. Registering a compatible provider again restores evaluation without touching stored data. Removing an edit is a separate explicit action that does not exist yet.

## Current formats

Each module accepts only its current effect format and payload shape. Unsupported formats fail explicitly without modifying the stored recipe. Breaking shape and algorithm changes are expected during pre-release development; tests target the current contracts.

## Outstanding query attribution

The neutral picker's `query.neutral-sample` answer must identify its renderer and reference-fallback reason, as `render.sample` and `mask.sample-input` do (owner, 2026-10-07). This response field is required but not implemented: the current module answer contains Temperature, Tint and patch samples only. A session's renderer alone cannot identify the provider that answered a particular read.

## Resources and external loading

Registration is cheap and expensive resources initialize on demand: a module that needs a model or other heavy state declares a pinned resource, which the host installs only when a client asks and a task reads on its worker; loading it once ahead of its tasks is activation, deferred until a module needs `local-runtime` ([module capabilities](module-capabilities.md)). Start with linked built-ins. Hiding controls is a UI preference, not effect removal, and persisted processing order never depends on panel order.

External loading remains required later: a separately authored tool must load without editing host source and expose its actions through the same APIs. Before implementing that loader, select a use case, measure startup, first-use, memory and idle costs, and define trust, dependencies, cancellation and packaging. A processing module supplies its exact-fixture CPU reference unit and module-owned WGSL program, qualified on corpus stacks by `gpu-qualification --manifest FILE --output NEW_DIR` within the declared GPU tolerance. Spatial modules carry their windows, halos, staged sweeps and incremental change propagation; the loader proof preserves pixel reads through the host tile service and exports through the GPU tile worker with the reference fallback, without adding a GPU dependency to the core. Activation measurements include shader compilation and warm-up on the surface and tile-worker devices, as well as disabled and enabled-but-unused states. Native binaries, workers or sandboxed runtimes are all still options; a marketplace and hot unload are not requirements. Later operations such as exposure, white balance, masks, clone strokes or presets must carry enough structured data to reproduce their results. Keep geometry and color stages explicit and do not prebuild a generalized graph.

A `crop-frame` canvas explicitly names its owned geometry `effect`; registration refuses a foreign or non-geometry effect. The desktop opens and edits that layer, independent of other geometry effects the module owns or their descriptor order.

## Acceptance

Descriptor validation rejects duplicate identities, missing handlers, invalid controls and unavailable providers explicitly. Pixel and transform actions invoked through generic controls and an independent API client produce identical stacks, history, pixels and errors. Current-format catalogs reopen with their IDs and undo/restore paths intact. Registration and first-use resources are measured separately. Real native M4 control layout, keyboard behavior and pixels are inspected with correlated state. Every module in the field-patch shape passes one [conformance suite](../engineering/development.md#the-field-patch-conformance-chapter), found from the registry and fed payloads derived from its field table, in `cargo test` and in release inside `editor-acceptance`.

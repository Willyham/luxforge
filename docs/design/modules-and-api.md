# Tool modules and the shared core

Status: implemented (M3, M4). The presets, pixel, RAW, Basic, presence, mixer, transform, crop and vignette tools are the built-in modules; the controls proof is registered only in developer mode, and the capabilities proof only in developer mode with a proof endpoint; the host owns everything a module does not declare here. Settings, provider profiles, secrets, consent, activation, resources, worker tasks and derived artifacts are the [module capabilities](module-capabilities.md) contract; this page lists only where they meet the descriptor, the trait and dispatch. The registry, descriptors and built-in modules live in `crates/lightwell-core/src/modules/`; the desktop models them in `crates/lightwell-app/src/state/` and renders them in `crates/lightwell-app/src/view/`, and the crop-frame editor's own draft and canvas live in `crates/lightwell-app/src/crop_draft.rs` and `crop_canvas.rs`.

An operation is semantic and programmable: set one pixel, rotate, set crop parameters, restore history, select a preview or change view state. Scripts never simulate pointer movement. Exposure, masks, clone strokes and lifecycle actions inherit this rule when they arrive.

## Ownership

| Owner | Responsibility |
| --- | --- |
| Host (`lightwell-core`) | Asset identity, shared invariants, atomic recipe and history commits, revisions, undo/redo/restore, request deduplication, the decoded-source cache, one-pass rendering of compiled processing, preview jobs, notifications, API discovery and dispatch; module settings, secrets, grants, the capability worker, installed resources and derived artifacts |
| Module (`lightwell-core::modules::*`) | Its descriptor (identity, effects, actions, parameters, controls), input parsing, state validation and no-op detection, payload validation and compilation of its payloads into host processing primitives |
| Desktop (`lightwell-app`) | Layout, styling, focus, text editing, gesture capture; renders controls, including the `crop-frame` canvas editor, from descriptors and calls the declared actions through the same API every client uses; holds no authoritative state |

Module code never writes catalog tables, never keeps an undo stack and never renders. Preview, undo and restore never ask a module to reverse pixels: a snapshot is evaluated from original pixels and its ordered payloads.

## Descriptor

Every module returns one `ModuleDescriptor` from `descriptor()`. It is plain data, cheap to build and serializable, and it is the single source of API discovery, GUI controls and validation limits.

| Field | Meaning |
| --- | --- |
| `id`, `title` | Stable provider identity, e.g. `lightwell.pixel`; lowercase ASCII words separated by dots |
| `hint`, `collapsed`, `developer`, `layout` | Section hints for clients: the one-line description under the title, whether the section starts collapsed (a person's own expand or collapse still wins), whether the module is a developer tool hidden outside developer mode, and how a client arranges the module's top-level controls — `stacked` (the default) or `tabs`. `tabs` is validated at registration: the module must declare at least two top-level controls and every one of them must be a group. None of them changes the API |
| `effects[]` | `id` (durable effect identity stored in every layer, e.g. `lightwell.pixel.replace`), `format` (internal payload format marker), `stage` (`source`, `pixel`, `color`, `spatial`, `geometry` or `finish`) and `order` (a `u16`, default `0`, always reported), which together decide where the host puts a new layer of that effect, `artifacts` (default `false`): only a layer of an effect that declares it may list derived artifacts, and `single` (default `false`, listed only when true): a stack holds at most one layer of the effect per target. Every delivered photo effect declares no artifacts, and order `0` except the mixer's `10` and the crop's `10`; Basic, Presence, the colour mixer, the vignette, the crop and both proof modules declare `single`; and `maskable` (default `false`, listed only when true): the host adds its optional `mask` target field to every action of the module, as [masking](masking.md) describes. Basic, the colour mixer and Presence declare it |
| `actions[]` | `id` (unique across all modules, e.g. `set-pixel`), `title`, `notes`, `summary`, `patch`, `parameters[]` |
| `queries[]` | Optional read-only questions about a stored stack, declared and validated exactly like an action: `id` (unique across all modules' queries), `title`, `notes`, `parameters[]`. A query mutates nothing, writes no history entry and emits no event. The Basic module declares `neutral-sample {x, y}` |
| `parameters[]` | `name`, `kind`, `required`, `default`, `unit`, `step`, `precision`, `soft_min`, `soft_max`, `fine_step`, `zero`, `notes`. Kinds: `integer {min, max}`, `number {min, max}` (finite f64), `enum {options[]}`, `color` (three 8-bit sRGB channels), `boolean`, `artifact` (one `artifact-…` identity; the commit checks the catalog holds it), `curve {points_min, points_max, monotone, fixed_x?}` (ordered `[x, y]` fractions, at most 32 points), `string {max_length}` (text of at most `max_length` characters, `max_length` at most 256, no control characters; emptiness is the module's to refuse) `settings` (a [settings set](presets.md#settings-sets): 1 to 16 field-patch action identities, each with a non-empty object of at most 64 validly named fields; the generic check validates only this shape), and two kinds only a [module setting](module-capabilities.md#configuration-contract) declares, which registration refuses on an action, query or task: `endpoint {classes[]}` (a URL of at most 4096 bytes the capability transport accepts as one of `remote` or `loopback`, never with a default) and `secret {max_length}` (a credential of at most 4096 characters held only by the OS secret store; no plain value is valid and it never has a default); and `identity {of}`, which only the host declares, for its own objects' commands, and which registration refuses on a module's action, query or task and on a setting: one host object's identity — `mask`, `component` or `stroke` — checked by that identity type's own parser. A required identity stays required on a patch, because it says which state the patch merges over, and no control edits one. Enum options are non-empty and distinct. Steps and display precision (at most 6 decimals) are hints for numeric and curve controls. Numeric soft bounds stay inside hard bounds; an omitted bound uses the hard bound. `fine_step` must be positive; `zero` stays inside the hard bounds. Hints never round or clamp a request: the host validates and stores the exact value sent |
| `controls[]` | Ordered semantic controls: `group {label, controls[], reset?, collapsed?}`, `number {action, parameter, label, style?, rail?, reset?}` (integer or number; slider, field or stepper), `toggle {action, parameter, label}` (boolean), `choice {action, parameter, label, style?}` (enum), `color {action, parameter, label, style?}` (fields or picker), `curve {action, channels[{parameter, label}], label, sample_query, background?}` (curve parameters), `action {action, label, preset?, style?, icon?}`, `picker {label}`, `presets {action}` and `task {task, label}` (runs a declared task through the consent and progress flow and offers Apply with its artifact when the task declares `apply`). A picker enters this module's own `point-pick` or `sample-apply` mode through `workspace.set`. A presets control is where the host renders its preset library; its action is this module's own, not a patch, and declares a required `settings` parameter of kind `settings`, a required `name` of kind `string`, optionally a non-required `preset-id` of kind `string`, and nothing else, and a module declares at most one. Omitted styles use the documented defaults. Rails are plain, hue, temperature, tint or a gradient of 2–8 RGB stops. A number control's `reset` is what resetting that one field runs — a double-click on its label or rail, or its field's own reset — as an `{action, preset}` of this module, the shape a group's and the module's resets use; it is listed only when declared, and without it the field resets to its parameter's declared default. RAW's Custom temperature and Custom tint declare `{action: use-as-shot-wb, preset: {}}`, so resetting either returns the development to the camera's white balance. A curve's `sample_query` declares each channel as an optional parameter without a default; the host sends only the active channel's points and uses the module's `{points: [[x, y], …]}` result for the plot (2–1024 finite, increasing-x fraction pairs). An action button on a patch action requires exactly one preset field. Icon names are lowercase hyphenated; an unknown valid name falls back to the label |
| `canvas` | Optional, and the mode's `title` and optional one-letter `shortcut` travel with it. `point-pick {action, x, y}`: a pointer pick on the image fills the named integer parameters of that action and never commits. `sample-apply {query, x, y, action}`: a pointer pick maps through `render.locate` to the content pixel, runs `query` with those coordinates and, when it answers, submits once to `action` every top-level number field of the result whose name is a parameter of `action`; a refused query commits nothing and its reason is shown. `crop-frame {action, angle, x, y, width, height, fit_action, aspect}`: the host's crop-frame editor edits a transient draft of the named number parameters of `action` and derives its ratio presets from the `aspect` enum of `fit_action`; only Apply calls the action. A `point-pick` or `sample-apply` module declares exactly one `picker` control; a `crop-frame` module declares none |
| `availability` | `available` or `unavailable {reason}`; an unavailable provider keeps its descriptor and effect identities |
| `settings`, `capabilities`, `resources`, `activation`, `tasks` | Optional capability declarations, all empty by default and omitted from JSON when empty: typed module settings and provider profiles with adapters, the `remote-image-request` and `download-artifact` capabilities, pinned resources, an activation's requirements, and worker tasks with their parameters, uses and optional `apply` action. Their shapes and every registration rule are in [module capabilities](module-capabilities.md#configuration-contract); declarations carry no values and never a secret |

API method names are generated: action `set-pixel` is `edit.set-pixel`, query `neutral-sample` is `query.neutral-sample`, and task `generate-proof-tint` is `task.generate-proof-tint`. Parameters are top-level request fields beside `asset_id` and, for an action, `mutation`. A query takes `asset_id`, an optional `entry_id` that defaults to the session's selection as `render.sample` does, and its own declared parameters; it is non-mutating, so a client previewing a historical entry may run one. `schema.list` lists generated action, query and task methods with their parameter descriptors, and `module.list` returns every descriptor, queries, tasks and capability declarations included. Beside `modules`, both answer `host`: the descriptors the host publishes for its own objects in the same shape — today one, `lightwell.masks`, whose actions are the `mask.*` commands, whose queries are `mask.list` and `mask.sample-input` and whose controls are the Masks panel's widgets. A host action or query is called by its own identity (`mask.create-linear`), which already carries its family's namespace. There is no hand-maintained list of module or mask methods. A task method takes the `request` mutation envelope, `asset_id` and `profile_id` when the task declares them, and its own parameters; it checks requirements and grants on the owner and answers a job, and a retry answers the first job (see [lifecycle](module-capabilities.md#lifecycle-jobs-and-resources)). A control the desktop cannot render shows an explicit unsupported-control message with the descriptor's kind; it is never silently dropped.

## Module trait

```text
descriptor()                             -> &ModuleDescriptor
parse(action_id, input)                  -> ActionInput { action_id, parameters }
plan(&ActionInput, &StageContext)        -> ActionPlan::{NoOp, Commit(NewLayer), Update(LayerUpdate), Edits(edits), Compose(steps)}
validate_payload(effect_id, format, payload)
describe_layer(effect_id, format, payload)               -> String
is_neutral(effect_id, format, payload)                   -> bool
label(&ActionInput)                                      -> Option<String>
values(effect_id, format, payload)                       -> Map<String, Value>
query(query_id, parameters, &StageContext)               -> Value
compile(effect_id, format, payload, Stage{width,height}) -> Processing
capabilities()                                           -> Option<&dyn CapabilityModule>
```

A module that declares worker tasks, an activation, managed resources or an effect with `artifacts: true` also implements `CapabilityModule` and returns itself from `capabilities()`; every other module keeps the default `None` and implements nothing more. Registration refuses a module whose declarations need the capability hooks and that provides none, naming the declaration.

```text
compile_bound(effect_id, format, payload, stage, &[PreparedArtifact]) -> Processing
activate(&ModuleContext) / deactivate()
validate_resource(resource_id, &Path)
run_task(task_id, parameters, &ModuleContext)             -> Value
```

- `parse` validates the request against the schema only and normalizes it. The returned `action_id` is the durable history action identity (`set-pixel`, `rotate-left`, `mirror-horizontal`, ...) and `parameters` is the object stored on the history entry. The host also checks required parameters, integer and number ranges, colors, enum options, booleans and curve constraints generically before calling `parse`, so every caller gets the same structured `validation` error.
- `plan` sees a `StageContext`: the current output stage (`width`, `height`), the current ordered layers, `stage_before(i)`, the stage the layer at index `i` receives, `insertion_index_for(effect_id)`, where the host would place a committed layer of that effect by its declared stage and order, `sample_before(i, x, y)`, one pixel of the stage the first `i` layers produce, `sensor_neutral(x, y)`, a RAW original's pre-white-balance sensor patch, and `own_layer(effect_id)`, the module's own layer for the plan's target. The context is lazy. The host compiles the output stage from the source's dimensions before the module is asked anything, which also refuses a stack that cannot compile, and answers the rest only when asked: a prefix stage by compiling that prefix, and the first question that reads a pixel or the sensor by looking up the verified source, and for a RAW stack its linear settings, strictly, once per plan (the questions that compile a prefix or read pixels are the `StageQuestions` trait the host implements). A plan that reads no pixel — a transform, a crop, a field patch, a RAW exposure or white balance — therefore needs neither the original prepared nor a development at the stack's white balance, and one that samples is `preparation-required` exactly when it samples. So a module plans against the stage its layer will actually receive. It rejects out-of-stage coordinates and reports no-ops; it allocates no frame and mutates nothing. A plan names only what the module decides: `Commit` names an effect and a payload (`NewLayer {effect_id, payload, artifacts}`, the artifacts only for an effect that declares them), and `Update` names a layer and its new payload (`LayerUpdate {id, payload, artifacts}`). The host owns the rest of a layer's identity: a committed layer gets a new identity, the format its effect declares and the request's mask target, and an updated layer keeps its identity, effect, position and mask while the host writes its effect's declared format, so no module can drop, move or invent a mask. A commit of an effect no provider declares is refused with `incompatible: unavailable effect <id>`. The host places a committed layer by the effect's declared stage and order:

  | Stage | Where a committed layer joins the stack |
  | --- | --- |
  | `source` | index zero |
  | `pixel`, `color` | before the first spatial, geometry or finish layer, so the geometry tail carries the edit |
  | `spatial` | before the first geometry or finish layer, after every pixel and colour layer |
  | `geometry` | before the first finish layer |
  | `finish` | at the end, in the output coordinates the geometry tail produced |

  A leading source layer always keeps index zero. Within the region its stage chooses, the new layer goes after the last layer of the **same** stage whose `order` is at most its own and before the first whose order is greater; layers of other stages in that region keep their positions. No existing layer ever moves, so two effects of one stage land in their declared order whichever was committed first.

  `Update` replaces the payload and artifacts of the layer with that identity in place, which is how the crop module edits its existing layer and the transform module folds an action into the orientation layer ahead of the crop without changing history identities. The host rejects an `Update` whose identity is not in the stack. Recipe validation does not reject other orders, and a stack renders by its stored order whatever it is, with one exception: a stored stack in which a finish layer precedes a geometry layer has no stage the finish effect could address, so compiling it — and therefore rendering, sampling and planning against it — fails with `validation: finish layer precedes geometry` naming both layers. Nothing is rewritten or reordered and the stack stays readable through `recipe.describe` and history.

  `Edits(changes)` applies several `Commit` and `Update` changes, in order and each by its own rule, as this one action, and commits the final stack once; it is never empty. The transform module returns it for a transform over a crop: the orientation ahead of the crop is committed or updated, and the crop is updated so it frames the same content in the turned stage ([orientation layer](orientation-layer.md#carrying-the-crop)). The host compiles the final stack before persisting, as for any plan.

  `Compose(steps)` applies other actions, in order, as this one action; the presets module's `apply-preset` is the one that returns it ([composite actions](presets.md#composite-actions)). The host runs each step exactly as that action would run alone, against the stack the steps before it produced: the action must be registered, a field patch and provided by an available module (otherwise `validation: unknown action X`, `validation: X is not a field-patch action` or `incompatible: unavailable module M`), its fields go through the generic check and the module's `parse`, and the module plans against the intermediate stack through the same plan path a single action takes. A step whose plan is itself a composite is refused with `validation: composite actions do not nest`, and more than 16 steps are refused. Any refused step refuses the whole action before anything is written. A final stack equal to the starting one is a no-op; otherwise it is committed once, as one entry storing the composite action's own identity, label and parameters. Planning costs O(steps × layers) and rasterizes nothing.
- `validate_payload` accepts or rejects a persisted payload structurally. `compile` turns it into a host processing primitive at its input stage. The capability hook `compile_bound` is called instead for a layer whose host-owned `artifacts` list is not empty, with the verified bytes of each listed artifact in order; its default ignores them and calls `compile`.
- The capability hooks `activate`, `deactivate`, `validate_resource` and `run_task` run only on the capability worker, never on the owner or UI thread, and receive only what the host checked through a `ModuleContext`: effective setting values, the secrets the module declares, installed resource paths, scoped file reads, host-built adapter sends, artifact publishing, progress and cancellation. Each has a default on `CapabilityModule`, so a capability module implements only the hooks its declarations use.
- A `single` effect is one a module owns exactly one layer of per target, because it could not say which of two holds its state; the global layer and each mask are distinct targets of a maskable effect. Compiling a stack that holds two layers of a `single` effect for one target fails with `validation: ambiguous <module title> layers` (`ambiguous Basic layers`, `ambiguous Crop and straighten layers`); nothing is rewritten and the stack stays readable. A module finds its one layer through `StageContext::own_layer(effect_id)`, the host's one lookup (`ModuleRegistry::own_layer`): it returns the layer of that effect that belongs to the target the plan or query addresses — a masked layer of a maskable effect only for its own mask, every other layer for every target — with its index, and refuses two with the same words. Every field-patch module, the crop, both proofs and a preset's capture use it. The transform's orientation effect is not `single`: folding an orientation stored after the crop leaves that layer neutral in place beside the one ahead of the crop ([orientation layer](orientation-layer.md)).
- `is_neutral` says whether a stored layer changes nothing, reading the payload only: a field patch by its own rule (every field at its default; the vignette at amount 0), the crop at the whole image unstraightened, the orientation at the identity and RAW at As shot and 0 EV. The default is `false`, because a payload with no neutral form, such as a pixel replacement, is always an edit. `recipe.describe` reports it as `neutral` on each layer's row (`ModuleRegistry::layer_neutral`); a layer whose provider is missing or unavailable, or whose payload the provider cannot read, is not neutral. A client's edited mark reads it rather than parsing a payload.
- `label` names the history entry a request deserves when the `summary` template cannot say it, such as a patch naming the one field it changed; the host consults it before the template and the title. `values` reports the parameter values a stored layer represents, which `recipe.describe` returns on that layer's row so a client can seed its controls from the displayed entry. Both read the request or the payload only: no render, no sample, no source. Both have defaults (`None` and an empty object), so a module declares them only when it has something to say. The crop module reports `angle`, `x`, `y`, `width` and `height`. The RAW module reports `ev`, `kelvin` and `tint`, the single parameters of its three sliders' actions: a custom temperature and tint as stored, and otherwise the temperature and tint whose gains are the gains in force — the camera's as-shot gains under As shot, or a neutral pick's — solved from the payload's gains and camera matrix; the temperature and tint actions keep the one they do not name at that same value (the payload itself stores no Kelvin value for As shot; see [initial RAW](initial-raw.md#minimal-controls-and-shared-basic-integration)). Its explicit gains have no control and are not reported.
- `query` answers one declared read-only question. The host resolves it from the same registry discovery lists, checks its parameters through the same generic check, and asks it through the same plan path an action is planned through, so a query sees exactly the stage a commit would address: point samples only, no frame and no catalog write. The default refuses with `validation: module <id> declares no queries`. `EditorService::run_query` is the read-only counterpart of `apply_action`, so a query and a commit can never disagree about which stage a coordinate names.

There is one plan path. `EditorService::ask` asks a module one question about one stack for one target: it refuses an unavailable module (`incompatible: unavailable module <id>`), checks the stack against the asset's source kind, binds its artifacts, refuses a mask target the stack does not hold, and hands the module the stack of that target through the lazy `StageContext`. `EditorService::plan_action` plans an action through it and resolves the plan into the stack it produces, or a no-op; a commit, a draft's effective recipe and each composite step plan through them, and a query is answered through `ask`. No module is special: the RAW development updates its source layer through the same path, and no plan can move or add one, because compiling refuses a source-stage layer anywhere but index zero and a RAW stack must hold exactly one.

Every action — a module's and a host `mask.*` command alike — resolves through the registry's one action lookup, `ModuleRegistry::resolve_action`, as `ActionRef::Module(module, action)` or `ActionRef::Host(command)`, and runs through one path, `EditorService::run_action`: `Prepared::new` resolves it, takes a module action's host `mask` field out and checks its parameters with the one generic check (a module then parses them); the request identity is built once; `EditorService::plan_request` plans it — a module action through `plan_action` above, a mask command through `plan_mask_command`, which rewrites the mask table and reads a pixel only for a stroke limited to a colour — and `mutate` admits and commits it. A draft's effective recipe is prepared and planned through the same two functions with the request its commit will send, so a draft equals its commit by construction for both. Queries resolve the same way (`resolve_query`, `QueryRef::{Module, Host}`), and `run_query` answers the host's `mask.list` and `mask.sample-input` beside a module's.

### Field patches

An action may declare `patch: true`. The generic check then validates the fields the caller sent and fills no declared default, so the module receives exactly those fields and merges them over the state it already holds; omitted fields are preserved by that merge, unknown fields are still rejected, and every parameter is optional however it is declared (`schema.list` lists them all as optional). The history entry stores the patch as sent, not the merged payload, request deduplication covers the patch as sent, and a patch that changes nothing is a no-op with no entry. Defaults stay declared on patch parameters because clients seed and reset fields from them.

Basic, the colour mixer, Presence and the vignette are each one declarative field-patch module (`modules/field_patch.rs`). A module declares a spec — its identity, its one effect, its `set-<name>` patch and `reset-<name>` action, and a field table giving each field's name, slider label, history name, range, default, step, display precision, unit, rail, zero hint and notes, grouped into its sections with their layout — and provides only `compile` over the payload's canonical values, optionally its own neutrality rule and optionally its queries. The shared module builds the descriptor from the spec and implements everything else once: a payload is a JSON object in which a missing key is that field's default, so a set merges the sent fields over the stored values or the defaults (planning does not check again the ranges the host's generic check already ran) and stores the canonical payload, which holds only the fields that differ from their defaults, so the all-default payload is `{}`; a first set whose merge is neutral commits no layer, a later one updates the layer in place, and a merge equal to the stored values is a no-op; `values` reports every field with defaults filled; a stored payload is refused by effect, format, shape, unknown field, non-finite value and range. A history label names the one field a patch moved with its declared decimals and unit, signed when the field's range is (`Exposure +0.50 EV`, `Red hue +20`, `Vignette midpoint 60`), `Reset <group>` for a patch holding exactly one group's fields at their defaults, `<title> (N fields)` for any other patch and `Reset <title>` for the reset action. A recipe row reads `Neutral` for the all-default payload and otherwise lists the fields that differ from their defaults, labelled the same way. The neutrality rule defaults to every field at its default; the vignette's is `amount == 0`. Basic's one query is its neutral picker.

The Basic module (`lightwell.basic`) owns the one colour-stage effect `lightwell.basic.adjust`, format 1, and is edited through `set-basic`, a field patch over the implemented Basic parameters, and `reset-basic`, which returns that layer to neutral. A payload is a JSON object whose keys are the implemented parameter names; a missing key is neutral, so the canonical neutral payload is `{}` and `{"exposure": 0}` is the same state written differently. Its fields are White balance (`temperature`, `tint`), Tone (`exposure`, `contrast`, `highlights`, `shadows`, `whites`, `blacks`) and Colour (`vibrance`, `saturation`); their ranges, equations and fixed internal order are in [Basic adjustments](basic-and-histogram.md), [Basic white balance](basic-white-balance.md) and [Basic Tone](basic-tone.md). The first non-neutral set commits the layer at the colour insertion index, before the geometry tail, and every later set updates it there in place.

The colour mixer module (`lightwell.mixer`) owns the one colour-stage effect `lightwell.mixer.hsl`, format 1, declared order 10 so a committed mixer layer always follows the Basic layer, and is edited through `set-mixer`, a field patch over its twenty-four `<range>-<property>` parameters (hue, saturation and luminance for each of the eight colour ranges red, orange, yellow, green, aqua, blue, purple and magenta), and `reset-mixer`, which returns that layer to neutral. The payload follows the same field-patch shape as Basic's: a missing key is neutral, so `{}` is the canonical neutral payload. The module compiles its payload into one `PointwiseColor` unit implementing the frozen equations in [the mixer study](mixer-study.md); a neutral payload compiles to no units, keeping the identity byte path and the shared source buffer.

The Presence module (`lightwell.presence`) owns the one spatial-stage effect `lightwell.presence.adjust`, format 1, and is edited through `set-presence`, a field patch over `texture`, `clarity` and `dehaze` (each −100..100, step 1, neutral 0), and `reset-presence`, which returns that layer to neutral. The payload follows the same field-patch shape as Basic's: a missing key is neutral, so `{}` is the canonical neutral payload. Because it declares the `spatial` stage, the first non-neutral set commits the layer after every pixel and colour layer and before the geometry tail, and every later set updates it there in place. The module compiles its payload into one `Spatial` operation whose units run in the frozen order dehaze, texture, clarity, implementing the equations, radii and halos in [the presence study](presence-study.md); a unit whose amount is 0 is the exact identity, so it is left out of the operation entirely and its halo and its work go with it, and a neutral payload compiles to no units at all, keeping the identity byte path and the shared source buffer. Dehaze declares the one global estimate in this design, an atmospheric light of three `f64`; texture and clarity declare none. The summed halo is 274 px at a 24 MP stage and 448 px at 60 MP and above, inside the host's 512 px bound.

The Vignette module (`lightwell.vignette`) owns the one finish-stage effect `lightwell.vignette.postcrop`, format 1, and is edited through `set-vignette`, a field patch over `amount`, `midpoint`, `roundness` and `feather`, and `reset-vignette`, which returns that layer to its all-default payload. Unlike Basic, a missing key does not mean 0: it means that field's own default (amount 0, midpoint 50, roundness 0, feather 50), so the canonical all-default payload is still `{}` but `{"midpoint": 50}` is the same state written differently, not the same as an empty payload for every other field. The layer as a whole is neutral — compiles to no processing and keeps the identity byte path — exactly when `amount` is `0`, whatever `midpoint`, `roundness` and `feather` hold, because the frozen mask geometry never affects the output when the amount equation is itself the identity. Because it declares the `finish` stage, the first non-neutral set commits the layer at the end of the stack, after the geometry tail, and every later set or crop that runs after it updates its own position or recentres its mask on the new output stage, in place.

Processing primitives are the closed host set for v0: `ExactGeometry` (an integer mapping with declared output size, composable into one raster pass), `PointReplace` (one input-stage pixel, applied through the geometry that follows it), `Color` (pointwise colour over the whole stage), `Spatial` (a bounded neighbourhood of the whole stage) and `Resample` (an affine map from output pixel centers to input coordinates with a declared output size, sampled bilinearly in linear light with edge clamping, as defined in the [crop contract](../specs/single-image.md#sampling)). A resample and a spatial operation are both stage boundaries: the exact layers before one rasterize into one bounded intermediate frame, the boundary writes the next frame, and exact layers after it compose as before. A point replace whose pixel falls outside a later crop is simply not visible. There is no generalized graph.

A `Color` operation is an ordered list of at most eight `PointwiseColor` units. The module owns each unit's equation and declares whether its coefficients are finite; the host owns everything else. A unit's `apply_row(y, x0, rgb)` carries the position of the row it is given: `y` is the row and `x0` the column of the first pixel, in the coordinates of the stage its segment produces, and the slice is always one contiguous run of that row. A unit that does not depend on position ignores both; every delivered unit does except the vignette's. The rasterizing pass, `render.sample`, the byte point path and the RAW linear path address the same coordinates, so a sample equals the rendered byte for a position-dependent unit as well. Only a stage whose input is its output — a finish-stage layer after the geometry tail — sees the coordinates its own payload was written in; a colour layer before a transform is still evaluated in the transformed frame, which is why position-dependent effects declare the `finish` stage. The host decodes each channel into f32 linear sRGB (D65) through a 256-entry table computed in f64, hands rows to every unit of every operation of a run in order, and only at the end of that run clamps to `[0, 1]` and quantizes to the code whose exact linear threshold interval holds the value, which equals `floor(255 · encode(v) + 0.5)`. Values outside `[0, 1]` and negative values are preserved between units and between consecutive operations, so an inverse pair returns its input bytes; alpha is never touched. A point replacement, a resample and the end of the recipe are the quantization boundaries: a replacement earlier in the operation list is processed by the colour operations after it and one later in the list is not, and a resample interpolates the quantized frame. Exact geometry commutes with a position-independent unit and composes as before. Compilation refuses an operation with more than eight units or a unit whose coefficients are not finite, and a non-finite value after any unit fails the render or sample with `resource-limit`; a neutral payload compiles to no units, which is no processing at all, so the identity byte path and the shared source buffer are kept. The rasterizing pass streams each run over the frame in bounded row chunks and hands each unit one row of a chunk at a time, and `render.sample` applies the same phases to one pixel at its own coordinates, so a sample equals the rendered byte.

A `Spatial` operation is an ordered list of at most four `SpatialUnit` units, for an effect whose value at a pixel depends on a bounded neighbourhood of that pixel. A unit declares `halo(stage)`, the input pixels it reads beyond what it writes; `scratch_bytes(region)`, the working buffer it wants; `estimate_key()` and `prepare(reduction)`, an optional global estimate and its identity; `apply(input, output, global, scratch)` over planar f32 linear-sRGB rectangles that carry their position in the stage; and `describe()`, which writes every coefficient exactly, in shortest round-trip form and never rounded to a display precision, because the host compares compiled operations by it. The module owns those answers and nothing else; a colour unit's `describe()` follows the same rule.

The operation opens a new segment at the same dimensions as the stage it receives, so the segment before it finishes its frame, the operation reads that frame and writes the next one, and later exact layers compose as before. The host streams 512 × 512 output tiles anchored at the stage origin, with partial tiles at the right and bottom edges, reading each tile grown by the operation's summed halo and clamped to the stage. Inside a tile the units chain: unit `i` is given the rectangle unit `i − 1` filled, and fills that rectangle shrunk by its own halo on every side except a side that lies on the stage edge, where it writes up to the edge because there is nothing further to read. Reads are clamped to the stage, so a unit never sees a coordinate outside it. A unit's value must therefore depend only on its pixel's neighbourhood: the host chooses the tiling, so a filter is evaluated in a fixed order that does not depend on where evaluation started, and a rendered frame is the same at any tile size and across runs.

One tile's working set — the input region, the intermediate planes, the last unit's output and the largest scratch any unit asked for — is charged to the render context's `SpatialBudget` with a 256 MiB target, separate from the 64 MiB float scratch budget, with an observable high-water mark. The target paces the work and never refuses it. The host refuses an operation when it compiles the recipe, before any pixel is read, only for what the operation declares: a summed halo over 512 px, more than four units or a non-finite one; nothing is reduced to fit and nothing is rewritten. Each batch of tiles reserves working sets before any of its tiles allocates, asking for as many as fit the whole target and the shared Rayon pool's workers, and runs as many tiles as fit beside what other evaluations hold, never fewer than one. So a render that overlaps another — the histogram's analysis and the preview's exact phase rendering the same stack — slows to one tile at a time rather than failing, and speeds up again once the other releases; a tile larger than the whole target runs alone. The process can then pass the target by at most one working set per spatial evaluation in flight, and the high-water mark shows it. Tiles run on the pool above the one-megapixel threshold, and the render's cancellation token is checked between batches.

A global estimate is prepared once from a host-built 1/16-per-side box average of the operation's input stage — at most a quarter of a megapixel, partial blocks averaged over their actual pixels, the grid anchored at the stage origin — and is at most 4 KiB. Only a unit that declares an estimate key has one: `estimate_key()` names everything `prepare` reads besides the reduction — the unit and any coefficient its preparation depends on — and a unit that declares none (the default) is never prepared, is handed no global and never causes a reduction. The host caches eight prepared estimates, keyed by source fingerprint, the hash of the layers before the operation, the stage and the estimate key, evicted oldest first, and reduces the stage at most once per evaluation, only when a unit that declares a key is missing from the store. So a second evaluation of the same stack reduces nothing, and neither does one whose units changed only in coefficients their keys do not name: Dehaze's atmospheric light reads the reduction alone, so every Dehaze amount over one stage shares one estimate, and Texture and Clarity declare none. The key belongs to the unit rather than to its position, because a module compiles whichever units its payload needs — Presence leaves out a unit whose amount is zero, which moves the others up — and two units that declare the same key over one stage share one estimate.

On the byte path each tile is decoded through the same table the colour run uses and quantized through the same exact thresholds into a new frame of the same size, with alpha copied; at most two frames exist and no full-frame float buffer ever does. The RAW linear path pulls single pixels through the compiled prefix and cannot pull a neighbourhood that way, so a render materializes each spatial operation's output once as three f32 planes inside the 1.5 GiB RAW planar limit and pulls from that, with nothing quantized before the terminal boundary. Each frame is built from the one before it and replaces it, so at most two exist at once. A point query through a spatial segment, on either path, evaluates the stage-aligned tile that contains its pixel, through the same tile function, plan, global estimates and input pulls the render uses, so a sample equals the rendered byte by construction; that cost is the declared exception to [performance rule 4](../engineering/performance-rules.md#rules). A point query materializes no frame. Every tile it evaluates, of every spatial segment, goes into one cache the two paths share and stays there for the rest of the query, so the four neighbours a resample blends, the points of a byte-path grid and a later segment's halo, which reads an earlier segment's tiles, evaluate each tile once. The summed halo is at most one tile and no geometry separates two spatial layers in the host's stage order, so one tile's input covers at most 3 × 3 tiles of the spatial segment before it, and one point through `k` spatial segments evaluates at most Σ (2d + 1)² tiles over d < k: 10 through two, 35 through three, 84 through four. Behind a resample it is Σ (2d + 2)²: 4, 20 and 56. The cache holds at most as many tiles as the spatial target has bytes for, 85 tiles of 3 MiB at 512 px and never fewer than 16. Each is charged to the budget while held and released with the query. Past that the query releases the least recently read tile and evaluates it again if it reads it again, which costs time and never refuses. Evaluating a tile reserves one working set while it runs, and a tile whose halo reads a missing tile of an earlier segment holds its own while that one is evaluated, so a point through `k` spatial segments holds at most `k`. A global estimate missing from the store is prepared from a reduction of the whole stage. When that stage comes through an earlier spatial segment, the reduction reads it serially through the same cache, one tile at a time, so each of its tiles is evaluated once. On a stage of more tiles than the cap, the at most 3 × 3 tiles the point's own halo reads after it may have been released and are evaluated again, and behind two spatial segments the earlier one's tiles stay held only while three of its tile rows and the walked row fit the cap, on stages up to about 10,700 px wide, 60 MP included. That is whole-frame work on the calling thread, paid only on a store miss; a preview's exact render stores the same estimates. The RAW path's sample grid materializes each spatial frame once, as a render does. A non-finite value after any unit fails the render or the sample with `resource-limit`, and a neutral payload compiles to no units, which is no processing at all, so no boundary is opened and the identity byte path and the shared source buffer are kept.

## Host dispatch

Every method resolves through one method table (`crates/lightwell-core/src/api/methods.rs`), for the desktop, the JSON API and headless callers alike. A host method's entry names its parameters, its notes and its handler: a service handler, which the editor service answers with the caller's session, or an owner handler, which the catalog owner answers from its own state — the source and analysis jobs, the event log, the capability host and the activity board. `edit.*`, `query.*` and `task.*` methods are generated from the registry's modules, and the `mask.*` methods from the host descriptor, by the same lookup (`action_for_method`, `query_for_method`). The owner finds the method, answers a retried revision-less mutation from its request table, otherwise calls the handler, and records the event each change announced; nothing is routed any other way. A host method's parameters are declared once, as the `deny_unknown_fields` struct its handler parses (`host_params!` in `api/params.rs`), and `schema.list` publishes that struct's required fields and its optional fields with their notes, so the schema and the parser cannot differ. Every host method refuses a field it does not declare, including one that takes none.

Every mutating method carries a `mutation` envelope, and `schema.list` names it in the method's `mutation` field; a method mutates exactly when it carries one. `revision` is `{expected_revision, request_id, actor}`, for a change to something with a revision: an asset (actions, `mask.*` commands, history, `draft.commit`) or a module's settings. `request` is `{request_id, actor}`, for every other change: the preset library, versions, `catalog.import`, `artifact.collect`, module permissions, activation, resources and capability jobs, and the `task.*` methods, which queue a job. The rule is the same for both: a retry with the same `request_id` and the same input returns the first answer marked `deduplicated: true`, changes nothing again and emits no event, and the same `request_id` with other input is a `conflict`. The catalog records an asset change's request durably in the same write as the change, per asset, because a retry after a restart must be answered rather than refused as stale. Every other mutation's retry — each `request` method's and a module settings write's — is answered from the owner's request table, keyed by `(scope, request_id)` with the scope the method's family (its name without the last segment) and the input hashed, a `set-secret` value redacted first; it holds the most recent 256 successful answers, at most 8 MiB, for the owner's lifetime. Each of those methods is safe to run again after a restart: it is a no-op, joins the work already done, fails visibly on the uniqueness it would break, or, for a settings write, which sets values rather than changing them, conflicts on the revision it was made against.

An action request goes through one path for the desktop, the JSON API and headless callers:

1. Validate the mutation envelope; resolve the action through the registry's one action lookup — a module's, or a host `mask.*` command — else `validation: unknown action`; refuse an action whose module is registered as unavailable with `incompatible: unavailable module <id>`.
2. Generic parameter checks, then module `parse` (a host command's checked parameters are what it stores). A patch action's check validates only the fields that were sent, and demands only the identities it addresses.
3. Request deduplication: the stored input hash covers `{action: <durable action id>, mutation}` merged with the parsed parameters. A retry returns the original answer, stored whole with the request — for a `mask.*` command its label and the mask and component it minted — marked `deduplicated`, and emits no event, because the first attempt emitted it; the same request ID with different input is a `conflict`.
4. Revision check, then module `plan` against the current stack through the one plan path, which looks up the cached verified source only when the plan samples a pixel.
5. `NoOp` records the request without a row. `Commit` places the layer by its effect stage, and `Compose` resolves its steps into one final stack or a no-op; `Commit`, `Update` and a changing `Compose` admit the resulting recipe and persist the snapshot, entry, current pointer, revision, cleared redo and request result in one transaction. Admission is one function that every new snapshot passes, a `mask.*` command's and a Restore's included: the registry validates the recipe, which checks its whole mask table once — the limits, every stroke it references and every component kind — it is checked against the asset's source kind, every artifact it lists must be recorded with a present file and is bound, and it is compiled against the asset, trusting that table, which leaves no later layer addressing a stage that no longer exists. A drafted `mask.*` gesture's recipe has its mask table checked once the same way; compiling never checks the table again.

### Preparation

An evaluation that needs something the catalog owner has not prepared — the verified original, a RAW development at a white balance, or a derived artifact's bytes — is refused `preparation-required`, and the refusal names exactly what the stack it evaluated needs as a typed `PreparationNeeds {asset_id, entry_id, gains, artifacts}`: the asset whose original it reads, the saved entry it evaluated (or planned over, for a change or a draft), the sensor gains a RAW development must hold (`None` for a JPEG) and the artifacts that stack references that are not ready. The service names them where it knows the stack, in one function every evaluating method answers through (`EditorService::needing`), so a request that leaves the entry to the session — `render.sample` or a `query.*` on a historical selection, a draft — is prepared for the stack it actually evaluated, never the current one re-derived from the request's parameters. A strict evaluation names its own white balance; a drafted preview, the one evaluation that approximates a white balance, names the development its entry holds, so a drag never queues one development per drafted value.

The owner has one answer to every such refusal, from any method or a preview job: it queues exactly those needs as one source job and answers `{code: "preparation-required", job_id, message}`, the message saying why. The job reads the original when the cache does not hold it, developing a RAW one at the named gains in the same pass; otherwise it redevelops only when the planes do not hold those gains; and it reads and verifies the named artifacts that are still not ready after either. Needs with nothing left to prepare answer with a job that is already ready. `source.prepare {asset_id, entry_id?}` queues the needs of that entry, or of the current one, the same way. A client waits for the job and asks again.

## Drafts

The core holds one draft per client session, in `ClientSession.draft`, reported by `session.state`. A draft is the settings of one gesture: it is bound to one asset and one action, never outlives the session, emits no event and appears in no history. Its methods are `draft.begin {asset_id, action}`, `draft.set {draft_id, fields}`, `draft.read {draft_id}`, `draft.cancel {draft_id}`, `draft.commit {draft_id, mutation}` and `draft.reapply {draft_id}`; only `draft.commit` touches the catalog.

`draft.begin` returns `{draft_id, action, asset_id, base_revision, draft_revision, fields, conflicted}` and is refused with `conflict` when the client already holds a draft and with `validation` while the session previews a historical entry or the action is unknown. `draft.set` validates every named field against the action's parameter descriptors — unknown name, non-finite, out of range or wrong kind is a `validation` error and nothing changes — then merges the fields and increments `draft_revision`. `conflicted` is `base_revision != the asset's current revision`, recomputed whenever the draft is read, set, committed or reported, so a commit by any client, including this client's own undo, redo or restore, marks it without a notification path. `draft.commit` refuses a conflicted draft or a `mutation.expected_revision` that is not the draft's `base_revision` with `conflict` and keeps the draft; otherwise it runs the action with the accumulated fields through the ordinary `apply_action` path and ends the draft, so a gesture that returned to its start is a `no-op` with no entry. `draft.reapply` rebases the draft on the current revision, keeps and revalidates only the fields this client set and clears `conflicted`; whatever another client changed meanwhile stays in the layer the next commit merges over. `draft.cancel` ends the draft and commits nothing. Two clients' drafts never interact, and the crop-frame editor's own desktop-local draft is unchanged.

A draft's effective recipe is the current snapshot with its action's plan applied to its fields, computed on demand by `EditorService::draft_recipe` and never persisted; a `NoOp` plan means the current recipe. A draft plans through the functions its commit plans through — `Prepared::new` and `plan_request`, for a module action and a `mask.*` gesture alike — with the request the commit will send, its drafted fields with its target's fields over them, so a draft equals its commit by construction for every module and source kind, composites included: a drafted Basic edit or RAW exposure previews exactly the bytes its commit renders. Planning it costs the same point queries as a commit and rasterizes nothing. `OwnerHandle::preview_job` takes a `PreviewRequest` carrying the client, the entry, an optional `layer_count` and an optional draft: the owner resolves the draft from that client's own session, the job carries the recipe to render and `draft_revision` for correlation, and another client's draft is a `validation` error. `render.sample {asset_id, x, y, draft_id?}` samples the same effective recipe and stamps the answer with `{draft_id, draft_revision}`.

Rendering and point sampling resolve every layer's effect through the registry: `compile` runs per layer at its input stage, exact geometry composes into one mapping per segment, point replacements map through the suffix geometry of their segment, and a resample separates segments. A preview job may truncate the stack to its first `n` layers; the desktop uses that to show a crop layer's input stage while drafting. `render.locate {asset_id, entry_id?, x, y}` maps one rendered pixel back through the geometry tail to the content pixel it shows, returning `{content_x, content_y, width, height}`; the desktop's canvas pick uses the same mapping to fill point-pick parameters and to give a `sample-apply` pick the content coordinates its query is run with.

## Histogram analysis

The histogram is not a recipe effect and writes no history. It is a read-only **analysis job** over the rendered SDR sRGB output of one evaluated stack, run off the catalog owner thread and keyed to an identity that says exactly which image the counts describe.

`analysis.request {asset_id, target}` returns `{job_id, status, identity}` promptly, with `report` included when the store already holds it. `target` is one of `{"kind": "current"}`, `{"kind": "entry", "entry_id"}` (a frozen historical entry, which a later commit by any client never relabels) or `{"kind": "draft", "draft_id"}` — the calling session's own draft, evaluated at the `draft_revision` it holds now; another client's draft, or one that has ended, is a `validation` error. `analysis.read {job_id}` returns `{status, identity, report?, error?}` and `analysis.cancel {job_id}` returns `{cancelled: true}`. A job this client never requested is a `validation` error on read and on cancel. None of the three mutates anything or emits an event, and none requires a GUI or a change of selection.

`status` is the one job-status vocabulary source, analysis and capability jobs all share (`crate::JobStatus`, [lifecycle and jobs](module-capabilities.md#lifecycle-jobs-and-resources)):

| Status | Meaning |
| --- | --- |
| `queued` | Accepted, waiting in the worker's one replaceable pending slot |
| `running` | The worker holds it now |
| `ready` | Complete; `report` carries the counts |
| `failed` | The stack could not be evaluated; `error` carries the structured reason |
| `superseded` | A newer request took the single pending slot; the requester may simply ask again |
| `cancelled` | Every interested client withdrew before the work finished |

Only `ready` ever carries `report`. Queued, running, failed, superseded and cancelled results have no counts at all, so no status can be read as a valid but empty histogram.

The identity is `{asset_id, source_fingerprint, entry_id, snapshot_id, recipe_hash, draft?, width, height, domain}`. `recipe_hash` is the SHA-256 of the effective recipe's canonical JSON, `draft` is `{draft_id, draft_revision}` when a draft was analysed, `width`/`height` are the **output** stage, and `domain` is always `srgb-8bit-output`. A `failed` job whose stack has no output stage at all — an unavailable provider, or a payload the registry refuses — reports `width` and `height` as `0` and carries its error; nothing is rewritten or discarded to make such a stack renderable.

Scheduling and bounds. One analysis worker runs one active job with one replaceable pending job, globally. Requesting a third job while one is active and one pending replaces the pending one, which reads `superseded`. Identical identities share one job: a second request joins its interest set and gets the same `job_id`, so the same work is never done twice. `analysis.cancel` drops only the calling client's interest; the job is cancelled only when no interested client is left, and a disconnect releases that client's interests the same way. A cancel drops a job that has not started and stops one already under way within a chunk of its render or reduction, and its cancelled outcome is discarded when it arrives. A newer request never interrupts the running job, because another client may still want it. The owner keeps at most eight completed reports and at most 32 job records, evicting the oldest first, and a report is bounded to 16 KiB. No raster is retained per result.

Building a job on the owner costs a state read, the cached verified source and an `O(layers)` plan and compile to learn the output stage; the render and the reduction happen on the worker. The worker is one persistent thread on the same latest-job primitive as the preview (`lightwell_core::latest`): it starts the pending job itself when the running one ends and wakes the owner through the owner's own channel when an outcome is ready, so nothing polls and no timer is added.

Preview reuse. `PreviewJob.analyse` (via `PreviewRequest::analyse()`) makes the preview worker reduce the frame it just rendered and return the `Report` beside the raster, with the job's `AnalysisIdentity` for correlation. The desktop hands that report to `OwnerHandle::submit_analysis(identity, report)`, and an `analysis.request` for the same identity is then a cache hit: a displayed target is never rendered twice. A preview job's identity is computed exactly as an analysis job's is; a truncated job (`layer_count`) renders a layer prefix its identity does not describe and cannot be analysed.

Overlays. `workspace.set` accepts `clip_shadows` and `clip_highlights` booleans and `session.state` reports them; they are per-client view state and change no raster, recipe, histogram population or export. The display overlay itself is derived from the same final raster by `analysis::overlay(rgba, width, height, cells_w, cells_h)`, which ORs the shared `clip_class` predicate over every source pixel of each display cell — one byte per cell, `0` none, `1` shadow, `2` highlight, `3` both — so an isolated clipped pixel survives a Fit reduction and a cell grid equal to the image is one to one. No full-resolution mask is allocated; the grid is bounded to 4096 cells a side.

## Registry

`builtin_modules()` lists the linked built-in modules — presets, pixel, RAW, Basic, presence, mixer, transform, crop and vignette, in that order — and `ModuleRegistry::builtin()` registers exactly those; the desktop and every test that serves another set start from that one list. `register_unavailable(module, reason)` registers a module with its descriptor, effects, actions, queries and tasks exactly as `register` does and its availability `unavailable {reason}`; the desktop's `--disable-module ID` uses it, and no client keeps a wrapper of its own. The presets module declares no effects, so it owns no layer; a module without effects registers like any other. The mixer's one colour-stage effect declares order 10, so a committed mixer layer always follows the Basic layer in the colour run whichever was touched first, and presence declares the spatial stage, so its layer follows both of them whichever was touched first. The crop's geometry effect declares order 10 too, so the orientation layer is always placed ahead of the crop and the crop's input stage includes every transform. `register` accepts any `ToolModule` and rejects: an invalid module, effect, action or query identity; a duplicate module, effect, action or query ID; a control naming an undeclared action or parameter; a module, group or number-control reset naming an action this module does not declare, or a preset field its action does not declare or cannot accept; a canvas interaction naming an undeclared action, query or coordinate parameter, or a coordinate parameter of the wrong kind; a preset or default outside the parameter's range; a parameter without a kind; a canvas shortcut letter another module already claims; a `picker` without a pick canvas, more than one `picker` in a module, or a pick canvas without a `picker`; a `string` bound outside 1..=256; a `presets` control whose action is undeclared, a patch or not shaped exactly as that control requires, or more than one `presets` control in a module. Queries and tasks have their own identity namespaces, because `query.<id>`, `task.<id>` and `edit.<id>` are different methods; a task identity is unique across the registry. Registration also runs every capability declaration rule. It builds hash lookups from descriptors only and touches no image, catalog, settings, keychain, network or model resource. A module that needs an expensive resource initializes it on first `compile` or `plan`; registration and first-use costs are measured separately.

The desktop registers `lightwell.capabilities`, the capability proof described in [module capabilities](module-capabilities.md#proof-module), only with `--developer --proof-endpoint URL`, and `lightwell-json` with `--proof-endpoint URL`. The desktop registers `lightwell.controls` only in developer mode (automatic in debug builds, explicit `--developer` in optimized builds). It declares the complete delivered control vocabulary over `edit.set-controls`, which accepts one field per request, plus the non-patch `edit.reset-controls` for module/group resets. Its two-channel curve query returns 257 piecewise-linear samples. The stored colour-stage layer compiles to identity and shares unchanged source pixels. Outside developer mode the module and its methods are absent; a catalog containing its layer reports an unavailable provider explicitly.

## Developer workspace

The developer components gallery is per-client workspace state, exposed by `workspace.set` and
`session.state` as `component_gallery`: pages 0–9, or `null` for the editor. It requires no asset,
changes no recipe and submits no rendering job. Normal optimized desktops keep the diagnostic
button and board hidden; debug builds and `--developer` runs expose them.

## Missing effects

A layer whose derived artifact is missing, corrupt or in a directory that belongs to another catalog stays in every snapshot unchanged too; rendering, sampling and analysis of its stack fail with `source-unavailable` (or `incompatible` for a foreign directory) naming the artifact, and history keeps working ([derived artifacts](module-capabilities.md#derived-artifacts)).

Layers whose effect has no available provider stay in every snapshot and entry unchanged. `state`, `history.list`, `history.inspect`, undo and redo keep working. Rendering, sampling, appending an edit and restoring such a stack fail with `incompatible: unavailable effect <id> (layers …)`; a cached preview may only be shown with an explicit stale or unavailable label. Registering a compatible provider again restores evaluation without touching stored data. Removing an edit is a separate explicit action that does not exist yet.

## Current formats

Each module accepts only its current effect format and payload shape. Unsupported formats fail explicitly without modifying the stored recipe. Breaking shape and algorithm changes are expected during pre-release development; tests target the current contracts.

## Resources and external loading

Registration is cheap and expensive resources initialize on demand: a module that needs a model or other heavy state declares a pinned resource and an activation, and the host installs and activates it only when a client asks, on its worker ([module capabilities](module-capabilities.md)). Start with linked built-ins. Hiding controls is a UI preference, not effect removal, and persisted processing order never depends on panel order.

External loading remains required later: a separately authored tool must load without editing host source and expose its actions through the same APIs. Before implementing that loader, select a use case, measure startup, first-use, memory and idle costs, and define trust, dependencies, cancellation and packaging. Native binaries, workers or sandboxed runtimes are all still options; a marketplace and hot unload are not requirements. Later operations such as exposure, white balance, masks, clone strokes or presets must carry enough structured data to reproduce their results. Keep geometry and color stages explicit and do not prebuild a generalized graph.

## Acceptance

Descriptor validation rejects duplicate identities, missing handlers, invalid controls and unavailable providers explicitly. Pixel and transform actions invoked through generic controls and an independent API client produce identical stacks, history, pixels and errors. Current-format catalogs reopen with their IDs and undo/restore paths intact. Registration and first-use resources are measured separately. Real native M4 control layout, keyboard behavior and pixels are inspected with correlated state. Every module in the field-patch shape passes one [conformance suite](../engineering/development.md#the-field-patch-conformance-chapter), found from the registry and fed payloads derived from its field table, in `cargo test` and in release inside `editor-acceptance`.

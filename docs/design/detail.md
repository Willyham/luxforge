## Outcome and scope

One small Detail module supplies manual capture sharpening and luminance/colour noise reduction on every supported JPEG and developed RAW source, globally or through existing masks. It keeps source bytes, continuous RAW editing, immutable history and UI/API parity. Lightroom informs familiar controls and 100% inspection, not equations or value equivalence ([Adobe's Detail guidance](https://helpx.adobe.com/in/lightroom-classic/desktop/process-and-develop-photos/retouch-photos.html)); the repository's [Lightroom](../research/lightroom/detail-and-local-contrast.md) and [darktable](../research/darktable/raw-and-denoise.md) research inform the alternatives.

This is **capture sharpening**: modest restoration of apparent edge definition at the developed image's pixel scale. It cannot recover missing information or undo arbitrary blur. Export renders the recipe once, including Detail. **Output sharpening** would be a separate export operation after destination resizing; it is out of scope, as are export resizing, AI denoise, sensor-domain denoise, camera/ISO noise profiles, deconvolution, automatic defaults, hot-pixel repair and a separate detail-preview pane. No new providers, capabilities, model downloads, dependencies or placeholder controls are selected.

Detail's host work is larger than the module. Placing a spatial operation before Basic changes four delivered host paths, and each is part of this plan: the byte path's precision between a spatial operation and a colour run, what a downstream drag at Fit re-renders, value-based mask overlays behind a spatial prefix, and every pixel read that planning or a query takes through a spatial prefix.

## Decisions

| Choice | Selected default and reason |
| --- | --- |
| Processing order | Noise reduction, then capture sharpening, before Basic and Presence. Noise is not amplified before it is reduced, and the denoiser's input does not change with later exposure or tone settings. Basic stays one composite |
| Host stage | A new `restoration` placement stage using the existing `Spatial` primitive: pre-tone work without moving Presence, overloading panel order or building a processing graph |
| RAW/JPEG defaults | All three strengths start at zero on both kinds and no layer is added at import: Original is preserved and a camera JPEG that may already be sharpened is not sharpened again. Ancillary defaults make the first deliberate adjustment useful |
| Algorithms | Bounded multiscale wavelet shrinkage plus thresholded, edge-gated unsharp masking: deterministic CPU kernels with fixed support, easier to bound and verify than patch search or iterative deconvolution |
| Fit | The effect is shown at Fit: an approximate moving preview, then a settled Fit reduced from the exact processed frame. Hiding Detail at Fit would misrepresent colour blotches and composition |
| Masks and presets | Host targets, spatial blending and field-patch presets are reused; one layer per target; no module-owned selection or history |
| Numerical work | Equations, coefficient mappings and fixtures are frozen against an independent reference before production kernels |
| **JPEG precision** (owner, 2026-09-30) | On the byte path a spatial frame that feeds a colour run or another spatial unit holds 16-bit encoded sRGB; 8-bit quantization happens only at a resample, a point replacement or the terminal output. An 8-bit hand-off between Detail and Basic bands under exposure and shadow lifts (a denoised dark ramp at +2 EV and Shadows +100 shows 3-code contour steps and 3.6× the high-pass banding of a float hand-off). This settles Presence's JPEG spatial precision the same way, and this plan implements it for both |
| **Restoration-prefix proxy cache** (owner, 2026-09-30) | The motion proxy after the leading restoration layers is kept and reused while only later layers change, so a Basic, curve, mixer, Presence or mask drag does not re-run Detail each frame. It is a cache under [performance rule 14](../engineering/performance-rules.md#rules): one entry within 128 MiB |
| **Mask overlays behind Detail** (owner, 2026-09-30) | Value-based mask overlays and Masks-panel thumbnails keep working behind Detail through a bounded input-grid cache on each overlay worker. The existing refusal remains only where a prefix still holds a spatial layer after its leading restoration run |
| **No pixel work on the owner** (owner, 2026-09-30) | A query or mutation that reads pixels through a spatial prefix is evaluated on the point worker; a mutation goes owner → point worker → owner with its identity checked on return. Performance rule 5 gains no exception |

## Placement and stage

`EffectStage::Restoration`, serialized `"restoration"` through the existing `rename_all = "kebab-case"`, `as_str` `"restoration"`, declared between `Pixel` and `Color`. Every exhaustive match over the stages gains an arm: placement, the registry's proxy-eligibility rule (`registry/compile.rs`), the field-patch shape (`Restoration` maps to `Shape::Spatial`) and `EffectStage::as_str`. Descriptor validation admits a maskable restoration effect.

For newly placed layers the regions are:

```text
prepared source → pixel edits → restoration (Detail) → colour (Basic, Tone curve, mixer)
                → spatial (Presence) → geometry (orientation, Lens, Perspective, crop) → finish (vignette)
```

`placement_index` changes in two places and nowhere else:

| New layer's stage | Opens its region at the first layer of stage | Moves its lower bound past |
| --- | --- | --- |
| `pixel` | restoration, spatial, geometry, finish | – |
| `restoration` | colour, spatial, geometry, finish | – |
| `color` | spatial, geometry, finish (unchanged) | – |
| `spatial` | geometry, finish (unchanged) | every pixel, colour **and restoration** layer |

A leading RAW source layer stays at index zero. In a stack without a restoration layer pixel placement is unchanged: a new pixel edit still lands after colour, before the first spatial layer. Existing layers never move on an ordinary edit, and stored noncanonical orders still evaluate in stored order: a stored `[mixer, Detail]` plus a new Basic becomes `[Basic, mixer, Detail]`, keeping the order among colour layers rather than moving anything. Nothing infers processing order from panel order.

RAW preparation still includes sensor white balance, demosaic, colour conversion and required DNG corrections before Detail. JPEG is already rendered input: Detail runs before Luxforge's relative white balance, exposure and tone, but cannot undo camera processing, clipping or compression. The asymmetry is intentional; moving JPEG white balance ahead would split Basic. A RAW white-balance commit invalidates dependent renders through development identity; Detail edits never redevelop the mosaic. RAW exposure uses the global Basic layer, after Detail, and changing it reuses the held restoration prefix.

## Pixel contract

One Detail layer compiles into at most two spatial units, denoise then sharpen. Unit presence depends **only on strengths**, never on the stage or scale, so a proxy and an exact compilation of one stack always have the same segments (a unit whose scaled effect is sub-pixel is still compiled, and degenerates to identity). The denoise unit is omitted iff `luminance == 0 && colour == 0`, the sharpen unit iff `sharpening == 0`, and with both omitted `compile` returns `Processing::Spatial(SpatialOperation::neutral())`, which the registry already compiles to nothing. The module keeps the default `is_neutral` (all fields at their defaults), so a first Radius edit with no layer commits a layer that renders identity and keeps its value; overriding `is_neutral` to "strengths zero", as the vignette does, would make that edit a no-op that snaps back. `describe.neutral` is "all default", so an ancillary-only layer shows the accent dot. A reset keeps the layer and its ID.

RAW keeps signed float linear-sRGB planes between the units and to the terminal. On the JPEG path the two units of one operation hand values to each other in `f32` inside the tile; the operation's frame follows the 16-bit hand-off below. No full-frame opponent-colour image, intermediate RAW clip or intermediate gamut clamp exists. The host's finite-value checks are reused and unsupported payload formats are refused without rewriting data.

### The 16-bit hand-off on the byte path

The byte path holds two frame widths, selected by the compilation rather than the caller:

- **Narrow**: RGBA8, 4 bytes a pixel, as today. The source, every resample's input and output, and the terminal frame are narrow.
- **Wide**: RGB16, 6 bytes a pixel, 16-bit encoded sRGB (`code = nearest(encode(v) × 65535)`, clamped to [0, 1] as the 8-bit quantizer clamps).

One pure function of the compilation, `byte_frame_widths(&Compiled)`, decides each frame's width, and the rendered path and the point path both read it:

1. A spatial boundary's output frame is wide iff the segment it feeds has colour runs and no point replacements, or that segment writes nothing and feeds another spatial boundary (a pass-through). Pass-through spatial chains preserve wide values backwards to the preceding boundary. Otherwise the tile output is quantized straight from `f32` to 8 bits, as today, so no value is rounded twice.
2. A segment's output frame is wide iff the boundary after it is spatial and the segment has colour runs or a wide input. The last segment's output is narrow.
3. A colour run's end quantizes to 8 bits when a point replacement phase follows it in the segment, and otherwise to the segment's output width.
4. A resample reads and writes narrow frames.

Types and helpers:

- `colour::srgb::decode16_table()`: a 65,536-entry `f32` table (256 KiB, built once), with `decode16_table()[257 × c] == decode_table()[c]` bit for bit for every 8-bit code `c`, asserted by a test, so a narrow value read through either table is the same number.
- `colour::srgb::quantize16(value: f32) -> u16`: the one 16-bit quantizer, exact thresholds computed once in `f64` (65,535 `f32` midpoints, 256 KiB), shared by rows and points.
- `Byte::Pixel` becomes `[u16; 3]` (opaque). An 8-bit value is stored as `257 × code`, so `terminal` divides exactly; `Byte::linear` and `Byte::spatial_input` decode through `decode16_table`.
- `Byte::SpatialFrame` is `Arc<Vec<u16>>` when wide and `Arc<Vec<u8>>` when narrow (an enum `ByteFrame`); `segment_pass` and `SegmentRows` become generic over the frame's sample type, and a wide segment holds its chunk rows as `f32` between load and store, as `LinearRows` does. `frame_mut` gains a `u16` sibling with the same test instrumentation.
- A wide frame's length is `width × height × 6`, checked-multiplied and refused above `MAX_FRAME_BYTES` (512 MiB). The largest JPEG decoded (64 MP) needs 366 MiB, so no supported source is refused.

Memory: two frames at once remains the byte driver's peak, but a wide frame is 1.5 times a narrow one: at 24 MP the peak goes from 183 to at most 275 MiB, at the 64 MP JPEG limit from 488 to at most 732 MiB. Point samples equal rendered bytes by construction, because both use `byte_frame_widths`, the same tables and the same quantizer.

Presence changes with it: on JPEG, Presence now reads Basic's output as a wide frame and hands its own output wide to the mixer or vignette. Its JPEG bytes change within rounding. The byte-path Presence tests (render, sample, window, estimate reuse and cancellation equality) are re-run and any literal pinned to the 8-bit hand-off is re-frozen with its reason, the Presence study records the new boundary, and Presence's JPEG timing is re-measured before and after in the performance task.

## Algorithms and numerics

The independent `f64` reference, `crates/luxforge-reference/src/detail.rs`, preceded production code. The [study](detail-study.md) freezes the formulation below, records independent and full-pipeline synthetic results, and gives dispositions for 13 crops from the four authentic sources at moderate and stress settings. Inspection is complete for those supplied images; quality qualification remains incomplete.

**Formulation (both units).** Each tile's linear RGB converts to the project's Oklab (`oklab::to_oklab`, signed cube roots, extended values kept). Every smoothing is written in difference form, `x + Σ_{i≠0} w_i (x_{p+i·h} − x_p)` with the taps in the fixed order −2, −1, +1, +2, so a constant input is returned exactly; a naive `Σ w_i x_i` changes 19.4% of constant values in `f32`. The unit forms `Δlab = Σ_j (s_j(d_j) − d_j)`. If `Δlab` is zero bit for bit the output is the input pixel, never a round trip (a round trip alone makes only 0.02% of pixels bit-exact). Otherwise, if `|a′| ≤ NEUTRAL_CHROMA_SNAP` and `|b′| ≤ NEUTRAL_CHROMA_SNAP` (`1e-6`) the output is the achromatic `[L′³; 3]`, so a grey ramp stays byte-neutral; otherwise `from_oklab(lab′)`. Sharpening changes lightness only.

**Denoise.** Three luminance and four chroma undecimated separable B3 levels, kernel `[1, 4, 6, 4, 1] / 16` at spacings 1, 2, 4 and (chroma only) 8 full-resolution pixels. Band noise factors `k_j = [0.8914, 0.1992, 0.0860, 0.0417]`. The study tuned thresholds to `T_L = 0.10 · (luminance / 100)^1.5 · k_j` and `T_C = 0.10 · (colour / 100)^1.5 · k_j` in Oklab units after the starting 0.05/0.04 baseline failed the dark flat-patch gate. Protection `π = e / (e + (3T)²)`, with `e` the 3 × 3 box of `d²` (of `|Δab|²` for chroma); `T_eff = T · (1 − detail / 100 · π)`. Non-negative garrote `s(d) = d · max(0, 1 − T_eff² / d²)`, applied to the chroma vector's magnitude. Exact halo is 31 px with colour active, 15 px for luminance alone. The fourth-level contingency passes sigma 8 in the independent reference (26.0%), while sigma 16 remains unmet (14.1% versus 25%). Through terminal production output, both cases fail at 21.20% and 7.96%; terminal-Original comparisons remain supplementary diagnostics. No image-wide noise estimate, ISO lookup or viewport-dependent statistic.

**Sharpen.** A separable Gaussian with `σ = radius`, support `ceil(3σ)`. Residual `r = −Σ g_i (L_i − L)`, cored as `r · r² / (r² + θ²)` with `θ = 0.01 · (1 − sharpen-detail / 100)²`, gain `sharpening / 100`. Masking guide `E² = |∇(G_1 ∗ L)|²` by central differences, `mask = E² / (E² + (masking / 100 · 0.05)²)`, or 1 at masking 0. A limiter soft-clamps to the 3 × 3 min/max of `L` with `tanh` at `δ = 0.04 · (hi − lo)`. Exact halo `max(ceil(3σ), 4)`, at most 9 px. This is unsharp masking, not deconvolution.

**Constants.** `DETAIL_DENOISE_HALO_MAX = 32` (full-resolution support), `DETAIL_SHARPEN_HALO_MAX = 16`, `NEUTRAL_CHROMA_SNAP = 1e-6`, asserted by `detail_declared_halos_stay_within_their_caps`. The fourth chroma-only contingency has been taken: the full-resolution operation cap is 48 px. The fixed sampled-Gaussian rule can need 46 px of denoise halo near scale 1, so sampled denoise declares its actual support and the evaluated operation cap is 62 px. No halo is clamped. The operation's summed halo stays under `SPATIAL_WIDE_HALO` (128), so it runs in 512 px tiles. A fused single unit is an optional measured optimization, not required: two units convert RGB↔Oklab twice.

**Edges and cuts.** Edge clamping at true image edges, full halos at tile, region and crop cuts, fixed arithmetic order, no tile-local estimator. Each unit's halo is fixed at compile from its `CompileStage` and `halo(&self, _: Stage)` ignores its argument, as Presence's Texture does, because a windowed cut hands a unit the window as its stage.

**Proxy kernels.** For sampling scale `(sx, sy)` from the compile context: denoise level `j` becomes a sampled normalized Gaussian with `σ′ = h_j · s` per axis (`h = 1, 2, 4, 8` with the fourth chroma only), radius `R′ = max(1, ceil(3σ′))`, weights `exp(−i² / 2σ′²)` normalized in `f64` and cast; nothing is floored or skipped, and `σ′ → 0` degenerates to identity. Thresholds are unchanged per level. The protection window stays 3 × 3; limiter and guide windows are `max(1, ceil(r · s))`. The sharpen blur uses `σ′ = radius · s` with the same sampling. Proxy halo is `Σ_j R′_j + 1` for denoise and `max(R′_s, R′_guide + 1, 1)` for sharpen, the per-axis maximum, as an integer. Exact (scale 1) keeps the B3 à trous. The independent probe at scales 1/2, 1/3, 1/4, 1/6 and 1/8 including non-integer axes passes the proposed RMS ≤ 1.2-code bound, but p99 reaches 4.13 codes and fails the proposed 3-code gate. The study preserves that failure and the clamp/skip control figures; the proposed gate has not been relaxed to claim a pass.

**Scratch.** Denoise declares `scratch_bytes(region) = 13 × 4 × w × h` (Lab 3, coarse 3, next 3, separable temporary 1, Δ 3) and sharpen `6 × 4 × w × h`, with checked multiplication (overflow is `resource-limit`). The direct 3×3 energy calculation uses scalar accumulators. One 512 px tile with halo is about 28 MiB (masked +3 MiB), so about nine tiles run at once under the shared 256 MiB spatial target. Scratch is the maximum over units, not the sum.

**Tolerance.** Production against the reference: `1e-5 + 1e-5 · |ref|` in linear light plus at most one output code at a quantization boundary, the colour and mixer studies' precedent; `1e-6` is below the `f32` Oklab round-trip floor (2.6e-6 in gamut, 1.1e-5 extended). Constants, untouched pixels, sample/full, region/full and serial/pool equality are exact.

## Compile context

`ToolModule::compile`, `FieldPatch::compile` and capability modules' `compile_bound` receive the shared `CompileStage` context from `modules/processing.rs`:

```rust
pub struct SamplingScale { pub x: f64, pub y: f64 }      // evaluated pixels per full-resolution pixel
pub struct CompileStage { pub stage: Stage, pub full: Stage, pub scale: SamplingScale }
impl CompileStage { pub fn exact(stage: Stage) -> Self } // full = stage, scale = (1, 1)
```

The three signatures take `at: CompileStage` in place of `stage`, and every implementation (about 25, test providers included) is updated mechanically; existing modules read `at.stage`, so their bytes are unchanged, which the existing Presence and oracle tests prove. `full` for each layer comes from `ModuleRegistry::stages(exact_width, exact_height, recipe)` (`O(layers)`, no pixels), `scale = stage / full` per axis in `f64`. `ModuleRegistry::compile_sampled` gains the exact content dimensions and the three proxy compile sites in `render/entry.rs` (`proxy_window`, `plan_proxy_region`, `render_proxy_region`) pass them. A module name never selects behaviour.

## Previews at Fit and percentage zoom

**Motion.** All effects still run during motion: Detail applies the scaled kernels above to the display-bounded proxy at Fit and to the half-scale visible region at 100% and above. Denoising and reduction do not commute, so the frame is labelled approximate. `ProxyApproximation` gains `restoration: bool`, set from a stage tag on `SpatialEntry` for a non-empty restoration operation, with the reason "a restoration layer's full-resolution filters run on averaged proxy pixels"; `spatial` then counts spatial-stage entries only, because its reason ("neighbourhoods scale with the stage") is false for Detail. The desktop status reads "Moving preview · Detail approximate". The same scaled kernels have a GPU program, which draws a Detail drag at Fit on the GPU once the drag's boundary, the Detail layer's input, is held: judged against this moving proxy, which it stands in for, and replaced on release by the CPU's proxy and then the settled Fit frame; the proxy's own jump to the settled frame is unchanged by it ([GPU previews](gpu-preview.md#qualifying-a-program)). A drag of a later layer starts its GPU boundary from the restoration-prefix proxy cache.

**Settle policy.** No preview contract exists on descriptors today; this adds one serialized field. `EffectDescriptor.fit_settle: FitSettle`, `enum FitSettle { #[default] Proxy, Exact }`, `#[serde(default, skip_serializing_if = "is_default", rename_all = "kebab-case")]`, so only Detail's descriptor snapshot changes (`"fit_settle": "exact"`). `Compiled::settles_from_exact()` is true only when a non-empty spatial entry's effect declares `Exact`; a neutral or ancillary-only Detail layer adds no work.

**Settled Fit.** With active Detail, the full-resolution exact phase supplies both the histogram and a bounded reduction for the settled display:

- Core: `ExactOutcome` gains `display: Option<Raster>`, the exact frame reduced to the job's proxy plan by `downscale_raster(&Raster, ProxyPlan, &Cancel)`, a sibling of `downscale_jpeg` reusing `BoxDownscale` and `Coverage` (the shared linear-light area reducer). The worker computes it right after `exact.frame()` under the exact phase's cancel token, only for a whole-stack Develop job (`layer_count == None`) with proxy bounds, an intent other than `Interactive`, `settles_from_exact()` and a scale below 1. It is at most 8 MP of RGBA8 (32 MiB). A scale of 1 presents exact pixels as today. The result event carries `"settled_from_exact": true`.
- Desktop: `Presenter::show_settled(raster, content)` sets `photo_content` and never `full_content`, so 100% never treats it as full detail. `Retained::Settled` keeps it for zoom back to Fit. It is adopted only when generation, content serial and `proxy_bounds()` all match; otherwise it is dropped and a reduce is requested. The status reads "Settled from exact · display reduced"; the drafted-RAW-white-balance flag stays when present. Counts are the exact whole-image counts, marked updating until their matching completion.
- Triggers: every whole-stack Develop job with Fit bounds whose compilation settles from exact — commits, history, presets, Compare exit, mask edits, other sliders and zoom to Fit. Never crop-draft stages (they keep their approximate proxy and label), Masks-panel thumbnails, coverage jobs, Compare sides or `Interactive` jobs.
- Resize and zoom to Fit re-reduce the retained exact raster with a reduce-only job on the preview queue (`PreviewIntent::Reduce`, holding an `Arc` of the raster, no clone), not a re-render.

**Restoration-prefix proxy cache.** Beside the source proxy, the preview worker retains the processed restoration prefix for downstream edits:

- The *restoration prefix* of a stack is its leading run of source, pixel and restoration layers, ending at the first layer of any other stage (`ModuleRegistry::restoration_prefix(layers) -> usize`). It is *active* when its compilation holds a non-empty restoration operation. `Compiled::restoration_boundary() -> Option<usize>` names the segment whose input frame is the prefix's output. A noncanonical stack with a colour layer before Detail has no active prefix and renders as today.
- `RestorationPrefixKey { proxy: ProxyKey, prefix_hash: String, domain: String, wide: bool, held: Region }`: the proxy source identity and plan (window included); the SHA-256 of the canonical JSON of the prefix layers and the masks and strokes they reference, as spatial entries already hash their prefix; and the domain's `estimate_prefix` (byte dimensions and orientation; RAW development, view and white-balance approximation); and the required boundary width and retained boundary rectangle (whole-stage origin and dimensions). With multiple restoration layers, two different later boundary windows can map to the same source proxy window, so that rectangle is part of the identity. A suffix changing from neutral to an active colour run rebuilds a narrow prefix as wide, preserving the uncached path's exact quantization.
- `RestorationPrefixCache`, owned by the preview worker beside `ProxyCache`, holds at most one `RestorationPrefixFrame { key, held: Region, pixels: Narrow(Arc<Vec<u8>>) | Wide(Arc<Vec<u16>>) | Linear(Arc<Vec<f32>>), bytes }`: the boundary's frame at the proxy stage (the RAW spatial frame becomes an `Arc` so it is shared, not copied). Frames above `RESTORATION_PREFIX_MAX_BYTES` (128 MiB) are not cached and render as today. At the 8 MP proxy bound it holds 48 MiB on JPEG and 96 MiB on RAW.
- A proxy phase (Fit, or a 100% interactive region) with an active prefix looks the key up. A hit renders only the segments after the boundary against the held frame (`Render::render_proxy_suffix`). A miss releases the held frame first, evaluates the proxy compilation through the boundary under the proxy cancel token, stores it and renders the suffix. A cancel or error leaves the cache empty. A `ProxyCache` miss clears it, so a switched photograph never pins the previous prefix. `PreviewResult.restoration_prefix: Option<PrefixUse>` (`Built`, `Reused`, `TooLarge`) reports what happened.
- A suffix render from the held frame is byte-identical to the uncached proxy render. Detail, pixel and drafted RAW white-balance drags change the key and still re-run proxy Detail each frame.

**Expected costs.** These are stated so the measurements can be read, not budgets met:

- Settlement: every settle, 100% refinement and export recomputes full-resolution Detail, including settles caused only by a Basic, curve, mixer, mask or crop edit: about 0.4–0.6 s at 24 MP and 1.5–2.7 s at 60 MP on the M4 (estimate). The provisional 200 ms settled-histogram budget is expected to miss whenever Detail is active.
- Motion: Detail and RAW white-balance drags pay proxy Detail per frame and are expected to miss the 16/32 ms Fit slider budget; downstream drags, including RAW exposure, pay only the suffix once the prefix is held. RAW exposure is measured against its 50 ms budget.
- Windows: `Entry::plan_window` declines with `EstimateAfterSpatial` whenever an estimating operation follows a tiled segment, so every stack with Detail and Dehaze loses the windowed proxy and region paths: 100% motion falls back to the whole-output proxy, refinement to the whole exact frame, and a tight crop at Fit renders the whole proxy stage. The fallback is kept, reported and measured as a named cost case. Accepting `EstimateAfterSpatial` when the estimate store already holds the exact estimate is provably exact but is not part of this plan.
- RAW memory: on the linear path two `f32` planar frames coexist while a second spatial layer is built, beside the retained development and the terminal RGBA. These buffers total 40 bytes per pixel (12 for development, 24 for two planar frames and 4 for RGBA), before scratch, the retained mosaic, caches, GPU resources and other process overhead. The supplied Z6 is 4024 × 6048 (24,337,152 pixels): about 278.5 MiB of development, 557.0 MiB of planar frames and 92.8 MiB of RGBA, totaling 928.4 MiB. A hypothetical 45.7 MP source totals about 1.70 GiB for those buffers alone, above the owner's 1.5 GiB RAW working-set investigation target. These are allocation estimates; actual residency is measured separately.

Windowed/whole and region/full equality are proved with multiple spatial segments, Detail before Presence and Dehaze's whole-stage estimate. A fallback is observable and measured, never evidence of a passing region latency check.

## Pixel reads off the owner

The JPEG neutral picker (a 5 × 5 patch through `sample_before`), `mask.sample-input` and a colour-limited brush seed can read through Detail. Queries and planning samplers that encounter such a spatial prefix defer their pixel work to the point worker by one mechanism. A draft retains the resulting seed rather than reading it again on every tick.

**Deferral.** `HostStage::sample_before` compiles the prefix once per index, as today. When that prefix `evaluates_spatial()` and the context's `PixelMemo` does not hold the answer, it records a `PixelRead { index, x, y }` in the service's `deferred_read` slot and returns an internal error; the owner checks the slot after every handler, and a recorded read takes precedence over whatever the handler returned. A prefix without a spatial layer is still answered on the owner in `O(layers)`, so `query.sample-curve`, which reads no pixel, and every pointwise pick stay owner work; a test pins each.

**Queries.** A deferred query becomes `Planned::Query(Box<QueryPlan>)`: an owned exact `Evaluation` of the entry, the resolved query (module or host), its checked parameters, target and view. The point worker re-runs it with `WorkerStage`, which implements `StageQuestions` over that evaluation and keeps one point `Evaluation` per prefix index for the whole query, so the neutral picker's 25 points share one tile cache. `mask.sample-input` answers from `MaskInputPixel::linear` of the prefix evaluation: the final colour run’s unclamped `f32` input for a colour layer, or the decoded boundary at the full recipe’s selected width for a spatial layer. Point replacements keep their quantization boundaries, and `sample_before` keeps terminal RGBA semantics. The answer goes straight to the caller with the owner's sequence, as a sample's does. Applying a neutral pick later relies on the existing `expected_revision` and the desktop's entry check.

**Mutations.** A deferred mutation (an action, a `mask.*` command, `draft.set`, `draft.reapply` or a commit) is parked on the owner as `ParkedRead { client, request, response, key, rounds }`, and a `PointCall` evaluates its reads and posts `OwnerMessage::PixelsRead { ticket, result }` back to the owner instead of answering the caller. On receipt the owner compares `PixelReadKey { asset_id, entry_id, asset revision, draft id and draft revision (if any), prefix_hash, input boundary width and input mode, source fingerprint and development }` with the current state; if equal it installs the answers as the call's `PixelMemo` and runs the request again, and if not it discards them and runs the request again, which defers anew. Each pass is a round; more than `MAX_PIXEL_READ_ROUNDS` (4) refuses with `conflict` ("the stack changed while its pixels were read; retry") or, when every round was answered but the plan kept asking, with `resource-limit`. Parked calls share the point worker's `POINT_QUEUE_CAPACITY` (a full queue refuses at once; the refusal names "point samples, queries or pixel reads"), and a disconnect drops its client's parked calls. A retried request is recorded only when it is finally answered.

**Draft memo.** A draft's reads are memoized in the client's session beside the draft (`Session::pixel_memo`, at most `MAX_PIXEL_MEMO` = 32 answers, keyed by `PixelReadKey` plus index and position) and cleared by `draft.begin`, `draft.reapply`, `draft.cancel`, commit and any key change. The seed of a colour-limited stroke is fixed within a mask draft, so a stroke reads it once: the first `draft.set` waits for one seed read (one tile set, estimated 15–40 ms at 24 MP), and later ticks and the commit answer from the memo. Because `draft.set` is a synchronous desktop call (rule 12), that first wait is on the desktop thread; the owner and other clients are not blocked.

**Point samples.** `render.sample` behind Detail is unchanged in route. An estimate miss behind Detail reduces the whole Detail output serially on the point worker (seconds at 24 MP); the reduction stays serial, `PointCall` gains a `Cancel` that a disconnect trips, and the case is measured.

## Masks, presets and history

Every control is available on the global target or an existing mask through the host's optional `mask` field. The host blends the completed Detail result against that layer's input in linear light as `(1 − M) · in + M · u`, the spelling that is bit-exact at `M = 1`. Halos read unmasked neighbours; masking limits the write, not the neighbourhood. Zero coverage returns input exactly under the host's finite and signed-zero rules; full coverage equals unmasked processing bit for bit. No full-resolution mask buffer or stored edge-mask artifact exists. Sharpening Masking is a transient local guide multiplied into sharpening only, never a host mask.

Global Detail precedes masked Detail, and masked instances follow the mask list and `mask.reorder`. Each instance denoises then sharpens its own input, so a masked Detail adds to global Detail and overlapping masks process repeatedly. Masked Detail and masked Presence layers count together against the shared `MAX_MASKED_SPATIAL_LAYERS` (4); the fifth is refused with the existing message, and the user guide says the cap is shared.

Range masks read each operation's input and may select differently at Detail than at Basic. A value-based overlay or thumbnail keeps the first-bound-layer input rule. Behind Detail it is answered through the **input-grid cache**:

- `InputGridKey { source, prefix_hash, domain, transform, region, cells }`: the exact source identity, the restoration prefix's hash and domain prefix, the geometry tail's `GeometryMap::mapping_sha256` (including nonlinear Lens and Perspective steps), the requested region and the cell dimensions.
- `InputGrid` holds, for every cell, the restoration prefix's output at the content pixel that cell reads (`[u16; 3]` wide values on JPEG, `[f32; 3]` on RAW, which is exact because every value a spatial prefix answers is an `f32` widened), plus an outside marker. It is built by grouping the cells by the stage-aligned tile that holds them and evaluating each tile once through the render's tile function and parallelism; a tile holding fewer than `tile area / window area` cells evaluates each cell through a window of its pixel grown by the prefix's summed halo instead, which region/full exactness makes identical. Cancellation is checked per tile; a cancelled build stores nothing.
- Each overlay worker owns one `InputGridCache` of at most one grid: the mask-coverage worker and the Masks-panel thumbnail worker. Grids above `INPUT_GRID_MAX_CELLS` (8,000,000, the proxy pixel bound; 48 MiB on JPEG, 96 MiB on RAW) are refused by name. `Evaluation::mask_overlay_coverage` and `Evaluation::mask_coverage` take the worker's cache.
- A cell's input is the cached prefix value run through the remaining prefix layers up to the mask's first bound layer, pointwise, `O(remaining layers)` per cell (`MaskPixels::Grid`). A mask inside a colour run reads its unquantized `f32` input, including extended values; the query and grid use that same input rather than encoding the truncated tail to RGB16. A mask on a spatial operation reads the materialized boundary at its compiled width. Point replacements retain their required quantization. The remainder must compile to colour and pixel operations with no boundary; a prefix holding a spatial layer after its leading restoration run (a mask bound after Presence) keeps today's refusal and its sentence.
- Mask edits and Basic, curve or mixer changes reuse the grid; a restoration-prefix change rebuilds it, about one full-resolution Detail pass over the touched tiles per worker (estimated 0.4–0.6 s at 24 MP for a dense overlay, far less for the 28 × 19 thumbnails). While it builds, the overlay shows updating. Adding an earlier Detail target changes the key and never creates a circular dependency or shows coverage from another stage.

Native presets capture, apply, export and import the patch through discovery, including ancillary fields and zero strengths; presets address global settings only and leave masks untouched. Lightroom sharpening and noise-reduction keys stay unsupported with per-setting reports whose reasons become "Lightroom sharpening is not mapped to Luxforge Detail" and "Lightroom noise reduction is not mapped to Luxforge Detail" (today they say Luxforge has none); the `Unless` rules are unchanged.

One gesture commits one attributed action on release, key-up or Enter; Escape or focus loss cancels; a no-op adds no row; external changes keep the draft with Discard and Reapply. Resets, preset application, mask targeting and history labels use the same action path. Original has no Detail effect. Missing or disabled Detail keeps recipes and history and refuses affected render, analysis, sample and export rather than omitting processing.

## Cross-plan rules

Detail, Tone curve, Lens and Perspective share these host contracts:

- **Order.** `linked_modules` and the panel: Presets · (Pixel) · (RAW) · Basic · Tone curve · Detail · Presence · Colour mixer · Transforms · Lens correction · Perspective · Crop · Vignette · (Controls). The registry array, its doc comment and the order test in `registry/tests.rs` cover this order.
- **Compile context.** `CompileStage` is threaded through `ToolModule::compile`, `FieldPatch::compile` and `compile_bound`; stage-independent modules ignore its scale. Lens freezes a dimensionless scale in its payload and does not need it.
- **Field patches.** `modules/field_patch.rs` supports Tone curve's curve values, Detail's restoration shape, Lens's geometry shape and non-presettable actions, with shared framework tests.
- **Queries.** `Planned::Query` is the one route for pixel-reading queries through a spatial prefix. `query.sample-curve` reads no pixels and stays an owner query. Lens warp point work (bounded mapping and four taps) stays on the owner; only spatial prefixes use the point worker. Point queries cost `O(layers)` unless a spatial layer precedes the sampled stage.
- **Generated and registry files.** The descriptor snapshot `fixtures/modules/builtin-descriptors.json`, conformance `KNOWN`, smoke `SCENARIOS`, the `xtask/src/fixtures.rs` table and the reference crate's `lib.rs` and `tests/studies/main.rs` are regenerated or re-added after each rebase; the snapshot is never merged by hand.
- **Render passes.** Detail uses `RenderPass::Spatial` (0.25 MP) until measured.
- **Preview.** Detail's settled Fit and prefix cache and Lens's mapping identity on overlays both edit `app/preview.rs` and `ProxyApproximation`; combined tests cover both contracts.
- **Measurements.** Timing runs only after all feature work, sequentially on a quiet host, never beside another plan's builds.
- **Masked spatial cap.** `MAX_MASKED_SPATIAL_LAYERS = 4` is shared by masked Detail and masked Presence.

# HDR exposure merges

Status: implemented on the M4 Mac with synthetic RAW brackets, its photo-sized costs measured ([evidence](#evidence-and-acceptance)); natural-bracket quality is unqualified, as no natural bracket was available. The owner requested this workflow and selected **RAW brackets only**, with **automatic alignment and deghosting**, on 2026-10-07 ([decisions](../decisions.md#hdr-exposure-merges)), and authorized its implementation on 2026-10-10.

## Outcome and boundaries

A bracket becomes one editable HDR photograph in Select. **Import merged** creates it in the catalog; **Pick merged** creates it and adds it to the current development set by default. Both keep Select open, make the result active, and collapse its inputs beneath it. The result is virtual in the grid, with durable, immutable pixels on disk and its own recipe, history, folder and collection memberships. Opening, editing or exporting it never requires another merge.

The originals remain where they were, byte-identical and independently selectable, pickable and developable. Creating a merge does not develop every input into a catalog photograph. Removing or undoing the merge exposes the originals again and retains the result and its edits for restoration. A merge is a library operation, not a layer in every input's editing history.

This design covers one selected RAW bracket at a time, supported local RAW source files, automatic alignment/deghosting, stored linear results, source provenance, persistent stacks, Select and Develop integration, command parity, recovery and bounded jobs. It does not cover JPEG bracket inputs, batch merge automation, live fusion during edits, editable alignment meshes, manual ghost masks, focus stacking, super-resolution, new HDR export formats or HDR monitor presentation. Export uses the existing SDR JPEG contract. There is no DNG-writing requirement: an internal lossless float source is sufficient.

The reusable boundary is a **derived image source**, a merge kind and input provenance, and a result-led stack. Only `hdr` is accepted today. [Panorama merges](panorama-merge.md) are planned as the second kind; their plan generalizes this boundary (kind-tagged provenance and commands, nullable stack offsets, a shared merge lane with band-read spools, catalog format 15) and updates the stored shapes and commands below when it lands. Inputs are original files or original-backed catalog photographs, never another generated result, so this does not introduce a generalized processing graph.

## Grid workflow

### Creating and selecting a result

The bracket header offers **Pick merged** and a secondary **Import merged**, alongside the existing Pick all. The same actions appear in the selection menu when 2–9 suitable frames are selected, including frames that automatic grouping missed. A detected moment is a suggestion: the selected identities, not a recomputed moment or a guessed neighbouring frame, define the request.

| Action | Successful result | Development set | Workspace |
| --- | --- | --- | --- |
| Import merged | Catalog HDR asset; active result tile; collapsed input stack | Unchanged | Stay in Select |
| Pick merged | Same asset and stack | Append the result once, by default; preserve current members and order | Stay in Select |
| Pick an existing merged result | Reuse its stored pixels and edits | Append once | Stay in Select |
| Pick an input frame | Ordinary file pick, or add an existing catalog photograph to the set | The merge's membership is unchanged | Stay in Select |

“Pick merged” is deliberately more direct than ordinary file picking: it does not leave three source picks waiting for Develop N, and needs no second Develop press for the result. The action's hint says “Merge HDR and add to Development set”. It neither replaces the current set nor automatically adopts a new editing photograph. If no set exists, create a one-result set; the filmstrip is shown when Develop is next opened. Import merged is the explicit catalog-entry exception to the current rule that only developing a file enters the catalog. It never copies an original.

Before starting, use the existing event-to-catalog-folder proposal, or the common selected catalog folder; mixed catalog folders default to the reference frame's folder. Default choices need no extra confirmation. A compact optional **Merge options…** form exposes the folder and provider parameters; all have schema-described equivalents. (Planned in the desktop: the [merge preview](panorama-merge.md#the-merge-preview) replaces it and opens first; its commands are [built in the core](#the-merge-preview).) Removable inputs use the current removable-media disclosure and any already authorized copy-selection mechanism; the saved result remains usable after the card is removed, while rerunning still needs the inputs. Do not add a second approval round for an action the person just requested.

The result is named after the reference frame with “HDR”, and carries an **HDR · N exposures** badge and a stack disclosure. During work, show one pending merge row with progress and Cancel, not a completed photograph. Do not hide originals before success. Publication makes the asset, provenance, stack, optional set membership and one attributed library change visible together. Failures leave these unchanged and name the offending input or stage. Duplicate requests return the same job/result, including after a restart, rather than creating another asset.

For the same verified inputs and resolved parameters, an active matching result is reused. Import merged selects it without another journal change; Pick merged only journals a new set membership if necessary. If the matching result is in Removed, offer **Put back merge** rather than restoring it silently. To rerun with different options, explicitly create a new result and independent history; never replace an existing source beneath its edits. A source input may belong to only one active collapsed merge stack; a second merge of overlapping inputs is refused with the existing stack named, until the person removes that merge. Permanent provenance is not limited to one use.

What the desktop's Select draws of this workflow (`crates/luxforge-app/src/{state,app,view}/select_merge.rs`); every decision and every word of refusal is the owner's. Planned: the owner chose on 2026-10-11 that Pick merged and Import merged open a [merge preview](panorama-merge.md#the-merge-preview) first, replacing Merge options…, with ⌥-click merging at once as today; the [boards](merges/hdr-preview.png) draw it. The header's title stays whole while anything else can give way to it: the evidence tag goes first, then the pick count, then the actions from the first; only Pick merged shortens the title, and goes last. A canvas button carries no tooltip, so the hints are the menu's.
- **Selection menu.** A right-click over files selects the cell if it is not selected. With 2 or more frames selected the menu offers Pick merged ("Merge HDR and add to Development set") and Import merged ("Merge HDR into the catalog only"), each with its hint under it, and Merge options… with the frame count. Opening it plans the selection at once (`merge.plan` of the selected files by identity, or `targets: selection` when a selected row is not a file), and a refusal disables both merges with the plan's reason as their tooltip. On a result alone it offers Expand or Collapse stack (`S`), Show all N originals while the view has filter conditions, and Remove merge; `Delete` over files is Remove merge of the active result.
- **Starting.** One owner task sends `merge.plan`, then, when the plan proposes no folder and none was chosen, `folder.create` of its `suggested_folder`, then `merge.create` with the plan's `plan_id` (Pick merged adds `add_to_development_set: true`) as the desktop's actor. The desktop runs one merge at a time. An exact match in Removed opens a notice over the grid offering **Put back merge** (`merge.restore`) and Not now.
- **Merge options….** A sheet listing each frame with its exposure, stepped by a third of a stop (an `hdr.exposure_overrides` entry by path; Auto takes it away), and Reference; Alignment and Deghosting, each Auto or Off; and the folder: the plan's proposal, its suggested new folder, or any catalog folder. Each change plans again; a refusal is shown in the error colour. Cancel, Import merged and Pick merged close it.
- **Running.** In the view it was asked from, one row before the merge's first frame says "Merging HDR · N exposures" with the job's progress message ("Reading 2 of 3", "Aligning", "Saving") and a bar while the fraction is known, and Cancel, which is the activity board's `job.cancel`. A failure turns the row into "HDR merge failed · N exposures", naming the input ("DSC_0002.NEF: …") or else the stage ("While aligning: …"), with Dismiss; a cancelled merge says "Cancelled the merge · nothing was added" in the status bar.
- **Result.** The view is read again with the result selected, active and scrolled into view, in Select. Its cell carries the badge "HDR · N exposures" with a chevron, "HDR · N" where the long words do not fit beside the check (the default cell), and only its icons in the smallest cells; a press on it or `S` sends `stack.set-expanded`, collapsed ↔ expanded, and `S` on an original collapses its stack. An original's footer is its EV offset; a note over its photograph says why it has no file, that it is outside the filter, or, where the filter left its leader out, that it is in an HDR stack. The Info panel's band says "HDR · N exposures" ("Original 2 of 3 · −2 EV" for an original), In the Development set, how many originals are beneath it, Expand or Collapse stack and Remove merge.

### The stack and the originals

The saved stack has a stable identity independent of an index `FileId` or computed moment. Its leader is the result; its members are the exact input identities in deterministic capture/request order, with their EV offsets. It starts collapsed. Clicking the disclosure or `S` expands it inline, showing the result followed by the originals. Expanding is view state, makes no library change, reads no pixels solely to expand, and is accessible through the command service.

Inputs retain their own badges, previews, metadata, picks, catalog identities and recipes. A RAW and its matching JPEG are alternative records of the same exposure, not two different bracket frames: reject such duplicates within a request. Picking a source never clears another source's existing pick or removes the result from the development set. Original picks are not consumed by merging. An input that was not developed remains a file/provenance row, even when reached through a stack in a catalog view; it joins the catalog only through ordinary Develop.

A result in the current development set carries an accent check labelled **In Development set**. Over files, Picked includes ordinary picked files and merged results in that set; Develop N still counts only file picks waiting to be developed, because the result is already a catalog photograph. Moments without a pick treats a result's set membership as a decision for its bracket; Import alone does not mark the bracket picked. These facets come from the same authoritative set/pick state and refresh after another client's change.

Over a folder, event or card, inject a result whose active stack has an input in that source; apply the result's metadata/filter conditions to the result, and collapse only members that actually occur in the view. In catalog views show catalog results and catalog originals, with undeveloped inputs available through stack expansion. A missing or offline input still has a provenance row with its reason. Removing/rebuilding the disposable index cannot erase a merge, its stack or its input identities.

Filters act on each item's own metadata. If a hidden input matches but the result does not, show the matching input normally with its stack badge; never conceal a matching pick or search result behind a nonmatching leader. If the result matches, disclosure explicitly offers **Show all N originals**; children revealed solely by that action are labelled outside the current filter. Counts distinguish photographs/results from the N inputs; a collapsed cell's selection targets the leader alone. Selecting a stack or its inputs requires an explicit selection action, never an implicit “all hidden children”. Stable ordering uses the reference capture time and the result's asset ID as a tie-breaker; overlapping sources do not duplicate its tile within a view.

## Remove, undo and retention

**Remove merge** on the result means “Remove this HDR photograph and show its originals”. It moves the result to Removed, deactivates the stack and removes its development-set memberships in one library change. Original files, ordinary picks, developed originals, their recipes and collection memberships remain. The result's edits, versions, catalog folder, collections, provenance and pixels are retained. General Remove from catalog uses the same semantics for a merge result. Removing an original-backed catalog photograph does not remove its file or invalidate the saved result; its provenance remains accessible.

Select's library Undo of merge creation hides the generated result, deactivates its stack and reverses only the set membership introduced by that change. It retains the generated asset internally with its immutable history and source references; do not reuse ordinary Develop undo, which deletes an unedited asset and refuses edited ones. Undo is allowed after editing the result because those edits are retained, not discarded. The existing per-actor journal's conflict checks still apply to subsequently changed visibility, stack or set-membership items, and return an all-or-nothing named conflict. Develop's Undo continues to undo photo edits, never merges.

Redo, Put back merge, and undoing Remove restore the same result, source bytes and edits without running the algorithm. Creation undo retains a recoverable result in Removed, labelled as an undone merge; restoration is journaled, not an implicit rerun. Restoring a stack is refused if another active stack now claims an input. Set-membership inverses remove or insert only the named result, preserving unrelated later members; a genuinely conflicting change to that member refuses undo rather than overwriting a whole set snapshot.

The stored shape (`crates/luxforge-core/src/library/merge.rs`, catalog format 15): `merges` records each merge once, immutably — its kind (`hdr`, or `panorama`, which this build cannot make: see [panorama merges](panorama-merge.md#generalizing-the-merge-boundary)), its result photograph, the source that photograph holds, an exact-match key (the SHA-256 of kind, provider and version, each input's path and signature in order, and the kind-tagged parameters) and the versioned provenance document (`MergeProvenance`, format 2: kind, provider, inputs with path, volume, signature, optional catalog photograph and frame interpretation, the parameters tagged by kind (`{"hdr": …}`), and the resolution tagged by kind: for HDR the resolved exposures, common development, registration, coverage, motion and fusion diagnostics). `merge_inputs` is the stack's members in the stack's order with their EV offsets (HDR's; null for a kind with none), keyed by path and the optional photograph, never by an index row; a stack's reference original is read from the provenance, never from a zero offset. A catalog of an earlier format, or a provenance of another format or of a kind this build has no reader for, is refused as `incompatible` and kept as it is. The merge's identity is its stack's. Its state, `active`, `removed` or `undone`, is `merge_stacks`, the library journal's `merge-stack` item; an active stack claims each input path in `stack_claims`, one stack a path, and writing `active` over a path another stack claims is refused naming that stack. Publication writes the result, its source reference, the merge and an active stack in one owner transaction and records one library change whose `asset-removal` and `merge-stack` items go from Removed and `undone` to visible and `active`, so the generic undo produces the retained, undone state and redo restores it; a caller's own items, such as a development-set membership with its item-level inverse, join that change. Remove and Put back of a result carry its `merge-stack` item in the same change, with a `set-member` item for each development set it belongs to (Remove) or that the removal took it out of (Put back), in the one function both use. A Develop's send-back refuses a result as a merged photograph. Format 15 also holds `development_sets` and `development_set_members` and the `set-member` item ([catalog](catalog.md#hdr-stacks-and-the-development-set)).

Only the existing explicit **Empty Removed** operation may permanently discard the retained generated photograph and its history. Its confirmation counts saved merges and explains that undo will no longer restore them; it never deletes bracket originals. Source chunks are collectible only after no retained asset/history/source reference, merge undo record that can restore it, or live publication references them. Purge makes journal operations on the deleted result conflict, as ordinary catalog purge does. No background cache eviction, stack collapse or input removal can collect a saved HDR source.

## HDR processing contract

The input and motion scopes are decided: RAW-only brackets, automatic alignment and deghosting. Numerical algorithms, thresholds, backend and layout details are delegated engineering choices within this scope; do not add an owner-review, reference-matching or research gate before implementing them. Pin any added dependency, keep its notices and record manual reviews as deferred.

### Validating and resolving exposures

Accept homogeneous supported RAW recording modes from one body. JPEG inputs, including mixed RAW/JPEG requests, are refused with the RAW-only scope named; existing JPEG browse/edit/export behavior is unaffected. Do not mix cameras, monochrome and colour, image dimensions, aperture, ISO or focal length in one merge. Initial bracketing is shutter/bias based; variable aperture changes depth of field and variable ISO changes noise/response, so reject them explicitly. Unknown body metadata may use consistent recording/colour interpretation, dimensions and robust image evidence; a grouping label alone never establishes suitability.

Resolve one deterministic reference frame: the unique zero-bias frame when present, otherwise the median exposure, with capture order breaking ties. Its upright coordinates, common RAW white balance, scale and metadata anchor the result. Resolve relative **effective exposure** once, from shutter/aperture/ISO when usable, else recorded exposure bias when it is the available encoding of the bracket; never add those two scales. The result's middle exposure remains approximately the reference frame's brightness. Preview-brightness grouping offsets are not calibrated exposure values.

For absent or contradictory exposure metadata, fit relative offsets from bounded, aligned, unsaturated image samples, with recorded residuals and confidence; refuse ambiguous/insufficient fits. The optional options form/API allows explicit per-input EV overrides and reference selection. Validate distinct effective exposures and enough usable overlap before full fusion. Every saved offset records whether it came from metadata, a measured fit or an override. A merge that cannot recover additional usable range reports that outcome, and does not claim recovery of measurements saturated in every exposure.

### Working pixels and fusion

Read original pixels through the shared verified source/development paths, not camera previews, current source recipes, presets or display renders. A catalog input's edits remain independent and are not baked into the merge. RAW inputs use the reference frame's common sensor white balance, qualified demosaic, required embedded optical corrections and camera calibration into **float32 linear sRGB/D65** before fusion. Optional recipe lens correction is not copied or applied twice. Bayer's current gain-dependent demosaic clipping is a known limit ([RAW contract](initial-raw.md#pixel-and-color-contract)): retain sensor clipping evidence, reject/downweight samples affected by clipping, and do not change the shared demosaic algorithm as hidden scope.

Fuse exposure-normalized samples with recorded clipping/noise-aware weights. Preserve finite negative gamut components and values above one until the normal SDR display/export boundary; weights are nonnegative and normalization is explicit. Alignment/deghost decisions use luminance/validity evidence without clipping the retained RGB. All-invalid regions keep a deterministically selected best available reference observation and a limitation flag; do not insert unexplained black pixels, infinities or synthetic recovered highlights. The result stores headroom rather than a tone-mapped JPEG or exposure-fusion look.

The immutable result has fixed merge-time sensor WB/calibration. Develop offers ordinary high-precision Basic exposure, tone, relative RGB Temperature/Tint, curves, mixer, Detail, masks and geometry through their declared source applicability; there is no sensor-RAW WB section or camera-look matching for a source without a mosaic. Further WB changes are relative RGB edits. Required optical corrections are baked and reported so automatic lens correction does not apply them again. New results start with a neutral editing recipe and the existing SDR boundary; no silent auto-tone or new appearance look is baked into the source. An explicit rerun is how different merge-time WB/parameters produce another source; it never mutates an edited result.

### Exposure resolution and fusion equations

The provider's numerical core is `luxforge_core::merge::hdr`: pure functions with no file, catalog or job work, which the merge job composes with source development, alignment and storage.

- **Suitability** (`validate_bracket`) checks, in order: 2–9 inputs; no identity twice; no RAW and JPEG of one exposure (one body, recorded instant and shutter/aperture/ISO/bias); RAW only; then make/model, recording mode, monochrome/colour, upright dimensions, aperture and focal length (within 0.1%) and ISO against the first input. A value recorded on one input and not another is a mixture; values absent on every input (an unknown body, a manual lens) agree. Each refusal is typed and names the input.
- **Exposure.** An offset `o` is in stops of exposure from the reference; its samples are scaled by `2^−o`. Settings give `log2(t)` when every input records a shutter time (aperture and ISO are equal by validation); else the bias when every input records one; never their sum. Settings and a varying bias are contradictory when they differ by more than 0.5 EV for some input, or when the settings do not vary. The reference is the requested input, else the unique zero-bias frame, else the median metadata exposure (lower middle for an even count, capture order breaking ties), else, when every input is overridden, the one overridden to 0 EV. Overrides are offsets from the reference, whose own must be 0; overrides that leave the reference undetermined are refused. Offsets must lie within 16 EV of the reference and at least 0.2 EV apart.
- **Measured fit.** Absent or contradictory metadata yields a fit plan: the reference (provisional, the capture-order middle, when nothing names it), aligned to before sampling. At most 65,536 aligned points are gathered on a grid; an input's Rec. 709 luminance is usable when its sensor level is within [1/256, 0.8]. For each pair with at least 64 shared usable points, the median `log2(Y_a/Y_b)` and its robust spread (1.4826 · MAD) are taken; offsets are the count-weighted least-squares solution with the reference at 0. An input unconnected to the reference is refused as insufficient overlap; a pair spread above 0.25 EV or an RMS residual above 0.1 EV as ambiguous. Confidence falls linearly from 1 to 0 at either threshold. A provisional reference is replaced by the median measured exposure and the offsets rebased; alignment is then anchored on the final reference.
- **Sensor clipping evidence** (`SensorClipModel`). A developed pixel's camera RGB is `rgb_cam⁻¹ · rgb`. Channel `c` reaches its sensor ceiling at its gained sensor white `g_c`, or for Bayer at `min(g_c, 65536/65535)` because RCD clips each gained site; the sample's level is the largest `camera_c / ceiling_c`, stored as `floor(level · 32768)` in 16 bits, or clipped at 0.999 and above. Demosaic interpolation and post-demosaic DNG corrections make it approximate near saturated sites; a lift over-reports clipping. Every saturated own site of the supplied Z6 and X100VI files reads as clipped (the ignored `supplied_raw_saturated_sites_read_as_clipped`, given `LUXFORGE_HDR_RAW`). Alignment resamples a level as the largest its footprint reads.
- **Fusion** (`fuse_rect`) of one rectangle of at most 1 Mi pixels, per pixel and channel in `f64`, rounded once to `f32`: `h(f)` is 1 up to 0.8, the smoothstep `u²(3 − 2u)`, `u = (0.95 − f)/0.15`, to 0 at 0.95, and 0 when clipped; `w_i = 2^o_i · h(f_i)` (the inverse variance of a shot-noise-limited normalized sample); `fused = Σ w_i · 2^−o_i · x_i / Σ w_i`. Signs and values above one pass through. Where every weight is zero the shortest exposure's normalized sample stands, flagged all-invalid. A motion selection of input `k` at confidence `c` gives `(1 − c) · fused + c · 2^−o_k · x_k`, flagged, and separately flagged when that sample is past the roll-off. Integer diagnostics aggregate over rectangles: highlight-extended pixels (the reference in its roll-off and a shorter exposure usable), shadow-extended (the reference below 1/64 of its ceiling and a longer exposure usable above it), all-invalid and motion counts; with neither extension the outcome is no additional usable range.
- **Evidence.** `cargo test -p luxforge-core hdr_merge_fusion` checks every refusal and resolution rule and the fit, and compares complete fused buffers with the independent f64 reference (`luxforge_reference::hdr`, an idealized per-pixel RAW camera with sensor white, the Bayer input ceiling and noise) within `1e-6 · max|reference| + 1e-9` per channel, noise-free recovered radiance with the scene within `1e-5 · max|scene|`, measured offsets within 0.02 EV, and bit-identical output for any split into rectangles. A one-rectangle CPU result is deterministic; the GPU is not involved.

### Alignment, coverage and motion equations

The same library's `proxy`, `align`, `coverage`, `resample` and `deghost` modules: pure functions over bounded data, with `cancel` checked between inputs, pyramid levels, iterations and passes.

- **Analysis proxy** (`AnalysisProxy`, `ProxyBuilder`). Each developed input is streamed, band by band, into a proxy and then dropped: the smallest integer box factor `f` bringing the longer side to at most 1024 (a 6048 × 4024 frame reduces by 6), whole boxes only. A proxy pixel holds `log2` of its box's mean Rec. 709 luminance and the box's largest and mean sensor level, 8 bytes (at most 8 MiB per input). It is usable for comparison when its mean level is at least 1/256 and its largest at most 0.8. Frames under 64 pixels a side are refused.
- **Coordinates.** Full-resolution upright pixel indices, pixel centres at integers. An input's `RigidTransform` maps a reference point to the input point that recorded it, `q = c + R(θ)(p − c) + t` about the frame centre `c`: rotation and translation, no scale (the focal length is equal by validation). Proxy pixel `i` stands for full-resolution `f·i + (f − 1)/2`.
- **Registration** (`register`). Exposure-invariant evidence: log luminance, where a stop is a constant offset, compared only where both frames are usable. Pyramid levels halve by a `[1 3 3 1]²/64` weighted mean of usable pixels until the longer side is at most 64 (at most six levels). The search runs on the coarsest level on which each frame of the pair has at least 256 usable pixels: the coarsest for an ordinary exposure, a finer one for a wide bracket's extreme, which records only a few percent of the frame (the +4 EV frame of a five-frame ±4 EV bracket, 4% of it). There, smoothed by `[1 2 1]²/16` and replaced by each value's rank among its frame's usable values (invariant to exposure and response, and bounding a far darker or brighter moving subject's pull to its area), the normalized correlation is searched at every whole-pixel shift within a quarter of the level and then every whole degree within ±4° around the best shift, each over at least a quarter of the smaller frame's usable pixels there (at least 64): for two frames usable everywhere a quarter of the level, for an extreme exposure a quarter of what it recorded, all of which its neighbour may share. A frame with fewer usable proxy pixels than an accepted fit's 1024 samples is refused (`AlignmentSupport`) without a search. The match needs correlation 0.5, no other local peak at least 3 coarse pixels away within 0.02 of it, and the reference's log-luminance structure tensor needs at least `10⁻³` (EV per coarse pixel)² in its weaker direction, over its usable pixels on the coarsest level and over those the match shares on the searched one. Gauss-Newton then refines rotation, translation and a brightness offset `β` from the searched level to the proxy, minimizing Huber-weighted (`k = 1.345σ`, `σ ≥ 0.02` EV) residuals `L_input(q) − L_reference(p) − β`, bilinear in the input, over at most 2¹⁸ samples and 30 iterations a level. Each level is read through a prefilter: the separable binomial `[1 4 6 4 1]/16`, or `[1 2 1]/4` where the fit's residuals there already predict more than 0.03 level pixel (noise, not detail, limits it), of the pixels whose whole neighbourhood under it is usable, and only those; as it is when filtering keeps under 80% of the samples the two frames share (an extreme exposure's narrow recorded regions, whose eroded edges would pull more than the detail does) or under 256. Unfiltered, detail near the level's sampling limit, softened by the bilinear sampling of the input alone by an amount that depends on the sub-pixel phase between the grids, and aliased differently by each frame's grid, pulls the fit wherever the grids are a fraction of a pixel apart: up to a few tenths of a pixel, the more the further the exposures. On the proxy, an accepted fit has at least 1024 shared usable samples, at least half of them within 0.25 EV, a one-sigma position error its residuals predict of at most 0.1 proxy pixel, and a motion within 3° and 8% of each side; otherwise a typed refusal (`AlignmentSupport`, `LowTexture`, `AmbiguousAlignment`, `SevereMisalignment`). The predicted error recorded adds, in quadrature, 0.03 proxy pixel that the residuals do not show: what the sampling and the interpolation leave through the prefilter, the same in every sample (the synthetic brackets' well-exposed handheld frames land up to about 0.05 proxy pixel from their motion). An accepted fit that moves no frame corner by more than three of its predicted one-sigma position errors, nor by more than 0.1 pixel (the registration's strictest declared accuracy), is recorded as the identity with how far it was (`snapped_px`): a still frame, whose fit lands a few hundredths of a pixel from no motion (about 0.01 for the ±2 EV frames of the default synthetic still bracket, 0.02 for a −3 EV frame, 0.04 for a +3 EV frame and 0.02 for a +4 EV frame), is copied exactly and the coverage keeps the whole frame, while a handheld frame's motion of pixels is always fitted. An input the reference cannot fix (typically a wide bracket's extreme, sharing only a narrow usable band with it) is fitted to an already aligned input, the furthest in measured brightness first, and the motions composed under the same acceptance and limits; with none, its refusal against the reference stands. Each input records its transform, correlation, samples, inlier fraction, residual, brightness, uncertainty, confidence, any chained input and any snap to the identity. Scratch is about 24 bytes a proxy pixel for one pair, and up to 20 more when the search reads a finer level, the most on the proxy itself, released before the refinement, whose prefiltered pair adds up to 22 more, one level at a time; a search visits the smaller frame's usable pixels at every shift. `AlignedProxies::gather_fit_samples` supplies a measured exposure fit's bounded samples from proxies registered to the plan's reference; `register` takes any reference, so a provisional one the fit replaces is registered again from the same proxies.
- **Alignment off** keeps every transform the identity but refuses another orientation, or a whole-pixel displacement of at least 2 coarse pixels whose correlation is 0.5 or more and at least 0.05 better than in place (`FramingMismatch`); the bracket's suitability checks still apply.
- **Coverage** (`common_coverage`). A reference pixel is covered when every transform maps it within `[0, W − 1] × [0, H − 1]`, so every bilinear tap is recorded. The output is the largest axis-aligned rectangle of covered pixels (ties: the smallest top row, then bottom row), with pixels lost reported; result pixel `(i, j)` is reference pixel `(x + i, y + j)`. A rectangle under half the frame on a side is refused (`InsufficientCoverage`).
- **Resampling** (`resample_rect`, `source_window`). One bilinear resample in the linear domain, `f64` rounded once to `f32`, never overshooting; the level is the largest among taps weighted above zero. The identity is an exact copy. A rectangle of at most 1 Mi pixels inside the coverage reads only `source_window`, the bounding box of its mapped corners widened by one pixel (about 1080 × 1080 for a 1024 × 1024 rectangle at 3°); anything outside the coverage or the window is refused, never filled.
- **Motion** (`AlignedProxies`, `detect_motion`, `MotionMap::render`). Proxies are resampled onto the reference's proxy grid (levels by the largest tap). Each input's log luminance is averaged over its usable 3 × 3 neighbourhood and brought to the reference by its resolved offset. A pixel is a candidate where two usable inputs differ by more than 0.5 EV (where either lost part of its neighbourhood, both averaged over the neighbours both recorded usably, so the edge of a still surface one exposure records past its roll-off or under its floor is no disagreement), or where one is past the roll-off while another's neighbourhood, brought to its exposure, stays under level 0.5 (or one is under the floor while the other's stays over 4/256). Candidates are opened by 3 × 3, grown by 3 proxy pixels and labelled into 8-connected regions. A region shows the reference when it records at least 95% of the region at or under level 0.8; otherwise a recorded fallback, the nearest exposure to the reference that does (else the most usable, nearest first, then shorter). Confidence is 1 at least 3 pixels inside a region and falls by a third per pixel (chessboard distance) to its edge. A full-resolution rectangle's confidence is the bilinear interpolation of the proxy confidences around each pixel's proxy position; its selected input is the region's of those four pixels (a 2 × 2 block touches at most one region). Diagnostics count regions, motion pixels, reference and fallback regions, fallbacks no exposure recorded usably, and regions per input. Deghosting off selects nothing.
- **Evidence.** `cargo test -p luxforge-core hdr_merge_alignment` builds brackets from independent generators (`luxforge_reference::hdr_align`: rigid motions, textured, ramped and moving scenes recorded through `luxforge_reference::hdr`'s camera, bilinear resampling and the exhaustive largest covered rectangle) and checks fitted motions within 0.1 pixel at every frame corner (0.15 with noise, and through a 2× proxy 0.25; 0.02 for a turned and shifted frame of a scene with gratings 3.3 and 3.7 pixels apart, at 0 to −4 EV, which the input-only bilinear sampling of unfiltered levels pulled 0.15 to 0.2 pixel) and brightness within 0.05 EV, a still fit recorded as the identity and a third of a pixel's motion kept, a −6 EV input fitted directly on the narrow band it shares with the reference and +6 and ±8 EV inputs chained, exact coverage rectangles, resampled buffers within `1e-6 · max|reference| + 1e-9` with identical levels, one exposure per moving region through `fuse_rect` with the reference preferred and a clipped subject's fallback recorded, every refusal and alignment-off framing, measured exposures from aligned proxies, cancellation at every stage, and the stated bounds. Natural-bracket tuning of these thresholds follows delivery.

### Alignment and moving subjects

Automatic exposure-robust registration for slight handheld rotation/translation and automatic deghosting are included and enabled by default, with alignment Auto/Off and deghost Auto/Off options. Fit a bounded global mapping to the reference using exposure-invariant/normalized multiscale evidence; resample once in the linear domain. Require support and confidence, record transforms/residuals, and refuse an unalignable bracket. Turning alignment off still validates common framing; it does not suppress all suitability checks. Severe parallax, different viewpoints and rolling-shutter distortions are not promised.

Crop to a deterministic valid common rectangular coverage region, without filled borders or upscaling. Report the output rectangle and pixels lost; preserve reference-coordinate mapping in provenance. Deghosting distinguishes radiance disagreement from exposure/clipping, selects one coherent exposure for each moving region, and feathers its confidence boundary rather than blending multiple positions. The default prefers the reference exposure where usable, otherwise a recorded best usable exposure; motion regions may lose HDR coverage. Do not promise reconstruction of a moving highlight no frame recorded correctly. Record aggregate motion/fallback diagnostics, and expose the same controls and errors through UI/API. Manual ghost painting is outside scope.

## Durable derived source

### Where it lives

- `crates/luxforge-core/src/merge/hdr/`: the HDR provider's pure numerics — suitability and exposure resolution (`frame.rs`, `exposure.rs`), sensor clipping (`clipping.rs`), fusion (`fusion.rs`), proxies, registration, coverage, resampling and motion (`proxy.rs`, `align.rs`, `coverage.rs`, `resample.rs`, `deghost.rs`); `merge/job.rs` the bounded job.
- `crates/luxforge-core/src/artifacts/derived_source.rs` and `editor/derived_source.rs`: the stored source, its catalog references, preparation and editing. A derived photograph's `SourceKind` is `Derived`, never sensor RAW.
- `crates/luxforge-core/src/library/merge.rs`, `catalog_types/merge.rs`: provenance, stacks, publication and the lifecycle; `library/development_set.rs`: the owner's development set; `browse/stacks.rs`: stacks in views.
- `crates/luxforge-core/src/api/owner/merge.rs` and `api/owner/library/development_set_methods.rs`: the `merge.*`, `stack.*` and `development-set.*` methods.
- `crates/luxforge-app/src/{state,app,view}/select_merge.rs`: Select's merge workflow; the filmstrip follows the owner's set (`state/develop.rs`).

### On-disk representation and commit

Store the result under the catalog's existing `.artifacts` root, not beside the originals or in the disposable index. Use a small versioned manifest and lossless **float32 linear RGB chunks**, with explicit byte order, layout, dimensions, colour/white point, crop mapping, chunk bounds/lengths and SHA-256 identities. A 60 MP RGB result occupies 720,000,000 uncompressed pixel bytes, already above one artifact's cap. Keep individual objects bounded; do not increase the generic prepared-artifact cache or squeeze source data through a layer's 16-artifact limit. An initial 1024-pixel chunk side fits within 16 MiB per RGB chunk; enforce the existing 16,384 side/128 MP/1.5 GiB decoded-linear limits and at most 256 source chunks. Compression choice is delegated only if it remains lossless and bounded.

The stored shape (`crates/luxforge-core/src/artifacts/derived_source.rs`): every source object lives in `<catalog>.artifacts/sources/`, apart from the derived artifacts' `objects/`, named by the SHA-256 of its bytes and staged through the shared `tmp/`. A chunk covers at most 1024 × 1024 pixels of a row-major grid and holds its red plane row by row, then green, then blue, each sample an uncompressed little-endian IEEE-754 binary32: 12 MiB for a full chunk. The manifest is a JSON document `{format: 1, width, height, colour: "linear-srgb-d65", sample: "f32-le", layout: "planar-rgb", chunk_side: 1024, crop?: {reference_width, reference_height, x, y}, chunks: [{x, y, width, height, bytes, sha256}]}` of at most 64 KiB, and the source identity is `source-` and the SHA-256 of the manifest's bytes. Any other format, field or value, or a grid that does not tile the frame, is `incompatible` and kept. The writer stages, syncs and renames each chunk, then the manifest, and syncs `sources/` once; a reader refuses a link or a `sources/` that leaves the root, a missing object, another length or hash, and a non-finite sample, by the source and chunk it names. Format 14 records each source in `derived_sources`, its chunks in `derived_source_chunks` and the photograph that holds it in `asset_sources`; a photograph's `SourceKind` is `derived` with `{source_id, width, height, colour}`. None of these rows changes, and only Empty Removed deletes an `asset_sources` row. A collection keeps every object a recorded source names and every object a writer of the running process published; a recorded source no photograph holds is released by the next collection, and Empty Removed releases a source with its last photograph.

Add explicit asset-source/manifest-to-chunk references. Source preparation streams verified chunks into one accounted `LinearImage` allocation on a worker; it does not bind every chunk into the generic recipe-artifact cache. Charge the full derived frame to the shared prepared-source accounting and all upload/tile allocations to the existing GPU budgets. Recipe references and source references remain distinct, so collecting an unrelated unreferenced module artifact cannot remove a merged photograph.

Preparation and editing (`crates/luxforge-core/src/editor/derived_source.rs`): `source.prepare` on a derived photograph reads and verifies its manifest and chunks on the source worker, through the plane gate, into one shared `LinearImage` (`PreparedSource::Derived`); the owner only stats the manifest, whose length is the source's signature, and reads catalog rows. A cached preparation reuses the planes with no read or hash, a cancelled one keeps nothing, and opening another photograph evicts them. A damaged or missing source fails preparation, samples, rendering, previews and export by the source and chunk it names, while history stays readable. The frame renders on the RAW linear path with no development: Basic (its relative white balance), curve, mixer, Detail, Presence, masks, geometry and vignette apply as on a JPEG; the RAW development and the look do not. The optics ledger reports every correction as already applied (`derived-source-baked`), so a lens profile is refused rather than applied twice. A derived photograph has no camera preview, so its first catalog preview is its render; `export.plan` suggests no name (there is no original), and a 100% view of the original is refused. The GPU corpus (`fixtures/preview/corpus.json`) holds a synthetic derived source, `derived-merge`, generated by `luxforge_testkit::derived::planes` with negative values and four times diffuse white, published and prepared by the harness as a merge's result.

Provenance records ordered input fingerprints, durable locators and source interpretations, optional existing asset IDs, exposure origins/scales, reference selection, common WB/calibration, algorithm/provider format, resolved parameters, alignment/coverage and motion diagnostics. It is authoritative catalog data, not an EXIF name or an index/moment foreign key. Capture time/place/camera/lens come from the reference, with a declared merged flag, exposure range and input count; the UI never presents one shutter time as a physical single capture for the HDR result.

Write chunks and manifest to bounded temporary storage, hash/sync/rename them durably, then commit source references, the result's Original, provenance, active stack and optional development-set membership as one owner transaction and journal change. Resolve catalog identities and signatures before work and recheck them before publication. A crash before the catalog transaction leaves only collectible unreferenced objects, never a visible half-result. A crash after commit leaves a complete reopenable result; event delivery or client disconnect does not undo it. A retry after restart returns the committed result; an unfinished request is reported interrupted, with no partial asset, and can be explicitly retried under a new request identity. Late cancellation returns the committed result if publication already won; no success is reported before durability. Journal reads/writes never read or hash payloads.

## Jobs, commands and client state

Every method listed here exists in the shared registry, each with its schema and notes (`crates/luxforge-core/src/api/owner/merge.rs`, the job in `crates/luxforge-core/src/merge/job.rs`).

The merge commands are shared by every merge kind ([panorama merges](panorama-merge.md#generalizing-the-merge-boundary)). `kind` is required on `merge.plan` and `merge.create` and optional on `merge.rerun`, where it must be the recorded merge's kind (`validation` otherwise). A schema's `kind` lists only the kinds this build registers a provider for (`crates/luxforge-core/src/merge/providers.rs`): here `hdr`. A request of a kind with no provider, such as `panorama`, is refused `not-ready` with the provider it lacks in `data` (`{kind, provider}`, for example "panorama merging is not available: this build has no luxforge.panorama provider"). HDR's options are the object `hdr: {reference?, exposure_overrides?: [{path, offset_ev}], alignment?: auto|off, deghost?: auto|off}`; a field named after another kind, or an `hdr` object on a request of another kind, is `validation` naming the field and the kind. Each kind has its own input bounds (HDR 2–9, panorama 2–32) and limits (HDR's 16 GiB temporary ceiling and 256 MiB scratch; panorama's 64 GiB and 512 MiB), and every kind shares the one merge lane. A typed refusal's `data` carries `kind`.

`merge.create` is Import merged by default and Pick merged with `add_to_development_set: true`; `set_id` is the set the client believes is current, used only with it. A Pick merged request captures the current set when the owner admits it and is refused with `conflict` at once, naming both sets, when `set_id` is not that set (or there is no set). The captured set rides the job to publication, where the result's `set-member` item joins the publication's one library change (after the result's `asset-removal` and `merge-stack`), so library undo removes the result from the set together with the merge, and nothing else from it. A set replaced, or opened where there was none, while the merge ran fails the whole publication with `conflict` and publishes nothing. With no set, publication starts a one-result set. A request for an exact active match merges nothing: Import answers with no journal change, and Pick appends the existing result as one library change of its own, answered as `change` with `reused: true`, unless it is a member already, when nothing changes; a retry of that request is answered from that change. A request for a merge already queued or running is answered with that job, the first request's intent governing what it publishes. `merge.rerun` takes no set fields. Its publication's change takes the replaced result out of every development set it is a member of, as Remove does (a `set-member` item each, through the same helpers), and, when it was a member of the current set, puts the new result at its place there, after it left; library undo takes the new result out and puts the replaced one back at its place in each set, and redo replaces it again. A replaced result already in Removed is in no set, and the new result joins none.

### The merge job

The merge lane is a library lane of its own: one worker thread, started on the first merge, one running merge and one waiting; a further request is `resource-limit`. No selection, view, workspace change or client disconnect cancels a merge, only `job.cancel`. The job:

- **Reads** each input, the planned reference first, after checking it against the signature the request captured, through the shared verified RAW development at the reference's as-shot white balance, one development at a time and outside the source worker's plane gate, so the merge never waits on a lease the active editor holds, nor the editor on the merge. A running merge therefore adds at most one development of its own beside the editor's prepared sources, reported as `development_bytes`; no total process-memory bound is claimed from the scratch budget.
- **Spools** each development to `merges/<request>/input-<k>.spool` under the artifact root, row-major, 14 bytes a pixel (red, green and blue as little-endian `f32`, then the sensor level as little-endian `u16`), 16 rows at a time, reducing each band into the input's analysis proxy as it goes, and then drops the development. The bracket's spool and result (`n · 14 + 12` bytes a pixel) are preflighted against the 16 GiB ceiling and the volume's free space at admission from the headers' size, when the index or catalog knows it, and from the real size after the first development, before anything is spooled.
- **Aligns** the decoded bracket: validation, exposures from metadata or fitted from aligned proxies, registration, coverage and motion, all on proxies.
- **Merges** each 1024 × 1024 chunk of the coverage from bounded windows of every input's spool, resampled and fused straight into the derived-source writer's chunk buffer, and checks every input's signature again before it answers.
- **Accounts** its scratch by phase against 256 MiB, refusing before allocation; `job.read`'s result while it runs is `{stage, accounting: {scratch_bytes, scratch_peak_bytes, scratch_limit_bytes, temp_bytes, development_bytes}}`, and the phases are `reading`, `aligning`, `merging` and `saving`.
- **Removes** its own spool files however it ends, and as it starts the spool files of any other request folder, which only a stopped process leaves; request markers stay.

The job runs in three stages (`crates/luxforge-core/src/merge/job.rs`): **read and spool** (`JobSpec::read`, into a `Prepared` holding the spool, every input's development facts and analysis proxy, and for a preview its colour proxy), **analyse** (`job::analyse`, into an `Analysis`: the parameters it was made for, exposures, registration, coverage and motion) and **fuse** (`JobSpec::merge`, fusion, the signature checks and provenance). A merge without a preview runs all three (`JobSpec::run`); a merge of a preview fuses only (`JobSpec::run_prepared`), from the preview's `Prepared` and, when the parameters are the ones it was made for, its `Analysis`. The result is the same bit for bit: the stages are the same code in the same order on the same spool and proxies.

Publication is the job's answer, committed on the owner as the job ends: one transaction and one library change, unless `job.cancel` reached the owner first, when nothing is published and the objects written are left for collection; a cancel after publication finds the job `ready`. The result is named after the reference with "HDR" and goes into an existing catalog folder: the folder of the inputs' one event, else the one folder every input photograph is in, else the reference photograph's; otherwise the plan names a `suggested_folder` for `folder.create`, and `merge.create` needs `folder_id`, because undoing a merge keeps its result in Removed and the folder with it.

Each admitted request keeps a marker, `merges/<key>/request.json` (`key` the SHA-256 of its method, actor and request identity; `{format: 1, method, actor, request_id, created_ms, ended?}`), written by rename without a sync, the newest 64 kept. A published request's marker is removed, since the journal answers its retries; a request that failed or was cancelled records its error there. A retry while the job is queued or running, or a new request for the same exact merge, answers that job; after it ends, a retry answers the published merge from the journal, the recorded error, or `cancelled` with `data.reason: "interrupted"` and nothing published when Luxforge stopped first, which a new request identity merges again.

The provider is `{module: "luxforge.hdr", version: 1}`, recorded in every provenance. A merge result's source is `derived`: `source.check` and Missing originals never look at it or record it missing, and `source.locate`, `source.find` and `source.relink` refuse it by name.

`cargo test -p luxforge-core hdr_merge_job` drives the real owner through the registry with several clients on deterministic synthetic brackets (a synthetic camera stands in for the development, so every stage can be held, slowed or failed; `hdr_merge_end_to_end` below covers the RAW path): creation, inspection, reuse, retries, cancellation at every stage and a late cancel, queue pressure, slow reads and a disconnect, inputs that change or vanish, the ceiling, free space, a full disk and the scratch limit, a write failure at every source-publication step and a refused transaction, a restart mid-merge, orphan cleanup, a corrupt chunk after reopening and its rerun, provider changes, and an editor sampling while a merge runs and a merge finishing while the editor's source work is held, with the originals' bytes and an unrelated photograph's recipe unchanged.

`cargo test -p luxforge-core hdr_merge_end_to_end` merges real DNG brackets through the production path. `luxforge_testkit::hdr_bracket::write_bracket` writes 2–9 deterministic 1536 × 1024 RGGB DNGs (SHA-256 pinned by `cargo test -p luxforge-testkit hdr_bracket`) of `Luxforge` `Synthetic Bracket`, a RAW test camera outside the shipped catalog that writing a bracket admits for the process (`luxforge_raw::admit_test_cameras`; the editor admits it only with `LUXFORGE_TEST_CAMERAS=1`, which the `hdr-merge` smoke scenario sets): 0, −s, +s, −2s… EV by shutter time at one aperture, ISO and focal length, with the bias and ordered capture times the index reads, colour matrices, levels and as-shot neutral; the scene, drawn through a lens blur, has a sky and lit window the metered frame clips, a sun no frame records, a doorway only the longest exposure lifts, a colour chart and edges, optionally each frame turned and shifted as a handheld bracket is and a ball that moves in one frame, and its ground-truth linear radiance is exposed. The tests index the folder, check that Select groups it as one bracket from metadata, plan and merge it through the registry with the shared development, and check the provenance (exposures from the settings with the zero-bias frame the reference, every transform exactly the identity when still, with the whole frame covered, and within 0.25 pixel of the generated motion when handheld), coverage, fusion and motion diagnostics, the result through `source.prepare` against the ground truth over flat 8 × 8 blocks (0.5% plus five standard deviations of the generator's noise; a noise-free development alone is within 0.3%), highlights recovered above one, one ball without a ghost, a JPEG export and unchanged originals. Beside the default three frames two stops apart, they merge five frames two stops apart (±4 EV) still and handheld, seven frames a stop apart and three frames three stops apart to the same ground-truth tolerance. Every handheld bracket is held to 0.25 pixel. Over generator seeds, the handheld frames of the brackets the tests merge land within 0.1 pixel of their motion, with noise and without (the −4 EV frame 0.06 to 0.1, the ±2 EV frames under 0.07), except the extremes the reference shares little with: the +4 EV frame of the five-frame bracket 0.14 to 0.15 without noise and 0.09 to 0.28 with it, against 0.07 and about 0.14 predicted, and the +3 EV frame of the three-frame bracket up to 0.16 with noise. Open for natural-bracket tuning: with noise, the +4 EV frame's fit to the reference rests on the reference's deepest shadows and lands 0.1 to 0.25 pixel from a still bracket's identity on about a quarter of seeds, past the 0.1-pixel snap, so that it is resampled rather than copied; the default seed's lands 0.02 pixel away.

### The merge preview

The [merge preview](panorama-merge.md#the-merge-preview)'s commands are built in the core for HDR (`crates/luxforge-core/src/api/owner/merge_preview.rs`, the worker side in `crates/luxforge-core/src/merge/preview.rs`); the desktop still opens Merge options…, which the preview is to replace there.

- **`merge.preview {kind, targets, hdr?, plan_id?}`** is admitted as `merge.create` admits its inputs: a kind with no provider is `not-ready`, a header-level refusal `validation` with the typed refusal in `data`, a stale `plan_id` `conflict`. It closes the caller's previous preview and answers a cancellable `merge-preview` job (activity `merge.preview`, "Preparing merge preview") on the merge lane. The job reads, develops and spools each frame as a merge does, the planned reference first, building a colour proxy beside each analysis proxy, aligns them, and draws the merge from the colour proxies. Its phases are `reading` ("Reading 2 of 3") and `aligning`, and `job.read`'s result while it runs is a merge's `{stage, accounting}`. The answer is a `MergePreview`: `{preview_id, revision, kind, options: {hdr: {reference?, exposure_overrides?, alignment, deghost}}, path?, width, height, diagnostics?: {hdr: {proxy_side, alignment, max_residual_px?, deghost, highlights_extended, shadows_extended, exposures, reference}}, overlays?: {hdr: {motion: [{input, offset_ev, fallback, bounds, outline}]}}, output?: {width, height, scale, source_bytes}, refusal?}`. The picture is a display-referred sRGB JPEG, `<catalog>.index/previews/merges/<preview_id>-<revision>.jpg`; writing a revision removes the older ones. The overlays are in the picture's pixels, and `output` is the coverage the merge would save at scale 1.
- **`merge.preview-update {preview_id, hdr}`** takes the full new options and answers the next revision as a short `merge-preview` job on a lane of its own, so it never waits behind a merge. It reads no frame: a Deghosting change finds the moving regions again and redraws; an Alignment, Reference or exposure-override change registers again on the retained proxies. A newer update cancels a stale one. While the preview is still preparing, the update waits behind it. Options the frames' headers refuse are `validation` at once, as `merge.create` refuses them.
- **`merge.preview-close {preview_id}`** answers `{preview_id, closed}` and discards the preview, its spool and its pictures, cancelling its job. It is idempotent.
- **Refusals.** A typed refusal found while reading or aligning is the revision's `refusal` (`{reason, …, kind, message}`), with no picture, diagnostics or output, and the preview stays open for another setting. A RAW-only refusal while reading leaves no frames, so every later revision answers it too.
- **`merge.create` with `preview_id`.** The preview must be the caller's open one, of the same inputs, unchanged since they were read, with the request's options equal to its latest revision's; otherwise `conflict`. A refused latest revision answers its refusal. The merge takes the preview's spool, proxies and alignment over, reading and aligning nothing, and equals a merge without a preview bit for bit. A preview still preparing is continued behind its own job, outside the lane's bound, never restarted. Duplicate, retry and marker semantics are a merge's. The preview is then gone.
- **White balance.** A preview's frames are developed at the as-shot white balance of the reference planned when it opened. A later Reference change registers again on the proxies and keeps that development, which the merge's provenance records.
- **Bounds.** Each client has one open preview; another client's `preview_id` is `conflict`. A preparing preview occupies the merge lane, sharing its one running and one waiting with merges. A ready preview's spool (`<artifact root>/merge-previews/<preview_id>/`) counts against the kind's temporary ceiling, beside every merge's and every other open preview's (`held_bytes` in a refusal's `data`). Its colour proxies are accounted in scratch. A preview stays until it is merged, closed, idle for 30 minutes (the owner's own wake-up closes it) or its client disconnects; a cancel or a failure while it prepares closes it. A preview publishes nothing and is not a library change. Every merge or preview job removes the preview spools and pictures no open preview owns, which only a stopped process leaves.

`cargo test -p luxforge-core merge_preview` drives it through the registry with several clients on the synthetic brackets: a picture with diagnostics and motion overlays, updates that read no frame and a stale update cancelled, a refusal that keeps the session open, a merge of a preview that reads and aligns nothing and equals a merge without one bit for bit, the lane, the ceiling, idleness, a disconnect, cancellation, restart cleanup and a stale `preview_id`.

## Bounds, recovery and regeneration

Process 2–9 RAW inputs within current RAW admission limits. Retain no N full-resolution developed frames together. Prepare/develop one input at a time, reuse a compatible verified cache entry without a whole-frame clone, and spool aligned working chunks as required. Full fusion reads bounded chunks across inputs with at most 256 MiB explicitly accounted scratch plus one admitted source/development allocation; if the chosen backend needs more, tile/spool or refuse before allocation. Bound feature counts, pyramids, response-fit samples, chunk fan-out, file handles and cancellation latency. A provisional 16 GiB per-job temporary-disk ceiling covers nine maximum-size float inputs plus the result; preflight it and treat it as an engineering limit, not a measured process-memory claim. Cleanup only job-owned temporary paths.

Never block the UI or catalog owner on decode, registration, hashing, encoding, fsync or fusion. A background merge must permit editing a different photograph and ordinary browse/command service work. Avoid a plane-gate deadlock in which merging holds a development while waiting for another; spill/release before acquiring the next source, and account contention with the active editor's prepared source. Do not claim a total memory bound from only the scratch or GPU budgets.

Reopen and render need only the saved manifest/chunks, not any bracket originals. Missing/offline/changed inputs are regeneration diagnostics, not a reason to invalidate a healthy saved source. A missing manifest/chunk or wrong hash makes preparation, samples, rendering and export fail explicitly with the result/object named; cached previews remain available and history/provenance remain readable. There is **no automatic remerge** when a file goes missing. Locate/restore saved data accepts only the exact stored identity. Rerun needs every fingerprint-verified input and the recorded algorithm version/provider; a missing provider/version or changed input is refused rather than generating a silently different source. New parameters or a current algorithm can explicitly produce a new result.

Moving/backing up a catalog must carry its consistent database/WAL and `.artifacts` tree; this feature documents that requirement without implementing the separate catalog-backup programme. Removing the index, collecting caches or taking input drives offline must not change the source-reference closure. Unsupported new catalog/source/manifest shapes are refused without rewriting files; no migrations or historical compatibility fixtures.

## Evidence and acceptance

Ordinary correctness and recovery evidence ship with the working feature. Extensive natural-scene quality refinement and quiet-host timing follow it; unavailable owner brackets do not block synthetic fixtures, numerical correctness, storage, UI or the background journey. Claims remain limited to the sources and workloads actually run.

1. Independent analytical/f64 fixtures verify exposure normalization, weights, reference scale, signs/headroom, clipping/all-invalid fallbacks, alignment/resampling/coverage and moving-region selection. The CPU source/result contract is whole-buffer exact for frozen deterministic fixtures; real GPU outputs are compared to the CPU reference under the already declared output/view tolerance, not demanded bit-identical to it.
2. All originals' hashes remain identical across success, cancellation, failures, undo/redo, removal/restoration and purge. Source recipes/history are unchanged. Index rebuild and catalog reopen preserve stable provenance and stack membership.
3. Crash/failure injection covers temporary writes, chunk publication, manifest publication, catalog rollback and commit/event boundaries; unreferenced cleanup preserves every retained result/undo/source reference. Retry, concurrent mutation and set-replacement checks prove one publication or a named atomic conflict.
4. A real-owner/API client comparison proves both creation modes, reuse, filter-aware stacks, expanded-source picks, independent source development, removal, edited-result creation undo/redo and set membership. Every GUI action sends the documented request; another client's mutations appear live.
5. A background rendered HDR scenario correlates captured frames, owner state and logs: bracket → Pick merged progress → one collapsed HDR tile → expanded originals → source pick → Develop with the saved result → edit → Select removal/undo/restart. It also proves Import leaves the set unchanged and redo never reruns. Existing no-adapter paths and JPEG/RAW journeys remain valid.
6. Derived linear sources render/edit/sample at Fit and 100%, in catalog tiers, masked/spatial/geometry stacks and JPEG export, including negative colours and highlight headroom. Qualify affected GPU source/output/view families against the reference and report unsupported providers explicitly.
7. Once the feature is complete, run quick once, rendered at integration and full only for an explicit milestone claim with the applicable manifest. Final photo-sized measurements report cold/warm merge stages, cancellation, reopen without input reads, temporary disk, peak process/source/scratch/GPU use and editor/browse latency beside merging on 24/60 MP and three/nine inputs. Use a quiet M4 and the host timing lock; native portability evidence is separate from headless checks.

**Verified** on the M4 Mac, with synthetic data only: items 1–3 by `cargo test -p luxforge-core hdr_merge` (fusion, alignment, lifecycle, browse, job and end-to-end), `derived_source` and `development_set`; item 4 by `cargo test -p luxforge-app hdr_merge`; item 5 by the background `hdr-merge` journey (`cargo xtask smoke --scenario hdr-merge`, part of the rendered tier: two generated brackets, Pick merged with progress, a collapsed HDR tile in the set, the expanded originals and an original's pick, Develop of the result with an edit, Remove merge, undo, redo and undo with no further merge job, Import merged leaving the set alone, and a relaunch with the brackets renamed away that reopens and renders the edited result); item 6 by the `derived-merge` GPU corpus source and the derived-source tests. Item 7's photo-sized measurements by `hdr-merge-measure` on synthetic 24 and 60 MP brackets of three and nine frames ([figures](../specs/performance.md#hdr-merges-measured-on-the-m4)):
- **Bounds.** Every merge stayed within its bounds: accounted scratch peaked at 104 MiB for three frames and 188 MiB for nine, against 256 MiB. The temporary spool peaked at 7.1 GiB for 60 MP × 9, against 16 GiB. No spool file outlived a merge, cancelled or not. Process footprint grew with frame size, not frame count (at most 1.36 GiB while merging 60 MP × 9); no total-memory bound is claimed.
- **Times.** A merge took about 2.2 s for 24 MP × 3, 5.7 s for 60 MP × 3, and 17 to 64 s for 60 MP × 9. Cancellation ended a merge within 423 ms at every stage.
- **Reopen and redo.** Reopening with the inputs moved away, undo, redo, preparation and export ran no merge and read no input.
- **Editing beside a merge.** Browse, samples, commits and exports through the same owner kept their idle p50 beside a merge.

Limits:
- **Fusion reads.** 60 MP × 9 fusion is bound by its row-by-row spool reads whenever the spool has left the file cache: 40.6 to 56.7 s of merging then, against 9.9 to 24.0 s when it is still cached. The panorama plan's shared merge lane reads spools by bands, for both kinds, and measures HDR again.
- **Still unmeasured.** A drag was measured only beside a merge's reading stage. GPU allocations of a merged result in the editor, Windows and Linux, and 24 MP × 9 on a quiet host are unmeasured.
- **Natural brackets.** None was available: the private manifest's three RAWs are single frames from three bodies. Natural-bracket quality (motion, seams, colour, highlights, shadows and crop losses on real brackets) is unqualified.

The implementation answers the [performance-rules checklist](../engineering/performance-rules.md#review-checklist): original reads/decode counts, shared allocations and every full frame's reason, owner/pixel work separation, bounded worker/queue/disk resources, stale-work handling, point queries and derived-state refresh, GPU accounting, visibility-independent jobs, reference pixels and measured photo-sized costs. Update this design, [feature status](../features.md), [user guide](../user-guide.md), catalog integration and command documentation when delivered.

## Numerical references

Radiance reconstruction has established references in [Debevec and Malik's HDR work](https://www.pauldebevec.com/Research/HDR/) and [OpenCV's HDR interfaces](https://docs.opencv.org/4.13.0/d6/df5/group__photo__hdr.html). OpenCV describes radiance merging, exposure alignment and exposure fusion as separate operations. These are numerical references, not a decision to adopt OpenCV or a claim that its algorithms meet Luxforge's resource/quality contract. This plan consumes qualified linear RAW development, without JPEG camera-response calibration.

[pfstools' alignment documentation](https://pfstools.sourceforge.net/man1/pfsalign.1.html) distinguishes global homography from moving-object ghosting and records parallax limitations; its all-frames-in-memory implementation is unsuitable as Luxforge's bounded scheduling model. [pfscalibration](https://pfstools.sourceforge.net/pfscalibration.html) provides another primary implementation reference for exposure weighting. Registration, deghosting and resource bounds still need their own evidence here.

# Preparing v0.1 for distribution

Status: **tag-build tooling and the ready-packet verifier implemented; public distribution qualification remains open**. Local archives are build rehearsals, not qualified public release candidates. This design and the [task plan](../../tasks/project/release-v0-1.json) describe the work; they distinguish implemented build tooling from the unrun signing/native/distribution qualification gates. [Tag-build behaviour](tag-release-builds.md) and [operator instructions](../engineering/releases.md) describe the automation.

## Scope

Prepare Luxforge **0.1.0**, tagged `v0.1` or `v0.1.0`, as an early preview of the implemented editor. **macOS and Linux** release together. Target Apple silicon macOS, and x86-64 and ARM64 Linux on the existing Ubuntu 24.04 baseline, through the repository's GitHub Releases page, marked pre-release. The published 0.1.0 pre-release has no ARM64 Linux download; tag builds after it produce one. Every download must satisfy its platform gates before the joint release is ready; Windows remains later scope. Platform-specific packaging work can proceed independently.

Use the existing `release` profile, pinned toolchain and lockfile. The `dist` profile is not a prerequisite. Release numbering does not establish a stable catalog, recipe, API or module compatibility promise: unsupported data continues to be refused without modification. There are no migrations or compatibility fixtures; catalog migrations begin at 1.0.0 ([catalog compatibility](../decisions.md#catalog-compatibility)).

Release the working editor as it stands at the selected commit. Features still planned or in progress, such as MCP, AI editing and Lightroom catalog import/alignment, are not release prerequisites. A feature merged before the candidate is frozen joins its qualification and documentation scope. Do not require the controlled RAW/Detail studies or all outstanding calibration and performance research. Report their remaining limits accurately.

The release does not add stores, accounts, telemetry, a website, package-manager publishing or a general release framework. GitHub hosts the files. The release includes [automatic updates](auto-update.md): Sparkle on macOS, the payload updater on Linux and the update feed on the backend API under `api.luxforge.app/v1/updates/`; a release-ready v0.1 needs them qualified. An update check is not telemetry: it sends only the app version. Linux has release packaging and native qualification under its recorded baseline; Windows stays development scope. A Linux release is not a promise of compatibility with every distribution or native GPU/driver combination.

## Identity and candidate inputs

Ordinary developer builds use `workspace.package.version`, currently `0.0.0`. A tag build uses its validated normalized SemVer as the shared compile-time application version, without changing manifests or `Cargo.lock`; `v0.1` normalizes to `0.1.0`. All three executables and archive/build metadata agree on it. The core's `APPLICATION_VERSION` is its one definition: `--version`, editor logs and evidence, the lens report, network requests' user agent, usage statistics and `update.status` all state it. The workflow supplies a numeric macOS build number from its run number. Keep `org.luxforge.app` as the bundle identifier. Recipe/catalog/module format markers change only when their own shapes change.

The editor, `luxforge-json`, `luxforge-ctl` and `luxforge-mcp` each support a non-launching `--version` that reports that application version. Reuse existing build-version reporting; do not add an About screen or duplicate authoritative version state in widgets. Any new service-visible build information follows the command registry/schema rules.

A candidate names a clean, full commit SHA, target triple, application version, build number, profile, pinned toolchain, lockfile hash and build environment (OS, SDK and native compiler). Reject unsupported targets, dirty tracked or untracked source input, a tag/version mismatch and an existing output directory. Excluded build/evidence directories do not make a source tree dirty. Refuse rather than silently editing the checkout or guessing the commit.

For macOS, the target is `aarch64-apple-darwin`. macOS 14 is the intended engineering floor, **not currently verified support**. `release-build` refuses an executable whose Mach-O deployment target is later than `LSMinimumSystemVersion` and records each one; that states what the executable asks of the OS, not that it runs there. Inspect runtime imports, and record execution on the oldest advertised OS before publishing that support claim. A hosted build on macOS 14 is not native installation or GPU evidence. A missing floor test remains an open release input; changing the advertised floor needs a focused scope update.

For Linux, use `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`, each built natively on Ubuntu 24.04 (the hosted `ubuntu-24.04` and `ubuntu-24.04-arm` runners) with glibc 2.39 as the existing baseline. Inspect actual ELF imports and symbol-version requirements. Require native Linux desktop/GPU evidence on that baseline for each architecture, including GNOME Wayland and X11, before claiming support. The owner's ARM64 Omarchy VM and hosted lavapipe runs supplement this evidence; neither replaces it. Other distributions and Intel macOS are outside the initial supported download matrix.

## Candidate records

`release-build` writes one record per target: `build.json` inside the payload and `target.json` beside the downloads. `release-assemble` binds every target's records into `release.json`. All three kinds of record have schema version 2, and only that shape is read ([release_candidate.rs](../../xtask/cli/src/release_candidate.rs)).

Before compiling, a build refuses an unsupported target, an existing output directory and a HEAD without a full commit ID. Unless `--allow-dirty` labels it a local rehearsal, it also refuses a dirty tree (tracked changes or untracked files; ignored build and evidence output does not count), a missing tag, a tag naming another commit and a Rust toolchain other than the `rust-toolchain.toml` pin. A rehearsal records its dirty state and toolchain and is never assembled for publication. After packaging, the lockfile, commit and cleanliness are checked again.

A target record holds:

- **Identity:** `tag`, normalized `version`, `build_number`, full `revision`, `target`, `platform`, `profile` (`release`), `lock_sha256`, `catalog_format`, `usage_release`, `working_tree_dirty`, `rehearsal` and, on macOS, `minimum_system_version` and `deployment_targets`, each executable's Mach-O minimum OS.
- **`toolchain`:** the `pinned` channel and the `rustc` and `cargo` versions the build used.
- **`build_environment`:** `os`, `native_compiler` (`cc --version`) and the macOS `sdk` or the Linux `libc`; the field that does not apply to the target is `not-applicable`.
- **`executables`:** each executable's SHA-256. macOS records `before_signing` when it builds; `release-sign` adds `final`, measured from the signed and stapled app, and each must differ from its before-signing hash. A macOS app that is not notarized has no `final`. Linux executables are not signed, so the built hashes are `final` and there is no `before_signing`.
- **Linux `elf_imports`:** what each executable imports, read on the build host with GNU `readelf -W --dynamic --version-info`: its `needed` libraries, the symbol `versions` it requires of each, its `max_glibc`, and overall `inspected_with` (the readelf version), `glibc_baseline` (`2.39`) and `max_glibc`. The build refuses an executable that requires a newer glibc or `GLIBC_PRIVATE`, or links a library outside glibc, the GCC runtime and the C++ runtime, which the packaged help would not name; assembly refuses a Linux record without the inspection or past the baseline ([release_elf.rs](../../xtask/cli/src/release_elf.rs)).
- **In `target.json` only:** `archive` and the macOS `disk_image`, each the final file's name, size and SHA-256, and `signing`. macOS signing is `unsigned`, `pending`, `failed` or `notarized`, and only `unsigned` or `notarized` builds are assembled. Linux signing is exactly `not-applicable`, so a Linux record never stands in for a macOS signing result.
- `release_ready: false`.

`build.json` names executables, never the archive or bundle that contains it; archive and disk image hashes exist only outside them.

`release.json` holds the common `tag`, `version`, `revision`, `lock_sha256` and `build_number`, `status: build-candidate`, `release_ready: false` and every target record in [target order](../../xtask/cli/src/release_artifacts.rs), each matching the common identity. `source_archive` is the complete source archive `luxforge-VERSION-source.tar.gz`'s name, size and SHA-256 when assembly's input holds `release-source`'s output in `source/`, whose `source.json` matches the common revision and lockfile and comes from a clean tree that is not a rehearsal; otherwise it is null. Each gate is an object whose `status` is `not-run`, `passed`, `failed` or `incomplete`:

- `distribution`: `source_and_notices_review` and `advisory_disposition`.
- `qualification.macos-arm64`: `native_full_verification`, `gpu_corpus_gate`, `minimum_os` and `clean_installation`.
- `qualification.linux-x86_64` and `qualification.linux-arm64`: `native_rendered_verification`, `gpu_corpus_gate`, `wayland_and_x11`, `baseline_os` and `clean_installation`.

Every listed gate applies to its platform, so `not-applicable` is refused there; Apple signing lives in the target records. Assembly writes every gate as `not-run`. `SHA256SUMS` is written last and covers `release.json`, which never contains its own hash. The field and gate names, the status vocabulary and the toolchain refusal are implementation choices the plan delegated.

### Gate results and readiness

A packet is the directory `release-assemble` writes: every target's downloads, `macos-arm64.json`, `linux-x86_64.json` and `linux-arm64.json`, `release.json`, `release-notes.md`, the source archive once it exists, and `SHA256SUMS` listing every one of them. The signed update record `luxforge-VERSION-updates.json` may sit beside them unlisted. Qualification works on a local copy of a candidate's packet; published assets stay fixed.

`release-gate` records one gate's result in that copy's `release.json` ([release_verify.rs](../../xtask/cli/src/release_verify.rs)). It first requires the packet to be consistent, then validates the result, replaces the gate's object and rewrites the `release.json` line of `SHA256SUMS`, so the checksum file still covers the final `release.json`. A gate that has not run is exactly `{"status": "not-run"}`. Any other result records:

- `status`: `passed`, `failed` or `incomplete`.
- `evidence`: a reference inside the private evidence store, such as `m4-full/summary.json`, or an `https` URL. Never a file path: absolute, home-relative or `..` references are refused.
- `scope`: one line naming what the evidence covers, such as the background test bundle and what it does not prove.
- For a distribution gate, `disposition`: `distribution` or `development-only`. A development-only disposition, such as the current development-scoped advisory exceptions, never passes a distribution gate.
- For a qualification gate, `executables`: the SHA-256 of each executable the evidence ran, `luxforge` at least, and `executable_identity`. Linux binds `final`. macOS binds `final` or, for evidence from before signing, `before-signing`; each hash must equal the candidate's recorded one, so evidence from another build is refused. The harness copying the editor into the background test bundle does not change the executable's hash.
- For a macOS qualification gate, `bundle`: `background-test` or `distributed`. `minimum_os` and `clean_installation` need the distributed app with final hashes; full verification and the corpus gate may use the background test bundle. Linux results carry no bundle or Apple field.

Evidence and scope are refused when they look like a private path, coordinates, a photo file name, a secret or an email address, so the packet carries none.

`release-verify` reads a packet, changes nothing and reports every reason it is not ready. It recomputes each listed file's hash against `SHA256SUMS`, each download against its build record and the source archive against `release.json`, and refuses missing, tampered or unlisted files. It requires all three shipping targets sharing the tag, version, commit, lockfile and build number, each platform record identical to its `release.json` copy, no rehearsal or dirty tree, the complete source archive, a notarized macOS app and disk image with their submissions and final hashes that differ from the before-signing ones, Linux signing exactly `not-applicable`, and every distribution and qualification gate `passed` with a valid result bound to its platform's build. A packet missing a platform is never ready. `release.json` itself always stays `status: build-candidate` with `release_ready: false`; one that claims more is refused.

With `--summary NEW_FILE`, outside the packet, it writes the public summary whether or not the packet is ready: the common identity, the `release.json` hash it describes, `release_ready` and `status` (`release-ready` or `not-ready`), every reason, each target's assets, signing status, toolchain, build environment and executable hashes, and each gate's status, scope, disposition, bundle and executable binding. Evidence references become `private` unless they are `https` URLs. If anything in the summary still looks private, nothing is written. The command succeeds only for a ready packet whose summary, when asked for, was written.

## Deliverables

The macOS download is `luxforge-0.1.0-macos-arm64.dmg`, a signed, notarized and stapled drag-to-Applications disk image ([automatic updates](auto-update.md#macos-sparkle)): people open it and drag Luxforge to the `Applications` link beside it. `luxforge-0.1.0-macos-arm64.zip`, containing one `Luxforge.app`, stays as the update archive. The app contains:

- `Contents/MacOS/luxforge`, with a normal foreground application plist for human launches.
- `Contents/Helpers/luxforge-json`, `Contents/Helpers/luxforge-ctl` and `Contents/Helpers/luxforge-mcp`, executable and signed before the app. No automatic PATH modification or privileged installer.
- `Contents/Resources/lensfun`, the existing runtime index and its attribution.
- A bundled application icon, notices, project licence, installation/help text and build metadata under `Contents/Resources`, so copying the app to Applications keeps them.

Delegate a modest original application icon and its source asset, plist serialization, code organization and routine archive mechanics to the implementer. Do not introduce a branding approval gate or a second packaging toolchain. Preserve the existing unsigned development command and its clear label; never silently sign, submit or publish when that command runs.

The Linux downloads are `luxforge-VERSION-linux-x86_64.tar.gz` and `luxforge-VERSION-linux-arm64.tar.gz` (0.1.0 has only the first), each containing a relocatable `Luxforge/` directory with `luxforge`, `luxforge-json`, `luxforge-ctl`, `luxforge-mcp`, adjacent runtime resources, icon, desktop-entry template, notices, licence, help and build metadata. Preserve executable modes and resolve resources relative to the installed payload, never the checkout or working directory: a tag build, compiled with `LUXFORGE_RELEASE_VERSION`, looks for the lens index only beside its executable and embeds no checkout path for it, while a development build also reads the checkout's. Provide an explicit user-level install/uninstall helper or documented commands for desktop-entry/icon integration; extraction and direct launch also work. A native file chooser requires a working XDG portal and backend; document runtime libraries and a Vulkan-capable driver rather than shipping vendor GPU drivers or promising a universally self-contained archive. AppImage, Flatpak, Snap and distro repositories are not v0.1 prerequisites.

The Linux payload's desktop integration ([release_linux.rs](../../xtask/src/release_linux.rs)) is:

- **`Luxforge/desktop-integration.sh install`**, a POSIX `sh` script ([source](../../packaging/linux/desktop-integration.sh)) that writes `luxforge.desktop` into `${XDG_DATA_HOME:-~/.local/share}/applications` from the payload's `desktop/luxforge.desktop.in`, and copies each icon the payload carries from `desktop/icons/hicolor/` into the same data home's `icons/hicolor/` (`256x256/apps/luxforge.png`, `512x512/apps/luxforge.png` and `scalable/apps/luxforge.svg`, from the committed [icons](../../packaging/icon/README.md)). `XDG_DATA_HOME` counts only when absolute, as for the updater. The script describes the folder it is in, resolved physically, never the working directory. Each file is replaced with a rename, mode 0644. It needs no root and changes no PATH, shell profile or driver; extraction and direct launch never need it.
- **The entry** runs the payload's absolute `luxforge` with no arguments: `Exec` always quotes it, with `"`, `` ` `` and `$` escaped for the quoting rule and again for the string escape rule, and `TryExec` names it. A path with a control character, a backslash or `%`, or one that is not UTF-8, is refused before anything is written: the updater does not write a backslash back, and GLib checks an `Exec` program before reading `%%`. The entry names `Icon=luxforge`, `StartupWMClass=luxforge`, `Categories=Graphics;Photography;`, the build's `X-Luxforge-Version` and `X-Luxforge-Build`, and the marker `X-Luxforge-Installed-By=desktop-integration.sh`. An existing `luxforge.desktop` without the marker is never replaced.
- **`uninstall`** removes the entry only when it carries the marker, and then the icon paths install writes; with no entry, it removes an icon only when it matches the payload's. It refuses, removing nothing, when the entry lacks the marker. It never touches the payload, catalogs, settings, logs, artifacts or originals, and says so; both commands and `help` name those locations.
- **The window's** Wayland app ID and X11 class are `luxforge`, the entry's name, so the desktop shows the running window under the entry and its icon.
- After a payload update, the updater [refreshes](auto-update.md#linux-the-payload-updater) an entry whose `Exec` program is inside the payload, reading and writing the same encoding.

The packaged Linux help, `Luxforge/INSTALL.txt`, names its architecture and archive and covers extraction and direct launch, the helper, the Ubuntu 24.04 baseline, the Vulkan loader and driver, the Wayland and X11 libraries the editor loads at run time, the linked libraries from the build's `elf_imports`, the XDG portal and file-chooser backend, the unsupported secret store and the data locations.

Alongside the downloads, the release carries `luxforge-0.1.0-source.tar.gz`, `SHA256SUMS`, `release.json` and release notes. The [source archive](../engineering/releases.md#the-source-archive) holds the exact tracked tree of the commit, vendored Rust dependencies, native sources and applied patches, compiled-in assets/data, the prebuilt ONNX Runtime libraries `ort-sys` would otherwise download, each target's notices, toolchain/lockfile and build/install/relink instructions. The repository Cargo configuration is kept, with the offline vendoring configuration added. ONNX Runtime is the one linked component whose source is not in the archive: it is pyke's prebuilt MIT-licensed library, identified by its pinned archive, and `RELINK.md` describes linking another build. Test builds for every shipping target from the extracted archive on their respective build hosts, without the original checkout or Cargo source cache. A Linux container may prove the offline build, but not native desktop/GPU qualification. Bit-reproducible binaries are not a v0.1 claim.

Review native static linking, selected licences and the ability to modify/rebuild/relink the LGPL components, alongside Rust and bundled font/theme/Lensfun/RawSpeed/GeoNames assets. Inventory is input to that review, not its conclusion. Supply applicable licence texts and attribution/change notices. Exclude private photographs, the licensed test corpus, catalogs, grants/secrets, credentials, developer paths, caches and verification output. Include only redistributable assets needed to build/run the shipped product; document any test-only omissions. GitHub's automatically generated repository archive does not substitute for this complete source deliverable.

`release.json` lives outside the signed app; its fields are the [candidate records](#candidate-records). It records every target's final filenames, sizes and SHA-256 hashes, the common commit/version/lock identity, per-target executable and build identities, source archive identity, macOS signing/notarization results and per-platform qualification. Linux Apple-notarization fields are explicitly not applicable, not a skipped required macOS gate. A packet missing any platform remains incomplete for this joint release. Keep private raw evidence separate from a sanitized public summary. Do not embed a hash of an archive inside that archive, or a bundle hash inside the bundle it describes. Label any pre-signing binary hash as pre-signing; final signed hashes are measured after signing. Generate `SHA256SUMS` only after final packaging and metadata are complete.

## Signing and notarization

Prepare tooling and failure tests without requiring account credentials. A real signed candidate later needs an Apple Developer membership, a usable **Developer ID Application** identity and notarization credentials controlled by the release operator. The owner's paid Apple Developer Program membership is active, verified read-only in the account's membership details; certificate tools are available. The owner reports completing signing setup and storing notarization credentials under the Keychain profile `luxforge-notarization`. Certificate/private-key usability and profile authentication have not been independently checked; validate them during the final candidate task before signing or submission. Read-only account inspection is authorized; this preparation does not authorize credential creation or acceptance of further agreements. Use a named Keychain profile or the supported notary API credential mechanism; keep passwords and private keys out of source, CLI logs and release assets. Do not enumerate or export the owner's credentials during preparation.

Operator setup on the build Mac:

1. In Xcode Settings, add the enrolled Apple Account, select its team and open **Manage Certificates**. Use the add button to create **Developer ID Application**, keeping its private key in the local Keychain. This is the certificate for the app; Developer ID Installer is for installer packages ([Apple certificate guidance](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/), [Xcode certificate management](https://help.apple.com/xcode/mac/current/en.lproj/dev154b28f09.html)).
2. For the Apple Account authentication path, create an app-specific password labelled for Luxforge notarization under **Sign-In and Security → App-Specific Passwords** at `account.apple.com` ([Apple instructions](https://support.apple.com/en-us/102654)). Store it locally with the existing Apple tool below, using the account's Team ID from membership details. Enter the app-specific password at its secure prompt; do not pass it as a command argument or send it in chat. The command validates credentials before saving the named Keychain profile by default.

```sh
xcrun notarytool store-credentials luxforge-notarization \
  --apple-id "YOUR_APPLE_ID" --team-id "YOUR_TEAM_ID"
```

This configures Apple's existing tool, not a Luxforge release command. No certificate or credential is created by the repository's preparation work. Final signing uses an explicitly selected Developer ID identity and the `luxforge-notarization` profile; it must validate both before submitting a candidate.

Sign nested executables first, then the finished app, with hardened runtime and a secure timestamp. Start with no exception entitlements and add only demonstrated requirements. Verify all executables, the bundle seal, expected identity and runtime configuration. Do not use recursive signing as a substitute for enumerating the payload.

Submit a metadata-preserving ZIP to `notarytool`, retain the submission ID and result, and require **Accepted**. Staple the ticket to the app, validate it, then create the final ZIP from that stapled app. A ZIP itself cannot be stapled. Then create the disk image from the stapled app, sign it with the same identity and a secure timestamp, submit it and require **Accepted**, staple and validate its ticket, and assess it with `spctl --assess --type open --context context:primary-signature`. Record both submissions. Fail on rejection, timeout, missing tools, absent identity or invalid tickets, keeping diagnostic output for the operator. No unsigned fallback may receive a release-ready label.

Treat the signed app as immutable. Signing, stapling and final archive extraction must precede its final hashes and assessment. Credentials and the Apple service are late inputs; their absence must not hold up identity, packaging, source, verifier or documentation work.

## Qualification and evidence

Build ordinary packaging/version/verifier tests with their implementation, then deliver the usable unsigned candidate machinery. Final qualification comes after those changes are integrated and the candidate commit is frozen:

1. Run fresh dependency audit and finish the target-specific source/native/asset review. Existing exception reasons explicitly say local development or no distribution approval. Do not infer distribution suitability from those suppressions; record a fresh bounded disposition or an unresolved publication blocker without replacing the GUI stack just to clear an advisory.
2. On the native M4, run `full` with the owner RAW manifest against the candidate executable, including the required GPU-against-reference gate. Retain state, logs, adapter identity, captures and source hashes. Cover current Select/Locate, RAW looks, copy/paste and Auto tone through the existing journeys, adding a narrow journey only where a release-critical path is absent. A partial corpus, software adapter, skip or incomplete component never passes the native release gate.
3. Inspect relevant captures and the full summary. Preserve the accepted motion policy and declared GPU tolerances. Report provisional timing misses and unreliable/unmeasured figures honestly; do not invent new performance targets or convert an unqualified total-memory claim into a support promise.
4. After signing/notarization, inspect an extraction of the final ZIP and a read-only mount of the final disk image for signatures, tickets, resources, versions, archive attributes and checksums. Rerun affected checks if signing, metadata or a rebuild changes the candidate. Normalized executable identity can connect pre-signing rendered evidence to the signed candidate, with the method recorded; never treat a different build as the same candidate.
5. On native x86-64 and ARM64 Ubuntu 24.04, run the complete platform-appropriate rendered tier and required GPU corpus gate against each Linux candidate with hardware Vulkan. Record native adapter/driver/OS and inspect correlated state/logs/captures. Cover Wayland and X11, file chooser/portal behavior, Select/index watching, Locate, RAW edits, masks, save/reopen/export, both CLIs and no-GPU-stage fallback. Reuse hosted no-adapter/lavapipe checks as functional evidence only, resolve candidate failures, and do not label the incomplete hosted software lane passed. Check extracted-archive launch without the checkout, desktop-entry/icon installation, updates and user-level uninstall retaining data and originals. Native Linux and minimum-baseline access are late external inputs; they do not block packaging implementation.
6. Record a clean installation from a quarantined downloaded final disk image on a separate supported Apple silicon Mac or clean test account: open it, drag Luxforge to Applications, Gatekeeper acceptance, first launch, native file picker, open JPEG and supplied supported RAW, edit/undo/reopen/export with original hashes unchanged, both CLIs, replacing the app while retaining its data, and uninstall retaining originals/catalogs. Verify offline ticket assessment. Test paths containing spaces and non-ASCII characters. Name the actual OS/adapter and tested build; the minimum OS remains unverified until tested.

Automated editor checks continue to use hidden background bundles and isolated catalogs/data roots. The existing harness copies the executable into `org.luxforge.background-test`, changing its bundle context; that proves renderer/command behavior, **not Finder launch, the distributed bundle seal, Gatekeeper, installed resources or production shader-cache behavior**. Keep that distinction in `release.json`. Installation/foreground checks require an explicit interaction request and a suitable test machine/account; this preparation does not authorize activating the owner's desktop.

Missing private RAW files, a macOS floor machine, native x86-64 and ARM64 Linux GPU machines, signing credentials or a clean install session affect only their final qualification steps. Prepare everything else first and record what remains unrun. No task asks an implementer to reconfirm scope or obtain approval.

## Delivery and publication

Prepare a local release packet with the final assets and notes; its machine-readable readiness result is the verifier's [public summary](#gate-results-and-readiness). The verifier fails closed on missing/tampered files, candidate mismatches, development-only policy dispositions, invalid signing/notarization or incomplete required evidence. An unsigned rehearsal remains explicitly a rehearsal. Public evidence contains no private file paths, coordinates, photos or secrets.

In the [tag workflow](../../.github/workflows/release.yml), a pushed tag builds every target, optionally signs/notarizes macOS, verifies transport identity/hashes and automatically publishes a **GitHub pre-release** after every asset upload succeeds. The tag is the build input; implementation work never pushes one. Hosted Apple secrets remain a separate operator input from the local `luxforge-notarization` profile. The published notes and metadata explicitly record source/advisory/native/install gates as pending or not run and never claim release readiness. Existing releases/assets are not overwritten. Only the publication job gets repository write permission; Apple secrets reach only its macOS signing step. Those candidates stay non-ready: `release-verify` reports a downloaded candidate's unrun gates, signing and missing source as its reasons until qualification records passing results. A hosted build is not native GPU evidence. The publication job attests the downloads' build provenance, which proves which workflow built them, not that any gate passed.

At handoff, provide the reviewable files, evidence scope and any unmet inputs. The owner pushes a chosen release tag to request a build; implementation work never creates or pushes one. Pushing a release tag requests automatic pre-release publication; the workflow stages all assets in a temporary draft and then publishes it. A failed upload or moved tag leaves the draft unpublished. Once published, assets stay fixed; corrections use another version. Updates, automatic or manual, replace the app, preserve user data and follow the current-format refusal rule. Retain the prior app and data backups when evaluating a newer format; do not promise an older app can read newer catalogs.

The [release notes draft](../releases/v0.1.md) exists. Before publication, fill in verified requirements and real download/hash/evidence links, describe only shipped features, and include installation, data preservation, current-format limitations, supported-file scope, manual updates and issue-report instructions. The README, guide, platform/status docs and package help change to downloadable-install instructions only when the corresponding artifact exists.

## Acceptance

- A clean common candidate produces every versioned download, complete matching source, notices, checksums, release metadata and useful installation/help text.
- All three executables agree on version; installed behavior uses no checkout-relative resources; replacing/removing the app preserves user data and originals.
- Signing/notarization and final extraction checks pass, with the actual bundle assessed separately from the background test wrapper.
- Native M4 full verification and the complete required corpus gate pass; native x86-64 and ARM64 Linux rendered/GPU qualification, Wayland/X11 and installation checks pass against the same commit. Advertised OS baselines and clean installations are tested. Remaining scope limits stay visible.
- Source/native/asset and advisory distribution dispositions are recorded; a development inventory/audit alone never passes readiness.
- The complete three-target packet is reviewable before any public tag or publication. None of these gates is claimed as passed.

## Primary distribution references

Apple documents Developer ID signing, hardened runtime and notarization in [Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), and ZIP submission/app stapling in [Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow). Its [packaging guide](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution) calls for testing the distributed product, preferably on a different Mac. GitHub documents draft/pre-release assets in [Managing releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository). The GNU [licence FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#LGPLStaticVsDynamic) explains source and LGPL relinking obligations; apply each bundled component's actual licence in the distribution review.

# Corrections: Clone, Heal and AI Remove

Status: **proposal for owner review; planning only**. The owner has requested a corrections module with Clone and Heal as the free, offline baseline and AI Remove as a more ambitious option. This proposal revisits the roadmap's earlier exclusion of generative editing, but that exclusion remains in force until the owner accepts the new scope. The implemented [module capabilities](module-capabilities.md) supply settings, permissions, resources, jobs and durable artifacts; the existing [module contract](modules-and-api.md) supplies discoverable actions and controls.

## User result and staged delivery

The Develop workspace gains one Corrections section with Clone, Heal and AI Remove modes. Clone copies chosen pixels from another region. Heal borrows detail and adapts it to destination tone. AI Remove takes a painted target mask and surrounding context, generates candidates, lets the user compare/refine/regenerate and commits only the selected result. Each operation remains editable in the history and through the API. Clone/Heal work without network, accounts or model downloads. AI is optional, using user-selected local or remote providers. A hosted provider may charge for use; the free application never silently uploads a photograph.

Deliver in slices: (1) a usable Clone/Heal module with exact output and UI/API parity; (2) the generic capabilities framework and artifact store, independently reusable by future modules; (3) AI Remove with a qualified local model if one passes, at least one remote adapter, and a second distinct provider path that proves provider choice (another remote adapter or a user-run local service). The framework may be built while Clone/Heal progresses; AI commit waits for both. Automatic object recognition and masks shared with all editing tools are later work. The first AI interaction is manual brush/add/subtract; there is no placeholder button for an unavailable mode.

Adobe's current Remove tool groups Remove, Heal and Clone; its Generative Remove can paint an object, refine selection and refresh variations. That is a **workflow reference**, not an exact rendering target ([Adobe Remove](https://helpx.adobe.com/lightroom-classic/desktop/help/healing-tool.html), [Adobe Generative Remove](https://helpx.adobe.com/in/lightroom/web/edit-photos/remove-objects/remove-objects-with-gen-ai.html)).

## Editing and persistence contract

Propose one built-in `lightwell.corrections` module with a list of ordered operations in its own repair layer. Each operation has a stable ID, kind, content-space brush geometry, opacity/feather and any source offset or chosen AI artifact. Add/update/delete/reorder within this layer are distinct discovered actions and each successful action creates one ordinary history entry. Canvas drags are session drafts; pointer motion creates no entry, release/Apply commits once, Escape/Cancel discards. An API client sends a whole stroke path or target-mask edit semantically; it never simulates pointer events. API mutation envelopes, stale-revision conflicts and request deduplication are the same as for other modules. Historical preview, undo, redo, restore and named versions retain the selected operations and artifacts.

Propose a narrow **repair stage** after source development and before the global colour/spatial effects and the geometry tail. Its insertion rule is explicit and does not reorder stored layers. Repairs use content coordinates after EXIF orientation, so a later crop, quarter-turn or mirror carries them. This new stage, its closed host processing primitive, and any old current-shape payload implications require an integration decision before code. The reason for the placement is that later Basic/Presence adjustments can apply to the generated and original pixels together. A change to a RAW source-development setting, source file or an earlier repair changes an AI result's input: that result is marked stale and its render/sample/export **fail explicitly** until the user removes it or generates a new candidate against the new prefix. Clone/Heal recompute from their saved geometry and source pixels and do not become stale. This is a proposed correctness policy; it needs owner acceptance because it restricts edits before an AI repair.

Clone reads a bounded source region from the **prefix before the correction operation**, mapped by a source-to-target offset, and blends it through the painted coverage, feather and opacity. Heal uses the same source geometry but adjusts low-frequency tone across the destination boundary while keeping sampled detail; a numerical study chooses and freezes the exact solver, convergence bound, colour domain and edge rule before shipping. Neither operation may recursively sample its own output. Ordered overlapping operations see earlier corrections; that order is stored and reproducible. A missing source region is handled by a declared clamp/skip rule, never by accidental out-of-bounds reads. Exact fixtures must cover overlap, edges, small strokes, reversed source directions, crop/orientation and RAW float inputs. All mutable brush work uses bounded regional tiles; the catalog owner plans only.

AI takes the developed repair-stage image plus a bounded context crop and a mask. The adapter declares accepted size, aspect, colour space and mask polarity; the host performs a recorded resize/pad and output mapping. The default request sends an sRGB rendition of the **minimum context crop** needed by the selected model, with EXIF/paths stripped. A provider that requires the whole frame must declare that and obtain specific consent. Output is checked for dimensions, format, colour interpretation, size, alpha and non-finite values. The host composites **only inside the committed mask/feather**; outside-mask pixels match the repair-stage input exactly. Generated pixels are converted to the stage's linear colour representation and saved as an immutable, content-addressed patch plus its mask, transform and checksum. The original RAW sensor/float data and all unmodified pixels stay in the continuous pipeline; generated pixels have the quality/precision of the model's output and are never described as recovered sensor data.

An accepted AI operation stores the artifact ID, model/provider identity, model version or hash, adapter version, input-prefix hash, mask/seed/prompt and transform needed to explain the result. **Rendering uses the frozen patch, not the provider**: it needs neither an installed model nor an API key and never regenerates unpredictably. Provider loss only blocks new generation or refresh. Candidate previews are disposable, bounded jobs with a frozen source revision/prefix; accepting one rechecks the revision, atomically publishes the patch and commits the recipe. No result from an older photo/revision or cancelled job can overwrite a newer draft. Regenerate explicitly creates new candidates; the user can retain, inspect and reselect candidates during the active session, while only accepted choices need durable storage. A failed provider, refusal, timeout, disconnect or bad output leaves the prior recipe untouched.

## Canvas and performance

The existing descriptor's `point-pick` and `crop-frame` do not describe a brush path. Add a semantic `brush-mask` interaction with declared mode, size/feather/opacity, add/subtract, source handle and operation selection. The desktop owns pointer capture and overlays; the module owns validation and pixel behavior; the service exposes equivalent stroke/mask geometry. On tool activation, preload only a configured local model that is installed and granted, using a cancellable worker; allow Clone/Heal while it warms. An external provider only validates configuration on activation; sending image data waits for Generate and the consent gate.

Painting draws an immediate vector overlay. A preview render may use a scaled mask against the display-bounded proxy and must label it approximate when its pixels differ from the exact render. The settled exact frame drives 100%, sample, histogram and export. If a regional effect is pixel-addressed and cannot be safely scaled, it takes the existing exact-only path and reports that status. Set admission limits for path points, stroke bounds, patch area, candidate count, provider input/output bytes, active jobs, downloaded model size and resident model memory before integration; exceed them with `resource-limit`, not silent resizing. Measure 24/60 MP JPEG and qualified RAW on the M4: input-to-overlay, stroke commit, exact render, first model load, warm generation, peak RSS/GPU memory, disk per accepted patch and idle CPU. Publish misses alongside the scope; do not infer native Windows/Linux GPU performance from a VM or headless run.

## Local and remote provider qualification

There is a plausible local starting point, **not a selected bundled model**. [LaMa's repository](https://github.com/advimman/lama) describes large-mask inpainting and is Apache-2.0 licensed; a hosted [big-lama model card](https://huggingface.co/smartywu/big-lama) also labels its weights Apache-2.0. It is a useful baseline for erased areas, but does not by itself establish Adobe-like generative quality. [PowerPaint](https://github.com/open-mmlab/PowerPaint) explicitly targets object removal and publishes MIT-licensed code; its exact weight chain, runtime dependencies and license must be checked independently. The popular [SDXL inpainting checkpoint](https://huggingface.co/diffusers/stable-diffusion-xl-1.0-inpainting-0.1/tree/main) is marked OpenRAIL++ and large; it is not automatically compatible with a GPL/open-source distribution policy. These are evaluation candidates, not promised features, and no model is bundled or fetched without the user's action. Prefer a reviewed non-executable weight format; [Hugging Face documents](https://huggingface.co/docs/hub/security-pickle) the code-execution risk of pickle model files.

Qualify candidates on a fixed, rights-cleared set of small blemishes, large people/objects, structured backgrounds, edges, shadows, texture and portraits, with JPEG and supported RAW. Record blinded visual scores, failure cases, changed pixels outside the mask, resolution limits, cold/warm M4 load/inference time, peak memory, package/runtime size, architecture portability, dependency/weight terms and download provenance. Compare LaMa, a true generative object-removal model and at least one remote service under **equivalent input crops and masks**. A local model ships as a download only if its quality, runtime, storage and terms meet the accepted thresholds; otherwise AI Remove can launch with remote adapters and the local slot remains an explicit open task. No claim of Adobe parity follows from model architecture alone.

Remote adapters use typed provider contracts with their own mask conventions, generation/variation semantics, size and response limits, pricing disclosure and data handling. The host's common job/result shape lets a user select different providers and models per generation. Start with a reviewed hosted adapter and a second independent provider path, verified with live test accounts and offline mocks; never assume one endpoint's request shape is universal. A user-run loopback service can provide flexibility if its protocol is documented and explicitly granted. Save the selected provider/model in each accepted result's provenance, but never a secret or endpoint credential. Future provider adapters can register without changing the correction recipe shape.

## Acceptance and decisions

Clone/Heal acceptance requires independent exact-buffer tests; source hashes; reopen, history, source-missing and conflict cases; UI/API parity; and native rendered captures correlated to state and logs. AI acceptance adds download/credential/permission denial and revocation, model absent after accept, offline reopen/export, corrupt/missing patch, stale prefix, provider failure, wrong output, cancel/race, catalog-plus-artifact relocation and truthful quality/resource measurements. The JPEG-export part depends on the separately planned shared exporter; if it has not shipped, the corrections milestone remains open and a render-to-buffer check cannot be called export verification. The user guide, feature status, module API design and current roadmap change only as behavior is actually delivered. Run `verify quick` for each code change, `rendered` and `timing` at integration, and `full` before a milestone claim.

Owner decisions to settle before AI implementation: accept the new generative-editing scope; accept the repair-stage ordering and stale-prefix behavior for source development changes; choose whether remote consent is per asset or remembered; set local-model quality/resource thresholds and first remote provider choices. The plans record recommended defaults and decision gates, not accepted product decisions.

# CPU and memory efficiency

Status: done, except the `dist` build profile, which the owner deferred. The owner accepted the scope and the decisions below on 2026-10-03. Every change is measured in [performance](../specs/performance.md#cpu-and-memory-efficiency-measured-on-the-m4) against the code before it, on the M4 in `release`, within the three hours the owner allotted on 2026-10-04; each paid for itself where measured, so none was reverted. The workloads that were not measured are listed there. The task plan is [efficiency](../../tasks/rendering/efficiency.json).

## Outcome

Spend less CPU time and hold less memory for the same pictures, the same numbers and the same or better latency. Every change in this plan leaves every output byte, histogram count, sample and digest identical, except the catalog's journal mode, which changes how a commit reaches the disk and not what it stores.

The work comes from a read-only audit of the whole workspace on 2026-10-03. The audit found the idle path, the desktop's texture and upload handling, the subscriptions and the GPU preview's steady state already tight. The remaining cost is concentrated in four places: per-pixel kernels (spatial tiles, the Detail and Presence filters, the RAW input reads), source preparation (hashing, zero-fills, reads), per-tick copying on the owner and the desktop while painting, and build configuration. Every figure below is an estimate from reading the code. None was measured, and none may be claimed until the measurement task records it under [rule 13](../engineering/performance-rules.md#rules).

## Constraints

- **Byte identity.** A kernel change keeps the same arithmetic in the same order per value, or proves equality another way (an exhaustive test over a finite domain, such as every `f32` threshold). Existing exactness tests stay unchanged and must pass. Rust does not contract `a * b + c` into a fused multiply-add, so reordering loops or vectorizing over independent values is safe; reassociating a sum is not.
- **Performance rules.** Each task answers the [review checklist](../engineering/performance-rules.md#review-checklist) for its own change. No new full-frame allocation without a named limit, no frame work on the owner or the interface thread, and no new idle wake-up.
- **Vendored sources stay pristine.** Native changes are checked-in patches that `crates/luxforge-raw/build.rs` applies to a copy in `OUT_DIR` with exact context matching, as `patches/librtprocess-local.patch` already is. No file under `vendor/` is edited.
- **Dependencies stay pinned and noticed.** A new crate (such as `sha2-asm`) is pinned in `Cargo.lock`, passes `cargo deny`, and gets its notice where [dependencies](../engineering/dependencies.md) says notices live. The task never claims a licence review is complete.
- **Portability.** Windows and Linux keep building and behave the same. An Apple-specific speed-up is selected at run time or by target, never assumed.
- **Measure once, at the end.** Tasks run only their own unit tests while building. A single measurement task takes before/after figures on a quiet host once the feature work is merged, with the base and the branch built back to back and run in alternating order.

## Work

### Build and dependencies

- **Hardware SHA-256.** Done. `sha2` stays at the pinned 0.10.9, whose aarch64 SHA-2 backend (`sha2-0.10.9/src/sha256.rs`) is compiled only with the `asm` feature, so it is on for aarch64 outside Windows. Without it every original, artifact and capability payload was hashed in software on the M4, an estimated 50–230 ms on a cold RAW open and 20–30 ms on a JPEG (not measured). Digests are identical, so this is not a format change.
  - **Where it is on.** Every manifest that names `sha2` (`luxforge-core`, `luxforge-jpeg` as a dev-dependency, `luxforge-raw`, `luxforge-testkit`, `xtask`) has `[target.'cfg(all(target_arch = "aarch64", not(target_os = "windows")))'.dependencies] sha2 = { workspace = true, features = ["asm"] }`, so a build of any one of them, whichever packages it selects, resolves the same `sha2` features. `cargo tree --locked --workspace -e features -i sha2 --target TARGET` shows `asm` and `sha2-asm` for `aarch64-apple-darwin` and neither for `x86_64-pc-windows-msvc` or `x86_64-unknown-linux-gnu`. The pin and the reason sit beside `sha2` in the workspace manifest.
  - **At run time.** The backend uses the SHA-256 instructions through `core::arch` and `cpufeatures`, which falls back to the software path when the CPU lacks them. Apple's Rust target enables the `sha2` target feature at compile time, so on the M4 the check is constant. A scratch crate on `sha2` 0.10.9 holds no `sha256h` or `sha256su` instruction without `asm` and 56 with it, and the `luxforge-raw` test binary holds them in `sha2::sha256::compress256`. `source::tests::fingerprint_hashing_has_the_sha2_instructions_on_apple_silicon` asserts the CPU feature on aarch64 macOS and the published digest for "abc"; it cannot see whether `asm` is on, which the recorded `cargo tree` and disassembly show.
  - **Why not `sha2` 0.11.** 0.11.0 has the aarch64 backend with no feature and no `sha2-asm`, but its digest output (`hybrid-array`) no longer formats as `{:x}`, which 83 call sites in 36 files use, so it needs a hexadecimal helper in four crates and a lock change of six packages. That is not contained, and nothing here needs it. Moving to it later removes the target tables and `sha2-asm`.
  - **What the feature costs.** One new package, `sha2-asm` 0.6.4 (MIT, assembled by the `cc` already in the lock file, notice in [dependencies](../engineering/dependencies.md#hardware-sha-256-on-aarch64)). `sha2` 0.10.9 calls it on x86 only, where it would replace the software fallback behind SHA-NI, so on aarch64 it is built and unused; it refuses to build for Windows, and x86 gains nothing, so no x86 target gets the feature.
- **JPEG XL DNG decode on the shared pool.** Done. `jxl-oxide` is built with its `rayon` feature, and `src/jxl.rs` passes `JxlThreadPool::rayon_global()` explicitly, so a JPEG XL DNG (Pixel, Galaxy) decodes on the global Rayon pool with no pool of its own (rule 9), and a build without the feature does not compile instead of silently decoding serially. The feature adds no package: `jxl-threadpool` uses the `rayon` and `rayon-core` already in the lock file. `render_frame` still has no cancellation hook, so a cancel waits for it. The decode is deterministic: the Galaxy S22 SM-S901E sample (`pixls-7783`, 4000 × 3000) gives the fixture's `mosaic_sha256` `58cd5a2f…916c4d` with the pool, with one Rayon thread (`RAYON_NUM_THREADS=1`) and on the base without the feature.
- **Half floats on x86.** Done. `half` is built with `std` in `luxforge-core` and `luxforge-ui`, so x86_64 detects F16C at run time (its baseline target has none at compile time) and converts boundary texels in hardware, falling back to software where the CPU lacks it. aarch64 is unchanged: Apple's target enables `fp16` at compile time, so `half` already converted in hardware there. `std` adds no package. `iced_graphics` already enables `half`'s default features, `std` among them, in every build that includes Iced, so the declarations matter for a core-only build (the CLI, the core's tests) and keep the feature on whatever Iced does. The conversions are IEEE binary16 round-to-nearest-even either way.
- **The system scan at launch.** `app/mod.rs:558` calls `iced::system::information()`. Iced's `sysinfo` path runs `System::new_all()` and `refresh_all()`, walking every process on the host, to supply two strings: `state.backend`'s graphics backend and adapter. Supply them without a process scan: from the renderer's adapter information if a hook is cheap, or by deferring the call until something reads them. `state.backend` keeps reporting the same strings to every client, with no extra wait for an API reader. Done: iced offers no adapter hook and wgpu's device none either, and only an evidence run reads the two strings (its frames, its capture gate and its `backend` event), so only an evidence launch asks for them.

### Source preparation

- **Read the original with its size.** Done. `read_bounded_file` measures the file once, refuses it past the limit, and `read_up_to` reserves that length plus one byte (room for `read_to_end`'s final empty read, so the end of the file never makes the buffer grow) before reading through `take(limit + 1)`. `Take` hides the file's size from `read_to_end`, so the unsized buffer it replaces doubled its way to up to twice the file, for example 64 MiB for a 40 MB NEF, through the whole unpack; now the capacity is at most the file's length plus one byte, which `a_file_is_read_into_a_buffer_no_larger_than_its_length_and_a_probe_byte` asserts across lengths that straddle powers of two. The length is a hint and not the bound. A file that grew since it was measured is still read in full while it stays inside the limit, and is refused once it passes it, after at most one byte past it (`a_file_that_outgrows_its_measured_length_is_still_bounded_by_the_limit`). A reservation the allocator refuses is a `resource-limit` error (`encoded byte allocation`). The saving is peak and retained memory; it is not measured.
- **Leave zeroing to the writers.** Done. `zeroed_vec::<T>(len, what)` (`luxforge-raw/src/zeroed.rs`) allocates with `alloc_zeroed` and builds the `Vec` from it, so a large request is fresh kernel pages that the first writer faults in, where `try_reserve_exact` plus `resize` wrote every value on one thread first. It is restricted to `f32` and `u16` through a sealed trait, since all-zero bytes are a valid value of both; a zero length allocates nothing; and a length that cannot be laid out, or that the allocator refuses, is `RawError::ResourceLimit(what)` with the site's own message, never an abort. The four sites use it: the RGB planes of a mosaic development (`develop.rs`, 12 bytes per site), direct development's planes (`develop.rs`), the u16 mosaic (`lib.rs`) and the Air 2S warp scratch (`dng.rs`). The content is the same zeros, so developed planes, mosaics and digests are identical by construction. A request the allocator serves from a recycled region is still cleared inside the allocator, so a warm benchmark loop can hide the saving; the measurement task measures cold opens. The estimate of 13–38 ms per development and per committed white-balance change, depending on size, is not measured.
- **No rescan of a proxy for non-finite values.** Done. `downscale_linear` builds every RAW proxy through `LinearImage::from_validated_planes`, which skips the scan of every value that `with_fingerprint` makes on one thread, with a `debug_assert!` that every value is finite. Each value is a weighted mean, with weights summing to one, of the finite values of a source that was scanned or validated when it was built. The public constructors (`new`, `with_fingerprint`) still scan untrusted input. `a_raw_proxy_of_a_finite_source_skips_the_finiteness_scan_and_equals_the_scanned_one` counts the scans through a test-only per-thread counter in the constructor (none for the proxy, one for `with_fingerprint` on the same planes), compares the proxy's planes bit for bit with those planes built through `with_fingerprint`, and includes a source of `f32::MAX` and `-f32::MAX`, whose mean must not overflow. The scan was one serial pass over every value of the proxy; the saving is not measured.

### Spatial tiles

- **Reuse the tile planes.** Done. A tile slot (`TileScratch` in `render/spatial.rs`) owns two plane buffers, ping-ponged along the unit chain (buffer 0 holds the tile's input and the odd units' outputs, buffer 1 the even units'), the masked snapshot and the unit scratch, each handed out as an exact-length prefix and never cleared; `fill` and every unit already write every value they are handed, and test builds fill each prefix with NaN first so the exactness tests prove it. A render's slot grows each buffer once, straight to the largest request any tile of the plan makes (`SlotValues`), so a render allocates its planes once per slot, where it allocated a zeroed input and one output per unit for every tile (about 34–125 MB per tile under Presence). `run_tile` returns a borrow of the buffer that holds the result; the RAW float frame copies the tile out of it in the parallel phase, and a point query takes the buffer out of its own slot. A slot holds two of the chain's rectangles, less than the working set its tile is charged.
- **The charge covers every tile.** `worst_case_working_set` charges each region of the chain at the largest it is over the plan's tiles (`largest_regions`, by the tiles' own grown and shrunk rule), where it used `tile + 2 × remaining halo` a side and so undercounted the tile beside a partial edge tile narrower than the summed halo. At the production sizes (Presence at 6000 × 4000 and 10000 × 6000, masked or not, and Detail) the figures are unchanged byte for byte, which a test freezes.
- **No barrier between tiles.** `run_tiles` runs a stage at or above the spatial threshold as a rolling window on the shared pool, inside one `rayon::scope`. The window starts with what one reservation for the plan's concurrency grants, split into one share per worker. Each worker owns one slot and pulls the next tile as soon as its last one is written, each tile a job of its own that hands the slot and share on, so a slow tile on an efficiency core holds back nothing else. After each tile a worker gives its share back while the budget is past its target, as long as another worker remains, and takes one more while one fits (`SpatialBudget::try_reserve`), so overlapping renders still trade the target as they did at batch boundaries. Tiles are written as they finish, under one lock that also advances the progress meter; they are disjoint, so the order changes no byte. Below the threshold the tiles run one at a time on the calling thread under one share. The cancellation token is checked before every tile. With all three Presence units at 60 MP a working set is about 208 MiB of the 256 MiB target, so that window is one tile wide and its passes run on the pool, as before.

### Detail and Presence kernels

- **Detail's limiter and reconstruction.** Done. Smoothing, noise reduction's shrinkage (one chroma factor for a and b) and its level planes already ran over row slices; now sharpening's limiter, both units' last passes and the Oklab conversion do too, with the halo checked once a pass. Every value is the same arithmetic in the same order.
  - **The limiter.** `Sharpen::limit` (`modules/detail/sharpen.rs`) is the arithmetic for one pixel's values, in the order it had: the residual, the coring, the guide's central differences, the energy, the mask, the proposal, the 3×3 minimum and maximum from the top left by rows with the centre among them, the limit and the `tanh` branches. `Sharpen::limiter` finds the interior once a pass, the output pixels one or more in from every stage edge, whose windows no clamp moves, and checks their windows against the held rectangle with `filters::guard`. `Limiter::row` reads the interior from row slices: each tap of rows y−1, y and y+1 of the lightness and the guide, and row y of the blur, is a slice as long as the run, cut once a row in the loop's own function (`Geometry::span` and `filters::taps` are inline). At opt-level 3 the interior loop is fourteen loads and `tanhf`, with no clamp, index assertion or bounds check. The columns and rows within one pixel of a stage edge keep `Sharpen::limited`, which reads its fourteen values through the clamped, release-asserted `Geometry::index` and `Geometry::sample` and computes them with the same `Sharpen::limit`.
  - **The last passes.** A reconstruction reads only its own pixel, which no clamp moves, so `Sharpen::finish` and `denoise::finish` read every output row from row slices: lightness, a, b and the change from the held planes, and the input through `Planes::row`, its columns found and checked once a pass (`filters::input_columns`, `filters::input_row`). Sharpening's limited row waits in the output's red row until the row is reconstructed, so nothing is allocated. `filters::lab` reads its input the same way; it was the last production reader of `Planes::sample`.
  - **Proof.** `modules/detail/exactness.rs` freezes the previous limiter, both last passes and the Oklab conversion, and its whole-unit sharpening reference reads the frozen limiter. With `to_bits`, the limiter row by row, both last passes, the conversion and the whole sharpening unit match them at every Radius the field takes (0.5 to 3.0 by 0.1; at 1 the guide is the blur), at Detail 0, 50 and 100 and Masking 0, 40 and 100, on stages from 1×1 to 41×33, with outputs on each edge, at each corner and clear of every edge, inputs wider than the held rectangle and both parallelisms. The planes hold distinct values, flat blocks where the limit is zero, zero residuals, chroma inside the neutral snap and zero changes, and a count shows every branch of the limiter is taken. A one-ulp change to an interior limited value or a reconstruction's change, a fused multiply-add in the energy, or a wrong window tap each fails them. The Detail oracle, the f64 fixtures and the restoration tests are unchanged. The saving is not measured.
- **Presence's box and guided passes.** Done. Each pass in `modules/presence/filters.rs` cuts a row once at the frame edges: the columns where no tap clamps read sub-slices of the held rows, with no clamp, index multiply or per-tap bounds check, and the columns within the pass's reach of an edge keep the clamped `Plane::get`. Every value is the same arithmetic in the same order.
  - **The box mean.** `horizontal_mean` runs four rows at once, each with its own `f64` running sum: `0.0` plus each seed column in order, then `+ (entering − leaving)` per step, exactly as one row alone, so the four dependent add chains overlap. `vertical_strip` reads each tap row, clamped to the frame, across its strip as one slice, so the 64 column sums vectorize.
  - **The guided filters.** The squared and product planes, the coefficients and the final combines run over rectangles inside the frame and read row spans of their planes.
  - **The upsample.** Each output column's reduced index and weights are computed once per call, not once per pixel, in a table as wide as the output rectangle (16 bytes a column, at most a few tens of KiB, a small allocation outside the declared scratch). The interior columns take each reduced index's four values once from the two reduced rows; there is no division per pixel.
  - **The units' input.** Clarity's and Texture's encode loops, Dehaze's block sums and the three units' output loops read the input through `Planes::row`, the column offset found once a pass, instead of `Planes::sample` per pixel, and their planes as row spans. None of their columns can leave the stage, so none clamps.
  - **Proof.** `modules/presence/exactness.rs` freezes the previous passes and units and holds the new ones to them with `to_bits`: odd and degenerate frames, radii past the frame, rectangles on every edge, at every corner and on none, reductions from 1 to 16, both parallelisms, values spanning eighty binary orders so a sum taken in another order rounds differently, and a block whose sum rounds differently column by column. Reassociating a running sum, seeding one with `−0.0`, a fused multiply-add in a combine or the upsample, or summing Dehaze's blocks column by column each fails them. The Presence oracle, fixtures and tiling tests are unchanged. The saving is not measured.

### The reduced-grid cache

Done; adoption waits for the measurement task. Clarity's encoded-luminance block means and Dehaze's block means are anchored at the stage origin and do not depend on the tile, the amount or the radius. Yet every tile re-encoded and re-summed them over its own halo, about 2.7× the stage at 60 MP for Clarity alone, and again on every amount change. Under rule 14, the render context now keeps them in a store of reduced planes (`render/reduced.rs`), which the render's own tiles fill and read:

- **Only a unit that runs first in its operation.** Presence runs Dehaze, then Texture, then Clarity. Its box filters keep running `f64` sums that start at each rectangle's first row and column, so a later unit's input can differ in its last bits from tile to tile. That input is the earlier units' output over the rectangle each tile's chain gives them (`filters.rs` holds a tiled run to the whole frame only within the frozen tolerance). No shared plane can reproduce every tile's values, and shrinking a later unit's reach would move the earlier units' rectangles and their sums. A unit that runs first reads the operation's own input, whose reduced cells are a fixed set of pixels summed in a fixed order, so its planes are the same in every tile. The host asks only the operation's first unit (`TilePlanes`, `SpatialEntry::reduced_key`). Dehaze's planes are therefore held whenever Dehaze is present, and Clarity's when Clarity runs alone. Clarity behind Texture or Dehaze runs as it did, so with all three fields Clarity's 327 px halo still costs about 2.7× the stage at 60 MP. Caching it would need the owner to accept output that differs in the last bit.
- **What.** The `f32` planes a unit computes from its reduced grid before any coefficient is applied, exactly as it computes them. `SpatialUnit::reduced_grid` declares them beside the estimate key: their key, the grid's factor and how many planes there are.
  - **Clarity:** one plane, its encoded-luminance 4× block means, about 15 MB at 60 MP.
  - **Dehaze:** two planes, about 30 MB at 60 MP. The first is the guided filter's guide, the encoded luminance of the `f32` block means. The second is the dark channel's input: each `f64` block mean divided by the atmospheric light, clamped, narrowed to `f32`, and the smallest of the three channels kept. The three `f32` means themselves would not do: the `f32` means cannot give back the `f64` mean the dark channel's input is computed from.
  - `SpatialUnit::reduced_reach` names the cells a unit reads for an output rectangle, and `SpatialUnit::apply_reduced` applies the unit with `Reduced::Hand`, computing and handing its cells back, or with `Reduced::Held`, reading them.
- **Key.** Mirrors `EstimateKey` (`ReducedKey`). It holds the source fingerprint and the domain's input identity (`estimate_prefix`: development, view, white-balance approximation, or a JPEG's dimensions and orientation) over the prefix hash of the layers before the operation. It also holds the stage dimensions and the unit's own reduction key. Neither the unit's amount nor the mask is part of it: a masked operation's units run on the unmasked input, and the blend follows them. An entry also records the bit patterns of the global estimate its planes were computed with. A lookup with another estimate misses, and a publish under the same key replaces it. In production Dehaze's light comes from the same input under the same key, but a qualification build can hold another. Tests change each part of the key alone, the light included, and a render test shows an amount-only change hits while a change of source, prefix, stage or unit misses.
- **Budget.** `REDUCED_STORE_BYTES`, 64 MiB in total, named in the [limits](architecture.md#limits) and held in the `RenderContext` beside the estimate store. The largest entry, Dehaze at 60 MP, is about 30 MB, so Dehaze's and Clarity's entries for one 60 MP layer fit together. Entries are shared as `Arc`s.
  - **Eviction:** the least recently used entry is evicted before one is added that would pass the limit.
  - **Refusal:** an entry larger than the limit is refused, and so is collecting planes whose whole grid alone would pass it.
  - **An entry's size:** it holds the smallest rectangle of cells around the tiles it covers, and a record of which tiles those are.
- **Fill, by the render's own tiles.** A frame render (`spatial_entry`) whose first unit finds no planes runs each tile as it always has. So does a tile whose reach the held planes do not cover.
  - **Handing back:** such a tile hands back, with its output, the cells it computed anyway whose first pixel lies in the tile (`ReducedGrid::owned`). The render's tiles therefore hand back every cell once, whatever the tile side, sides that are not multiples of 4 included.
  - **Collecting:** the window's write lock copies the cells into the render's pending planes. These span the whole grid, are allocated zeroed on the first cell handed back, and touch no page no tile writes. A frame render collects at most one such set for each spatial operation, and publishes or drops it before the next operation's tiles run.
  - **Publishing:** when every tile is written, the render publishes the planes with the tiles they cover, merged with the cells of the entry it read and of the store's entry of the same key. A render that fails or is cancelled publishes nothing.
  - **Cost:** a cold render computes what it did and copies only the cells it hands back, a sixteenth of each tile per plane. It reads the stage no extra time and needs no pass, scratch or budget of its own, and the frame work stays on the render's workers.
  - **Masks:** a masked operation's copied tiles compute nothing and hand back nothing, so its planes cover the tiles that ran.
- **Use.** A tile reads the held planes when they cover the first unit's reach in the grid, which they do when every tile that owns one of the reach's cells is covered. It reads exactly the sub-rectangle it would have computed, and its guided filter stays per tile.
  - **The served tile's input:** it reads the operation's input over the rectangle today's chain gives the first unit as its output (`regions[1]`). That is not the tile regrown by a smaller summed halo: beside a tile narrower than the halo, that rectangle would start elsewhere and move a running sum. Every later unit keeps today's rectangles.
  - **The charge, slots and scratch:** these stay today's, which bound both cases. A unit reading held planes takes a subset of what it takes computing them, and the host hands it the scratch it declares for the rectangle it reads without them.
  - **Masked layers:** a masked tile is read only where every tile its reach touches ran. With all three fields Dehaze fills the rectangle Texture's and Clarity's halos need, so behind a small mask few tiles are read.
  - **Point samples:** a point sample reads planes that cover its tile's reach, and otherwise computes its tile as today. It never hands cells back or fills the store. Both give the same byte.
- **Not windows.** A windowed render runs a spatial operation over its window as its own stage, whose edge blocks differ from the whole stage's. `SpatialEntry::cut` therefore marks the operation windowed, and a window neither reads nor fills the store and computes as today.
- **Disposable.** Losing an entry costs only time. It is never part of history, an artifact or a source.
- **Counters.** The store counts the following since its context was created:
  - frame renders that found or missed planes;
  - their tiles that read or computed them;
  - the tiles of point queries that read or computed them;
  - cells handed back, publishes, evictions and refusals;
  - retained bytes and entries.

  `resources.read` reports them as `budgets.reduced_planes`, so the Performance section's samples, `editor-latency`'s evidence and an in-process `editor-performance` (`luxforge_core::resources::read`) can take a hit rate from two reads.
- **Proof.** `modules/presence/cache_tests.rs` tests each unit directly over the rectangles a tile's chain gives it on an odd stage. Computing its planes, handing its cells back and reading them back write the same bits, in the scratch it declares, at tile sides 5, 9, 16 and 61. The file also renders both domains at tile sides that divide neither side of the stage, Dehaze alone, Clarity alone and all three, masked and not:
  - A cold render, a warm one and a warm one after an amount-only change write the bytes of a render in a fresh context.
  - A masked render's partial planes serve only the tiles they cover.
  - A cancelled render publishes nothing.
  - Samples equal the rendered byte with and without the held planes.
  - Each cell is handed back once and holds its value recomputed from the input.
  - The store evicts and refuses at its limit, and Clarity behind Texture touches nothing.

  `render::window` shows a window neither reads nor fills, and `render::reduced` tests the store itself.
- **Adoption.** Kept: on the 24 MP JPEG with Clarity alone, only each stage's first render misses, a drag with the GPU preview off reads every tick but its first from the store, a settle takes 59 to 60 ms against 99 to 103 ms before, the miss that fills costs at most about 26 ms more than a hit and is still faster than any settle before, and the store held 6.5 MB in two entries ([performance](../specs/performance.md#the-reduced-grid-cache)). Each masked layer reads its own input and so has its own entry, and at 60 MP the budget holds about two Dehaze entries. Stacks of several masked Clarity and Dehaze layers at 60 MP are not yet measured.

### RAW rendering reads

- **Row reads instead of pixel reads.** Done. `load_pulled`, `region_in` and `fill_rows` read each pixel through the geometry's unmap, the view's orientation `match`, the entry and the white-balance adjustment, widened to `f64` and narrowed back to `f32` with a per-pixel `finish` check; only an uncropped, unrotated source was read by rows. Now a segment without point replacements whose entry is the source, or a spatial frame the evaluation holds, reads it by rows through any exact geometry. `ViewReader::walk` (`source/linear.rs`) composes the segment's geometry (the unmap of a rectangle's first pixel and its two unit steps, `ExactGeometry::unmap_steps`) with the view's orientation into a first base-plane index and a signed index step per column and per row, checked once at the rectangle's corners, and `ViewReader::visit` copies each row's span from the three planes, as three slices where the step is one value. A spatial frame is read the same way through an identity view (`ViewReader::over`). The last segment's chunks (`LinearRows::load_pulled`), a neighbourhood read before a resample (`Evaluation::region_in`, through `PixelDomain::region_rows`) and a spatial operation's tile input and reductions (`Evaluation::fill_rows`, through `PixelDomain::fill_rows`) all take it. A segment with replacements, a resample's taps and a spatial entry a point query answers from its tiles are still pulled per pixel (`region_pulled`, `fill_pulled`, `LinearRows::entry`), and that pull, through `ViewReader::pixel`, is the reference every row is held to. Values stay `f32` from the planes to a colour segment's rows, the spatial input, the terminal and the boundary texels, and are widened only where the reader is `f64` (a resample's taps). The white-balance test is made once per chunk or row; under an approximation each pixel still takes `WhiteBalanceApproximation::adjust` in `f64`, in the same order and with the same overflow error. Each row's entry, colour and finite check run in the pull's order, so a failing read reports the pull's error. Nothing is materialized: the colour layers before a spatial layer are still pulled again for every tile, now by rows. `every_walk_lands_where_pixel_says` holds every walk over every orientation, crop and step pair to `ViewReader::pixel` on planes whose values name their place; `rows_through_every_view_and_exact_geometry_are_the_pulled_pixels` and `rows_from_a_spatial_frame_through_exact_geometry_are_the_pulled_pixels` compare each chunk's rows, both outputs, a neighbourhood read and a spatial input with the per-pixel pull bit for bit, and the frame with the point evaluator, through all eight source orientations, two view crops, every recipe orientation, crops touching each edge and crops between turns, with and without colour and white balance; `a_white_balance_overflow_is_the_point_error_on_every_row_path` keeps the overflow error.
- **Portrait planes read in blocks.** Done. A portrait view's output row (orientations 5 to 8, or a quarter turn in the recipe) walks down a base column, so reading a chunk row by row touched a new row of all three planes for every output pixel and came back to each base row once per output row. `ViewReader::visit` (`source/linear.rs`) now reads a walk of more than one row whose rows step down a base column as a blocked transpose: each column of the chunk is one contiguous span of a base row, so it reads the base rows the chunk covers once each, in the order the planes hold them, and writes every output row of the chunk from each span, each value at the offset `ViewReader::pixel` gives it. The last segment's chunks (up to 16 rows) take it, from the source and from a spatial frame; a neighbourhood or spatial-input read, one row at a time, is unchanged. Within one chunk's load only one error kind can arise (a white-balance overflow, or a non-finite frame value at the terminal), so the order cannot change the error reported. `a_walk_reads_each_base_row_once_and_a_portrait_walk_reads_them_in_order` checks the order on planes whose values name their base index; the row identity tests above load portrait chunks of 16, 7, 3 and 1 rows with partial last chunks against the per-pixel pull.
- **Resolve without replacements.** Done. `Segment::resolve` (`render/compiled.rs`), which every point query and per-pixel pull calls through `pixel_in`, composed every operation's geometry per pixel to look for a winning replacement even in a segment with none. A segment without point replacements (`!has_pixels`) now answers straight from its unmap with no replacement; one with them walks its operations as before. `resolve_without_replacements_is_the_full_composition` holds the shortcut to the full composition at every pixel of both segments of a stack with two exact crops, every orientation and a resample, with and without replacements.
- **Quantize `f32` without the guard.** Done. The RAW terminal widened every `f32` to `f64` and quantized it through `Quantizer::rounded`, whose ±1e-12 guard re-evaluates the forward transfer near a threshold. Rows whose values are `f32` — a colour segment's rows, and the developed planes or a spatial frame read without colour or white balance — now go through `terminal_f32` (`render/linear.rs`): the same non-finite refusal, then `Quantizer::pixel`. Values that are `f64` (a resample's blend, a decoded point replacement, a white-balance approximation's product, a point sample) keep `rounded`. The 8-bit quantizer is the only one involved; the RAW terminal has no 16-bit output. `only_the_f32_threshold_and_the_value_below_it_lie_in_the_guard_band` shows that within the guard of each of the 255 thresholds there are at most two `f32` values, the threshold's own `f32` and the one below it, and that every other `f32` (those below 0 and above 1 included) is answered by the threshold search both quantizers share; `the_f32_thresholds_are_where_both_quantizers_change_code` holds both to the same code at those two. `the_f32_terminal_is_the_f64_terminal_of_the_same_values` compares the two terminals byte for byte and error for error.

### The RAW float mosaic

Done. A development whose sensor stage leaves the normalized values alone allocates no float mosaic: it holds the u16 mosaic (2 bytes per site, the source's) and the RGB planes (12), where the float mosaic added 4 more, 240 MB at 60 MP.

- **The patch.** `crates/luxforge-raw/patches/librtprocess-mosaic.patch`, which `build.rs` applies to the staged librtprocess after `librtprocess-local.patch` with the same exact-context rule and its own list of the four files it may change, makes RCD, one-pass Markesteijn and both border passes templates over their input. The float rows' instantiation is the code the local patch leaves. The other, `rpMosaicSites`, is the retained mosaic with the black, scale and gain tables `Normalization::sites` builds over one CFA and black-repeat period, and reads every site through one inline function, `rpNormalizedSite`: `((s - black) * scale) * gain` in `f32`, in `Normalization::run`'s order. RCD's tile fill and the border passes read it where they read a float row. Markesteijn addresses its input by flat hexagon offsets, so a tile first writes the sites within three of it (the furthest any read goes, checked when the offsets are built) through the function into a 120 px input tile at the start of its own derivative scratch, which a tile writes only after its last input read and reads only where it has written it: no scratch is added. The adapter's `lf_raw_develop_sites` sits beside `lf_raw_develop` and shares its checks, statuses and error mapping. No file under `vendor/` changes.
- **Contraction.** The float rows' values were rounded and stored in Rust, so the function's last multiply must not fuse with a caller's add. Clang contracts only within one source expression (`-ffp-contract=on`, its default; the build passes no contraction flag), so it cannot. GCC contracts across statements and inlined calls by default (`-ffp-contract=fast`), so under GCC alone the function passes its result through an empty `asm` that emits no instruction. Built with GCC 15 at `-O3` on arm64 without it, 39,485 values of synthetic Bayer developments differed in the border band, where the border pass sums sites; with it, none did. Linux CI builds this crate with GCC on x86-64, whose baseline has no fused multiply-add, and compares no RAW digest there: the pinned digests are M4-only, and the corpus job compares mosaics and ranges, not development hashes.
- **The input, once per development.** `DemosaicInput::of` takes the float mosaic for a development whose sensor stage rewrites the normalized values, a DNG stage-one radial vignette or stage-two gain maps (`apply_sensor`, as on Pixel 7/8 Pro, Leica and Ricoh GR II) or sparse bad-pixel repairs, and the sensor sites for every other one. Cancellation, the resource limits and the native statuses are unchanged; the sensor sites check cancellation once their tables are built and then where the float mosaic's demosaic does.
- **The peak.** The development's diagnostics record its input, the float mosaic's bytes and the bytes it holds through the demosaic. `developments_drop_the_float_mosaic_unless_the_sensor_stage_rewrites_it` asserts that the sensor sites hold 4 bytes a site less, plus their tables (1,536 bytes for a 2×2 Bayer period, 4,752 for a 6×6 X-Trans one), and that sparse repairs keep the float mosaic.
- **Proof.** Synthetic Bayer mosaics in all four CFA phases at RCD's tile edges, black repeat patterns that do and do not divide the CFA, X-Trans frames from the 120 px minimum up and in all 36 phases of the pattern, gains far past sensor white (RCD's input clip and X-Trans's unclamped values) and mosaics at white and under black develop to the float mosaic's planes bit for bit, serial and pooled, border band included, with the float mosaic's cancellation checks, refusals and fault handling. A DNG stage-two gain map or stage-one vignette keeps the float mosaic and a stage-three correction does not. The owner's Z6 NEF, X100VI RAF and Air 2S DNG all take the sensor sites (the Air 2S's opcodes all follow the demosaic) and match the float mosaic and their pinned pre-change digests. Over 120 authentic files, 117 of a local corpus and the owner's three, 102 Bayer and 18 X-Trans, at their as-shot and a perturbed white balance, every development is identical; two DNGs with bad-pixel opcodes (DJI FC220, Leica CL) take the float mosaic, and the 113 the [evidence manifest](../../fixtures/modern-camera-evidence.json) records keep its development hashes. The test is `sensor_sites_match_the_float_mosaic_on_every_local_sample` ([luxforge-raw](../../crates/luxforge-raw/README.md)). The time saved is not measured.

### Analysis and the owner

- **Histogram reducer.** `Bins::add_pixel` (`analysis.rs:202`) counts each channel's 0 and 255 into their own counters, which equal `r[0]`, `r[255]` and so on, and then recomputes the same comparisons in `clip_class`. Derive the per-channel extremes from the bins in `into_report`. Classify with a 256-entry table (`v == 0` as bit 0, `v == 255` as bit 1), combining the three channels with `|` for any-channel and `&` for all-channel counts into a four-way class count. Use `u32` counts per bounded chunk, widened on merge. This runs between the exact render and the settled frame, an estimated 5–18 ms per settle.
- **API answers not copied twice.** `ApiResponse::success` (`api/mod.rs:57`) calls `serde_json::to_value` on its result, which is usually already a `Value`, so every answer is rebuilt on the owner thread. Add a constructor that moves a `Value` in, and use it wherever the answer is one.
- **Lineage prepared once.** `history.lineage` (`editor/history.rs:394`) runs `query_row`, preparing the statement anew for each of up to 100 steps after every undo, redo and restore. Prepare it once (`prepare_cached`), or answer with one recursive CTE.
- **Buffered live-session writes.** The TCP session writer (`api/transport.rs:138`, `:200`) serializes straight into the socket, one `write` per JSON fragment, with Nagle on. Wrap it in a `BufWriter` flushed at each line, and set `TCP_NODELAY`.
- **Strokes shared on entry reads.** `entry_from` → `hydrate_strokes` → `read_strokes` (`editor/catalog.rs:378`, `:515`) reads, parses and re-hashes every stroke a new entry references, even though the entry cache holds the same immutable, content-addressed strokes for the asset's other entries. That is O(strokes) per commit and O(n²) over a painting session. Resolve stroke IDs from cached entries of the same asset first, and query only the rest. Those strokes came from the catalog and were verified there, so the cache's rule that it holds only what the catalog returned still holds.

### Painting

A brush tick is O(points), and so O(n²) over a stroke, on both sides of the owner call:

- **Desktop.** Each path-growing move clears the stroke's memoized decimation (`mask_draft/brush.rs:192`), re-runs Ramer–Douglas–Peucker over the captured path through `capture_error` (`app/masks.rs:1673`), clones the points and builds a `Value` per point (`brush.rs:315`). It then overwrites `pending` even when a round trip is in flight (`app/draft.rs:196`), so the work is thrown away, deep-clones the fields into `sent` (`draft.rs:296`) and clones the set again into the session (`app/gesture.rs:745`). Build the fields only when they will be sent, by marking the draft dirty while a round trip is in flight. Hold the decimated points as `Arc<[[f64; 2]]>` and cache their `Value`. Keep a revision in place of the `sent` clone.
- **Owner.** Every call deep-clones the session, draft included (`api/owner.rs:1483`). `draft.set` clones the draft (`api/methods.rs:2074`) and builds `next.request()` only to test a key (`:2083`). Planning builds `draft.request()` again (`editor/plan.rs:608`). The answer repeats the draft. Test keys on the fields directly, snapshot the session only for handlers that can park a pixel read (or share the draft behind an `Arc`), and avoid the second `request()`.
- **Not in scope.** The wire protocol stays as it is. Append-only points would be an API change for the owner to decide.
- **Done, and what remains.** The desktop builds a stroke's fields once per send, from the decimation cached as `Arc<[[f64; 2]]>`, which a position snapping into the cell before it keeps. `draft.set` answers in the update that sends it, so every path-growing move is still one send with one whole-path decimation and one copy into `sent`. The owner takes `draft.set`'s fields out of its request, merges without copying the fields it replaces and keeps the draft out of its rollback copy, so an unplanned tick copies the path once, into its answer. A tick planned over a spatial stack still copies it twice more: the request `Prepared` reads (`Draft::request`) and the values the mask planner splits; removing them needs the planner to read parameters by reference.

The frozen coverage, draft identities, evidence semantics (`frame_pending`, `drained`) and one-entry-per-stroke history do not change.

### The desktop

- **GPU preview blocks.** Each prepared frame during a GPU gesture concatenates every program's block into one `Vec<u32>` (`pack`, `luxforge-ui/src/photo_surface/gpu_preview.rs`), then the slot and each link of a spatial chain (`gpu_preview/chain.rs`, `write`) compare the whole of it with their last write through `mask::changed_ranges` and copy it again on any difference: up to about 6 MiB per frame with a lens warp grid or a heavy brush mask. Separately, the lens warp grid is converted and collected into a new `Arc<[u32]>` on every tick (`luxforge-app/src/app/gpu_plan.rs`, `grid.nodes`) although it is fixed for the draft. Convert the grid once when the boundary is held. In the surface, remember each step's block `Arc` and offset, skip blocks whose pointer is unchanged and compare only the rest. Done, on the slot's [shared scratch pool](gpu-preview.md#plane-sharing-and-precision), which restructured the same chains: the held boundary keeps its warp grid as the tail's words (`gpu_plan::WarpGrid`), and the slot and each link keep the blocks they packed (`gpu_preview/blocks.rs`), so a block handed again at the same place is neither compared nor copied and a link's key hashes each block once. What remains per tick: a spatial link's schedule (`spatial::Schedule::run`) still hashes its steps' words and blocks whenever the link runs, which over a lens warp includes the whole grid.
- **Collapsed sections build no controls.** `state/tools.rs:814` builds every section's control models on every message, collapsed or not. For presets that clones each preset's settings and strings (`state/presets.rs:451`), about 1 ms per message with a large library. Build controls only for a section that shows them, after checking what reads section models outside the view: evidence summaries, `query_choice.rs` and curve sampling.
- **Job polls without a full update.** While an export or capability job runs, `time::every(100 ms)` produces two full updates per tick (`app/export.rs:330`, `app/capabilities.rs:429`), each re-deriving the workspace and rebuilding the view even when the read changed nothing. Extend the idle fast path in `update_inner` to unchanged poll reads, or replace the timer with an owner wake on job change like the event waker.
- **Done, and what remains.** A collapsed or unavailable section builds no control models; the evidence report and the readers outside the view that need them build them on demand from the same inputs. A live job is read inside its subscription's stream (`app/job_reads.rs`), which sends the desktop a message only when the job's record changes or the job ends, because iced rebuilds the view after every message whatever `update` does; an export reports no progress, so only its end reaches the update loop. Each live job still costs one owner read every 100 ms on the executor; only an owner push on job change would remove it. An expanded Presets section still builds its library on every message. A `module.status` answer applied after a newer read can show an older job record until the job next changes.

## Catalog durability

The catalog opens with `synchronous=FULL` and `locking_mode=EXCLUSIVE`, and a rollback journal by default (`editor.rs:642`). Each commit writes its pages twice and syncs three to four times. Bundled SQLite's syncs on macOS are plain `fsync`, because `fullfsync` is off by default, so a commit is not flushed from the drive's cache. That contradicts the crate's own rule in `atomic_file.rs`, where every durable write is `F_FULLFSYNC`.

In the durable build, open with `PRAGMA journal_mode=WAL`, `synchronous=FULL`, `fullfsync=ON` and `checkpoint_fullfsync=ON`, after `locking_mode=EXCLUSIVE`, so no shared-memory file is created. A commit then appends once and makes one full flush; checkpoints run automatically. Test builds keep `synchronous=OFF` behind `test-skip-disk-flush`.

The consequences, each covered by a test or documented:

- While a catalog is open, `<catalog>-wal` lives beside it, and a crash leaves it there for the next open to recover. Anything that copies, moves or backs up a catalog treats the WAL file as part of it. The catalog-backup question stays open in [decisions](../decisions.md#open-product-questions).
- A clean close checkpoints and removes the WAL file. Quitting the desktop through the macOS application menu (Cmd+Q) does not run its close, as before this change, so the WAL file stays beside the catalog and the next open recovers it.
- The format marker, the refusal of unsupported catalogs and recovery after an interrupted commit behave exactly as now.

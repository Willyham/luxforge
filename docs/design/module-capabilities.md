# Module settings, permissions and managed resources

Status: **implemented and verified on the M4 Mac.** The contract was frozen on 2026-09-23 under the owner's delegation ("make sensible decisions, don't block on me"); its decisions are recorded in [product decisions](../decisions.md#module-capabilities) and can be revisited by the owner. The code lives in `crates/luxforge-core/src/capabilities/` (settings, the secret store's contract, grants, consent, endpoint parsing, the transport's contract, the worker, resources, tasks, the `local-runtime` resident set in `runtime.rs` and the host-planned read in `read.rs`), `crates/luxforge-core/src/inference/` (the inference port and its deterministic fake), `crates/luxforge-net` (the transport and the macOS Keychain store, which the desktop and `luxforge-json` give the host through `HostConfig`), `crates/luxforge-core/src/artifacts/` and `editor/artifact_store.rs` (derived artifacts), `modules/capabilities_proof.rs` (the proof module and its endpoint) and, in the desktop, `app/capabilities.rs`, `state/capabilities.rs` and `view/capabilities.rs`. This is the shared host capability contract for linked modules. It extends the [current module contract](modules-and-api.md); it does not select a binary plugin format or introduce accounts, cloud sync or a marketplace. [AI editing](ai-editing.md) is the first intended consumer. Every operation available in the desktop is a discoverable method of the shared service.

## Outcome and boundary

A module declares settings, provider adapters, capabilities, resources and worker tasks. Only the host stores settings or secrets, downloads resources, contacts endpoints, schedules work or publishes persistent artifacts; a module receives those through a worker-side `ModuleContext` that enforces the grant it runs under. Descriptors stay plain data and registration does no I/O. A module loads nothing ahead of a request: a task reads the installed resources it uses through its own context, on a worker, and nothing is loaded as a side effect of `module.list`, catalog reopen, recipe compilation or panel construction. Listing, reopening and schema discovery cause no network, keychain or model activity.

These capabilities apply to **trusted linked modules**. A declaration serves consent, least privilege and auditing; it is not a sandbox for code linked into the editor. External executable loading stays the separate measured project on the [roadmap](../plan.md) and must add a process/ABI trust boundary before untrusted code is supported.

## Decisions

| Question | Decision |
| --- | --- |
| Setting scopes | Two, both user-level and outside every catalog: module settings and named provider profiles of a module. No per-catalog or per-photo settings. Settings never create history entries and have no image effect by themselves |
| Consent unit | **Per asset** for sending image data: a grant names the module, capability, provider profile, adapter, endpoint origin, data class and asset. Grants are not remembered for later photos. A resource download is granted per resource version and origin. Revised by the owner on 2026-10-05 for provider photo data: a grant is remembered per provider profile and data class until revoked; the change lands with the [AI editing](ai-editing.md) remote tier |
| Who may grant | Only a client with **permission authority**: the desktop's own client (after the person presses Allow) or `luxforge-json --permission-authority` (an explicit local headless setup step). Loopback live-session clients and plain `luxforge-json` never can. Anyone may deny or revoke, since both reduce privilege |
| Revocation | Stops new work, cancels queued and running jobs that depend on the grant (`cancelled`, reason `permission revoked`) and never touches recipes, history or accepted artifacts. Changing a profile's endpoint, removing a profile or resetting a module revokes the grants scoped to the old value (a profile's adapter cannot change) |
| Secret store failure | macOS Keychain first. A locked, missing or unsupported store fails with `not-ready` naming the store; there is no plaintext fallback. Windows Credential Manager and Linux Secret Service report `not-ready: secure storage is not implemented on this platform` until natively verified |
| Endpoints | HTTPS for anything remote, with public addresses only; plain HTTP only to loopback (`127.0.0.0/8`, `::1`, `localhost` resolving to loopback), which is a separately labelled `loopback` class. No proxies, no `file:` or other schemes, no userinfo in URLs |
| Remote provider adapters in the first release | None besides the developer proof adapter. Real adapters arrive with AI editing, each reviewed |
| `managed-storage` capability | Not implemented; a descriptor naming it is refused as an unknown kind until its first consumer defines it |
| `local-runtime` capability | Defined by [AI editing](ai-editing.md#the-inference-port-and-its-runtime): a declared resource held loaded by the host's inference runtime between tasks, in a host-owned slot with a declared resident size. Needs no grant: nothing leaves the machine, and installing the resource already took the `download-artifact` grant. See [local runtime](#local-runtime) |
| Activation | Per model, not per module: `module.runtime.load` opens one model ahead of its first task on the module lane, and `module.runtime.unload` releases it. There is no `module.activate` or `module.deactivate`. Nothing loads on `module.list`, `schema.list`, `module.status`, a catalog open or a launch |
| Host-planned reads | A task that declares `reads` is given the stage it names, planned by the owner at request time and read on the module lane from the reference renderer. See [the host-planned read](#the-host-planned-read) |
| Catalog format | The [current catalog format](versions-and-lineage.md#storage-the-catalog-format) holds the catalog's identity and the artifact tables beside the preset library, library journal, previews and the [mask](masking.md) table and stroke store; unsupported formats are refused by name and kept intact (current shapes only) |
| Settings format | One JSON file per user with `format: 1`; any other marker is refused and the file is retained unmodified |

## Configuration contract

`ModuleDescriptor` gains optional, plain-data fields. Every one defaults to empty, so existing descriptors are unchanged.

```text
settings:   { schema: u32 ≥ 1, fields: [Setting], profiles?: { label, max: 1..16, adapters: [Adapter], fields: [Setting] } }
Setting:    { …Parameter, label }
kind:       boolean | integer | number | enum | string | endpoint {classes: [remote|loopback]}
            | secret {max_length ≤ 4096}
Adapter:    { id, title, auth: none|bearer, data: [data class], max_request_bytes, max_response_bytes,
              timeout_ms, retention?, cost: free|paid|unknown }
capabilities: [ { id, kind: remote-image-request {adapter, data}
              | download-artifact {resource}
              | local-runtime {resource, model: session|generator, resident_bytes,
                               backends: [name], precision: fp32|fp16|bf16|int8|mixed}, purpose } ]
resources:  [ { id, title, version, url, bytes, sha256, format, license, provenance, redirect_origins?,
              files?: [ { name, url, bytes, sha256 } ], tradeoff?, use_restriction?,
              min_memory_bytes?, flag? } ]
tasks:      [ { id, title, notes, asset: bool, profile: bool, uses: [capability id],
              parameters: [Parameter], apply?: {action, parameter}, reads?: repair-input,
              flags?: [flag id] } ]
```

A setting is declared in the module parameter vocabulary: it is a `Parameter` exactly as an action declares one ([module contract](modules-and-api.md)), serialized the same flat way with the same fields (`name`, `kind` and the kind's own fields, `required`, `default`, `unit`, `step`, `precision`, the numeric hints and `notes`), with `label` beside them. Its `name` is the setting's identity, `notes` is the help a settings view shows under it, and `schema.list` emits it through the same serialization as every method's `parameters`. A setting takes the kinds a settings store holds and a settings view edits — `boolean`, `integer`, `number`, `enum`, `string`, `endpoint` and `secret` — and registration refuses any other kind by name. `endpoint` and `secret` are parameter kinds that only a setting declares: an action, query or task parameter of either kind is refused at registration, so a destination is never part of a request, a recipe or a job, and the one request that carries a secret stays `module.settings.set-secret`. An `endpoint` is a profile field only: the host sends only to a profile's endpoint, so a module-level one would do nothing and is refused. An `endpoint` value is a URL of at most 4096 bytes that the transport policy accepts as one of its classes; no plain value of a `secret` is ever valid. Identities follow the existing rules: setting, adapter, capability, resource and task IDs are hyphenated lowercase names; a task ID is unique across the registry because it generates the method `task.<id>`. Registration rejects, with a `validation` error naming the field: a malformed or duplicate ID; an unknown kind; any declaration the parameter vocabulary refuses for a parameter (an empty range, empty or duplicate enum options, a `string` `max_length` outside 1..=256, a `secret` `max_length` outside 1..=4096, an `endpoint` with no class or a class twice, an unsound hint, a default outside its kind; a `secret` never has a default and an `endpoint` default is refused); a capability naming an undeclared adapter or resource; a module-level `endpoint` setting; a profile block without an `endpoint` field when an adapter is declared; a resource whose `url` is not HTTPS unless it is loopback, whose `sha256` is not 64 lowercase hex, whose `bytes` is 0 or above 16 GiB, or whose `redirect_origins` are not HTTPS origins; a task naming an undeclared capability or an `apply` action or parameter that does not exist or is not of kind `artifact`; a task that `reads` a stage without taking an asset; a `local-runtime` capability whose resource is undeclared, is installed by no `download-artifact` capability or is held by another `local-runtime` capability, whose `resident_bytes` is outside 1 byte..64 GiB, or whose `backends` are not 1 to 8 distinct names; and `managed-storage`, an unknown kind. It also refuses a profile block without adapters; a `bearer` adapter whose profile fields do not declare exactly one secret; adapter byte limits outside 1 byte..256 MiB or a timeout outside 1..600000 ms; an empty title, format, license, provenance or retention note; a resource version that is not a plain directory name; a task that uses a capability twice; a task that takes a profile without a profile block, and a `remote-image-request` task that does not take both an asset and a profile. A `remote-image-request` data class must be one of its adapter's, and `redirect_origins` are exact serialized origins (`https://host[:port]`, default port omitted). Profile `max` is 1..16 and module-level plus profile fields are at most 32 each.

`module.list` and `schema.list` return exactly these declarations. They contain no setting values and never a secret: a secret field declares only its presence.

A module that declares tasks, resources or an effect with `artifacts: true` implements the capability hooks, `CapabilityModule` beside its `ToolModule` ([module trait](modules-and-api.md#module-trait)); registration refuses one that declares any of them and provides no hooks, naming the declaration. Settings, profiles and capabilities alone are the host's and need no module code.

Two descriptor additions support the rest of the contract. A parameter kind `artifact` carries one artifact ID published in the catalog; the host checks its syntax generically and the commit checks that it exists. A control kind `task {task, label}` is a button that runs the task through the desktop's consent and progress flow and, when the task declares `apply`, offers Apply with the result. An effect may declare `artifacts: true`; only a layer of such an effect may reference artifacts.

### Settings store

Non-secret values live in `<config>/modules/settings.json`, outside every catalog: `{format: 1, modules: {<module_id>: {schema, revision, values, profiles: [{id, adapter, label, values}]}}}`. Profiles have host-generated IDs (`profile-<uuid>`). Each module has its own monotonic `revision`. The settings file, the grants file and each installed resource's `installed.json` are one kind of store: a JSON document of one shape under its own `format` marker and size bound, read afresh on every call. A change takes an OS advisory lock beside the file, re-reads it, applies the change, and writes a temporary file, syncs it, renames it over the old one and syncs the directory; a failure leaves the previous file, and a change that changes nothing writes nothing. The derived-artifact store publishes its objects and manifest through the same durable write. The settings file is at most 1 MiB. A `format` other than 1, or unparseable JSON, fails every settings method with `incompatible` and the file is never rewritten. A module whose stored `schema` differs from its descriptor reads `state: incompatible`, keeps its stored values untouched and refuses writes until `module.settings.reset` clears that module's entry explicitly. A stored value its field's declaration does not accept reads `valid: false` with the reason and is kept until it is written or reset; nothing rewrites or drops it. Entries for modules that are not registered are kept verbatim.

Every settings mutation takes the edit mutation envelope `mutation: {expected_revision, request_id, actor}`, where the revision is the module's settings revision. A stale revision is a `conflict`. The settings file keeps no request log: a settings write sets values rather than changing them, so its retry is answered from the catalog owner's request table like every revision-less mutation ([host dispatch](modules-and-api.md#host-dispatch)) with the first answer marked `deduplicated: true`, and the same `request_id` with a different input is a `conflict`. The table lives for the owner's lifetime and holds the most recent requests; a retry after a restart, or after its answer left the table, conflicts on the revision it was made against, and the client reads the settings its write left. A write that changes nothing is `outcome: no-op` and keeps the revision. Committed settings writes emit an event whose method is the method name; a retry emits none. Every write answers `{module_id, outcome, revision, deduplicated, profile_id?, profile?, changed, revoked?}` plus `settings`, a read after the write; a retry gets that first answer again. A `set-secret` request is keyed with its value redacted, so a retry is matched by the setting alone and no hash of a secret is held; writing a secret is idempotent.

`module.settings.read {module_id}` returns `{module_id, schema, revision, state, fields: {<id>: {value, default, source: user|default, valid, error?}}, profiles: [{id, adapter, label, fields, status}]}`. A secret field reports `{secret_present, valid, error?}` instead of a value, where `secret_present` is `null` when the store cannot answer, so a locked keychain shows on that field rather than failing the read. A profile's `status` is `ready`, `incomplete` (a required field is missing or invalid), `missing-credentials` (the adapter authenticates and the secret is absent) or `incompatible`. The host can report this without loading anything.

`module.settings.set {module_id, profile_id?, values: {<id>: value | null}, mutation}` validates each named field with the parameter vocabulary's own check of its declared parameter, exactly as an action's parameter is checked, and commits them together; `null` returns the field to its default. A secret field is refused here. An `endpoint` value is parsed and classified by the transport policy. `module.settings.set-secret {module_id, profile_id?, setting, value, mutation}` stores the value through the secret store and returns the read result; the value is never echoed. `module.settings.clear-secret` removes only that secret. `module.profile.create {module_id, adapter, label, mutation}` returns the new profile; `module.profile.remove {module_id, profile_id, mutation}` removes its values, clears its secrets and revokes its grants. `module.settings.reset {module_id, mutation}` deletes the module's values and profiles, clears their secrets and revokes their remote grants (a download grant names a pinned resource, not a setting, and survives); it keeps the module's schema and revision, so the revision never goes backwards and a retry the request table no longer holds conflicts rather than clearing values written since, and it is the explicit way out of an incompatible schema or an entry that is not in the current shape. Removing a profile or resetting a module that declares secrets answers `not-ready` while the secret store is unavailable, because the secrets could not be cleared.

### Secrets and redaction

`SecretStore` is a host trait with `set`, `clear`, `present` and `read`, defined in the core; the macOS store is `luxforge-net`'s `KeychainSecretStore`, which the desktop and `luxforge-json` give the host. It keeps generic passwords under the service `app.luxforge.module-secret` and the account `<module_id>/<profile_id or ->/<setting_id>`; `present` queries attributes only, so it never asks for the secret's data. A locked or unavailable keychain maps to `not-ready`. `read` is called only on the module worker, inside a task of the module that declares the secret; the value is a `SecretValue` that is not `Serialize`, whose `Debug` prints `<redacted>` and whose buffer is zeroed on drop. The OS may show its own prompt when a rebuilt executable reads an item an earlier build stored; that prompt belongs to the OS, and a set or clear that waits on it holds the owner for its duration. Evidence runs and tests use an in-memory store and never touch the login keychain; the native journey is an opt-in ignored test in `luxforge-net`.

The core also exposes `UnavailableSecretStore` and its constructor for hosts without secure storage. `luxforge-net` uses it on Linux and Windows; every secret operation returns `not-ready`, with no plaintext fallback.

Redaction is structural: no descriptor, read result, event, error, job record, status, log or evidence file can carry a secret, because nothing but `set-secret` requests and the worker's `SecretValue` ever hold one. `redact_params` replaces the `value` of a `module.settings.set-secret` request's parameters with `"<redacted>"`; the desktop's request log, evidence capture and Copy as JSON record a request's method and its parameters through it, never its live-session token. Tests set a sentinel secret and scan every response, event, log and evidence file for it.

### Provider adapters

A profile names one declared adapter: a typed contract, not a URL template. The adapter declares its data classes, request and response size limits, timeout, authentication, retention note and cost. The host builds the request body only from the task's declared data, sends it through the transport under the grant and returns the response bytes to the module; a module never supplies a URL. The first data class is `sample-grid-8`: an 8 × 8 grid of rendered sRGB samples of the asset's current entry at the centres of an 8 × 8 grid over its output stage, sent as fixed-width JSON of exactly 959 bytes (`{"data_class":"sample-grid-8","width":8,"height":8,"samples":[[r,g,b],…]}`, each channel padded to three characters), which is the size the disclosure states. The owner binds the entry at request time and the module lane takes the 64 samples through one evaluation of the whole-frame reference renderer, off the catalog owner. A spatial prefix materializes each spatial segment's frame once and shares it across the samples; a stack without a spatial segment needs no frame. This capability-data path does not use the desktop tile service. AI editing adds its crop and mask classes with its remote tier. No provider receives an original path, EXIF or extra context.

## Capability and consent contract

Three capabilities are implemented. `download-artifact` installs a declared resource from its pinned URL. `remote-image-request` sends a declared data class of one asset to a profile's endpoint through its adapter. Each of these two is gated by a **grant** whose scope is exact. The third, [`local-runtime`](#local-runtime), holds an installed resource loaded on this machine and needs no grant; a grant of it is refused as a `validation` error.

| Capability | Grant scope |
| --- | --- |
| `download-artifact` | `{module_id, capability, resource, version, origin}` |
| `remote-image-request` | `{module_id, capability, profile_id, adapter, origin, data, asset_id}` |

A module that reads a user-chosen file may add a `read-user-file` capability back later, consented per canonical path.

A gated operation without a matching grant fails before any work starts with `consent-required` and `data.consent: {module_id, capability, scope, disclosure, denied}`. The disclosure names the module and purpose, the destination (an origin), the data to be read or sent and its size, the storage location and expected bytes for a download, the adapter's retention note and whether it may cost money; `denied` is true when a denial is recorded for that scope. The desktop shows this as a consent notice with Allow and Don't allow; a headless client receives the same failure.

Every permission and resource change takes the `{request_id, actor}` mutation envelope: none of them changes anything with a revision, so a retry is answered from the owner's request table with the first answer marked `deduplicated: true`, and the same `request_id` with other input is a `conflict` ([host dispatch](modules-and-api.md#host-dispatch)). `module.permission.grant {module_id, capability, scope, mutation}` requires permission authority and otherwise fails with `forbidden`; the scope must be one the module can use. It records `{grant_id, module_id, capability, kind, scope, actor, request_id, created_ms}` from the envelope and clears a matching denial; a grant of a scope that already has a live one returns that grant as a no-op. A denial does not revoke a live grant. `module.permission.deny {module_id, capability, scope, mutation}` records a denial with the envelope's actor. `module.permission.revoke {grant_id, mutation, reason?}` marks the grant revoked with a reason and cancels dependent jobs. `module.permission.list {module_id?}` returns grants, revocations and denials; `module.status` carries only their counts. Grants live in `<config>/modules/grants.json`, a document of the same store as settings with its own `format: 1` marker and bounds (at most 1024 records and 2 MiB); nothing is copied with a catalog. A record past the bound first prunes the oldest revoked grant or denial. When every record is a live grant, the oldest live `remote-image-request` grant is evicted instead of the new record being refused, so the next request for that scope fails with `consent-required` and is asked for again; a `download-artifact` grant is never evicted, so a file holding only live download grants refuses a new record with `resource-limit`. No grant follows from a retry, a saved recipe, a configured key or same-user API access.

### Transport

The host transport is the only network path. It parses a URL, requires `https` for the `remote` class and allows `http` only for the `loopback` class, rejects userinfo, fragments and every other scheme, resolves the host once, requires every resolved address to belong to the endpoint's class (`remote` refuses loopback, private, link-local, shared, unique-local, multicast, unspecified, documentation and IPv4-mapped forms of these) and connects to the checked address, so a second resolution cannot rebind it. A host must be ASCII: an internationalized name is refused as an invalid URL (`invalid international domain name`), while its punycode form (`xn--…`) is accepted and resolved as written, because URL parsing carries no Unicode data. TLS uses rustls with the ring provider and the operating system's certificate verifier (native roots with webpki on Linux); tests inject their own roots. Redirects are refused unless the request allows them; an allowed redirect must stay HTTPS, target an origin in the declared list and passes the same checks, and it drops the `Authorization` header when the origin changes. A response larger than its limit is refused from its length header or cut off at the piece of at most 16 KiB that would cross it; a connect deadline, an idle deadline between reads and writes and a whole-request deadline apply, and cancelling the request's job shuts its socket down, so a blocked read, write or TLS handshake returns at once (a lookup or a connect attempt is bounded by its timeout instead). Only 301, 302, 303, 307 and 308 redirect, always as a `GET` without a body; other `3xx` answers are returned as data, and a same-origin redirect must be listed too. A request refuses a body on `GET`, more than 32 caller headers, a head over 16 KiB, control characters and every connection-level or cookie header; a response refuses compression, any transfer coding but `chunked` (and any at all on HTTP/1.0), a length that is not one plain number or disagrees with another, both a coding and a length, `101`, a status of 600 or more, a head over 64 KiB or 100 fields, and a TLS body that ends without the server's close signal. Every failure is structured: `validation` for a refused URL, address or redirect, `resource-limit` for size, `read-error` for network and TLS failures and timeouts, `cancelled` for a cancel.

The core defines the transport as a trait, `capabilities::transport::Transport`, that sends one checked request under the caller's bounds and job, and takes it in `HostConfig`; resource installs and `ModuleContext::send` call it, and the core links no network stack. The implementation is `HttpTransport` in `crates/luxforge-net`, which the desktop and `luxforge-json` build (it builds its TLS configuration on its first request, never at start). The core's capability tests send through an in-memory transport instead, and the TLS, protocol and address tests run against `HttpTransport` in `luxforge-net`.

The HTTP/1.1 is [`ureq`](https://crates.io/crates/ureq)'s own agent, 3.4.2 with no features, one per request, built with `Agent::with_parts` from the transport's own parts (`luxforge-net`'s `transport/agent.rs`): a resolver that resolves the endpoint's host once through `Resolve` and answers only if every address passes `address_allowed` for the endpoint's class (an IP literal without a lookup); a connector that connects through `Connect` to those addresses only, checks each again, and hands the job's `JobControl` a clone of the socket, which the job's cancel shuts down; and TLS on the transport's own rustls configuration. The agent has no proxy, no pool and no redirect following, returns every status as data and sends `Accept-Encoding: identity`, so the transport keeps its own redirect check and its loop over at most three redirects. It streams the final body through the agent's reader in pieces of at most 16 KiB, reporting progress after each; the reader stops one byte past the limit, so a body of exactly the limit is whole. The request head is the one the transport writes (`Host`, `User-Agent`, `Accept-Encoding: identity`, `Connection: close`, the caller's headers, and a `POST`'s `Content-Length`), with no `Accept` added.

Two parts of `ureq` are not used. It does not export its `TcpTransport`, so the connector supplies its own socket transport. Its `RustlsConnector` would accept a truncated body: `ureq` ends a close-delimited body at an `UnexpectedEof`, which is how rustls reports a connection that closed without the server's close signal, so the transport's own TLS transport reports that as an error. For the same reason a cancelled close-delimited plain body reads as complete, so the transport checks the job's cancel before it reports a body whole, and a cancel overrides any other outcome. The agent's own timeouts are per phase and turn a zero remaining time into one second, so the socket applies the transport's deadlines itself: before every read and write it checks the job's cancel and the whole-request deadline and waits at most the idle timeout or what remains of the request, whichever is shorter; a connection reset is a failure, never the end of a body. A cancel of a request stalled in its TLS handshake, TLS or plain response head, TLS or plain body or close-delimited body returns within 0.4 ms (20 samples, 74 to 352 µs, test build on the M4 at load 9 to 11), where the hand-written client this replaced waited for its 100 ms read slice.

The transport keeps the stricter framing it can judge from a parsed head: the compression, transfer-coding and length checks above, the 100-field cap (`ureq-proto` holds 128) and the refusal of `101` and statuses over 599. Three bounds of the hand-written client went with it, as `ureq-proto` reads them: a bare line feed ends a line (RFC 9112 lets a recipient accept one, and with one request per connection nothing can be smuggled behind it); interim responses are each held to the 64 KiB head limit, not to one budget together, and trailers are read and discarded line by line, each line within the connection's 128 KiB input buffer, so their total is bounded by the idle and whole-request deadlines, not by size; and a chunked body whose last chunk arrives before the connection closes is whole without its closing blank line. `ureq` and `ureq-proto` trace request heads, `Authorization` included, to the `log` facade at trace level; Luxforge installs no logger, and one added later must leave them out. `cargo xtask check-repository` refuses `ureq_proto::` and `httparse::` outside `luxforge-net` and a dependency on `ureq` or `ureq-proto` outside it, so no second HTTP framing appears, and refuses a TLS, HTTP or Keychain crate in `luxforge-core`'s manifest. The executable and package cost is in [performance](../specs/performance.md#transport-on-ureqs-agent).

## Lifecycle, jobs and resources

Methods: `module.status {module_id}`, `module.resource.list {module_id}`, `module.resource.install {module_id, resource_id, mutation, source?}`, `module.resource.remove {module_id, resource_id, mutation}`, `module.runtime.load {module_id, resource_id}`, `module.runtime.unload {module_id, resource_id?}` ([local runtime](#local-runtime)), and `task.<id> {asset_id?, profile_id?, mutation, …parameters}`; a capability job is read and cancelled with the one job API every kind shares, `job.read {job_id}` and `job.cancel {job_id}` ([jobs](modules-and-api.md#jobs)), and a task job's [candidates](#job-candidates) are read and released with `job.read-candidate` and `job.release-candidates`. All are in `schema.list`. An install records the envelope's actor in its `installed.json`. A `task.<id>` request queues a job, so it carries the `{request_id, actor}` envelope like every other job it starts: a retry returns the first `{job_id, status}` marked `deduplicated: true` and starts no second job, and a refusal such as `consent-required`, `not-ready` or `preparation-required` is not remembered, so a client asks again under the same `request_id` once it has answered it.

Every task request checks its declared requirements before anything is queued: a profile that is not ready, a resource the task uses that is not installed, a `local-runtime` capability on a host with no inference runtime (`{kind: runtime, id: <capability>, state: unavailable}`) and a flag the request needs that is off (`{kind: flag, id, state: off}`) fail together with `not-ready` and `data.requirements: [{kind: profile|resource|runtime|flag, id, state}]`, and a missing grant fails with `consent-required` for the first one. Three optional hooks let a module shape this per request, each a pure function of the request's parameters: `task_needs` narrows the capabilities a request uses to a subset of the task's declared `uses` (a generative fill needs its text encoder only with a prompt), names the flags it needs and says whether it locks its photograph; `admit_task` refuses a request from the stage size the task reads and the bytes of the stack's bound artifacts, before anything is queued or read (a fill's `resource-limit`s); `status` adds the module's own fields to `module.status` from the host's resource, runtime and flag state, opening nothing. A task that locks its photograph holds it while its job is queued or running and not cancelled: every edit of the photograph (`edit.*`, `history.undo`, `history.redo`, `history.restore`, `draft.begin`, `draft.reapply`, `draft.commit`) and another locking task on it are refused `conflict` with `data: {reason: "locked", asset_id, job_id, method}`, `batch.apply-settings` skips it as `locked`, and every other photograph stays editable. Otherwise the request returns `{job_id, status}` promptly, and the job's record names its `asset_id`. `job.read` answers a capability job as `{job_id, kind: install|remove|task|load, status, progress: {fraction?, message?}, module_id, resource_id?, result?, error?, request_id?, candidates?}`, a task job with its [candidates](#job-candidates) with `status` the one job-status vocabulary every job kind shares; a capability job never reads `superseded`. `error` is `{code, message, data?}`. Any client may read or cancel a capability job: resources and tasks belong to the module, not to a session, and a client's disconnect leaves its jobs running. Cancelling a queued job removes it; a running job stops at its next checkpoint and releases what it held. The owner keeps the last 32 finished capability jobs. A request that changes state at once (a grant, denial, revocation or settings write) and a successful install, removal or task emit an event carrying the originating method and request ID; a cancelled job that had not started emits one under the request that started it; failures emit none.

Capability jobs are records in the catalog owner's one job table and run on two of its lanes, each one thread that sleeps while idle and is started on first use: `transfer` (install and remove) and `module` (tasks and model loads). Each lane runs one job and holds at most four queued; a fifth request fails with `resource-limit`. Nothing that hashes, downloads, loads resources, runs a task or reads a secret's data runs on the catalog owner or UI thread. Workers post completions into the owner's channel; nothing polls. The desktop follows each capability job through a stable `job.wait` subscription: first, changed and terminal records only. Hidden presentation coalesces progress while retaining consent, partial business results and every outcome; restore reconciles current state once.

Every capability job publishes to the [activity board](performance-panel.md#activity-board) the moment its lane picks it up, and ends it when its result is in: `activity.list` lists it beside source preparation and analysis, with `kind` `module.resource.install`, `module.resource.remove`, `module.task` or `module.runtime.load`, and `detail` naming the module and, for a resource job, the resource. A job's `progress` is read from that same activity, the one progress model every publisher shares; the job record keeps no separate copy.

A task receives the path of every installed resource it `uses` through `ModuleContext::resource_path` and reads it on the module lane itself; only a `local-runtime` capability keeps a resource loaded between tasks ([local runtime](#local-runtime)). `module.status` reports settings validity, resources, grant and denial counts, live jobs, `machine: {memory_bytes}` and, for a module that declares `local-runtime`, `runtime: {held_bytes, budget_bytes, available, models}`. Removing a resource releases a model a `local-runtime` capability holds of it and cancels its load, then queues the removal on the transfer lane; a task that uses it is refused `not-ready` from then on, and an accepted edit keeps rendering from its artifact.

A resource installs only from its pinned URL, under the `download-artifact` grant: `source` is `{kind: "download"}` or absent, and any other source or field is refused as a `validation` error, so no client can make the host read a path it names. The worker streams into `<data>/modules/resources/.staging/<module_id>/<resource_id>/<version>/`, refuses a file once it exceeds its declared `bytes`, checks each file's exact length and SHA-256, asks the module's `validate_resource` hook to check each file's format, checks the resource quota (16 GiB across modules), then renames the directory to `<data>/modules/resources/<module_id>/<resource_id>/<version>/` (the resource's own file is named after the resource ID, each further file by its declared name) and writes `installed.json` last with the URL, hash, bytes, every further file's pin, license, provenance, actor and time. Only a directory with a matching `installed.json` beside every file at its declared length is installed, so an interruption, crash, short, corrupt, oversized, redirected or disk-full transfer leaves no installed resource, and staging no current declaration names is removed by the next install. Downloaded data is never executed or deserialized with a general object loader, and a checksum proves the bytes match the manifest, not that a model is safe or licensed for reuse. Removal deletes the version directory and any kept partial transfer of the resource, and can never make an accepted edit disappear.

**Several files.** A resource is its own file (`url`, `bytes`, `sha256`) and up to seven further `files: [{name, url, bytes, sha256}]`, at most 16 GiB together; a model's encoder and decoder, or a transformer and its autoencoder, are one resource. Every file is served from the resource's own origin, the one its download grant names; a file name is a plain name that is neither the resource's own nor `installed.json`, and appears once. They download in order into one staging directory, are verified, checked and moved into place together, and are removed together, so a resource is installed whole or not at all. `module.resource.list` reports `bytes` as their total, `files: [{name, bytes}]`, and the quota counts every file.

**Resuming.** The staging directory holds a `.partial.json` naming the module, resource, version and every file's pin it was fetched under. A transfer interrupted by a network failure, an error status or a cancel (`file-access` or `cancelled`) keeps what it staged; a verification failure, a refusal, a full disk or a revoked grant discards it. The next install of the same pins keeps each staged file whose pin is unchanged and resumes it from its length with `Range: bytes=<offset>-`; anything else in the directory starts again. The answer's head is checked before any body is written (the transport's `SendOptions::head`): a `206` must carry exactly `Content-Range: bytes <offset>-<bytes-1>/<bytes>` and is appended; a `200` to a ranged request restarts the file from its first byte; a `206` to a request for the whole file and a `416` are refused as `validation` and discard the staging. The whole file is hashed at the end, so a resumed file that does not match its pin is refused and discarded. A resource row that is not installed reports `staged_bytes` while a partial transfer is kept, and the progress counts the staged bytes as done.

**Labels and the machine minimum.** A resource may declare a `tradeoff`, the one plain line a person chooses a model by beside another ("Finds smaller objects; slower to start"), at most 120 characters, and a `use_restriction`, one line present only when the licence restricts how the person may use their own results ("Non-commercial use only"), at most 160; an empty or multi-line label is refused by name. Neither gates anything, and no licence gate or training-data note exists. The download disclosure states the size of every file together, the URL it comes from, the install directory, the licence, the trade-off and the use restriction when there is one. A resource may declare `min_memory_bytes`, 1 GiB to 4 TiB: the least memory a machine must have to install it. For a resource a `local-runtime` capability holds, it is at least the capability's `resident_bytes` plus the held candidates' bound (1 GiB) plus the analysis cache (256 MiB, the recorded default) (`descriptor::machine_floor`), and a smaller one is refused at registration naming all three. The runtime requirements are not repeated on the resource: `module.resource.list` derives `requirements: {model, backends, precision, resident_bytes, min_memory_bytes}` from the capability that holds it and the minimum, and `fits` from this machine's memory. The machine's memory is `HostConfig::machine_memory_bytes`, which the desktop and `luxforge-json` read from the operating system (`luxforge_process::installed_memory_bytes`: `hw.memsize`, `/proc/meminfo` or `GlobalMemoryStatusEx`) and tests inject; both listings answer it as `machine: {memory_bytes}`. An install on a machine below the minimum is refused before consent is asked, with `resource-limit` ("Proof segmenter needs a machine with at least 2 GB of memory; this machine has 1 GB") and `data.requirements: [{kind: memory, id, required_bytes, machine_bytes}]`. A host that cannot read its memory checks nothing.

**Experiment flags.** A task may declare `flags`, the toggle flags ([settings and flags](settings-and-flags.md)) it is offered under, and a resource that only a flagged feature uses may declare that one `flag`. Each names a toggle the flag registry lists; an unknown flag, one that is not a toggle, or a task naming one twice is refused at registration by name. A request of a task whose declared flag is off is `not-ready` with `{kind: flag, id, state: off}`, together with any flag the module's `task_needs` names, each once. A resource's `flag` gates nothing in the host: it is listed, installed and removed as ever. Both are there so a client can hide a flagged feature and its models from the descriptor alone, before any status read: the desktop offers a task only while its flags are on and lists a resource only while its flag is on, reading off before `flags.list` first answers.

**Preparing and forgetting a model.** After moving a resource a `local-runtime` capability holds into place, and before writing `installed.json`, the install calls the inference runtime's `prepare_for(model, backends, cancel)` on the resource's own file with the capability's backends ("preparing the model" in the job's progress); a composite runtime asks only the members serving one of those backends, so a fake model is never handed to ONNX Runtime. What the runtime derives inside the version directory (`luxforge-onnx`'s fixed-shape Core ML copy and its record) is recorded in `installed.json` as `derived: [{path, bytes}]` and in the job's result, counts against the resource quota (the quota is not checked again for it, so an install is never refused for its own derived copy) and is removed with the directory. A cancel ends the install and removes the directory; any other failure leaves the resource installed and is reported in the result as `prepare_error: {code, message}`, since the first open derives what it needs again and reports its own failure. A removal of such a resource calls the runtime's `forget(sha256)` for every file it pinned, which removes `luxforge-onnx`'s Core ML compile-cache entries (`<data>/inference/coreml/<sha256>-…`), and answers how many in `compiled_removed`. The compile cache does not count against the quota: it is outside the resources directory, is pruned when a model is opened under another runtime version or OS build and is rebuilt on demand.

## Local runtime

A `local-runtime` capability `{resource, model, resident_bytes, backends, precision}` holds one declared resource loaded by the host's **inference runtime** between tasks. The runtime is the [inference port](ai-editing.md#the-inference-port-and-its-runtime)'s `InferenceRuntime`, handed to the host as `HostConfig::inference` exactly as the transport is: `None` means this host runs no local inference. The desktop and `luxforge-json` hand it ONNX Runtime from `luxforge_onnx::host_runtime`, which in developer runs composes it with the deterministic fake (`inference::fake::FakeInference`) under the backend name `fake` (`inference::CompositeInference`); tests install the fake directly. The model is opened as a tensor `session` or a `generator`, on the first of `backends` the runtime offers, at `precision`; a runtime that offers none of them is `not-ready`. The code is `capabilities/runtime.rs` (the resident set) and `capabilities/host/runtime.rs` (the methods).

**The slot.** The host owns one slot per `(module, resource)` and counts each loaded model's declared `resident_bytes` against one host-wide resident budget (`HostConfig::runtime_budget_bytes`, 16 GiB by default). A load that does not fit releases the least recently used idle models first; when a model in use leaves no room it is refused `resource-limit`, before anything is queued. A model a task is using is never released for room or idleness; one an unload, a removal or a memory signal released while a task used it is dropped when that task ends.

**Loading.** `module.runtime.load {module_id, resource_id}` answers `{module_id, resource_id, state: loaded}` at once for a resident model, joins a load already queued or running (`state: loading` with its `job_id` and `status`), and otherwise checks the module's availability, that a runtime is configured (`not-ready: no local inference runtime is configured`), that the resource is installed (`not-ready` with `data.requirements: [{kind: resource, id, state}]`) and the budget, then queues a `load` job on the module lane and answers `state: loading` with its `job_id` and `status`. The job opens the model off the owner and reads `ready` with `result: {module_id, resource_id, resident_bytes}`; a failed open fails the job and keeps nothing. A task that uses the capability opens the model the same way on its first use (`ModuleContext::session` or `ModuleContext::generator`), so an explicit load is never required, and every later task reuses the resident model. Nothing loads on `module.list`, `schema.list`, `module.status`, a catalog open or a launch. Load and unload take no mutation envelope: both are idempotent and change no catalog, settings or grant state.

**Unloading.** `module.runtime.unload {module_id, resource_id?}` releases one model, or every model the module holds when `resource_id` is absent, and cancels their queued or running loads (reason `unloaded`). It answers `{module_id, unloaded: [resource], cancelled_jobs: [job_id]}` and emits an event when it released or cancelled something. A model is also released after it has been idle for `RUNTIME_IDLE_UNLOAD` (10 minutes, `HostConfig::runtime_idle`), by the catalog owner, which wakes at the earliest idle deadline beside its held waits' and starts no thread for it; when its resource is removed; when the owner stops; and on the host's memory signal, `OwnerHandle::memory_signal()`, which releases every model at once from any thread and answers how many it released. No host calls the memory signal from an operating-system pressure notification yet. Idle, memory-signal and stop releases emit no event.

**Status.** `module.status` answers a module that declares `local-runtime` with `runtime: {held_bytes, budget_bytes, available, models: [{resource_id, capability, model, state: loaded|loading, resident_bytes, placement?, loaded_ms?, idle_ms?, in_use?}]}`, `placement` being `{backend, device, precision, partitions?}` as the runtime reports it.

## The host-planned read

A task that declares `reads: repair-input` (it must also take an asset) is given the stage it names, planned when it is requested: the owner binds the asset's current entry as one immutable evaluation with its verified source and artifacts, chooses the stage the repair layer receives (`ReadStage::Before` the repair layer's index, or the index a new one would take), and records that stage's input identity, the four components a new top correction is checked by ([Corrections](corrections.md#input-identity)). Planning is `O(layers)` and reads no pixel; an unprepared source answers `preparation-required` with the job to wait for, as any request does. On the module lane the task opens `ModuleContext::stage_reader()` and reads bounded rectangles of linear sRGB values, each answered with the rectangle clipped to the stage, the stage's size and the input identity (`StageRead {boundary, stage, rect, linear, input}`). A candidate made from the read and published by the same task carries the same identity, so `edit.accept-correction-patch` accepts it, or refuses it `conflict` once the stack below it has changed.

Every read comes from the reference renderer on the lane's own thread, whatever tile provider the host gave the owner (every AI input is a reference read), so it is byte-identical to the reference renderer's own read of the same stage on any host. A reader holds one reference session for its life, so a spatial prefix's frames are evaluated once however many rectangles it reads. Every read checks the job's cancellation first, and the reference checks it before every row. Module reads never enter the owner's tile queue, so `TILE_QUEUE_CAPACITY` stays the clients' and the desktop's; they have their own admission instead: one open reader per owner (`MODULE_READS_IN_FLIGHT`), a second refused `resource-limit` at once, and at most 4 Mi pixels a read (`MAX_MODULE_READ_PIXELS`, 48 MiB of linear values), a larger one refused `resource-limit` before anything is read. A task that declares no `reads` cannot open a reader (`validation`).

## Derived artifacts

The core owns immutable **derived artifacts** that committed recipes reference: content-addressed bytes plus a kind, optional dimensions and colour interpretation, and a SHA-256, addressed by an ID the host derives from the hash (`artifact-<sha256>`; clients treat it as opaque). A module publishes one from a task through `ModuleContext::publish_artifact` (at most 16 per task); the worker writes the bytes to `<root>/tmp/`, syncs them and renames them to `<root>/objects/<sha256>`, and the owner records the row when the job completes, before the job reads `ready`, so an artifact is committable as soon as its task reports it. Publishing the same bytes twice yields the same artifact, and a corrupt object file is replaced atomically. One artifact is at most 256 MiB. A failed or cancelled task's artifact stays an unreferenced file that the next process can collect.

The artifact root is the directory `<catalog stem>.artifacts` beside the catalog file, created on the first publish with a `manifest.json` holding the format marker and the catalog's own `catalog_id`. It moves with the catalog. The [current catalog format](versions-and-lineage.md#storage-the-catalog-format) holds `catalog_meta` (catalog ID), `artifacts` (ID, hash, bytes, kind, dimensions, colour, publishing module, time) and `artifact_refs` (entry, artifact). A layer lists the artifacts it references in its host-owned `artifacts` field, which only an effect declaring `artifacts: true` may use; the commit transaction checks every listed artifact has a row and a present file of the recorded length and inserts the entry's references with the entry itself; reference rows can never be deleted. Undo and redo add no entry and bind no bytes. A crash between the file rename and the catalog commit leaves only an unreferenced file, never a snapshot that points at an unpublished artifact.

Every history entry, branch, version, preview and restore keeps its references, because entries are never deleted and a reference is a row. `artifact.collect` removes only unreferenced artifacts that no task of the current process published, orphan files without a row, stale temporary files and the [candidate](#job-candidates) directories no job of the current process holds; nothing reachable from any entry is ever eligible. Its result counts `{rows, objects, temporary, candidates}`.

Evaluation binds artifact bytes explicitly, into the recipe. A recipe carries a table of the verified bytes its layers list beside its resolved strokes: like them it is never serialized, excluded from the recipe's equality and shared between the recipe's clones, and a recipe read out of the catalog has an empty one. Where a stack that references artifacts enters evaluation or admission — before the owner plans an action or a draft, admits a commit, renders, samples, locates, answers a query or builds a preview, analysis or sample job — the owner binds it (`EditorService::bind_artifacts`): it checks each artifact's row, root and file length and looks for its verified bytes in the prepared-artifact cache (256 MiB, least recently used, keyed by hash and file signature), and fills the table with exactly what the stack lists. A miss returns `preparation-required` with a source job that reads and hashes the artifacts on the source worker, exactly like a source miss: the refusal names the identities still to prepare among the evaluated stack's needs ([preparation](modules-and-api.md#preparation)), and the job reads exactly those; `source.prepare` covers both and `analysis.request` queues the same job. A stack whose artifacts could not all be held ready at once (256 MiB or 4096 artifacts) is a `resource-limit`. A job owns the bytes it evaluates by owning its evaluation's bound recipe, so an eviction from the cache never breaks a job already planned, and nothing else holds them. Compiling reads a layer's artifacts from its recipe's table, in the layer's order, and `CapabilityModule::compile_bound` receives them beside the payload; a listed artifact the table lacks refuses the stack by name (`source-unavailable: artifact <id> of layer <id> is not bound to this recipe`), never compiles it without the bytes. A missing root, a missing file (`is missing`) or a file of the wrong length or hash (`is corrupt`) fails render, sample and analysis with `source-unavailable` naming the artifact, and a root whose manifest names another catalog with `incompatible`; nothing is rewritten; the original source stays byte-identical. [Export](export.md) binds the same way before it evaluates, and fails the same way.

Moving the catalog together with its `.artifacts` directory keeps every reference valid. Copying only the SQLite file leaves every artifact-referencing render failing with `source-unavailable: artifact directory … is missing` while history stays readable. `artifact.collect` deletes the eligible rows in one catalog transaction and then queues a source job for their files; if that queue is full the files wait as orphans for the next collection. Opening a catalog queues this same collection once on its own, on the source worker, before any client asks; `artifact.collect` stays for a client that wants one sooner. `artifact.status` reports the root, its state (`absent`, `ready`, `missing`, `foreign`) and counts; `artifact.inspect {artifact_id}` reports one artifact's metadata, file state and how many entries reference it. Settings, grants and secrets are not copied with a catalog.

## Job candidates

A task that takes an asset may also publish **candidates**: disposable results a client reads and either accepts as a durable artifact or releases, such as the patches a fill generates for the person to choose between ([AI editing](ai-editing.md#candidates-accept-and-the-frozen-patch), [Corrections](corrections.md#candidates)). A candidate is never an artifact and never JSON pixels: its bytes live as files under `<artifact root>/tmp/candidates/<job_id>/`, and only its description reaches `job.read`. The code is `artifacts/candidates.rs` (the store), `api/owner/candidates.rs` (the two methods) and `modules/candidate_proof.rs` (the developer producer).

**Publication.** On its worker a task calls `ModuleContext::reserve_candidate {width, height, preview_width, preview_height}` and then publishes the reservation, or `ModuleContext::publish_candidate` for both at once, with the patch's rectangle `[x, y, width, height]` in the content pixels of the asset, its RGB as linear sRGB `f32` or 8-bit sRGB codes, one coverage `0..=1` a pixel, an 8-bit sRGB RGB preview of at most 1,024 pixels a side, a label of 1 to 32 characters and string and number provenance fields. The reservation admits the candidate before anything is converted or written; the publication checks the rectangle against the asset's content dimensions, every value (finite and within the half-float range once linear) and coverage, the preview's length, the label and the provenance (at most 2 KiB with the host's `module` and `task`, which a producer cannot set), converts the patch on the worker to the stored form, `width × height` RGBA IEEE half floats, little-endian, RGB linear sRGB (D65) and A the coverage, not premultiplied (`rgba16f-le`), hashes it and writes it and its preview. A refused or abandoned publication returns its reservation and leaves no file. A job cancelled meanwhile publishes nothing. The task job records what its candidates were generated against when it is queued: the asset, its revision and its content dimensions. A task that takes no asset publishes none.

**Bounds.** A job publishes at most **4** candidates, numbered `0..=3` and never reused, of at most **64 MiB** each, patch and preview together; every job's reserved and live candidates hold at most **1 GiB** together. Past that bound a reservation releases the oldest finished job's live candidates first, in number order and only as many as it needs (reason `budget`); a running job's candidates and one an accept holds are never released for room, and when the room cannot be made nothing is released and the reservation is refused `resource-limit`, before the producer allocates. The admission is a short critical section over the store's table; nothing is held in memory but the table.

**Reading.** `job.read` answers a task job with `candidates: [{candidate, state: live | accepted | released, released?: budget | released | cancelled | closed, width, height, bytes, rect, preview: {width, height}, asset_id, revision, label, provenance, input?}]`, `input` being the input identity a new top correction of the photograph had when the task was queued ([Corrections](corrections.md#input-identity)), every candidate it published in number order, and a candidate change answers a held `job.wait`. `job.read-candidate {job_id, candidate, part: preview | patch, offset?, length?}` answers `{job_id, candidate, part, width, height, format, offset, length, total, data}`, `data` being base64 of at most 768 KiB; the chunk is read on the index lane's query thread, never on the catalog owner, while a read pin keeps the files. A job that is not a task, or a number it never published, is `validation`; a candidate accepted or released, before or while the chunk is read, is `conflict` with `data: {state, released}`; a file missing or of the wrong length is `source-unavailable`.

**Ownership and release.** A candidate belongs to its task job, which belongs to the catalog: any client reads, releases or accepts it, and a client disconnecting releases nothing. `job.release-candidates {job_id, candidates?, mutation: request}` releases the named live candidates or every one, answering `{job_id, outcome, released, candidates, deduplicated}`; a candidate already accepted or released is left as it is, a number never published is `validation` and one an accept holds `conflict`, releasing nothing; a retry is answered from the owner's request table and a release that released something is announced. `job.cancel` of a task job releases its live candidates (`cancelled`), whether the job is running or finished; a task that ends cancelled releases them too, while a task that fails keeps those it published. A job the job table forgets takes its candidates with it. Every release deletes the candidate's files, once no chunk read holds them; closing the catalog deletes every candidate's files, and the collection that opening a catalog queues sweeps whatever a process that ended without closing left.

**Accepting.** The accept is a seam a candidate-accepting action (`ActionDescriptor::accepts_candidate`, declaring `job_id` and `candidate`) drives through the owner; `edit.accept-correction-patch` is the one ([Corrections](corrections.md#candidates)): the owner pins a live candidate (`Candidates::pin`), and while it is pinned no budget release takes it, an explicit release of it is a `conflict` and a cancel waits for the accept to settle. On a worker the pin publishes the stored patch through the catalog's artifact writer (`CandidatePin::publish`): the file is read whole, its length and hash checked against what was stored (`source-unavailable` when they differ), and it is published as an immutable `repair-patch` artifact with its dimensions and colour `linear-srgb`, live for the process. The owner runs it as an `artifacts` source job while the call is parked, records the row (`EditorService::register_artifact`) and commits one ordinary entry that references it through the ordinary action path, the action reading the published candidate through `StageQuestions::accepting`, then settles the pin (`CandidatePin::accepted`): the candidate is `accepted`, its files go and its bytes leave the budget. A commit that is refused, or a request cancelled before it, drops the pin instead: the candidate stays live, or is released if a cancel waited for the accept, and the published artifact is only an unreferenced object that `artifact.collect` removes once no process holds it live. The revision and input checks and the operation the commit appends are the accepting action's.

**Developer producer.** `luxforge.candidates` (Candidates proof, developer runs only) declares one task, `generate-proof-patches {asset_id, count 1..8, width, height 1..4096, x, y, seed, colour: linear | srgb8}`, that reserves and publishes `count` deterministic patches of the photograph, labelled `Patch` with the seed in their provenance, each with a preview of at most 64 pixels a side, and answers `{candidates: [n, …]}`; a fifth candidate ends the job `resource-limit` with four live, and a candidate past 64 MiB is refused before it is made. It is what the remaining frozen-patch work and AI editing's workflow tests drive instead of a model.

## Proof module

`luxforge.capabilities` (title Capabilities proof) is a developer-only test fixture, registered by the desktop and `luxforge-json` only with `--developer --proof-endpoint URL` and by tests directly. It declares a non-secret `strength` number; a profile adapter `proof-echo` (bearer auth, `sample-grid-8`) whose profiles hold an `endpoint` and a secret `api-key`; the capabilities `echo` (remote-image-request) and `palette` (download-artifact); one pinned resource `proof-palette` served by the proof endpoint; the task `generate-proof-tint` (asset, profile, uses `echo` and `palette`) that reads the installed palette through its context, posts the sample grid to the endpoint, combines the answer with the palette and `strength`, and publishes a 12-byte tint artifact; and the actions `apply-proof-tint {artifact}` (commits the one layer, then updates it in place) and `reset-proof-tint` (returns that layer to a neutral payload with no artifacts, or is a no-op) over the colour-stage effect `luxforge.capabilities.tint`, whose `compile_bound` multiplies linear channels by the artifact's three gains. Its controls are the task button and a Reset tint action; its settings are not controls. `ProofEndpoint`, its loopback fake provider with knobs for delays, failures and a wrong palette, is started by the test or smoke harness, never by the editor. It lives in `luxforge-testbase` on the workspace's one loopback test server, so the shipped core carries no test server, and takes the proof module's paths, palette and grid size from its caller (`luxforge-testkit`'s `proof_protocol`, or the core's own test harness); the core, desktop and `luxforge-json` tests take it as a dev-dependency and `xtask` as a dependency.

`luxforge.models` (title Models proof, `modules/models_proof.rs`) is the model manager's developer-only fixture, registered beside it under the same `--developer --proof-endpoint URL`. It declares one model resource, `proof-segmenter` (Proof segmenter, version 1), of two files the endpoint serves: its own, the 6000-byte encoder at `/proof-model/encoder.bin`, and `decoder`, 3000 bytes at `/proof-model/decoder.bin`, each a fixed pattern behind the magic `LFMDL001` that `validate_resource` checks; the trade-off "Small and quick to load; finds nothing, as a proof", the use restriction "For testing Luxforge only" and a 2 GiB minimum; the capability `model` (download-artifact) that installs it and `segment` (local-runtime, a `session` of 64 MiB resident on `fake` at fp32) that holds it. It has no task, effect or control. The endpoint answers its files whole, as a `206` with `Content-Range` to a range request, or `416` past the end, and `ProofEndpoint::cut_next_model(n)` makes the next model answer promise the whole file and close after `n` bytes, which is how the resume is driven over loopback.

## Desktop

Any module that declares settings, resources or tasks gets a capability block at the top of its tools-panel section, generated from its descriptor and drawn above the section's own controls: one row per resource with its version, size and state (with progress while it installs) and the one action that state allows, Download, Cancel or Remove; a settings form of the module-level fields, each drawn as the tools panel draws a control of its kind (a number field, a toggle, a segmented choice, a text field that commits on Enter); the permission counts `module.status` reports, with a Revoke all that lists the module's grants through `module.permission.list` and withdraws each live one through `module.permission.revoke`; and one status line for the last failure, a `not-ready` answer's message or settings the module cannot use. Every write carries the module's settings revision; a conflict reads the settings again and says so on the status line. Provider profiles, secrets and a single grant are not drawn: they are set through `module.profile.*`, `module.settings.set-secret` and `module.permission.*`, which is how every client sets them. A task control sends the open photo and its first ready profile, shows progress with Cancel and, on success, Apply, which commits the task's artifact through the ordinary edit path; another profile is chosen by sending `task.<id>` with its `profile_id`. A `consent-required` answer to anything the desktop started opens a consent notice over the canvas, not a modal: "Allow <module> to download a resource / send photo data?" with the disclosure and "You declined this before." when it was; Allow grants exactly that scope with the desktop's authority and retries once, and Don't allow records a denial. While a job the desktop tracks is in flight, an authoritative `job.wait` subscription follows its first, changed and terminal records off the update loop, with no polling interval. The stream sends a message only when a tracked record is news: a job's first read, a record that differs from the last one sent (progress included), a job's end or a failed read. An unchanged record sends nothing, so a held wait costs no message, no update and no view rebuild, and a job that ended or failed to read is followed no more. A first read that answers the record the round trip which started the job already tracked runs no hooks and no derive while nothing else is going on; every other message takes the full update. Capability events from other clients refresh the block without rendering. `state.json` carries a redacted `capabilities` summary per module: the settings as `module.settings.read` answers them, the jobs, the open consent and the status line.

**Settings › Models.** When a registered module holds a model (a resource a `local-runtime` capability names), Settings gains a **Models** tab after Appearance, and the palette a Settings · Models entry; without one the tab is not listed. Opening it reads `module.status` for each such module. Under a short introduction, one line names this machine's memory against each model's minimum ("This machine has 36 GB of memory. Proof segmenter needs 2 GB."), adding "more than it has" for a model it cannot install. Then it lists every known model with its title, version, size and file count, its state (Not installed, Installing with its percentage, then the step past the download such as "preparing the model", Installed, Loading, Loaded or Failed with the reason, adding "X of Y downloaded, resumes on the next download" while a partial transfer is kept), its trade-off, its use restriction and its requirement ("Needs 2 GB of memory · 64.0 MB while loaded · fake · fp32"), with Remove for an installed model or a kept partial transfer; then the loaded models, each with its size, placement and precision and Unload now, under a line naming what they hold against the resident budget. Default tiers are not shown until a feature offers one. The tab has no Download: a model is installed from the tool that needs it or by `module.resource.install`. Remove sends `module.resource.remove` and Unload now `module.runtime.unload {module_id, resource_id}` through the capability driver, which reads `module.status` again when each ends; each row's menu (**⋯**) copies the request its button sends as JSON. The widgets hold no state: the rows are derived from the modules' status in `state/models.rs`. `state.json` records the tab under `settings.models`: each row with its `remove_request`, each loaded model with its `unload_request`, the resident and machine lines, `tiers: []` and each module's `status`.

## Evidence

Each capability behaviour is tested once per layer. Unit tests cover descriptor acceptance and every named rejection, the shared JSON document (its marker, refusals, bound, write-on-change and concurrent writers), settings revision, conflict, deduplication and format refusal, the in-memory secret store, grant scopes and bounds, endpoint classes and the proof module's palette, answer and tint. `capabilities/lifecycle_tests.rs` owns every shared behaviour at the owner's JSON methods, on a fixture module: inert discovery and reopen, grant authority, scope validation, denial, revocation of queued and running jobs and on endpoint, profile and reset changes, cancellation mid-transfer, task requirements, status, verified installs under every failure with nothing installed afterwards and the staging kept only for an interrupted transfer, which a cancel keeps and a revoked grant discards, the quota, removal and retries. The core's capability tests send through an in-memory transport that answers in process, holds an answer at a gate and counts every request, and drive the owner through one shared harness in `capabilities/testing.rs`. `luxforge-net`'s tests cover the transport's address classes, single resolution, redirects, request and response bounds, refused framing, deadlines, cancellation, TLS roots and truncation against loopback servers, and the native Keychain store. `capabilities/proof_tests.rs` keeps one journey of the proof module end to end through the owner's JSON methods, including a pixel-exact render of the applied tint, reopen and the one sentinel-secret scan of every answer, refused secret request, file and endpoint record, and what only a sending, publishing task shows: per-asset consent, a revoked send, a retried task, a wrong key and a task that fails after publishing. Derived artifacts are tested on the proof module's tint through publish, commit, reopen, branches, versions, restore, collection, missing and corrupt bytes and crash points. Candidates are tested at the store (`artifacts/candidates_tests.rs`: the stored form against the half crate and an independent sRGB decode, every publication refusal, the per-job, per-candidate and across-job bounds with the oldest finished job released first and a pinned candidate never, releases, cancels, read and accept pins, a cancel during publication, forgetting, sweeping and closing, and the accept seam publishing a pinned candidate for one ordinary commit by a test-only consumer, a refused commit leaving only an unreferenced artifact that a collection removes after reopening, and a corrupt candidate refused) and through the owner's JSON methods with the developer producer (`capabilities/candidate_tests.rs`: listing, chunked reads by two clients, releases and retries, a disconnect, cancels of a running and of a finished job, the bounds a producer meets, a held `job.wait`, discovery, closing and the sweep at the next open). The inference port is tested against its fake (`inference/tests.rs`: object safety, tensors and their bounds, backend choice and open refusals, a session's determinism and precision, a generator's determinism, coverage, conditioning and provenance, distinct fills for distinct seeds, cancellation at a step boundary and the fail and slow knobs). `capabilities/runtime_tests.rs` drives `local-runtime` through the owner's JSON methods: nothing loads on a listing, a status or a launch; a load and a task's first use open once and tasks reuse the model; an unload, its event, a removal, the idle interval and the memory signal release it; the budget evicts an idle model and refuses one beside a model in use; an unload cancels a queued load; and the refusals without a runtime, without the resource and after a failed open. `capabilities/read_tests.rs` drives the host-planned read under a tile provider that refuses every read: the values against an independently planned reference region read of the same stage, the identity a candidate carries, an accept and a stale candidate's `conflict`, a cancelled read, the one-reader admission, the pixel bound and a task that declares no read.

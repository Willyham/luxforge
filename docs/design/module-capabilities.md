# Module settings, permissions and managed resources

Status: **implemented and verified on the M4 Mac.** The contract was frozen on 2026-09-23 under the owner's delegation ("make sensible decisions, don't block on me"); its decisions are recorded in [product decisions](../decisions.md#module-capabilities) and can be revisited by the owner. The code lives in `crates/luxforge-core/src/capabilities/` (settings, the secret store's contract, grants, consent, endpoint parsing, the transport's contract, the worker, resources, tasks), `crates/luxforge-net` (the transport and the macOS Keychain store, which the desktop and `luxforge-json` give the host through `HostConfig`), `crates/luxforge-core/src/artifacts/` and `editor/artifact_store.rs` (derived artifacts), `modules/capabilities_proof.rs` (the proof module and its endpoint) and, in the desktop, `app/capabilities.rs`, `state/capabilities.rs` and `view/capabilities.rs`. This is the shared host capability contract for linked modules. It extends the [current module contract](modules-and-api.md); it does not select a binary plugin format or introduce accounts, cloud sync or a marketplace. The [corrections design](corrections.md) is the first intended consumer. Every operation available in the desktop is a discoverable method of the shared service.

## Outcome and boundary

A module declares settings, provider adapters, capabilities, resources and worker tasks. Only the host stores settings or secrets, downloads resources, contacts endpoints, schedules work or publishes persistent artifacts; a module receives those through a worker-side `ModuleContext` that enforces the grant it runs under. Descriptors stay plain data and registration does no I/O. A module loads nothing ahead of a request: a task reads the installed resources it uses through its own context, on a worker, and nothing is loaded as a side effect of `module.list`, catalog reopen, recipe compilation or panel construction. Listing, reopening and schema discovery cause no network, keychain or model activity.

These capabilities apply to **trusted linked modules**. A declaration serves consent, least privilege and auditing; it is not a sandbox for code linked into the editor. External executable loading stays the separate measured project on the [roadmap](../plan.md) and must add a process/ABI trust boundary before untrusted code is supported.

## Decisions

| Question | Decision |
| --- | --- |
| Setting scopes | Two, both user-level and outside every catalog: module settings and named provider profiles of a module. No per-catalog or per-photo settings. Settings never create history entries and have no image effect by themselves |
| Consent unit | **Per asset** for sending image data: a grant names the module, capability, provider profile, adapter, endpoint origin, data class and asset. Grants are not remembered for later photos. A resource download is granted per resource version and origin |
| Who may grant | Only a client with **permission authority**: the desktop's own client (after the person presses Allow) or `luxforge-json --permission-authority` (an explicit local headless setup step). Loopback live-session clients and plain `luxforge-json` never can. Anyone may deny or revoke, since both reduce privilege |
| Revocation | Stops new work, cancels queued and running jobs that depend on the grant (`cancelled`, reason `permission revoked`) and never touches recipes, history or accepted artifacts. Changing a profile's endpoint, removing a profile or resetting a module revokes the grants scoped to the old value (a profile's adapter cannot change) |
| Secret store failure | macOS Keychain first. A locked, missing or unsupported store fails with `not-ready` naming the store; there is no plaintext fallback. Windows Credential Manager and Linux Secret Service report `not-ready: secure storage is not implemented on this platform` until natively verified |
| Endpoints | HTTPS for anything remote, with public addresses only; plain HTTP only to loopback (`127.0.0.0/8`, `::1`, `localhost` resolving to loopback), which is a separately labelled `loopback` class. No proxies, no `file:` or other schemes, no userinfo in URLs |
| Remote provider adapters in the first release | None besides the developer proof adapter. Real adapters arrive with Corrections, each reviewed |
| `managed-storage` and `local-runtime` capabilities | Not implemented; registration rejects them by name until their first consumer defines them |
| Activation | Deferred until a module needs `local-runtime`. Loading a module's state ahead of its tasks, on a cancellable worker with an explicit activate and deactivate, has one real consumer: preloading a configured local model in the [corrections design](corrections.md). It returns with that capability, defined by that consumer; until then there is no `module.activate`, `module.deactivate`, activation job or activation requirement, and a task reads its installed resources itself |
| Catalog format | Format 8 holds the catalog's identity and the artifact tables beside the preset library and the [mask](masking.md) table and stroke store; two branches each claimed format 6 for one of those halves, so a catalog of either is refused by name and kept intact (current shapes only) |
| Settings format | One JSON file per user with `format: 1`; any other marker is refused and the file is retained unmodified |

## Configuration contract

`ModuleDescriptor` gains optional, plain-data fields. Every one defaults to empty, so existing descriptors are unchanged.

```text
settings:   { schema: u32 ≥ 1, fields: [Setting], profiles?: { label, max: 1..16, adapters: [Adapter], fields: [Setting] } }
Setting:    { …Parameter, label }
kind:       boolean | integer | number | enum | string | endpoint {classes: [remote|loopback]}
            | secret {max_length ≤ 4096}
Adapter:    { id, title, auth: none|bearer, data: [data class], max_request_bytes, max_response_bytes,
              timeout_ms, retention?, cost: free|paid|unknown }
capabilities: [ { id, kind: remote-image-request {adapter, data}
              | download-artifact {resource}, purpose } ]
resources:  [ { id, title, version, url, bytes, sha256, format, license, provenance, redirect_origins? } ]
tasks:      [ { id, title, notes, asset: bool, profile: bool, uses: [capability id],
              parameters: [Parameter], apply?: {action, parameter} } ]
```

A setting is declared in the module parameter vocabulary: it is a `Parameter` exactly as an action declares one ([module contract](modules-and-api.md)), serialized the same flat way with the same fields (`name`, `kind` and the kind's own fields, `required`, `default`, `unit`, `step`, `precision`, the numeric hints and `notes`), with `label` beside them. Its `name` is the setting's identity, `notes` is the help a settings view shows under it, and `schema.list` emits it through the same serialization as every method's `parameters`. A setting takes the kinds a settings store holds and a settings view edits — `boolean`, `integer`, `number`, `enum`, `string`, `endpoint` and `secret` — and registration refuses any other kind by name. `endpoint` and `secret` are parameter kinds that only a setting declares: an action, query or task parameter of either kind is refused at registration, so a destination is never part of a request, a recipe or a job, and the one request that carries a secret stays `module.settings.set-secret`. An `endpoint` is a profile field only: the host sends only to a profile's endpoint, so a module-level one would do nothing and is refused. An `endpoint` value is a URL of at most 4096 bytes that the transport policy accepts as one of its classes; no plain value of a `secret` is ever valid. Identities follow the existing rules: setting, adapter, capability, resource and task IDs are hyphenated lowercase names; a task ID is unique across the registry because it generates the method `task.<id>`. Registration rejects, with a `validation` error naming the field: a malformed or duplicate ID; an unknown kind; any declaration the parameter vocabulary refuses for a parameter (an empty range, empty or duplicate enum options, a `string` `max_length` outside 1..=256, a `secret` `max_length` outside 1..=4096, an `endpoint` with no class or a class twice, an unsound hint, a default outside its kind; a `secret` never has a default and an `endpoint` default is refused); a capability naming an undeclared adapter or resource; a module-level `endpoint` setting; a profile block without an `endpoint` field when an adapter is declared; a resource whose `url` is not HTTPS unless it is loopback, whose `sha256` is not 64 lowercase hex, whose `bytes` is 0 or above 16 GiB, or whose `redirect_origins` are not HTTPS origins; a task naming an undeclared capability or an `apply` action or parameter that does not exist or is not of kind `artifact`; `managed-storage` or `local-runtime`. It also refuses a profile block without adapters; a `bearer` adapter whose profile fields do not declare exactly one secret; adapter byte limits outside 1 byte..256 MiB or a timeout outside 1..600000 ms; an empty title, format, license, provenance or retention note; a resource version that is not a plain directory name; a task that uses a capability twice; a task that takes a profile without a profile block, and a `remote-image-request` task that does not take both an asset and a profile. A `remote-image-request` data class must be one of its adapter's, and `redirect_origins` are exact serialized origins (`https://host[:port]`, default port omitted). Profile `max` is 1..16 and module-level plus profile fields are at most 32 each.

`module.list` and `schema.list` return exactly these declarations. They contain no setting values and never a secret: a secret field declares only its presence.

A module that declares tasks, resources or an effect with `artifacts: true` implements the capability hooks, `CapabilityModule` beside its `ToolModule` ([module trait](modules-and-api.md#module-trait)); registration refuses one that declares any of them and provides no hooks, naming the declaration. Settings, profiles and capabilities alone are the host's and need no module code.

Two descriptor additions support the rest of the contract. A parameter kind `artifact` carries one artifact ID published in the catalog; the host checks its syntax generically and the commit checks that it exists. A control kind `task {task, label}` is a button that runs the task through the desktop's consent and progress flow and, when the task declares `apply`, offers Apply with the result. An effect may declare `artifacts: true`; only a layer of such an effect may reference artifacts.

### Settings store

Non-secret values live in `<config>/modules/settings.json`, outside every catalog: `{format: 1, modules: {<module_id>: {schema, revision, values, profiles: [{id, adapter, label, values}]}}}`. Profiles have host-generated IDs (`profile-<uuid>`). Each module has its own monotonic `revision`. The settings file, the grants file and each installed resource's `installed.json` are one kind of store: a JSON document of one shape under its own `format` marker and size bound, read afresh on every call. A change takes an OS advisory lock beside the file, re-reads it, applies the change, and writes a temporary file, syncs it, renames it over the old one and syncs the directory; a failure leaves the previous file, and a change that changes nothing writes nothing. The derived-artifact store publishes its objects and manifest through the same durable write. The settings file is at most 1 MiB. A `format` other than 1, or unparseable JSON, fails every settings method with `incompatible` and the file is never rewritten. A module whose stored `schema` differs from its descriptor reads `state: incompatible`, keeps its stored values untouched and refuses writes until `module.settings.reset` clears that module's entry explicitly. A stored value its field's declaration does not accept reads `valid: false` with the reason and is kept until it is written or reset; nothing rewrites or drops it. Entries for modules that are not registered are kept verbatim.

Every settings mutation takes the edit mutation envelope `mutation: {expected_revision, request_id, actor}`, where the revision is the module's settings revision. A stale revision is a `conflict`. The settings file keeps no request log: a settings write sets values rather than changing them, so its retry is answered from the catalog owner's request table like every revision-less mutation ([host dispatch](modules-and-api.md#host-dispatch)) with the first answer marked `deduplicated: true`, and the same `request_id` with a different input is a `conflict`. The table lives for the owner's lifetime and holds the most recent requests; a retry after a restart, or after its answer left the table, conflicts on the revision it was made against, and the client reads the settings its write left. A write that changes nothing is `outcome: no-op` and keeps the revision. Committed settings writes emit an event whose method is the method name; a retry emits none. Every write answers `{module_id, outcome, revision, deduplicated, profile_id?, profile?, changed, revoked?}` plus `settings`, a read after the write; a retry gets that first answer again. A `set-secret` request is keyed with its value redacted, so a retry is matched by the setting alone and no hash of a secret is held; writing a secret is idempotent.

`module.settings.read {module_id}` returns `{module_id, schema, revision, state, fields: {<id>: {value, default, source: user|default, valid, error?}}, profiles: [{id, adapter, label, fields, status}]}`. A secret field reports `{secret_present, valid, error?}` instead of a value, where `secret_present` is `null` when the store cannot answer, so a locked keychain shows on that field rather than failing the read. A profile's `status` is `ready`, `incomplete` (a required field is missing or invalid), `missing-credentials` (the adapter authenticates and the secret is absent) or `incompatible`. The host can report this without loading anything.

`module.settings.set {module_id, profile_id?, values: {<id>: value | null}, mutation}` validates each named field with the parameter vocabulary's own check of its declared parameter, exactly as an action's parameter is checked, and commits them together; `null` returns the field to its default. A secret field is refused here. An `endpoint` value is parsed and classified by the transport policy. `module.settings.set-secret {module_id, profile_id?, setting, value, mutation}` stores the value through the secret store and returns the read result; the value is never echoed. `module.settings.clear-secret` removes only that secret. `module.profile.create {module_id, adapter, label, mutation}` returns the new profile; `module.profile.remove {module_id, profile_id, mutation}` removes its values, clears its secrets and revokes its grants. `module.settings.reset {module_id, mutation}` deletes the module's values and profiles, clears their secrets and revokes their remote grants (a download grant names a pinned resource, not a setting, and survives); it keeps the module's schema and revision, so the revision never goes backwards and a retry the request table no longer holds conflicts rather than clearing values written since, and it is the explicit way out of an incompatible schema or an entry that is not in the current shape. Removing a profile or resetting a module that declares secrets answers `not-ready` while the secret store is unavailable, because the secrets could not be cleared.

### Secrets and redaction

`SecretStore` is a host trait with `set`, `clear`, `present` and `read`, defined in the core; the macOS store is `luxforge-net`'s `KeychainSecretStore`, which the desktop and `luxforge-json` give the host. It keeps generic passwords under the service `app.luxforge.module-secret` and the account `<module_id>/<profile_id or ->/<setting_id>`; `present` queries attributes only, so it never asks for the secret's data. A locked or unavailable keychain maps to `not-ready`. `read` is called only on the module worker, inside a task of the module that declares the secret; the value is a `SecretValue` that is not `Serialize`, whose `Debug` prints `<redacted>` and whose buffer is zeroed on drop. The OS may show its own prompt when a rebuilt executable reads an item an earlier build stored; that prompt belongs to the OS, and a set or clear that waits on it holds the owner for its duration. Evidence runs and tests use an in-memory store and never touch the login keychain; the native journey is an opt-in ignored test in `luxforge-net`.

Redaction is structural: no descriptor, read result, event, error, job record, status, log or evidence file can carry a secret, because nothing but `set-secret` requests and the worker's `SecretValue` ever hold one. `redact_params` replaces the `value` of a `module.settings.set-secret` request's parameters with `"<redacted>"`; the desktop's request log, evidence capture and Copy as JSON record a request's method and its parameters through it, never its live-session token. Tests set a sentinel secret and scan every response, event, log and evidence file for it.

### Provider adapters

A profile names one declared adapter: a typed contract, not a URL template. The adapter declares its data classes, request and response size limits, timeout, authentication, retention note and cost. The host builds the request body only from the task's declared data, sends it through the transport under the grant and returns the response bytes to the module; a module never supplies a URL. The first data class is `sample-grid-8`: an 8 × 8 grid of rendered sRGB samples of the asset's current entry at the centres of an 8 × 8 grid over its output stage, sent as fixed-width JSON of exactly 959 bytes (`{"data_class":"sample-grid-8","width":8,"height":8,"samples":[[r,g,b],…]}`, each channel padded to three characters), which is the size the disclosure states. The owner binds the entry at request time and the module lane takes the 64 point samples, so a spatial layer's per-sample tile never runs on the owner; no frame is rendered. Corrections adds its crop and mask classes with its own design. No provider receives an original path, EXIF or extra context.

## Capability and consent contract

Two capabilities are implemented. `download-artifact` installs a declared resource from its pinned URL. `remote-image-request` sends a declared data class of one asset to a profile's endpoint through its adapter. Each is gated by a **grant** whose scope is exact:

| Capability | Grant scope |
| --- | --- |
| `download-artifact` | `{module_id, capability, resource, version, origin}` |
| `remote-image-request` | `{module_id, capability, profile_id, adapter, origin, data, asset_id}` |

A module that reads a user-chosen file may add a `read-user-file` capability back later, consented per canonical path.

A gated operation without a matching grant fails before any work starts with `consent-required` and `data.consent: {module_id, capability, scope, disclosure, denied}`. The disclosure names the module and purpose, the destination (an origin), the data to be read or sent and its size, the storage location and expected bytes for a download, the adapter's retention note and whether it may cost money; `denied` is true when a denial is recorded for that scope. The desktop shows this as a consent notice with Allow and Don't allow; a headless client receives the same failure.

Every permission and resource change takes the `{request_id, actor}` mutation envelope: none of them changes anything with a revision, so a retry is answered from the owner's request table with the first answer marked `deduplicated: true`, and the same `request_id` with other input is a `conflict` ([host dispatch](modules-and-api.md#host-dispatch)). `module.permission.grant {module_id, capability, scope, mutation}` requires permission authority and otherwise fails with `forbidden`; the scope must be one the module can use. It records `{grant_id, module_id, capability, kind, scope, actor, request_id, created_ms}` from the envelope and clears a matching denial; a grant of a scope that already has a live one returns that grant as a no-op. A denial does not revoke a live grant. `module.permission.deny {module_id, capability, scope, mutation}` records a denial with the envelope's actor. `module.permission.revoke {grant_id, mutation, reason?}` marks the grant revoked with a reason and cancels dependent jobs. `module.permission.list {module_id?}` returns grants, revocations and denials; `module.status` carries only their counts. Grants live in `<config>/modules/grants.json`, a document of the same store as settings with its own `format: 1` marker and bounds (at most 1024 records and 2 MiB); nothing is copied with a catalog. A record past the bound first prunes the oldest revoked grant or denial. When every record is a live grant, the oldest live `remote-image-request` grant is evicted instead of the new record being refused, so the next request for that scope fails with `consent-required` and is asked for again; a `download-artifact` grant is never evicted, so a file holding only live download grants refuses a new record with `resource-limit`. No grant follows from a retry, a saved recipe, a configured key or same-user API access.

### Transport

The host transport is the only network path. It parses a URL, requires `https` for the `remote` class and allows `http` only for the `loopback` class, rejects userinfo, fragments and every other scheme, resolves the host once, requires every resolved address to belong to the endpoint's class (`remote` refuses loopback, private, link-local, shared, unique-local, multicast, unspecified, documentation and IPv4-mapped forms of these) and connects to the checked address, so a second resolution cannot rebind it. A host must be ASCII: an internationalized name is refused as an invalid URL (`invalid international domain name`), while its punycode form (`xn--…`) is accepted and resolved as written, because URL parsing carries no Unicode data. TLS uses rustls with the ring provider and the operating system's certificate verifier (native roots with webpki on Linux); tests inject their own roots. Redirects are refused unless the request allows them; an allowed redirect must stay HTTPS, target an origin in the declared list and passes the same checks, and it drops the `Authorization` header when the origin changes. A response larger than its limit is refused from its length header or cut off at the piece of at most 16 KiB that would cross it; a connect deadline, an idle deadline between reads and writes and a whole-request deadline apply, and cancelling the request's job shuts its socket down, so a blocked read, write or TLS handshake returns at once (a lookup or a connect attempt is bounded by its timeout instead). Only 301, 302, 303, 307 and 308 redirect, always as a `GET` without a body; other `3xx` answers are returned as data, and a same-origin redirect must be listed too. A request refuses a body on `GET`, more than 32 caller headers, a head over 16 KiB, control characters and every connection-level or cookie header; a response refuses compression, any transfer coding but `chunked` (and any at all on HTTP/1.0), a length that is not one plain number or disagrees with another, both a coding and a length, `101`, a status of 600 or more, a head over 64 KiB or 100 fields, and a TLS body that ends without the server's close signal. Every failure is structured: `validation` for a refused URL, address or redirect, `resource-limit` for size, `read-error` for network and TLS failures and timeouts, `cancelled` for a cancel.

The core defines the transport as a trait, `capabilities::transport::Transport`, that sends one checked request under the caller's bounds and job, and takes it in `HostConfig`; resource installs and `ModuleContext::send` call it, and the core links no network stack. The implementation is `HttpTransport` in `crates/luxforge-net`, which the desktop and `luxforge-json` build (it builds its TLS configuration on its first request, never at start). The core's capability tests send through an in-memory transport instead, and the TLS, protocol and address tests run against `HttpTransport` in `luxforge-net`.

The HTTP/1.1 is [`ureq`](https://crates.io/crates/ureq)'s own agent, 3.4.2 with no features, one per request, built with `Agent::with_parts` from the transport's own parts (`luxforge-net`'s `transport/agent.rs`): a resolver that resolves the endpoint's host once through `Resolve` and answers only if every address passes `address_allowed` for the endpoint's class (an IP literal without a lookup); a connector that connects through `Connect` to those addresses only, checks each again, and hands the job's `JobControl` a clone of the socket, which the job's cancel shuts down; and TLS on the transport's own rustls configuration. The agent has no proxy, no pool and no redirect following, returns every status as data and sends `Accept-Encoding: identity`, so the transport keeps its own redirect check and its loop over at most three redirects. It streams the final body through the agent's reader in pieces of at most 16 KiB, reporting progress after each; the reader stops one byte past the limit, so a body of exactly the limit is whole. The request head is the one the transport writes (`Host`, `User-Agent`, `Accept-Encoding: identity`, `Connection: close`, the caller's headers, and a `POST`'s `Content-Length`), with no `Accept` added.

Two parts of `ureq` are not used. It does not export its `TcpTransport`, so the connector supplies its own socket transport. Its `RustlsConnector` would accept a truncated body: `ureq` ends a close-delimited body at an `UnexpectedEof`, which is how rustls reports a connection that closed without the server's close signal, so the transport's own TLS transport reports that as an error. For the same reason a cancelled close-delimited plain body reads as complete, so the transport checks the job's cancel before it reports a body whole, and a cancel overrides any other outcome. The agent's own timeouts are per phase and turn a zero remaining time into one second, so the socket applies the transport's deadlines itself: before every read and write it checks the job's cancel and the whole-request deadline and waits at most the idle timeout or what remains of the request, whichever is shorter; a connection reset is a failure, never the end of a body. A cancel of a request stalled in its TLS handshake, TLS or plain response head, TLS or plain body or close-delimited body returns within 0.4 ms (20 samples, 74 to 352 µs, test build on the M4 at load 9 to 11), where the hand-written client this replaced waited for its 100 ms read slice.

The transport keeps the stricter framing it can judge from a parsed head: the compression, transfer-coding and length checks above, the 100-field cap (`ureq-proto` holds 128) and the refusal of `101` and statuses over 599. Three bounds of the hand-written client went with it, as `ureq-proto` reads them: a bare line feed ends a line (RFC 9112 lets a recipient accept one, and with one request per connection nothing can be smuggled behind it); interim responses are each held to the 64 KiB head limit, not to one budget together, and trailers are read and discarded line by line, each line within the connection's 128 KiB input buffer, so their total is bounded by the idle and whole-request deadlines, not by size; and a chunked body whose last chunk arrives before the connection closes is whole without its closing blank line. `ureq` and `ureq-proto` trace request heads, `Authorization` included, to the `log` facade at trace level; Luxforge installs no logger, and one added later must leave them out. `cargo xtask check-repository` refuses `ureq_proto::` and `httparse::` outside `luxforge-net` and a dependency on `ureq` or `ureq-proto` outside it, so no second HTTP framing appears, and refuses a TLS, HTTP or Keychain crate in `luxforge-core`'s manifest. The executable and package cost is in [performance](../specs/performance.md#transport-on-ureqs-agent).

## Lifecycle, jobs and resources

Methods: `module.status {module_id}`, `module.resource.list {module_id}`, `module.resource.install {module_id, resource_id, mutation, source?}`, `module.resource.remove {module_id, resource_id, mutation}`, and `task.<id> {asset_id?, profile_id?, mutation, …parameters}`; a capability job is read and cancelled with the one job API every kind shares, `job.read {job_id}` and `job.cancel {job_id}` ([jobs](modules-and-api.md#jobs)). All are in `schema.list`. An install records the envelope's actor in its `installed.json`. A `task.<id>` request queues a job, so it carries the `{request_id, actor}` envelope like every other job it starts: a retry returns the first `{job_id, status}` marked `deduplicated: true` and starts no second job, and a refusal such as `consent-required`, `not-ready` or `preparation-required` is not remembered, so a client asks again under the same `request_id` once it has answered it.

Every task request checks its declared requirements before anything is queued: a profile that is not ready and a resource the task uses that is not installed fail together with `not-ready` and `data.requirements: [{kind: profile|resource, id, state}]`, and a missing grant fails with `consent-required` for the first one. Otherwise the request returns `{job_id, status}` promptly. `job.read` answers a capability job as `{job_id, kind: install|remove|task, status, progress: {fraction?, message?}, module_id, resource_id?, result?, error?, request_id?}` with `status` the one job-status vocabulary every job kind shares; a capability job never reads `superseded`. `error` is `{code, message, data?}`. Any client may read or cancel a capability job: resources and tasks belong to the module, not to a session, and a client's disconnect leaves its jobs running. Cancelling a queued job removes it; a running job stops at its next checkpoint and releases what it held. The owner keeps the last 32 finished capability jobs. A request that changes state at once (a grant, denial, revocation or settings write) and a successful install, removal or task emit an event carrying the originating method and request ID; a cancelled job that had not started emits one under the request that started it; failures emit none.

Capability jobs are records in the catalog owner's one job table and run on two of its lanes, each one thread that sleeps while idle and is started on first use: `transfer` (install and remove) and `module` (tasks). Each lane runs one job and holds at most four queued; a fifth request fails with `resource-limit`. Nothing that hashes, downloads, loads resources, runs a task or reads a secret's data runs on the catalog owner or UI thread. Workers post completions into the owner's channel; nothing polls.

Every capability job publishes to the [activity board](performance-panel.md#activity-board) the moment its lane picks it up, and ends it when its result is in: `activity.list` lists it beside source preparation and analysis, with `kind` `module.resource.install`, `module.resource.remove` or `module.task`, and `detail` naming the module and, for a resource job, the resource. A job's `progress` is read from that same activity, the one progress model every publisher shares; the job record keeps no separate copy.

A task receives the path of every installed resource it `uses` through `ModuleContext::resource_path` and reads it on the module lane itself; nothing keeps a resource loaded between tasks. `module.status` reports settings validity, resources, grant and denial counts and live jobs. Removing a resource queues the removal on the transfer lane; a task that uses it is refused `not-ready` from then on, and an accepted edit keeps rendering from its artifact. Loading a module's state once, ahead of its tasks, is activation, which is deferred until `local-runtime` (see [decisions](#decisions)).

A resource installs only from its pinned URL, under the `download-artifact` grant: `source` is `{kind: "download"}` or absent, and any other source or field is refused as a `validation` error, so no client can make the host read a path it names. The worker streams into `<data>/modules/resources/.staging/<job_id>`, refuses the transfer once it exceeds the declared `bytes`, checks the exact length and SHA-256, asks the module's `validate_resource` hook to check the format, checks the resource quota (16 GiB across modules), then renames the directory to `<data>/modules/resources/<module_id>/<resource_id>/<version>/` (the file is named after the resource ID) and writes `installed.json` last with the URL, hash, bytes, license, provenance, actor and time. Only a directory with a matching `installed.json` is installed, so an interruption, crash, short, corrupt, oversized, redirected or disk-full transfer leaves no installed resource, and stale staging directories are removed by the next install. Downloaded data is never executed or deserialized with a general object loader, and a checksum proves the bytes match the manifest, not that a model is safe or licensed for reuse. Removal deletes the version directory and can never make an accepted edit disappear.

## Derived artifacts

The core owns immutable **derived artifacts** that committed recipes reference: content-addressed bytes plus a kind, optional dimensions and colour interpretation, and a SHA-256, addressed by an ID the host derives from the hash (`artifact-<sha256>`; clients treat it as opaque). A module publishes one from a task through `ModuleContext::publish_artifact` (at most 16 per task); the worker writes the bytes to `<root>/tmp/`, syncs them and renames them to `<root>/objects/<sha256>`, and the owner records the row when the job completes, before the job reads `ready`, so an artifact is committable as soon as its task reports it. Publishing the same bytes twice yields the same artifact, and a corrupt object file is replaced atomically. One artifact is at most 256 MiB. A failed or cancelled task's artifact stays an unreferenced file that the next process can collect.

The artifact root is the directory `<catalog stem>.artifacts` beside the catalog file, created on the first publish with a `manifest.json` holding the format marker and the catalog's own `catalog_id`. It moves with the catalog. The [current catalog format](versions-and-lineage.md#storage-catalog-format-11) holds `catalog_meta` (catalog ID), `artifacts` (ID, hash, bytes, kind, dimensions, colour, publishing module, time) and `artifact_refs` (entry, artifact). A layer lists the artifacts it references in its host-owned `artifacts` field, which only an effect declaring `artifacts: true` may use; the commit transaction checks every listed artifact has a row and a present file of the recorded length and inserts the entry's references with the entry itself; reference rows can never be deleted. Undo and redo add no entry and bind no bytes. A crash between the file rename and the catalog commit leaves only an unreferenced file, never a snapshot that points at an unpublished artifact.

Every history entry, branch, version, preview and restore keeps its references, because entries are never deleted and a reference is a row. `artifact.collect` removes only unreferenced artifacts that no task of the current process published, orphan files without a row and stale temporary files; nothing reachable from any entry is ever eligible.

Evaluation binds artifact bytes explicitly, into the recipe. A recipe carries a table of the verified bytes its layers list beside its resolved strokes: like them it is never serialized, excluded from the recipe's equality and shared between the recipe's clones, and a recipe read out of the catalog has an empty one. Where a stack that references artifacts enters evaluation or admission — before the owner plans an action or a draft, admits a commit, renders, samples, locates, answers a query or builds a preview, analysis or sample job — the owner binds it (`EditorService::bind_artifacts`): it checks each artifact's row, root and file length and looks for its verified bytes in the prepared-artifact cache (256 MiB, least recently used, keyed by hash and file signature), and fills the table with exactly what the stack lists. A miss returns `preparation-required` with a source job that reads and hashes the artifacts on the source worker, exactly like a source miss: the refusal names the identities still to prepare among the evaluated stack's needs ([preparation](modules-and-api.md#preparation)), and the job reads exactly those; `source.prepare` covers both and `analysis.request` queues the same job. A stack whose artifacts could not all be held ready at once (256 MiB or 4096 artifacts) is a `resource-limit`. A job owns the bytes it evaluates by owning its evaluation's bound recipe, so an eviction from the cache never breaks a job already planned, and nothing else holds them. Compiling reads a layer's artifacts from its recipe's table, in the layer's order, and `CapabilityModule::compile_bound` receives them beside the payload; a listed artifact the table lacks refuses the stack by name (`source-unavailable: artifact <id> of layer <id> is not bound to this recipe`), never compiles it without the bytes. A missing root, a missing file (`is missing`) or a file of the wrong length or hash (`is corrupt`) fails render, sample and analysis with `source-unavailable` naming the artifact, and a root whose manifest names another catalog with `incompatible`; nothing is rewritten; the original source stays byte-identical. [Export](export.md) binds the same way before it evaluates, and fails the same way.

Moving the catalog together with its `.artifacts` directory keeps every reference valid. Copying only the SQLite file leaves every artifact-referencing render failing with `source-unavailable: artifact directory … is missing` while history stays readable. `artifact.collect` deletes the eligible rows in one catalog transaction and then queues a source job for their files; if that queue is full the files wait as orphans for the next collection. Opening a catalog queues this same collection once on its own, on the source worker, before any client asks; `artifact.collect` stays for a client that wants one sooner. `artifact.status` reports the root, its state (`absent`, `ready`, `missing`, `foreign`) and counts; `artifact.inspect {artifact_id}` reports one artifact's metadata, file state and how many entries reference it. Settings, grants and secrets are not copied with a catalog.

## Proof module

`luxforge.capabilities` (title Capabilities proof) is a developer-only test fixture, registered by the desktop and `luxforge-json` only with `--developer --proof-endpoint URL` and by tests directly. It declares a non-secret `strength` number; a profile adapter `proof-echo` (bearer auth, `sample-grid-8`) whose profiles hold an `endpoint` and a secret `api-key`; the capabilities `echo` (remote-image-request) and `palette` (download-artifact); one pinned resource `proof-palette` served by the proof endpoint; the task `generate-proof-tint` (asset, profile, uses `echo` and `palette`) that reads the installed palette through its context, posts the sample grid to the endpoint, combines the answer with the palette and `strength`, and publishes a 12-byte tint artifact; and the actions `apply-proof-tint {artifact}` (commits the one layer, then updates it in place) and `reset-proof-tint` (returns that layer to a neutral payload with no artifacts, or is a no-op) over the colour-stage effect `luxforge.capabilities.tint`, whose `compile_bound` multiplies linear channels by the artifact's three gains. Its controls are the task button and a Reset tint action; its settings are not controls. `ProofEndpoint`, its loopback fake provider with knobs for delays, failures and a wrong palette, is started by the test or smoke harness, never by the editor. It lives in `luxforge-testbase` on the workspace's one loopback test server, so the shipped core carries no test server, and takes the proof module's paths, palette and grid size from its caller (`luxforge-testkit`'s `proof_protocol`, or the core's own test harness); the core, desktop and `luxforge-json` tests take it as a dev-dependency and `xtask` as a dependency.

## Desktop

Any module that declares settings, resources or tasks gets a capability block at the top of its tools-panel section, generated from its descriptor and drawn above the section's own controls: one row per resource with its version, size and state (with progress while it installs) and the one action that state allows, Download, Cancel or Remove; a settings form of the module-level fields, each drawn as the tools panel draws a control of its kind (a number field, a toggle, a segmented choice, a text field that commits on Enter); the permission counts `module.status` reports, with a Revoke all that lists the module's grants through `module.permission.list` and withdraws each live one through `module.permission.revoke`; and one status line for the last failure, a `not-ready` answer's message or settings the module cannot use. Every write carries the module's settings revision; a conflict reads the settings again and says so on the status line. Provider profiles, secrets and a single grant are not drawn: they are set through `module.profile.*`, `module.settings.set-secret` and `module.permission.*`, which is how every client sets them. A task control sends the open photo and its first ready profile, shows progress with Cancel and, on success, Apply, which commits the task's artifact through the ordinary edit path; another profile is chosen by sending `task.<id>` with its `profile_id`. A `consent-required` answer to anything the desktop started opens a consent notice over the canvas, not a modal: "Allow <module> to download a resource / send photo data?" with the disclosure and "You declined this before." when it was; Allow grants exactly that scope with the desktop's authority and retries once, and Don't allow records a denial. While a job the desktop tracks is in flight it reads that job every 100 ms; nothing polls otherwise, and capability events from other clients refresh the block without rendering. `state.json` carries a redacted `capabilities` summary per module: the settings as `module.settings.read` answers them, the jobs, the open consent and the status line.

## Evidence

Each capability behaviour is tested once per layer. Unit tests cover descriptor acceptance and every named rejection, the shared JSON document (its marker, refusals, bound, write-on-change and concurrent writers), settings revision, conflict, deduplication and format refusal, the in-memory secret store, grant scopes and bounds, endpoint classes and the proof module's palette, answer and tint. `capabilities/lifecycle_tests.rs` owns every shared behaviour at the owner's JSON methods, on a fixture module: inert discovery and reopen, grant authority, scope validation, denial, revocation of queued and running jobs and on endpoint, profile and reset changes, cancellation mid-transfer, task requirements, status, verified installs under every failure with nothing installed or staged afterwards, the quota, removal and retries. The core's capability tests send through an in-memory transport that answers in process, holds an answer at a gate and counts every request, and drive the owner through one shared harness in `capabilities/testing.rs`. `luxforge-net`'s tests cover the transport's address classes, single resolution, redirects, request and response bounds, refused framing, deadlines, cancellation, TLS roots and truncation against loopback servers, and the native Keychain store. `capabilities/proof_tests.rs` keeps one journey of the proof module end to end through the owner's JSON methods, including a pixel-exact render of the applied tint, reopen and the one sentinel-secret scan of every answer, refused secret request, file and endpoint record, and what only a sending, publishing task shows: per-asset consent, a revoked send, a retried task, a wrong key and a task that fails after publishing. Derived artifacts are tested on the proof module's tint through publish, commit, reopen, branches, versions, restore, collection, missing and corrupt bytes and crash points. Beside them, one `luxforge-json` test checks that only a client started with `--permission-authority` may grant, and one drives the journey through the command line; one desktop test drives consent, install, the task and Apply through the notice. The native Keychain journey is the opt-in `keychain_sets_reports_presence_reads_and_clears_a_secret`, which passed on the M4 without a dialog.

The rendered `capabilities` smoke scenario sets the proof up through `api` steps and drives the desktop's task control, consent notice and Apply against the loopback endpoint; its 22 frames show the settings, profile and key read back into the block, download progress, installed, the photo-data consent before and after a denial, a task's progress and result, the applied tint (within 1.13 codes of the core's own render of the same stack, against a 2-code tolerance) and the endpoint's 401, and no file the run wrote contains the sentinel key. The desktop's own tests prove the block's Download and consent, a settings conflict's one status line, and Revoke all.

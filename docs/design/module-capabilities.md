# Module settings, permissions and managed resources

Status: **proposal for owner review; no implementation is authorized by this plan**. This is a shared host capability contract for linked modules and later externally loaded modules. It extends the [current module contract](modules-and-api.md); it does not select a binary plugin format or introduce accounts, cloud sync or a marketplace. The [corrections design](corrections.md) is the first intended consumer. All operations available in the desktop must also be discoverable through the shared service.

## Outcome and boundary

A module can declare settings and required capabilities, but only the host can store settings or secrets, open user files, download resources, contact endpoints, schedule work or publish persistent assets. Descriptors remain cheap to register. Activation is an explicit, cancellable lifecycle request on a worker, never a side effect of `module.list`, catalog reopen, recipe compilation or tool-panel construction. The UI may request activation when a tool opens; the same request and status are available to JSON/MCP clients. There is no network request, file picker or model download merely because a module is listed.

These capabilities apply first to **trusted linked modules**. A permission declaration is useful for consent, least privilege and auditing, but does not sandbox arbitrary code linked into the editor. Loading third-party executable modules remains the separate external-module path on the [roadmap](../plan.md), which must add an actual process/ABI trust boundary before untrusted code is supported.

## Configuration contract

`ModuleDescriptor` may declare a versioned settings schema: stable setting IDs, label/help, kind (`boolean`, bounded number, enum, bounded text, endpoint URL, selected file/directory, secret), required/default, validation and whether a change invalidates activation. A setting may be per module or per named provider profile. Profiles are user-level: a correction can choose among a local model and multiple remote endpoints without storing keys or paths in a photo recipe. Settings have no image effect by themselves and do not create history entries.

The host stores non-secret values in its app-owned configuration, outside the photo catalog, with atomic writes, a revision and a current-shape marker. Unsupported shapes fail explicitly and retain the bytes. Secrets go through a host `SecretStore` abstraction backed by the OS credential facility; the first implementation targets macOS Keychain, with Windows Credential Manager and Linux Secret Service as later portability work. A missing or locked secure store yields an actionable error; there is no plaintext fallback. `module.settings.read` returns values, defaults, effective/invalid status and `secret_present`, never secret bytes. `module.settings.set` validates a revision and request ID, commits atomically where possible, and emits a settings-change event; `module.settings.clear-secret` removes only the selected secret. Redaction covers `schema.list`, `module.list`, events, logs, errors, request capture, support bundles and copied JSON. A secret may be supplied through a dedicated input path but is never echoed, persisted in an image catalog, or exposed to other modules.

Provider profiles describe a **typed adapter**, not a generic URL template that any module can use to send arbitrary bytes. The adapter declares supported input/output and model IDs, endpoint rules, image size limits, auth mechanism, data-retention/cost information if known, and cancellation. An endpoint edit must be revalidated and lose the previous network grant. The host can report whether a configured provider is ready, missing credentials, offline, or incompatible without loading it.

The desktop builds a module Settings surface from this schema: a module-level Settings action opens its values and named provider profiles, lets the user add/remove a profile, select a model, edit an endpoint, choose a local file, enter/replace/clear a secret and inspect permission/resource status. A secret field displays only whether a value exists. Validation and structured status come from the shared service; widgets hold no authoritative configuration. The corresponding API methods can create/select/remove profiles and set/clear the same fields. Changing a profile in use does not rewrite a historical AI result, which records the model/provider provenance it used.

## Capability and consent contract

Declarations name a purpose and narrow resource: `managed-storage`, `download-artifact` (pinned HTTPS origin, expected size/hash and artifact type), `read-user-file` (explicitly selected file or directory), `remote-image-request` (configured endpoint and disclosed image/crop/mask bytes), and `local-runtime` (specific reviewed worker/runtime). Module-private state is namespaced and quota-bound under the app data root; modules receive opaque handles and cannot choose arbitrary host paths. The host owns all operations and records grant scope, provenance, creation/revocation and last use in user-level state. Grants are revocable; revocation stops new work and cancels affected pending work. It does not erase a saved repair or existing history.

The editor asks for in-app consent immediately before the first gated operation, with the module, concrete destination or selected path, data to be sent/read, expected download size and storage location, and whether the operation may cost money. The OS may separately prompt when its own protected folders or credential store require it. App-private storage needs no extra prompt. A headless client receives `consent_required` plus the exact request scope. `module.permission.grant` is a programmatic operation, but an ordinary edit-capable client cannot self-grant: it requires a separate permission-management authority established by an interactive owner action or an explicit local headless setup step. The grant's own request ID, scope and actor are recorded without secrets; no grant follows from retry, `module.activate`, a saved recipe or mere same-user API access. Grants for sending a photo are scoped to the provider endpoint and selected asset. Each later send for that asset still requires an explicit Generate action, and its UI shows the destination; it does not require a second permission grant. Network send is opt-in even if an API key is configured. A change of endpoint, transmitted data class or provider revokes the applicable grant. Denial is a usable state with local/manual tools still available.

The host resolves network destinations under an allowlist for each reviewed adapter; HTTPS is mandatory for remote services and loopback is an explicit, separately labelled local-service case. Redirects, DNS rebinding, private-address resolution, non-HTTP schemes and file URLs must not bypass the grant. Downloads and response bodies have size/time limits, TLS verification, SHA-256 verification where pinned, temporary files and atomic publish. Downloaded model data are never executed or deserialized with a general object loader; model repositories' custom code is never run automatically, and formats and runtime code are separately reviewed. A checksum proves bytes match a manifest, **not** that a model is safe or legally reusable. No provider receives an original path, EXIF or extra context unless its declared request explicitly requires that data and consent names it.

## Lifecycle, jobs and resource ownership

The host exposes `module.activate`, `module.deactivate`, `module.status`, `module.resource.list`, `module.resource.install` and `module.resource.remove` as typed operations with schema discovery and structured errors. Activation can pre-load a model on a bounded worker after its settings and grants are valid; it returns a job/status promptly and can be cancelled or superseded. Opening a panel may request it, but the panel remains responsive and shows progress, disk footprint and fallback/manual actions. First use may request activation if needed. Deactivation releases memory; it never deletes a downloaded resource or edit. The worker admits a bounded number of queued/active jobs, reports progress and cancels between bounded work units. Nothing that hashes, downloads, loads weights or runs inference executes on the catalog owner or UI thread.

Managed downloads use a manifest with model/runtime ID, exact version, URL, expected byte count, SHA-256, license/notices and required runtime. The user chooses Download or selects an existing verified copy. A partial download is resumable only when the server and hash checks make that safe; otherwise it is discarded. Publish occurs only after hash and format checks. Model files stay outside the app bundle and catalog, with storage used/available and a Remove action. Removing a model must leave accepted image edits renderable. Module-private mutable state is small, separate from immutable image artifacts, and has a quota and current-shape validation. User-selected files are read through scoped handles, with symlink/path traversal and changed-file checks, and are never rewritten by a module.

The core owns immutable **derived image artifacts** needed by a committed recipe: content-addressed bytes plus format, dimensions, colour interpretation and hash, addressed by opaque IDs. The proposed storage is a catalog-adjacent managed directory with a manifest, so a catalog and its derived assets can be moved as a pair; copying only the SQLite file is diagnosed as incomplete. A commit that references an artifact validates it and atomically publishes the catalog reference with the recipe/history transaction (with crash recovery for the file/DB boundary). Every retained history snapshot keeps its references alive. Eviction only applies to disposable previews, never to any artifact reachable from history or a named version. Missing/corrupt artifacts cause explicit render, sample and export errors and keep every snapshot intact. A recovery action may select a moved artifact directory only after all referenced hashes match; it never silently rewrites history. Backup, catalog relocation and shared editing must carry these references before their own portability claims are made. Settings, grants and secrets are not copied with a catalog.

## Evidence and open decisions

Implement the shared framework with a tiny proof module that declares one non-secret setting, one secret, one selected-file read, one pinned test download and one cancellable activation. Its UI and JSON operations must agree; test denied/revoked grants, bad endpoints, redirects, changed files, malformed/oversized downloads, crash during publish, unavailable secure store, secret redaction and catalog reopen. Measure cold registration, panel activation, idle CPU, memory, disk and job cancellation on the M4. Follow the [performance rules](../engineering/performance-rules.md) and run `verify quick`; rendered and timing tiers apply at integration.

Owner choices before implementing network/photo transfer: whether a grant can be remembered for later photos, and which remote provider adapters the first release supports. The default above is per-asset consent. The local runtime/model and any third-party weight license are selected by [corrections qualification](corrections.md), not by this generic framework. External executable loading stays a separate measured project.

# Module settings, permissions and managed resources

Status: **implemented and verified on the M4 Mac.** The contract was frozen on 2026-09-23 under the owner's delegation ("make sensible decisions, don't block on me"); its decisions are recorded in [product decisions](../decisions.md#module-capabilities) and can be revisited by the owner. The code lives in `crates/lightwell-core/src/capabilities/` (settings, secrets, grants, consent, the transport, the worker, resources, tasks), `crates/lightwell-core/src/artifacts/` and `editor/artifact_store.rs` (derived artifacts), `modules/capabilities_proof.rs` (the proof module and its endpoint) and, in the desktop, `app/capabilities.rs`, `state/capabilities.rs` and `view/capabilities.rs`. This is the shared host capability contract for linked modules. It extends the [current module contract](modules-and-api.md); it does not select a binary plugin format or introduce accounts, cloud sync or a marketplace. The [corrections design](corrections.md) is the first intended consumer. Every operation available in the desktop is a discoverable method of the shared service.

## Outcome and boundary

A module declares settings, provider adapters, capabilities, resources, an activation requirement and worker tasks. Only the host stores settings or secrets, downloads resources, contacts endpoints, schedules work or publishes persistent artifacts; a module receives those through a worker-side `ModuleContext` that enforces the grant it runs under. Descriptors stay plain data and registration does no I/O. Activation is an explicit, cancellable request on a worker, never a side effect of `module.list`, catalog reopen, recipe compilation or panel construction. Listing, reopening and schema discovery cause no network, keychain or model activity.

These capabilities apply to **trusted linked modules**. A declaration serves consent, least privilege and auditing; it is not a sandbox for code linked into the editor. External executable loading stays the separate measured project on the [roadmap](../plan.md) and must add a process/ABI trust boundary before untrusted code is supported.

## Decisions

| Question | Decision |
| --- | --- |
| Setting scopes | Two, both user-level and outside every catalog: module settings and named provider profiles of a module. No per-catalog or per-photo settings. Settings never create history entries and have no image effect by themselves |
| Consent unit | **Per asset** for sending image data: a grant names the module, capability, provider profile, adapter, endpoint origin, data class and asset. Grants are not remembered for later photos. A resource download is granted per resource version and origin |
| Who may grant | Only a client with **permission authority**: the desktop's own client (after the person presses Allow) or `lightwell-json --permission-authority` (an explicit local headless setup step). Loopback live-session clients and plain `lightwell-json` never can. Anyone may deny or revoke, since both reduce privilege |
| Revocation | Stops new work, cancels queued and running jobs that depend on the grant (`cancelled`, reason `permission revoked`) and never touches recipes, history or accepted artifacts. Changing a profile's endpoint, removing a profile or resetting a module revokes the grants scoped to the old value (a profile's adapter cannot change) |
| Secret store failure | macOS Keychain first. A locked, missing or unsupported store fails with `not-ready` naming the store; there is no plaintext fallback. Windows Credential Manager and Linux Secret Service report `not-ready: secure storage is not implemented on this platform` until natively verified |
| Endpoints | HTTPS for anything remote, with public addresses only; plain HTTP only to loopback (`127.0.0.0/8`, `::1`, `localhost` resolving to loopback), which is a separately labelled `loopback` class. No proxies, no `file:` or other schemes, no userinfo in URLs |
| Remote provider adapters in the first release | None besides the developer proof adapter. Real adapters arrive with Corrections, each reviewed |
| `managed-storage` and `local-runtime` capabilities | Not implemented; registration rejects them by name until their first consumer defines them |
| Catalog format | Format 7 holds the catalog's identity and the artifact tables beside the preset library and the [mask](masking.md) table and stroke store; two branches each claimed format 6 for one of those halves, so a catalog of either is refused by name and kept intact (current shapes only) |
| Settings format | One JSON file per user with `format: 1`; any other marker is refused and the file is retained unmodified |

## Configuration contract

`ModuleDescriptor` gains optional, plain-data fields. Every one defaults to empty, so existing descriptors are unchanged.

```text
settings:   { schema: u32 ≥ 1, fields: [Setting], profiles?: { label, max: 1..16, adapters: [Adapter], fields: [Setting] } }
Setting:    { id, label, help?, kind, required, default?, invalidates_activation }
kind:       boolean | integer {min,max} | number {min,max,step?,precision?} | enum {options}
            | text {max_length ≤ 4096} | endpoint {classes: [remote|loopback]}
            | secret {max_length ≤ 4096}
Adapter:    { id, title, auth: none|bearer, data: [data class], max_request_bytes, max_response_bytes,
              timeout_ms, retention?, cost: free|paid|unknown }
capabilities: [ { id, kind: remote-image-request {adapter, data}
              | download-artifact {resource}, purpose } ]
resources:  [ { id, title, version, url, bytes, sha256, format, license, provenance, redirect_origins? } ]
activation: { requires_settings: [id], requires_resources: [id], notes } | null
tasks:      [ { id, title, notes, asset: bool, profile: bool, requires_active: bool,
              uses: [capability id], parameters: [Parameter], apply?: {action, parameter} } ]
```

A setting's kind is flattened into it, as a parameter's is. Identities follow the existing rules: setting, adapter, capability, resource and task IDs are hyphenated lowercase names; a task ID is unique across the registry because it generates the method `task.<id>`. Registration rejects, with a `validation` error naming the field: a malformed or duplicate ID; an unknown kind; a default outside its kind (a `secret` never has a default; an `endpoint` default is refused); a `required` setting in `requires_settings` that is not declared; a capability naming an undeclared adapter or resource; an `endpoint` with no class; a profile block without an `endpoint` field when an adapter is declared; a resource whose `url` is not HTTPS unless it is loopback, whose `sha256` is not 64 lowercase hex, whose `bytes` is 0 or above 16 GiB, or whose `redirect_origins` are not HTTPS origins; a task naming an undeclared capability or an `apply` action or parameter that does not exist or is not of kind `artifact`; `managed-storage` or `local-runtime`. It also refuses a profile block without adapters; a `bearer` adapter whose profile fields do not declare exactly one secret; adapter byte limits outside 1 byte..256 MiB or a timeout outside 1..600000 ms; an empty title, format, license, provenance or retention note; a resource version that is not a plain directory name; duplicate enum options, endpoint classes or requirement entries; a task that takes a profile without a profile block, one that `requires_active` without an activation, and a `remote-image-request` task that does not take both an asset and a profile. `requires_settings` names module-level fields, a `remote-image-request` data class must be one of its adapter's, and `redirect_origins` are exact serialized origins (`https://host[:port]`, default port omitted). Profile `max` is 1..16 and module-level plus profile fields are at most 32 each.

`module.list` and `schema.list` return exactly these declarations. They contain no setting values and never a secret: a secret field declares only its presence.

Two descriptor additions support the rest of the contract. A parameter kind `artifact` carries one artifact ID published in the catalog; the host checks its syntax generically and the commit checks that it exists. A control kind `task {task, label}` is a button that runs the task through the desktop's consent and progress flow and, when the task declares `apply`, offers Apply with the result. An effect may declare `artifacts: true`; only a layer of such an effect may reference artifacts.

### Settings store

Non-secret values live in `<config>/modules/settings.json`, outside every catalog: `{format: 1, modules: {<module_id>: {schema, revision, values, profiles: [{id, adapter, label, values}], requests: [...]}}}`. Profiles have host-generated IDs (`profile-<uuid>`). Each module has its own monotonic `revision`. A write takes an OS advisory lock on `settings.lock`, re-reads the file, checks the revision and the request, writes a temporary file, syncs it and renames it over the old one; a failure leaves the previous file. The file is at most 1 MiB. A `format` other than 1, or unparseable JSON, fails every settings method with `incompatible` and the file is never rewritten. A module whose stored `schema` differs from its descriptor reads `state: incompatible`, keeps its stored values untouched and refuses writes until `module.settings.reset` clears that module's entry explicitly. Entries for modules that are not registered are kept verbatim.

Every settings mutation takes the edit mutation envelope `mutation: {expected_revision, request_id, actor}`, where the revision is the module's settings revision. A stale revision is a `conflict`. Request deduplication covers the last 64 requests of that module, stored in the file with the SHA-256 of the canonical request and the result: a retry returns the original result; the same ID with a different input is a `conflict`. A write that changes nothing is `outcome: no-op` and keeps the revision. Committed settings writes emit an event whose method is the method name; a retry answered from the request log emits none. Every write answers `{module_id, outcome, revision, deduplicated, profile_id?, profile?, changed, invalidates_activation, revoked?}` plus `settings`, a fresh read; a retry gets its stored result with `deduplicated: true` and a fresh read. A `secret` write is deduplicated by setting identity only, because the host never stores a hash of a secret; writing a secret is idempotent.

`module.settings.read {module_id}` returns `{module_id, schema, revision, state, fields: {<id>: {value, default, source: user|default, valid, error?}}, profiles: [{id, adapter, label, fields, status}]}`. A secret field reports `{secret_present, valid, error?}` instead of a value, where `secret_present` is `null` when the store cannot answer, so a locked keychain shows on that field rather than failing the read. A profile's `status` is `ready`, `incomplete` (a required field is missing or invalid), `missing-credentials` (the adapter authenticates and the secret is absent) or `incompatible`. The host can report this without loading anything.

`module.settings.set {module_id, profile_id?, values: {<id>: value | null}, mutation}` validates each named field against its kind and commits them together; `null` returns the field to its default. A secret field is refused here. An `endpoint` value is parsed and classified by the transport policy. Changing a field declared `invalidates_activation` on an active module queues its deactivation, and the module reads `inactive` with the reason `settings changed`. `module.settings.set-secret {module_id, profile_id?, setting, value, mutation}` stores the value through the secret store and returns the read result; the value is never echoed. `module.settings.clear-secret` removes only that secret. `module.profile.create {module_id, adapter, label, mutation}` returns the new profile; `module.profile.remove {module_id, profile_id, mutation}` removes its values, clears its secrets and revokes its grants. `module.settings.reset {module_id, mutation}` deletes the module's values and profiles, clears their secrets and revokes their remote grants (a download grant names a pinned resource, not a setting, and survives); it keeps the module's schema, revision and request log, so the revision never goes backwards and a retried reset is recognised, and it is the explicit way out of an incompatible schema. Removing a profile or resetting a module that declares secrets answers `not-ready` while the secret store is unavailable, because the secrets could not be cleared.

### Secrets and redaction

`SecretStore` is a host trait with `set`, `clear`, `present` and `read`. The macOS store keeps generic passwords under the service `app.lightwell.module-secret` and the account `<module_id>/<profile_id or ->/<setting_id>`; `present` queries attributes only, so it never asks for the secret's data. A locked or unavailable keychain maps to `not-ready`. `read` is called only on the module worker, inside a task or activation that declares the secret; the value is a `SecretValue` that is not `Serialize`, whose `Debug` prints `<redacted>` and whose buffer is zeroed on drop. The OS may show its own prompt when a rebuilt executable reads an item an earlier build stored; that prompt belongs to the OS, and a set or clear that waits on it holds the owner for its duration. Evidence runs and tests use an in-memory store and never touch the login keychain; the native journey is an opt-in ignored test.

Redaction is structural: no descriptor, read result, event, error, job record, status, log or evidence file can carry a secret, because nothing but `set-secret` requests and the worker's `SecretValue` ever hold one. `redact_request` replaces the `value` of a `module.settings.set-secret` request with `"<redacted>"` and drops the live-session token; the desktop's request log, evidence capture and Copy as JSON use it. Tests set a sentinel secret and scan every response, event, log and evidence file for it.

### Provider adapters

A profile names one declared adapter: a typed contract, not a URL template. The adapter declares its data classes, request and response size limits, timeout, authentication, retention note and cost. The host builds the request body only from the task's declared data, sends it through the transport under the grant and returns the response bytes to the module; a module never supplies a URL. The first data class is `sample-grid-8`: an 8 × 8 grid of rendered sRGB samples of the asset's current entry at the centres of an 8 × 8 grid over its output stage, sent as fixed-width JSON of exactly 959 bytes (`{"data_class":"sample-grid-8","width":8,"height":8,"samples":[[r,g,b],…]}`, each channel padded to three characters), which is the size the disclosure states. The owner binds the entry at request time and the module lane takes the 64 point samples, so a spatial layer's per-sample tile never runs on the owner; no frame is rendered. Corrections adds its crop and mask classes with its own design. No provider receives an original path, EXIF or extra context.

## Capability and consent contract

Two capabilities are implemented. `download-artifact` installs a declared resource from its pinned URL. `remote-image-request` sends a declared data class of one asset to a profile's endpoint through its adapter. Each is gated by a **grant** whose scope is exact:

| Capability | Grant scope |
| --- | --- |
| `download-artifact` | `{module_id, capability, resource, version, origin}` |
| `remote-image-request` | `{module_id, capability, profile_id, adapter, origin, data, asset_id}` |

A module that reads a user-chosen file may add a `read-user-file` capability back later, consented per canonical path.

A gated operation without a matching grant fails before any work starts with `consent-required` and `data.consent: {module_id, capability, scope, disclosure, denied}`. The disclosure names the module and purpose, the destination (an origin), the data to be read or sent and its size, the storage location and expected bytes for a download, the adapter's retention note and whether it may cost money; `denied` is true when a denial is recorded for that scope. The desktop shows this as a consent notice with Allow and Don't allow; a headless client receives the same failure.

`module.permission.grant {module_id, capability, scope, request_id}` requires permission authority and otherwise fails with `forbidden`; the scope must be one the module can use. It records `{grant_id, module_id, capability, kind, scope, actor, request_id, created_ms}` and clears a matching denial; a retried request, or a grant of a scope that already has a live one, returns that grant as a no-op. A denial does not revoke a live grant. `module.permission.deny {module_id, capability, scope}` records a denial. `module.permission.revoke {grant_id}` marks the grant revoked with a reason and cancels dependent jobs. `module.permission.list {module_id?}` returns grants, revocations and denials. Grants live in `<config>/modules/grants.json` with the same format marker, lock, atomic write and bounds (at most 1024 records) as settings; nothing is copied with a catalog. No grant follows from a retry, `module.activate`, a saved recipe, a configured key or same-user API access.

### Transport

The host transport is the only network path. It parses a URL, requires `https` for the `remote` class and allows `http` only for the `loopback` class, rejects userinfo, fragments and every other scheme, resolves the host once, requires every resolved address to belong to the endpoint's class (`remote` refuses loopback, private, link-local, shared, unique-local, multicast, unspecified, documentation and IPv4-mapped forms of these) and connects to the checked address, so a second resolution cannot rebind it. TLS uses rustls with the ring provider and the operating system's certificate verifier (native roots with webpki on Linux); tests inject their own roots. Redirects are refused unless the request allows them; an allowed redirect must stay HTTPS, target an origin in the declared list and passes the same checks, and it drops the `Authorization` header when the origin changes. A response larger than its limit is refused from its length header or cut off when the limit is crossed; connect, read and whole-request deadlines apply; sockets wake every 100 ms so cancellation is checked between reads without a poll loop (a lookup or a connect attempt is bounded by its timeout instead). Only 301, 302, 303, 307 and 308 redirect, always as a `GET` without a body; other `3xx` answers are returned as data, and a same-origin redirect must be listed too. A request refuses a body on `GET`, more than 32 caller headers, a head over 16 KiB, control characters and every connection-level or cookie header; a response refuses compression, any transfer coding but `chunked` (and any at all on HTTP/1.0), a length that is not one plain number or disagrees with another, both a coding and a length, a line ending in a bare line feed, `101`, a head over 64 KiB (interim responses included) or 100 fields, trailers over 64 KiB and a TLS body that ends without the server's close signal. Every failure is structured: `validation` for a refused URL, address or redirect, `resource-limit` for size, `read-error` for network and TLS failures, `cancelled` for a cancel.

The HTTP/1.1 itself is [`ureq-proto`](https://crates.io/crates/ureq-proto), the sans-IO protocol crate of `ureq` 3, pinned with only its `client` feature: it writes the request head and frames the response, with `httparse` reading the head, while the transport keeps its own resolution, socket, TLS session, redirects, deadlines, read slice and bounds, and refuses the framing above that the crate would otherwise accept. `ureq`'s own agent was not used: its connector, transport and resolver must be `'static` and a request runs to completion inside its call, so the caller's borrowed cancel could reach a read slice only through a watcher thread or an owned cancel handle, and its pool, proxy-from-environment and redirect following would each have to be switched off. `ureq-proto` traces request heads, `Authorization` included, to the `log` facade at trace level; Lightwell installs no logger, and one added later must leave out `ureq_proto`.

## Lifecycle, jobs and resources

Methods: `module.activate {module_id}`, `module.deactivate {module_id}`, `module.status {module_id}`, `module.resource.list {module_id}`, `module.resource.install {module_id, resource_id, source?}`, `module.resource.remove {module_id, resource_id}`, `task.<id> {asset_id?, profile_id?, …parameters}`, `module.job.read {job_id}` and `module.job.cancel {job_id}`. All are in `schema.list`.

Every request checks declared requirements before anything is queued: missing or invalid required settings, uninstalled required resources, an inactive module for a `requires_active` task and missing grants all fail with `not-ready` and `data.requirements: [{kind: setting|resource|activation|grant, id, state}]`, or with `consent-required` for the first missing grant. Otherwise the request returns `{job_id, status}` promptly. A job reads `{job_id, kind: activate|deactivate|install|remove|task, module_id, resource_id?, status, progress: {fraction?, message?}, result?, error?, request_id?}` with `status` one of `queued`, `running`, `succeeded`, `failed`, `cancelled` or `superseded`; `error` is `{code, message, data?}`. Any client may read or cancel a capability job: activation and resources belong to the module, not to a session. Cancelling a queued job removes it; a running job stops at its next checkpoint and releases what it held. The owner keeps at most 32 finished job records. A request that changes state at once (a grant, denial, revocation, settings write, deactivation or queued cancel) and a successful activation, install, removal or task emit an event carrying the originating method and request ID; failures emit none.

The capability worker has two lanes, each one thread that sleeps while idle and is started on first use: `transfer` (install and remove) and `module` (activate, deactivate and tasks). Each lane runs one job and holds at most four queued; a fifth request fails with `resource-limit`. A second activation request joins the queued or running one; `module.deactivate` supersedes a queued activation and cancels a running one, and an active module reads `inactive` at once while the release of what it loaded runs on the module lane after any earlier work; a release is never refused for a full lane and cannot be cancelled. The host calls `deactivate()` after any activation that fails, panics or is cancelled. Nothing that hashes, downloads, loads resources, runs a task or reads a secret's data runs on the catalog owner or UI thread. Workers post completions into the owner's channel; nothing polls.

`activate` calls the module's `activate(context)` on the module lane after the host checks its requirements; the module keeps what it loads and `deactivate()` releases it. Activation state is `inactive`, `activating`, `active` or `failed {error}`, reported by `module.status` together with settings validity, resources, grants and live jobs. Deactivation never deletes a resource or an edit. Removing a required resource of an active module deactivates it at once and queues the removal on the transfer lane; the release runs on the module lane and may finish after the files are deleted, which is harmless on macOS and Linux but would fail the removal with `read-error` on Windows if the module still held the file open.

A resource install from its declared URL requires the `download-artifact` grant; `source: {kind: "file", path}` copies a local file instead and needs no grant, because only bytes matching the pinned hash are accepted. Either way the worker streams into `<data>/modules/resources/.staging/<job_id>`, refuses the transfer once it exceeds the declared `bytes`, checks the exact length and SHA-256, asks the module's `validate_resource` hook to check the format, checks the resource quota (16 GiB across modules), then renames the directory to `<data>/modules/resources/<module_id>/<resource_id>/<version>/` (the file is named after the resource ID) and writes `installed.json` last with the URL, hash, bytes, license, provenance, actor and time. Only a directory with a matching `installed.json` is installed, so an interruption, crash, short, corrupt, oversized, redirected or disk-full transfer leaves no installed resource, and stale staging directories are removed by the next install. Downloaded data is never executed or deserialized with a general object loader, and a checksum proves the bytes match the manifest, not that a model is safe or licensed for reuse. Removal deletes the version directory and can never make an accepted edit disappear.

## Derived artifacts

The core owns immutable **derived artifacts** that committed recipes reference: content-addressed bytes plus a kind, optional dimensions and colour interpretation, and a SHA-256, addressed by an ID the host derives from the hash (`artifact-<sha256>`; clients treat it as opaque). A module publishes one from a task through `ModuleContext::publish_artifact` (at most 16 per task); the worker writes the bytes to `<root>/tmp/`, syncs them and renames them to `<root>/objects/<sha256>`, and the owner records the row when the job completes, before the job reads `succeeded`, so an artifact is committable as soon as its task reports it. Publishing the same bytes twice yields the same artifact, and a corrupt object file is replaced atomically. One artifact is at most 256 MiB. A failed or cancelled task's artifact stays an unreferenced file that the next process can collect.

The artifact root is the directory `<catalog stem>.artifacts` beside the catalog file, created on the first publish with a `manifest.json` holding the format marker and the catalog's own `catalog_id`. It moves with the catalog. Catalog format 7 holds `catalog_meta` (catalog ID), `artifacts` (ID, hash, bytes, kind, dimensions, colour, publishing module, time) and `artifact_refs` (entry, artifact). A layer lists the artifacts it references in its host-owned `artifacts` field, which only an effect declaring `artifacts: true` may use; the commit transaction checks every listed artifact has a row and a present file of the recorded length and inserts the entry's references with the entry itself; reference rows can never be deleted. Undo and redo add no entry and bind no bytes. A crash between the file rename and the catalog commit leaves only an unreferenced file, never a snapshot that points at an unpublished artifact.

Every history entry, branch, version, preview and restore keeps its references, because entries are never deleted and a reference is a row. `artifact.collect` removes only unreferenced artifacts that no task of the current process published, orphan files without a row and stale temporary files; nothing reachable from any entry is ever eligible.

Evaluation binds artifact bytes explicitly. Before the owner plans, samples, analyses or builds a preview job for a stack that references artifacts, it checks each artifact's row, root and file length and looks for its verified bytes in the prepared-artifact cache (256 MiB, least recently used, keyed by hash and file signature). A miss returns `preparation-required` with a source job that reads and hashes the artifacts on the source worker, exactly like a source miss, with the identities still to prepare in `error.data.artifacts`; `source.prepare` covers both and `analysis.request` queues the same job. A stack whose artifacts could not all be held ready at once (256 MiB or 4096 artifacts) is a `resource-limit`. Jobs pin the prepared bytes they use, and `ToolModule::compile_bound` receives them beside the payload. A missing root, a missing file (`is missing`) or a file of the wrong length or hash (`is corrupt`) fails render, sample and analysis with `source-unavailable` naming the artifact, and a root whose manifest names another catalog with `incompatible`; nothing is rewritten; the original source stays byte-identical. Export does not exist yet and will inherit the same check.

Moving the catalog together with its `.artifacts` directory keeps every reference valid. Copying only the SQLite file leaves every artifact-referencing render failing with `source-unavailable: artifact directory … is missing` while history stays readable. `artifact.collect` deletes the eligible rows in one catalog transaction and then queues a source job for their files; if that queue is full the files wait as orphans for the next collection. `artifact.status` reports the root, its state (`absent`, `ready`, `missing`, `foreign`) and counts; `artifact.inspect {artifact_id}` reports one artifact's metadata, file state and how many entries reference it. Settings, grants and secrets are not copied with a catalog.

## Proof module

`lightwell.capabilities` (title Capabilities proof) is a developer-only test fixture, registered by the desktop only with `--developer --proof-endpoint URL` and by tests directly. It declares a non-secret `strength` number; a profile adapter `proof-echo` (bearer auth, `sample-grid-8`) whose profiles hold an `endpoint` and a secret `api-key`; the capabilities `echo` (remote-image-request) and `palette` (download-artifact); one pinned resource `proof-palette` served by the proof endpoint; an activation that requires the resource and loads it; the task `generate-proof-tint` (asset, profile, requires activation, uses `echo`) that posts the sample grid to the endpoint, combines the answer with the palette and `strength`, and publishes a 12-byte tint artifact; and the actions `apply-proof-tint {artifact}` (commits the one layer, then updates it in place) and `reset-proof-tint` (returns that layer to a neutral payload with no artifacts, or is a no-op) over the colour-stage effect `lightwell.capabilities.tint`, whose `compile_bound` multiplies linear channels by the artifact's three gains. Its controls are the task button and a Reset tint action; its settings are not controls. `ProofEndpoint`, its loopback fake provider with knobs for delays, failures and a wrong palette, is started by the test or smoke harness, never by the editor.

## Desktop

Any module that declares settings, resources, an activation or tasks gets a capability block at the top of its tools-panel section, generated from its descriptor: a Status view with the activation state and Activate or Deactivate, one row per resource with its version, size and state and Download, Cancel or Remove, a permissions line that opens the grants and denials with Revoke, and any requirement a `not-ready` answer named; and a Settings view that renders every module and profile field by kind — a secret only as Set or Not set with a masked Replace and Clear, each profile with its adapter and status, Add profile and Remove. Every write carries the module's settings revision, a conflict re-reads and says "Changed elsewhere", and text fields commit on Enter. A task control sends the open photo and its ready profile, shows progress with Cancel and, on success, Apply, which commits the task's artifact through the ordinary edit path. A `consent-required` answer to anything the desktop started opens a consent notice over the canvas, not a modal: "Allow <module> to download a resource / send photo data?" with the disclosure and "You declined this before." when it was; Allow grants exactly that scope with the desktop's authority and retries once, and Don't allow records a denial. While a job the desktop tracks is in flight it reads that job every 100 ms; nothing polls otherwise, and capability events from other clients refresh the block without rendering. `state.json` carries a redacted `capabilities` summary per module.

## Evidence

Core tests cover descriptor acceptance and every named rejection, inert discovery, settings revision, conflict, deduplication, format refusal, concurrent writers and restart, the in-memory and native secret stores, sentinel-secret scans of every response, event, job, status, file and log, grant authority, scope validation, denial, revocation of queued and running jobs and on endpoint, profile and reset changes, transport address classes, single resolution, redirects, request and response bounds, refused framing, deadlines, cancellation, TLS roots and truncation, lane bounds, join, supersede and cancel, verified installs under every failure with nothing installed or staged afterwards, and derived artifacts through publish, commit, reopen, branches, versions, restore, collection, missing and corrupt bytes and crash points. `capabilities/proof_tests.rs` drives the proof module end to end through the owner's JSON methods, including a pixel-exact render of the applied tint, per-asset consent, a revoked send, a wrong key, cancellation, resource removal and reopen; one `lightwell-json` test drives the same journey through the command line with `--permission-authority`. The native Keychain journey is the opt-in `keychain_sets_reports_presence_reads_and_clears_a_secret`, which passed on the M4 without a dialog.

The rendered `capabilities` smoke scenario drives the desktop through the same path against the loopback endpoint; its 25 frames show the consent notice before and after a denial, download progress, installed, active, a task's progress and result, the applied tint (within 1.13 codes of the core's own render of the same stack, against a 2-code tolerance), the endpoint's 401 and a revoked grant, and no file the run wrote contains the sentinel key. Costs, and the before and after comparison, are in the [performance plan](../specs/performance.md#module-capabilities-qualification).

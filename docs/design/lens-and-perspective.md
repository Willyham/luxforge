# Lens and perspective correction

Status: planned, not implemented. The owner delegated scope and approach selection for this plan; the choices below are planning decisions, not claims of delivered or verified behavior. Implementation is tracked in [the task plan](../../tasks/lens-and-perspective.json). No owner-review gate is required by this plan.

The planned sections are drawn on the [lens and perspective board](develop-workspace/lens-and-perspective.png) (a Perspective drag over a selected profile) and in their states on the [planned module panels](develop-workspace/planned-module-panels.png), with renders of [Lens correction](develop-workspace/modules/lens-correction.png) and [Perspective](develop-workspace/modules/perspective.png). Camera, lens and profile names on them are illustrative, not claims about the pinned database. The boards are design references, not evidence of anything built.

## Scope and decisions

| Decision | Rationale |
| --- | --- |
| First delivery: optional profile distortion correction for rectilinear lenses, plus manual horizontal and vertical perspective on JPEG and supported RAW | A useful geometry tool with a small, testable mathematical surface. Perspective also works without a lens profile. |
| Lensfun data, pinned and bundled offline; a bounded Rust resolver/evaluator for its `poly3`, `poly5` and `ptlens` distortion subset | Reuse community calibration without adding a native library, a second raster engine or a network prerequisite. Qualify the subset against pinned upstream numerical behavior; do not claim full Lensfun support. |
| Profile correction starts off; metadata suggests candidates, a person or API client explicitly selects one | Camera JPEGs may already be corrected, and ambiguous metadata is not evidence of an uncorrected lens. Never silently apply a best fuzzy match. |
| Manual two-axis projective adjustment, neutral at zero; straighten and rotation remain in the existing tools | No automatic Upright, line detection, guided quadrilaterals, arbitrary homographies, fisheye projection conversion, anamorphic correction or free scaling in this delivery. |
| Keep the pre-crop canvas dimensions; automatically zoom each warp stage just enough to cover it, with combined scale at most 4× | Opaque frames and the existing no-empty-corners crop contract remain useful. This deliberately sacrifices edge field of view; the applied scale is visible in UI/API. Refuse a mapping that cannot cover the canvas within the bound. |
| Distortion only from profiles | Lateral CA, optical vignetting, defringing, manual distortion coefficients, profile authoring and external profile imports are later scope. The artistic post-crop vignette remains distinct. Required embedded DNG corrections stay mandatory. |

The dependency choice is based on the [Lensfun project and licensing](https://github.com/lensfun/lensfun/blob/v0.3.4/README.md), its [distortion models](https://lensfun.github.io/manual/v0.3.2/group__Lens.html) and [correction order and inverse lookup](https://lensfun.github.io/manual/latest/corrections.html). Lensfun's library is LGPL-3.0 and its database is CC BY-SA 3.0. Bundle the data's license, attribution, provenance and modification notices separately from GPL-3.0-or-later project code. Manual license/native/asset review remains deferred, not passed.

Use the version-1 database shipped with tag `v0.3.4` as the initial reproducible baseline; the packaging task records the resolved commit, exact source-file hashes and a generated-index hash. This deliberately trades newest-camera coverage for a fixed baseline, with no automatic database update. Import only rectilinear records in the supported model subset into a deterministic compact index with existing Rust tooling. Missing X100VI or other profiles remain unsupported, even when RAW decoding supports that camera. Do not import Adobe LCPs or substitute proprietary profile data. Reuse Lensfun's documented normalization and pinned interpolation algorithm, verified by reference vectors from that tag, rather than inventing coefficient interpolation. An unsupported calibration shape stays unavailable with a reason.

## Source interpretation and profile selection

Source preparation reads lens/camera identity, actual focal length, sensor crop factor, active/default area and optical provenance from the already verified encoded snapshot. Never reread EXIF from the owner thread. Use a typed, immutable per-operation correction ledger: `distortion`, `lateral-ca`, `shading`, each carrying `applied`, `known-unapplied` or `unknown`, plus provider, stage, operation/version, interpretation identity and coordinate domain where known. Absence of metadata means unknown, not uncorrected. Preserve the RAW adapter's existing correction records; derive this common view from them rather than maintaining two independent truths.

The [Air 2S contract](air2s-dng.md) remains authoritative: GainMap and WarpRectilinear run once, in recorded order, in camera-linear space before the matrix, source crop and EXIF orientation. WarpRectilinear marks distortion as applied (and channel-dependent warps record their chromatic role); GainMap records shading. An embedded distortion marked applied **refuses profile distortion**, including explicit selection, pasted/preset payloads, draft reapply, Restore admission, reopen and export evaluation. A neutral/off lens layer remains legal. Unknown mandatory DNG opcodes still fail source preparation. Disabling the optional lens layer never disables required DNG processing. WB redevelopment starts from retained sensor data and executes the required source correction once; recipe geometry reuses the corrected development. Perspective is legal on that corrected content. Never infer correction eligibility from `.dng`, camera name, an empty opcode list or a lens match alone.

Candidates require compatible camera/sensor coverage, lens identity/mount and actual focal length. Use explicit aliases from the pinned index only; return ambiguous candidates for selection, not fuzzy auto-application. Refuse missing calibration, unknown physical calibration geometry, incompatible aspect/crop coverage or out-of-range focal length; no extrapolation. A missing focal length may be supplied explicitly and is recorded as an override. JPEG or other unknown baked-correction status requires an explicit `assume-uncorrected` selection acknowledgement, exposed equally in UI/API; this cannot override an applied embedded correction. Non-distortion profile fields are never enabled as a side effect.

Persist the resolved model, coefficients, normalization, calibration frame/crop transform, focal length and override provenance, camera/lens keys, database commit/hash, selected calibration record hashes and interpretation marker in the lens payload. Keep this bounded (16 KiB per resolved selection), without image data. Reopening, history and export evaluate that payload without rematching the current database. A removed selection index prevents new selection but does not break an already resolved edit; a missing evaluator/provider or unsupported interpretation fails explicitly. Profile updates affect only new explicit selections. No migration or compatibility shim is introduced.

## Geometry and sampling contract

Content remains the upright prepared source, including mandatory source corrections. Pixel, colour, spatial and mask work remain ahead of geometry. The proposed canonical tail is **orientation (order 0) → lens (2) → perspective (4) → crop/straighten (10) → finish**. Lens and perspective are separate single, non-maskable geometry effects. The host admits their canonical placement; a new warp in an unsupported interleaving is refused without rewriting the stack. Modules own payload validation and compilation; the host owns the mapping primitive, stage composition, admission and execution. `ToolModule::carry` only re-expresses a payload after an exact orientation; it is not the warp evaluator.

Add one geometry mapping primitive with explicit input/output extents, forward and inverse evaluation, valid domain, conservative `reads(rect)` including filter support, and a stable interpretation marker. It has bounded exact, affine, radial and projective steps, not arbitrary executable callbacks or a general graph. Route it through `Processing`, registry stage calculation, compiled `Entry`, byte and linear drivers, point/sample/grid queries, locate/transform, window/proxy planning, analysis and export. No caller invents its own transform.

Coordinates use continuous pixel edges `[0,W] × [0,H]`, centers `(i+0.5,j+0.5)`, x right and y down. Convert profile calibration coordinates into this convention explicitly, including EXIF orientation and any qualified source crop. Lens correction maps ideal output positions back to distorted input positions using the resolved Lensfun model; its forward mapping uses a bounded monotone inverse. Reject non-finite coefficients, folds, singularities and out-of-domain solutions. Never clamp a failed mapping to a plausible pixel.

For perspective, center isotropic coordinates at `(W/2,H/2)` with unit `max(W,H)/2`. The forward homography is `H(u,v)=(u/d,v/d)`, `d=1+h*u+v_parameter*v`; UI Horizontal and Vertical range from −100 to 100, with `h=Horizontal/400` and `v_parameter=Vertical/400`. This is a manual keystone control, not a physical camera-angle estimate. Its inverse uses denominator `1-h*u-v_parameter*v`. Zero is exact identity; a positive horizontal value compresses the right side and a positive vertical value compresses the bottom. Reject denominator crossings and ill-conditioned cases over the whole admitted domain. Freeze orientation conjugation, signs and limits in independent reference fixtures before building controls.

Each lens and perspective step includes its own centered cover scale, producing a fully covered canvas with the dimensions of its input. Its map depends only on that input and its payload: adding perspective never changes an earlier lens stage or its prefix preview. Compose these covered mappings in order, with combined cover scale at most 4×. This can trim more than jointly fitting both warps; stable stage meaning takes priority in this first scope. Coverage must be certified over the entire continuous rectangle, including curved edges and interior extrema; four corners or a sampled grid alone are insufficient. Use polynomial/interval bounds with bounded subdivision and inward safety rounding. Search scale monotonically up to 4× with at most 32 steps; inability to certify within the bounded work is an explicit refusal, not presumed coverage. Bound a certificate to 4096 cells and 256 KiB; expensive certificate construction belongs on a cancellable worker, cached by source interpretation and resolved mapping, with typed preparation needs rather than blocking `draft.set` or the owner. The owner only adopts a matching certificate and validates bounded descriptors. The initial implementation must prove the assumed monotonic coverage search for its supported maps or refuse that map.

Crop then uses its existing rotated-box coordinates and rounding over this covered rectangular stage. Compose its inverse with the preceding mapping and **resample once** into final geometry output, before finish effects. Adjacent new geometric steps describe coordinate operations with one sampling boundary; do not silently fuse previously independent quantizing effects across colour, spatial or other boundaries. If this changes a persisted interpretation, advance the current marker and explicitly refuse unsupported data; do not rewrite it. A tail with only orientation and an integer crop retains the exact copy/shared-buffer path; crop alone retains its current bilinear output.

Use the existing linear-light bilinear kernel initially, four taps with replicated raster-edge indices only after continuous coverage succeeds. JPEG decodes those taps to linear light and quantizes at the geometry boundary; RAW retains signed/highlight values and quantizes only at the terminal boundary. Profile and perspective identity bypass interpolation exactly. Lens plus perspective plus straighten is one interpolation, not three. Bilinear is a deliberate quality limit: do not claim antialiasing under strong minification. Reference/photographic tests must qualify the admitted range; mappings outside the qualified footprint bounds are refused, and a higher-order or footprint-aware kernel is separate follow-up scope. The numerical task freezes those footprint bounds before implementation acceptance.

## Crop, masks and picking

Changing lens or perspective holds the crop's stored rectangle, angle and ID in its fixed pre-crop canvas; the content under that rectangle changes as intended. It does not silently refit or accumulate trims. Both cover scales are computed before crop, so an existing crop cannot hide otherwise uncovered areas to admit a stronger warp. Crop reset restores the covered corrected canvas, not the uncorrected source; lens/perspective reset affects only that module. Lens/perspective sweeps derive every candidate from the same draft base, so returning to the start restores identical output. Crop's input-stage preview includes the new geometry, and its straightening preview remains labelled display filtering until commit. Quarter-turns/reflections carry lens calibration, perspective and crop in one transaction by conjugating their mappings; existing subpixel crop-carry limits still apply.

Masks retain their original normalized content positions and height-based sizes. Pixel replacements, range-mask sampling and neutral picking still address the same content stage. Applying or removing a warp never rewrites mask/stroke coordinates. The artistic finish vignette evaluates the final cropped dimensions. Compare with `keep_geometry` carries the displayed entry's whole geometry, including its resolved profile and perspective; uncropped Original retains mandatory source corrections but no optional warp.

Replace the affine-only `render.transform` result with a schema-described, revision-stamped bounded mapping descriptor (exact/affine fast path or nonlinear step chain, dimensions and domain). The desktop uses the core evaluator locally once acquired per gesture; no API round trip per pointer movement and no UI-owned polynomial implementation. `render.locate` maps a rendered center to the content pixel containing it (`floor`), while `render.sample` evaluates the full filter footprint: a locate result is not the sole contributing sample. Reject outside/invalid points explicitly. RAW neutral picking performs this recipe inverse first, then the existing corrected-content-to-sensor query; do not apply the DNG warp again in recipe space.

Warp masks and their coverage overlays through the same map and generation as the photograph. Draw radial/brush outlines and gradients as bounded adaptively subdivided curves (maximum 1024 segments per visible figure, target 0.25 physical-pixel chord error); an affine ellipse is not correct under distortion. On reaching the cap, expose a coarser display approximation without changing the stored mask. Map pointer positions into content before existing path quantization/decimation; preserve capture/sample caps and erase semantics. A geometry commit during an active gesture conflicts its draft; Discard or explicit Reapply refreshes the map and revalidates. A brush merely held between strokes refreshes on the displayed entry change. Crop, pick, overlay and stroke must never mix mapping revisions.

## Modules, API and history

All names in this section are **proposed**, not available commands. Add a small descriptor-backed paged query-choice control for profile selection, with declared query/action bindings and shared parameter validation; existing static enum controls cannot represent a searchable profile database. Do not hard-code profile eligibility in the panel. Register Lens correction and Perspective beside the existing geometry tools, collapsed initially. Lens shows Off, suggested/matching profile choices, explicit selection, focal override when needed, source-correction reason and read-only stage/combined cover scales. Perspective shows Horizontal, Vertical and Reset using generated numeric controls. No disabled future CA/vignetting/Upright widgets.

- `query.lens-profiles`: bounded search/pages (at most 100 records, bounded query text), eligibility, metadata, match reasons, calibration range and embedded-correction status. A lazy immutable index is loaded off the UI/owner threads; result paging is a read-only query.
- `edit.select-lens-profile`: explicit profile key, optional focal override and `assume-uncorrected`; resolve and freeze the calibration before committing. Async preparation uses the existing bounded job mechanisms, revision checks and cancellation, not synchronous database parsing. `edit.reset-lens-profile` makes the layer neutral, retaining its ID; both are semantic non-presettable selection actions in this delivery.
- `edit.set-perspective`: descriptor-defined field patch for `horizontal` and `vertical`, neutral defaults zero; reset uses the same fields. It supports the standard draft lifecycle and field-patch conformance. Mapping preparation must finish before the candidate can commit; stale completions never become a current draft.
- The shared mapping query reports stage and combined cover scales, eligibility/refusal, source/entry/snapshot and draft revisions. `recipe.describe`, `module.list` and `schema.list` describe all new values, source applicability and errors. Source kind alone cannot express embedded-correction eligibility; admission and queries share that rule.

The host owns one atomic action/snapshot per selection or gesture, request deduplication, expected revisions, labels, undo/redo, versions, Restore and reopen. A same-value/reset-at-neutral action is a no-op. A module never edits another module's crop opportunistically. Current-format invalid, unavailable or duplicate-correction payloads remain readable in history and fail evaluation; a stale preview is explicitly unavailable. Failed certification, source changes, cancelled preparation and failed catalog writes cannot partially commit. Profiles are small recipe data, not a new image/artifact store or a user-level setting that can alter old output.

Export freezes the committed entry, source interpretation, resolved profile and mapping with the existing `Evaluation`; it never rematches a profile, exports a draft or takes a proxy. `export.plan` uses compiled output dimensions without rendering. JPEG export shares the exact geometry kernel and existing job lane, destination/alias protection, atomic publication, metadata normalization and temporary-file cleanup. Missing providers, unsupported mappings and duplicate DNG correction fail before publication. Compare the lossless pre-encode render with exact output; JPEG's lossy bytes are not an image oracle.

## Bounded execution and acceptance

The [performance rules](../engineering/performance-rules.md) apply. Profile indexing/certification and pixels run on workers, with cancellation at each bounded chunk/row, immutable results and generation/revision adoption. Reuse the shared pool and latest-job scheduling: one active preview and one replaceable pending preview, existing half-detail motion, exact refinement and 120 ms quiet settlement; exports retain their one-running/four-waiting lane. No private pools, idle polls, frame-sized displacement maps or extra source reads/hashes/developments. Profile index input and compiled storage each cap at 16 MiB, 10,000 records and 256 calibrations per record; excess fails explicitly. Certificate cache caps at 16 entries/4 MiB, with live-job pins charged separately and bounded by admitted jobs.

`reads(rect)` must conservatively include nonlinear extrema and bilinear taps, with bounded subdivision; underestimation is forbidden. Use a full-stage bound only as an explicit budget-checked region fallback. Region output must equal the same slice of a full render. Proxy mappings retain source calibration normalization and derive rounded stages from the same recipe; report approximations and fallback reasons. Exact point work costs bounded mapping plus four taps and the existing spatial-tile exception, never a frame; expensive filtered queries use the point worker. No-op detection compares payloads.

Preserve 512 MiB per RGBA frame and 1.5 GiB per RAW planar buffer, and at most two live segment frames; stream mapping/tap blocks with at most 1 MiB scratch per worker, accounted through `RenderContext`. No new full RGB warp intermediate is justified. Document actual liveness across preview, analysis, source redevelopment and export; existing spatial/colour budgets are targets, not hard process limits. Crop textures, overlays and native staging remain separately accounted limitations. Desktop mutation completion refreshes only changed state and one preview, not history pages; mapping refresh adds no idle timer.

Acceptance requires independent f64 geometry/reference vectors, exact identity and integer cases, full/slice/sample equality in both domains, all eight orientations, curved-edge coverage, invalid/folded mappings and bounded inversion (at most 32 iterations, residual at most 1e-4 source pixel; failure is explicit). Use line grids, off-center crops, impulses, checkerboards, edges, signed RAW/highlights and real rectilinear photographs. Preserve masks, pixel edits, range/neutral picks, history, cancellation and unchanged original hashes. Profile qualification is per camera/lens/focal range, separate from RAW decode support; an unsupported/missing photographic fixture is not a pass.

At integration, background native M4 captures must correlate photo and overlays with source/entry/recipe, mapping and preview generation, UI/API stacks and refusal reasons. At feature completion take before/after release distributions on 24 MP and 60 MP JPEGs and qualified NEF, RAF and the supplied DNG: Fit drag/commit, 100% region pan/refinement, crop opening, brush/pick, simultaneous export, cancellation, RSS and scratch high-water, GPU residency and idle. Measure the new kernel's serial/pool threshold; do not inherit one unmeasured. Record every performance-checklist answer and scoped evidence. Run quick at finished handoffs, rendered at integration and full with an authentic manifest before a milestone claim; unavailable evidence remains incomplete.

Open implementation questions are numerical qualification of the bounded coverage certificate, usable minification range with bilinear, and which camera/lens/focal fixtures qualify the pinned database. Their tests are explicit early tasks, not owner-review requests or permission to broaden scope. Update the current architecture, crop/mask/API specs, feature status and user guide only with the behavior actually delivered.

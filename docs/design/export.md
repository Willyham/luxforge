# JPEG export

Status: implemented and verified on the M4 Mac; the reference export measured in the [performance plan](../specs/performance.md#jpeg-export). The GPU export (stage 4 of [GPU-first](gpu-first.md)) is within the display limit of the reference export on every corpus stack ([the contract](gpu-first.md#the-contract)); measured on the M4 on 2026-10-07, the heavy stack takes 275 ms at 24 MP against the reference's 784 ms and 629 ms at 60 MP against 2,016 ms, the Air 2S masked export stack 457 ms against 1,177 ms, and Basic exposure alone 101 against 85 ms at 24 MP and 190 against 175 ms at 60 MP ([performance](../specs/performance.md#export)). This design implements the accepted export contract in [decisions](../decisions.md#editing-and-storage) and [crop and export](../specs/single-image.md#export): quality 90, a native destination picker suggesting `-edited.jpg`, never overwriting an existing file or a source alias, and optional metadata stripped by default with a Keep metadata option. What this design chose beyond that contract, the encoder included, was accepted by the owner on 2026-09-27 and is listed under [decisions](#decisions).

Export writes one saved entry's render to a new JPEG file: the GPU's where it can draw the stack, held to the reference renderer's within the display limit, and otherwise the reference renderer's exact render. It never touches the original, the catalog's history or any existing file.

## Behavior

1. **Freeze.** `export.jpeg` resolves the target on the catalog owner: the asset, the entry (the current entry unless `entry_id` names another), its snapshot, the recipe hash and the source fingerprint, the same identity an analysis job freezes. It binds the verified prepared source, the registry, the render context, the recipe and the original's capture metadata into one job, in `O(layers)`, and returns the job id. Later commits by any client, including the caller, cannot change a job already accepted. A draft is never exported: only a saved entry can be named.
2. **Render.** The export lane renders that snapshot's output stage — source scale, after orientation, transforms and crop; nothing is resized — through the catalog owner's tile service (`luxforge_core::tiles`) unless the export asks for the reference renderer. On the desktop the service is its GPU tile worker ([GPU previews](gpu-preview.md#qualifying-a-program)): on a device of its own, on the adapter the window draws with, it draws the stage in full-resolution square tiles, each a fresh evaluation of the picture at rest's plan over an anchored window of the source with its halos, at the longest side of 2048, 1024 and 512 pixels whose every tile fits its budget, fixed for the export from the plan and constants alone. A stack whose spatial layers together reach past 64 pixels of halos and leads is drawn in staged sweeps where they fit the same budget ([GPU previews](gpu-preview.md#qualifying-a-program)): every sweep but the last is drawn whole into stage textures of the content stage on the worker's device, and the last sweep's tiles, cut from them, are the bands, which the tests hold bit for bit to the same stack's chained tiles. A row of tiles is one band of the stage's width, handed to the lane in order with at most two waiting (`EXPORT_BANDS_IN_FLIGHT`). The reference renderer renders the whole exact frame through `luxforge_core::render` instead, with the job's cancellation token — a JPEG source in the byte domain and a RAW through the linear domain, converted to 8-bit sRGB once, here — when the export asks for it (`reference: true`), on a host with no GPU provider (`luxforge-json`), and when the service says why the GPU cannot: at once (the launch refused the GPU, no usable adapter or device, the window's adapter not yet named, its tiles past the budget, a plan the GPU cannot draw such as one holding a pixel-stage layer) or part-way (a device lost, a tile the GPU cannot draw). A stream that stops part-way is dropped with its temporary file and the reference renders the export again from nothing, so one file is never two renderers' pixels ([proposals](#proposals-with-recorded-defaults)).
3. **Encode.** libjpeg-turbo writes a baseline JPEG at quality 90, 8-bit sRGB with full-resolution (4:4:4) chroma in one interleaved scan and the standard Huffman tables, always with an embedded sRGB ICC profile ([decision 5](#decisions)). The JFIF header names the density `export.jpeg` was given in pixels per inch, or a unitless 1:1 aspect ratio when it was given none; the desktop gives one on macOS ([decision 7](#decisions)). The encoder reads the reference's frame in place, or takes the GPU's bands as they arrive, 16 rows per call, checking cancellation and reporting progress (rows encoded over the stage's height) between calls; a cancellation stops the GPU's stream between tiles; the encoded bytes stream into the temporary file through libjpeg's buffer of at most 64 KiB rather than into a whole buffer. A libjpeg error fails the export with its message; it never aborts the process.
4. **Metadata.** Off by default: the file carries no EXIF, IPTC or XMP at all, only the JFIF header and the ICC profile. With Keep metadata, one EXIF segment carries the supported fields read from the original (below) plus the structural fields the export itself defines: Orientation 1, ColorSpace sRGB, the output's pixel dimensions and `Software`. No thumbnail, maker note, serial number or preview survives in either mode.
5. **Publish.** The temporary file is created exclusively in the destination directory, written, flushed and synced, then published under the final name without replacement: a hard link that fails if the name exists, or, on a file system without hard links, an exclusive create of the final name and a copy. The temporary file is then removed and the directory synced. Failure or cancellation removes only the temporary file, and a final file this job itself created and did not finish.
6. **Report.** The job ends `ready` with the written path, byte length, dimensions, the metadata fields kept and the renderer that rendered the file (and `batch.export`'s report names each file's renderer the same way, `written: [{asset_id, path, renderer}]`, since one batch may hold files of both renderers), or `failed` or `cancelled` with its reason. A finished export records an event on the owner's log, so every client sees it. Progress is published to the activity board as the phases `rendering`, `encoding` and `writing`; a GPU export draws its tiles while it encodes, so it goes from `rendering` to `encoding` at once, and one the reference renders again after its stream stopped begins `rendering` again.

A stack the host cannot evaluate — an unavailable provider, a refused payload, a missing or changed original — fails the export explicitly with that reason and writes nothing. An unprepared source is answered `preparation-required` with a source job, exactly as `analysis.request` is, and the client asks again once that job ends.

## Destination rules

- The destination is an absolute path whose extension is `.jpg` or `.jpeg`, in either case, whose parent is an existing directory.
- Anything already at the destination path is refused with `conflict`: a file, a directory, a symlink (dangling or not) or a hard link to an original. Because nothing that exists is ever replaced, no path can reach an original or its alias. The check is repeated by the publish step itself, which never replaces, so a file that appears between the request and the write is refused too.
- `export.plan` suggests `<source stem>-edited.jpg` in the original's directory, or `-edited-2.jpg`, `-edited-3.jpg` and so on when that name is taken, reading at most 64 names; past that it suggests no name rather than guessing.

## Keep metadata

The original's EXIF is read once, when the source is prepared, from the bytes the source worker has already read: the JPEG's APP1 segment, the TIFF structure of a NEF or DNG, or the EXIF segment of the JPEG a RAF embeds. The reader is bounded (at most 64 KiB of EXIF for a JPEG, 256 entries per IFD, no IFD visited twice) and never fails a preparation: an unreadable block is simply no metadata. Each retained field must have its expected type and count, or it is dropped; a text field longer than 1 KiB, or blank, is dropped too. `Software` is written as `Luxforge`.

| Group | Fields |
| --- | --- |
| Descriptive | ImageDescription, Artist, Copyright |
| Camera | Make, Model, LensMake, LensModel, LensSpecification |
| Capture | DateTimeOriginal, DateTimeDigitized, OffsetTimeOriginal, OffsetTimeDigitized, SubSecTimeOriginal, ExposureTime, FNumber, ExposureProgram, PhotographicSensitivity, ExposureBiasValue, MeteringMode, Flash, FocalLength, FocalLengthIn35mmFilm |
| GPS | GPSVersionID, GPSLatitudeRef, GPSLatitude, GPSLongitudeRef, GPSLongitude, GPSAltitudeRef, GPSAltitude, GPSTimeStamp, GPSDateStamp, GPSImgDirectionRef, GPSImgDirection |

Everything else is dropped: maker notes, thumbnails, serial numbers, user comments, the original's orientation, dimensions, colour space and profile, and all IPTC and XMP. Private manufacturer metadata is not round-tripped.

## API

| Method | Envelope | Behavior |
| --- | --- | --- |
| `export.plan {asset_id, entry_id?}` | none | `{asset_id, entry_id, snapshot_id, width, height, suggested}`: the output dimensions from the compiled recipe and the suggested destination. Renders nothing |
| `export.jpeg {asset_id, entry_id?, destination, keep_metadata?, pixels_per_inch?, reference?}` | request (`request_id`, `actor`) | Validates the destination, freezes the target and queues one job; `{job_id, status, asset_id, entry_id, snapshot_id, destination, width, height, keep_metadata, pixels_per_inch, reference}`. `reference: true` (default `false`) asks for the reference renderer's export, the CPU render every GPU output is measured against. A retry with the same request id and parameters, `reference` included, is answered from the stored answer and writes no second file |
| `job.read {job_id}` | none | The one job read ([jobs](modules-and-api.md#jobs)): `{job_id, kind: "export", status, progress, asset_id, result?, error?, request_id}`; `progress.message` names the phase (`rendering`, `encoding`, `writing`) and `result` is `{path, bytes, width, height, metadata, renderer}` where `metadata` lists the EXIF fields written and `renderer` names the renderer that rendered the file in the shape `session.state` names the desktop's ([GPU-first](gpu-first.md#the-contract)): `{record: "gpu", reason: null}`, or `{record: "reference", reason}` with why the reference rendered it — `requested` for `reference: true`; `surface-pending` before the desktop has named its window's adapter to its tile worker; `no-adapter`, `refused` (`--no-gpu-render`), `device-lost` (before or during the export) or `adapter-mismatch` for a tile worker that cannot draw; `tiles-budget`; or the GPU plan's or stage's own code, such as `pixel-stage` — and a `null` reason on an owner with no GPU provider, such as `luxforge-json` (`schema.list`'s `renderer` block lists them). Any client may read any export job |
| `job.cancel {job_id}` | none | Cancels an export for every client: a queued job never starts, a running one stops at its next row or block and removes its temporary file, and a finished one is answered unchanged |

Export jobs are records in the catalog owner's one job table and run on its `export` lane: one running and four waiting, refused beyond that with `resource-limit`. The lane never supersedes a job, so a newer export waits instead of replacing an older one, and it never takes the preview or analysis worker. A client that disconnects leaves its exports running.

## Desktop

The title bar's Export button, beside Open, offers **Export JPEG…** and **Export JPEG, keep metadata…**. `Cmd+E` runs the first and `Shift+Cmd+E` the second; the command palette lists both, and a third, **Export reference render…**, which sends `reference: true` through the same chain and is offered nowhere else ([proposal](#proposals-with-recorded-defaults)). Each asks `export.plan` for the suggested name, opens the native save dialog in the original's folder with that name, and sends `export.jpeg` for the displayed entry: the current entry, or the entry being previewed from history. While the Before/After slider is open, export uses its fixed After entry, including when the divider shows only Before. The status bar reads *Exporting DSC_0042-edited.jpg…*, then *Exported DSC_0042-edited.jpg · 6000 × 4000 · 8.4 MB*, or the refusal's reason. The Performance section shows the running export with its phase, as it shows every other long job. The desktop reads the job with `job.read` every 100 ms, from a subscription stream that exists only while the job is queued or running and makes the reads itself, off the update loop (on the executor, where an owner task runs). A read that finds the record as the one before it did costs no message, no update and no view rebuild. The stream sends the job's first record, a record that differs from the last one it sent, the job's end and a failed read, each as one message that takes the full update, which sets the status line and the Export button; after the end or a failed read it reads no more. An export reports no progress, so a running export sends at most its first record, the change to running and its end.

## Bounds and cost

- A GPU export holds no frame: at most three bands of `width × side × 4` bytes — two waiting for the encoder or being assembled (`EXPORT_BANDS_IN_FLIGHT`), and the one it reads — so, for a 10000 × 6000 stage, about 123 MB with 1024-pixel tiles and 246 MB with 2048-pixel ones, against the reference's 240 MB frame; its tiles are drawn on the tile worker's device, two in flight, each band's window of the source uploaded once, and a staged stack's stage textures, at most two of the content stage in the boundary's format, held until the export ends, within its own budget, `GPU_TILE_BUDGET` (2 GiB), less a 256 MiB reserve for reads, and a stage none of whose sides fits is the reference's (`tiles-budget`). The reference's frame is the render's own exact frame, inside the existing 512 MiB evaluated-frame limit, which the encoder reads in place. Either way the encoded bytes stream to the temporary file. A RAW export keeps the source's developed planes alive until it ends, like any render holding them.
- Nothing runs on the catalog owner beyond planning in `O(layers)` and short file-system checks on the destination. The stream is planned on the export lane and drawn on the tile worker's thread, which answers a waiting pixel read before its next export tile; the reference render uses the shared Rayon pool and render context, so it and a preview pace each other rather than one starving the other.
- The reference export's wall time and peak additional memory are recorded in [performance](../specs/performance.md#jpeg-export). The current [GPU comparison](../specs/performance.md#export) covers trivial and heavy JPEG stacks at 24 and 60 MP and the Air 2S masked stack; the tile worker peaks at 2,112.9 MB of its separate 2 GiB budget on the latter. Current export process-memory peaks and native GPU export qualification of every supported RAW camera remain unmeasured.

## Decisions

Accepted by the owner on 2026-09-27:

1. The title-bar Export button opens a two-item menu, with `Cmd+E` and `Shift+Cmd+E`, rather than a dialog or a state-panel section.
2. The desktop exports the displayed entry, including a history preview, and never a draft.
3. The suggested name counts up (`-edited-2.jpg`) when `-edited.jpg` is taken, so the save dialog does not open on a name that will be refused.
4. Keep metadata carries exactly the EXIF fields in the table above and no IPTC or XMP.
5. The encoder is libjpeg-turbo through the pinned `mozjpeg` crate, whose `mozjpeg-sys` bundles the C source and builds it with `cc`, set to its fastest profile: baseline, 4:4:4, one interleaved scan and the standard Huffman tables, which is plain libjpeg-turbo output. Encode only on the M4 at quality 90 and 4:4:4 (shared host, median of 7), it takes 47 to 48 ms at 24 MP and 117 to 121 ms at 60 MP against 111 and 274 ms for the `image` encoder it replaces, and 64 and 105 ms against 149 and 245 ms on Z6 and X100VI renders, at the same file size and PSNR within 0.04 dB; `turbojpeg` 3.1.0 took 43 and 103 ms, and `jpeg-encoder` 0.7.1 110 and 273 ms (61 and 152 ms only at 4:2:0). `jpeg-encoder` was not chosen because it has no NEON path, its speed comes only from point-sampled 4:2:0 chroma, and its optimized and progressive modes buffer the whole image; `turbojpeg` because it needs CMake at build time and encodes a whole in-memory image in one call, with no marker writing or per-strip progress. Optimized Huffman tables would cost about twice the encode time and are not used. aarch64 builds libjpeg-turbo's NEON code through the C compiler; its x86_64 SIMD needs NASM, which is not required, so x86_64 builds the slower portable C path (not yet measured). The same library decodes originals on import ([decisions](../decisions.md#export)), so one crate, `luxforge-jpeg` ([architecture](architecture.md#the-jpeg-codec)), holds the libjpeg session handling and the JPEG container for both: export keeps its policy (quality, 4:4:4, the EXIF payload and the sRGB profile, progress and cancellation) and the crate the error recovery and the markers, among them the ICC profile's APP2 chunks, numbered from 1 as ICC.1 Annex B.4 requires and split across as many markers as a profile takes.
6. The method names `export.plan` and `export.jpeg`; an export job is read and cancelled through the one job API, `job.read` and `job.cancel`, as every other job is.
7. The desktop's export names a density of 72 pixels per inch for each physical pixel of a point on the window's display, 144 on a Retina display (owner, 2026-10-05), so Preview's Actual Size shows one image pixel per physical pixel, as the editor's 100% does; Preview sizes a file that names no density at 72 pixels per inch, twice the editor's 100% on a Retina display. It is macOS's convention, so elsewhere the desktop names none. The core never reads a display: the density is a parameter of `export.jpeg`, absent by default, so an export through the API is the same file on every host.

Owner, 2026-10-04 ([GPU-first](gpu-first.md#decision)):

8. The GPU renders exports where it can, and the reference renderer is the export of a machine without a usable GPU and an explicit option a test or a person asks for (`reference: true`). A GPU export is held to the reference export within the display limit of the stack's class over every pixel ([GPU-first](gpu-first.md#the-contract)). On one machine with one driver it is identical run to run, and across machines an export may differ in the last digit, which is accepted: the same entry exported on two machines, or by the desktop and by `luxforge-json`, need not be the same bytes.

Also accepted: the build follows the accepted export contract rather than the earlier state-panel proposal with presets, resizing, unique names by default and durable export records, which stays unadopted; and the export lane is a lane of the one job table. Not in this build: presets, resizing, other formats, output sharpening and durable export records; each would need its own decision. Each image-changing follow-up needs a reference implementation and a GPU tile-worker export path with warm-up and bounded resources; resizing and output sharpening also need their window, halo and staged-sweep handling. Resized, 16-bit and wide-gamut output each declares a feature-specific tolerance against its reference export and qualifies it on the corpus, rather than inheriting the current 8-bit display limit. Quality 90 and the per-export Keep metadata choice remain the current settings. Batch export (`batch.export`, [the catalog](catalog.md#the-catalog)) writes many photographs through this same export — streamed through the tile service with the same reference fallback — and naming rule into one folder.

## Proposals with recorded defaults

Recorded by the integrator from the stage-4 plan; each stands until the owner records otherwise.

| Question | Default the build runs on | Alternative |
| --- | --- | --- |
| A desktop way to ask for the reference export | A command-palette entry, **Export reference render…**, only; the title bar's menu keeps its two items | A third menu item, or none (API only) |
| A device lost, or a tile the GPU cannot draw, part-way through an export | The export starts again from nothing on the reference renderer, and its result names why; GPU and reference tiles are never mixed in one file | Fail the export |
| The tile worker's budget | `GPU_TILE_BUDGET`, 2 GiB (owner, 2026-10-06), apart from the 2 GiB GPU-preview budget ([GPU previews](gpu-preview.md#qualifying-a-program)) | Charge the tiles to the preview budget |

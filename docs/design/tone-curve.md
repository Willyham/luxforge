## Outcome and scope

One Lightroom-familiar section, **Tone curve**, that shapes the tones of the whole photograph with a point curve a person drags and an agent posts as the same list of points.

In scope for the first version:

- One module, `luxforge.curve`, owning one colour-stage layer with **one composite channel** that maps encoded luminance to encoded luminance, on the supported JPEG subset and every implemented RAW source alike.
- Points a person adds, drags, nudges, types and deletes in the curve editor, with the histogram drawn behind the plot; the same points through `edit.set-curve`; the module's sampled curve through `query.sample-curve`.
- The shared curve editor's gesture and layout changes listed under [module boundaries](#module-boundaries), which every `curve` control receives.
- Masks, presets, Lightroom preset import of the composite point curve, history, undo and redo, with the exact-image and numerical verification every module has.

Out of scope, with no placeholders: per-channel Red, Green and Blue curves, Lightroom's parametric region sliders and region splits, a "linear versus strong contrast" preset menu, dragging the histogram, targeted-adjustment drags on the photograph, non-monotone curves, a second curve editor, the board's full-width plot, dashed reference diagonal, `# Input Output` header and row layout without remove buttons, and any approximate preview. Per-channel curves are the one extension this design keeps a place for: the control kind already carries up to eight channels, so they would be further curve fields of the same layer, evaluated after the composite one, under their own study.

## The module

- **Identity.** Module `luxforge.curve`, title `Tone curve`, hint `A point curve over the photograph's tones`; effect `luxforge.curve.tone` (`CURVE_EFFECT`, exported at the crate root beside `MIXER_EFFECT`), stage `color`, order `5`, `single`, `maskable`; actions `set-curve` (the field patch) and `reset-curve`; query `sample-curve`. The registry lists it directly after Basic, so its section follows Basic in the tools panel, collapsed, where the [workspace tool array](develop-workspace.md#tool-array) places it, and ahead of the planned [Detail](detail.md) section ([panel order](#landing-beside-detail-and-lens)).
- **One field**, `luminance`: kind `curve` with `points_min 2`, `points_max 16`, `monotone true`, no `fixed_x`; default `[[0, 0], [1, 1]]`; `step 0.01`, `precision 2`, no `fine_step` (the Option nudge falls back to a tenth of the step, `0.001`). The host stores exactly the points it was sent, which the `curve` kind has already checked. Its refusals are the kind's generic texts, which name the field: "parameter luminance has an invalid curve point count" and "parameter luminance has an invalid curve point N". A patch that changes nothing is a no-op; `{}` is the canonical neutral payload and `{"luminance": [[0, 0], [1, 1]]}` the same state written differently.
- **One group**, `Tone curve`, whose only control is the curve: `Control::curve("set-curve", [{luminance, "Luminance"}], "Tone curve", "sample-curve")` with `background: histogram`. A stacked module whose controls are one group is drawn headerless: the curve editor sits directly under the band, with no sub-group header, no disclosure, and no Original or Custom caption. One channel declares no channel switch. The band carries the module reset and the active dot.
- **History words.** The field declares `.history("Tone curve")`, so a field patch is labelled by the delivered rule for a curve, its point count: `Tone curve 3 points`. A patch that returns the field to its default is `Reset Tone curve`, and so is `reset-curve`. A recipe row reads `Tone curve 3 points` or `Neutral`.
- **Neutrality** is the framework's rule: the layer is neutral exactly when `luminance` is canonically its default two points. An agent that posts exact on-diagonal points, or a person who double-clicks the drawn identity diagonal (the add snaps to a sample on it, so `x == y` exactly; [controls](#controls-and-interaction)), adds a point that a geometric rule would treat as a no-op whose point vanishes on the next refresh. So an on-diagonal three-point curve is a stored, described, labelled layer. `compile` still maps a curve that is the exact identity map to a colour operation with no units, so such a layer keeps the identity byte path and shares the source allocation. The exact identity test is, in `f64`, `points[0] == [0.0, 0.0] && points[n - 1] == [1.0, 1.0] && every x == y`, so `-0.0` equals `0.0`. Any other curve compiles to exactly one unit.
- **Points are a function of the encoded tone.** The plot's `x` axis is the sRGB-encoded luminance the histogram is drawn in, so the histogram background and the curve share one axis by construction, and `y` is the encoded output luminance. This is the same domain the Basic tone controls act in; the curve's `x = 0.5` is Basic's contrast pivot.

## Placement

The delivered host places a new layer by its effect's stage and declared order and never moves an existing layer ([registry](modules-and-api.md#registry)). Basic declares order `0` and the mixer `10` in the colour stage; the curve declares **order `5`**, so a curve layer always lands after the Basic layer and before the mixer layer whichever was touched first, and a stack stored in another order renders in its stored order. Within a mask the same rule places the masked curve layer after the masked Basic layer and before the masked mixer layer, and masked curve layers follow the global one in mask-list order ([mask order](masking.md#order)).

Why after Basic: the curve finishes the global tone shaping Basic starts, in the same encoded domain, so the composition is one monotone luminance map a person reads from the plot. Why before the mixer: the mixer addresses the colours of the toned photograph, and its order-10 place is kept. Why not after the mixer: a luminance curve after Oklab hue and chroma changes would still be hue-preserving, but the panel would then read top to bottom in an order the pipeline did not follow. The neutral picker samples the stage the Basic layer receives, so the curve never sits in front of it.

Canonical stack for a fully edited photograph: source (RAW only) → pixel proof → Basic → **Tone curve** → mixer → presence → orientation → crop → vignette.

## Processing contract

The unit is one `PointwiseColor` in the layer's colour operation, evaluated in the existing run with no new quantization boundary and the run's single clamp at the end: values outside `[0, 1]` and negative values are preserved, nothing is clamped inside the unit, alpha is never touched, and a non-finite value fails the render or sample as every colour unit's does. Per pixel:

```text
L        = 0.2126*R + 0.7152*G + 0.0722*B        Rec. 709 luminance on linear sRGB
x        = encode(L)                             the sRGB OETF, analytically continued (basic-tone.md)
y        = C(x)                                  the curve, below
L_out    = decode(y)                             the inverse, continued the same way
L_floor  = decode(C(0)) = decode(y_0)            the curve's black level, once per curve
|L| <  1e-6:  rgb_out = rgb + (L_out - L)                        the additive near-black rule
|L| >= 1e-6:  rgb_out = L_floor + rgb * ((L_out - L_floor) / L)  the floor-subtracted ratio
```

`encode`, `decode`, the luminance weights and the `1e-6` threshold are the Basic tone contract's: production uses `colour::srgb::{encode_f32, decode_f32}`, `colour::luma::rec709` and `colour::luma::NEAR_BLACK` from `crates/luxforge-core/src/colour.rs` and never restates the transfer function. The reconstruction is the frozen one applied to the floor-subtracted output: both branches of the frozen rule act on `L_out - L_floor` in place of `L_out`, and `L_floor` is added back to every channel. The additive branch simplifies to the frozen additive rule unchanged. Production implements it as `colour::luma::reconstruct_over_floor(rgb, l_in, l_out, l_floor)`, which calls `colour::luma::reconstruct` unchanged when `l_floor == 0.0`.

Properties of the reconstruction, proved by the study and then by production tests:

- **The frozen rule when the black is not lifted.** When `y_0 = 0`, `L_floor = decode(0) = 0` exactly, and the unit is the frozen luminance-ratio reconstruction bit for bit (`reconstruct_over_floor` calls `reconstruct`). Every curve whose first point has output `0` is in this case.
- **Greys stay grey.** Three equal channels go through the same operations and stay bit-identical to each other.
- **A non-negative scale.** For `|L| >= 1e-6`, `k = (L_out - L_floor) / L >= 0` for every admissible curve: `C` is non-decreasing with `C(0) = y_0`, and `encode` and `decode` are increasing with `encode(0) = 0`, so `L_out - L_floor` has the sign of `L` or is zero. No channel's offset from the floor grey changes sign, and no hue inverts.
- **Hue.** When `y_0 = 0` the output is `k · rgb` with `k >= 0`: Oklab hue is exactly preserved, because a uniform non-negative scale of linear RGB scales `a` and `b` equally, and relative saturation (chroma over luminance) is preserved; the study measures at most `1.9e-11` degrees of hue and `2.2e-13` of relative saturation, which is `f64` rounding. When `y_0 > 0` the output is the floor grey plus a non-negative scale of the input: the deep shadows desaturate toward that grey, as a matte curve does, and Oklab hue there is not claimed exact.
- **Bounded at the threshold.** At `|L| = 1e-6` the two branches differ by `(k - 1) · (rgb - L)`, and `k` near black is bounded by the curve's slope there, so the switch adds no visible step. The frozen ratio under a lifted black would scale by `L_out / L`, which grows as `L_floor / L`.

This reconstruction is the one way the composite differs from a per-channel curve, which colours greys and shifts hues; the difference is stated to people in the user guide and the channel choice stays a [proposal](#proposals-with-recorded-defaults).

### The curve `C`

Given the checked points `(x_0, y_0) … (x_{n-1}, y_{n-1})`, `n` in `2..=16`, `x` strictly increasing, `y` non-decreasing:

1. **On the span `[x_0, x_{n-1}]`: a monotone piecewise-cubic Hermite interpolant** (PCHIP, Fritsch–Carlson monotonicity with Fritsch–Butland weighted-harmonic-mean knot slopes), the construction the [mixer's hue warp](mixer-study.md#the-warp) already froze, here open rather than periodic. With `h_i = x_{i+1} - x_i` and secants `Δ_i = (y_{i+1} - y_i) / h_i`, all in `f64`:
   - interior knot slope `d_i = (w_1 + w_2) / (w_1 / Δ_{i-1} + w_2 / Δ_i)` with `w_1 = 2 h_i + h_{i-1}` and `w_2 = h_i + 2 h_{i-1}`, and `d_i = 0` when either adjacent secant is `0`;
   - end slopes `d_0 = Δ_0` and `d_{n-1} = Δ_{n-2}`;
   - **a non-finite secant** (only possible for a subnormal `h_i`): segment `i` is linear, `C = y_i + (y_{i+1} - y_i) · t`, and `Δ_i` enters its neighbours' harmonic means as `+∞` (its term `w / Δ_i` is `0`). A knot slope with no finite adjacent secant, and an end slope taken from a non-finite secant, belong only to linear segments, are never evaluated and are stored as `0`;
   - on segment `i`, with `t = (x - x_i) / h_i`: `C(x) = y_i h00(t) + h_i d_i h10(t) + y_{i+1} h01(t) + h_i d_{i+1} h11(t)`, the cubic Hermite basis, and a segment whose two `y` are equal is exactly constant by a direct rule rather than by evaluating the basis.
2. **Inside `[0, 1]` but outside the span: held flat** at `y_0` below `x_0` and at `y_{n-1}` above `x_{n-1}`, the rule the controls proof states and the one a moved endpoint means in a curve editor (an endpoint dragged inward clips the tones beyond it). So `C(0) = y_0` and `C(1) = y_{n-1}` for every point list.
3. **Outside `[0, 1]`: a unit-slope extension**, `C(x) = y_0 + x` for `x < 0` and `C(x) = y_{n-1} + (x - 1)` for `x > 1`. Exposure and white balance run before this unit and routinely push encoded luminance past `1` on the JPEG path, and scene-linear RAW planes carry values above white until the terminal boundary. Holding flat there would collapse every over-white value to one output, which the mixer and Presence downstream would then see as a plateau; a tangent extension would amplify them by the end segment's slope, which the tone study measured and rejected for its own family. Slope one keeps them finite, keeps their ordering, keeps them apart from each other by exactly the distance they had, and is continuous with the curve at the boundary. For the identity curve it is the identity.

Properties, each proved by the study and then by production tests rather than asserted:

- **Interpolation.** `C(x_i) = y_i` at every knot.
- **Monotone.** `C` is non-decreasing on the whole real line for every admissible point list: on each segment both Hermite slopes lie in `[0, 3 · min(Δ_{i-1}, Δ_i)]` (the harmonic mean is at most three times the smaller secant, the end slopes are exactly one secant), which is inside the Fritsch–Carlson monotone region; linear segments, the flat holds and the unit-slope tails are monotone by inspection; and the pieces meet continuously. A non-decreasing curve on a non-decreasing luminance never inverts two tones, so the composition with Basic's monotone curve is monotone. Strict positivity is not claimed: a person may draw a flat segment, and it is exactly flat.
- **No overshoot.** On segment `i`, `C(x)` lies within `[y_i, y_{i+1}]`, so a curve never leaves `[0, 1]` for an input in `[0, 1]`, whatever the points.
- **Smooth.** `C` is C1 across every interior knot whose two segments are cubic (the two segments share `d_i`), which is what keeps a gradient from showing a crease at a point; it is only C0 at the span's ends where it meets a flat hold, at `0` and `1` where it meets the tails, and beside a linear segment, and that is stated.
- **Identity.** Points all on the diagonal with the span covering `[0, 1]` give slopes exactly `1` and `C(x) = x` to within `f64` rounding (at most `3.3e-16` over the grid for 1,000 random on-diagonal lists); `Interpolant::value` returns `x` exactly for an exact identity point list, and production compiles that case to no unit at all.
- **Two points are an affine map.** `[[0, a], [1, b]]` is `C(x) = a + (b - a) x`: the black and white points, the remap Basic's Whites and Blacks perform, so an agent can post one without a slider. The pixels agree with Basic's where Basic's black is not lifted, within `8.0e-16` relative over 79,808 pixels in the study ([study](#reference-study-and-fixture)); a lifted black takes the floor-subtracted reconstruction here and the frozen ratio in Basic.
- **Finite.** Every finite input and every admissible point list gives finite knot slopes and a finite `C(x)`, the subnormal-spacing case included: a non-finite secant makes its segment linear, and every division is by a strictly positive `h_i` or a strictly positive harmonic-mean denominator. The sRGB encode and decode are finite on the tested `[-0.5, 2.0]` extended domain, as the tone study proved.

Why this interpolant and not another, measured by the study on the same point sets over a 4001-point grid and an 8-bit ramp: a natural cubic spline and a Catmull–Rom spline overshoot between points and can leave `[0, 1]` or invert tones, so a person could not trust that the plot's monotone points give a monotone map; linear interpolation is monotone but only C0, and its slope steps at every knot show as creases on a smooth gradient; Akima is not guaranteed monotone. PCHIP is the smallest construction that is shape-preserving, local (moving one point changes at most the two segments either side plus their neighbours' slopes) and already frozen in this repository. Its known cost is that its slope at a knot is bounded by the smaller neighbouring secant, so a curve rises a little less steeply into a sharp corner than a free spline would draw; that is the trade for never overshooting.

What `curve_study_figures` prints for the comparison, with the flat holds and unit-slope tails the same for every candidate and a step down counted as an inversion only beyond eight ulps of the value:

| Candidate | Named sets leaving `[0, 1]` (largest overshoot) | Named sets inverting | 10,000 random lists leaving `[0, 1]` / inverting | Largest slope jump at a knot, steep sets aside |
| --- | --- | --- | --- | --- |
| Linear | 0 | 0 | 0 / 0 | `1.80` (`wiggle-16`); `0.40` on `midtone-lift`, `s-curve` and `inverse-s` |
| Natural cubic | 4, three by overshoot (`38.4` on `steep-600`, `1.9e6` on `collapsed-1e-8`, `2.2e13` on `collapsed-4eps`) and `subnormal` non-finite | 6: those four, `wiggle-16` and `flat-pair` | 4,930 (largest `4.8e4`) / 8,993 | `4.4e-16` |
| Catmull–Rom | 2 (`0.147` on `steep-600`, `0.148` on `subnormal`, which also goes non-finite) | 4: those two, `wiggle-16` and `flat-pair` | 684 (largest `0.134`) / 8,578 | `0` |
| PCHIP | 0 | 0 | 0 / 0 | `0`; only `subnormal`'s linear segment meets its neighbour with a jump |

Inside a segment the free splines also leave the segment's own knot values, by `0.0132` (natural cubic) and `0.0046` (Catmull–Rom) on `wiggle-16` and `0.0109` and `0.0250` on `flat-pair`, so a flat segment is not flat under either. On the 512-pixel 8-bit ramp (input code `round(k · 255 / 511)`, the curve's output quantized) the candidates use nearly the same codes where none overshoots, 230 or 231 on `midtone-lift`, `s-curve` and `inverse-s` with a longest run of 4, so linear's cost is the crease, not lost codes; on `wiggle-16` linear and PCHIP use 128 codes and the free splines 140 and 144, the extra codes coming from their excursions.

### Production evaluation

`ToneCurve::new` builds everything in `f64` and casts each value to `f32` once:

- per knot, `x_i` (as `x32`) and per segment `inv_h_i = 1 / h_i`, cast saturating at `f32::MAX`;
- per segment, the `t`-form coefficients `c0 = y_i`, `c1 = h_i d_i`, `c2 = 3 Δy − 2 h_i d_i − h_i d_{i+1}`, `c3 = −2 Δy + h_i d_i + h_i d_{i+1}` with `Δy = y_{i+1} − y_i`; a flat segment has `c1 = c2 = c3 = 0`, and a linear segment (non-finite secant) has `c1 = Δy`, `c2 = c3 = 0`;
- `y_0`, `y_{n-1}` and `L_floor = decode(y_0)`.

Per pixel, the curve is evaluated by the first rule that applies:

1. `x < 0`: `y_0 + x`;
2. `x > 1`: `y_{n-1} + (x − 1)`;
3. `x <= x32[0]`: `y_0`;
4. `x >= x32[n−1]`: `y_{n-1}`;
5. otherwise `i = partition_point(x32, |k| k <= x) − 1`, clamped to `0..=n−2`; `t = ((x − x32[i]) * inv_h[i]).clamp(0.0, 1.0)`; `C = c0 + t · (c1 + t · (c2 + t · c3))`.

`h` and `1 / h` are never computed in `f32`, and no local-`u` polynomial is used: knots closer than an `f32` step collapse to one `f32` value, and the rules above then pick the later segment, give a finite `t` and keep `C` within the segment's knot values up to `f32` rounding (every `|c| <= 9`). `is_finite` checks every cast coefficient; `describe` writes `luxforge.curve.tone` and the `f64` points with the shortest round-trip form. The unit ignores the row coordinates.

### Cost

Per pixel, in `f32`: the luminance, one `encode`, a segment search over at most sixteen knots (four comparisons), one cubic in `t` by Horner, one `decode` and the reconstruction's subtract, divide and three multiply-adds. That is the Basic tone unit's own work minus its `exp`. The recorded cost of Exposure plus the three composed Tone stages over the colour baseline is about 48 ms (24 MP) and 127 ms (60 MP) on the `editor-performance` crop-fit stack, whose output stage is 3695 × 2077 and 5542 × 3116 ([performance](../specs/performance.md#core-render-one-run-30-samples-per-recipe)), not a full frame. One curve unit is expected to cost less on the same stack; the plan measures it with a `tone_curve_layer()` row there rather than promising it. No lookup table: a 4096-entry table with linear interpolation can miss a steep segment's cubic by more than the frozen tolerance, and the direct cubic is already cheap. The unit runs in the existing colour run, so it takes the colour pass's measured parallel threshold, the row-chunk scratch budget and the masked-run blend as delivered; it adds no pass kind, no allocation that scales with the image, no timer and no hop on the input path.

### Sample query and point queries

`query.sample-curve` takes `asset_id`, an optional `entry_id`, an optional `mask` (the host adds it for a maskable module) and an optional `luminance`. With `luminance` it returns `{"points": [[i / 256, C(i / 256)] for i in 0..=256]}`, computed by `Interpolant::value` in `f64`, the construction production casts its coefficients from, so the plot shows the curve the pixels receive. Without `luminance` it is refused with "sample-curve requires the luminance points". `entry_id` and `mask` are accepted and select nothing: the answer depends only on the submitted points. It runs on the catalog owner, reads no pixel and allocates no frame (the answer is a small JSON value); it is answered for the entry the desktop shows, and only while the curve is on screen, as the delivered sampling rule says. If query routing becomes per-query (a pixel-reading query routed to a point worker), `sample-curve` is classified explicitly as an owner query.

`render.sample`, the neutral picker and every other point query keep their `O(layers)` contract, unless a spatial (restoration) layer precedes the sampled stage: the unit is pointwise, and no-op detection and validation compare payloads, never pixels.

## Frozen tolerance

Fixture inputs are `f32`-representable linear triples, so the tolerance measures the unit and not the input cast.

- **Forward tolerance.** For a point set whose steepest slope `s_max` (the largest value of `C'` on any segment, computed exactly from each segment's quadratic derivative by `CurvePoints::peak_slope`) is at most `64`, production versus the `f64` reference is within **`1e-5 + 1e-5 × |reference|`** per channel in linear float, and at most one output code after quantization: the Basic tone tolerance.
- **Backward tolerance.** For a steeper set, the `f32` luminance and encode errors (about `1e-7` relative) are amplified by the slope and the forward bound does not hold. Production must then lie, per channel, within the range of the reference evaluated with the encoded input perturbed to `x · (1 − 2^-20)` and `x · (1 + 2^-20)` (`luxforge_reference::curve::curve_pixel_with_input_error`), widened by the forward tolerance; and the unit must stay finite and monotone on the grey ramp. The study measures that band, the largest change of a grey pixel from a `2^-20` relative error in its encoded input over 20,001 encoded inputs in `[0, 1]` plus 1,025 per segment: at most `0.26` forward tolerances on every named set of peak slope up to `2.755` (`wiggle-16`), `26.1` on `steep-600` (`3.99e-4` linear) and `1.6e4` on both collapsed sets (`0.186` linear).

The bound is on the peak slope rather than the knot slopes: a steep segment between two flat ones has both knot slopes `0` and a peak slope of one and a half times its secant. Production's largest deviation of each class over the fixture is recorded with the module, as the tone and mixer studies did for theirs. As `production_matches_the_frozen_curve_fixture_within_tolerance` measures it over the 1,204 cases: in the forward class, `7.6e-7` in linear light (`0.014` forward tolerances, `wiggle-16/ramp-63`); in the backward class, `4.8e-7` from the unperturbed reference (`steep-600/ramp-63`) and no channel outside the backward band. Through `render`, every channel is at most one code from the reference's code: on the RAW linear path over the 1,204 cases, and on the byte path over every grey code and a colour cube in steps of 51 under each named set.

## Controls and interaction

A point drag drafts through `draft.begin`, `draft.set` and `draft.commit`, previews each accepted value with the proxy following motion and the exact phase and histogram settling after the shared quiet policy or release, and commits once on release; Escape cancels; arrow keys nudge the selected point by `0.01`, Shift by ten times and Option by a tenth, each coordinate rounded through `f32`; right-click copies the exact `edit.set-curve` request. Adding, removing and typing commit at once, as the desktop already does for every curve. The widget's changes, shared by every `curve` control:

- **Click classification.** The widget classifies a left press with `iced::mouse::Click::new(point, mouse::Button::Left, state.last_click)`, as `widgets/double_click.rs` does, and removes its own `DOUBLE_CLICK` (350 ms, 9 px) in favour of iced's thresholds. `Kind::Single` on a point selects it; `Kind::Double` on a point publishes `Remove(index)` and nothing else; `Kind::Double` away from a point publishes `Add`; `Kind::Triple` publishes nothing.
- **Drag slop.** `const DRAG_SLOP: f32 = 3.0`: after a press on a point, no `Move` is published until the pointer has moved more than 3 px from the press. A press and release without motion, or with jitter inside the slop, opens no draft and commits nothing, so the first press of a double-click on a point never drafts a move.
- **Where an add lands.** When the pointer is within `CURVE_SNAP_RADIUS = 4.0` px of the drawn sampled curve, the widget publishes `Add` at the nearest sample, `[k / 256, C(k / 256)]` as the host supplied it, so a double-click on the drawn line adds a point on the curve (exactly `x == y` on the identity). Otherwise it publishes the pointer's fraction, and the desktop clamps `y` between the neighbours as delivered. An add at an existing point's `x` is ignored as delivered.
- **Selection.** After an add the new point's sorted index is selected; after a remove the selection is cleared, so the next nudge or Delete acts on the point the person sees selected.
- **Refusals, with status text** rather than a silent return: past the maximum, "`{label}` holds at most `{max}` points" ("Tone curve holds at most 16 points"); below the minimum, "`{label}` needs at least `{min}` points"; removing the first or last point by double-click or Delete, "The end points move but are not removed" (the API is unchanged and may remove them).
- **The label line.** A curve control that is the only control of a headerless group draws no label line (`CurveControl::label_shown` is false), so the section does not print "Tone curve" twice.

**The point list is closed until opened.** Under the plot a one-line hint, "Double-click to add a point, or on one to remove it", is shown when points can be added and removed (no `fixed_x`, and `points_min != points_max`). Below it a **Points** disclosure row, a button styled like `sub_group_header` with a chevron, "Points" and the right-aligned count (`4 of 16`); the numeric list of input and output fields appears only after the person opens it. The rows keep their delivered layout: X and Y captions and a remove button per row. Each Enter commits one coordinate, validated against the current points, so a typed value that would make the curve decreasing is refused with the kind's text until the neighbouring point is typed first. Open or closed is view state: `CurveUi::points_open` (default closed), keyed by control like the channel switch, shared by the global and masked targets, kept while the window is open and not cleared by a sample refresh or a photo change. Opening sends no request; closing drops that control's uncommitted typed text. The widget reports it as `CurveEditorEvent::Points(bool)`, and its model carries `points_open`, `points_max` and `hint: Option<String>`. The drag's draft bar and the status bar carry the moving point's values, so a closed list hides nothing a gesture needs; an agent posts the same points through `edit.set-curve` either way.

The plot keeps its delivered fixed 200 × 200 px size and draws its reference diagonal only when the curve is the identity. The histogram drawn behind the plot is the inspector's current one; it is a hint and edits nothing. The band's dot shows a non-neutral layer; a single-group section has no Original or Custom caption.

## Masks

The effect declares `maskable`, which is the whole of what a module does to inherit masking: the host adds the `mask` target to both actions and the query, places masked curve layers after the global one in mask-list order, blends the masked run against its own input in linear light before the run's clamp, keeps `render.sample` equal to the rendered byte through it, and shows the Masks panel's scope chip on the section. A masked curve is a colour layer, so it does not count toward the masked-spatial cap `MAX_MASKED_SPATIAL_LAYERS` that masked Presence and masked Detail share. What the plan verifies is that a masked curve behaves as the masked Basic layer does: one layer per mask target, two refused by name, a curve layer bound beside the mixer on one mask and listed in placement order, its order kept through `mask.reorder` and `mask.duplicate`, `render.sample` equal to the rendered byte, the drag through a mask target, the scope chip and the coverage overlay reading the curve layer's input (`mask::commands::input_layer_index`); and that the [masking design](masking.md#how-a-mask-reaches-an-effect) lists the curve among the maskable effects. The masked blend itself is effect-independent and already proved by `render/mask_tests.rs`.

## Limitations

- **Global and pointwise.** Two tones map the same way wherever they are; the curve cannot lift a backlit subject without lifting the sky's equal tones, exactly the [Basic tone limitation](basic-tone.md#limitations).
- **Composite only.** No per-channel colour work: an S-curve does not increase saturation as a per-channel curve would, and a colour cast cannot be corrected here. Hue and relative saturation are preserved when the black is not lifted.
- **A lifted black desaturates.** With `y_0 > 0` the floor grey is added to every channel: the deep shadows move toward grey, and a saturated mid-tone shifts by a few codes against the plain ratio (the study renders `(0.2, 0.05, 0.02)` under `lifted-black` to codes 146/79/55, against 149/78/49 under the plain ratio). This is the matte look, and it is what keeps shadow noise from turning into coloured speckle.
- **Basic's Blacks is unchanged.** Basic's lifted black still uses the frozen ratio, which turns shadow noise into coloured speckle (on the study's noise field, Blacks +100 puts 61.6% of pixels above 40 codes of channel spread and its 99th percentile at 255), so the same lift made with Blacks and with the curve renders differently in the deep shadows. Whether Basic adopts the floor-subtracted ratio is a separate follow-up, outside this plan.
- **Steep segments.** A segment steeper than a slope of 64 is held to the backward tolerance, not the forward one; the desktop's drag clamp can place two points `4 · f64::EPSILON` apart, and such a curve renders as a step.
- **Monotone only.** The host refuses a decreasing `y`, so solarization and other inversions are not expressible; a flat segment is expressible and discards the tones it covers.
- **Bounded by the points.** Sixteen points; a Lightroom curve with more is refused at import rather than decimated.
- **No parametric mode.** Lightroom's region sliders are not built; Basic's Highlights, Shadows, Whites and Blacks already cover that shape of adjustment.

## Decided

- **Reconstruction below black** (owner, 2026-09-30). The curve unit uses the floor-subtracted ratio, `rgb_out = L_floor + rgb · (L_out − L_floor) / L` with `L_floor = decode(C(0))`, and the additive near-black rule `rgb_out = rgb + (L_out − L)` below `|L| < 1e-6`; it is identical to the frozen rule when `C(0) = 0`. Basic's Blacks is unchanged in this work; a separate follow-up decides it.

## Proposals with recorded defaults

Recommendations for the owner, recorded as proposals until decided. The plan runs on the defaults.

| Question | Default the plan runs on | Alternatives |
| --- | --- | --- |
| What the composite channel acts on | Encoded luminance with the reconstruction above: hue-preserving where the black is not lifted, one axis shared with the histogram, the frozen Basic vocabulary reused | Lightroom's per-channel composite, which applies one curve to R, G and B and so saturates on an S-curve; or both, as two channels of the one control |
| Channels | One, `luminance` | Red, Green and Blue curves as further channels of the same control, evaluated after the composite one, under their own study and per-channel arithmetic |
| Order in the colour run | `5`: after Basic, before the mixer | After the mixer (order above 10) |
| Section place | After Basic, before Detail and Presence, collapsed | After the mixer |
| Endpoints | Free: `x` and `y` of every point move, with the curve held flat inside `[0, 1]` beyond the span | Endpoints fixed at `x = 0` and `x = 1` with only their `y` movable, which needs a validation hook the field-patch framework does not have |
| Behaviour past white and below black | The unit-slope tail | Flat (collapses over-white values) or tangent (amplifies them) |
| Point limit | 16 | The kind's maximum, 32 |
| Neutrality | The framework rule (points equal the default), with the exact identity map compiled to nothing | A geometric rule (any identity map is neutral), which makes a point added on the diagonal a no-op that vanishes |
| Lightroom `ToneCurvePV2012` | Transferred onto the luminance curve as a value, refused above sixteen points or when not monotone | Refused outright as a different rendering |
| A Lightroom identity `ToneCurvePV2012` | Mapped: transferred as written, so it resets the curve, as every mapped control transfers its neutral value | Neutral, reported among the settings Luxforge has no tool for |
| Interpolant | Open PCHIP with harmonic-mean slopes and secant end slopes | Linear (creases), a free cubic spline (overshoots), or PCHIP with three-point end slopes |
| Where a desktop double-click adds a point | Within 4 px of the drawn curve, at the nearest sample `x = k / 256` with the sample's `y`; otherwise at the pointer, `y` clamped between the neighbours | Always at the pointer |
| Removing an end point from the desktop | Refused with "The end points move but are not removed"; the API may remove it | Allowed, which flattens every tone below (or above) the next point |
| Point-list layout | The delivered rows (X and Y captions, a remove button per row) with only the hint and the Points disclosure added; the plot keeps its fixed size | The board's full-width plot, dashed reference diagonal, `# Input Output` header and rows without remove buttons |

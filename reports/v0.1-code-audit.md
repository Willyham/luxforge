# v0.1 code and architecture audit

Audit date: 2026-10-13. Baseline: `ea114ed90b334bf52e478fa0d5d194f5ec673365`.
The fixes are the working-tree changes on `t3code/release-readiness-audit`.

**Recommendation: do not qualify this candidate for release yet.** The permanent-deletion retry
defect below is a release blocker. Native rendering, signing, clean-install and corpus gates also
remain open. This audit supplies bounded fixes and specific follow-up work; it is not a release
acceptance or a manual third-party source/licence audit.

## Scope and method

Astra coordinated the review and validation; Luna inventoried structure, dependencies and apparent
dead code; Sol reviewed catalog/history, desktop orchestration, image/GPU/codec paths,
network/update/capability boundaries, release tooling, inference/merges and platform/settings
paths in successive waves. Builds ran serially through `tools/cargo-cached`.

The inventory covers the 23 first-party crates, xtask and its CLI, the standalone usage-ingest
service, workflows, packaging, tools and research probes. Detailed review followed state and
ownership boundaries, error paths, retry/cancellation semantics, source preservation, bounded work
and existing acceptance contracts. Roughly 960,000 Rust source lines include tests and evidence
support; this is a risk-driven repository-wide audit, not a claim that every line was manually
proved correct. Vendored codec/model implementations, malicious-file fuzzing/sanitizers, native
macOS/Windows execution and authentic photographic corpus qualification were not completed here.

The host is headless Linux. Rust 1.94.0 was selected explicitly in PATH because the host's mise
shim selected 1.99 despite the repository pin. The initial doctor found no graphical session.
Headless functional evidence cannot substitute for the owner's native M4 GPU evidence.

## Open findings and decisions

### O01 — P1: permanent deletion and no-op navigation are unsafe to retry after cache loss

The owner's request cache holds 256 successful answers / 8 MiB and is lost on restart. Normal
asset-history mutations durably store input hashes and answers, but catalog-only operations do
not all do so. A no-op `library.undo` can later undo a new pick when the identical envelope is
retried. More seriously, retrying an earlier `catalog.empty-removed` can permanently delete the
history of photographs removed after that first request. Original files are untouched. The
deletion method requires permission authority; this is a trusted-client correctness defect,
not an authorization bypass. Recorded library changes also lack durable input matching, so a
changed payload after restart can receive an earlier success; batch retry matching has a related
gap. Cache eviction can expose these problems without restarting.

**Worth fixing before release; deliberately not patched with another ephemeral cache.** Add a
catalog-level durable request identity/input-hash/result record in the same transaction as each
mutation, including no-ops and deletion. The existing asset request table has an asset foreign
key and cannot safely represent catalog-only deletion. Review current catalog/API shape and
format refusal, batch target freezing and job result semantics together; do not invent fake
assets or hide records in unrelated metadata. Test restart and eviction, exact retries, changed
inputs, later removal of another photo, rollback, and unchanged originals.

**Public API reproduction: confirmed.** With the built `luxforge-json`, the first Undo answered
`no-op`; the identical request after a later pick and restart answered `applied` and removed the
pick. The first Empty Removed deleted A; after removing B and restarting, the identical request
deleted B too (`asset.state` then returned `unknown asset`). Both source hashes remained unchanged.
[Exact requests and answers](../artifacts/v01-audit/retry-reproduction/requests-and-answers.jsonl),
[summary](../artifacts/v01-audit/luxforge-audit-retry-repro.log),
[isolated reproducer](../artifacts/v01-audit/luxforge-audit-retry-repro.py).

Sources: [owner request cache](../crates/luxforge-core/src/api/owner/requests.rs),
[journal](../crates/luxforge-core/src/library/journal.rs),
[permanent deletion](../crates/luxforge-core/src/api/owner/library/remove.rs).
The misleading comment claiming every cached method was restart-safe has been corrected.

### O02 — P2: source.check can clear a known byte mismatch using metadata alone

[Availability checking](../crates/luxforge-core/src/library/availability.rs) compares file identity
and length. In-place changes preserving both can be reported Available, even after preparation
has fingerprint-confirmed Changed. Later preparation/export still verifies the fingerprint and
refuses wrong bytes: no wrong-photo render or source overwrite was found.

**Worth fixing, with a bounded verification policy.** Preserve a known Changed result unless
bytes are verified; decide whether explicit source.check performs streamed integrity verification
or only metadata presence. Automatically hashing every archive on watcher paths is not a
proportionate release patch. Acceptance: same-inode/same-length corruption, known-Changed
recheck, repaired bytes, concurrent locator change, and bounded cancellation/memory.

### O03 — P2: shared model-resource storage has only per-owner transfer exclusivity

[Resource installation](../crates/luxforge-core/src/capabilities/resources.rs) uses deterministic
staging and a per-user final directory, but serializes only within one catalog owner. Two catalogs
can truncate/append/remove the same staging files, race final publication, or both pass a stale
quota check. Hashes prevent corrupt bytes being admitted as pinned; they do not prevent lost
installs and excess quota.

**Worth fixing before shared downloads are qualified.** Use a cancellable resource-root lock on
the worker, recheck installed state and quota after acquisition, and hold it through publication,
removal and cleanup. Unique staging alone does not solve final-directory/quota races. Test two
owners installing the same and different near-quota resources, install versus remove, and a
cancelled lock waiter. Deferred because it is a shared lifecycle change, not a safe leaf patch.

### O04 — P2: post-rename errors are reported like unpublished writes

[Atomic file publication](../crates/luxforge-core/src/atomic_file.rs) renames, then syncs the
directory. If that sync fails, the target has visibly changed despite an ordinary error. A grant
revocation can consequently be written without cancelling dependent jobs; a retry sees no
change and can skip cancellation again. Settings side effects have the same boundary. The helper's misleading rollback comments have been corrected; its outcome API remains unchanged.

**Worth fixing as a coherent durability outcome.** Distinguish not-published from
published-but-durability-unconfirmed, reconcile visible state and required cancellation/events,
and still report the durability failure. Do not suppress the error or pretend a blind rollback
restores durability. Add a post-rename sync-failure seam and test retries. Deferred to avoid
changing every durable-write caller inconsistently during a release audit.

### O05 — P2: global permission revocation cancels only the current owner's jobs

[Permission handling](../crates/luxforge-core/src/capabilities/host/permissions.rs) writes a shared
grant file but cancels only its local jobs. Already granted work in another owner can send after
revocation; its [context](../crates/luxforge-core/src/capabilities/context.rs) checks a captured
cancel token. Newly admitted work reads the revoked state.

**Worth fixing before claiming cross-instance revocation.** Revalidate before sends and propagate
grant changes to in-flight job controls without adding an always-on owner polling loop. Test two
catalog owners with a gated send and revoke from the other. This shares O03's cross-process
lifecycle concern, but needs its own acceptance; an install lock alone cannot solve it.

### O06 — P2 candidate: hard vignette precision boundary needs device qualification

For a white 20 × 20 stage with amount -100, midpoint 65, roundness 0, feather 0, the f64 reference
radius at (6,1) is just below 0.65 while a stepwise f32 evaluation of the shader is just above its
narrowed threshold. Eight symmetric pixels are predicted to switch white to black. That would
violate aggregate pointwise tolerance on this legal small stage. The same coordinates occur in
a 6020 × 6020 photograph; no whole-photo aggregate failure is inferred from eight pixels.

**Worth a dedicated GPU regression before release; runtime failure is not yet established.**
The existing [vignette device test](../crates/luxforge-app/src/app/gpu_colour_tests.rs) does not
cover midpoint 65 at this shape. Run the exact case against actual shader readback and the
whole-frame reference. If confirmed, qualify robust shared edge semantics or a narrowly declared
reference fallback. Do not widen tolerance, change the oracle or disable broad GPU ranges based
only on arithmetic simulation; near-zero positive feathers also deserve coverage.

## Architecture, duplication and dead-code decisions

- Keep the UI-independent command service, immutable recipe snapshots, transactional history and
  source verification. The reviewed export publication paths refuse replacement of originals;
  no original-modification defect was established. Avoid replacing working ownership boundaries
  with a generalized graph or a new async framework for v0.1.
- Put invariants at every durable writer, not only forward planners. F01/F02 demonstrate the
  practical value: shared validation covers ordinary commands and undo/redo. Audit future
  journal item types against their inverse writes.
- Carry immutable identity across asynchronous work, including errors. F03/F05 were missing
  identity, not a need for additional polling or reloading all document state.
- Global files require global lifecycle coordination. O03/O05 show the limit of per-owner lanes;
  O01/O04 show why mutation outcome and publication point must be explicit. These are the main
  architectural follow-ups, ahead of cosmetic splitting of large files.
- Keep GPU/reference implementations and independent oracle fixtures distinct. Similarity there
  provides verification value. Select/loupe caches and evidence journeys also have different
  ownership and acceptance contracts; no safe, high-value consolidation was established.
- No speculative dead-code sweep. Reviewed `allow(dead_code)` examples hold native callback
  lifetimes, GPU retirement state, macro-generated identifier helpers or test/qualification
  seams. `MenuTarget` is used and the preview `never()` panic is a test sentinel. Removal would
  add risk without demonstrated benefit.
- Correct the architecture's stale unsafe-boundary inventory and Tokio description to match
  manifests. Preserve leaf-crate FFI boundaries; this review does not qualify every native
  callback or vendor implementation.
- Dependency pins and automated advisory/license policy passed with the repository's existing
  scoped exceptions. This does not complete the explicitly deferred manual licence/native/asset
  review or waive exception expiries.

## Performance-rules checklist

1. No new original reads, hashes or decodes in editor interactions. Merge retry tests explicitly
   check no new input reads. Signing hashes package files on the release tool's path.
2. No new full-frame allocation. UI changes add identity/one-generation state; server shutdown
   retains at most the existing connection cap. Production prompt capture is removed. Native
   conditioning validates sizes before allocation (at most two fields, 2^28 f32 values per field);
   admission preflights headers/length without allocating payloads. Index collection charges its
   existing file/folder limits before growing its queues.
3. No point query, validation or no-op check renders a frame.
4. The owner gains bounded tree ancestry/sibling validation, not pixel work. Watch rebuilds run
   on the watcher worker. Large directory-tree recovery remains a platform cost to qualify.
5. Existing recipe tasks now carry their entry. Stale results are discarded without an extra
   asset/history/preview/upload request. Preference failure recovery uses its existing reread.
6. No new periodic timer, polling subscription or idle wake loop. Watch root addition explicitly
   wakes pending delivery; shutdown explicitly wakes retained sockets.
7. No new image cache. Signing adds bounded extraction/tree hashing; it is deliberately extra
   release admission work. No hit-rate, latency or memory improvement is claimed without data.
8. Native 24 MP before/after editor-performance was not run on this headless host. UI timing,
   watcher recovery at scale and native inference cost remain unqualified.
9. The Contrast equation is preserved but its numerically unstable small-slope evaluation is
   replaced on CPU/GPU and the f64 oracle. Independent high-precision equation fixtures and the
   pre-fix failing regression qualify CPU semantics without widening tolerance; native GPU
   readback and full corpus acceptance remain required. Other fixes use focused state/API/codec/
   native-parser tests, and rendered UI acceptance remains outstanding.

# Bundled RAW native source

This crate builds its native code from the source files in `vendor/` at compile time. The vendored trees are pristine snapshots. `build.rs` copies librtprocess into Cargo's `OUT_DIR`, applies `patches/librtprocess-local.patch` with exact context matching, and compiles that staged copy. An upstream update that no longer matches the patch fails the build explicitly. LibRaw is also staged in `OUT_DIR`: `patches/libraw-arw6.patch` applies with exact context and `patches/sony_arw6.cpp` adds the upstream Sony Compressed HQ decoder. RawSpeed and pugixml are compiled unpatched. It does not download code, load a system LibRaw, use OpenMP, or call LibRaw's `dcraw_process` output converter. The `build.rs` selects LibRaw source, librtprocess's RCD, Markesteijn, and border routines, and RawSpeed's library sources except `common/Common.cpp` (its stdout log sink, replaced by the adapter's) with pugixml. Compiler/runtime toolchains are still required to build the application; clean Windows and Linux packages are not yet verified.

The source selection is pinned in the directory names and `build.rs`; changing a bundled file must be reviewed as a dependency update, with the local patch rebased separately. The build deliberately excludes LibRaw's `postprocessing_ph.cpp` and `write_ph.cpp` alternative stubs, because they duplicate functions in the selected decompressor and writer sources, and RawSpeed's `common/Common.cpp` (below); no Adobe DNG SDK source is copied. RawSpeed's tests, fuzzers, benchmarks, utilities, documentation, CMake files, CI and the rest of `data/` are not copied. For an independent local integrity check of a vendored directory, list every file under it, relative to it with `/` separators and sorted by that path, as JSON objects `{"path": …, "sha256": …}` holding each file's lowercase hex SHA-256; serialize that array with Python's `json.dumps(entries,sort_keys=True,separators=(',',':'))` and take the SHA-256 of the UTF-8 text. SHA-256 of those serialized pristine inventories: LibRaw `4186672bc6edcde428f2097064bb0c851e2b9b76620c7a1ab5f821e0650c080e` (104 files); librtprocess `6cf59b4c87d170e62f8475075360027f0fd9e118186e777255ddc168a3591aa9` (33 files); RawSpeed `37f690ef89889b955caa667ca30a39be33b5a8c295dbc741beb22cd5efffb680` (255 files, 1,980,131 bytes); pugixml `50388cf41147b5383c8894c47a8fcff844051cba17d24e2f2d63320dbded3de0` (5 files, 426,576 bytes). ### RawSpeed build

`build.rs` compiles 88 of RawSpeed's 89 library sources and `pugixml.cpp` into one static library, `luxforge_rawspeed`, in a `cc` build of its own, separate from LibRaw's C++17 flags: `-std=c++20`, `NDEBUG` (upstream's Release build type), `PUGIXML_NO_XPATH` (RawSpeed reads cameras.xml through the DOM only), `-fvisibility=hidden -fvisibility-inlines-hidden` (upstream's presets; not passed to MSVC) and `cc`'s `warnings(false)` (`-w`), plus `cc`'s target and Cargo-profile defaults. There is no `-march`/`-mtune`, so code is generated for the target's baseline CPU. No OpenMP, zlib or libjpeg is enabled, so RawSpeed decodes serially and deflate and lossy JPEG DNG are unsupported. RawSpeed's CMake-generated `rawspeedconfig.h` is replaced by the hand-written [`native/rawspeed/rawspeedconfig.h`](native/rawspeed/rawspeedconfig.h), which configures upstream's `src/config.h.in` as a CMake `BINARY_PACKAGE_BUILD=ON` build would (64-byte cache line, 4096-byte page and large page), with `HAVE_PUGIXML` and `HAVE_CXX_THREAD_LOCAL` and without `HAVE_OPENMP`, `HAVE_ZLIB`, `HAVE_JPEG` or `RAWSPEED_STANDALONE_BUILD`; this commit generates no other configuration or version header. The crate's adapter, [`native/rawspeed_adapter.cpp`](native/rawspeed_adapter.cpp), is a second library, `luxforge_rawspeed_adapter`, with the same language and preprocessor settings and the compiler's `-Wall -Wextra`; it includes the vendored and configuration headers as system headers, so their warnings are not reported against it. The configuration header uses GCC/Clang attributes unconditionally, so a Windows build needs clang-cl rather than MSVC's `cl`; native Windows is unverified.

`data/cameras.xml` is compiled into the adapter as a byte array (generated into `OUT_DIR` from the vendored file) and parsed with pugixml's `load_buffer` on first use behind `std::call_once`, into one immutable `CameraMetaData` that lives for the process. RawSpeed's own `CameraMetaData(const char *)` reads a file and its `addCamera` is private, so the adapter's subclass fills the public camera tables from the embedded bytes with the same rules: one `Camera` per `<Camera>` node and one per alias, the first entry kept for a duplicate make, model and mode, and CHDK modes indexed by their filesize hint. Nothing is read from disk or the environment. RawSpeed's unpacking path does not use that file's white, black, crop or colour values. Explicit source-attributed matrices in the Luxforge catalog are separate calibration data. The camera-table fill prints nothing.

RawSpeed's only log sink, `rawspeed::writeLog`, is the one definition in upstream's `src/librawspeed/common/Common.cpp`, and it prints errors and warnings to standard output, where the `luxforge-json` CLI writes its JSON. `build.rs` leaves that one file out of the RawSpeed build (it asserts the file exists, so an upstream move fails the build), and the adapter defines `rawspeed::writeLog` with the same signature, filtering and message format, writing each message as one line to standard error. The vendored file is unchanged; a crate test pins its SHA-256 (`2d19717b…64e3`) so an update that adds anything to it is reviewed, and another checks, in a child process, that a warning from RawSpeed's own code reaches standard error and nothing reaches standard output.

The adapter's private C ABI decodes borrowed encoded bytes synchronously with `uncorrectedRawValues`, no crop, no bad-pixel interpolation, no stage-1 DNG opcodes and `failOnUnknown`, runs `checkSupport` then `decodeRaw`, and copies a one-component u16 uncropped image of exactly the size the caller expects into the caller's buffer; any other result, and every exception, is a failure with a message. Qualified catalog modes route it through `RawSource::decode`; LibRaw identification and source metadata remain authoritative.

The build does not define `USE_ZLIB`, `USE_JPEG`, `USE_RAWSPEED`, `USE_DNGSDK`, `USE_LCMS`, or an OpenMP flag. The enabled recording modes and required processing capabilities are declared in `data/cameras.json` and backed by the modern-camera evidence manifest; upstream model recognition alone does not qualify rendering. GainMap and WarpRectilinear are parsed and applied by Luxforge's Rust adapter, with interpolation semantics checked against the Adobe DNG specification and SDK source; Adobe SDK code is not bundled. The adapter intentionally retains float headroom outside the specification's per-opcode clipped range, as recorded in its interpretation metadata.

The C ABI in `native/adapter.cpp` is private to this crate. It consumes borrowed Rust-owned source/mosaic/output buffers synchronously, catches C++ exceptions, and returns a status and message. `RawSource::decode` closes LibRaw and drops the encoded byte buffer after copying one bounded u16 source buffer (CFA/monochrome or interleaved RGB). Rust normalizes the mosaic and scales the demosaiced planes; `develop` hands the adapter the normalized f32 mosaic and one Rust-owned planar float allocation it writes directly. The adapter's RCD and one-pass Markesteijn paths use synchronous tile-job callbacks on Rust's shared Rayon pool, run through the crate's refill executor with at most eight jobs at once, the final job on the calling thread. The local patch changes `rcd.cc`, `markesteijn.cc` and the private header for that scheduling boundary, joined cancellation/error propagation, a private test-fault parameter and, in Markesteijn, once-safe CIELab table initialization. For MSVC, the patch moves the callback's fixed array bounds to namespace scope and makes `mytime.h` use the compiler's `_WIN32` macro for its Windows timer. RCD's equations, tile geometry and allocations are unchanged; its OpenMP region and per-tile progress reports are replaced by the job function. An RCD tile reads scratch that earlier tiles left only when it is partial, so each RCD job is a contiguous run of the serial tile raster that begins at a full 194 px tile: up to eight tiles of a full-height row, the row's partial right tiles staying with their full predecessor, and a final job from the last full-height row's last chunk to the end of the frame. Frames without a full tile run one serial job. For Markesteijn, full tile rows retain their left-to-right scratch history, and the final partial row stays with its predecessor in one callback. Small frames run serially through the same admitted callback; X-Trans dimensions below 120 px fail explicitly because the pinned native edge code needs one full tile to initialize its scratch. The final border pass runs only after all worker entries join.

One-pass Markesteijn allocates `(114² × 19 + 128) × 4 = 988,208` explicit scratch bytes per active callback and RCD `194² × 6.5 × 4 = 978,536`. Each development runs at most eight callbacks at once, so its explicit scratch is at most 7,905,664 bytes; the editor runs one development at a time behind the plane gate, and a library caller running several developments at once gets eight lanes for each. Each callback allocates and releases one scratch set; a Z6 frame runs 110 RCD jobs and an Air 2S frame 80 (current per-camera job counts, including Fuji's Markesteijn callbacks, are in [native demosaic parallelism](../../docs/design/native-demosaic-parallelism.md)), so total allocation traffic is larger than the peak. Each callback also uses stack locals, including Markesteijn's `dcolor[3][6]` (72 bytes) and RCD's row buffers (2,984 bytes), plus thread-stack and allocator overhead; the explicit scratch figure is not an RSS bound. Each callback's scratch lives only while its native tile work runs, and is released before any Rayon scope join. Cancellation is checked before every RCD and X-Trans tile and suppresses partial output. The surrounding source worker continues to cap active/pending full-frame work and memory reservations. The local fault mode in the private C ABI is used only by crate tests; production calls pass zero.

## Camera calibration data

The OM-3, Nikon Z50_2 (Z50II) and Nikon Z5_2 (Z5II) `xyz_to_camera` matrices
in `data/cameras.json` are attributed to the RawSpeed contributors'
[camera data](https://github.com/darktable-org/rawspeed/blob/0a4a6fdc2da228c71c39025a2a5647b081042299/data/cameras.xml),
licensed [CC-BY-SA 3.0 Unported](https://creativecommons.org/licenses/by-sa/3.0/).
Each matrix's nine values are transcribed from that model's own entry (OM
Digital Solutions OM-3; `NIKON Z50_2` and `NIKON Z5_2`, 14bit-compressed) and
scaled by 1/10000; no other camera's calibration is substituted. Pinned LibRaw
0.22.2 has no calibration for these three models. That matrix data retains the
upstream license. That source XML has SHA-256
`d67d32beb3acf073a4ecc521daae29545f90bf79270749e9041031dedb89d166`, the same
file as the `data/cameras.xml` now bundled with RawSpeed.
The configured matrix uses the pinned LibRaw coefficient conversion; the GFX100RF and X-E5 matrices come from their own entries in that same pinned
RawSpeed XML, also scaled by 1/10000 with the attribution/license retained in
each profile. Other non-DNG profiles use LibRaw calibration, and DNG profiles use
validated source matrices. Manual license review remains deferred.

## Sony Compressed HQ backport

The pristine LibRaw 0.22.2 vendor snapshot is unchanged. The staged patch
selects Sony ILCE-7M5 identification/calibration from upstream commit
`c05370da7246ecdc690b65f6c1789974cd3ed5c0`, the ARW6 HQ decoder from
`f6b3a5008c04c624b739c0793dce6779ed43e792`, and black/white corrections from
`e419de08001de28ae6988ecb22df47e52b9c5eaa` in
[LibRaw](https://github.com/LibRaw/LibRaw). The added decoder retains its LibRaw
LLC and Jiang Yaogeng copyright headers and the same LGPL-2.1/CDDL license
choice. The local patch has SHA-256
`2fd65028ebb39f1566feba089fce6d09c29966f9ee712018cc27ee9cfc9b27c9`
and the added decoder
`e7dc103273a6680e95ec5f423ac745635b20da9e38c1f49dc18bca1f60de5946`.
The upstream decoder checks estimated working bytes against
`max_raw_memory_mb`; only this decoder receives the owner-approved 1024 MiB
budget. No other decoder or source/pixel/development limit is enlarged.

## Rust JPEG XL dependencies

`jxl-oxide` 0.12.6 (default features disabled, `rayon` enabled) and `jxl-image` 0.13.0
are pinned in Cargo.toml; Cargo.lock pins their transitive `jxl-*` crates. They come from
[tirr-c/jxl-oxide](https://github.com/tirr-c/jxl-oxide), licensed MIT OR Apache-2.0;
preserve the packaged license/copyright notices. No system libjxl is loaded.
The `rayon` feature adds no package: `jxl-threadpool` uses the `rayon` and `rayon-core`
already in the build, and the decoder runs on the process's global Rayon pool, never a
pool of its own. Libjxl 0.11.2 is used only as
an independent developer reference for the sampled S22 DNG. Manual dependency
license and native security review remains deferred.

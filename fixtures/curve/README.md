# Tone curve fixtures

Synthetic-only, small, deterministic oracle data for the Tone curve module's one pointwise unit, the
contract in [the Tone curve design](../../docs/design/tone-curve.md) ("Processing contract", "The
curve `C`", "Frozen tolerance"). Nothing here comes from a photograph. No production code reads it
yet: the module is planned, and its unit is to be checked against every case directly and through
the render path.

## `curve-cases.json`

1,204 cases: 86 inputs under each of the design's 14 named point sets, and 257 samples of each
set's curve. Generated by the independent `f64` reference (`crates/luxforge-reference/src/curve.rs`)
through its generator test, and reloaded and recomputed on every ordinary test run, so the file
cannot drift from the reference without failing the build:

```sh
# regenerate (only after an intended, documented change to the reference)
cargo test -p luxforge-reference --test studies -- --ignored regenerate_committed_curve_case_fixture
# re-verify (runs by default)
cargo test -p luxforge-reference --test studies curve::
```

Structure:

- `point_sets` — by name, the `points` (`[x, y]` pairs exactly as the design lists them) and the
  set's `peak_slope`, the largest value of `C'` on any segment of its span, computed exactly from
  each segment's quadratic derivative. `peak_slope` is `null` when it is not finite in `f64`: only
  `subnormal`, whose first segment's secant overflows and is evaluated as linear. It selects the
  tolerance class below.
- `cases` — `name` (`{set}/{input}`), `set`, `input_linear_rgb` and `expected_linear_rgb`: the
  unclamped linear-sRGB output of the unit at full `f64` precision. Every input value is
  `f32`-representable, so the tolerance measures the unit and not the input cast.
- `samples` — by set, `[x, C(x)]` for `x = i / 256`, `i` in `0..=256`: what the planned
  `query.sample-curve` answers for those points, to `1e-12`.

| Input group | Count | What it covers |
| --- | --- | --- |
| `ramp-00` to `ramp-64` | 65 | Greys whose encoded luminance runs over `[-0.5, 2.0]` in 64 steps, decoded and cast to `f32`: the unit-slope tails below black and past white, the flat holds and every segment |
| `black` … `white` | 8 | The corners of the unit cube: black, the three primaries, their three complements and white |
| `black-quarter` … `white-quarter` | 8 | The same corners scaled by `0.25` |
| `near-black-chroma-1`, `-2` | 2 | `(3e-4, 1e-5, 1e-5)` and `(2e-4, -1e-4, 3e-4)`: the luminance-ratio branch just above the `1e-6` threshold, one with a negative channel |
| `negative-luminance-1`, `-2` | 2 | `(-0.1, 0, 0)` and `(0.2, -0.1, 0.1)`: negative luminance through the lower tail |
| `over-white` | 1 | `(1.5, 1.2, 0.9)`: the upper tail |

| Point set | What it isolates |
| --- | --- |
| `identity`, `identity-3` | The exact identity map, two and three points: the output is the input |
| `midtone-lift`, `s-curve`, `inverse-s` | Ordinary interior points |
| `lifted-black` | `C(0) = 0.1`: the floor-subtracted reconstruction |
| `cut-white` | A lowered white point |
| `inner-span` | The flat holds inside `[0, 1]` beyond the span |
| `wiggle-16` | Sixteen points, alternating secants, a lifted black |
| `flat-pair` | An exactly flat segment |
| `steep-600` | A segment of peak slope 600 between two flat ones, whose knot slopes are all zero |
| `collapsed-4eps`, `collapsed-1e-8` | Two knots `4 · f64::EPSILON` and `1e-8` apart |
| `subnormal` | A knot at `1e-310`: a non-finite secant, evaluated as a linear segment |

## Declared precision

- **The reference is exact to the contract** in the design, computed in `f64` with no intermediate
  clamping. Values are `serde_json`'s shortest round-trippable representation.
- **Reload agreement**: the committed values agree with a fresh computation within `1e-12` relative
  (plus `1e-12` absolute), which covers only `powf` differences between platforms.
- **Production tolerance** ([frozen tolerance](../../docs/design/tone-curve.md#frozen-tolerance)):
  for a set whose `peak_slope` is at most `64`, production agrees with `expected_linear_rgb`
  within `1e-5 + 1e-5 * abs(reference)` per channel in linear light and within one output code.
  For a steeper set (`peak_slope` above `64` or `null`), production lies per channel within the
  range of `luxforge_reference::curve::curve_pixel_with_input_error` at `-2^-20` and `+2^-20`,
  widened by that forward tolerance, and stays finite and monotone on the grey ramp.

## What is not here

No photograph-derived colour, no rendered images and no pixel buffers (the unit is pointwise, so a
buffer proves nothing a pixel does not), and no 8-bit expected outputs: quantization belongs to the
host's output boundary, not to this unit.

# Presence fixtures

Synthetic-only, small and deterministic, prepared for the [frozen Presence
study](../../docs/design/presence-study.md), which the production `luxforge.presence` module is checked against. Nothing
here is generated from a real photograph and no private original is committed. As of this
task no production code reads these files: they exist so the later `luxforge.presence`
module has an oracle it cannot influence.

Both files are generated by, and re-checked against, the independent `f64` reference in
`crates/luxforge-core/tests/reference/presence.rs`:

```sh
cargo test --package luxforge-core --test presence_reference \
    -- --ignored generate_presence_fixtures
```

`presence_fixtures_match_reference` and `measurements_match_reference` (not ignored, and so
part of `cargo xtask check`) reload the committed files and recompute every value from the
same reference, so a silent drift between these files and the frozen formulas fails the
build instead of going unnoticed.

## Images are specs, not pixel buffers

Neither file stores an image. Each case names a deterministic `ImageSpec` — a step edge, an
encoded-domain sinusoid, an 8-bit quantised ramp, uniform noise, a multi-scale textured
patch, a linear grey ramp, or a synthetic hazed scene — from which the exact input is
rebuilt. Noisy specs draw from one 64-bit LCG, `x <- x * 6364136223846793005 +
1442695040888963407`, value `(x >> 11) / 2^53`, so a production implementation can rebuild
byte-identical inputs from the spec alone.

Every case also records `long_side`, the **stage** long side the radii scale by, which is
deliberately not the fixture's own long side: a fixture is a small region of a large stage,
and Presence's radii belong to the stage. `long_side: 6000` gives the production radii of a
24 MP photograph; `long_side: 24` exercises the minimum-radius path where every radius
rounds down to 1.

## `cases.json`

Ten oracle cases on 24 × 24 images, each holding the input spec, the stage long side, the
three amounts and the full linear-sRGB `f64` output, row-major, unclamped, computed in the
frozen unit order (dehaze, then texture, then clarity).

| Case | Image | Stage | What it pins |
| --- | --- | --- | --- |
| `patch-texture-plus100-stage6000` | tinted textured patch | 6000 | Texture at full positive gain on multi-scale content |
| `patch-texture-minus100-stage6000` | tinted textured patch | 6000 | Texture's band removal |
| `patch-clarity-plus100-stage6000` | tinted textured patch | 6000 | Clarity's reduced base where the base radius exceeds the reduced grid, so every box read is edge-clamped |
| `patch-clarity-minus60-stage6000` | tinted textured patch | 6000 | An intermediate amount, so the gain mapping is pinned away from its endpoints |
| `patch-all-stage24` | tinted textured patch | 24 | All three units at the minimum-radius path |
| `step-texture-plus100-stage6000` | step edge | 6000 | Texture's edge-awareness collapsing the band at a strong edge |
| `step-clarity-plus100-stage24` | step edge | 24 | Clarity at the minimum reduced radius |
| `haze-dehaze-plus100-stage6000` | hazed scene, `t` 0.35 → 0.8 | 6000 | The atmospheric-light estimator with fewer reduction pixels than its own minimum count, and the model inverse |
| `haze-dehaze-minus100-stage24` | hazed scene | 24 | The forward (veil-adding) branch |
| `haze-all-stage6000` | hazed scene | 6000 | The three units composed in their frozen order |

The images are small enough that Clarity's and Dehaze's neighbourhoods exceed them, so these
cases deliberately exercise the edge-clamped and degenerate paths as well as the ordinary
one. They are an exactness oracle, not a visual demonstration.

## `measurements.json`

The 76 figures quoted in the study note: step-edge overshoot and halo width for Texture and
Clarity at ±100 on three step fixtures, band-gain tables for both units, the maximum 8-bit
code step introduced on a quantised ramp, noise amplification at three amplitudes, haze
recovery error for a constant and two ramped transmissions, and the measured `f32`-versus-
`f64` guided-filter error at each frozen radius.

## Declared precision

- **These fixtures versus the reference**: `1e-12` absolute, which absorbs the JSON float
  round trip only. A larger difference means the frozen formulas changed and the files must
  be regenerated deliberately.
- **Production versus the reference**: `2e-4 + 2e-4 * |reference|` in linear light, and at
  most one output code of difference after quantization. The
  [study](../../docs/design/presence-study.md#frozen-tolerance) records how that number was
  estimated from the measured `f32` filter error and states that no `f32` production
  implementation exists yet to verify it against.
- **Tiled versus whole-frame**: exact. A tiled production run that reads each output tile
  plus the units' declared halos must reproduce the whole-frame reference bit for bit, up to
  float summation order within a box window.

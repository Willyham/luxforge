# Colour mixer fixtures

Synthetic-only, small, deterministic oracle data for the frozen colour mixer unit described in
[the mixer study](../../docs/design/mixer-study.md) and required by the
[Presence, colour mixer and vignette design](../../docs/design/presence-mixer-vignette.md). Nothing
here comes from a photograph; no private originals are committed. As of this task no production
code reads these files: the mixer module does not exist yet, and this is the reference a later
implementation is checked against.

## `mixer-cases.json`

414 cases: 46 inputs under 9 parameter sets. Generated by the frozen f64 reference
(`crates/lightwell-core/tests/reference/mixer.rs`) through its generator test, and reloaded and
recomputed on every ordinary test run, so the file cannot drift from the formulas without failing
the build:

```sh
# regenerate (only after an intentional, documented formula change)
cargo test --package lightwell-core --test mixer_reference -- --ignored generate_mixer_fixtures
# re-verify (runs by default)
cargo test --package lightwell-core --test mixer_reference
```

Structure:

- `range_order` — the eight hue ranges in wheel order (`red`, `orange`, `yellow`, `green`, `aqua`,
  `blue`, `purple`, `magenta`). Every parameter array is indexed in this order.
- `parameter_sets` — named settings of the twenty-four sliders, each array holding one value per
  range in `[-100, 100]`. A case references a set by name so the file stays small and readable.
- `cases` — `name`, `input`, the `parameters` set name, and `expected_linear`: the unclamped linear
  sRGB output of the mixer at full f64 precision.

An `input` is either `{"kind": "srgb8", "rgb": [r, g, b]}` (8-bit codes decoded through the standard
sRGB transfer function before the unit runs) or `{"kind": "linear", "rgb": [r, g, b]}` (a linear
sRGB triple given directly, used for the hue wheel and the out-of-gamut cases, which no 8-bit code
represents).

| Input group | Count | What it covers |
| --- | --- | --- |
| Range centres | 8 | The sRGB reference colours whose Oklab hues define the range centres: each is exactly one range's centre, where that range's weight is 1 and every other range's weight is 0 |
| Achromatic ramp | 6 | Codes 0, 32, 64, 128, 192, 255: invariance under every slider |
| Near-black chroma | 3 | sRGB `(2,2,6)`, `(6,4,2)`, `(3,5,3)`: the partially-ramped region just below the chroma edge |
| Hue wheel | 24 | Oklab `L = 0.6` at chroma 0.05, 0.12 and 0.20, every 45 degrees: continuity and the weight blend between centres |
| Skin-like patches | 3 | sRGB `(255,219,172)`, `(224,172,140)`, `(141,85,36)`, the same patches the [colour study](../../docs/design/basic-colour.md) uses |
| Out-of-gamut linear | 2 | `[1.5, 0.5, 0.2]` and `[1.5, -0.1, 0.7]`: the no-clamping gamut policy |

| Parameter set | What it isolates |
| --- | --- |
| `neutral` | The exact identity |
| `red_hue_plus_100`, `aqua_hue_minus_100` | One hue slider at each extreme, in the narrowest and widest gap |
| `blue_saturation_minus_100`, `green_saturation_plus_100` | Chroma to zero and doubled |
| `orange_luminance_plus_100`, `purple_luminance_minus_100` | The luminance response at both extremes |
| `orange_combined` | Three sliders of one range at once (hue -50, saturation +50, luminance -50) |
| `all_ranges` | All twenty-four sliders non-zero (hue +25, saturation -40, luminance +30) |

## Declared precision

- **This reference is exact to the equations frozen in
  [the study](../../docs/design/mixer-study.md)**, computed in f64 with no intermediate clamping.
  `expected_linear` is `serde_json`'s shortest round-trippable representation, so reloading it
  reproduces the same doubles.
- **Reload agreement**: the checked-in values must agree with a fresh computation to within
  `1e-12` absolute. The margin covers only libm differences in `cos`, `sin`, `powf` and `cbrt`
  between the platform that generated the file and the platform re-verifying it.
- **Production tolerance** (for the later module task, not tested here): production must agree
  with this reference within `1e-5 + 1e-5 * abs(reference)` in linear light, and output codes may
  differ by at most one at a quantization boundary — the same tolerance
  [the colour study](../../docs/design/basic-colour.md) freezes, for the same reasons.

## What is not here

No photograph-derived colour, no rendered images, no per-pixel buffers (the mixer is pointwise, so
a buffer proves nothing a pixel does not), and no 8-bit expected outputs: the unit's contract is a
linear-float one and the quantization boundary belongs to the host, not to this unit.

# Working on Luxforge

Luxforge is an open-source, non-destructive desktop photo editor for macOS, Windows and Linux, built around a small, fast core that people, programs and agents operate equally. Read this file before changing anything. It is the source of truth for what we are building and how we work.

## Pillars

Every change is measured against these.

1. **Originals are sacred.** Source files are never modified. Edits are data: ordered layers in a recipe, with immutable history. Never silently discard an incompatible catalog, recipe or edit; fail explicitly and keep the data.
2. **Everything is programmable.** Every operation a person can perform has a discoverable, schema-described programmatic equivalent through the same command service. A GUI gesture is never the only interface. UI and API parity is verified, not assumed.
3. **Fast, bounded and honest.** Responsiveness, bounded memory and image correctness are architectural requirements, not later tuning. The GPU is the renderer of record and correctness is a declared tolerance against the whole-frame CPU reference, measured on the corpus ([GPU-first](docs/design/gpu-first.md), owner 2026-10-04); bit identity is asked of the reference, not of the GPU. Measure on photo-sized inputs before claiming a performance result. The rules that keep this true are in [performance rules](docs/engineering/performance-rules.md).
4. **Small core, deliberate extension points.** The core owns recipe transactions, history and undo, shared invariants and bounded services. Tool modules own their validation, controls and processing through those APIs. Prefer lazy, optional modules and measure before splitting the core into loadable binaries. External module loading is required later, not now.
5. **Open source, first on the owner's Mac.** GPL-3.0-or-later project code and open-source dependencies. Target the owner's M4 MacBook Pro first; keep Windows and Linux portable, and distinguish VM or headless functional checks from native GPU evidence.
6. **Prove it.** Claims about behavior come with evidence: exact-buffer tests for the reference renderer, reference-buffer tests within the declared tolerance for the GPU, correlated state, logs and captures for UI, and recorded measurements with their scope. A skipped check is not a pass.
7. **Beautiful defaults, familiar feel.** A small, focused workspace with sensible defaults. Lightroom Library and Develop are a familiarity reference, not a feature checklist or a rendering target; its sliders' responses are the exception, so a value does about what the same value does there ([Lightroom alignment](docs/design/lightroom-alignment.md), owner 2026-10-06).

## Current state

S0 through M4 are accepted, and the [Develop workspace](docs/design/develop-workspace.md), [Basic adjustments and the histogram inspector](docs/design/basic-and-histogram.md), initial continuous RAW editing for the Nikon Z6, Fujifilm X100VI and the supplied DJI Air 2S DNG ([design](docs/design/initial-raw.md)), [instant previews](docs/design/instant-preview.md), [popular camera support](docs/design/popular-camera-support.md) and [RawSpeed unpacking](docs/design/rawspeed-unpack.md), [Presence, the colour mixer and the vignette](docs/design/presence-mixer-vignette.md), [presets](docs/design/presets.md), [masking](docs/design/masking.md), the state panel's [Performance section](docs/design/performance-panel.md), [shared module capabilities](docs/design/module-capabilities.md), [settings and feature flags](docs/design/settings-and-flags.md), the person's [preferences](docs/design/preferences.md) and [UI themes](docs/design/ui-themes.md) with Omarchy import are implemented and verified on the M4 Mac. The [live-session CLI](docs/design/live-cli.md) (`luxforge-ctl`), [copy and paste settings](docs/design/copy-settings.md) and [Auto tone](docs/design/auto-tone.md) with per-photo Auto presets are implemented and verified on an M2 Mac; their M4 and corpus qualification remains open. The [catalog](docs/design/catalog.md) (the Select workspace: browse, pick, develop, with Locate and resolving missing originals) is implemented on the recorded defaults of its proposals, which await the owner. The post-consolidation programme is complete, including the roadmap groundwork for MCP, the library and Locate, Corrections and new geometry modules. Next: MCP and full-editor verification. JPEG export is delivered; GPU-first portability remains open: the retained hosted lavapipe journeys await a passing run, while Linux no-adapter checks, release acceptance and packaging pass. Everything is v0: no public compatibility framework, release planning, cloud, accounts, marketplace or generalized node graph. Status, scope and evidence for every area live in [feature status](docs/features.md); see the [roadmap](docs/plan.md) for what comes after.

## How we work

- **Read first.** For any milestone or tracked task, read the relevant spec and its plan in [tasks](tasks/README.md). Work that can start now is listed in the roadmap's [ready to implement](docs/plan.md#ready-to-implement) section, with the minimum model each task needs; re-review a plan against current `main` before implementing it, as that section describes. Product context lives in [decisions](docs/decisions.md).
- **Plan proportionately, for execution.** Substantial features, milestones and other coordinated multi-step work start with a Markdown design (behavior, scope, constraints, acceptance and settled decisions or explicitly delegated choices) and a validated JSON task plan. Resolve material product questions while creating or revising the plan, in a concise batch where possible. The handed-off tasks are concrete work an implementer can complete from that context, not instructions to ask questions, seek approval or reconfirm the plan. Research, reviews, diagnostics, documentation maintenance and small contained changes do not need a task plan unless asked or already tracked. See the [planning conventions](tasks/README.md#planning-for-execution).
- **Stay in scope.** Do what was asked. A planning request does not authorize implementing the plan. Do not prebuild future features or placeholder controls.
- **Maximise autonomous work.** Use existing decisions and authorization; leave routine implementation details to the implementer and record delegated choices explicitly. Ask the owner during planning only about consequential tradeoffs whose answers materially change scope or behavior. Never turn silence into a decision. Deliver a useful working feature first where possible, with ordinary correctness tests alongside it; move owner review, calibration, reference perfection and other deferrable gates to the end, with no dependency back into that delivery. Genuine prerequisites name the required output and why it is needed. External inputs or final approval must not hold up independent implementation or preparation. An unforeseen consequential scope change calls for a focused plan update, while unaffected work continues.
- **Verify proportionately, and last.** While building, run only the tests for the code you are changing (`cargo test -p CRATE FILTER`). The whole suite, `check` and `verify` are for finished work, not the edit loop: `quick` once before handing off any change, `rendered` at integration points, `full` before a milestone claim ([when to verify](docs/engineering/development.md#when-to-verify)). Timing runs (the `timing` tier, `editor-performance`, `editor-latency`, `measure`) wait until feature work is complete, unless the task itself is performance work. UI or image changes need a real rendered check with correlated state and logs. Changes under `crates/` answer the performance-rules checklist.
- **Keep automated app launches in the background.** A real launch of the editor takes focus like any application; an automated one never does. On macOS, `verify`, `cargo xtask smoke`, `hardening` and `measure` launch a hidden window in a background-only bundle, so a run neither activates nor appears, whatever else is happening on the desktop. For ad hoc API/render checks use `cargo xtask develop --background` with an isolated catalog or evidence directory. Do not launch the GUI binary directly or activate it through UI automation for routine tests. Foreground interaction checks require the owner's explicit request.
- **Keep docs current, not historical.** When behavior or scope changes, update the spec, [feature status](docs/features.md) and [user guide](docs/user-guide.md). Document current behavior and outstanding work only: no change logs, run logs or planning history. Record a lesson only when something was tried and did not work. Never document a proposed command as if it exists.

- **Use the shared compiler cache.** On macOS and Linux, agents run Cargo through `tools/cargo-cached` (for example, `tools/cargo-cached test -p CRATE FILTER` and `tools/cargo-cached xtask verify --tier quick --output NEW`). Use ordinary Cargo to bootstrap the pinned tool if it is missing. The pinned local sccache installation is shared across worktrees; target directories stay separate. The wrapper preserves incremental compilation, disables native preprocessor shortcuts and path normalization, and caches only registry leaf Rust libraries, bypassing workspace Rust and all direct/transitive procedural-macro consumers. Never enable cache sloppiness or point worktrees at one target directory. If diagnosing a cache issue or using another compiler wrapper, set `LUXFORGE_CACHE_OFF=1`; see [cache setup](docs/engineering/development.md#build-caches-and-worktrees). Windows uses ordinary Cargo until a native wrapper is verified.

## Engineering rules

- Framework widgets hold no authoritative editing or catalog logic. Business rules live in the UI-independent core.
- Every user-facing operation extends the command registry and its schema. Add the API with the feature.
- Decode, render, import and export never block the UI thread or the catalog owner thread. Bound queues and memory; cancel stale work.
- Back image behavior with exact fixtures for the reference renderer and with the reference comparison, within the declared tolerance, for the GPU. Test source preservation and recovery, not just successful rendering.
- Pin dependencies. Manual license, native and asset reviews are deferred by the owner; keep notices and never claim an audit is complete.
- **Current shapes only.** Luxforge is pre-release and breaking changes are expected. Support only the latest catalog, recipe, API and module shapes. Do not maintain migrations, compatibility shims, old-version fixtures or historical parity checks. Internal format markers reject unsupported data explicitly without rewriting or discarding it; use a new catalog when necessary. Current UI/API correctness and exact image tests still apply. Missing or disabled providers report affected edits; they never silently omit an effect from a render or export.
